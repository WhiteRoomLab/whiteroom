## 7. 管理画面・認証・監査

### 7.1 決定済み

- 管理画面を提供する。
- 管理ユーザーを登録・管理できるようにする。
- **ログイン履歴**と**アクティビティログ**を実装する。
- これらを監査にも利用できるようにする。

### 7.2 提案段階

- 権限モデル：ロールは `admin`・`editor`・`author`・`viewer` の4つ（仮に決めた。7.3）。
- ユーザー作成方法：管理者による招待・登録（一般公開の自己登録は行わない）。招待の仕方と最初の管理者は7.3。
- 著者プロフィールとの紐付け：ログインアカウントに著者プロフィールのID（任意。6.6.3・7.3）を持たせる（決定済み。6.1）。投稿の `author` の初期値や、自分のプロフィールを編集できるかの判断に使う。
- 認証：サーバーサイドセッション認証（作った。7.3・9.6）、WebAuthn / PasskeyまたはMFA（まだ無い。7.3の「まだ無いもの」）。
- 記録対象：ログイン成功・失敗、権限変更、記事編集・公開・削除、設定変更、バックアップ操作など（仮に決めて作った。7.4。バックアップ操作は、記録の形だけで、書く口が、まだ無い）。
- 監査操作と実データ変更を、可能な限り同一トランザクションで記録（保存先は、変更と同じコミットに記録を書き、記録の無い書き込みを断る。7.4）。
- 監査ログへの通常UIからの編集・削除操作を禁止（保存先の口に、記録を書き換える口と消す口は無い。7.4）。
- ハッシュチェーンと独立した検証値の保管を組み合わせて改ざん検知を強化（ログごとの鎖と、鎖の頭の保存先の外への書き出し。7.4）。
- 管理画面の到達経路をlocalhost / Unixドメインソケット / VPNなどに限定する（案。9.6の「経路とオリジン」）。

**注意：** 保存先（3.4）に監査データを記録するだけでは、OS・DBの管理権限を奪われた場合の改ざん防止にはならない。改ざん耐性や証跡の外部退避は別途設計が必要。7.4の「改ざんの検知」に、見つけられるものと見つけられないもの（限界）と、運用で使う外への退避（journald の封・別のマシンへの転送）を書いた。
