## 1. プロジェクトの目的

### 1.1 決定済み

- **WordPressの代替となる自作CMS**を開発する。
- **想定利用者は、現在WordPressを利用しているユーザー**とする。
- **多言語サイトを対象とする。**
- WordPressと、その実行基盤（PHP、Webサーバー、MySQL系DBなど）およびプラグインを含む依存関係の運用負荷・脆弱性リスクを減らしたい。
- **AWSに依存しない、Linuxへインストールして運用できるソフトウェア**とする。特定クラウドのマネージドサービスを必須条件にしない。
- 予約システム、ECなどの**複雑な動的Webアプリケーション機能は対象にしない**。
- 最低限の動的機能として、**管理画面、管理ユーザーの管理、お問い合わせ**を実装する。
- 公開コンテンツは、編集・管理する原本から**静的ビルドでHTML等を生成して公開**する方式とする。
- ストレージ方針として、候補のうち **「SQLite + CMS専用Content Store」** を採用する。#63 の判断で、SQLiteは、自作の保存の層に替えることにした（決定済み。3.1・3.5）。

### 1.2 方向性として合意

- **一般閲覧者向けの公開サイトを原則静的にし、動的処理を管理画面・お問い合わせに限定する。**
- 公開されるサイトの表現品質はWordPressに匹敵する水準を目指す。ただしWordPressの全機能・プラグイン互換は目標にしない。
- 最初は**開発者がファイルでテーマを定義し、管理者が記事や固定ページを編集**する構成から始める。
- 将来的に、テーマ設定・レイアウト・サイト全体のビジュアル編集へ段階的に拡張可能な設計を意識する。
- CMSの実行時依存と攻撃対象領域を小さくする。whiteroomは、外部のサードパーティのGoのモジュールを使わない。依存の数え方と扱いは、次のとおり。
  - `golang.org/x/...` は、依存に数えない（標準ライブラリと同じに扱い、使ってよい）。
  - 仕様から作った第三者のデータは、依存に数えない。実行ファイルに入れるもの（`internal/nfc` のUnicodeの表、`internal/html` の文字参照の表）も、テストだけが使うもの（yaml-test-suite・html5lib-tests・web-platform-tests）も、取得元・版・ライセンスの表示を、データの横に置く。
  - 開発・テスト・CIの道具（Nixの開発シェル、golangci-lint、テストで動かすNginxとApache、libwebpとlibvpxのツール、cgoのCコンパイラー、e2fsprogs）は、製品の依存と分けて、数えない。
  - 実行するときに、外部のコマンドを動かさない。
  - 標準ライブラリで安全に作れないもの（WebAuthnなど）は、まず、自分で作る・仕様を変える・機能をやめることと比べる。それでも要るものだけを、メンテナーが理由とともに認めた例外にし、理由とともに構想書に書く。危険な暗号は、自分で作らない。いまの例外は、替えるまでの `github.com/mattn/go-sqlite3`（3.4・3.5）。
  - 外部のモジュールは、`golang.org/x/...` も、足す前に、そのたびに、理由を添えてメンテナーに確かめる（決定済み。13章）。

### 1.3 対象としないもの（現時点）

- 予約、在庫、決済などの業務アプリケーション機能
- WordPressプラグインとの完全互換
- あらゆるサーバーサイド言語を実行できる汎用アプリケーション基盤
- 独自のコンテンツDSL・コンパイラ（コンテンツは型付きのモデルで表現する）
- コメント機能（WordPressの既存コメントの移行も含む）
