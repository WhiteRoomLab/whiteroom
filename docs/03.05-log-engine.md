### 3.5 保存の層のエンジン（案）

Goの標準ライブラリだけで作った保存の層：エンジン（`internal/logdb`）と、その上の保存先の自作の層（`internal/store`。3.4）。SQLiteから替えた判断は、下記の「判断」と13章。エンジンは、DBのデーモン（`whiteroom-db`。3.6）の中で動く：データのディレクトリを開くのは、デーモンだけで、エンジンの書くプロセスは、デーモン1つ。エンジンの判断と計算だけの部分を、Ada/SPARKの核にすることは決めたが、まだ作っていないので、この節は、Goのエンジンの形のまま（3.6。核が変える所は、下記の「デーモンで変わる所」）。

**目的と状態**

- 設計：CAS（内容のSHA-256で指す、書き換えないオブジェクト）・表（キーと値）・追記するだけのログ（正本）・チェックポイントを、1つのコミットと復旧の仕組みの上で動かす（別々の3つのデータベースにはしない）。
- 作らないもの：SQL、JOIN、クエリの最適化、ディスクの上の汎用のB-tree、高度なMVCC（版を持つ同時実行の制御）、グループコミット（いくつかのコミットを1回の同期にまとめること）、ネットワークのファイルシステムへの対応。
- 規則：この節の規則は、どれも案（3.4の規則も、案。3.4の初め）。

**構成**

この節では、`internal/logdb` をエンジン、エンジンを使う `internal/store` の保存の層を自作の層と呼ぶ。メッセージの例は、データのディレクトリが `/srv/data` のときのもの（3.4と同じ）。

| パッケージ | 内容 |
| --- | --- |
| `internal/logdb` | エンジン（この節の形・コミット・復旧・読み手・保守・バックアップ） |
| `internal/logdb/vfs` | ファイルシステムの口（ファイル・ディレクトリ・同期・名前の変更・`flock(2)` のロック）と、Goの `os.Root` の上の実装（外を指すシンボリックリンクは、たどらない）。書き込みと同期を数える口（`vfs.Count`）も |
| `internal/logdb/simfs` | テストの模擬のファイルシステム（下記の「テスト」） |
| `internal/logdb/dmlog` | dm-log-writes の記録を読んで、再生する（下記の「テスト」） |
| `internal/store` | 保存先（3.4）。保存の層は、自作の層。デーモンのクライアント（`internal/dbclient`）の上に載り、エンジンは開かない |
| `internal/dbserver`・`cmd/whiteroom-db` | エンジンを開くプログラム：DBのデーモン（3.6）。本番で、エンジンを開くのは、これだけ |

データのディレクトリ：

| 名前 | 内容 |
| --- | --- |
| `files/` | 原本（3.4の「データのディレクトリ」） |
| `logdb/` | エンジンのディレクトリ |
| `logdb/lock/entry`・`logdb/lock/readers`・`logdb/lock/writer` | 空のファイル。`flock(2)` のロックにだけ使う（下記の「ロック」） |
| `logdb/log/<世代>-<番号>.log` | ログのセグメント。世代と番号は、1からの数を、小文字の16進数16桁で書く（`0000000000000001-0000000000000001.log`） |
| `logdb/objects/<16進数2桁>/<16進数64桁>` | ファイルに置くオブジェクト（置き場所Bのものと、混合の大きいもの。下記の「オブジェクトの置き場所」）のファイル。名前は、中身のSHA-256 |
| `logdb/objects/<16進数2桁>/.tmp-<ランダムな16進数16桁>` | 書いている途中のオブジェクト。プロセスが途中で止まったときと、同期に失敗したときだけ残る |
| `logdb/checkpoint` | チェックポイント（下記）。名前の変更で置き換える |
| `logdb/.tmp-checkpoint-<ランダムな16進数16桁>` | 書いている途中のチェックポイント。プロセスが途中で止まったときだけ残る |
| `logdb/head` | 書くプロセスが同期したログの終わり。ほかのプロセスの読み手のためのもの（下記の「ほかのプロセス」） |

規則：

- モード：ディレクトリは0700、ファイルは0600で作る。あるもののモードは、変えない（3.4と同じ）。
- 知らない名前：`logdb/` の中の、上の表に無い名前は見ない。`logdb/log/` の中の、セグメントの名前でないものは、壊れているとして拒む（`/srv/data/logdb/log/x: corrupt: not the name of a segment`）。シンボリックリンクと、種類の違うもの（ディレクトリであるべきところのファイルなど）は、3.4と同じ形のメッセージで拒む（`/srv/data/logdb/head: symbolic links are not allowed` など）。
- 作る：エンジンは、ロックのファイル・初めのセグメント・`head` を作り、セグメントと `head` と、ディレクトリを同期する（デーモンの `whiteroom-db init` が `files/` と `logdb/` を作る順と、書き手が表の版を書くことは、3.4の「データのディレクトリ」）。

正本と、そこから作るもの：

| もの | 正本か、作るものか | 作り直し |
| --- | --- | --- |
| ログ（`logdb/log/`） | 正本。すべてのコミット（表の変更・ログの中のオブジェクト・監査イベント） | - |
| オブジェクトのファイル（`logdb/objects/`） | 正本（ファイルに置くオブジェクトの中身） | - |
| 原本（`files/`） | 正本（3.4） | - |
| チェックポイント | 作るもの（あるコミットの後の状態） | ログから作れる。壊れていれば使わず、ログを世代の初めから読む |
| メモリの状態（表・ハッシュからオブジェクトの位置への索引・イベントの数） | 作るもの（エンジンの中の索引） | 開くたびに、チェックポイントとログから作る |
| `head` | 作るもの（読み手のための写し） | 壊れていれば、書くプロセスが開くときに書き直す |

- チェックポイントは、無くてもよい：世代のログは、いつも、状態のすべてを持つ（古いログを消すのは、保守モードの圧縮だけで、圧縮は、新しい世代の初めに、状態のすべてを書く。下記の「保守モード」）。そのため、チェックポイントは、開くのを速くするだけで、無くても、壊れていても開ける。
- いまの版：保存先のいまの版（`documents`）は、版の履歴から決まるものだが、表として持ち、ほかの表と同じく、ログで確定する（3.4の `documents` と同じ）。エンジンの中の索引（ハッシュから位置、文書からいまの版）は、開くたびに作り直す。

自作の層の表は、3.4の「表」と「索引」。

**ファイルの形**

どのファイルも、形の版は1。整数は、大きさの決まったものはリトルエンディアンで、決まらないものはuvarint（Goの `encoding/binary` の可変長の形。必要より長く書いたものは拒む）。CRCは、CRC-32C（Castagnoli）。

| ファイル | 印（ASCIIの8バイト） | 見出し |
| --- | --- | --- |
| セグメント | `whrm-log` | 64バイト |
| チェックポイント | `whrm-ckp` | 64バイト |
| `head` | `whrm-hed` | 64バイトの欄が2つ（128バイト） |
| オブジェクトのファイル | `whrm-obj` | 16バイト |

本体：

| 位置 | バイト | 内容 |
| ---: | ---: | --- |
| 0 | 1 | 種類：1 コミット、2 ベース（世代の初めのレコード。下記の「保守モード」）、3 ベースの終わり |
| 1 | 8 | レコードの番号。コミットは、前のコミットの番号に1を足したもの（1から、世代をまたいで続く）。ベースとベースの終わりは、前の世代の最後のコミットの番号 |
| 9 | - | コミット：変更の並び。ベース：部分の番号（0から）と、変更の並び。ベースの終わり：ベースのレコードの数・キーの数・オブジェクトの数・イベントの数・次のイベントの番号。番号と数は、どれもuvarint |

変更の並びは、変更の数（uvarint）と、変更ごとに、1バイトの種類とその中身：

| 種類 | 変更 | 中身 |
| ---: | --- | --- |
| 1 | キーを置く | 表の番号（uvarint。1以上）・キーの長さ（uvarint。4096まで）・キー・値 |
| 2 | キーを消す | 表の番号・キーの長さ・キー |
| 3 | ログの中のオブジェクト | SHA-256（32バイト）・値（オブジェクトの中身） |
| 4 | ファイルのオブジェクト | SHA-256（32バイト）・大きさ（uvarint） |
| 5 | 監査イベント | イベントの番号（uvarint）・コミットの番号（uvarint）・値 |

値は、1バイトの封筒の後に、0（そのまま）なら長さ（uvarint）と中身。1（暗号化）なら、鍵のID（uvarint）・12バイトのノンス・長さ（uvarint）・暗号文と認証タグ（下記の「イベント・操作のID・暗号化の封筒」）。

チェックポイント（64バイトの見出しと、本体）：

| 位置 | バイト | 内容 |
| ---: | ---: | --- |
| 0 | 8 | 印 `whrm-ckp` |
| 8 | 4 | 形の版 |
| 12 | 4 | レコードS（チェックポイントの状態の、最後のレコード）のCRC |
| 16 | 8 | 世代 |

- 本体：次のイベントの番号と、イベントの数。表の数と、表ごとに（番号の順）、表の番号・キーの数・キーごとに（キーの順）キーの長さ・キー・値。オブジェクトの数と、オブジェクトごとに（ハッシュの順）、SHA-256・置き場所（1 ログの中：セグメント・位置・大きさ。2 ファイル：大きさ）。数と長さは、どれもuvarint。ファイルの大きさは、64+B。
- Sは、コミットか、ベースの終わり。コミットが1つも無ければ、書かない。

規則：

- 確かめる順：印と版があって、版が新しければ、大きさやCRCより先に拒む（新しい版は、見出しの大きさも変えるかもしれない。`/srv/data/logdb/log/0000000000000001-0000000000000001.log: format version 2, newer than this program knows (1)`）。それから、大きさ（`short file`）、印（`not a segment of whiteroom's log` など）、版0（`bad format version 0`）、CRC（`bad header CRC`。`head` の欄は `bad slot CRC`）、欄の中身の順に確かめる。新しい版のファイルは、どれも、何も変えずに拒む。
- 名前と見出し：セグメントの見出しの世代と番号は、ファイルの名前と同じでなければならない（違えば `the header names generation 1, index 3` のような理由で拒む）。
- 厳しい読み方：読んでから書き直すと、同じバイト列になるように読む。必要より長いuvarint（`bad uvarint`）、0でない予約のバイト（`nonzero reserved bytes`）、余るバイト（`trailing bytes`）、知らない種類（`unknown record type 4`・`unknown op 6`）は、拒む。
- ソルト：置き場所A（下記）では、文書のJSONが、レコードの中に入る。JSONの中に、正しいレコードに見えるバイト列を書けると、書きかけの末尾（下記の「復旧」）の後ろに正しいレコードがあることになり、開くのを拒ませることができる。レコードのCRCに、セグメントごとのランダムなソルトを入れるので、ソルトを知らなければ、そうしたバイト列は作れない。
- 上限：キーは4096バイトまで（`key too long: 5000 bytes (max 4096)`）。本体は268435456バイト（256MiB）まで。コミットのレコードの本体は、それより10バイト少ない268435446バイトまでで、これが1回の `Update` の上限になる（`the transaction is too large: 300000000 bytes (max 268435446)`）。圧縮は、どの変更も、部分の番号（uvarintで、10バイトまで）の付くベースのレコードに書き直すので、その分を空けておく。

**コミット**

1回の `Update` のコミットは、次の順に書く。

1. 変更が無ければ、何も書かない（キーの無いものを消すのも、変更にしない）。
2. 監査イベントに、状態の次のイベントの番号から順に番号を付け、レコードを作る。上限を超えれば、何も書かずに失敗する。
3. 置き場所B（下記）の、状態に無いオブジェクトのファイルを書く：`objects/<16進数2桁>/` を作り（あってもよい）、その中の一時ファイルに、見出しと中身を1回で書き、同期して閉じ、オブジェクトの名前に変える。それから、名前がディスクにあると知らないディレクトリ（作ったものも）を使ったときは、`objects/` を1回同期し、使ったディレクトリを、それぞれ1回同期する。
4. いまのセグメントにレコードが1つ以上あり、このレコードで `SegmentBytes`（既定は64MiB）を超えるなら、次の番号のセグメントを作り（見出しを書いて同期し、`log/` を同期する）、そこに書く。セグメントより大きなレコードは、新しいセグメントに1つだけ入る。
5. レコードを、セグメントの終わりに、1回の書き込み（`WriteAt`）で書き、セグメントを同期する。この同期が成功したときが、コミットの確定点。
6. 状態を公開する（それからの `View` が見る）。`head` を書き（同期しない）、ログがチェックポイントの後に `CheckpointBytes`（既定は64MiB）増えていれば、チェックポイントを書き始める（下記の「チェックポイント」）。

規則：

- 1つのコミットは、1つのレコード：セグメントの同期は、コミットごとに1回（グループコミットはしない）。`Update` は、プロセスの中で1つずつ動くので、同期していないレコードは、いつも、最後の1つだけ。これが、下記の「復旧」で、書きかけの末尾と、壊れたものを分けられる理由。
- 参照するものが先：オブジェクトのファイルと、その名前（ディレクトリの同期）は、それを指すレコードより先にディスクに置く。原本は、それを使うメディアの文書の `Update` より先に書く（3.4の「原本は先に書く」）。そのため、無いオブジェクトや原本を指すコミットはできない。途中で止まると、使われないファイルが残る（下記の「保守モード」の回収で消す）。
- あるディレクトリ：作ろうとしたディレクトリが既にあっても、名前がディスクにあると知らなければ、`objects/` を同期する（`Update` の失敗や、強制終了したプロセスが作ったディレクトリは、名前がまだディスクに無いことがある。原本も同じ。3.4の「原本」）。
- 確定の後に公開：公開する状態は、復旧がレコードから作るのと同じコードで、レコードを書く前に作り、確定点の後に公開する。そのため、`View` は、確定したコミットだけを見る。

**失敗の扱い**

| 失敗 | 扱い |
| --- | --- |
| 確定点の前の書き込みの失敗（EIO・ENOSPC・短い書き込み）と、ファイルやディレクトリを作る・名前を変える失敗 | 書いたかもしれないレコードを切り戻し（セグメントを前の終わりで切り、同期する）、一時ファイルと、見出しを書けなかった新しいセグメントを消す（名前を変え終えたオブジェクトのファイルは残り、回収で消す）。その `Update` は、そのエラーで失敗し、保存先は使い続けられる（ENOSPCなら、空きを作れば、次の `Update` は書ける） |
| 切り戻しの失敗（切ること・その同期） | 止まる（下記） |
| 同期の失敗（レコード・オブジェクトのファイル・`objects/` とその下のディレクトリ・新しいセグメントと `log/`・開くときの同期・圧縮と回収の同期） | 止まる：その `Update` と、後のすべての `Update` が、`ErrFailed`（`the store has stopped after a sync failed; restart the machine before opening it again`）で失敗する。`Close` は、何も書かない |
| 圧縮の、ベースの終わりのレコードを書き始める前の失敗（同期のほか） | 古い世代のまま、使い続けられる（作りかけの新しい世代は、開くときに使わず、次の圧縮か回収で消す） |
| 圧縮の、ベースの終わりのレコードを書き始めてからの失敗 | 止まる（新しい世代ができたかが分からないので、古い世代に書き続けられない） |
| 修復（`Apply`。下記の「保守モード」）の失敗（案。#144） | 圧縮と同じ道（同じコード）で扱う。ベースの終わりのレコードを書き始める前の失敗（同期のほか）：直す前のまま（開けなかった保存先は、開けないまま。作りかけの新しい世代は、開くときに使わず、次の修復か回収で消す。ただし、下記の、ほかの世代を消す所のクラッシュを除く）。同期の失敗と、ベースの終わりのレコードを書き始めてからの失敗：止まる。ベースの終わりのレコードの後の、チェックポイント・ファイルを消すことの失敗：そのエラーを返し、保存先は、直した状態で、使わないファイルが残る：もう1度、修復を動かすと、それを消し、行もイベントも、足さない。`head` が、無かった保存先で、`head` を作ることの失敗：そのエラーを返す。保存先は、新しい世代が完全だが、`head` が無く、前の世代のセグメントと、前のチェックポイントが残るので、`Open` は、直す前と同じに、`head: missing file` で拒む：もう1度、修復を動かすと、計画の `Recovery` に `head` と前のチェックポイントが、`Remove` に前の世代のセグメントが出て（`recover:` と `remove:` の行）、`head` を作り、それらを消し、行もイベントも、足さない |
| 回収で、ファイルを消す失敗 | そのエラーを返す。保存先は使い続けられる |
| チェックポイントの失敗 | 止まらない。一時ファイルを消す。自動のものは数え（`Stats`）、`Checkpoint` と `Close` は、エラーを返す |
| `head` を書く失敗 | 何も止めない（数えるだけ。同じ欄を書き直すので、もう1つの欄は正しいまま） |
| 開くときの読む失敗 | 開くのが失敗する。ファイルを何も変えない（末尾を切らない） |

- 同期をやり直さない：同期に失敗すると、Linuxは、ディスクに書けなかったページを、書いたものとして扱う（汚れていない印を付ける）ことがあり、後の同期は、それを書かずに成功する。そのため、失敗した同期を、もう一度呼んで信じることはしない。失敗した `Update` が残るかは分からず、開き直した後は、すべてあるか、無いかのどちらか。
- 再起動してから開き直す（F1）：同期に失敗した後、マシンを再起動せずに開き直すと、エンジンは、ページキャッシュにだけある変更（ディスクには書かれない）を、ディスクにあるものとして、続きを書く。その後にクラッシュすると、最後のレコードより前が壊れたログが残る（開くのを拒むか、チェックポイントから開けても、`Verify` と `Events` が失敗する。テストでは、黙って中身が変わることは無かった）。そのため、`ErrFailed` の文で、マシンを再起動してから開き直すように伝え、開くときの同期（最後のセグメントと `log/`）の失敗も、`ErrFailed` にした。プロセスを再起動するだけ（systemdの自動の再起動など）では足りない。再起動したかは、エンジンではなく、デーモンが確かめる：止まったときに、データのディレクトリに、マシンの起動ごとのID（Linux の boot ID）を書いた印（`stopped`）を残し、同じ起動の間は、`serve`・`compact`・`gc`・`accept-break`・`repair` が、エンジンを開く前に、何も変えずに断る（何も変えない確かめの `check` と、`-apply` の無い `repair` も、断る。案。#68 の計画への答え（2026-11-23）で決めた。3.6の「同期の失敗」。下記の「運用の制約」と「残る危険」。6.12の129）。印を残すのは、エンジンの `ErrFailed` のすべて（開くときの同期の失敗も、切り戻しの失敗も、圧縮の確定点の後の失敗も）。デーモンは、書く要求に、`the store has stopped after a sync failed; restart the machine before starting the daemon again` で答える（3.6の「同期の失敗」）。
- 修復の、ほかの世代を消す所で止まったとき（案。#144 のレビューの後）：傷んで、中の1つのセグメントを欠く、完全でない新しい世代（修復も圧縮も、自分では、そうは残さない：新しいセグメントごとに `log/` を同期し、消すときは、最後のセグメントから消す）があると（`Open` は、それを拒む）、新しい修復は、その世代を、最後のセグメントから消す（圧縮と同じ）。その途中でクラッシュすると、欠けた所を越えて消えた後に、`Open` が、直す前の世代 G を、そのまま開くことがある：修復の行は無く、G のコミットした状態で、圧縮が、完全でない世代を消す途中で止まったときと同じ。`Open` は、壊れた状態を、開かない（前と同じエラーか、G か、直した保存先のどれか）。もう1度、修復を動かす。
- 原本（F2）：原本の同期の失敗は、3.4の「原本」の「同期の失敗」：エンジンの同期の失敗と同じ印で、デーモンの全体が止まり（原本の保存だけでなく、文書の書き込みも）、同じ起動の間は、デーモンが起動しない（3.6の「同期の失敗」）。

**チェックポイント**

- 中身：ある公開した状態（すべての表、オブジェクトの位置、イベントの数）と、その最後のレコードS（世代・番号・セグメント・位置・CRC）。
- 書き方：一時ファイル（`.tmp-checkpoint-<ランダムな16進数16桁>`）に、本体を流しながら書き（CRCも求める）、見出しを書き、同期して閉じ、`checkpoint` に名前を変え、エンジンのディレクトリを同期する。そのため、クラッシュで壊れることは無い（前のものか、新しいもののどちらか）。
- いつ書くか：ログが前のチェックポイントの後に `CheckpointBytes`（既定は64MiB）増えたときに、`Update` の後に、バックグラウンドで書く（`Update` は待たない）。`Close` は、最後のコミットのものを書く（動いているものを待ってから）。`Checkpoint` を呼んでも書く。前のものより新しい状態のものだけを書く。
- ログと組にする：開くときに使うのは、ログの、チェックポイントの示す位置に、その番号とCRCの正しいレコード（コミットか、ベースの終わり）があるときだけ（下記の「復旧」）。
- ログを消さない：チェックポイントは、セグメントを消さない（ログを消すのは、保守モードの圧縮だけ）。

**復旧**

書くプロセスが開くとき（`Open`）は、次の順にする。

1. ディレクトリの形（`lock/`・ロックのファイル・`log/`・`objects/`・`head`）を確かめ、ロックを取る（下記の「ロック」）。
2. チェックポイント：無ければ使わない（`none`）。壊れていれば（大きさ・印・CRC・読めない本体）、使わずに、ログを初めから読む（`damaged: <理由>`）。新しい版なら、拒む。`log/` の名前より先に読む（読み手も、同じ順に読むため。下記の「ほかのプロセス」）。
3. `log/` の名前を読み、世代ごとに分ける。
4. 世代：完全な世代のうち、いちばん新しいものを使う。世代1は、いつも完全。2からの世代は、ベースの終わりのレコードが正しければ、完全。それより新しい、完全でない世代（圧縮の途中で止まったもの）は、使わずに残す（次の保守で消す）。チェックポイントが、完全でない世代を指していれば、拒む（`/srv/data/logdb/checkpoint: corrupt: names generation 3, which is incomplete`）。
5. その世代のセグメントは、1から続いていなければならない（`/srv/data/logdb/log: corrupt: missing segment 2 of generation 1`）。
6. 初め：その世代のチェックポイントが、ログと組になれば、その状態から始め、その後のレコードを読む。チェックポイントのセグメントより前のセグメントは、読まず、同じセグメントの、チェックポイントのレコードより前のレコードは、確かめない。組にならなければ、拒む（`/srv/data/logdb/checkpoint: corrupt: the log does not have sequence 9 at /srv/data/logdb/log/0000000000000001-0000000000000002.log offset 352`）。その世代のチェックポイントが無ければ、世代の初めから読む。
7. 読む：どのレコードも、正しく、番号が続かなければならない。正しくない初めのレコードは、下の表のとおりにする。
8. ここまでは、ファイルを何も変えずに決める。それから、自作の層の表の版を確かめ（3.4の「エンジンと設定」）、決めた変更（書きかけの末尾を切る・作りかけのセグメントを消す）をし、最後のセグメントと `log/` を、いつも同期し、`head` を書く。

正しくない初めのレコード（位置X）の扱い：

| 見つけたもの | 最後のセグメント | それより前のセグメント |
| --- | --- | --- |
| 途中で終わる・長さが範囲の外・CRCが合わないレコードで、その後ろ（8バイトの倍数の位置）に、CRCが合って、番号が後のレコードが無い | 書きかけの末尾：Xで切る | 拒む |
| 同じで、その後ろに、CRCが合って、番号が後のレコードがある | 拒む（`a valid record follows at offset 416` のような理由） | 拒む |
| CRCが合うのに、0で埋めるところが0でない・本体を読めない・番号が違う | 拒む（書き終えたレコードなので、切ると、新しい版のプログラムの書いたコミットを捨てるかもしれない） | 拒む |
| 見出しが正しくなく、64バイトの後がすべて0 | 作りかけのセグメント：消す（世代1のセグメント1は、拒む） | 拒む |
| 見出しが正しくなく、64バイトの後に0でないバイトがある | 拒む | 拒む |
| 読む失敗（EIOなど） | 開くのが失敗する（切らない） | 同じ |

拒むときは、ファイルと位置と理由を付けたエラーにする（`/srv/data/logdb/log/0000000000000001-0000000000000001.log: corrupt at offset 352: truncated record`）。拒んだときは、ファイルを何も変えない。

規則：

- 分けられる理由：同期していないレコードは、いつも最後の1つだけ（上記の「コミット」）。そのため、クラッシュで残る正しくないレコードは、最後のセグメントの最後のものだけで、正しくないレコードの後ろに正しいレコードがあることは、クラッシュでは起きない（壊れている）。正しい過去のレコードを、黙って捨てることは無い。圧縮のベースは、ベースの終わりの前に同期するので、ベースの中の書きかけは、世代が完全でないことになる（その世代を使わない）。
- 開くときの同期：切るものが無くても、最後のセグメントと `log/` を同期する。強制終了したプロセスが、ページキャッシュにだけ残したレコードや、作ったセグメントの名前を、続きを書く前に、ディスクに置くため。この同期の失敗も `ErrFailed`（上記の「失敗の扱い」）。
- 残る曖昧さ：最後のレコードが、クラッシュでなく、ディスクの故障などで壊れたときも、書きかけの末尾に見えるので、切る（そのコミットが無くなる）。チェックポイントが、これを狭める：`Close` は、最後のコミットのチェックポイントを書くので、閉じた後に最後のレコードが壊れれば、チェックポイントと組にならず、拒む。最後のレコードが、チェックポイントのレコードより後にあるとき（クラッシュの後など）だけ、この曖昧さが残る。
- チェックポイントの前は読まない：チェックポイントから開くときは、そのセグメントより前のセグメントを読まず、同じセグメントの、チェックポイントのレコードより前のレコードも確かめないので、そこが壊れていても、開くときには分からない（`Verify`・`VerifyEach`・`Inspect` の `Check`（`whiteroom-db check`）・`Events` が見つける。`Events` と圧縮は、そこで失敗する：`whiteroom-db compact` も、古い世代のイベントを、ログのすべてから読むので、同じ傷で失敗し、保存先は、古い世代のまま開ける。2026-11-23に、`main`（`6983bcb`）で、チェックポイントを書いた25のセグメントの保存先の、1つ目のセグメントの1バイトを書き換えて確かめた：開けて、保存先の `Check`（`whiteroom doctor`）の `engine` は、ファイルと位置を示し、`compact` は失敗し、`gc` は動いた。直す道は、保守モードの修復（`whiteroom-db repair`。下記の「保守モード」。#144）か、写しから戻すこと。6.12の131）。
- `head`：`head` は、読み手のためのもので、書くプロセスは、ログを終わりまで読み、`head` を使わない。壊れていれば（大きさ・正しい欄が無い）、書き直す。新しい版なら、拒む。

**スナップショット**

- メモリの状態：表ごとの、書き換えない木（キーの順の木で、変えるときは、変わる道だけを写す）と、ハッシュからオブジェクトの位置への索引と、数。公開した状態は書き換えず、`Update` が新しい状態を作って、取り替える。
- `View`：関数が初めに読んだときの状態を、終わりまで見る（3.4と同じ）。ロックを取らず、`Update` を待たない。
- `Update` の中：読む操作（キーの `Get`・`Scan`・`ScanAfter`、オブジェクト）は、同じ `Update` の書いたものを見る。
- `ScanAfter`：`Scan` と同じで、後のキー（表のキーでなくても、接頭辞で始まらなくてもよい）より大きいキーだけを、キーの順に渡す。後のキーは、表にあっても、渡さない。後のキーが空でも、空のキーは渡さない（最初のページは、`Scan`）。木を、そのキーの所まで降りるので、前のキーを通らない。読むだけで、ファイルの形も、書く道も、変えない。デーモンが、`Scan` のページを、位置を覚えずに答えるために足した：続きのページは、前のページの最後のキーの後から読む（3.6の「ファイルの形」）。
- 木の形：キーの優先度を、プロセスごとのランダムな種のハッシュ（Goの `hash/maphash`）で決めるので、細工したキーで、木を偏らせることはできない。
- 監査イベント：メモリには数だけを持ち、`Events` が、ログから読む。
- `Close` の間：`Close` のときに動いている `View` は、終わるまで読める（セグメントのファイルは、最後の `View` が閉じる）。

**ほかのプロセス**

- 読み手（`OpenReader`）：エンジンの読み手は、デーモンの `Backup` だけが使う（デーモンの中で、書くプロセスと同じプロセスに開く。3.6の「保守の口」。6.12の281）。ほかのプロセス（9.2）は、エンジンの読み手を開かず、デーモンの読み手用のソケットで読む（3.6の「接続」）。以下は、エンジンの読み手の規則で、エンジンのテストが確かめる。読み手は、ファイルを書かず、切らず、消さない（同期はする。下記）。`Update` は `read-only transaction` で失敗する。読み手は、`Options.Accept` を渡せば、開くときに、表の版を確かめる（デーモンの `Backup` は渡さない：表の版は、デーモンが開いたときに確かめている。3.4の「エンジンと設定」）。
- `head`：書くプロセスは、コミットのたびに、同期したログの終わり（世代・セグメント・位置・番号・最後のレコードのCRC）を、`head` の2つの欄に、交互に書く（同期しない。作るときと閉じるときだけ同期する）。読み手は、正しい欄のうち、書いた数の大きいほうを使う（書いている途中の欄は、CRCで分かる）。どちらも正しくなければ、1ミリ秒おきに、3回まで読み直す。
- 書くプロセスがあるとき：`head` の示すレコードまでだけを読む。それが、読んだ最後のレコードでなければ、拒む（`/srv/data/logdb/head: corrupt: the log does not match head`）。書いたが、まだ同期していないレコード（失敗すれば、切り戻すもの）は、見ない。開くときに、チェックポイントが `head` より新しいときは、下記の「開くときに読む順」。
- 書くプロセスが無いとき：`lock/writer` を共有で持ち（その間、書くプロセスは始まらない）、ログを、最後の正しいレコードまで、復旧と同じ規則で読む（書きかけの末尾は、そこで終わりとし、切らない）。読んだレコードのセグメントを同期してから、ロックを放す。強制終了した書くプロセスが、ページキャッシュにだけ残したレコードを、見せる前に、ディスクに置くため。
- 開くときに読む順（デーモンの `Backup` の読み手と、エンジンのテストの読み手が、この順に読む）：書くプロセスがあるときに開く読み手は、`head`、チェックポイント、`log/` の名前、セグメントの順に読む。書くプロセスは、その間も書くので、後に読むものは、先に読んだものより新しいことがある。この順なら、先に読んだものの示すレコードは、後に読むものに、かならずある（`head` とチェックポイントは、同期したレコードだけを示す。読み手が開いている間に無くなるのは、同期していないものだけ：書くプロセスが、失敗した `Update` で切り戻すか消すものと、その復旧が切るか消すもの）。`log/` の名前を先に読むと、その後に切り替えたセグメントを示すチェックポイントが、ログと組にならず、壊れていない保存先を拒むことになる。チェックポイントが `head` より新しければ、チェックポイントの状態から始める。`head` の世代の `log/` の名前のうち、`head` とチェックポイントの示すセグメントより後のものは、使わない（名前を読んでいる間に、書くプロセスがセグメントを2つ続けて作ると、ファイルシステムが、後のものの名前だけを返すことがあり、それを、セグメントの抜けとして拒まないため）。その後のセグメントが本当に無ければ、それを読む読み直しが拒む。
- 読み直し：`View`（と `Events`）のたびに、関数を呼ぶ前に、新しく同期したコミットを読む。失敗すれば、関数を呼ばずに、エラーを返す。`head` が、読み手の状態より古いとき（書くプロセスが、`head` を書く前に止まったときなど）は、何もしない（戻らない）。
- セグメントの切り替え：読み手は、次のセグメントに続けて読む。見出しが正しくなかったセグメントは、開いたままにせず、次の読み直しで開き直す（書くプロセスの復旧が消して、同じ名前で作り直すことがあるため）。
- チェックポイントの置き換え：読み手は、開いた後は、チェックポイントを読まないので、置き換えの影響を受けない。
- 世代：読み手が開いている間は、保守モードが動かないので、世代は変わらない。
- 同期の失敗：読み手の同期が失敗すれば、読み手も止まる（`ErrFailed`）。
- 遅れ：書くプロセスの `head` を書く失敗が続く間は、読み手は、その前のコミットまでしか見ない。デーモンの `Backup` は、その位置が、デーモンの最後のコミットより前なら、失敗する（`the engine's head is behind its last commit; take the backup again after the next commit`。3.6の「保守の口」）。

**ロック**

3つのロックのファイル（`lock/entry`・`lock/readers`・`lock/writer`）に、`flock(2)` で、共有か排他のロックを取る。取る順は、どこでも `entry`・`readers`・`writer` で、放すのは、その逆の順。

| 開くもの | `lock/entry` | `lock/readers` | `lock/writer` |
| --- | --- | --- | --- |
| 書くプロセス（`Open`） | 共有。待たない（取れなければ `/srv/data/logdb: maintenance is running`）。ほかの2つを取ったら放す | 共有。待たない。閉じるまで持つ | 排他。`WriterWait`（既定は2秒）まで、10ミリ秒ごとに試す（取れなければ `/srv/data/logdb: another process holds the writer lock`）。閉じるまで持つ |
| 読み手（`OpenReader`） | 共有。待たない。`lock/readers` を取ったら放す | 共有。待たない。閉じるまで持つ | 読み直すたびに、共有で、待たずに試す。取れれば、ログの終わりを読んで同期する間だけ持つ |
| 保守（`Maintain`） | 排他。取り消し（Goの `context`）まで待つ（10ミリ秒から、間を倍にして100ミリ秒ごとまで） | 排他。同じ | 排他。同じ |

- 待つもの：開くもの（書くプロセス・読み手・バックアップ）は、`lock/entry` と `lock/readers` を待たない（保守が動いていれば、すぐに失敗する）。書くプロセスは、`lock/writer` を2秒まで待つ（読み手が、ログの終わりを読む間、持つため）。保守は、3つを順に、取り消しまで待つ。
- だれが使うか：書くプロセス（`lock/writer` を排他で持つ）は、デーモン1つ。読み手の行は、デーモンの `Backup`（と、エンジンのテストの読み手）が使う。保守は、デーモンを止めて動かす `whiteroom-db compact`・`gc`・`accept-break`・`repair`（3.6の「保守の口」）。確かめ（`Inspect`。`whiteroom-db check`）と、修復の読み（`Salvage`。`whiteroom-db repair`）も、保守と同じ3つのロックを、同じに取る。ほかのプロセスは、ロックを取らない：エンジンを開かず、デーモンのソケットで読む（3.6の「接続」）。
- デッドロックしない理由：読み手は、何も待たない。待っている書くプロセスが待つのは、`lock/writer` を持つもの（開いている書くプロセスか、読み手の短い読み直し）で、それらは何も待たない（保守は、書くプロセスが `lock/readers` を共有で持つ間は、`lock/readers` を取れないので、`lock/writer` を持たない）。保守が待つのは、前のロックを持ったままで、次のロックを持つものだけで、それらは保守を待たない。どの待ちにも、上限（2秒か、取り消し）がある。強制終了したプロセスのロックは、カーネルが放す。
- 飢え：書くプロセスは、`lock/writer` を待つ間、`lock/entry` を共有で持つので、開こうとし続ける2つ目の書くプロセスがあると、保守が `lock/entry` を取れないことがある。デーモンは、開けなければ終わり、開き直し続けないので、保守は、デーモンを止めれば、動ける（6.12の135）。
- `flock(2)` の無いシステム：ロックを取るときに失敗する（`cannot lock …: logdb needs flock(2), which windows does not have` など）。

**保守モード**

- 入る（`Maintain`。デーモンの `whiteroom-db compact`・`gc`・`accept-break`。3.6の「保守の口」）：3つのロックを、排他で取り（上記の「ロック」）、書くプロセスとして開き（復旧をする）、渡した関数を動かして、閉じる。動いている間、ほかのプロセスは、開けない（`maintenance is running`）。修復の `Salvage` は、同じ3つのロックを取るが、書くプロセスとして開かない（下記）。
- 圧縮（`Compact`）：いまの状態を、渡した書き直し（`Rewrite`：値を書き換えるか、キーを落とす。オブジェクトを落とす。イベントのデータを書き換えるか、落とす）を通して、次の世代の初めのレコード（ベース）に書く。
  1. ほかの世代のセグメント（前の圧縮が途中で止まって残したもの）を、最後のものから消す（消すたびに、`log/` を同期する）。
  2. 次の世代のセグメント1を作る（見出しの初めのレコードの番号は、いまの最後のコミットの番号S。新しいソルト）。
  3. ベースのレコード（1つが約4MiBの変更。それより大きい変更は1つだけ）を書く：表（番号とキーの順）、オブジェクト（ログの中のものは、古いセグメントから読み、SHA-256を確かめて、中身ごと。ファイルのものは、ハッシュと大きさ）、古い世代のイベント（番号とコミットの番号を変えない）。セグメントが一杯になれば、同期してから、次のセグメントを作る。
  4. ベースを同期し、ベースの終わりのレコードを書いて、同期する。これが、圧縮の確定点。
  5. メモリの状態を、新しい世代のものにし、チェックポイントと `head` を書き、古い世代のセグメントを、最後のものから消して、`log/` を同期する。チェックポイントを書けなければ、古い世代のセグメントを残す（回収で消す）。
- どこで止まっても：古い世代（新しい世代は、完全でないので使わない）か、新しい世代（完全）のどちらかになり、混ざらない。新しい世代のコミットは、S+1から続く。
- いちばん新しい完全な世代を使う理由：ベースの終わりと、新しいチェックポイントの間でクラッシュすると、古いチェックポイントは、古い世代を指す。それを使うと、書き直して消したデータ（個人情報など）が戻り、消すはずの世代に、書き続けることになる。
- 回収（`CollectGarbage`）：いまの世代でないセグメント（最後のものから。消すたびに `log/` を同期する）、`objects/` の中の、状態がファイルに持たないオブジェクトのファイル（圧縮で落としたもの・失敗した `Update` が書いたもの）と一時ファイル、チェックポイントの一時ファイルを消し、変えたディレクトリを同期する。ほかの名前は、残す。
- 保守の中の読みと書き（`Maintenance` の `Events` と `Update`。案。#70 の計画への答え（2026-11-23）で決めた）：`Events` は、イベントを、番号の順に渡す。`Update` は、エンジンの順番を取って1回の書き込みをし、返るときは、同期済み（同期に失敗すれば、何も書かず、`ErrFailed`）。デーモンの規則（3.6の「デーモンが守る規則」）は、保守の `Update` には当たらないので、保守だけが、表 `chains`（3.4の「表」）と、デーモンのイベント（3.6の「印」の 0x02〜0x04）を書ける。デーモンの `whiteroom-db compact` は、これで、鎖の始まりを先に書き、続けて、圧縮の書き直し（`Rewrite.Event`）で、ログイン履歴の1年より古い記録のイベントを落とす（3.6の「保守の口」。7.4の「保持の期間と個人の情報」）。`whiteroom-db accept-break` は、これで、認めた切れ目の行と、そのイベント（0x03）と、印を、1回の書き込みで書く（圧縮はしない：ログは、同じ世代のまま、新しいコミットを持つ）。`whiteroom-db repair` は、修復の `Apply` の足す行と足すイベントで、穴の行と、そのイベント（0x04）と、印を、新しい世代のベースの中に書く（下記の「修復」）。書き直しは、残るイベントの番号を変えない：ベースのレコードは、イベントの番号に欠けがあってよい。
- 書くプロセスが止まっている間にできること（エンジンの口として）：読み手（ログを終わりまで読み、同期する）、バックアップ（読み手として）、保守（読み手も無いとき）、何も書かない確かめ（`Inspect`。保守と同じロックを取るので、読み手も無いとき）。デーモンは、自分が動いている間に `Backup` を使い、保守と `Inspect` は、デーモンを止めて動かす。
- 検出と修復（9.2の `whiteroom doctor`・`whiteroom-db check`・`whiteroom-db repair`。検出と、写しの確かめは作り（#70）、エンジンの修復も作った（#144）。9.4。6.12の131）の制約（案。#70 の計画への答え（2026-11-23）と、#144 の計画への答え（2026-11-25）で決めた）：エンジンは、壊れたものを、黙って直さない。開くときに変えるのは、書きかけの末尾を切ること・作りかけのセグメントを消すこと・`head` を書き直すことと、同期だけ。確かめる口は、3つある。
  - `Verify`：ログをディスクから読み直して、メモリの状態と比べ、すべてのオブジェクトのハッシュを確かめ、最初の問題を、エラーで返す。読み手でもでき、書くプロセスが動いていてもよい（書くプロセスのものは、その間、`Update` を待たせる。デーモンの `Verify` は、これ。3.6の「保守の口」）。
  - `VerifyEach(ctx, found)`：同じ確かめで、問題のすべてを、1つずつ `Problem{Path, Offset, Reason}`（ファイルと、その中の位置と、理由。位置が無いときは -1。理由に、行のキーも値も、オブジェクトのデータも入らない）で渡す。`found` が `false` を返せば、そこで止める。順は、ログ（最初の傷まで読み、そこで止める。その後に読めない所が、まだあるかは分からない）、状態の食い違い（ログを終わりまで読めたときだけ。表ごとに、値の違うキーと、メモリだけ・ログだけにあるキーの数を示し、キーも値も示さない）、状態のオブジェクト（ハッシュの順。ログの傷があっても、読む）。`Verify` は、これの最初の問題で、エラーの型と文は、変えていない。
  - `Inspect(ctx, fsys, o, f)` と、`f` に渡す `(*Inspection).Check(ctx, found)`：どのプロセスも開いていない保存先を、何も書かずに確かめる。保守のロックを、排他で取り（取れるまで、`ctx` の終わりまで待つ）、書くプロセスとして開かない。`f` が動く間、`Open`・`OpenReader`・`Backup` は、`maintenance is running` で、すぐに失敗する。`Check` は、`Open` の復旧（上記の「復旧」）が、変えるもの（書きかけの末尾・作りかけのセグメント）と、使わないもの（完全でない新しい世代のセグメント・壊れたか、古い世代のチェックポイント）と、ログの終わりを指さない `head` を、問題として示し、続けて、`VerifyEach` の問題を、すべて示す。`Open` が拒むもの（チェックポイントとログが組にならない・新しい版のファイルなど）は、1つの問題で、そこで止める。ファイルは読むだけで開き、書く呼び出しを、1つも使わない（書けないディレクトリも確かめる）。クラッシュで止まった書くプロセスの保存先は、`Open` が直すものを持つので、問題として示す（そのとおりに決めた。直す前に示すため）。デーモンの `whiteroom-db check`（3.6の「保守の口」）が、使う。表の版（自作の層）は、確かめない：デーモンの確かめ（`Accept`）は、`Inspect` の中では呼ばない。
  - 修復：ファイルを変える修復（壊れたものを落とす圧縮・回収など）は、保守モードでだけする。正しいコミットを捨てる修復（壊れたレコードから後を切ることなど）は、自動ではせず、操作する人が決める。操作する人が決めるものは、4つ：(1) 直すか、見るだけか：落とすものと失うものを示すだけの動き方があり、何も変えない（`whiteroom-db repair`。`-apply` なし）。直すのは、選んだときだけ（`-apply`）。(2) 直す前のファイル：直すときは、先に、`logdb/` の写しを、決めた場所に取り、それから直す（`-keep DIR`。必須）。(3) 正しいコミットを捨てるか：壊れたレコードより後の、読めるコミットを捨てる切り詰めは、選んだときだけ（`-truncate`）。選ばなければ、何も変えずに断る。(4) 記録として読めないイベントを落とすか：選んだときだけ落とす（`-drop-unreadable-records`）。チェックポイントが覆う傷（開くときには分からない傷）を落とすことは、選びに入れない：チェックポイントの状態は、その傷より後のコミットのものなので、正しいコミットを捨てない。この修復は、下記の `Salvage` と `Apply`（デーモンの `whiteroom-db repair`。3.6の「保守の口」）。ほかに作った保守は、ログイン履歴の古い記録を落とす圧縮（下記）と、読める鎖の切れ目を認める口（3.6の「保守の口」。7.4の「改ざんの検知」）。
- 修復（`Salvage`・`Apply`。案。#144 の計画への答え（2026-11-25）で決めた）：壊れた保存先を、写しから戻さずに、新しい世代に書き直す。読んで決めることと、書くことを、2つの口に分ける。
  - 読む（`Salvage(ctx, fsys, o, f)`）：`Inspect` と同じに、3つのロックを、排他で取り（取れるまで、`ctx` の終わりまで待つ）、書くプロセスとして開かず、読めるものを読んで、`f` に、`Salvager` を渡す。`f` が動く間、`Open`・`OpenReader`・`Backup` は、`maintenance is running` で、すぐに失敗する。`Apply` を呼ぶまで、ファイルは、何も変えない（書く呼び出しを、1つも使わない。書けない木も読める）。`f` の前に、何も変えずに断るもの：新しい版のファイル（`VersionError`）、`log/` の、セグメントの名前でない名前、状態を、推し量らずには作れない保存先（下記の (4)）。`head` が、無いか壊れているのは、断りでなく、計画の問題（`Apply` が、書き直す）。
  - 残す状態：(1) 世代：完全な世代のうち、いちばん新しいもの、か、有効なチェックポイントが指す世代（チェックポイントは、その世代が完全だった証拠なので、ベースの終わりが読めなくてもよい）。(2) チェックポイント：ファイルが有効で、その世代のもので、ログの、その位置に、その番号とCRCのレコードがあるときに使い、その状態から始める。その位置のレコードが読めないとき（閉じた後に、最後のレコードが壊れた保存先。`Open` は拒む）は、チェックポイントだけを使い、その状態を、そのまま取る。別の番号のレコードがあるときは、使わず、世代の初めから読む。(3) その後のレコード：読めるものを、続けて当てはめ、最初に読めないものの前の、コミットの状態で止める。(4) 状態を作れないとき：チェックポイントが使えず、世代2以降のベースのレコードが読めないときは、断る（`<ファイル>: corrupt at offset N: <理由>; the base of generation G cannot be read, and no checkpoint has its state: restore the store from a copy`）。
  - 落とすもの（`RepairPlan`）：(1) スパン：読めないバイトの範囲。欠けたセグメントと、見出しの読めないセグメントは、1つずつ。ファイル・位置・長さと、失うレコードの連番と、イベントの番号（周りのレコードから分かるときだけ）を持つ。傷の後は、次の、枠のCRCが、そのセグメントのソルトで合い、本体が読め、連番が後のレコードの初めから読み、その間が、1つのスパン。傷のバイトが無いのに、レコードが欠けているとき（セグメントが、レコードの境で切れているなど）は、長さ0のスパン。チェックポイントが覆うスパンが失うのは、そのレコードの、イベントだけで、表とオブジェクトは、チェックポイントが持つ。(2) オブジェクト：状態のオブジェクトのうち、データが読めないか、ハッシュが合わないもの。(3) 要らないファイル：ほかの世代のセグメントと、一時のファイル（状態が持たないオブジェクトのファイルは、`Apply` が、回収と同じに消す）。(4) 切り詰め：最初に読めない所が、状態の始まりの後（チェックポイントの後。チェックポイントが無いときは、世代の初めの後）にあり、その後に、読めるレコードがあるとき、それらを落とす（残る状態は、傷の前の、コミットのもの。計画は、残る状態の、次のイベントの番号（`NextEvent`）も持ち、切り詰めのイベントは、それ以降の番号）。読めるレコードが無い、末尾の傷は、スパンで、切り詰めではない：切り詰めだけが、正しいコミットを捨てるので、`Apply` は、`Truncate` が無ければ、何も書かずに断る（`ErrTruncation`）。(5) `Open` が直すもの（書きかけの末尾・作りかけのセグメント・`head` のずれ・使わないチェックポイント）は、計画の `Recovery` に、`Inspect` と同じ文で入り、`Apply` が、新しい世代に、直して書く。
  - 読むもの：残る世代のすべてのレコード（チェックポイントより前も）と、状態のすべてのオブジェクト。`Events(ctx, fn)` は、残るイベントを、番号の順に渡し、`View(ctx, f)` は、残る状態を、読むだけの `Tx` で読ませる（デーモンが、表 `chains`・`meta`・`heads` を読み、監査の穴を決めるため。3.6の「保守の口」）。どちらも、何も変えない。1つのセグメントのバイト列から、どれがレコードで、どこから読めなくなるかを決める部分（`scanBytes`）は、I/O を持たない関数で、3.6の「核の範囲」の、「ログを読むときの判断」に当たる（Ada/SPARKの核は、これを引き取る。修復の進行は、Goに残す。#144 の計画への答え（2026-11-25）で決めた）。
  - 書く（`(*Salvager).Apply(ctx, r)`）：残る状態を、圧縮と同じコードで、次の世代に書く（壊れていない保存先に動かすと、`Compact` と同じレコードと、同じチェックポイントを書く：`TestRepairLikeCompact`）：(1) `head` が、あれば、書くために開く（変えない。開けなければ、何も変えずに断る）。(2) ほかの世代のセグメントを、最後のものから消す。(3) 次の世代のセグメント1から、ベースを書く：表（呼ぶ側が足す行（`Puts`）は、同じ表とキーの行を置き換える）、オブジェクト（失ったものを除く）、残るイベント（`Rewrite.Event` が、落とすか、書き換えたもの）、呼ぶ側が足すイベント（`Events`。残る最後のコミットの連番を持ち、残る状態の、次のイベントの番号から、番号を付ける）。(4) ベースを同期し、ベースの終わりのレコードを書いて、同期する：これが、確定点（圧縮と同じ）。(5) `head` が無ければ作る（名前を、データのディレクトリの同期で、耐久にする）。(6) チェックポイントと `head`。(7) 前の世代のセグメントを消し、状態が持たないオブジェクトのファイルと、一時のファイルを消す。足す行とイベントは、ベースの中にあるので、修復があるときだけ、保存先にある。`Truncate` が無く、計画が切り詰めを要するときは、何も書かずに、`ErrTruncation` を包んだエラーで断る（`Apply` は、使い切らず、`Truncate` をつけて、もう1度呼べる）。`Rewrite` は、`Event` だけを使い、`Value`・`Object` があれば断る。呼ぶ側の行かイベントが、1つで、ベースのレコードに入らない大きさのとき、残る状態に、コミットが1つも無いのに、足すイベントがあるときは、書く前に断る。
  - どこで止まっても：確定点の前は、直す前の保存先（`Open` は、前と同じエラーか、同じ状態。ただし、上記の「失敗の扱い」の、ほかの世代を消す所のクラッシュを除く：`Open` が、直す前の世代 G を、修復の行なしで、開くことがある）、確定点の後は、直した保存先（`Open` が、チェックポイントを使って開く）。`head` が、無かった保存先は、確定点の後も、`head` を作るまで、前と同じエラー（`head: missing file`）で、`Open` が拒む：もう1度、修復を動かす（計画の `Recovery` に、`head` が出る）。圧縮と同じフック（`compact:base`・`compact:base-end`・`checkpoint:synced`・`checkpoint:renamed`・`checkpoint:done`・`compact:checkpoint`・`compact:delete`・`gc:remove`。同じ順。確定点の後のフックは、止めるだけで、`gc:remove` のエラーだけは、回収を止めて、返る）が、`Options.Hook` から呼ばれる。`Salvage` の読みは、フックを呼ばない。
  - 切り詰めの後の、イベントの番号（案）：切り詰めた後の、残る状態の、次のイベントの番号は、傷の前のコミットのものなので、落としたコミットの、イベントの番号は、書き手の、次のコミットから、また使われる。そのため、修復の前の文の「イベント N」（`whiteroom doctor` の問題の行・`whiteroom-db repair` の `drop:` の行）と、修復の後の同じ文の「イベント N」は、別のイベントを指すことがある（写しは、修復前のものなので、前の番号は、写しで読める）。イベントの番号を、保存先の中で持つのは、ログだけで、表の行も、記録の番号も、頭の行も、持たない（読み手への答え（`Events`）が、その場で、番号を返すだけ）。チェックポイントが覆う傷の後は、チェックポイントの、次のイベントの番号から続くので、失ったイベントの番号は、使わない。
- バックアップ（`Backup`）：保存先を読み手として開き（その間、保守は動かない）、そのときの、最後の同期したコミット（位置P）を決める。それから、保存先のバックアップは、原本（`files/`。一時ファイルは除く）をコピーし、エンジンが、セグメントをPまでコピーし（最後のものは、Pで切る）、チェックポイントを、Pまでのログと組になるときだけコピーし、状態のオブジェクトのファイルをコピーし、Pを示す `head` を書く。どのファイルも同期し、それからディレクトリを同期する。書くプロセスは、その間も書き続けてよく、元のファイルは、何も変えない。コピーの先は、無いか、空のディレクトリ。失敗したら、空にしてから、やり直す。リストアは、コピーを開くこと。デーモンの `Backup` は、読み手を、デーモンの中に開き（状態を、もう1つ、メモリに持つ）、読み手が開く間だけ、`Commit` を待たせる（3.6の「保守の口」。6.12の281）。
- 原本を、位置の後にコピーする理由：Pまでのコミットが指す原本は、そのコミットより前に書いたので、Pを決めた後にコピーすれば、すべてある（Pの後に書いた原本も入ることがあるが、使われない原本が増えるだけ）。

**オブジェクトの置き場所**

置き場所は、オブジェクト（文書とリビジョンのJSON）の中身を、どこに置くか。どれでも、論理のCAS（SHA-256で指し、同じ内容は1つ）は同じで、変わるのは、物理的な置き場所だけ。

| 置き場所 | ベンチマークの名前 | 中身 | レコードに入るもの |
| --- | --- | --- | --- |
| A | `log-inline` | コミットのレコードの中 | 中身 |
| B | `log-files` | オブジェクトのファイル（`objects/<16進数2桁>/<16進数64桁>`） | ハッシュと大きさ |
| 混合 | `log-hybrid` | `Threshold`（既定は64KiB、65536バイト）以上はファイル、ほかはレコードの中 | どちらか |

- 同じ内容：状態か、同じトランザクションにあるハッシュのオブジェクトは、何も記録しない（どの置き場所でも。`Update` をまたいでも、開き直した後も）。
- 読む：Aは、位置と大きさが、セグメントのファイルに収まることを確かめて、その位置から読む（読んだセグメントのファイルを、閉じるまで開いたまま使う。データのキャッシュは無い。ファイルの大きさは覚え、足りないときだけ調べ直す）。収まらなければ、壊れている（`/srv/data/logdb/log/0000000000000001-0000000000000001.log: corrupt: has 664 bytes, too few for an object of 1000 bytes at offset 573`）。Bは、ファイルの見出しと大きさを確かめて読む。エンジンは、中身をハッシュと照らさない（照らすのは保存先。3.4の「読むたびに確かめる」）。`Verify` と圧縮は照らす。
- 無いとき：状態に無いハッシュは、無いことの分かるエラー（`object 9f86…: file does not exist`。`fs.ErrNotExist`）。状態にあるのにファイルが無いのは、壊れている（`/srv/data/logdb/objects/9f/9f86…: missing file`。`fs.ErrNotExist` にはしない）。
- 原本：メディアの原本は、どの置き場所でも、`files/` に置く（3.4の「原本」）。
- 評価：下記の「置き場所の評価」。保存先は、混合（64KiB）を使う（3.4の「エンジンと設定」。6.12の137）。

**イベント・操作のID・暗号化の封筒**

- 監査イベント：`Update` の中で足し、ほかの変更と同じレコードに入る。そのため、イベントは、その `Update` がコミットされたときだけある（ほかの変更とともに、あるか無いかのどちらか）。保存先（3.4）は、ログイン履歴とアクティビティログの記録（7.4）に使い、足す口・読む口・確かめる口を持つ（3.4の「操作」）。エンジンの口と、形の版は、変えていない。番号は、コミットのときに、状態の次の番号から付けるので、失敗した `Update` と取り消した `Update` は、番号を空けない。メモリには数だけを持ち、ログから読む（`Events`）。圧縮は、番号とコミットの番号を変えずに写す（書き直しで落とせば、番号が空く）。
- 操作のID：エンジンには、そのための機能は無い。呼ぶ側が、変更と同じ `Update` で、操作のID（保存先では、表 `operations`。3.4の「索引」）を置く。返事が届く前にクラッシュしても、開き直した後に、そのキーで、コミットしたかが分かり、2度しない（監査イベントも、2度書かない）。
- 暗号化の封筒：どの値も、初めの1バイトが封筒（0 そのまま。1 暗号化：鍵のID・ノンス・暗号文。上記の「ファイルの形」）。エンジンは、そのままの値だけを書き、暗号化した値は読まない（`sealed values are not supported by this version`）。
- 鍵は、ログに置かない：追記するだけのログに置いた鍵は、書き直さなければ消せない。鍵は、ログの外の、消せる場所に置く（下記の「個人情報の削除」）。
- 封筒の限界（決めていない）：認証する追加のデータに表とキーを含めないことと、1つの鍵で暗号化する回数の上限は、6.12の138。

**対象のOSとファイルシステム**

- 対象：Linuxの、ローカルのファイルシステム（ext4・xfs・btrfs）を、1つのマシンから使う。電源断の記録（下記の「テスト」）は、3つとも確かめた。ほかのテストとベンチマークを動かしたのは、ext4（NVMeのSSDの上）だけ（6.12の130）。ネットワークのファイルシステムは、対象の外。
- 前提：ファイルの同期（`fsync`）は、その中身をディスクに置く。ディレクトリの同期は、その中の名前の変更（作る・消す・名前を変える）を、ディスクに置く。同じディレクトリの中の名前の変更は、すべてあるか、無いかのどちらか。新しいファイルの名前は、ディレクトリを同期するまで、ディスクにあるとみなさない（ext4などより厳しい前提。下記の「テスト」の模擬のファイルシステム）。
- ほかのシステム：デーモン（`whiteroom-db serve`）は、Linuxだけで動く（3.6の「実行ファイル」。6.12の283）。`whiteroom-db compact`・`gc`・`check`・`accept-break`・`repair` も、始めるときに、マシンの起動ごとのID（Linux の boot ID。`/proc/sys/kernel/random/boot_id`）を読み、読めなければ、何も変えずに失敗する（同期に失敗した後の印を守るため。3.6の「同期の失敗」）ので、実際は、Linuxだけで動く。エンジンは、`flock(2)` のあるシステム（darwin・dragonfly・freebsd・illumos・linux・netbsd・openbsd）では、ロックも動くはずだが、Linuxのほかでは動かしていない。ほかのシステムでは、ロックを取るときに失敗する（上記の「ロック」）。

**制限**

- 1回の `Update`：コミットのレコードの本体が268435446バイト（256MiBより10バイト少ない。上記の「ファイルの形」の「上限」）まで。置き場所Aでは、レコードに文書とリビジョンのJSONが入る（Bでは、ハッシュと大きさだけ）。保存先の混合では、64KiB以上のJSONが、ハッシュと大きさだけになる（3.4の「エンジンと設定」）。1つの文書の64MiBの上限は、別（3.4の「上限」）。6.12の136。
- メモリ：状態（すべての表のキーと値、オブジェクトの位置）を、メモリに持つ。開くときは、チェックポイントと、その後のログを読むので、開く時間は、チェックポイントの後のログとともに延びる（6.12の132）。`Verify`・`VerifyEach` は、ログから、もう1つの状態を、メモリに作って比べるので、その間の最大のメモリは、開いた後の1.4〜1.8倍まで増える（デーモンを通して、88MiBから2.8GiBのデータのディレクトリで測った。3.6の「測った値」）。
- 書くプロセスは1つ：2つ目は、2秒の後に拒む（上記の「ロック」。6.12の135）。デーモンも、書き手の接続を、1つしか許さない（3.6の「デーモンが守る規則」）。
- 読み手：書くプロセスがあるとき、エンジンの読み手は、ほかのプロセスでも、同じプロセスでも開ける（書くプロセスの `Open` は、読み手が開いたものを待つ。上記の「ほかのプロセス」）。ほかのプロセスは、エンジンの読み手を開かず、デーモンのソケットで読む（3.6の「接続」）。
- 開いたファイル：読んだセグメントのファイルを、閉じるまで開いたままにする（書くプロセスも読み手も。セグメントの数だけ増える。6.12の132）。
- `Events` と `Verify`：セグメント（既定は64MiBまで）を、1つずつ、すべてメモリに読む（6.12の132）。保存先の、記録を読む口と確かめる口（7.4）は、`Events` で読む。`Verify` の時間は、データのディレクトリの大きさに比例し、ファイルがページキャッシュに無いときは約1秒/GiB、あるときは約0.4秒/GiB（88MiBから2.8GiBで測った。2026-11-23。3.6の「測った値」）。その間、デーモンの `Commit` は待つ。`Inspect` の `Check` は、`Open` の復旧が読むものと、`VerifyEach` を、続けて動かす。時間は、測っていない。
- 作りかけのセグメント：見出しを書けなかった新しいセグメントを消すのにも失敗すると、開き直すまで、新しいセグメントを作れない（その間、セグメントを替える `Update` は失敗する）。
- ファイルのモード：開くときに、緩いモード（グループが読めるなど）を拒まない。エンジンは0700・0600で作る。別のUnixユーザーの読み手（9.2の「公開用と管理用を別プロセス・別Unixユーザー」）は、データのディレクトリを読まず、デーモンのソケットで読むので、そのままで足りる（6.12の134）。

**テスト**

模擬のファイルシステム（`internal/logdb/simfs`）は、ext4などより厳しいPOSIXの規則（ファイルの中身はその同期で、名前はディレクトリの同期で、はじめてディスクに置く）のモデルで、クラッシュ・失敗の差し込み・強制終了したプロセスを作る。

クラッシュ・強制終了・失敗の差し込みの、どの場合も確かめる不変条件：

- 開くのを拒まない（クラッシュで、壊れていると言わない）。チェックポイントは、壊れていない。
- 成功を返した `Update` と `PutOriginal` は、すべてある。動いていた `Update` は、すべてあるか、無いかのどちらか。
- 無いオブジェクトや原本を指すコミットは無い。監査イベントは、それを足した `Update` があるときだけある。
- 読み手が見るものも同じで、その後のクラッシュでも残る（同期したものだけを見せる）。
- `Verify` が通る。保存先の行列では、状態が、同じ操作の後のテストの模型の状態と同じ。

クラッシュ・強制終了・失敗の差し込みの行列（エンジンの `TestCrashMatrix`・`TestKillMatrix`・`TestFaultMatrix`・`TestReadFaultsDuringOpen`、保存先の `TestStoreCrashMatrix`・`TestStoreKillMatrix`・`TestStoreFaultMatrix`）は、数えるすべての操作の後のクラッシュと、1つの失敗の後で、上の不変条件を確かめる。`-race` では、試すクラッシュの型を減らす。長い版は `WHITEROOM_LONG_TESTS=1`（`internal/logdb`・`internal/store`・`internal/dbclient` を、一緒に動かして約7分。`-race` なし。`-timeout 120m` を付ける。`AGENTS.md`）。

保存先の行列は、デーモンを通して動かす：保存先は、プロセスの中のデーモンに繋ぎ、デーモンは、模擬のファイルシステムの上で、エンジンを開く。強制終了の行列は、327の点と22,578のクラッシュ（デーモンを通す前は、333と23,088。減った6点は、旧い `PutOriginal` の長さ0の書き込み）を、4つの開き方（新しいデーモンの書き手のクライアント・新しいデーモンの読み手のクライアント・止まったデーモンの読み手のクライアント・殺した後のデーモンの、同じソケットに繋ぎ続ける読み手のクライアント）で確かめる。エンジンの読み手（`OpenReader`）の性質（同期したものだけを見せる・何も書かない）は、`internal/logdb` のテストが確かめる。保存先の失敗の差し込みの行列（`TestStoreFaultMatrix`）と `TestOriginalAfterFailedSync` は、デーモンが止まるたびに、同じ起動（テストが決めたマシンの起動ごとのID）では、エンジンの書き込みを1つもせず、印の文で開けず、印が残ること、再起動した起動（本物のID）では、開いて印が消えること、止まらない失敗は、印を残さないことも確かめる（3.6の「同期の失敗」と「テスト」）。エンジンは、印を知らないので、エンジンの行列は、変えない：どの失敗が `ErrFailed` になるか（デーモンが印を残す条件）は、エンジンの行列が確かめ、`TestReopenAfterFailedSync` が、同じ起動で開き直す危険（F1）を示す。

状態を読むこと：エンジンのモデルのテストの `observe`（クラッシュ・強制終了・失敗の差し込みの行列も、状態を見るのに使う）は、すべての表を、3行ずつのページで、`ScanAfter` でも読み、`Scan` の行と同じことを確かめる。`ScanAfter` だけの確かめは、ほかに、キーの境のケース・読み手・`Update` の書き込みの中・取り消した後のもの（`internal/logdb` の `db_test.go`・`reader_test.go`）と、木の `AscendAfter` のファズ（`FuzzAscendAfter`）が持つ。

読み込みのファズ（`internal/logdb` の `FuzzBody`・`FuzzSegHeader`・`FuzzFrame`・`FuzzHead`・`FuzzObjHeader`・`FuzzCheckpoint`・`FuzzOpen`）は、どんなバイト列を読ませても、panicしないことを確かめる。CIは、種の入力（`f.Add`）だけを動かす。探索は、手で、ファズを1つずつ動かす（動かし方は `AGENTS.md`。例：`go test ./internal/logdb -run '^$' -fuzz '^FuzzOpen$' -fuzztime 60s -fuzzminimizetime 5s`。`-fuzzminimizetime` の既定は60秒で、短い探索では、探索の時間の大半を、1つの入力を小さくすることに使う）。

- ファイルの形（レコードの本体・セグメントの見出し・レコードの枠・`head`・オブジェクトのファイルの見出し・チェックポイント）：受け入れたものを書き直すと、同じバイト列になる（上の「ファイルの形」の「厳しい読み方」）。セグメントの見出し・`head`・オブジェクトのファイルの見出し・チェックポイントは、拒むときに、ファイルの全体の `CorruptError`（位置は付かない）か、新しい版の `VersionError` を返す（チェックポイントの本体は、読めなければ、理由だけを返し、状態を返さない）。セグメントの見出しは、ファイルの名前と違う世代・番号のものとして読ませると、拒む（上の「名前と見出し」）。レコードの枠は、拒むときの理由が、書きかけの末尾になりうるもの（途中で終わる・長さが範囲の外・CRCが合わない）か、0で埋めるところが0でないもののどちらか（上の「復旧」の表）。ファズは、CRCを当てられないので、セグメントの見出し・レコードの枠・`head`・チェックポイントは、入力のCRCを計算し直したものも読む。
- 書き直して比べる範囲：形ごとに決める。本体は、その全体。セグメントの見出しは、初めの64バイト（後ろはレコード）。レコードは、その枠（後ろは次のレコード）。`head` は、選んだ欄だけ（もう1つの欄は、正しくないか、書いた数が小さい）。オブジェクトのファイルは、見出しの16バイト（後ろは中身）。チェックポイントは、ファイルの全体（読んだ状態を、書く側の関数で書き直す）。
- 開く道（`FuzzOpen`）：模擬のファイルシステムの上の保存先（世代1だけのものと、圧縮した後のもの。それぞれ、チェックポイントのあるものと無いもの。どれも、すべての種類の変更を、複数のセグメントに書いてある）の、1つのファイルを、上書き・切る・置き換える・足す・消すのどれかで壊して、開く。拒むなら、`CorruptError` か `VersionError`（`head` やロックのファイルなど、ディレクトリの形のファイルを消したときは、そのファイルの `missing file`）で、ファイルを1つも変えない。開けたなら、表とオブジェクトの一覧は、壊す前の保存先の、コミットのどれかの後のものと同じ（保存先を作った直後を含む。最後のコミットとは限らない。上の「復旧」の「残る曖昧さ」）で、読み手（`OpenReader`）も同じものを見る。閉じて開き直すと、同じ状態で、もう何も切らず、消さない。`Verify` が通るなら、イベントも、そのコミットの後のものと同じで、オブジェクトは、どれも、ハッシュと大きさが合う（開くときは、チェックポイントのレコードより前のレコードと、オブジェクトのファイルを確かめないので、そこの傷は、`Verify`（と `VerifyEach`・`Inspect` の `Check`）が見つける）。ソルトは `testing/cryptotest` で決める（保存先は、いつも同じバイト列になる）ので、失敗した入力は、同じ失敗を繰り返す。

電源断の記録（dm-log-writes）：

Linuxの dm-log-writes は、ブロックデバイスへの書き込みを、flush・FUAの印とともに、順にログに写す。保存先のワークロード（プロセスの中のデーモンを通る。下記）を、その上のファイルシステムで動かして記録し、ログを途中まで再生して、そこで電源が切れたときのデバイスの中身を作り、マウントして、保存先を確かめる。模擬のファイルシステムは、エンジンの同期の順を、厳しい規則で確かめる。記録は、同じ同期が、実際のファイルシステム（ジャーナルの再生も）で足りているかを確かめる。

ワークロード（`internal/store` の `TestDMLogWorkload`）は、保存先の200回の `Update`（2つの用語の組と、監査の記録。10回に1回は、原本とメディアの文書も）。セグメント（16KiB）とチェックポイント（32KiB。`Update` の中で書く）を小さくし、100バイト以上のオブジェクトをファイルに置くので、セグメントの切り替え・チェックポイント・オブジェクトのファイルを含む。データのディレクトリは、記録するファイルシステムの `site/data` で、親の `site` も、作る。10個のプロセスを順に動かし（どれも、プロセスの中にデーモンを持ち、保存先は、それに繋ぐ。デーモンのエンジンは、記録するファイルシステムの上にある）、そのうち6つは、決めた所で、自分を強制終了する（SIGKILL。書いたものは、ページキャッシュに残る）：

| 順 | プロセスのすること | 強制終了する所 |
| --- | --- | --- |
| 1 | 保存先を作り、`Update` を40回 | 41回目の、レコードを書いた後、同期の前 |
| 2 | 読み手のクライアントで、組を読む（プロセスの中のデーモンが、書き手として開き、ログの終わりを同期する） | しない |
| 3 | 書くプロセスとして開き直し、69回目まで | ほかの `Update` が置かないメディアの文書の、オブジェクトのファイルを書いた後、レコードの前（使われないファイルが残る） |
| 4 | 開き直し、100回目まで | チェックポイントの名前を変えた後、ディレクトリの同期の前 |
| 5 | 開き直し、129回目まで | 130回目の原本を、一時ファイルに書いて同期した後、名前を変える前 |
| 6 | 開き直し、180回目まで。160回目の後に、`Backup`（`site/backup` へ） | しない（閉じる） |
| 7 | 保守（回収・圧縮・回収） | 圧縮の、ベースを書いた後、ベースの終わりの前（世代2は、完全でない） |
| 8 | 保守 | ベースの終わりの後（世代2は完全で、チェックポイントは世代1のもの） |
| 9 | 保守（世代3になる） | しない |
| 10 | 開き直し、200回目まで | しない（閉じる） |

- 印：ワークロードは、`Update` が成功するたび、書くプロセスが開き直す前、開いたプロセスが組を読むたび、`Backup` の後、閉じた後、保守の前と後に、ログに印を置き、印がログに入ってから、先へ進む。確かめは、印から、その時点までに成功したことを知る。
- 確かめる状態：mkfs の後の、デバイスを変えるエントリー（書き込みとdiscard）と印の、それぞれの後。flush・FUA・印の時点（点）だけでなく、その間も見るのは、装置が、flush の前の書き込みの一部を、書き終えていることがあるため。ログは、1回の flush までの書き込みを、終わった順に持ち、FUAの書き込みを、終わった所に持つので、ログの初めから、どのエントリーまでを取っても、装置に残りうる状態になる（ほかの組み合わせは、見ない）。FUAの書き込みの後、次の flush までに、同じセクタの、FUAでない書き込みかdiscardがあると、どちらが後かが、ログからは分からないので、確かめは、その記録を拒む（下の記録には、無かった）。この見分け方は、記録するデバイスが、自分のFUAを持たないとき（`record.sh` のループデバイス。持つデバイスでは、`record.sh` が止まる）に、正しい。
- 確かめること（`TestDMLogCheck`）：どの状態でも、(1) ファイルシステムが、マウントできる。(2) 最初の印の後は、保存先を、まず読み手のクライアント（取り出した写しの上の、プロセスの中のデーモンが、書き手として開き、書きかけの末尾を切る）が開け、それから、書き手のクライアントが開ける。(3) どちらの見る組の番号も、最後の印のものか、その次（動いていた `Update`）で、書くプロセスのものは、読み手の見たものより前でない。閉じた後は、最後の印のもので、チェックポイントから開ける（ログを読み直さない）。(4) どちらが見ても、メディアの文書・原本・監査の記録が、その番号までのすべてで、エンジンの `Verify`・監査の鎖・索引の確かめが通る。(5) 書くプロセスが、次の `Update` を書いて閉じ、開き直すと、それがある。(6) `Backup` が成功した後は、写しを、読み手も、書くプロセスも開けて、そのときの組（160）を持ち、(4)が通る。(7) 世代は、保守の外では、最後の保守が終えたもので、保守の間は、それか、それより後。最初の印の前は、保存先が、無くても、開けなくてもよい。
- 動かし方：`nix build -L .#dmlog`（`internal/logdb/dmlog/vm.nix`）。記録（`internal/logdb/dmlog/record.sh`。rootが要る）と確かめを、記録ごとに、QEMUの仮想マシンの中で動かすので、ホストのrootは要らない（KVMが要る。動かしたのは、x86_64-linux だけ。16のCPUの開発のマシンで、約10分）。カーネルは、flake の nixpkgs のもの。結果の `summary.txt` に、記録ごとの1行があり、問題があれば、ビルドが失敗する。1つの記録だけなら、`nix build -L .#dmlog.xfs` のように書く。入力（`go.mod`・`internal/`・flake の nixpkgs）が同じなら、2回目からは、動かさずに、前の結果を返す。CIでは動かさない。
- 実機での動かし方：rootで `internal/logdb/dmlog/record.sh` を動かす（使い方は、その初めのコメント。Linuxの `CONFIG_DM_LOG_WRITES`、ループデバイス、`dmsetup`・`losetup`・`mkfs` などが要る）。ext4の記録は、rootなしで確かめられる（`e2fsck -fy` がジャーナルを再生し、`debugfs` がファイルを取り出す）：`WHITEROOM_DMLOG=<結果のディレクトリ> go test -count=1 -v -timeout 0 -run '^TestDMLogCheck$' ./internal/store`（既定は、点だけ。`WHITEROOM_DMLOG_STATES=all` で、上の状態のすべて。`WHITEROOM_DMLOG_POINTS=<n>` で、初めのn個だけ）。ほかのファイルシステムの記録は、rootで、`WHITEROOM_DMLOG_MOUNT=<ファイルシステム>` を足して、テストのバイナリを動かす（状態ごとに、マウントする）。
- 落ちることの確かめ：同じビルドが、同期を落とした保存先のワークロードも記録し、確かめが、保存先の問題を1つも見つけなければ、失敗にする。ファイルの同期を落とすと、ext4・xfs・btrfs のどれでも、見つかる（下の記録では、ext4 で1603のうち1393の状態・xfs で488のうち437の状態・btrfs で1659のうち1620の状態）。ディレクトリの同期だけを落とすと、btrfs では見つかる（2913のうち2579の状態。空のディレクトリ `files/` が無い、など）。ext4 と xfs では、見つからなかった（2026-11-15 に1回ずつ測って、ext4 の3016・xfs の964の状態で、問題は0。ファイルの同期が、それまでの名前の変更も、ディスクに置くため。ビルドには入れていない）。ディレクトリの同期の不足を見つけるのは、3つのうち、btrfs の記録だけ。
- 示せないもの：(1) flush を守らない装置（flush が成功した書き込みを、電源断で失うディスクとキャッシュ）。(2) 途中で切れる書き込み：1つの書き込み（ログのエントリー。複数のセクタのことが多い）は、すべて残るか、まったく残らないかで、その途中や、セクタの途中で切れた状態は、作らない。(3) flush の前の書き込みが、ログの順の初めからでない組み合わせで残った状態。(4) 同期の失敗（上記の「失敗の扱い」。6.12の129）。(5) ほかのカーネルの版と、ほかのマウントの設定。(6) ほかのワークロード（保存先の既定の設定の、64MiBのセグメントとバックグラウンドのチェックポイント、`whiteroom` のコマンド、デーモンを別のプロセスにした記録。6.12の273）。(7) データのディレクトリの親の同期（3.4の「作る」）が要ること：3つのファイルシステムでは、親を同期しない版でも、新しく作った2段の親とデータのディレクトリの名前は、最初の印の後、いつも残った（保存先が、データのディレクトリ自身を同期するため）。6.12の130。

**ベンチマークの条件**

ベンチマーク（`TestBenchmarks`）は、自作の層の3つの置き場所を、同じデータのセットと同じ操作で測る。保存先は、シナリオのプロセスの中のデーモンに、`net.Pipe` で繋ぐ（`results.md` の初めに、そう書く。デーモンを別のプロセスにして、ソケットで繋いだ数ではない）。下記の表と数は、保存先が、エンジンを、プロセスの中で直接使っていたときの、前の実行のもので、デーモンを通した数ではない。デーモンを通した小さな試し（1つのセルを1回）と、デーモンの速さは、3.6の「測った値」。

動かし方：

- テスト：`TestBenchmarks`（`internal/store/bench_test.go`）。環境変数 `WHITEROOM_BENCH` で結果のディレクトリを渡したときだけ動き、渡さなければ、すぐに飛ばす。`-race` は付けない（付けると、失敗する）。Goのランタイムの設定（`GOGC` など）は、既定のまま：`WHITEROOM_BENCH=<結果のディレクトリ> WHITEROOM_BENCH_DIR=<作業のディレクトリ> go test -count=1 -run '^TestBenchmarks$' -timeout 0 ./internal/store`
- 作業のディレクトリ：データのディレクトリは、回（下記）と保存の層ごとに、`WHITEROOM_BENCH_DIR`（無ければ `os.TempDir()`）の中に作り、その保存の層のシナリオ（下記）の後に消す。作業のディレクトリは、実際のディスクに置く（tmpfsなどのメモリには置かない）。
- プロセス：シナリオ（下記）ごとに、テストの実行ファイルを、別のプロセスで動かす（`TestBenchHelper`。することは `WHITEROOM_BENCH_HELPER` で渡し、渡さなければ、すぐに飛ばす）。そのため、最大RSS（下記）は、シナリオごとに測れる。2時間を超えたプロセスは止め、ベンチマークは、そこで失敗する。
- 初めの確かめ：初めに、どのセットも、`load`（下記）のすべての保存を作り、`Put` と `AddRevision` が文書とリビジョンを確かめるのと同じ確かめ（大きさ・読み込み・文書の `id`。3.4の「書くときの確かめ」）を通ることと、下記の大きさであることを確かめる。
- 小さな試し：`WHITEROOM_BENCH_SMOKE=1` では、仕組みを確かめるために、100文書のセット（`smoke`：エントリー70・ターム20・メディア10で、2回目の保存は14）を、保存の層ごとに1回だけ動かす（初めの確かめは、下記のすべてのセットにもする）。

保存の層：

| 名前 | 保存の層 |
| --- | --- |
| `log-inline` | 自作の層。オブジェクト（文書とリビジョンのJSON）を、ログに入れる |
| `log-files` | 自作の層。オブジェクトを、1つずつファイルにする |
| `log-hybrid` | 自作の層。64KiB（65536バイト）以上のオブジェクトを、ファイルにし、ほかをログに入れる |

- 自作の層の設定：エンジンの既定値。ログのセグメントは64MiBまで。チェックポイントは、ログが64MiB増えるたびに、バックグラウンドで書く（`Update` は待たない）。書くロックは、2秒まで待つ。`log-hybrid` は、保存先の既定の設定と同じ（3.4の「エンジンと設定」）。

- 原本：どの保存の層でも、原本（`PutOriginal`）は使わない。

データのセット：

| セット | 文書 | 版 | リビジョン | 監査イベント | 1回の `Update` | `Update` の数 |
| --- | --- | --- | --- | --- | --- | --- |

- リビジョンの大きさ：それぞれ1%の確率で、100〜400KiB（一様）。ほかは、対数正規分布で、中央値が2KiB（2048バイト）、9割が8KiB以下（対数の標準偏差は、ln 4 ÷ 1.2816）。そのうえで、256バイト〜65535バイト（64KiBの1バイト前）に収める。そのため、`log-hybrid` では、大きいリビジョンだけが、ファイルになる。
- 1回の保存（下記の「シナリオ」）のJSONも、同じ大きさにする。

シナリオ：

回と保存の層ごとに、新しいデータのディレクトリで、次のシナリオを、この順に、それぞれ1つのプロセスで動かす。

| シナリオ | すること |
| --- | --- |
| `load` | 保存先を作り（`Create`）、セットを保存して（上記）、閉じる |
| `ops` | 開き、ランダムな文書の `Document` を1000回、ランダムな文書の `History` を1000回、ランダムなエントリーの `Revisions` を1000回、エントリーの `Documents` を5回、ビルドのような読み込み（下記）を1回する（それぞれ1つの `View`）。それから、1回の保存（下記）を300回して（それぞれ1つの `Update`）、閉じる |
| `open-clean` | 閉じた保存先を開き、文書（エントリーの1番目）を1つ読んで、閉じる |
| `open-replay` | チェックポイント（`logdb/checkpoint`）を消してから、`open-clean` と同じことをする（ログのすべてを読み直して開く。閉じるときに、チェックポイントを書く） |
| `open-killed` | 別のプロセスが、開いて1回の保存を続け、100回の後に、`SIGKILL` で止められる（止められる前に、もう1回保存していることがある）。その後で、`open-clean` と同じことをする |
| `checkpoint` | 開き、1回の保存をしてから、チェックポイントを書いて（`Checkpoint`）、閉じる |
| `backup` | 閉じた保存先を、新しいディレクトリにコピーする（デーモンの `Backup`（3.6の「保守の口」）で、ログ・チェックポイント・オブジェクトのファイルと、`files/` をコピーして、それぞれ同期する）。それから、コピーと元を開いて、数が同じことを確かめ、コピーを消す |

- 1回の保存：ランダムなエントリーの新しい版と、新しいリビジョンと、監査イベント（どのセットでも1件）を、1つの `Update` でする。
- ビルドのような読み込み：1つの `View` で、8つの種類のすべての文書（`Documents`）と、すべてのエントリーのリビジョンの一覧（`Revisions`）と、それぞれの最後のリビジョン（`Revision`。JSONも）を読む。
- 続けて動かす：シナリオは、同じデータのディレクトリで続けて動かすので、前のシナリオの保存（`ops` の300回など）は、後のシナリオに残る。どの保存の層も、同じ順に動かす。
- 回：セットごとに3回。1回の中で、`log-inline`・`log-files`・`log-hybrid` の順に動かす（同じ保存の層の回を、続けない）。結果は、3回の中央値と、最小・最大。

測るもの：

- 時間：Goの `time.Now` の差（単調な時計）。`load` は、`Update` の時間の和（保存を作る時間は含めない）。ほかに、閉じる時間（`Close`）、開く時間（`Open` が返るまで）、開いた後の初めの読み込み、`Checkpoint`、バックアップ、ビルドのような読み込みの時間を測る。
- p50・p99：`ops` のそれぞれの操作の N 回の時間を、小さい順に並べて、N×0.5番目・N×0.99番目（切り上げ）のもの。`Documents` の5回は、中央値（3番目）と最大。
- 最大RSS：シナリオのプロセスの `/proc/self/status` の `VmHWM`（テストの実行ファイルを動かしてからの、いちばん大きい常駐のメモリ）。`getrusage` の `ru_maxrss` は使わない（Linuxは、それを `execve` をまたいで残す。Goの `os/exec` で動かしたプロセスは、`execve` まで親のメモリを使うので、親の最大から始まる）。

**置き場所の評価**

数によらないこと：

- 同じ内容：どの置き場所でも、同じハッシュのオブジェクトは1つで、2度目からは何も記録しない（論理のCASは同じ）。
- 同期の回数：Aは、コミットごとに、セグメントの同期が1回。Bは、それに、新しいオブジェクトごとのファイルの同期と、使ったディレクトリごとの同期が足される。混合は、大きいオブジェクトの分だけ足される。
- 途中で止まったとき：Aは、書きかけのレコードを切り戻すだけで、何も残らない。B（と、混合の大きいオブジェクト）は、レコードより先に書いたオブジェクトのファイルと一時ファイルが残り、回収で消す。
- 圧縮：Aは、残すすべてのオブジェクトの中身を、新しい世代に写す（読んで、ハッシュを確かめて、書く）。Bは、ハッシュと大きさだけを写し、ファイルはそのまま使う。
- 回収：どれも、要らなくなったオブジェクトを状態から落とすのは、圧縮。領域が空くのは、Aでは、古い世代のセグメントを消すとき、Bでは、回収でファイルを消すとき（どちらも、保守モード）。
- バックアップ：Aは、少しの大きなファイル（セグメント）を写す。Bは、オブジェクトの数だけのファイルを写し、それぞれを同期する。
- 開くとき：ログを初めから読み直すとき、Aは、オブジェクトの中身も読む（メモリには、位置だけを持つ）。Bのログは、ハッシュと大きさだけなので、小さい。
- 1回の `Update` の上限：Aは、オブジェクトの中身もレコードに入るので、Bより早く、上限（約256MiB）に届く。

数（決めたときの測定の、3回の中央値の比。索引を足す前の、エンジンをプロセスの中で直接使っていたときのもので、測り直していない）：

**運用の制約**

本番で使うなら、次のことを守る（案）。

- エンジンを開くのは、デーモンだけ：データのディレクトリを開くのは、デーモン1つで、2つ目のデーモンは、書くロックで断られる。管理のサーバーと書くコマンドは、書き手として、ビルド・バックアップ・検出は、読み手として、デーモンのソケットに繋ぐ（3.6の「接続」）。
- 同期に失敗した後は、マシンを再起動する：デーモンが、`stopped`（`the store has stopped after a sync failed; restart the machine before starting the daemon again`）で、書く要求を断ったら、マシンを再起動してから、デーモンを起動し直す。プロセスを再起動するだけでは足りない（同じ起動の間は、ページキャッシュが残る）。デーモンは、これを強制する（案。#68。3.6の「同期の失敗」。6.12の129）：止まったとき、データのディレクトリに印（`<DATA>/stopped`）を残し、同じ起動の間は、`whiteroom-db serve`・`compact`・`gc`・`accept-break`・`repair` が、`<DATA>: a sync failed at …, and the machine has not restarted since; restart the machine before starting whiteroom-db on this directory again` で、何も変えずに、終了コード1で断る（`whiteroom-db check` と、`-apply` の無い `repair` も、同じ文で断るが、前の起動の印は、消さずに、そのまま残す：何も書かない確かめなので）。止まったデーモンは、動き続ける（書く要求を断り、読みは続く）ので、systemdの、止まったプロセスを自動で再起動する設定（`Restart=always` など）でも、プロセスは終わらず、再起動されない。人が `systemctl restart` したり、デーモンが落ちたりすると、次の起動は、すぐに1で終わり、`Restart=` で起動し直す仕組みは、起動の回数の上限（`StartLimitBurst=`）の後に、ユニットを失敗にする。マシンを再起動した後の最初の起動は、印を消し、1行書き（`… before the machine restarted; the mark <DATA>/stopped is removed: check the store with whiteroom doctor`。`serve` はログに、`compact`・`gc`・`accept-break`・`repair -apply` は標準エラーに）、起動する：そのあと、`whiteroom doctor`（9.4）で、保存先を確かめる。マシンを再起動する前に、印を手で消さない（消すと、ページキャッシュだけにある変更を、ディスクにあるものとして、続きを書く）。印が読めないとき（空・壊れたもの）は、いつも断るので、マシンを再起動した後に、人が消す（断る文が、そう言う）。
- 保守：圧縮と回収は、デーモンを止めてする（`whiteroom-db compact`・`gc`。3.6の「保守の口」）。デーモンが動いていれば、2秒待って失敗し、保守が動いている間、デーモンは、すぐに始まれない（6.12の133）。`compact` は、ログイン履歴の、1年より古い記録も落とす（案。#70 の計画への答え（2026-11-23）で決めた。7.4の「保持の期間と個人の情報」）ので、ログイン履歴を、期間で消すには、運用が、`compact` を、定期的に動かす（間隔は、運用が決める。記録は、1年と、その間隔の分まで残る）。デーモンが動かない間の確かめ（`whiteroom-db check`。何も変えない）は、下記の「移行・バックアップ・リストアの条件」。ログの鎖が切れていて、調べて、認めるときは、`whiteroom-db accept-break -log LOG -record N`（案。#70 の計画への答え（2026-11-23）で決めた。`whiteroom doctor` が示す記録の番号を使う。記録は変えず、デーモンは止めて動かす。3.6の「保守の口」。7.4の「改ざんの検知」）。エンジンのファイルが壊れて、`whiteroom doctor` か `whiteroom-db check` が示すか、デーモンが開けないときは、デーモンを止めて、`whiteroom-db repair`（案。#144 の計画への答え（2026-11-25）で決めた）で、落とすものと失うものを見て、直す（`-apply -keep DIR`。直す前の `logdb/` の写しが、`DIR` に残る。3.6の「保守の口」。9.4）。写しがあれば、写しから戻す道も、残る（下記の「移行・バックアップ・リストアの条件」）。
- 置き場所：Linuxの、ローカルのファイルシステム（NFSなどは使わない）。データのディレクトリそのもの（`logdb/` と `files/` の親）も、デーモンのユーザーが書けること：印を置くため。書けなければ、`serve`・`compact`・`gc`・`accept-break`・`repair -apply` は、何も変えずに断る（3.6の「書けるかの確かめ」）。`check` と、`-apply` の無い `repair` は、書かないので、動く。
- バックアップ：コピーは、その時点のすべて（個人情報も）を持つ（下記の「個人情報の削除」）。

**移行・バックアップ・リストアの条件**

- 形の版：どのファイルにも、印と形の版があり、新しい版は、何も変えずに拒む。形を変えるときは、古い版を読めるようにするか、新しい世代に書き直す（圧縮は、状態のすべてを、新しい世代のベースに書くので、新しい形に書き直す道になる）。エンジンの形は、版1だけで、移すコードは無い。形の版の移行の道は、別の issue（#145。6.12の131）で作る（#70 の計画への答え（2026-11-23）で、#70 から分けた）。
- 表の版の更新：作るものの表（索引）は、作り直して表の版を上げる（規則は、3.4の「エンジンと設定」の「表の版」と、3.4の「索引」の「表の版の更新」）。形の版の移行の道（#145。6.12の131）の、最初の例。表の版は、#70 で、7から8にした（表 `chains` と、デーモンのイベント 0x02・0x03 を足したため。3.4の「表」。3.6の「印」）。書き手が繋ぐときの1回の `Update` で、表の版の行と、更新の記録（`store.upgrade`）と、その鎖の頭と、頭の行だけを書く、これまでと同じ道（`store` の `upgradeLog`。データは移さない）で上げる。表 `chains` の行は、書き手が書かず、保守だけが書く（3.6の「デーモンが守る規則」）ので、更新は、行を書かない。表の版は、#144 で、8から9にした（穴の行と、デーモンのイベント 0x04 を足したため。3.4の「表」。3.6の「印」）。8から9の更新も、同じ道で、行を書かない。`whiteroom-db repair` が、穴の行を書くときは、同じ新しい世代の中で、表の版の行を、8から9にする（更新の記録は足さない。データは移さない）。
- バックアップ：書くプロセスが書いている間も、1つのコミットの時点のコピーを作れる（上記の「保守モード」の `Backup`）。コピーは、元と同じ形のデータのディレクトリ。デーモンが、自分のエンジンの `Backup` を、読み手の接続のメッセージで動かす（3.6の「保守の口」）。保存先の口とコマンドは、3.4と9.4の「`whiteroom backup`」。
- リストア：コピーの上で、デーモンを動かす（デーモンが、エンジンの `Open` で開く）。チェックポイントがあれば、それから、無ければログから、状態を作る。使うのは、`Backup` が成功したコピーだけ。コマンドの手順は、コピーを、データのディレクトリの場所に置くこと（9.4の「`whiteroom backup`」の「戻す手順」。写しから戻すコマンドは、まだ無い。6.12の131・258）。
- 修復か、写しから戻すか（案。#144 の計画への答え（2026-11-25）で決めた）：写しがあり、写しを取った後の書き込みを失ってよいなら、写しから戻すのが、いちばん簡単。写しが無いか、写しの後の書き込みを残したいなら、`whiteroom-db repair` で、読めるものを残して直す：落とすものと失うものは、直す前に示され、直す前の `logdb/` は、写しとして残る。修復が直すのは、エンジンのファイルで、表の行が、失ったオブジェクトと原本を指すことは、直さない（`whiteroom doctor` が、示し続ける。#147。6.12の291）。直した後は、`whiteroom-db check` と `whiteroom doctor` で確かめる。ベースを覆うチェックポイントの無い保存先は、修復が断るので、写しから戻す（上記の「残る危険」）。9.4の「`whiteroom-db`」。
- コピーの確かめ（案。#70 の計画への答え（2026-11-23）で決めた）：デーモンが開く前に、`whiteroom-db check`（3.6の「保守の口」。`Inspect` の `Check`。何も変えない）で、コピーを確かめる。デーモンは、書き手として開くので、書きかけの末尾を切り、`head` を書き直し、そのあとの確かめは、切った後の保存先のものになる：コピーが、最後のコミットを欠いていても（最後のセグメントが無い・最後のレコードが切れている）、デーモンは、1つ前のコミットまでで開け、`whiteroom doctor` も、鎖の頭を渡さなければ通る（2026-11-23に、`main`（`6983bcb`）で確かめた。コピーを、先に変えてしまう）。`check` は、それらを、開く前に、問題として示す。`check` が通るコピーは、`Open` が直すものを持たないので、デーモンは、何も切らずに開ける。`check` が確かめるもの・確かめないもの（表の行・表の版）と、そのあとの手順は、3.6の「保守の口」と、9.4の「`whiteroom backup`」。
- コピーの確かめが示せないもの：チェックポイントが、最後のレコードまで届いているコピーは、最後のレコードが切れると、`Open` が、チェックポイントと組にならないものとして拒むので、`check` の問題は、1つ（`engine: <DIR>/logdb/checkpoint: the log does not have sequence N at <セグメント> offset X`）で、書きかけの末尾としては、示さない（上記の「復旧」の「残る曖昧さ」）。書きかけの末尾と、`head` のずれの2つが並ぶのは、チェックポイントが、最後のレコードより前にあるか、無いコピー（`Backup` は、組になるチェックポイント（閉じたときのものか、バックグラウンドで書いたもの）だけを写すので、チェックポイントを1度も書いていないデーモンの写しは、持たない）。どちらも、デーモンが切る前に、示す。

**個人情報の削除**

個人情報が残る場所と、消し方：

| 場所 | 残るもの | 消し方 |
| --- | --- | --- |
| ログ（いまの世代） | 書き換えた前の値と、消したキーの値、ログの中のオブジェクト（文書とリビジョンのJSON）、監査イベント（ログイン履歴のアドレス・User-Agent・打たれたログイン名と、アクティビティログのアカウントのログイン名。保持の期間は7.4） | 圧縮の書き直しで、値を書き換えるか落とし、オブジェクトとイベントを落とした新しい世代を書き、古い世代を消す。ログイン履歴の、1年より古い記録は、`whiteroom-db compact` が落とす（案。#70 の計画への答え（2026-11-23）で決めた。3.6の「保守の口」。7.4の「保持の期間と個人の情報」）。アクティビティログの記録は、消さない |
| オブジェクトのファイル | 文書とリビジョンのJSON | 圧縮で落とした後、回収で消す |
| チェックポイント | ある時点のすべての表の値 | 圧縮が、新しい世代のチェックポイントで置き換える |
| メモリの状態（エンジンの中の索引） | 表の値 | 圧縮の後は、新しい世代のもの |
| 保存先の履歴（3.4） | すべての版とリビジョン（消した文書のものも） | 履歴から消す操作は、まだ無い（6.12の125）。作るなら、圧縮の書き直しを使う |
| 原本（`files/`） | メディアのファイル | 原本の回収（6.12の125） |
| バックアップ | その時点のすべて | エンジンの外。保持の期間を決めて消す |
| 古い公開のリリースと、画像のキャッシュ | 公開したページと画像 | エンジンの外（4.3・6.6.2） |
| ファイルシステムとディスク | 消したファイルのブロック | 物理的に消えたことは、保証しない |

- 示したこと：圧縮の書き直しで、値を書き換え、オブジェクト（ログの中のものと、ファイルのもの）とイベントを落とすと、印にした文字列は、ログ・チェックポイント・古いセグメントのどれにも無くなり、落としたオブジェクトのファイルにだけ残る。そうしたファイルは、回収が消す。
- 暗号化して鍵を消すこと（crypto-shredding）は、候補。鍵は、ログの外の、消せる場所に置く（上記の「イベント・操作のID・暗号化の封筒」）。鍵の扱いと、鍵を消すことを消去とみなさないこと、暗号化しても分かるものは、6.12の138。

**冪等性の責務**

- エンジン：復旧の後に、コミットは、すべてあるか、無いかのどちらか（上記の「テスト」）。呼ぶ側は、同じ `Update` に置いた操作のID（上記の「イベント・操作のID・暗号化の封筒」）で、そのコミットがあるかを確かめられる。エンジンは、同じ操作の再送を、自分では見分けない。
- 保存の操作（案）：操作のIDで再送を見分け、その記録を、保存と同じコミットに入れる（規則は6.7の「保存の操作（案）」。表 `operations` は3.4の「索引」）。
- 記録を残す期間と、管理のAPIの層での再送の扱い：記録は24時間残す（保存の操作が消す。6.7・6.12の153）。管理のAPIは、`Idempotency-Key` で操作のIDを受け取る（9.7の「再送」）。メールなどの外への作用（送るものを同じコミットに書いておき、コミットの後に送るもの。outbox）は、外への作用がまだ無いので、作っていない（6.12の202）。
- 監査の二重の記録：監査イベントは、状態の変更と同じコミットに入るので、操作のIDで再送を見分ければ、2度は書かれない。

**デーモンで変わる所**

エンジンを、DBのデーモンの中で動かすことは、作った（3.6）。エンジンの核をAda/SPARKにすると（3.6。まだ作っていない）、この節の、次の所が変わる。上の記述は、核を作るときに、コードと一緒に書き換える。

- 構成：エンジンのうち、判断と計算だけの部分（形の符号化と復号、ログを読むときの判断、書く順の指示）を、Ada/SPARKの核にし、I/O（`vfs`）・ロック・メモリの状態・保守の進行は、Goに残す（3.6の「エンジンの形」「核の範囲」）。ファイルの形は、変えない（3.6の「ファイルの形」）。
- 読み手：エンジンの読み手は、いま、デーモンの `Backup` だけが使う。核に、読み手のための `head` と、読み手の同期と、`flock(2)` のロックの形を含めるか、`Backup` の形を替えて、エンジンの読み手を外すかは、決めていない（6.12の281）。
- 移行：形を変えるときは、書き直して移し、読めるのは、いまの版と1つ前の版にする（仮置き。3.6の「ファイルの形」）。
- テスト：模擬のファイルシステムの行列を、核で動くエンジンにも流し、Goのエンジンと核を、同じテストと、同じディレクトリで比べる（3.6の「進める順」）。dm-log-writes のワークロードは、プロセスの中のデーモンを通る（上記の「テスト」）。核で動くエンジンの記録と、2つの実行ファイルをプロセスにした記録を取るかは、6.12の273。
- 判断：「Goの標準ライブラリだけで作った」は、核を入れるまでのこと（3.6の「エンジンの形」）。

**判断**

自作へ移行する（メンテナーの判断。2026-11-06）。保存の層を、SQLite（`internal/db` と `github.com/mattn/go-sqlite3`）から、この節のエンジンと自作の層に替える。

- 理由：外部のサードパーティのGoのモジュールを無くす目標（1.2）の、残る唯一の例外が、保存の層（ドライバーとcgo）。PoCで、結果はSQLiteと同じになり（差分テスト）、どのクラッシュ・強制終了・失敗の差し込みの後も、確定したコミットだけが見えた。書き込みと読む操作は、SQLiteより速いか同じくらいで、書くバイトも少ない。引き受けるもの：エンジンの保守、データとともに増えるメモリと開く時間、確かめていない電源断。
- 本番で使う前に：検出と、写しの確かめと、読める鎖の切れ目の修復は、作った（案。#70。#70 の計画への答え（2026-11-23）で決めた）：検出は `Verify`・`VerifyEach`・`Inspect` と、保存先の `Check`・`whiteroom doctor`・`whiteroom-db check`、写しの確かめは `whiteroom-db check`、鎖の切れ目の修復は `whiteroom-db accept-break`、ログイン履歴の古い記録を消すのは `whiteroom-db compact`（上記の「保守モード」と「移行・バックアップ・リストアの条件」。3.6の「保守の口」。7.4）。エンジンの修復も、作った（案。#144。#144 の計画への答え（2026-11-25）で決めた）：読めないものを落として、新しい世代に書き直す `whiteroom-db repair`（上記の「保守モード」。3.6の「保守の口」。9.4）と、それが作る鎖の穴（7.4）。残るのは、形の版の移行（#145）と、修復が直さないもの（#147）（6.12の131・290〜293）。同期に失敗した後の再起動の強制は、作った（案。#68。上記の「運用の制約」と「残る危険」。残りは6.12の129）。電源断の確かめ（dm-log-writes の記録）は、済んだ（上記の「テスト」の「電源断の記録」。残りは6.12の130）。
