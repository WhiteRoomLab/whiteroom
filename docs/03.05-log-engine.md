### 3.5 保存の層の自作の検証（PoC）

issue #63 の検証（PoC）として、そのときの3.4の保存先のうち、SQLite（`internal/db`）が受け持つところを、Goの標準ライブラリだけで作った保存の層（`internal/logdb`）に置き換えられるかを確かめる。この節の結果から、保存の層を自作の層に替えることにし（下記の「判断」）、#66 で替えた（`Create`・`Open`・`OpenReader` は、自作の層を使う。3.4）。ベンチマークの条件（下記）は、ベンチマークを動かす前に決めて書き、動かした後で変えていない（#66 で、注記と参照だけを足した）。

**目的と状態**

- 目的：外部のサードパーティのGoのモジュールを無くす目標（1.2）に向けて、当時のSQLiteのドライバー（`github.com/mattn/go-sqlite3`）とcgoを、データを失わずに置き換えられるかを判断する材料を、そろえる。エンジンを採用することは、目的ではない。
- 仮説：CAS（内容のSHA-256で指す、書き換えないオブジェクト）・表（キーと値）・追記するだけのログ（正本）・チェックポイントを、1つのコミットと復旧の仕組みの上で動かす。別々の3つのデータベースにはしない。
- 作らないもの：SQL、JOIN、クエリの最適化、ディスクの上の汎用のB-tree、高度なMVCC（版を持つ同時実行の制御）、グループコミット（いくつかのコミットを1回の同期にまとめること）、ネットワークのファイルシステムへの対応。アカウント・セッション・WebAuthn・メール、#43の索引、管理のサーバーとコマンドも、範囲の外。
- コードの場所：エンジンと自作の層（下記の「構成」）は、mainにある。#66 で、`Create`・`Open` を自作の層にし、SQLiteの保存の層・`internal/db`・ドライバーを外した（3.1・3.4）。
- 判断：メンテナーが、この節の結果から、「自作へ移行」「SQLiteを継続」「追加検証」のうち、「自作へ移行」を選んだ（2026-11-06。この節の最後の「判断」）。#66 で替えた。#43（索引と保存の操作）と#45（アカウント）は、自作の層の上に作る。
- 規則：この節のエンジンと自作の層の規則は、どれも、PoCのために仮に決めたもの（案）。保存先（3.4）の規則も、案（3.4の初め）。

**構成**

この節では、`internal/logdb` をエンジン、エンジンを使う `internal/store` の保存の層を自作の層と呼ぶ。メッセージの例は、データのディレクトリが `/srv/data` のときのもの（3.4と同じ）。

| パッケージ | 内容 | 使うもの |
| --- | --- | --- |
| `internal/logdb` | エンジン（この節の形・コミット・復旧・読み手・保守・バックアップ） | 標準ライブラリと `internal/logdb/vfs` だけ |
| `internal/logdb/vfs` | ファイルシステムの口（ファイル・ディレクトリ・同期・名前の変更・`flock(2)` のロック）と、Goの `os.Root` の上の実装（外を指すシンボリックリンクは、たどらない）。書き込みと同期を数える口（`vfs.Count`）も | 標準ライブラリだけ |
| `internal/logdb/simfs` | テストの模擬のファイルシステム（下記の「テスト」） | 標準ライブラリと `internal/logdb/vfs` だけ。テストだけが使う |
| `internal/logdb/dmlog` | dm-log-writes の記録を読んで、再生する（下記の「テスト」） | 標準ライブラリだけ。`internal/store` のテストだけが使う |
| `internal/store` | 保存先（3.4）。保存の層は、自作の層（`logbackend.go` と `events.go`）。口・確かめ・メッセージ・原本のコードは、保存の層の口（`backend.go`）の上にある | `internal/logdb`・`internal/logdb/vfs`・`internal/content` |

- 標準ライブラリだけ：`internal/logdb` とその下のパッケージは、`internal/store` と、標準ライブラリの外のモジュールを使わない。リポジトリのすべてが、`CGO_ENABLED=0` でもビルドでき、テストが通る（CIの `build without cgo`・`test without cgo`）。
- 設定：`Create`・`Open`・`OpenReader` は、保存先の既定の設定（3.4の「エンジンと設定」）でエンジンを使う。テストは、パッケージの中の口（`create`・`open`・`openLogReader` と、エンジンの設定）で、置き場所や設定を変える。
- 原本：原本（3.4の「原本」）は、`files/` に置く。原本のコードも、ファイルを `internal/logdb/vfs` で使うので、テストでは、模擬のファイルシステムに置ける。
- 確かめの置き場所：3.4の確かめ（書くときの確かめの順とメッセージ、読むたびのハッシュの確かめ、64MiBの上限、リビジョンを書き換えないこと）は、保存の層の口の上のコードにある。保存の層は、版・リビジョン・オブジェクトを置いて読むだけで、テストの模型も、同じ口を持つ（下記の「テスト」の差分テスト）。

データのディレクトリ：

| 名前 | 内容 |
| --- | --- |
| `files/` | 原本（3.4の「データのディレクトリ」） |
| `logdb/` | エンジンのディレクトリ |
| `logdb/lock/entry`・`logdb/lock/readers`・`logdb/lock/writer` | 空のファイル。`flock(2)` のロックにだけ使う（下記の「ロック」） |
| `logdb/log/<世代>-<番号>.log` | ログのセグメント。世代と番号は、1からの数を、小文字の16進数16桁で書く（`0000000000000001-0000000000000001.log`） |
| `logdb/objects/<16進数2桁>/<16進数64桁>` | ファイルに置くオブジェクト（置き場所Bのものと、混合の大きいもの。下記の「オブジェクトの置き場所」）のファイル。名前は、中身のSHA-256 |
| `logdb/objects/<16進数2桁>/.tmp-<ランダムな16進数16桁>` | 書いている途中のオブジェクト。プロセスが途中で止まったときと、同期に失敗したときだけ残る |
| `logdb/checkpoint` | チェックポイント（下記）。名前の変更で置き換える |
| `logdb/.tmp-checkpoint-<ランダムな16進数16桁>` | 書いている途中のチェックポイント。プロセスが途中で止まったときだけ残る |
| `logdb/head` | 書くプロセスが同期したログの終わり。ほかのプロセスの読み手のためのもの（下記の「ほかのプロセス」） |

規則：

- モード：ディレクトリは0700、ファイルは0600で作る。あるもののモードは、変えない（3.4と同じ）。
- 知らない名前：`logdb/` の中の、上の表に無い名前は見ない。`logdb/log/` の中の、セグメントの名前でないものは、壊れているとして拒む（`/srv/data/logdb/log/x: corrupt: not the name of a segment`）。シンボリックリンクと、種類の違うもの（ディレクトリであるべきところのファイルなど）は、3.4と同じ形のメッセージで拒む（`/srv/data/logdb/head: symbolic links are not allowed` など）。
- 作る：`files/` と `logdb/` を作り、データのディレクトリを同期してから、エンジンを作る（ロックのファイル・初めのセグメント・`head` を作り、セグメントと `head` と、ディレクトリを同期する）。それから、1回の `Update` で、表の版（3.4の「表」）を書く。

正本と、そこから作るもの：

| もの | 正本か、作るものか | 作り直し |
| --- | --- | --- |
| ログ（`logdb/log/`） | 正本。すべてのコミット（表の変更・ログの中のオブジェクト・監査イベント） | - |
| オブジェクトのファイル（`logdb/objects/`） | 正本（ファイルに置くオブジェクトの中身） | - |
| 原本（`files/`） | 正本（3.4） | - |
| チェックポイント | 作るもの（あるコミットの後の状態） | ログから作れる。壊れていれば使わず、ログを世代の初めから読む |
| メモリの状態（表・ハッシュからオブジェクトの位置への索引・イベントの数） | 作るもの（エンジンの中の索引） | 開くたびに、チェックポイントとログから作る |
| `head` | 作るもの（読み手のための写し） | 壊れていれば、書くプロセスが開くときに書き直す |

- チェックポイントは、無くてもよい：世代のログは、いつも、状態のすべてを持つ（古いログを消すのは、保守モードの圧縮だけで、圧縮は、新しい世代の初めに、状態のすべてを書く。下記の「保守モード」）。そのため、チェックポイントは、開くのを速くするだけで、無くても、壊れていても開ける。
- いまの版：保存先のいまの版（`documents`）は、版の履歴から決まるものだが、表として持ち、ほかの表と同じく、ログで確定する（3.4の `documents` と同じ）。エンジンの中の索引（ハッシュから位置、文書からいまの版）は、開くたびに作り直す（下記の「テスト」の差分テストは、チェックポイントを消して開き直すことも、くり返す）。

自作の層の表（表の版1）は、3.4の「表」。

**ファイルの形**

どのファイルも、形の版は1。整数は、大きさの決まったものはリトルエンディアンで、決まらないものはuvarint（Goの `encoding/binary` の可変長の形。必要より長く書いたものは拒む）。CRCは、CRC-32C（Castagnoli）。

| セグメント | `whrm-log` | 64バイト |
| チェックポイント | `whrm-ckp` | 64バイト |
| `head` | `whrm-hed` | 64バイトの欄が2つ（128バイト） |
| オブジェクトのファイル | `whrm-obj` | 16バイト |

変更の並びは、変更の数（uvarint）と、変更ごとに、1バイトの種類とその中身：

| 種類 | 変更 | 中身 |

| 4 | ファイルのオブジェクト | SHA-256（32バイト）・大きさ（uvarint） |

- 本体：次のイベントの番号と、イベントの数。表の数と、表ごとに（番号の順）、表の番号・キーの数・キーごとに（キーの順）キーの長さ・キー・値。オブジェクトの数と、オブジェクトごとに（ハッシュの順）、SHA-256・置き場所（1 ログの中：セグメント・位置・大きさ。2 ファイル：大きさ）。数と長さは、どれもuvarint。ファイルの大きさは、64+B。
- Sは、コミットか、ベースの終わり。コミットが1つも無ければ、書かない。

規則：

- 確かめる順：印と版があって、版が新しければ、大きさやCRCより先に拒む（新しい版は、見出しの大きさも変えるかもしれない。`/srv/data/logdb/log/0000000000000001-0000000000000001.log: format version 2, newer than this program knows (1)`）。それから、大きさ（`short file`）、印（`not a segment of whiteroom's log` など）、版0（`bad format version 0`）、CRC（`bad header CRC`。`head` の欄は `bad slot CRC`）、欄の中身の順に確かめる。新しい版のファイルは、どれも、何も変えずに拒む。
- 名前と見出し：セグメントの見出しの世代と番号は、ファイルの名前と同じでなければならない（違えば `the header names generation 1, index 3` のような理由で拒む）。
- 厳しい読み方：読んでから書き直すと、同じバイト列になるように読む。必要より長いuvarint（`bad uvarint`）、0でない予約のバイト（`nonzero reserved bytes`）、余るバイト（`trailing bytes`）、知らない種類（`unknown record type 4`・`unknown op 6`）は、拒む。
- ソルト：置き場所A（下記）では、文書のJSONが、レコードの中に入る。JSONの中に、正しいレコードに見えるバイト列を書けると、書きかけの末尾（下記の「復旧」）の後ろに正しいレコードがあることになり、開くのを拒ませることができる。レコードのCRCに、セグメントごとのランダムなソルトを入れるので、ソルトを知らなければ、そうしたバイト列は作れない。
- 上限：キーは4096バイトまで（`key too long: 5000 bytes (max 4096)`）。本体は268435456バイト（256MiB）までで、これが1回の `Update` の上限になる（`the transaction is too large: 300000000 bytes (max 268435456)`）。

**コミット**

1回の `Update` のコミットは、次の順に書く。

1. 変更が無ければ、何も書かない（キーの無いものを消すのも、変更にしない）。
2. 監査イベントに、状態の次のイベントの番号から順に番号を付け、レコードを作る。上限を超えれば、何も書かずに失敗する。
3. 置き場所B（下記）の、状態に無いオブジェクトのファイルを書く：`objects/<16進数2桁>/` を作り（あってもよい）、その中の一時ファイルに、見出しと中身を1回で書き、同期して閉じ、オブジェクトの名前に変える。それから、名前がディスクにあると知らないディレクトリ（作ったものも）を使ったときは、`objects/` を1回同期し、使ったディレクトリを、それぞれ1回同期する。
4. いまのセグメントにレコードが1つ以上あり、このレコードで `SegmentBytes`（既定は64MiB）を超えるなら、次の番号のセグメントを作り（見出しを書いて同期し、`log/` を同期する）、そこに書く。セグメントより大きなレコードは、新しいセグメントに1つだけ入る。
5. レコードを、セグメントの終わりに、1回の書き込み（`WriteAt`）で書き、セグメントを同期する。この同期が成功したときが、コミットの確定点。
6. 状態を公開する（それからの `View` が見る）。`head` を書き（同期しない）、ログがチェックポイントの後に `CheckpointBytes`（既定は64MiB）増えていれば、チェックポイントを書き始める（下記の「チェックポイント」）。

規則：

- 1つのコミットは、1つのレコード：セグメントの同期は、コミットごとに1回（グループコミットはしない）。`Update` は、プロセスの中で1つずつ動くので、同期していないレコードは、いつも、最後の1つだけ。これが、下記の「復旧」で、書きかけの末尾と、壊れたものを分けられる理由。
- 参照するものが先：オブジェクトのファイルと、その名前（ディレクトリの同期）は、それを指すレコードより先にディスクに置く。原本は、それを使うメディアの文書の `Update` より先に書く（3.4の「原本は先に書く」）。そのため、無いオブジェクトや原本を指すコミットはできない。途中で止まると、使われないファイルが残る（下記の「保守モード」の回収で消す）。
- あるディレクトリ：作ろうとしたディレクトリが既にあっても、名前がディスクにあると知らなければ、`objects/` を同期する（`Update` の失敗や、強制終了したプロセスが作ったディレクトリは、名前がまだディスクに無いことがある。原本のコードの同じ問題は、このPoCで見つけて直した。下記の「テスト」）。
- 同じ内容：状態か、同じトランザクションにあるハッシュのオブジェクトは、何も記録しない（下記の「オブジェクトの置き場所」）。
- 確定の後に公開：公開する状態は、復旧がレコードから作るのと同じコードで、レコードを書く前に作り、確定点の後に公開する。そのため、`View` は、確定したコミットだけを見る。

**失敗の扱い**

| 失敗 | 扱い |
| --- | --- |
| 確定点の前の書き込みの失敗（EIO・ENOSPC・短い書き込み）と、ファイルやディレクトリを作る・名前を変える失敗 | 書いたかもしれないレコードを切り戻し（セグメントを前の終わりで切り、同期する）、一時ファイルと、見出しを書けなかった新しいセグメントを消す（名前を変え終えたオブジェクトのファイルは残り、回収で消す）。その `Update` は、そのエラーで失敗し、保存先は使い続けられる（ENOSPCなら、空きを作れば、次の `Update` は書ける） |
| 切り戻しの失敗（切ること・その同期） | 止まる（下記） |
| 同期の失敗（レコード・オブジェクトのファイル・`objects/` とその下のディレクトリ・新しいセグメントと `log/`・開くときの同期・圧縮と回収の同期） | 止まる：その `Update` と、後のすべての `Update` が、`ErrFailed`（`the store has stopped after a sync failed; restart the machine before opening it again`）で失敗する。`Close` は、何も書かない |
| 圧縮の、ベースの終わりのレコードを書き始める前の失敗（同期のほか） | 古い世代のまま、使い続けられる（作りかけの新しい世代は、開くときに使わず、次の圧縮か回収で消す） |
| 圧縮の、ベースの終わりのレコードを書き始めてからの失敗 | 止まる（新しい世代ができたかが分からないので、古い世代に書き続けられない） |
| 回収で、ファイルを消す失敗 | そのエラーを返す。保存先は使い続けられる |
| チェックポイントの失敗 | 止まらない。一時ファイルを消す。自動のものは数え（`Stats`）、`Checkpoint` と `Close` は、エラーを返す |
| `head` を書く失敗 | 何も止めない（数えるだけ。同じ欄を書き直すので、もう1つの欄は正しいまま） |
| 開くときの読む失敗 | 開くのが失敗する。ファイルを何も変えない（末尾を切らない） |

- 同期をやり直さない：同期に失敗すると、Linuxは、ディスクに書けなかったページを、書いたものとして扱う（汚れていない印を付ける）ことがあり、後の同期は、それを書かずに成功する。そのため、失敗した同期を、もう一度呼んで信じることはしない。失敗した `Update` が残るかは分からず、開き直した後は、すべてあるか、無いかのどちらか。
- 再起動してから開き直す（F1）：同期に失敗した後、マシンを再起動せずに開き直すと、エンジンは、ページキャッシュにだけある変更（ディスクには書かれない）を、ディスクにあるものとして、続きを書く。その後にクラッシュすると、最後のレコードより前が壊れたログが残る（開くのを拒むか、チェックポイントから開けても、`Verify` と `Events` が失敗する。テストでは、黙って中身が変わることは無かった）。このPoCで見つけた（下記の「テスト」）。そのため、`ErrFailed` の文で、マシンを再起動してから開き直すように伝え、開くときの同期（最後のセグメントと `log/`）の失敗も、`ErrFailed` にした。プロセスを再起動するだけ（systemdの自動の再起動など）では足りない。エンジンは、再起動したかを確かめない（下記の「運用の制約」と「残る危険」。6.12の129）。
- 原本（F2）：原本の同期の失敗は、3.4の「原本」の「同期の失敗」（原本の保存を止める）。これも、このPoCで見つけて直した。

**チェックポイント**

- 中身：ある公開した状態（すべての表、オブジェクトの位置、イベントの数）と、その最後のレコードS（世代・番号・セグメント・位置・CRC）。
- 書き方：一時ファイル（`.tmp-checkpoint-<ランダムな16進数16桁>`）に、本体を流しながら書き（CRCも求める）、見出しを書き、同期して閉じ、`checkpoint` に名前を変え、エンジンのディレクトリを同期する。そのため、クラッシュで壊れることは無い（前のものか、新しいもののどちらか）。
- いつ書くか：ログが前のチェックポイントの後に `CheckpointBytes`（既定は64MiB）増えたときに、`Update` の後に、バックグラウンドで書く（`Update` は待たない。テストでは、`Update` の中で書く設定もある）。`Close` は、最後のコミットのものを書く（動いているものを待ってから）。`Checkpoint` を呼んでも書く。前のものより新しい状態のものだけを書く。
- ログと組にする：開くときに使うのは、ログの、チェックポイントの示す位置に、その番号とCRCの正しいレコード（コミットか、ベースの終わり）があるときだけ（下記の「復旧」）。
- ログを消さない：チェックポイントは、セグメントを消さない（ログを消すのは、保守モードの圧縮だけ）。

**復旧**

書くプロセスが開くとき（`Open`）は、次の順にする。

1. ディレクトリの形（`lock/`・ロックのファイル・`log/`・`objects/`・`head`）を確かめ、ロックを取る（下記の「ロック」）。
2. `log/` の名前を読み、世代ごとに分ける。
3. チェックポイント：無ければ使わない（`none`）。壊れていれば（大きさ・印・CRC・読めない本体）、使わずに、ログを初めから読む（`damaged: <理由>`）。新しい版なら、拒む。
4. 世代：完全な世代のうち、いちばん新しいものを使う。世代1は、いつも完全。2からの世代は、ベースの終わりのレコードが正しければ、完全。それより新しい、完全でない世代（圧縮の途中で止まったもの）は、使わずに残す（次の保守で消す）。チェックポイントが、完全でない世代を指していれば、拒む（`/srv/data/logdb/checkpoint: corrupt: names generation 3, which is incomplete`）。
5. その世代のセグメントは、1から続いていなければならない（`/srv/data/logdb/log: corrupt: missing segment 2 of generation 1`）。
6. 初め：その世代のチェックポイントが、ログと組になれば、その状態から始め、その後のレコードを読む。チェックポイントのセグメントより前のセグメントは、読まない。組にならなければ、拒む（`/srv/data/logdb/checkpoint: corrupt: the log does not have sequence 9 at /srv/data/logdb/log/0000000000000001-0000000000000002.log offset 352`）。その世代のチェックポイントが無ければ、世代の初めから読む。
7. 読む：どのレコードも、正しく、番号が続かなければならない。正しくない初めのレコードは、下の表のとおりにする。
8. ここまでは、ファイルを何も変えずに決める。それから、自作の層の表の版を確かめ（3.4の「エンジンと設定」）、決めた変更（書きかけの末尾を切る・作りかけのセグメントを消す）をし、最後のセグメントと `log/` を、いつも同期し、`head` を書く。

正しくない初めのレコード（位置X）の扱い：

| 見つけたもの | 最後のセグメント | それより前のセグメント |
| --- | --- | --- |
| 途中で終わる・長さが範囲の外・CRCが合わないレコードで、その後ろ（8バイトの倍数の位置）に、CRCが合って、番号が後のレコードが無い | 書きかけの末尾：Xで切る | 拒む |
| 同じで、その後ろに、CRCが合って、番号が後のレコードがある | 拒む（`a valid record follows at offset 416` のような理由） | 拒む |
| CRCが合うのに、0で埋めるところが0でない・本体を読めない・番号が違う | 拒む（書き終えたレコードなので、切ると、新しい版のプログラムの書いたコミットを捨てるかもしれない） | 拒む |
| 見出しが正しくなく、64バイトの後がすべて0 | 作りかけのセグメント：消す（世代1のセグメント1は、拒む） | 拒む |
| 見出しが正しくなく、64バイトの後に0でないバイトがある | 拒む | 拒む |
| 読む失敗（EIOなど） | 開くのが失敗する（切らない） | 同じ |

拒むときは、ファイルと位置と理由を付けたエラーにする（`/srv/data/logdb/log/0000000000000001-0000000000000001.log: corrupt at offset 352: truncated record`）。拒んだときは、ファイルを何も変えない。

規則：

- 分けられる理由：同期していないレコードは、いつも最後の1つだけ（上記の「コミット」）。そのため、クラッシュで残る正しくないレコードは、最後のセグメントの最後のものだけで、正しくないレコードの後ろに正しいレコードがあることは、クラッシュでは起きない（壊れている）。正しい過去のレコードを、黙って捨てることは無い。圧縮のベースは、ベースの終わりの前に同期するので、ベースの中の書きかけは、世代が完全でないことになる（その世代を使わない）。
- 開くときの同期：切るものが無くても、最後のセグメントと `log/` を同期する。強制終了したプロセスが、ページキャッシュにだけ残したレコードや、作ったセグメントの名前を、続きを書く前に、ディスクに置くため。この同期の失敗も `ErrFailed`（上記の「失敗の扱い」）。
- 残る曖昧さ：最後のレコードが、クラッシュでなく、ディスクの故障などで壊れたときも、書きかけの末尾に見えるので、切る（そのコミットが無くなる）。SQLiteのWALにも、同じ曖昧さがある：開くときの復旧は、WALを初めから読み、チェックサムの合わない初めのフレームで止まり、その前の、最後のコミットのフレームまでを使う（SQLiteの文書の「Database File Format」の4.1と、「WAL-mode File Format」の3）。そのため、SQLiteでは、WALの途中のフレームが壊れても、そこから後のコミットは使わない（このエンジンは、最後のレコードより前の傷では、開くのを拒む）。チェックポイントが、これを狭める：`Close` は、最後のコミットのチェックポイントを書くので、閉じた後に最後のレコードが壊れれば、チェックポイントと組にならず、拒む。最後のレコードが、チェックポイントのレコードより後にあるとき（クラッシュの後など）だけ、この曖昧さが残る。
- チェックポイントの前は読まない：チェックポイントから開くときは、そのセグメントより前のセグメントを読まないので、そこが壊れていても、開くときには分からない（`Verify`・`Events`・圧縮が見つける。6.12の131）。
- `head`：`head` は、読み手のためのもので、書くプロセスは、ログを終わりまで読み、`head` を使わない。壊れていれば（大きさ・正しい欄が無い）、書き直す。新しい版なら、拒む。

**スナップショット**

- メモリの状態：表ごとの、書き換えない木（キーの順の木で、変えるときは、変わる道だけを写す）と、ハッシュからオブジェクトの位置への索引と、数。公開した状態は書き換えず、`Update` が新しい状態を作って、取り替える。
- `View`：関数が初めに読んだときの状態を、終わりまで見る（3.4と同じ）。ロックを取らず、`Update` を待たない。
- `Update` の中：読む操作（キーの `Get`・`Scan`、オブジェクト）は、同じ `Update` の書いたものを見る。
- 木の形：キーの優先度を、プロセスごとのランダムな種のハッシュ（Goの `hash/maphash`）で決めるので、細工したキーで、木を偏らせることはできない。
- 監査イベント：メモリには数だけを持ち、`Events` が、ログから読む。
- `Close` の間：`Close` のときに動いている `View` は、終わるまで読める（セグメントのファイルは、最後の `View` が閉じる）。

**ほかのプロセス**

- 読み手：ほかのプロセス（後のビルド・`whiteroom backup`・`whiteroom doctor` など。9.2）は、保存先を、読み手として開く（エンジンの `OpenReader`。保存先では `OpenReader`。3.4の「同時に使う」）。読み手は、ファイルを書かず、切らず、消さない（同期はする。下記）。`Update` は `read-only transaction`、`PutOriginal` は `the store is opened to read only` で失敗する。読み手を開くときも、表の版を確かめる。
- `head`：書くプロセスは、コミットのたびに、同期したログの終わり（世代・セグメント・位置・番号・最後のレコードのCRC）を、`head` の2つの欄に、交互に書く（同期しない。作るときと閉じるときだけ同期する）。読み手は、正しい欄のうち、書いた数の大きいほうを使う（書いている途中の欄は、CRCで分かる）。どちらも正しくなければ、1ミリ秒おきに、3回まで読み直す。
- 書くプロセスがあるとき：`head` の示すレコードまでだけを読む。それが、読んだ最後のレコードでなければ、拒む（`/srv/data/logdb/head: corrupt: the log does not match head`）。書いたが、まだ同期していないレコード（失敗すれば、切り戻すもの）は、見ない。
- 書くプロセスが無いとき：`lock/writer` を共有で持ち（その間、書くプロセスは始まらない）、ログを、最後の正しいレコードまで、復旧と同じ規則で読む（書きかけの末尾は、そこで終わりとし、切らない）。読んだレコードのセグメントを同期してから、ロックを放す。強制終了した書くプロセスが、ページキャッシュにだけ残したレコードを、見せる前に、ディスクに置くため。
- 読み直し：`View`（と `Events`）のたびに、関数を呼ぶ前に、新しく同期したコミットを読む。失敗すれば、関数を呼ばずに、エラーを返す。`head` が、読み手の状態より古いとき（書くプロセスが、`head` を書く前に止まったときなど）は、何もしない（戻らない）。
- セグメントの切り替え：読み手は、次のセグメントに続けて読む。見出しが正しくなかったセグメントは、開いたままにせず、次の読み直しで開き直す（書くプロセスの復旧が消して、同じ名前で作り直すことがあるため）。
- チェックポイントの置き換え：読み手は、開いた後は、チェックポイントを読まないので、置き換えの影響を受けない。
- 世代：読み手が開いている間は、保守モードが動かないので、世代は変わらない。
- 同期の失敗：読み手の同期が失敗すれば、読み手も止まる（`ErrFailed`）。
- 遅れ：書くプロセスの `head` を書く失敗が続く間は、読み手は、その前のコミットまでしか見ない。

**ロック**

3つのロックのファイル（`lock/entry`・`lock/readers`・`lock/writer`）に、`flock(2)` で、共有か排他のロックを取る。取る順は、どこでも `entry`・`readers`・`writer` で、放すのは、その逆の順。

| 開くもの | `lock/entry` | `lock/readers` | `lock/writer` |
| --- | --- | --- | --- |
| 書くプロセス（`Open`） | 共有。待たない（取れなければ `/srv/data/logdb: maintenance is running`）。ほかの2つを取ったら放す | 共有。待たない。閉じるまで持つ | 排他。`WriterWait`（既定は2秒）まで、10ミリ秒ごとに試す（取れなければ `/srv/data/logdb: another process holds the writer lock`）。閉じるまで持つ |
| 読み手（`OpenReader`） | 共有。待たない。`lock/readers` を取ったら放す | 共有。待たない。閉じるまで持つ | 読み直すたびに、共有で、待たずに試す。取れれば、ログの終わりを読んで同期する間だけ持つ |
| 保守（`Maintain`） | 排他。取り消し（Goの `context`）まで待つ（10ミリ秒から、間を倍にして100ミリ秒ごとまで） | 排他。同じ | 排他。同じ |

- 待つもの：開くもの（書くプロセス・読み手・バックアップ）は、`lock/entry` と `lock/readers` を待たない（保守が動いていれば、すぐに失敗する）。書くプロセスは、`lock/writer` を2秒まで待つ（読み手が、ログの終わりを読む間、持つため）。保守は、3つを順に、取り消しまで待つ。
- デッドロックしない理由：読み手は、何も待たない。待っている書くプロセスが待つのは、`lock/writer` を持つもの（開いている書くプロセスか、読み手の短い読み直し）で、それらは何も待たない（保守は、書くプロセスが `lock/readers` を共有で持つ間は、`lock/readers` を取れないので、`lock/writer` を持たない）。保守が待つのは、前のロックを持ったままで、次のロックを持つものだけで、それらは保守を待たない。どの待ちにも、上限（2秒か、取り消し）がある。強制終了したプロセスのロックは、カーネルが放す。
- 試したこと：書くもの2つ・読み手2つ・保守1つが、開いて閉じるのを繰り返すのを、同時に1秒動かしても、どれも返った（`TestNoDeadlock`。同じプロセスの中で、ロックのファイルを別々に開いたもので、`flock(2)` は、これを別のプロセスと同じに扱う）。読み手のプロセスを `SIGKILL` で止めると、それを待っていた保守は、55〜66ミリ秒の後に進んだ（`TestKilledReaderReleasesMaintenance`）。
- 飢え：書くプロセスは、`lock/writer` を待つ間、`lock/entry` を共有で持つので、開こうとし続ける2つ目の書くプロセスがあると、保守が `lock/entry` を取れないことがある（上のテストで、書くもの2つの横では、保守が入れたのは1秒に1〜6回で、書くものが1つなら29〜39回だった。`-race` の有無で、3回ずつ）。書くプロセスが1つ（管理のサーバー）なら、読み手が閉じれば、保守の番になる（6.12の135）。
- 2つ目の書くプロセス：2秒の後に拒む（3.4の「同時に使う」）。
- `flock(2)` の無いシステム：ロックを取るときに失敗する（`cannot lock …: logdb needs flock(2), which windows does not have` など）。

**保守モード**

- 入る（`Maintain`）：3つのロックを、排他で取り（上記の「ロック」）、書くプロセスとして開き（復旧をする）、渡した関数を動かして、閉じる。動いている間、ほかのプロセスは、開けない（`maintenance is running`）。
- 圧縮（`Compact`）：いまの状態を、渡した書き直し（`Rewrite`：値を書き換えるか、キーを落とす。オブジェクトを落とす。イベントのデータを書き換えるか、落とす）を通して、次の世代の初めのレコード（ベース）に書く。
  1. ほかの世代のセグメント（前の圧縮が途中で止まって残したもの）を、最後のものから消す（消すたびに、`log/` を同期する）。
  2. 次の世代のセグメント1を作る（見出しの初めのレコードの番号は、いまの最後のコミットの番号S。新しいソルト）。
  3. ベースのレコード（1つが約4MiBの変更。それより大きい変更は1つだけ）を書く：表（番号とキーの順）、オブジェクト（ログの中のものは、古いセグメントから読み、SHA-256を確かめて、中身ごと。ファイルのものは、ハッシュと大きさ）、古い世代のイベント（番号とコミットの番号を変えない）。セグメントが一杯になれば、同期してから、次のセグメントを作る。
  4. ベースを同期し、ベースの終わりのレコードを書いて、同期する。これが、圧縮の確定点。
  5. メモリの状態を、新しい世代のものにし、チェックポイントと `head` を書き、古い世代のセグメントを、最後のものから消して、`log/` を同期する。チェックポイントを書けなければ、古い世代のセグメントを残す（回収で消す）。
- どこで止まっても：古い世代（新しい世代は、完全でないので使わない）か、新しい世代（完全）のどちらかになり、混ざらない。新しい世代のコミットは、S+1から続く。
- いちばん新しい完全な世代を使う理由：ベースの終わりと、新しいチェックポイントの間でクラッシュすると、古いチェックポイントは、古い世代を指す。それを使うと、書き直して消したデータ（個人情報など）が戻り、消すはずの世代に、書き続けることになる。
- 回収（`CollectGarbage`）：いまの世代でないセグメント（最後のものから。消すたびに `log/` を同期する）、`objects/` の中の、状態がファイルに持たないオブジェクトのファイル（圧縮で落としたもの・失敗した `Update` が書いたもの）と一時ファイル、チェックポイントの一時ファイルを消し、変えたディレクトリを同期する。ほかの名前は、残す。
- 書くプロセスが止まっている間にできること：読み手（ログを終わりまで読み、同期する）、バックアップ（読み手として）、保守（読み手も無いとき）。
- 検出と修復（9.2の `whiteroom doctor`。作っていない。6.12の131）の制約（案）：エンジンは、壊れたものを、黙って直さない。開くときに変えるのは、書きかけの末尾を切ること・作りかけのセグメントを消すこと・`head` を書き直すことと、同期だけ。確かめること（`Verify`：ログをディスクから読み直して、メモリの状態と比べ、すべてのオブジェクトのハッシュを確かめる）は、読み手でもでき、書くプロセスが動いていてもよい。ファイルを変える修復（壊れたものを落とす圧縮・回収など）は、保守モードでだけする。正しいコミットを捨てる修復（壊れたレコードから後を切ることなど）は、自動ではせず、操作する人が決める。
- バックアップ（`Backup`。保存先では、テストの `backupLog`）：保存先を読み手として開き（その間、保守は動かない）、そのときの、最後の同期したコミット（位置P）を決める。それから、保存先の `backupLog` が、原本（`files/`。一時ファイルは除く）をコピーし、エンジンが、セグメントをPまでコピーし（最後のものは、Pで切る）、チェックポイントを、Pまでのログと組になるときだけコピーし、状態のオブジェクトのファイルをコピーし、Pを示す `head` を書く。どのファイルも同期し、それからディレクトリを同期する。書くプロセスは、その間も書き続けてよく、元のファイルは、何も変えない。コピーの先は、無いか、空のディレクトリ。失敗したら、空にしてから、やり直す。リストアは、コピーを開くこと。
- 原本を、位置の後にコピーする理由：Pまでのコミットが指す原本は、そのコミットより前に書いたので、Pを決めた後にコピーすれば、すべてある（Pの後に書いた原本も入ることがあるが、使われない原本が増えるだけ）。

**オブジェクトの置き場所**

置き場所は、オブジェクト（文書とリビジョンのJSON）の中身を、どこに置くか。どれでも、論理のCAS（SHA-256で指し、同じ内容は1つ）は同じで、変わるのは、物理的な置き場所だけ。

| 置き場所 | ベンチマークの名前 | 中身 | レコードに入るもの |
| --- | --- | --- | --- |
| A | `log-inline` | コミットのレコードの中 | 中身 |
| B | `log-files` | オブジェクトのファイル（`objects/<16進数2桁>/<16進数64桁>`） | ハッシュと大きさ |
| 混合 | `log-hybrid` | `Threshold`（既定は64KiB、65536バイト）以上はファイル、ほかはレコードの中 | どちらか |

- 同じ内容：状態か、同じトランザクションにあるハッシュのオブジェクトは、何も記録しない（どの置き場所でも。`Update` をまたいでも、開き直した後も）。
- 読む：Aは、セグメントの位置から読む（読んだセグメントのファイルを、閉じるまで開いたまま使う。データのキャッシュは無い）。Bは、ファイルの見出しと大きさを確かめて読む。エンジンは、中身をハッシュと照らさない（照らすのは保存先。3.4の「読むたびに確かめる」）。`Verify` と圧縮は照らす。
- 無いとき：状態に無いハッシュは、無いことの分かるエラー（`object 9f86…: file does not exist`。`fs.ErrNotExist`）。状態にあるのにファイルが無いのは、壊れている（`/srv/data/logdb/objects/9f/9f86…: missing file`。`fs.ErrNotExist` にはしない）。
- 原本：メディアの原本は、どの置き場所でも、`files/` に置く（3.4の「原本」）。
- 評価：下記の「置き場所の評価」（ベンチマークの結果から）。保存先は、混合（64KiB）を使う（3.4の「エンジンと設定」。6.12の137）。

**イベント・操作のID・暗号化の封筒**

- 監査イベント（まだ公開の口ではない。口の形は#47で決める）：`Update` の中で足し（保存先では `appendEvent`。Content Storeの口ではない）、ほかの変更と同じレコードに入る。そのため、イベントは、その `Update` のほかの変更があるときだけある。番号は、コミットのときに、状態の次の番号から付けるので、失敗した `Update` と取り消した `Update` は、番号を空けない。メモリには数だけを持ち、ログから読む（`Events`）。圧縮は、番号とコミットの番号を変えずに写す（書き直しで落とせば、番号が空く）。
- 操作のID：エンジンには、そのための機能は無い。呼ぶ側が、変更と同じ `Update` で、操作のID（`ops/<ID>` のキー）を置く。返事が届く前にクラッシュしても、開き直した後に、そのキーで、コミットしたかが分かり、2度しない（監査イベントも、2度書かない）。確定点の前・書いた後・同期した後・返事の後のクラッシュ（ページキャッシュを残すものと、失うもの）で確かめた（`TestOperationID`）。
- 暗号化の封筒：どの値も、初めの1バイトが封筒（0 そのまま。1 暗号化：鍵のID・ノンス・暗号文。上記の「ファイルの形」）。エンジンは、そのままの値だけを書き、暗号化した値は読まない（`sealed values are not supported by this version`）。テストで、標準ライブラリのAES-256-GCM（`crypto/aes`・`crypto/cipher`）で値を暗号化して開けること、鍵のIDも認証されること、鍵を消すと開けないこと（`key 7 is gone`）を確かめた（`TestSealedValue`）。
- 鍵は、ログに置かない：追記するだけのログに置いた鍵は、書き直さなければ消せない。鍵は、ログの外の、消せる場所に置く（下記の「個人情報の削除」）。
- 封筒の限界（決めていない。6.12の138）：認証する追加のデータは、封筒のバイトと鍵のIDだけで、表とキーを含まないので、暗号化した値を、ほかのキーに移せる。ランダムなノンスでは、1つの鍵で暗号化してよいのは、2^32回まで（NIST SP 800-38D の8.3）。

**対象のOSとファイルシステム**

- 対象：Linuxの、ローカルのファイルシステム（ext4・xfs・btrfs）を、1つのマシンから使う。確かめたのは、ext4（NVMeのSSDの上）だけ（ほかは6.12の130）。ネットワークのファイルシステムは、対象の外。
- 前提：ファイルの同期（`fsync`）は、その中身をディスクに置く。ディレクトリの同期は、その中の名前の変更（作る・消す・名前を変える）を、ディスクに置く。同じディレクトリの中の名前の変更は、すべてあるか、無いかのどちらか。新しいファイルの名前は、ディレクトリを同期するまで、ディスクにあるとみなさない（ext4などより厳しい前提。下記の「テスト」の模擬のファイルシステム）。
- ほかのシステム：`flock(2)` のあるシステム（darwin・dragonfly・freebsd・illumos・linux・netbsd・openbsd）では、ロックも動くはずだが、Linuxのほかでは動かしていない（darwinとwindowsで、`go vet` が通ることだけを確かめた）。ほかのシステムでは、ロックを取るときに失敗する（上記の「ロック」）。

**制限**

- 1回の `Update`：レコードの本体が256MiB（268435456バイト）まで。置き場所Aでは、レコードに文書とリビジョンのJSONが入る（Bでは、ハッシュと大きさだけ）。保存先の混合では、64KiB以上のJSONが、ハッシュと大きさだけになる（3.4の「エンジンと設定」）。1つの文書の64MiBの上限は、別（3.4の「上限」）。6.12の136。
- メモリ：状態（すべての表のキーと値、オブジェクトの位置）を、メモリに持つ。開くときは、チェックポイントと、その後のログを読むので、開く時間は、チェックポイントの後のログとともに延びる（下記の「ベンチマークの結果」。6.12の132）。
- 書くプロセスは1つ：2つ目は、2秒の後に拒む（上記の「ロック」。6.12の135）。
- 読み手：ほかのプロセスは、読み手として開かなければならない（書くプロセスがあれば、`Open` は拒む）。
- 開いたファイル：読んだセグメントのファイルを、閉じるまで開いたままにする（書くプロセスも読み手も。セグメントの数だけ増える。6.12の132）。
- `Events` と `Verify`：セグメント（既定は64MiBまで）を、1つずつ、すべてメモリに読む（6.12の132）。
- データのディレクトリの名前：データのディレクトリ自身の名前（親のディレクトリの中のもの）を、保存先は、同期しない（6.12の130）。
- 作りかけのセグメント：見出しを書けなかった新しいセグメントを消すのにも失敗すると、開き直すまで、新しいセグメントを作れない（その間、セグメントを替える `Update` は失敗する）。
- ファイルのモード：開くときに、緩いモード（グループが読めるなど）を拒まない。エンジンは0700・0600で作るので、別のUnixユーザーの読み手（9.2の「公開用と管理用を別プロセス・別Unixユーザー」）は、そのままでは読めない（6.12の134）。

**テスト**

模擬のファイルシステム（`internal/logdb/simfs`）：

- 持つもの：メモリの中のディレクトリとファイル。それぞれ、ディスクにあるもの（同期したもの）と、ページキャッシュにだけあるもの（同期していない書き込み・切り詰め・名前の変更）を、分けて持つ。
- ディスクに置く規則：ext4などより厳しいPOSIXの規則で、ファイルの中身は、そのファイルの同期で、名前は、そのディレクトリの同期で、はじめてディスクに置く。ディレクトリをまたぐ名前の変更は、新しい名前と古い名前を別に扱い、ファイルそのものは失わない。
- クラッシュの型：同期していない変更を、すべて失う・すべて残す・初めから順にいくつかを残す（最後の書き込みが途中まで残るものと、大きさだけ残って中身が0のものも）・一部だけを残す（後に書いたものだけが残るものも。少なければ、すべての組み合わせを、多ければ、種を決めたランダムな組み合わせを試す）。
- 失敗の差し込み：どの操作にも、EIO・ENOSPC・短い書き込みと、同期の失敗（同期しなかった変更が、ディスクに行かないまま、ページキャッシュには残るもの。Linuxで、同期に失敗した後に起きることがある）を返せる。
- プロセス：ある操作の後に強制終了したプロセス（ロックを放し、書いたものはページキャッシュに残る）と、止まったまま、ロックを持ち続けるプロセス。
- OSと同じ：16の操作の並びの結果（値・エラーの型・メッセージ）が、Linuxの `os.Root` と同じであることを確かめる。

エンジンのテスト：`internal/logdb` には、140のテストの関数がある（形・表・コミット・失敗・復旧・チェックポイント・世代・読み手・保守・バックアップと、下記の行列とプロセス）。レコードの本体の読み方は、ファジング（`FuzzBody`）でも確かめた（120秒で約970万の入力。失敗なし）。

このPoCで見つけて直したもの：

- 原本のディレクトリ（#42からのもの。09d7691）：`PutOriginal` は、原本の `files/<16進数2桁>/` が既にあるとき、`files/` を同期しなかった。`files/` の同期に失敗した `PutOriginal` や、強制終了したプロセスが作ったディレクトリは、名前がまだディスクに無いことがあるので、後の `PutOriginal` が成功を返しても、クラッシュで原本が消えることがあった。保存先は、名前がディスクにあると分かったディレクトリを覚え、ほかは同期するようにした（3.4の「原本」）。当時のSQLiteの保存の層も、同じコードだった。
- F1（581260c）：同期に失敗した後、マシンを再起動せずに開き直すと、後のクラッシュで、ログが壊れる（上記の「失敗の扱い」）。エンジンの失敗の差し込みの行列が見つけた：開くときに書きかけの末尾を切り、その同期が失敗した（変更は捨てられた）。もう一度開くと、切った後のものがページキャッシュにあるので、切ることも同期することも無い。後の `Update` が次のセグメントに書いた後でクラッシュすると、最後でないセグメントに、書きかけの末尾が戻った（`/srv/data/logdb/log/0000000000000001-0000000000000001.log: corrupt at offset 352: truncated record`）。`ErrFailed` の文を変え、開くときの同期の失敗も `ErrFailed` にした。
- F2（233c0fa）：`PutOriginal` の同期に失敗した後、同じ起動の間の `PutOriginal` が、名前がディスクに無い原本に、成功を返すことがあった（同期に失敗した、`files/` の新しいディレクトリの名前が、ページキャッシュにだけあり、後の `files/` の同期は、それを書かずに成功する）。保存先の失敗の差し込みの行列が見つけた。同期に失敗したら、原本の保存を止めるようにした（3.4の「原本」の「同期の失敗」）。当時のSQLiteの保存の層も、同じコードだった。
- ほかに、エンジンと自作の層の間違いは、クラッシュ・強制終了・失敗の差し込み・差分のテストでは、見つからなかった。

まだ確かめていないもの：

- 電源断：模擬のファイルシステムは、モデルで、電源断に強いことの証明にはならない。dm-log-writes の記録も、動かしていない（上記。6.12の130）。
- 同期の失敗の後：模擬のファイルシステムの、同期の失敗（変更を捨てる）で確かめただけで、実際のカーネルとディスクで確かめていない。
- ほかのファイルシステム（xfs・btrfs）、ほかのカーネルとマウントの設定、Linuxのほかのシステム（6.12の130）。
- 長く動かすこと（多くのセグメント、長い期間）と、ベンチマークより大きいデータ（6.12の132）。

**ベンチマークの条件**

#66 で、SQLiteの保存の層を外した。ベンチマークのコード（`TestBenchmarks`）は、いまは、自作の層の3つの置き場所だけを測る。この下の条件と、下記の「ベンチマークの結果」（どちらもSQLiteを含む）は、#66 の前に、コミット f026575 のコードで測ったもの。

SQLiteと、自作の層の3つの置き場所（オブジェクトを、ログに入れる・1つずつファイルにする・大きいものだけファイルにする）を、同じデータのセットと同じ操作で比べる。

動かし方：

- テスト：`TestBenchmarks`（`internal/store/bench_test.go`）。環境変数 `WHITEROOM_BENCH` で結果のディレクトリを渡したときだけ動き、渡さなければ、すぐに飛ばす。`-race` は付けない（付けると、失敗する）。Goのランタイムの設定（`GOGC` など）は、既定のまま：`WHITEROOM_BENCH=<結果のディレクトリ> WHITEROOM_BENCH_DIR=<作業のディレクトリ> go test -count=1 -run '^TestBenchmarks$' -timeout 0 ./internal/store`
- 作業のディレクトリ：データのディレクトリは、回（下記）と保存の層ごとに、`WHITEROOM_BENCH_DIR`（無ければ `os.TempDir()`）の中に作り、その保存の層のシナリオ（下記）の後に消す。作業のディレクトリは、実際のディスクに置く（tmpfsなどのメモリには置かない）。
- プロセス：シナリオ（下記）ごとに、テストの実行ファイルを、別のプロセスで動かす（`TestBenchHelper`。することは `WHITEROOM_BENCH_HELPER` で渡し、渡さなければ、すぐに飛ばす）。そのため、最大RSS（下記）は、シナリオごとに測れる。2時間を超えたプロセスは止め、ベンチマークは、そこで失敗する。
- 初めの確かめ：初めに、どのセットも、`load`（下記）のすべての保存を作り、`Put` と `AddRevision` が文書とリビジョンを確かめるのと同じ確かめ（大きさ・読み込み・文書の `id`。3.4の「書くときの確かめ」）を通ることと、下記の大きさであることを確かめる。
- 小さな試し：`WHITEROOM_BENCH_SMOKE=1` では、仕組みを確かめるために、100文書のセット（`smoke`：エントリー70・ターム20・メディア10で、2回目の保存は14）を、保存の層ごとに1回だけ動かす（初めの確かめは、下記のすべてのセットにもする）。

保存の層：

| 名前 | 保存の層 |
| --- | --- |
| `sqlite` | SQLite（#66 の前の3.4）。`internal/db` の設定のまま（WAL、`synchronous` は `FULL`、`busy_timeout` は5秒など） |
| `log-inline` | 自作の層。オブジェクト（文書とリビジョンのJSON）を、ログに入れる |
| `log-files` | 自作の層。オブジェクトを、1つずつファイルにする |

- 自作の層の設定：エンジンの既定値。ログのセグメントは64MiBまで。チェックポイントは、ログが64MiB増えるたびに、バックグラウンドで書く（`Update` は待たない）。書くロックは、2秒まで待つ。テストの保存の層（`allBackends`）の設定（ロックを待つのは50ミリ秒で、チェックポイントは `Update` の中で書く）は使わない。`log-hybrid` は、#66 の後の保存先の既定の設定と同じ（3.4の「エンジンと設定」）。

- 原本：どの保存の層でも、原本（`PutOriginal`）は使わない。

- 乱数：種は63（Goの `math/rand/v2` のPCG）。保存ごとに、その番号から作った生成器で作るので、どの保存の層でも、どの回でも、同じ文書を、同じ順に保存する。保存の順と、`ops`（下記）の読む文書も、それぞれの生成器で決めるので、どれでも同じ。
- `docs-` のセット：初めに、ターム・メディア・エントリーを、この順に、IDの順に1回ずつ保存する。それから、エントリーの2割をランダムに選び、ランダムな順に、もう1回保存する。保存のたびに、監査イベントを1件足す。
- `history-heavy`：すべてのエントリーを、回ごとにランダムな順に1回ずつ保存することを、10回くり返す（1回目で作る）。保存のたびに、監査イベントを10件足す。
- 1回の保存：文書の `Put` と、エントリーなら、新しいリビジョンの `AddRevision` と、監査イベントを、同じ `Update` でする。エントリーの `publishedRevision` は、その保存のリビジョンにする（そのため、同じエントリーの保存でも、版のJSONは毎回違う）。
- まとめ方：保存は、段階（`docs-` のセットは、初めの保存と2回目の保存の2つ。`history-heavy` は、10の回）ごとに、初めから500（`history-heavy` は100）ずつ、1つの `Update` にまとめる。段階の最後の `Update` は、少ないことがある。どの保存の層でも、同じまとめ方にする。
- 監査イベント：自作の層は、エンジンのイベントに足す（保存先のトランザクションの `appendEvent`。このPoCだけのもので、Content Storeの口ではない）。SQLiteには、イベントの口が無いので、ベンチマークのコードが `load` の初めに（保存先を作った後に）作る表（`CREATE TABLE bench_events (seq INTEGER PRIMARY KEY, data BLOB NOT NULL) STRICT`。`internal/db` の `migrations` には入れない）に、ほかの書き込みと同じトランザクションで、1件を1行にして足す。
- ID：`ent_01JK` と、番号の22桁（ほかの種類も、同じ形。ULIDの形）。保存する人は10人で、保存ごとにランダムに選ぶ。

- 1回の保存（下記の「シナリオ」）のJSONも、同じ大きさにする。

シナリオ：

回と保存の層ごとに、新しいデータのディレクトリで、次のシナリオを、この順に、それぞれ1つのプロセスで動かす。

| シナリオ | すること |
| --- | --- |
| `load` | 保存先を作り（`Create`）、セットを保存して（上記）、閉じる |
| `ops` | 開き、ランダムな文書の `Document` を1000回、ランダムな文書の `History` を1000回、ランダムなエントリーの `Revisions` を1000回、エントリーの `Documents` を5回、ビルドのような読み込み（下記）を1回する（それぞれ1つの `View`）。それから、1回の保存（下記）を300回して（それぞれ1つの `Update`）、閉じる |
| `open-clean` | 閉じた保存先を開き、文書（エントリーの1番目）を1つ読んで、閉じる |
| `open-replay` | 自作の層だけ。チェックポイント（`logdb/checkpoint`）を消してから、`open-clean` と同じことをする（ログのすべてを読み直して開く。閉じるときに、チェックポイントを書く） |
| `open-killed` | 別のプロセスが、開いて1回の保存を続け、100回の後に、`SIGKILL` で止められる（止められる前に、もう1回保存していることがある）。その後で、`open-clean` と同じことをする |
| `checkpoint` | 自作の層だけ。開き、1回の保存をしてから、チェックポイントを書いて（`Checkpoint`）、閉じる |
| `backup` | 閉じた保存先を、新しいディレクトリにコピーする。自作の層は、`backupLog`（ほかのプロセスの読み手として開き、ログ・チェックポイント・オブジェクトのファイルと、`files/` をコピーして、それぞれ同期する）。SQLiteは、別の接続での `VACUUM INTO` と、できたファイルの同期と、`files/` のコピー（`backupLog` と同じ）。それから、コピーと元を開いて、数が同じことを確かめ、コピーを消す |

- 1回の保存：ランダムなエントリーの新しい版と、新しいリビジョンと、監査イベント（どのセットでも1件）を、1つの `Update` でする。
- ビルドのような読み込み：1つの `View` で、8つの種類のすべての文書（`Documents`）と、すべてのエントリーのリビジョンの一覧（`Revisions`）と、それぞれの最後のリビジョン（`Revision`。JSONも）を読む。
- 続けて動かす：シナリオは、同じデータのディレクトリで続けて動かすので、前のシナリオの保存（`ops` の300回など）は、後のシナリオに残る。どの保存の層も、同じ順に動かす。
- 回：セットごとに3回。1回の中で、`sqlite`・`log-inline`・`log-files`・`log-hybrid` の順に動かす（同じ保存の層の回を、続けない）。結果は、3回の中央値と、最小・最大。

測るもの：

- 時間：Goの `time.Now` の差（単調な時計）。`load` は、`Update` の時間の和（保存を作る時間は含めない）。ほかに、閉じる時間（`Close`）、開く時間（`Open` が返るまで）、開いた後の初めの読み込み、`Checkpoint`、バックアップ、ビルドのような読み込みの時間を測る。
- p50・p99：`ops` のそれぞれの操作の N 回の時間を、小さい順に並べて、N×0.5番目・N×0.99番目（切り上げ）のもの。`Documents` の5回は、中央値（3番目）と最大。
- 最大RSS：シナリオのプロセスの `/proc/self/status` の `VmHWM`（テストの実行ファイルを動かしてからの、いちばん大きい常駐のメモリ）。`getrusage` の `ru_maxrss` は使わない（Linuxは、それを `execve` をまたいで残す。Goの `os/exec` で動かしたプロセスは、`execve` まで親のメモリを使うので、親の最大から始まる）。
- 書いたバイト：`/proc/self/io` の `write_bytes`（プロセスがストレージに送るバイトを、ページを書き換えたときに数える）の、シナリオの初めと終わりの差。
- ディスク：`load` の後（閉じた後）のデータのディレクトリと、`backup` の後のデータのディレクトリとコピーの、すべてのファイルとディレクトリの `st_blocks`（512バイトの単位）の和と、ふつうのファイルの大きさの和と数。
- 数（自作の層だけ）：シナリオの間に、数える口を通った書き込み（回数とバイト）・ファイルの同期・ディレクトリの同期・名前の変更・削除・ディレクトリの作成。`checkpoint` では、`Checkpoint` の間の数も。`backup` のコピーは、数えない。
- エンジンの統計（自作の層だけ）：`load` の後の `Stats`（表ごとのキー・ログの大きさ・セグメント・ログとファイルのオブジェクト・失敗した自動のチェックポイント）と、開いた後の `Recovery`（使ったチェックポイント・読み直したレコード）。
- ヒープ：`runtime.GC` の後の `HeapAlloc`。`load` の段階ごとの後（`docs-` のセットは2つ、`history-heavy` は10の回）と、開いた後に測る。
- 大きさ：`checkpoint` のチェックポイントのファイル。

測らないもの：

- SQLiteの同期の回数（SQLiteは、自分で `fsync` を呼ぶので、数える口を通らない）。
- ページキャッシュは、空にしない（rootが要る）。開く・読む操作は、ページキャッシュから読む。読んだバイトは、測らない。
- SQLiteのCのメモリは、ヒープに入らない（最大RSSには入る）。
- 保存を作る時間、シナリオの後の確かめ（数を数える・コピーを開く）、ほかのプロセスの読み手（`openLogReader`）、保守（圧縮とGC）、同時に動く操作、原本、電源断。

マシンについて残すもの（`env.json`）：Goの版、OSとCPUの種類、カーネル（`/proc/sys/kernel/osrelease`）、CPUのモデル（`/proc/cpuinfo`）、CPUの数と `GOMAXPROCS`、メモリ（`/proc/meminfo`）、作業のディレクトリのファイルシステム（`/proc/mounts` のマウント点・デバイス・種類・オプション）と、ディスクのモデル（`/sys`）、SQLiteの版（`sqlite_version()`）と設定（`PRAGMA`）、モジュールの版、Goのランタイムの環境変数（`GOGC`・`GOMEMLIMIT`・`GODEBUG`・`GOMAXPROCS`・`GOFLAGS`）、テストのコマンドの引数、始めと終わりの時刻。ほかに、すべての設定と、セットの数とJSONの大きさ（種類ごとの和・最小・最大、64KiB以上のリビジョンの数、リビジョンの大きさの中央値と90パーセンタイル）も残す。

**置き場所の評価**

数によらないこと：

- 同じ内容：どの置き場所でも、同じハッシュのオブジェクトは1つで、2度目からは何も記録しない（論理のCASは同じ）。
- 同期の回数：Aは、コミットごとに、セグメントの同期が1回。Bは、それに、新しいオブジェクトごとのファイルの同期と、使ったディレクトリごとの同期が足される。混合は、大きいオブジェクトの分だけ足される。
- 途中で止まったとき：Aは、書きかけのレコードを切り戻すだけで、何も残らない。B（と、混合の大きいオブジェクト）は、レコードより先に書いたオブジェクトのファイルと一時ファイルが残り、回収で消す。
- 圧縮：Aは、残すすべてのオブジェクトの中身を、新しい世代に写す（読んで、ハッシュを確かめて、書く）。Bは、ハッシュと大きさだけを写し、ファイルはそのまま使う。
- 回収：どれも、要らなくなったオブジェクトを状態から落とすのは、圧縮。領域が空くのは、Aでは、古い世代のセグメントを消すとき、Bでは、回収でファイルを消すとき（どちらも、保守モード）。
- バックアップ：Aは、少しの大きなファイル（セグメント）を写す。Bは、オブジェクトの数だけのファイルを写し、それぞれを同期する。

**残る危険**

- 電源断：実際のディスクでの電源断を、確かめていない（dm-log-writes の記録を動かしていない）。模擬のファイルシステムは、モデル（厳しいPOSIXの規則）で、実際のディスクの装置のキャッシュ、セクタの途中の書き込み、ファイルシステムの振る舞いとは、違うことがある（6.12の130）。
- 同期の失敗の後（F1・F2）：マシンを再起動せずに開き直すと、後のクラッシュで、ログが壊れる（開くのを拒む）か、原本が無くなることがある。エンジンも保存先も、再起動したかを確かめない（下記の「運用の制約」。6.12の129）。
- 新しいコード：エンジンは、PoCで書いたもので、#66 で保存先の保存の層にしたが、保存先を使うサイトは、まだ無い。テストの見つけない間違いが、残っていることがある。形は版1だけで、移す道具は無い（6.12の131）。
- メモリと開く時間：状態のすべてをメモリに持ち、開くときは、チェックポイントの後のログを読むので、どちらも、データとともに増える（`history-heavy` で、ヒープが86.1MiB、開くのに150ミリ秒、ログをすべて読み直すと1249ミリ秒。上記の「ベンチマークの結果」。6.12の132）。
- ログの大きさ：書き換えた値（いまの版・番号など）の古いものも、圧縮まで、ログに残る。圧縮は、書くプロセスを止める保守モードでしかできない（6.12の133）。
- 開いたファイル：読んだセグメントの数だけ、開いたファイルが増える（6.12の132）。
- 保守の飢え：2つ目の書くプロセスが、開こうとし続けると、保守が入れないことがある（6.12の135）。
- 見つけにくい傷：チェックポイントより前のセグメントの傷は、開くときには分からない（`Verify` で見つける）。チェックポイントより後の、最後のレコードの傷は、書きかけの末尾として切る（上記の「復旧」。6.12の131）。
- 確かめた範囲：Linuxの ext4 と、1つのマシンだけ（6.12の130）。ベンチマークも、1つのマシンで、3回ずつ。

**運用の制約**

本番で使うなら、次のことを守る（案）。

- 書くプロセスは1つ：管理のサーバーだけが、書くプロセスとして開く。ビルド・バックアップ・検出は、読み手として開く。
- 同期に失敗した後は、マシンを再起動する：`ErrFailed`（`the store has stopped after a sync failed; restart the machine before opening it again`）か、原本の `saving originals has stopped after a sync failed; restart the machine before opening the store again` が出たら、マシンを再起動してから、保存先を開き直す。プロセスを再起動するだけでは足りない（同じ起動の間は、ページキャッシュが残る）。たとえば、systemdの、止まったプロセスを自動で再起動する設定（`Restart=`）では、同じ起動のまま開き直すことになる。保存先は、これを強制しない（6.12の129）。
- 保守：圧縮と回収は、書くプロセスと、すべての読み手を止めてする。その間、開こうとするものは、すぐに失敗する（6.12の133）。
- 置き場所：Linuxの、ローカルのファイルシステム（NFSなどは使わない）。
- 読み手のユーザー：エンジンは、ファイルを0600で作るので、読み手は、書くプロセスと同じUnixユーザーで動かす（別のユーザーにするなら、グループで読む決まりが要る。決めていない。6.12の134）。
- 書くプロセスの起動：書くプロセスが無い間に、読み手がログの終わりを読んでいると、書くプロセスの起動が、2秒まで待つ（過ぎれば失敗する。6.12の135）。
- バックアップ：コピーは、その時点のすべて（個人情報も）を持つ（下記の「個人情報の削除」）。

**移行・バックアップ・リストアの条件**

- 形の版：どのファイルにも、印と形の版があり、新しい版は、何も変えずに拒む（エンジンの形の版1と、自作の層の表の版1）。形を変えるときは、古い版を読めるようにするか、新しい世代に書き直す（圧縮は、状態のすべてを、新しい世代のベースに書くので、新しい形に書き直す道になる）。いまは、版1だけで、移すコードは無い（6.12の131）。
- SQLiteのデータのディレクトリ：#66 の前にSQLiteの保存の層で作ったデータのディレクトリを写す道具は、作らなかった（保存先を使うサイトが無かったため。下記の「判断」）。そうしたデータのディレクトリは、開けない（3.4の「データのディレクトリ」）。写すなら、すべての文書の版・リビジョン・オブジェクトを、番号の順に、保存した日時と保存した人とともに写す（版とリビジョンの番号を変えない）。原本（`files/`）は、同じ形なので、そのまま使える。
- バックアップ：書くプロセスが書いている間も、1つのコミットの時点のコピーを作れる（上記の「保守モード」の `Backup`）。コピーは、元と同じ形のデータのディレクトリ。
- リストア：コピーを開く（`Open`）。チェックポイントがあれば、それから、無ければログから、状態を作る。使うのは、`Backup` が成功したコピーだけ（リストアの道具は6.12の131）。
- コマンド：`whiteroom backup`（9.2）は、まだ無い（#49）。

**個人情報の削除**

個人情報が残る場所と、消し方：

| 場所 | 残るもの | 消し方 |
| --- | --- | --- |
| ログ（いまの世代） | 書き換えた前の値と、消したキーの値、ログの中のオブジェクト（文書とリビジョンのJSON）、監査イベント | 圧縮の書き直しで、値を書き換えるか落とし、オブジェクトとイベントを落とした新しい世代を書き、古い世代を消す |
| オブジェクトのファイル | 文書とリビジョンのJSON | 圧縮で落とした後、回収で消す |
| チェックポイント | ある時点のすべての表の値 | 圧縮が、新しい世代のチェックポイントで置き換える |
| メモリの状態（エンジンの中の索引） | 表の値 | 圧縮の後は、新しい世代のもの |
| 保存先の履歴（3.4） | すべての版とリビジョン（消した文書のものも） | 履歴から消す操作は、まだ無い（6.12の125）。作るなら、圧縮の書き直しを使う |
| 原本（`files/`） | メディアのファイル | 原本の回収（6.12の125） |
| バックアップ | その時点のすべて | エンジンの外。保持の期間を決めて消す |
| 古い公開のリリースと、画像のキャッシュ | 公開したページと画像 | エンジンの外（4.3・6.6.2） |
| ファイルシステムとディスク | 消したファイルのブロック | 物理的に消えたことは、保証しない |

- 示したこと：圧縮の書き直しで、値を書き換え、オブジェクト（ログの中のものと、ファイルのもの）とイベントを落とすと、印にした文字列は、ログ・チェックポイント・古いセグメントのどれにも無くなり、落としたオブジェクトのファイルにだけ残る（`TestCompactRewrite`。模擬のファイルシステムとOSのファイルで）。そうしたファイルは、回収が消す（`TestMaintainCompactAndGC`）。
- 暗号化して鍵を消すこと（crypto-shredding）は、候補（6.12の138）：値を、人（または期間）ごとの鍵で暗号化し（上記の「イベント・操作のID・暗号化の封筒」）、消すときに、鍵を消す。持ち主のいない個人情報（ログインしていない人のIPアドレスなど）は、期間ごとの鍵で暗号化し、保持の期限に鍵を消す方法がある。
- 鍵の置き場所：鍵は、ログの外の、消せる場所に置く（ログに置けば、書き直さなければ消せない）。鍵の作り方・保管・バックアップ・失ったときの復旧・失効は、決めていない。複数の人にかかわるイベントを、誰の鍵で暗号化するかも、決めていない。
- 鍵を消すことは、物理的な消去ではない：暗号文は残り、鍵の写し（バックアップなど）があれば開ける。鍵を消すことを、消去と同じとはみなさない。
- 暗号化しても分かるもの：表とキー（文書の種類とIDなど）、値とレコードの大きさ、コミットとイベントの番号、鍵のIDは、暗号化しない（ログから分かる）。

**冪等性の責務**

- エンジン：復旧の後に、コミットは、すべてあるか、無いかのどちらか（上記の「テスト」）。呼ぶ側は、同じ `Update` に置いた操作のID（上記の「イベント・操作のID・暗号化の封筒」）で、そのコミットがあるかを確かめられる。エンジンは、同じ操作の再送を、自分では見分けない。
- #43・#48：業務の操作（管理のAPIの要求など）の再送の扱い、操作のIDの付け方と残す期間、メールなどの外への作用（送るものを同じコミットに書いておき、コミットの後に送るもの。outbox）は、そこで決める。
- 監査の二重の記録：監査イベントは、状態の変更と同じコミットに入るので、操作のIDで再送を見分ければ、2度は書かれない（`TestOperationID` で、イベントが1つだけであることも確かめた）。

**判断**

自作へ移行する（メンテナーの判断。2026-11-06）。保存の層を、SQLite（`internal/db` と `github.com/mattn/go-sqlite3`）から、この節のエンジンと自作の層に替える。

- 理由：外部のサードパーティのGoのモジュールを無くす目標（1.2）の、残る唯一の例外が、保存の層（ドライバーとcgo）。PoCで、結果はSQLiteと同じになり（差分テスト）、どのクラッシュ・強制終了・失敗の差し込みの後も、確定したコミットだけが見えた。書き込みと読む操作は、SQLiteより速いか同じくらいで、書くバイトも少ない。引き受けるもの：エンジンの保守、データとともに増えるメモリと開く時間、確かめていない電源断。
- 進め方：#66 で替えた（`Create`・`Open` を自作の層にし、SQLiteの保存の層・`internal/db`・ドライバーを外した）。#43・#45 は、自作の層の上に作る。
- 本番で使う前に：電源断の確かめ（dm-log-writes の記録）、同期に失敗した後の再起動の強制、検出と修復・リストア・形の移行の道具（6.12の129・130・131）。
- データの移し替え：保存先を使うサイトは、まだ無い（ビルドはまだ保存先を使わない。4.3）ので、SQLiteから写す道具は作らなかった。
