### 9.7 管理のAPI（案）

管理用のサーバー（9.6）の上に、文書・メディア・公開とビルド・アカウント・ログを読み書きする HTTP の口（管理のAPI）を、`internal/admin` に作った（#48）。画面（管理画面）と、コマンド `whiteroom serve admin` と待ち受けるアドレスの設定（#49。9.4）は、まだ無い。この節は、口の一覧・形・エラー・権限・上限・再送・記録を、1か所で決める（ほかの節は、この節を指す）。この節の規則は、どれも仮に決めたもの（案）。

**目的と状態**

- 目的：管理画面が、文書の読み書き、メディアのアップロードと原本の取得、公開とビルド、アカウントとパスワード、ログの読みを、HTTP で行うための口。保存の操作と公開の操作（6.7）、公開の仕組み（4.4）、アカウントの操作（7.3）を、ログインしたセッション（9.6）の権限で呼ぶ。
- 管理画面のためのAPIで、版を付けない：パスは `/api/<資源>` で、`/api/v1/…` のような版は付けない。画面は、管理用のサーバーと同じ版で一緒に出す前提で、口を変えるときは、同じ版の画面と一緒に変える。スクリプトなどのほかのプログラムも、ログインの Cookie（9.6）で同じ口を使えるが、互換性は約束しない。
- ヘッドレスの配信（ログインなしで、公開した内容を読む口）は、作らない。静的なサイト（4章）と別の、新しい公開の口と脅威（9.2・10章）を決めることになるため（6.12の241）。
- 作ったもの：下記の口のすべて。ほかに、権限を保存先の `Update` の中でも確かめる仕組み（下記の「権限」）、`html` ブロックの権限（`html.edit`。7.3・6.5.4）、断った要求の記録（`access.denied`。7.4）、操作のIDの記録を24時間で消すこと（6.7）、保存先の一時のファイル（3.4）、メモリを抑える場所と1人の数（下記の「上限」）。
- 作っていないもの：下記の「まだ無いもの」。

**置き場所**

- `internal/admin`（9.6）。`Config.Publisher`（`*publish.Publisher`）を渡すと、文書・メディア・公開・ビルドの口と、定義の口ができる。渡さないと、アカウント・パスワード・ログの口だけができる（定義・設定・文書・メディア・エントリー・公開・ビルドの口は、404になる）。`Publisher` は、`Config.Accounts` と同じ保存先を使うものにする（違えば `New` が断る：`admin: Config.Publisher must use the store of Config.Accounts`）。
- `New` は、`Publisher` を動かさない。`Publisher.Run`（ビルドと予約の公開）と、HTTP のサーバー（`NewHTTPServer`）は、呼ぶ側（コマンド。#49。テストも）が動かす。
- ビルドは、管理用のサーバーのプロセスの中で動く（下記の「プロセスと Unix ユーザー」）。
- 依存の向き：`.golangci.yml` の depguard の規則が正。`internal/publish` を import するのは `internal/admin` だけ、`internal/edit` を import するのは `internal/publish` と `internal/admin` だけ。`internal/admin` は `internal/serve` を import しない。

**形**

- 要求と答えの本文は JSON（`Content-Type: application/json`。アップロードと原本の取得は、ファイルそのもの）。名前は、文書と同じ camelCase。日時は、UTC の RFC 3339（9.6の答えと同じ）。空・0・無いものは書かない。ただし、`false` や 0 が値の項目（`publishes`・`translatable`・`failed` など）と、画面が確かめずに読む配列（`items`・`schedules`・`names`・定義の配列）は、空でも書く（空の配列は `[]`）。
- 文書は包む：文書の取得の答えは `{"version":{"seq":…,"hash":"sha256:…","savedAt":"…","savedBy":"usr_…"},"document":<文書>}`。`version` は文書の版（3.4）で、`hash` は、消した版には無い。`document` は、保存先が持つバイト列を、エンコーダーを通さず、そのまま書く（空白も変えない）。保存先のバイト列そのものなので、問題の行と列（6.7）が、ほかの口と食い違わない。一覧の行も同じ形。
- 保存の本文は `{"base":<元にした版>,"document":<文書>}`、作る本文は `{"document":<文書>}`。`document` は JSON のオブジェクトにする。その値のバイト列は、送られたまま保存の操作に渡す（Go の `encoding/json/v2` の `jsontext.Value` は、値の中の空白と改行も含めて、送られたバイト列を写す。2026-11-12に確かめた）ので、検証の問題の行と列は、送った値の中に付く（6.7）。保存は、文書の全体（`id` も）を送る。補わない。
- 操作の答え（作成・保存・削除・公開の操作）は、保存の操作の結果（6.7の `edit.Result`）の JSON：`kind`・`id`・`version`・`revision`・`redirect`・`number`・`status`・`publishes`・`warnings`・`omittedWarnings`。`publishes` は、いつも書く（`true` なら、公開するものが変わり、ビルドが起こる。4.4）。`warnings` は、下記の「エラー」の `errors` と同じ形で、100件まで。例（公開の操作の答え）：

```json
{"kind":"entry","id":"ent_01JB8W2N5KD3F6H9J1M4P7R2T5","version":{"seq":18,"hash":"sha256:43cc23fa52b87b4cc1d02b5b114154151d6adddb17c9fddc06b027fa99e24008","savedAt":"2026-11-12T01:02:03.456789Z","savedBy":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6"},"revision":"rev_01JB8X9Y3ZE5G8K1N4Q7S2V6W9","redirect":"rdr_01JBG3N6Z7B0E3G6J9M2P5S8V1","status":"published","publishes":true}
```

- 作成は201と `Location`（RFC 9110の15.3.2）。作った資源のパス：文書は `/api/<資源>/<ID>`、エントリーは `/api/entries/<ID>`、リビジョンの保存は `/api/revisions/<ID>`、翻訳の作成は `/api/entries/<新しいID>`、メディアのアップロードは `/api/media/<ID>`、招待は `/api/accounts/<ID>`。
- 400：本文が、その口の JSON でないとき（`bad-request`。空・JSON でない・知らないメンバー・同じメンバーが2つ・型の違い・`null`・要るメンバーが無い。9.6の「上限」と同じ）。クエリが、その口の受けるものでないとき（`bad-query`。知らない名前・同じ名前が2つ・値の形の違い・要る名前が無い）。ヘッダーが、その口の受けるものでないとき（`bad-header`。`Idempotency-Key` の形の違いと、取らない口への付与）。

**元にした版と409**

- 作成のほかの保存・削除・差し替え・公開の操作は、読んだときの版を `base` で渡す。版は、文書では `Seq`（数。設定の文書は、まだ無ければ0）。エントリーのリビジョンの保存では、最後のリビジョンのID（無ければ空の文字列）。公開・公開をやめる・アーカイブ・予約では、エントリーの `Seq`（公開と予約は、公開するリビジョンも `revision` で渡す。最後のリビジョンのID）。本文の無い削除と、原本の差し替えは、クエリの `?base=<Seq>` で渡す。
- 版が合わなければ、何も変えずに409（`conflict`。RFC 9110の15.5.10）。画面は、読み直す。作成のほかで、`base` が無い・負の数・形の違いは、400。
- HTTP の条件つきの要求（`ETag` と `If-Match`。RFC 9110の13.1.1。`If-Match` が無ければ428。RFC 6585の3章）は使わない。エントリーは版が2つ（状態の `Seq` と最後のリビジョン）あり、名前で分けて渡せるため。最後のリビジョンが無い状態（空）も、`base` なら書ける。

**口の一覧**

どの口も、ログインが要る（`withSession`。9.6）。ただし `POST /api/password` は、ログインなし。`GET` の口は `HEAD` も受ける。口が無いパスは404、メソッドが違えば405（9.6）。権限の欄は、7.3の操作の名前で、「自分の」は、author が自分のものだけ（7.3）。ここに書かない読む口の権限は `view`（すべてのロール）。

**エラー**

形は9.6（RFC 9457の `application/problem+json`。`detail` は固定の文）。9.6の表のほかの `code`：

| `code` | ステータス | `detail` | 付けるヘッダー |
| --- | --- | --- | --- |
| `too-many-requests` | 429 | `too many requests at once; try again later` | `Retry-After: 1` |
| `forbidden` | 403 | `the account is not allowed to do this` | |
| `conflict` | 409 | `the document has changed since it was read` | |
| `invalid` | 422 | `the request has problems` | |
| `operation-reused` | 422 | `the Idempotency-Key was used for another request` | |
| `last-admin` | 409 | `it would leave no active administrator` | |
| `disabled` | 409 | `the account is disabled; enable it first` | |
| `invalid-token` | 401 | `invalid or expired token` | `WWW-Authenticate: Session` |
| `rollback-running` | 409 | `another rollback is running` | |
| `bad-query` | 400 | `the query is not one that this resource takes` | |
| `bad-header` | 400 | `a header of the request is not one that this resource takes` | |

- 下の層のエラーとの対応：
  - 検証の問題（`content.Errors`）→ 422 `invalid`（RFC 9110の15.5.21）。
  - 元にした版の食い違い（`edit.ErrConflict`・`account.ErrConflict`）→ 409 `conflict`。
  - 操作のIDを別の要求に使った（`edit.ErrOperationReused`）→ 422 `operation-reused`（下記の「再送」）。
  - 無い文書・リビジョン・リリース・アカウント（`fs.ErrNotExist`）と、その種類のIDの形でないパスの値 → 404 `not-found`。
  - 権限（`account.ErrForbidden`）→ 403 `forbidden`。記録してから答える（下記の「記録」）。
  - 最後の有効な admin を失う操作（`account.ErrLastAdmin`）→ 409 `last-admin`。無効のアカウントの再設定（`account.ErrDisabled`）→ 409 `disabled`。
  - 使えないトークン（`account.ErrInvalidToken`）→ 401 `invalid-token`（`POST /api/password` だけ）。
  - 別の戻す操作が待っている（`publish.ErrRollbackRunning`）→ 409 `rollback-running`。
  - 要求を認証した後で、アカウントが無くなった・資格が変わった・セッションが終わった（`Update` の中の確かめ。下記の「権限」）→ 401 `unauthenticated`。Cookie を消す。
  - 現在のパスワードが違う（`account.ErrBadCredentials`。本人のパスワードの変更だけ）→ 422 `invalid`（`errors` は `/current` の `wrong password` の1つ）。
  - 要求のコンテキストが終わった・場所を待つ時間が過ぎた → 503 `busy`（`Retry-After: 5`）。
  - ほか（保存先の失敗など）→ 500 `internal`。記録する（9.6の「記録」）。
- `invalid` の本文：problem の本文に、`errors` の配列を足す（RFC 9457の3章の例と同じ名前）。各要素は、`file`（サイトのディレクトリでの名前。`revisions/rev_….json` など。無いときは書かない）・`pointer`（JSON Pointer の文字列。`/title`。文書の全体は空の文字列）・`line`・`column`（分かるとき。送った値の中での位置）・`detail`（ビルドと同じ文）。RFC 9457 の例の `pointer` は、URI のフラグメントの形の `"#/age"` だが、本文は「a JSON Pointer」とだけ言い、形を定めない。ここは、ビルドの問題の文と同じ形にした。例：

```json
{"type":"about:blank","title":"Unprocessable Entity","status":422,"detail":"the request has problems","code":"invalid","errors":[{"file":"revisions/rev_01JB8X9Y3ZE5G8K1N4Q7S2V6W9.json","pointer":"/body/3","line":12,"column":9,"detail":"only an administrator can add or change html blocks"}]}
```

- 100件まで：`errors` は、操作が返す並び（ファイル・行・列・ポインター・文の順）の最初の100件までで、残りの数を `omittedErrors` に持つ。成功した操作の答えの `warnings` も、同じ形で、100件までと `omittedWarnings`。多くの文書が使うものを変えると、問題が文書の数だけ増える（2万件の投稿で20009件。1件約150バイトとして約3MB。見積もり。6.12の154）ので、答えの大きさを、問題の数によらず、100件分にした。101件目からは、文が分からない（直して、もう一度保存すると見える）。問題を探すのを途中で止めるかは、6.12の154に残す。
- アップロードで、知らない形式（下記の「メディア」）を断るときは、`errors` が1つ（`pointer` は空で、`file`・`line`・`column` は無い）。

**一覧**

- 絞り込みと並べ替え：エントリーの一覧は、索引の要約（3.4）を読み、言語・タイプ・状態・ターム・作った人・翻訳グループで絞り、番号・作った日時・公開したリビジョンの日付・予約の日時で並べる（メモリの中で）。索引は変えない。
- ページ送り：`offset`（0以上の整数。既定は0）と `limit`（1〜100。既定は50）。WordPress の REST API も `per_page` を100までとする（2026-11-12に確かめた）。答えは `{"items":[…],"total":…,"offset":…,"limit":…}` で、`total` は、絞り込みに合う全体の数。`offset` が `total` 以上なら、`items` は空。一覧を読む間に文書が増えると、`offset` では行がずれる（読み直せば直る）。
- 書き方の誤り（知らない名前・同じ名前が2つ・値の形の違い・`limit` が100を超える）は400（`bad-query`）。形の合う値が何にも合わなければ、空の一覧。
- 文書の一覧（ターム・著者プロフィール・メニュー・フォーム・リダイレクト・メディア）：行は `{version, document}` で、IDの順（作った順）。絞り込みは、ターム：`taxonomy`・`language`、メニュー：`language`・`location`、メディア：`kind`（`image` か `pdf`。`mimeType` で決まる）・`uploadedBy`（`usr_` のID）。著者プロフィール・フォーム・リダイレクトは、絞り込みが無い。`uploadedBy` は、要約に無いので、ほかの絞り込みに合う各メディアの文書を読んで決める。
- エントリーの一覧：絞り込みの名前は `type`・`language`・`status`（`draft`・`published`・`scheduled`・`archived` を、コンマでつなぐ）・`term`（`trm_` のID）・`createdBy`（`usr_` のID）・`translationGroup`（`tg_` のID）。`sort` は `number`（既定）・`createdAt`・`date`（公開したリビジョンの日付）・`scheduledAt`、`order` は `asc` か `desc`（既定）。同じ値は、方向によらず、IDの順。並べる時刻の無いエントリー（公開していない・予約していない）は、方向によらず、最後。
- エントリーの一覧の行：`{version, document, latestRevision?, published?}`。`document` は状態の文書（番号・タイプ・言語・状態・翻訳グループ・作った日時と人など）。`latestRevision` は `{id, title?, savedAt, savedBy}`（最後のリビジョン。無ければ書かない。`title` は、最後のリビジョンの `title` が文字列のときだけ）。`published` は `{slug, date?}`（公開したリビジョンのスラッグと日付。公開したリビジョンが無ければ書かない）。ページの行の分だけ、最後のリビジョンを読んで、`title` だけを読む。
- `term` の絞り込み：公開したリビジョンか最後のリビジョンの `terms` に、そのタームがあるエントリー。本文の中のリンクは数えない。最後のリビジョンは、索引の `Referrers` が役割 `latest` で示すものだけ読んで確かめる。
- タイトルで探す・並べるは、作らない（要約にタイトルが無く、探すたびにすべてのリビジョンを読む。下記の費用。全文検索の索引（12章の論点3）と合わせて決める。6.12の242）。

**定義**

画面が、標準のタイプの決まり（6.4.4）を自分で持たずに済むように、保存の操作が検証に使う定義を、そのまま返す。どちらも、プロセスが読み込んだもの（`Editor` を作るときに渡したスキーマのファイルとテーマの設定。テーマは起動のときに読む。6.12の181）で、だれでも（`view`）読める。`Publisher` を渡さないと、無い。

- `GET /api/schema`：`{authorUrl, types, taxonomies}`。`authorUrl` は著者のURLの規則。`types` は、`post`・`page` を先頭に、スキーマのファイルの順に、ほかのタイプ。各要素は `{name, label?, url, archive?, body, taxonomies, fields}`（`url` はURLの規則。`taxonomies` はタクソノミーの名前の配列。`fields` はフィールドの定義の配列）。`taxonomies` は、`category`・`tag` を先頭に、スキーマのファイルの順に、ほかのタクソノミー。各要素は `{name, label?, url, hierarchical}`。フィールドの定義は、6.4.4の項目と同じ名前：`name?`（リストの項目 `of` は、名前を持たない）・`type`・`label?`・`required?`・`translatable`（いつも書く。既定が真なので、偽も値）・`minLength?`・`maxLength?`・`min?`・`max?`・`options?`・`multiple?`・`minItems?`・`maxItems?`・`accept?`・`types?`・`taxonomy?`・`fields?`・`of?`。標準のもの（`post`・`page`・`category`・`tag`）を合わせた、実際に使う定義にする。スキーマのファイルは、要求のたびに読み込む（読めなければ500）。
- `GET /api/theme`：テーマの設定を、`theme.yaml` の項目（5.4.2）と同じ名前で。`{defaultLanguage, presets, styles, custom, blocks, marks, locations, pageTemplates, imageSizes, mobileWidth}`。`presets` は `{color, fontSize, spacing, fontFamily, gradient, shadow}` で、各要素は `{name, value}` の配列（テーマが書いた順）。`styles` はスタイルの項目の名前の配列（テーマが書かなければ、標準の13項目）。`custom` は `{color, fontSize, spacing}`（プリセットのほかに直接書けるか）。`blocks` は `[{type, styles, variants}]`（`styles` は、ブロックが書かなければ、テーマの `styles`。`variants` は `[{name, label}]`）。`marks` は `{highlight:{variants}}`。`locations`・`pageTemplates` は `[{name, label}]`。`imageSizes` は `[{name, label, width?, height?, crop}]`。`mobileWidth` は、書かなければ `781px`。どの配列も、空でも `[]`。
- 定義の形（API の形）は、ファイルの形と別に、ここに書く。ファイルの形の変更は、この形と合わせて直す。

**メディア**

- アップロード（`POST /api/media?fileName=<名前>`）：本文は、ファイルそのもの（原本）。`Content-Type` は、申告の形式で、保存の操作に渡す（ファイルの中身から読んだ形式と違えば、操作の答えの `warnings` に、文書の `/mimeType` の警告が付く。6.6.2）。`fileName` は、クエリに1回だけ（空でない）。ほかのクエリの名前は400。名前の規則（6.6.2）は、保存の操作が確かめる（断れば422、`/fileName`）。差し替え（`PUT /api/media/{id}/file?base=<Seq>`）も同じ。
- 形式の早い確かめ：本文の初めの512バイトを読んで、形式を確かめてから、保存の操作に渡す。知らない形式（初めの12バイトの印で決まる。空のファイルも）は、原本を書かずに、422で断る（`errors` が1つ：`cannot read the file: unsupported file format`）。ほかのエラー（初めの512バイトが、ファイルの全体でないために出るものなど）は、保存の操作に任せる。大きさ・画素数・壊れ方などの確かめは、いまどおり、原本を書いた後の保存の操作がする（6.6.2）。読めない形式のファイルが、使われない原本として残らない。
- 上限：64MiB。`Content-Length` が上回れば、読まずに413。読む途中で超えれば413（`too-large`）、本文を読み切れなければ400（`bad-request`）。本文は、メモリに溜めず、保存先の一時のファイルに流す（`PutOriginal`。3.4）。受け取る期限は10分（下記の「上限」）。
- 失敗しても原本が残るもの（使われない原本。6.12の125）：形式の印は合うが、壊れている・足りないファイル（422 `cannot read the file: invalid …`）、文書が断る名前（422 `/fileName`）、元にした版が古い（409）・差し替えるメディアが無い（404）、`Update` の中で断られた（403）、操作のIDを別の要求に使った（422）、記録の失敗。1人4つの数（下記）は、同時に受け取る数を抑えるだけで、回数と合計は抑えない（64MiBずつ）。
- CSRF との関係：本文が原本そのもの（画像や PDF の `Content-Type`）なら、CORS の単純な要求の形式（`application/x-www-form-urlencoded`・`multipart/form-data`・`text/plain`）ではないので、ほかのサイトのページは、事前の確認（preflight。サーバーは断る。9.6）なしには送れない（Fetch Standard。2026-11-12に確かめた）。ただし、Fetch Standard の3.3.7（CORS protocol exceptions）は、`application/csp-report`・`application/expect-ct-report+json`・`application/xss-auditor-report`・`application/ocsp-request` を、ほかのオリジンの内容が、事前の確認なしに送りうる形式とする（ページは、本文とヘッダーをほとんど決められない）。それで送られても、9.6のCSRFの確かめ（`Sec-Fetch-Site` と `Origin`）で断り、通ったとしても、形式の早い確かめが、知らない形式として断るので、原本は残らない。`multipart/form-data` は、CORS の単純な要求の形式なので、取らない（守りが1つ減る）。
- ファイル名はクエリに置く：GitHub のリリースの添付も、ファイル名をクエリ（`name`）に置き、本文をファイルそのものにする（2026-11-12に確かめた）。欠点：ファイル名が、リバースプロキシのアクセスログに残る（秘密ではないが、個人の名前を含むことがある）。
- 原本の取得（`GET /api/media/{id}/file`。`HEAD` も）：
  - 原本を、文書の `mimeType` の `Content-Type` と、文書の `size` の `Content-Length` で返す。`Content-Disposition: attachment` を付ける（ファイル名は文書の `fileName`。ASCII でない名前は、RFC 2231 の `filename*=utf-8''…`）。ブラウザーが文書として開かないようにするため：アップロードされたファイル（PDF の中のスクリプトなど）を、管理用のオリジンで開かない。画面の `<img>` のような埋め込みは、`attachment` でも表示されると考えている（実際のブラウザーでは確かめていない。画面の段階で確かめる）。
  - 9.6のヘッダーは、そのまま付く：`Cache-Control: no-store`（個人の情報を残させない例外にしない）・`Content-Security-Policy`・`X-Content-Type-Options: nosniff`・`Cross-Origin-Resource-Policy: same-origin` など。そのため、画面が画像を見せるたびに、もう一度取りに来る（キャッシュと `ETag` の案は6.12の245）。
  - いつも200：`Range`・`If-Range` は無視する（`Accept-Ranges`・`Content-Range`・`ETag`・`Last-Modified` も付けない）。原本は、最後まで読んだときにハッシュを確かめる（3.4）ので、途中だけを返すと、確かめを飛ばすため（6.12の245）。
  - 原本が読めないとき：答えを始める前に分かるもの（原本が無い・大きさが文書と違う）は、500（`internal`）。404にはしない（メディアはあり、保存先の異常で、無い資源ではない）。ログに、`the original of <ID>: <理由>` を含む1行を書く。答えを始めた後で読めなくなったら（ハッシュが合わないなど）、ログに `cannot read the original of <ID>: <理由>` を含む1行を書いて、接続を切る（`http.ErrAbortHandler`。途中までの本文が、全部とみなされないため）。クライアントが切ったことは、ログに書かない。
  - 文書は、重い仕事の場所で読み、場所を返してから、原本を流す（流す間は場所を持たない）。送る期限は10分。1人4つの数には数える（下記）。`HEAD` は、ヘッダーだけ（原本を開いて、大きさは確かめるが、読まない）。

**公開とビルド**

- 公開の操作（`publish`・`unpublish`・`archive`・`schedule`）：本文は上の表のとおり。`base` はエントリーの `Seq`（0以上の整数）、`revision` は公開・予約するリビジョンのID（`rev_` とULID。最後のリビジョンでなければ409）、`at` は RFC 3339 で読める日時（オフセットも、秒の下の桁も読める。ゾーンの無い日時は400）。
- 答えは200と操作の答え（`Location` は無い）：`status` は、公開の操作が決めた状態、`revision` は、公開・予約したリビジョン（日付の無い投稿の公開は、日付を入れた新しいリビジョン。6.7）、`redirect` は、URL が変わって登録したリダイレクト（6.7）。`publishes` は、公開するものを変えたか（公開と、公開中のエントリーの公開をやめる・アーカイブは真。予約は、いつも偽）。
- 失敗：409 `conflict`（`base` が合わない・`revision` が最後のリビジョンでない）。422 `invalid`（リビジョンの無いエントリー：`file` は `entries/<ID>.json` で `pointer` なし。公開の検証に通らないリビジョン：`file` は `revisions/<ID>.json`。ビルドと同じ、エンティティをまたぐ検証。公開しているエントリーの予約：`/status`、`a published entry cannot be scheduled; unpublish it first`。いまより後でない予約の時刻：`/scheduledAt`、`publish it instead`）。404（保存先に無いエントリーと、エントリーのIDの形でないパス）。
- 答えが返るのは、操作が保存先に入ったとき。ビルドが終わったときではない。画面は、答えの `publishes` を見て、`GET /api/builds` で状態を読み直す。ビルドが失敗しても、公開の操作は取り消されない（4.4）。
- ビルドの状態（`GET /api/builds`。`Publisher.Status`）：`{running?, pending, paused, last?, schedules}`。
  - `running`：動いているビルド `{startedAt, requests, omittedRequests?}`。
  - `last`：最後に終わったビルド。`running` の項目に加えて、`endedAt` と、`failed`（いつも書く）。リリースを公開したビルドは、`release`・`changed`・`pages`・`files`（0や偽も書く）と、`warnings`（`errors` と同じ形。100件まで）・`omittedWarnings`。失敗したビルドは、サイトの問題（`content.Errors`）なら `errors`（100件まで）・`omittedErrors`、ほかの失敗（ディスクなど）なら `error`（固定の文：`the build failed for a reason other than the content of the site`）。
  - `requests`：ビルドが取った要求 `{at, reason, kind?, id?, status?}`。`reason` は `start`・`operation`・`rebuild`・`resume`（4.4）。`operation` の要求は、操作の結果の `kind`・`id`・`status`（設定は `kind` が `settings`）を持つ。100件まで、残りの数が `omittedRequests`。
  - `pending`：待っている要求があるか。`paused`：戻した後で、自動のビルドを止めているか。`schedules`：公開できなかった予約 `{entry?, at?, tried, errors?, omittedErrors?, error?}`（失敗の示し方は `last` と同じ。固定の文は `the scheduled publish failed for a reason other than the content of the site`）。空でも `[]`。
  - サイトの問題でない失敗は、固定の文にする（サーバーの中のパスを、ふつうのロールに見せないため）。失敗の文そのものは、アクティビティログの `build` の記録の `detail` の `error` にあり、admin が読める（7.4）。ビルドの記録は、ビルドが終わった後の別の `Update` で書く（4.4・7.4）ので、状態にビルドが出た直後は、まだ記録が無いことがある。
  - 状態は、メモリだけで、プロセスを起動し直すと空になる（6.12の177）。失敗したビルドを、自動ではやり直さない（6.12の176）。
- ビルドのやり直し（`POST /api/builds`）：`Publisher.Rebuild`。202とビルドの状態（要求は出したが、新しいビルドは、まだ `last` に無い）。再開（`POST /api/builds/resume`）：`Publisher.Resume`。200とビルドの状態。止めていないときも200で、変えなかった印の記録を1件書く（4.4）。
- リリース（`GET /api/releases`）：`{current, names}`。出力先がまだ無い・リリースがまだ無いときは、`current` が空の文字列で、`names` が `[]`。ほかのエラー（出力先に、ビルドが作ったのでないものがあるなど）は、500。
- 戻す（`POST /api/releases/{name}/rollback`）：`{name}` は、小文字の16進数16桁（違えば、何も記録せずに404）。200とビルドの状態（`paused` が真）。動いているビルドの終わりを待つので、要求の期限（30秒）までかかり、過ぎれば503。残っていないリリースは404（要求の記録と、失敗の記録が付く。4.4・7.4）、ほかの戻す操作が待っていれば409（`rollback-running`）。ほかのプロセスのビルドがロックを持っているとき（`another build is running in <出力先>`）は、見分ける印が無く、500（ログにそのエラー）。
- この5つの口は、重い仕事の場所を使わず、1人の数にも数えない（下記の「上限」）。操作のIDを取らない（`Idempotency-Key` があれば400）。ビルドを変える3つ（やり直し・再開・戻す）は、`builds.manage`（admin だけ）。順は、権限 → `Idempotency-Key` → クエリ → リリースの名前の形（404）→ `Publisher`。

**アカウントとパスワード**

- アカウントの答えの形は2つ（7.3・7.4が、ログイン名とメールアドレスを、ほかのロールに見せないため）：
  - 全項目：`accounts.manage` を持つ人（admin）が見るすべてのアカウントと、自分のアカウントを見る本人。`{id, login, name, email, role, author?, status, createdAt?, createdBy?, credentialsChangedAt?, token?}`。`status` は `active`・`pending`・`disabled`。`token` は `{purpose, expiresAt}`（`purpose` は `invitation` か `reset`）で、トークンそのものは入らない。
  - 簡略：ほかのロールが見る、ほかのアカウント。`{id, name, role, author?}`（だれが作った・保存したかを、画面に示すため）。
  - どちらにも、パスワード・ハッシュ・トークンは入らない。
- 一覧（`GET /api/accounts`）：`{items, total, offset, limit}`。IDの順で、`items` は、空でも `[]`。すべての行を読んで、ページを切る（想定は、数人から数十人。7.3）。取得（`GET /api/accounts/{id}`）：アカウントそのもの（包まない）。無いアカウントと、アカウントのIDの形でないパスは404。
- 招待（`POST /api/accounts`）：本文は `{login, name, email, role, author?}`で、メンバーは、すべて文字列。無いメンバーは、空の文字列として扱い、アカウントの操作が `/login`・`/name`・`/email`・`/role` の問題（422）にする。`null`・文字列でない値・知らないメンバー・同じメンバーが2つ・`null` の本文は400。201と `Location` で、答えは `{account, token, expiresAt}`：`account` は全項目の形、`token` は base64url の43文字、`expiresAt` はトークンの期限（7日）。
- 変更（`PATCH /api/accounts/{id}`）：書いたメンバーだけを変える（`login`・`name`・`email`・`role`・`author`。`Manager.Update` と同じ。7.3）。200と `{account}`。権限は、本文を読んだ後に確かめる（下記の「権限」）。
- 無効（`POST …/disable`）・有効（`…/enable`）：200と `{account}`。削除（`DELETE`）：204で、本文も `Content-Type` も無い。最後の有効な admin を、無効にする・消す・ほかのロールにする・再設定すると、409（`last-admin`）。
- 再設定（`POST …/reset`）：200と `{token, expiresAt?}`。期限は24時間（認証の手段を一度も持ったことの無いアカウントは7日）。再設定の後に読んだアカウントにトークンが無ければ（その間に使われた）、`expiresAt` は書かない。無効のアカウントは409（`disabled`）。
- どの口も、操作のIDを取らず（`Idempotency-Key` があれば、読む口も400）、クエリも取らない（一覧の `offset`・`limit` のほかは400）。重い仕事の場所も、1人の数も使わない（アカウントの行は小さい）。
- 順：読む口：権限（`view`）→ `Idempotency-Key` → クエリ → パスの形（404）。招待：権限 → `Idempotency-Key` → クエリ → 本文（415・413・400）→ アカウントの操作。変更：`Idempotency-Key` → クエリ → パスの形 → 本文 → 権限 → アカウントの操作。無効・有効・再設定・削除：権限 → `Idempotency-Key` → クエリ → パスの形 → アカウントの操作（本文は読まない）。
- トークンを返す答えは2つだけ（招待の201と再設定の200）：トークンは、パスワードを決める権利で、渡す相手のほかに、何も持たない（保存先にはハッシュだけ。7.3）。そのため、この2つの本文には、トークンを入れる（9.6の「記録」の「秘密を出さない」の例外）。ほかの答え・ヘッダー（`Location` も）・エラーの文・ログ・記録・URLには出ない（テストのサーバーが調べる。下記の「テスト」）。admin が、本人に渡すURLを、トークンから作る（URLの形は、画面の段階で決める。トークンは、URLのパスにもクエリにも入れない。9.6の「記録」）。メールでは送らない（6.12の202）。
- 本人のパスワードの変更（`PUT /api/session/password`）：
  - 本文は `{current, password}`（どちらも文字列で必須）。順：権限（`account.self`。対象は自分）→ `Idempotency-Key` → クエリ → 本文（64KiBまで）→ 現在のパスワードの長さ（8KiBを超えれば、比べず、数えず、アカウントも読まずに、422 `invalid`：`/current` の `wrong password`）→ セッションごとの制限（下記）→ アカウントの操作（`ChangeOwnPassword`）。
  - 成功は200：新しいセッションの `Set-Cookie`（このCookieだけが、新しいトークンを渡す）と、`GET /api/session` と同じ本文。そのアカウントのすべてのセッションが終わる（ほかのセッションも。7.3）。
  - `current` が違えば、422 `invalid`（`/current` の `wrong password`）で、数えたまま。新しいパスワードの問題は422（`/password`）で、数えない（返す）。セッションが終わっていれば401（Cookie を消す）。コンテキストの終わりは503、保存先の失敗は500、権限が無ければ403で、どれも数えない（返す）。
  - 制限（案）：セッションごと（アカウントごとではない）に、`current` が違った回数を数える。ログインの組（9.6の「試行の制限」）と同じ数え方：5回までは自由、そのあと、30秒から倍に延びる待ち（1時間まで）。待たせるときは、アカウントを読まずに429（`too-many-attempts`。`Retry-After` は、秒に切り上げた値）。成功で忘れる。最後の試しから24時間で忘れる。セッションは、トークンのSHA-256で持つ（トークンは持たない）。表は1万セッションまで（メモリだけ。再起動で忘れる）。いっぱいのときは、期限が切れたもの、なければ、5回未満のうち最後に使ったのが最も古いもの、それもなければ、最後の試しが最も古いものを忘れ、セッションを断らない。ログインの表（9.6）には触れない。429の `detail` は、ログインと同じ固定の文（`too many failed logins; try again later`）なので、パスワードの変更でも「logins」と言う。
  - 理由：盗まれたセッションから、`current` を速く試されない（毎秒約35件。7.3）ため。盗んだ人は、5回のあと、最初の64分で7回、そのあとは1時間に1回まで。本人は、別のセッションでは待たない。欠点：数えるのはメモリだけで、再起動で忘れる（9.6と同じ）。
- パスワードをトークンで決める（`POST /api/password`。ログインなし）：本文は `{token, password}`（どちらも文字列で必須）。200と `{account}`（`id`・`login`・`name`・`email`・`role`・`author?`。Cookie は付けない。本人は、次にログインする）。使えないトークン（形の違い・無い・期限切れ・無効のアカウントのもの）は401（`invalid-token`）で、ログイン履歴に `token.failure`（7.4）。パスワードの問題は422（`/password`）で、トークンは使われないまま残る。トークンは、本文だけで渡す（クエリがあれば400）。CSRFの確かめ（9.6）は、ほかの書く口と同じに通る。回数の制限は付けない（トークンは256ビットで、当てられない。7.3）。ただし、トークンの形のものが来るたびに、すべての行を読む（6.12の215）。`ChangePassword`（セッションを使わない変更）の口は、作らない。

**ログ**

- 口：`GET /api/logs/login`（ログイン履歴）と `GET /api/logs/activity`（アクティビティログ）。`logs.view`（admin だけ）。7.4の `Store.ReadAudit` の上に、新しい順のページ送りを作った。
- クエリ（それぞれ1回まで。ほかの名前は400）：`from`・`to`（RFC 3339。`from` 以上 `to` 未満）、`account`（`usr_` のIDか `system`。`actor` か `account` がそれのもの、または `target` がそのアカウントのもの）、`action`（操作の名前か、`.` で終わる接頭辞。`entry.` など）、`targetKind`・`targetId`、`before`（記録の番号。1以上）、`limit`（1〜100。既定は50）。絞り込みの値が合わないとき（`audit.Filter` の確かめ。7.4）は400。
- 答え：200 `{records, next?}`。`records` は、新しい順に `limit` 件までで、各要素は、保存先に保存した記録のJSON（7.4の「記録の形」。キーは記録の順で、`detail` のキーは並べ替えて書く。書き直して確かめることはしない）。`next` は、そのページの最も古い記録の番号で、条件に合う、もっと古い記録があるときだけ書く。次のページは、`next` を `before` に渡して読む（`before` の記録そのものは入らず、番号がそれより小さい記録が入る）。記録が無ければ `{"records":[]}`。
- 読み方：ログの初めから、`before` の記録に着くまで（無ければ終わりまで）、`limit` 件の輪に入れながら読み、最後の `limit` 件を返す。毎ページ、ログの全体を（`before` まで）読む（7.4の費用。時刻と番号の索引は持たない。6.12の232）。どちらのログを読むときも、もう一方のログの記録は読み飛ばす。
- 場所と期限：ログを読む口は、重い仕事の場所とは別の、ログの場所で動く。同時に1つで、待たない（2つ目は503 `busy`）。要求の期限は120秒（答えを送る期限は、60秒。一時のファイルの答えは10分）。1人4つの数には数える（下記の「上限」）。メモリは、読む間のエンジンの分（下記の測った値）と、輪（100件まで）と、答えの一時の置き場（256KiBまではメモリ）。
- 費用と、読めなくなる時期は、下記の「上限」の「ログを読む口の最悪の形」。画面は、打たれたログイン名と User-Agent を、エスケープして見せる（7.4の「記録の形」）。

**権限**

- 2回確かめる（案）：
  1. 本文を受け取る前に、セッションの `Principal` で `account.Check`（7.3）する。保存先は読まない（読むと、場所の外で保存先を読むことになる。下記の「上限」）。持ち主で決まる操作（`entry.edit`・`entry.publish`・`entry.delete`・`media.edit`・`media.delete`）は、持ち主を、そのアカウント自身にして確かめ、それでも断られるロール（どの物にもできないロール。viewer など）だけを、本文を受け取る前に403で断る。`author.edit` は、パスのIDを対象にして確かめる（author は、自分の紐付けるプロフィールだけ）。
  2. 操作の `Update` の中で、アカウントを読み直し（`account.Read`。7.3）、いまのロールと状態で、本当の対象（エントリーの `createdBy`・メディアの `uploadedBy` など。同じ `Update` で読む）に、もう一度 `account.Check` する。ロールの変更や、無効にする操作と重なっても、古い権限で書かない。アカウントが無い、または資格（パスワード）が変わっていれば401（`unauthenticated`。Cookie を消す）、権限が無ければ（ロールの変更・無効・保留も）403。
- 自分の物だけを変えられるロール（author）の人は、ほかの人の物への本文を送れ、受け取った後（大きいものは、一時のファイルに書いた後）に、`Update` の中で403になる。その人の4つの要求の中で起きる。メディアの差し替えでは、流した原本が、使われない原本として残る（6.12の125）。
- `Update` の中で確かめる仕組み：
  - `edit.Op.Check`（`func(tx *store.Tx) error`。6.7の「権限の確かめ（案）」）：保存の操作と公開の操作に渡す。
  - `Publisher` の `Rebuild`・`Rollback`・`Resume` の `check`（4.4）：要求を記録する `Update` の中で、記録の前に呼ばれる。エラーはそのまま返り、記録も動きも無い。
  - 管理のAPIは、どちらにも、`Update` の中でアカウントを読み直して `account.Check` する関数を渡す。
- アカウントの口の2回目の確かめは、これと違う：アカウントの `Manager` が、自分の `Update` の中で、行為者の行（ロールと状態）で確かめる（`internal/account` の `authorize`。7.3の「作る」）。資格の時刻は、比べない（セッションの確かめが、要求の初めに見ている）。
- アカウントの `PATCH` は、本文を読んだ後に、権限を確かめる：自分のアカウントの名前とメールアドレスは `account.self`、ほかの変更（ログイン名・ロール・紐付けと、ほかのアカウント）は `accounts.manage` で、どちらが要るかは、本文で決まるため。ほかの口は、本文の前に確かめる。
- `html.edit`（7.3の表。admin だけ）：リビジョンの保存で、`html` ブロックを足すか変える（前のリビジョンに、同じIDで同じ `html` のブロックが無い）ときに要る。管理のAPIは、`Op.EditHTML` を `account.Allowed(html.edit)` で決めて渡す。無ければ、保存の操作が、そのブロックの位置の検証の問題（422。`/body/3: only an administrator can add or change html blocks`）で断る（6.7・6.5.4）。`html` ブロックを消すことと、変えずに残すことは、`entry.edit` だけでよい。翻訳の作成は、元のリビジョンのブロックを写すので、断られない。`Op.EditHTML` が真のとき、`Update` の中の確かめも `html.edit` を求める（保存の途中で権限を失った人は、403と、`permission` が `html.edit` の `access.denied`）。
- だれが何を読めるか：文書（エントリー・リビジョン・ターム・メディアと原本・著者・メニュー・フォーム・リダイレクト・設定）・定義・ビルドの状態とリリースの一覧は、`view`（すべてのロール）。アカウントは、admin（`accounts.manage`）がすべての項目、ほかのロールは、ほかのアカウントの ID・名前・ロール・著者プロフィールの紐付けだけ（自分のアカウントは、すべての項目）。ログイン名とメールアドレスを、ふつうのロールに見せない。ログイン履歴とアクティビティログは `logs.view`（admin だけ）。
- 記録の `actor` は、要求の中の値でなく、確かめたセッションの `Principal`（`Authenticate` が返したアカウント）のIDで決める（`edit.Op.By`・`account.By`・`Publisher` の `by` に渡す）。`system` は渡さない（6.12の240）。

**要求を確かめる順**

文書・エントリー・メディア・公開の口は、次の順に確かめる。どれかで答えたら、そこで終わる（アカウント・パスワード・ビルド・ログの口の順は、それぞれの節）。

1. 9.6の確かめ（Host・パス・CSRF）と、ログイン（セッションを使う口は、`Sec-Fetch-Site`（403）、そのあとセッション（401））。
2. 本文を受け取る前の権限（403。保存先は読まない）。読む口は `view`。
3. `Idempotency-Key`（400）。取らない口は、ヘッダーがあれば400。
4. クエリ（400）。
5. パスのIDの形（404）。
6. 小さい本文（64KiBまで）の口だけ：本文を読む（415・413・400）。
7. 1人4つの数（429）。
8. 文書を持つ口とアップロードだけ：宣言された長さ（413）と、本文の受け取り（415・413・400）。
9. 重い仕事の場所を待つ（503）。アップロードは、場所を使わない。
10. 場所の中で：本文を読み（400）、保存の操作を呼ぶ（`Update` の中の権限の確かめ（401・403）、操作のIDの確かめ（422）、検証の問題（422）、元にした版の食い違い（409）など）。答えを一時の置き場に作る。
11. 場所を返して、答えを送る。

**記録**

- 成功した操作は、下の層が記録する：保存の操作と公開の操作（`internal/edit`）、アカウントの操作と本人のパスワードの変更（`internal/account`）、ビルドと戻す操作（`internal/publish`）が、操作と同じ `Update` で、アクティビティログに1件足す（7.4）。管理のAPIは、成功した操作の記録を足さない。
- 権限で断った要求（`account.ErrForbidden`。読む口も）は、答える前に、記録だけの `Update` で、アクティビティログに `access.denied` を足す（7.4）：`actor` は断られたアカウントのID、`target` は断られた対象（種類とID。口が知っているときだけ。パスの値がIDの形でないときは、書かない）、`detail` の `permission` は断られた権限の名前、`suppressed` は記録しなかった断りの数（下記）。OWASP の Logging Cheat Sheet は、認可の失敗を記録することを挙げ、記録が資源を使い尽くさないことを求める（2026-11-12に確かめた）。
- 1分に10件まで：サーバー全体で、`Config.Now` の時計の1分ごとに、10件まで1件ずつ書く。超えた断りは、書かずに数え、次に書く `access.denied` の `detail.suppressed` に足す。ログインの断りの枠（比べる前に断ったログインと無効なトークン。1分に10件。7.4）と同じ数。理由：断った要求は、ハッシュを作らない安い要求で、ログインした人が続けて起こせる。アクティビティログは消さないので、1分に60件にすると、攻撃が続くとき、1日に最大約8.6万件が残り、ログイン履歴の失敗の記録と合わせて、ログを読む口（下記）が120秒で読める量に、約11か月で届く（見積もり）。10件なら、断りは1日に最大約1.44万件。
- 書けなかったとき：記録を書く `Update` は、要求の取り消しから切り離し、保存先を最大5秒待つ。書けなければ、`Config.ErrorLog` に `cannot record access.denied: <理由>` を書き、その断りを、記録しなかった断りに数える。答えは、403のまま変えない（7.4の「記録できなかったとき」と同じ）。記録は、重い仕事の場所の外で書く。
- 記録しないもの：成功した読み（一覧・取得・原本の取得・ログを読む口も）。検証の問題・元にした版の食い違い・上限・形の違いなど、権限の断りでない失敗（失敗した操作は記録しない。7.4）。401（セッションの無い要求）。アクティビティログは、「どこから」（アドレス・User-Agent・セッションのキー）を持たない（7.4）。だれが、は `actor` で分かる（6.12の237）。

**再送**

返事が届く前に切れたとき、画面が同じ要求をもう一度送っても、2度保存しないようにする。

- `Idempotency-Key`：書く口（文書・エントリー・リビジョン・翻訳・設定の作成と保存と削除、メディアのアップロードと差し替え、公開の操作）は、任意で、このヘッダーを受け取る。値は、操作のID（`op_` とULID。6.7）を、構造化フィールドの文字列として（引用符つきで）書いたもの：`Idempotency-Key: "op_01JBG3N6Y6A9D2F5H8K1N4Q7S0"`。画面が、利用者の操作ごとに作る。IETF の draft-ietf-httpapi-idempotency-key-header-08 に合わせた（Internet-Draft。RFC ではない。2026-11-12に確かめた）。1行で、形の合うものだけ：2行以上・引用符の無い値・操作のIDの形でない値は400（`bad-header`）。
- 取らない口：アカウント・パスワード・ビルド・リリース・ログの口と、読む口は、ヘッダーがあれば400（`bad-header`）。ただし、定義の口（`/api/schema`・`/api/theme`）は、ヘッダーもクエリも見ない。アカウントの操作とビルドの操作は、操作のIDを取らない（アカウントの操作の再送は6.12の203）。
- 動き：渡された値は、保存の操作の `Op.ID` になる。同じ値で同じ要求（操作した人も同じ）なら、何も保存せず、前の結果を返す（そのとき、権限の確かめ（`Op.Check`）は呼ばず、アクティビティログにも足さない）。同じ値で違う要求（操作した人が違うのも）なら、422（`operation-reused`。draft も422を求める）。同じ値の要求が同時に来ても、保存先の `Update` は1つずつ動くので、後の要求は、先の要求の記録を見て、その結果を返す（draft が、処理中の同じキーに求める409（SHOULD）は、使わない）。
- 残す期間は24時間：記録は、書いた時刻（`at`）を持つ。保存の操作は、1時間に1回まで、操作の前に、別の `Update` で、24時間以上たった記録（時刻の無い古い記録も）を消し、1件でも消したら、アクティビティログに `operations.expire`（`actor` は `system`、`detail.expired` は消した数）を1件足す（6.7・7.4）。消す `Update` が失敗しても、操作は続け、次の確かめは1時間後。24時間たった再送は、新しい操作として動く。draft は、キーの期限を決めて、文書に書くことを求める（SHOULD）。Stripe も、API v1 では、24時間以上たったキーを、自動で消せるとする（2026-11-12に確かめた）。
- メモリ：記録1件は、メモリを約570〜630バイト使う。測った値（2026-11-12。開発のマシン、Go 1.27.3。`SaveRevision` の記録と同じ形の436バイトの値と29バイトのキーを、1000件ずつの `Update` で置いた）：10万件で、置くのに0.40秒、ヒープが約60MiB増え（1件約632バイト）、開き直すと0.06秒で約56MiB（1件約570バイト）、ディスクは約90MiB。100万件で、置くのに4.35秒、ヒープが約593MiB増え（1件約622バイト）、開き直すと0.51秒で約545MiB（1件約570バイト）、ディスクは約900MiB。消さないと、操作のIDを付けた保存のたびに増え続ける（10人が1日50回なら、1年に約110MB。見積もり）ので、4.3が目安とする1GiBほどのVPSでは、数年で効く。24時間で消せば、1日に1万件でも約6MB（見積もり）。
- 表の版は上げない（6のまま）：表のキーと値の置き方は変わらず、値は edit が書く JSON で、保存先は読まない（3.4）。前のプログラム（`at` を知らないもの）は、知らない `at` を読み飛ばし（`encoding/json/v2` の既定。2026-11-12に確かめた）、新しいプログラムは、`at` の無い記録を古いものとして消す。監査の記録は、読むときに操作の名前を確かめない（7.4の `Decode`）ので、前のプログラムも、`access.denied` と `operations.expire` の記録を読み、鎖を確かめられる。これで、前のプログラムに戻しても、同じ保存先を開ける。
- 外への作用（メールなど。コミットの後に送るもの）は、まだ無いので、outbox は作らない（作るときに決める。6.12の202）。

リバースプロキシ（設定は9.6の「リバースプロキシ」。設定の例は #49）：

- 本文の上限：Nginx の `client_max_body_size` の既定は1MiBで、本文がそれを超えると、Nginx が413を返す（2026-11-12に確かめた）。文書の口の本文は64MiBと64KiBまで、アップロードは64MiBまで受け取る（上記）ので、管理用のサーバーへの場所では、64MiBと64KiB以上（例：`65m`）にする。
- 上流を待つ時間：Nginx の `proxy_read_timeout` の既定は60秒で、上流から読む2回の間の時間（応答の全体の時間ではない）。その間に何も来なければ、接続を閉じる。Apache の `ProxyTimeout` の既定は `TimeOut` の値で、`TimeOut` の既定は60（2026-11-12に確かめた）。答えを作り終えてから送る口は、その間、何も送らない：ログを読む口は、最大120秒（要求の期限が120秒）、重い仕事の口は、場所を待つ30秒と処理の30秒で、答えの最初のバイトまで最大約60秒かかり、既定の60秒の境にある。そのため、管理用のサーバーへの場所では、上流を待つ時間を120秒以上にする（120秒にすれば、両方が収まる）。
- アップロードと原本の取得は、最大10分かかる（サーバーの側の、受け取る期限と、送る期限）が、プロキシの時間を10分以上にする必要は無い：Nginx の `proxy_read_timeout`・`client_body_timeout`・`send_timeout`（どれも既定は60秒）は、2回の読み書きの間の時間で、転送の全体の時間ではなく、データが流れ続ける間は、既定のままでも切られない（2026-11-12に確かめた）。
- Nginx は、既定で、本文と答えをバッファーする（`proxy_request_buffering on`・`proxy_buffering on`。2026-11-12に確かめた）ので、Nginx の後ろでは、本文をゆっくり送る人と、答えを読まない人を、Nginx が受け持つ（バッファーしない設定や、プロキシを通さない localhost の http では、サーバー自身の期限と1人の数が守る）。Apache の、この点は、確かめていない。
- 設定の例は #49。

**プロセスと Unix ユーザー**

- ビルドは、管理用のサーバー（書くプロセス）の中で、`Publisher` が動かす（4.4）。管理のAPIも、そのプロセスの中でビルドの口を持つ。ビルドのメモリ（2万件で最大RSS 512MiBが目標。4.3）が、管理用のサーバーのメモリに足される。テーマのテンプレートの実行には、時間とメモリの上限がかからない（5.3）。ビルドを別のプロセスにして、上限をかけることは、まだしない（6.12の182）。
- 公開用のサーバー（9.5）と管理用のサーバーを、別の Unix ユーザーで動かすときの、データのディレクトリと出力先の分け方は、9.2（案）：データのディレクトリは管理用のユーザーだけ、出力先は管理用のユーザーが書き、公開用のユーザーが読む。ファイルのモード（3.4・4.3）は、いまの作りのまま変えない。

**テスト**

- 主な規則は、テストで守る。主なもの：
  - 権限：ロールごとに許される口と断られる口、本文を受け取る前の確かめと `Update` の中の確かめ（確かめの間に、ロールの変更・無効にする操作・資格の変更・アカウントを消すことを差し込む）、断った要求の記録（1分に10件と `suppressed`、記録が書けないとき）。
  - 上限：場所が1つであること、1人4つ、本文をゆっくり送る人と、答えを読まない人が（実際に待ち受けるサーバーで）ほかの人を止めないこと、本文と答えが一時のファイルに移ること、一時のファイルが要求の終わりに消えること、期限。
  - 形：答えの JSON の形（ビルドの状態などは、文字列で比べる）、文書のバイト列がそのまま返ること、一覧の絞り込み・並べ替え・ページ送り、問題の100件と残りの数。
  - 秘密：テストのサーバーが、答え・ヘッダー・ログ・記録のすべてを集め、要求に入れたパスワードとトークンが、どこにも出ないことを確かめる。例外は、セッションのトークンを渡す `Set-Cookie` と、招待と再設定の答えの本文のトークンだけ。
  - 通し：API だけで、エントリーを作り、下書きを保存し、公開し、ページが出力先に出るまで。閲覧者の公開は断られ、`access.denied` が記録され、何も公開されない。
- 確かめていないもの：実際のブラウザー（Cookie。`Content-Disposition: attachment` でも `<img>` が表示されること。画面の段階で確かめる）、実際のリバースプロキシ（Nginx・Apache・Caddy）の上限と待ち、HTTP の口での同時の要求（測った値は、保存先の読みで、HTTP の口ではない）、メモリの最悪の重なり（見積もり）、大きいログの上での読み（200万件までしか測っていない）。
