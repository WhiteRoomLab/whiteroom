### 6.7 検証のルール（Validator）

- 定義にないブロック・属性・フィールドはエラーにする。型、必須、文字数、数値の範囲を検証する。
- JSONの読み込み（案）：定義にない種類とキーはエラーにする。キーは大文字小文字を区別して照合する。重複したキー、`null`、空の値（`""`・`{}`・`[]`）、不正なUTF-8、対になっていないサロゲート（`\ud800` など）、1つの値の後に続く余分なデータは拒否する。空の値は書かずに省く（ただし、文中装飾つきのテキストそのものと、ブロックの列そのものは空の `[]` でもよい）。読み込みでは値を変えず、正規化（制御文字の除去など）と検証は、その後の別の段階で行う。ブロックの読み込みでは、種類と合わないキー（部品の `id`、中身を持たない種類の `content`、ほかの種類の属性など）もエラーにする。必須の項目（`id`、必須の属性、子の数）は読み込みでは確かめず、検証でまとめて確かめる（問題をエディタに一度に示せるように）。整数の属性は、読み込みでも書き方（`2.0` や `2e0` は不可）と範囲を確かめる（0は省略と区別できず、書き出すと消えるため）。サイト設定の2つのファイル（設定の文書とスキーマのファイル。6.6.8）と、テーマの設定ファイルと翻訳ファイル（5.4.2・5.4.6）も、この規則で読む（YAMLのファイルは、YAMLをJSONにしてから読む。YAMLの範囲は6.6.8）。
- 入れ子の規則：`listItem` は `list` の中だけ、`column` は `columns` の中だけ、`tableRow`・`tableCell` は表の中だけに置ける。`columns` の入れ子と、共有ブロックの循環は禁止する。追加の規則（案）：`button` も `buttons` の中だけに置ける。`list`・`table`・`tableRow`・`buttons`・`columns` には、それぞれ `listItem`・`tableRow`・`tableCell`・`button`・`column` だけを1つ以上置く。`listItem` の中身は、`paragraph` 1つと、その後の `list`（任意）。本文の直下と、`quote`（1つ以上）・`group`・`column`（空でもよい）の中には、部品・`button`・`column` 以外のブロックを置ける。`columns` は、祖先のどこかに `columns` があれば置けない（`column` の中の `group` の中なども同じ。横並びは `group` の `layout` で表す）。表の行は `head`・`body`・`foot` の順に並べる（`section` を省いた行は `body`。`foot` の後の `body` のように、それまでの行より前の区分に戻る行はエラー）。見出しの中身は空にできない。
- 上限：入れ子の深さ、1文書あたりのブロック数、テキストの長さ、表のセル数、メディアの大きさ、メニューとフォームの項目の数に上限を設ける。ビルドを安定させ、サービス妨害を防ぐため。仮の値（案）は、入れ子の深さ32段（本文の直下が1段目。部品も1段と数える）、1文書（6.5.1）のブロック数1万個（部品を含む）、1つの表のセル5千個（各行の `tableCell` の合計）、1つの文字列1MiB（UTF-8のバイト数。テキスト・HTML・URL・名前のそれぞれの文字列にかける）、メディアの1つのファイル64MiB（画像もPDFも）と画像の幅×高さ1億画素（6.6.2）、メニューの入れ子の深さ8段（最上位の項目が1段目）と1つのメニューの項目1000個（子項目も数える。6.6.4）、1つのフォームの入力の項目100個・1つの項目の選択肢1000個・通知先10個（6.6.5）。ブロックの入れ子の深さとブロック数、メニューの入れ子の深さと項目の数は、JSONの読み込みでも確かめ、超えたところで読むのをやめる（フォームの上限は、検証だけで確かめる。値の見直しは6.12の9）。
- ID：エンティティのIDは、種類ごとの接頭辞と `_` のあとに、ULID（26文字。大文字のCrockford Base32で、先頭は `0`〜`7`）を続ける（決定済み。6.1）。接頭辞は、エントリー `ent`、リビジョン `rev`、翻訳グループ `tg`、メディア `med`、ターム `trm`、著者プロフィール `aut`、メニュー `mnu`、フォーム `frm`、リダイレクト `rdr`、ログインアカウント `usr`（案）。参照では、種類と接頭辞の合わないID（画像の `media` に `ent_` など）をエラーにする。ブロックのIDは6.5.1。保存の操作が作るIDは、ULIDの先頭の48ビットを、作った時刻（Unixミリ秒）にし、残りの80ビットを乱数にする（案）。同じプロセスの中では、IDは、作るたびに大きくなる（同じミリ秒の中と、時計が戻ったときは、前のIDの乱数の部分に1を足す。足せなくなれば、エラー）。WordPressからの取り込みのID（6.10.5）は、時刻の部分が `0` で、残りをハッシュから作る。保存の操作の操作のID（下記の「保存の操作（案）」）は、接頭辞 `op` と、同じ形のULID。
- 参照：メディア・エントリー・ターム・フォーム・著者プロフィールのIDが存在すること。下書きのエントリーへのリンクは、公開時に警告する（描画では、リンクにせずに文字を残して警告する。6.5.2。公開していないエントリーを指すメニューの項目とリダイレクトは、ビルドで警告して出力しない。6.6.4・6.6.6）。照会（案）：IDの書式を確かめ、存在するかと種類は、検証に渡す照会の関数で確かめる。照会の関数は、参照の種類とIDを受け取り、あるかどうかと、エントリーのタイプ・タームのタクソノミー・メディアの種類（`image`・`pdf`。`mimeType` から決まる。6.6.2）、エントリーとタームの言語を返す。関数を渡さなければ、存在も種類も確かめない。ビルドは、読んだ文書から作り（下記の「ビルドでの検証」）、保存の操作（下記の「保存の操作（案）」）は、保存先の索引の要約（3.4の「索引」）から作る。保存先を読めなかったとき（`Summary` が、無いことの分かるエラー（Goの `fs.ErrNotExist`）以外のエラーを返したとき）は、その操作を、保存先のエラーで失敗させ、検証の結果は返さない（6.12の18）。照会の関数は、エラーを返さない形のままなので、最初のエラーを覚えて、検証の後に返す。ブロックの属性の参照（`image`・`file` の `media`、`form` の `form`）も、リンク（文中と、`image`・`button` の `link`）の `entry`・`media` も、エントリーの項目とカスタムフィールドの参照も、タームの `parent` と著者プロフィールの `avatar` も、メニューの項目の `entry`・`term` も、リダイレクトの `to` のID（接頭辞で種類を決める。6.6.6）も、フォームの `thanksPage`・`policy` も、サイト設定の `logo`・`icon`・`seo.ogImage`・`frontPage`・`postsPage`（6.6.8）も、同じ関数で確かめる。種類の照合（案）：`image` ブロック・アイキャッチ画像・OGP画像・著者プロフィールの `avatar`・サイト設定の `logo`・`icon`・`seo.ogImage` のメディアは画像だけ、`media` のフィールドは `accept` の種類だけ、`entry` のフィールドは `types` のタイプだけ、タームはタクソノミーが合ってエントリーと同じ言語のものだけ、固定ページの `parent` は同じ言語の固定ページだけ、タームの `parent` はタクソノミーと言語が同じタームだけ、フォームの `thanksPage`・`policy` はキーと同じ言語のエントリーだけ（タイプは問わない）、サイト設定の `frontPage`・`postsPage` はキーと同じ言語の固定ページだけ。メニューの項目の `entry`・`term` と、リダイレクトの `to` のIDは、存在だけを確かめる（言語、エントリーのタイプ、タームのタクソノミー、メディアの種類は問わない）。
- 日時：時差付きのRFC 3339で、秒まで書く（例：`2026-10-25T10:00:00+09:00`。決定済み。6.1）。小数の秒は使えず、`T` と `Z` は大文字、時差は `Z` か `±hh:mm`（00:00〜23:59）にする（案）。日付だけのもの（`date` のフィールド）は `YYYY-MM-DD`。
- サイト設定（案）：サイトのURL・タイムゾーン（IANAの名前）・タイトルの書式・URLの規則（一覧のパスを含む）は、6.6.8の規則で確かめる。サイト設定の正規化（制御文字の除去など）は、設定の文書の項目に、管理画面が保存する前に6.6.8のとおり行い、スキーマのファイルの項目には行わない（どちらも、正規化していない値は、検証でエラーにする）。
- 複数のエンティティにまたがる検証：スラッグの一意性（エントリーは6.4.2のとおり、タームは同じタクソノミー・同じ言語の中、著者プロフィールはサイト内）、翻訳グループの中で同じ言語は1件まで（エントリーとターム）、同じ言語・同じ表示場所のメニューは1つまで（6.6.4）、同期する項目の一致（6.4.5）、親の循環（固定ページとターム）、リダイレクトのループと `from` の重複、出力パスの重複（4.1。パスの求め方は6.6.8、リダイレクトの `from` の比べ方は6.6.6）。保存の操作は、保存先の索引（3.4）から作ったサイトの模型を、ビルドと同じコード（`internal/siteplan`。4.3）で確かめる（案。下記の「保存の操作で」）。公開の操作（下記の「公開の操作（案）」）も、同じ規則で扱う。ビルド（4.3）は、同期する項目の一致（決め方は6.12の27）を除いて、これらを確かめ、1つでもあれば失敗する（決定済み。4.1）。ビルドの規則（案）は次のとおり（エラーの形は4.3の「エラーと警告」。下の例は、JSON Pointerと文だけ）。
  - 確かめるとき：ビルドの段階（4.3）のうち、文書の読み込み・サイト設定とテーマ・公開するものの検証（下記の「ビルドでの検証」）にエラーが無いときだけ確かめ、見つけたものをまとめて示す。出力パスの重複は、その後で、パスを求めてから確かめる。
  - エラーを付けるもの：重なりの規則（下の2〜6と9）では、文書をIDの順（ファイル名の順）に見て、同じキーを最初に持つものを残し、後のものすべてにエラーを付ける。エラーの文は、最初のもののファイルを示す（3つ重なれば、2つ目と3つ目が、どちらも1つ目を示す）。循環の規則（8と10）では、循環に入るものそれぞれに、循環ごとに1回付ける。
  1. トップページと投稿ページ：サイト設定の `frontPage`・`postsPage`（6.6.8）は、公開しているエントリー（`status` が `published`）を指す。サイト設定の検証は、照会の関数がどの状態のエントリーも見つけるので、下書きを指すものも受け付けるが、ビルドは、公開したリビジョンのスラッグでパスを求めるので、公開していないものはエラーにする（ほかのページで代えない）。設定の文書の `/frontPage/<言語>`・`/postsPage/<言語>` に、`/frontPage/ja: entry "ent_…" is not published`。
  2. エントリーのスラッグ（6.4.2）：公開しているエントリーだけを比べる（ほかのエントリーのリビジョンは読まない）。言語・タイプ・スラッグが同じものを重なりとし、固定ページは、親（公開したリビジョンの `parent`）も同じものだけにする。同じスラッグは、ほかの言語・ほかのタイプと、親の違う固定ページ（`/about/team/` と `/services/team/`）なら使える。後のエントリーの公開したリビジョンの `/slug` に、`/slug: slug "about" is also used by revisions/rev_….json`（最初のエントリーの公開したリビジョン）。
  3. タームのスラッグ（6.6.1）：すべてのタームで、タクソノミー・言語・スラッグが同じものを重なりとする（親は問わない。階層ありのタクソノミーでも、タクソノミーと言語の中で一意）。タームの `/slug` に、`/slug: slug "news" is also used by terms/trm_….json`。
  4. 著者プロフィールのスラッグ（6.6.3）：サイトの中で一意。`/slug` に、`/slug: slug "yamada" is also used by authors/aut_….json`。
  5. 翻訳グループ（6.4.5）：1つのグループに、1つの言語のエントリーは1件まで、タームも1件まで。エントリーは、すべての状態のもの（下書き・予約・アーカイブも）を数え、`translationGroup` か `language` の無いもの（検証しない下書きにはあり得る）は除く。エントリーとタームは別に数え、エントリーのタイプは比べない。エントリーかタームの `/translationGroup` に、`/translationGroup: translation group "tg_…" already has an entry in the language "en": entries/ent_….json`（タームは `… already has a term in the language "en": terms/trm_….json`）。
  6. メニュー（6.6.4）：1つの言語・表示場所に1つまで。`location` の無いメニューは除き、テーマの表示場所は見ない（テーマに無い表示場所のものも数える）。メニューの `/location` に、`/location: location "header" already has a menu in the language "ja": menus/mnu_….json`。
  7. 固定ページの親：公開している固定ページの親（公開したリビジョンの `parent`）は、公開しているものにする（同じ言語の固定ページであることは、参照の検証で確かめてある）。固定ページの公開したリビジョンの `/parent` に、`/parent: entry "ent_…" is not published`。
  8. 親の循環（6.4.3・6.6.1）：公開している固定ページ（公開したリビジョンの `parent` でたどる。公開していない親で終わるものは7）と、すべてのタームで、親をたどって元に戻るもの。循環に入るものそれぞれの `/parent`（固定ページは公開したリビジョン、タームは文書）に、`/parent: the parents make a cycle: A -> C -> B -> A`（A・B・CはIDで、いちばん小さいものから、親の順に並べ、最初のものに戻る）。循環の外から循環に入るものには付けない。自分を親にするものは、ほかの検証のエラー（`an entry cannot be its own parent`・`a term cannot be its own parent`）。
  9. リダイレクトの `from` の重複（6.6.6）：同じリクエストに一致する `from` を重複とする。`from` の正規の形から、パスの末尾の `/` を除いたもの（`/` だけのものは除かない）で比べる。`/old/` と `/old`、`/old/?x=1` と `/old?x=1` は重複し、`/old/` と `/old/?x=1` は重複しない（両方に一致するリクエストには、6.6.6の順で、クエリつきのものを使う）。後のリダイレクトの `/from` に、`/from: from "/old" matches the same requests as that of redirects/rdr_….json`。
  10. リダイレクトのループ（6.6.6）：リダイレクトごとに、`to` をリクエストとしてたどる。たどるのは、サイト内のパス（`#` 以降を除く）と、サイトのURLの中の `http`・`https` のURL（サイトのURLからのパスとクエリにする。自分自身への転送の検査と同じ規則。6.6.6）。エンティティのIDはたどらない（行き先のURLにクエリが無いので、それに一致する `from` は出力パスと重なり、4.1のエラーになる）。サイトの外のURLもたどらない。次のリダイレクトは、そのリクエストに使われるもの（6.6.6の照合と順）にする。リクエストのクエリは行き先に付けない（6.12の55）ので、`to` に書いたクエリだけで照合する。終わる転送の連鎖は、長さによらず受け付け、循環だけをエラーにする。循環に入るものそれぞれの `/to` に、`/to: redirect loop: A -> B -> A`（並べ方は8と同じ）。例：`/a` から `/b?x=1` へ、`/b?x=1` から `/a` への2つは循環になる（後のものが `/b?y=1` からなら、`/b?x=1` に一致する `from` が無く、そこで終わる）。自分自身への転送は、ほかの検証のエラー（6.6.6）。`.`・`..` の区切りを含む `to`（ブラウザーは `/x/../a` を `/a` にする）は、自分自身への転送の検査と同じく、書いたままで比べる。
  11. 出力パスの重複（4.1）：ページとほかの出力のパスを求めてから、リダイレクトと合わせて確かめる（規則とエラーの文は6.6.8）。
  - 保存の操作で（案）：保存の操作は、変更の前のサイトと、後のサイトの模型（ビルドが、読んだ文書から作るものと同じ形のものを、保存先の索引から作る）に、ビルドの段階の順で、上の1〜10と、11のうち書く前に確かめるもの（ページとほかの出力の計画と、リダイレクトの行き先の決定を含む）を確かめ、後のサイトで増えた問題だけを示す。増えた問題とは、ファイル・JSON Pointer・文が、前のサイトのどの問題とも同じでないもの。示すファイル・JSON Pointer・文は、ビルドと同じで、行と列は、操作に渡したバイト列（無ければ、保存先のバイト列と、スキーマのファイル）に付く（テーマの `assets/` のように、位置の無いものには付かない）。重なりの問題は、上の「エラーを付けるもの」に従って、後のIDの文書に付くので、いま保存した文書ではなく、ほかの文書に付くことがある。段階の順に確かめ、増えた問題のある最初の段階で止めて、その段階の増えた問題だけを示す（ビルドは、問題のある最初の段階で止めるが、保存の操作は、前からの問題だけの段階では止めない）。増えた問題は、エラーで、操作を断り、何も保存しない（ただし、下書きのリビジョンを保存する操作の、公開したとしたときの問題は、警告。下記の「保存の操作（案）」）。変更の前からあった問題は、断らず、示さない（前からの問題のあるサイトにも、ほかの変更を保存できる）。ビルドだけが確かめるもの（書いた後に分かる出力パスの重複。6.6.8・6.12の151）と、同期する項目の一致（警告にする。6.4.5）は、ここでは確かめない。費用は、サイトの大きさに比例する（6.12の150）。
- 取り込みと前のリビジョン（案）：検証には、`html` ブロックを有効にしたか（サイト設定の `allowHtml`。6.6.8）、取り込みかどうか、前のリビジョンのブロックと、サイトのテーマの設定（5.4.2。渡さなければ、テーマと照合しない）を渡す。`html` は有効にしたときだけ受け付ける。`legacy` と、`alt` の無い画像（`decorative` でないもの）は、取り込みのときと、前のリビジョンの同じ `id` のブロックから変えていないとき（`legacy` は `html` と `reason` が同じ、画像は同じ `media` で `alt` が無いまま）だけ受け付ける。テーマとの照合（6.5.3）でも、取り込みと、前のリビジョンから変えていない値は受け付ける（決定済み。6.1）。前のリビジョンのブロックは `id` で探し、位置は問わない（同じ `id` が2つ以上あれば、最初のもの）。リビジョンの検証では、前のリビジョンの本文と、`blocks` 型のフィールド（`group`・`list` の中も含む）のブロックをまとめて探す（本文からフィールドへ移したブロックも、変えていなければ受け付ける）。`highlight` の色は、`richText` 型のフィールド（`group`・`list` の中も含む）の中も探す。
- ビルドでの検証（案）：ビルド（4.3）は、公開するものを検証し、1つでもエラーがあれば失敗する（決定済み。4.1）。失敗しても、公開中の成果物は変えない（通らなくなる変更は6.12の109）。検証のしかたは次のとおり。
  - 読み込み：すべての種類のすべての文書を、この節のJSONの読み込みの規則で読む（照会に使うので、検証しない下書きのエントリーも）。文書の中の `id` は、文書のID（サイトのディレクトリでは、ファイル名のID。4.3）と同じにする（違えば `/id: id "ent_…" differs from the ID of the document, "ent_…"`。`id` の無いものは、検証するものだけを、検証で `missing id` にする）。
  - エントリー：公開しているもの（`status` が `published`）だけを、IDの順に検証する。エントリーが検証を通れば、`publishedRevision` のリビジョンを読み（無ければ、エントリーの `/publishedRevision` に `revision "rev_…" does not exist`）、公開するリビジョンとして（必須の項目も。6.4.2）検証する。下書き・予約・アーカイブのエントリーは検証せず、そのリビジョンも読まない（無くても、壊れていてもよい）。
  - 取り込みとして：リビジョンは、取り込みとして検証する（上記の「取り込みと前のリビジョン」）ので、`legacy` と、`alt` の無い画像を受け付ける。保存の検証が、取り込みと、前のリビジョンから変えていないものだけを受け付けており、ビルドは、取り込んだリビジョンと、前のリビジョンから変えずに残したものを見分けられないため。`html` は、取り込みでも、`allowHtml`（6.6.8）が無効なら受け付けない。
  - テーマを渡さない：テーマとの照合（6.5.3）をしないので、テーマが許さない見た目の値では失敗しない（描画で、警告して無視する。6.5.3）。
  - ほかの文書：ターム・メディア・著者プロフィール・メニュー・フォーム・リダイレクトは、下書きが無いので、すべてを検証する（6.12の38）。
  - 照会の関数：ビルドが、読んだ文書から作る。参照の照会（上記の「参照」）は、エントリー（どの状態のものも）・ターム・メディア・フォーム・著者プロフィールを見つける（下書きへのリンクは、描画で警告する。6.5.2）。パスの照会（6.6.8）は、公開している固定ページ（公開したリビジョンのスラッグと親）と、すべてのタームを見つける。
- 保存の操作（案）：管理画面が文書を保存するときの操作（`internal/edit`）。文書を検証してから、保存先（3.4）に保存する。操作は、エントリーの作成（`CreateEntry`）・下書きのリビジョンの保存（`SaveRevision`）・翻訳の作成（`CreateTranslation`）・削除（`Delete`）、ターム・著者プロフィール・メニュー・フォーム・リダイレクトの作成（`Create`）・保存（`Save`）・削除、設定の文書の保存（`SaveSettings`）、メディアの追加（`AddMedia`）・差し替え（`ReplaceMedia`）・メタデータの保存（`Save`）・削除と、エントリーの状態を変える公開の操作（公開 `Publish`・公開をやめる `Unpublish`・アーカイブ `Archive`・予約 `Schedule`・予約の日時の公開 `PublishScheduled`。下記の「公開の操作（案）」）。呼ぶ側（管理のAPI。#48）が、操作した人のID（`usr_` とULID）を渡し、操作は、書式だけを確かめる（アカウントは#45）。同時に呼んでもよい。各操作は、保存先の1回の `Update`（3.4の「壊れない書き込み」）で、文書・リビジョン・索引・操作のIDの記録を書き、失敗すれば、何も残さない（メディアの原本は、先に書く。3.4の「原本」）。
  - 進み方：操作する人と、操作のID（下記）の書式を確かめる。`Update` を始めて、操作のIDの記録があれば、その結果を返して終わる（下記）。元にした版を確かめる（下記）。渡された文書を、大きさ（64MiB。読む前に確かめる。3.4の「上限」。リクエストの本文の上限は#48。6.12の24）と、上記の「JSONの読み込み」で確かめる（作るときは、`id` を書けない。`/id: not allowed when creating; the store assigns the ID`。保存では、`id` があれば、文書のIDと同じにする。`/id: id "…" differs from the ID of the document, "…"`）。正規化する。サイト設定（保存先の設定の文書と、スキーマのファイル。ビルドと同じ読み込み。6.6.8）・テーマの設定（5.4.2）・前のリビジョン（上記の「取り込みと前のリビジョン」）で検証する（参照の照会は、索引から。上記の「参照」）。保存する。ほかの文書を検証し直す（下記の「参照する文書の検証」）。サイトの模型を作って、またがる検証をする（上記の「保存の操作で」）。操作のIDの記録を書く。
  - 問題の示し方：文書の問題は、ビルドと同じ形（ファイル・行・列・JSON Pointer・文。4.3の「エラーと警告」）で、エラー（Goの `content.Errors`）として返し、何も保存しない。ファイルは、サイトのディレクトリでの名前（`terms/<ID>.json`・`revisions/<ID>.json`・`site/settings.json`。3.4の「書くときの確かめ」）で、行と列は、渡したバイト列に付く（操作が作る文書は、書き出したもの。1行）。警告は、保存して、結果に付ける。同じ問題のあるサイトで、保存の操作とビルドが、同じ行を示すことは、テストで確かめる（`internal/edit` の `TestSaveParity`・`TestRefChangeParity`・`TestSettingsChangeParity`・`TestImportParity` など）。
  - 保存するバイト列（案）：正規化しても、書き出す値が変わらなければ、渡されたバイト列のまま保存し、変われば、正規化した値の書き出したもの（6.9）を保存する。操作が作る文書（作成・翻訳・メディアの追加と差し替えなど）は、書き出したもの。いまの版と同じバイト列の保存は、何も保存せずに、いまの版を返す（3.4）。
  - 元にした版（案）：作成のほかの保存と削除には、呼ぶ側が読んだときの版を渡し、保存先のいまの版と違えば、何も変えずに失敗する（Goのエラーは `ErrConflict` を包む）。後で保存する人が、前の保存を黙って消さないため。版は、文書ではいまの版の番号（`Seq`。設定の文書は、まだ無ければ0）、エントリーのリビジョンの保存では、最後のリビジョンのID（無ければ空）。例：`terms/trm_….json: changed since it was read: it is at version 4, not 3`、`entries/ent_….json: changed since it was read: its latest revision is rev_…, not none`。無い文書は、`<名前>: not found`（`fs.ErrNotExist`）。
  - 操作のID（案）：呼ぶ側は、操作に、任意で、操作のID（`op_` とULID。呼ぶ側が作る）を渡せる。渡せば、操作の `Update` の中で、操作のIDの記録を、表 `operations`（3.4の「索引」）に、要求（操作した人・操作の名前・引数・渡したバイト列）のSHA-256と、結果（警告も）で置く。同じIDの操作が、同じ要求で来れば、何も保存せずに、前の結果を返し（返事が届く前にクラッシュしたときの再送で、2度保存しないため。3.5の「冪等性の責務」）、要求が違えば（操作した人が違うのも）、`operation ID "op_…" was used for another request` で失敗する。失敗した操作は、記録しない（再送すれば、もう一度動く）。成功して何も保存しなかった操作（同じバイト列の保存など）は、記録する。記録は、消さずに残す（残す期間は#48。6.12の153）。
  - 下書きのリビジョンの保存（案。`SaveRevision`。6.4.2）：エントリーの最後のリビジョンとして、リビジョンを足す（公開はしない）。保存のたびに新しいリビジョンを足す（6.4.1）ので、最後のリビジョンと同じ内容でも足す（6.12の157）。リビジョンのIDは、保存先が作る。リビジョンは、エントリーのタイプで正規化して、公開しないリビジョンとして検証する（上記の「取り込みと前のリビジョン」。取り込みではなく、前のリビジョンは、そのエントリーの最後のリビジョン）。その問題（書式・型・参照・テーマとの照合。新しい `legacy` のブロックと、`alt` の無い画像など）は、エラーで、保存しない。保存して、警告にするものは、次の順に求める。(1) 公開するのに足りない項目（必須の項目、最小の文字数・件数、`{category}` に要る `category`。6.4.2。公開するときの検証だけが見つけるもの）。(2) (1)が無いときだけ、そのリビジョンでエントリーを公開したとしたときに、ビルドと同じ確かめが見つける問題（スラッグの重なり・親が公開していない・翻訳グループ・リダイレクトの `from` と出力パスの重なり、リダイレクトの警告など。上記の「保存の操作で」を、そのエントリーを公開したサイトの模型にかけて、いまのサイトの模型には無い問題だけ）。(3) 同期する項目の食い違い（6.4.5）。警告の位置は、新しいリビジョンに付くが、重なりのように、ビルドが後のIDの文書に付けるものは、後のIDのエントリーの公開したリビジョンに付く（行と列は、保存先のバイト列に付く）。翻訳の作成（6.4.5）も、新しいリビジョンを、同じに確かめる。
  - 削除（案。`Delete`）：公開中のものが参照しているものは、消せない。公開中のものは、ターム・メディア・著者プロフィール・メニュー・フォーム・リダイレクトの文書と、設定の文書（下書きが無いので、どれも公開中）と、エントリーの公開中のリビジョンと、予約中のエントリーの予約したリビジョン（予約の日時に公開するので、公開中のものと同じに守る）。参照は、索引の `Referrers`（3.4の「索引」。本文のテキストの中のIDも数える。6.12の152）で調べる。エラーは、`media/med_….json: cannot delete: used by revisions/rev_….json, site/settings.json` で、使っているファイルを、名前の順に10個まで示し、残りは `and <数> more` にする（6.12の154）。下書き（公開も予約もしていないエントリーの最後のリビジョン）だけが参照しているときは、警告して消す（`terms/trm_….json: deleted although used by revisions/rev_….json, the latest revision of entries/ent_….json, which is not published`。エントリーごとに1つ）。公開中・予約中のエントリーは、消せない（先に公開をやめる。公開をやめる操作は、下記の「公開の操作（案）」の `Unpublish`。`entries/ent_….json: /status: cannot delete a published or scheduled entry; unpublish it first`）。エントリーを消しても、そのリビジョンは残る（3.4）。メディアを消しても、原本は残る（3.4・6.12の125）。設定の文書は、消せない（`site/settings.json: cannot be deleted`）。消した後のサイトの模型も、またがる検証にかける（上記の「保存の操作で」）。
  - 参照する文書の検証（案）：ビルドは、公開するもの（ターム・メディア・著者プロフィール・メニュー・フォーム・リダイレクトの文書と、公開しているエントリーの状態と公開したリビジョン）を、それぞれ検証する（上記の「ビルドでの検証」）ので、保存した文書が、ほかの文書の検証が読むものを変えると、保存した文書が検証を通っても、ビルドが失敗することがある（例：タグの `language` を `en` に変える保存が通り、そのタグを使う公開中のリビジョンで、ビルドが `/terms/tag/0: term "trm_…" is in the language "en", not "ja"` で失敗する）。そこで、保存の操作は、ほかの文書を、次のように検証し直す（示す問題の範囲は6.12の163）。
    - 時：文書を保存して、その文書について照会の関数が返すもの（エントリーのタイプと言語、タームのタクソノミーと言語、メディアの種類。上記の「参照」）が、保存の前と変わったとき、その文書を参照する文書（索引の `Referrers`）を、検証し直す。設定の文書を保存して、設定が変わったときは、すべての文書と、すべてのエントリーの公開したリビジョンと予約したリビジョンと最後のリビジョンを、検証し直す（設定は、すべての検証が読むため）。いまの操作では、エントリーのタイプと言語と、メディアの種類は、変えられない（6.12の164）ので、働くのは、タームの `taxonomy`・`language` の変更と、設定の保存。
    - 検証：ターム・メディア・著者プロフィール・メニュー・フォーム・リダイレクトの文書と、設定の文書と、公開しているエントリーの状態と公開したリビジョン（取り込みとして、テーマ無しで）は、ビルドと同じに検証する。そこで増えた問題は、エラーで、操作を断る（ビルドと同じファイル・JSON Pointer・文。行と列は、保存先のバイト列に付く）。予約しているエントリーの状態と予約したリビジョンは、ビルドは検証しないが、予約の日時の公開が、公開するときと同じに検証する（下記の「公開の操作（案）」）ので、公開しているものと同じに検証し、増えた問題は、エラーで断る（予約の日時に公開できなくなる変更を、先に断るため）。下書き・アーカイブのエントリーの状態と、エントリーの最後のリビジョンのうち、そのエントリーが公開も予約もしていないものは、ビルドが検証しないので、下書きのリビジョンの保存と同じに検証し、増えた問題は、警告にする（上記の「削除」と同じ分け方）。
    - 増えた問題：変更の前の状態（文書は、保存の前に照会が返したもの。設定は、前の設定）にも、同じファイル・JSON Pointer・文の問題があれば、増えたものではない（エラーにも、警告にもしない）。前の設定が無いか、読み込めないときは、すべての問題が、増えたものになる。
    - 順：保存した文書自身の検証の後、またがる検証（上記の「保存の操作で」）の前（ビルドの段階の順と同じ）。エラーがあれば、またがる検証はしない。
    - 費用：検証し直す文書の数に比例する（6.12の150）。多くのリビジョンが使うタームを変えると、ビルドと同じに、リビジョンごとに1つのエラーが出る（6.12の154）。照会の関数が返すものが変わらない保存と、何も保存しない保存は、読むものが増えない。
- 公開の操作（案）：エントリーの状態（6.4.1）を変える操作（`internal/edit`）。公開（`Publish`）・公開をやめる（`Unpublish`）・アーカイブ（`Archive`）・予約（`Schedule`）・予約の日時の公開（`PublishScheduled`）と、予約の一覧（`Schedules`）。上記の「保存の操作（案）」と同じく、1回の `Update` で確かめてから保存し、失敗すれば何も残さない。操作した人・操作のID・問題の示し方も同じ（`PublishScheduled` と `Schedules` は、操作した人も操作のIDも渡さない）。ビルドを起こすかは4.4。
  - 公開するリビジョンと元にした版（案）：`Publish` と `Schedule` は、エントリーの最後のリビジョンだけを、公開（予約）する。呼ぶ側は、エントリーの文書のいまの版（`Seq`）と、読んだ最後のリビジョンのIDを渡し、どちらかが違えば、何も変えずに失敗する（`ErrConflict` を包む。`entries/ent_….json: changed since it was read: it is at version 4, not 3`、`entries/ent_….json: changed since it was read: its latest revision is rev_…, not rev_…`）。リビジョンの無いエントリーは、文書の問題（`entries/ent_….json: has no revision to publish`。`Schedule` は `to schedule`）。`Unpublish` と `Archive` は、文書の版だけを渡す。
  - 日付（案）：投稿のリビジョンに `date` が無いとき、操作の時刻（予約は、予約の日時）を、サイトのタイムゾーン（6.6.8）で秒まで書いた `date` を入れたコピーを、新しいリビジョン（新しいID）として足し、そのリビジョンを公開（予約）する。足したリビジョンは、最後のリビジョンになる。元のリビジョンは変えない（6.4.1）。操作が失敗するときは、足さない。固定ページとカスタムタイプは `date` を持たない（6.4.3）ので、足さない。コピーの問題は、コピーのバイト列（`revisions/<新しいID>.json`。1行）に付く。
  - 確かめ：状態は、`status` に合わせた必須の項目も含めて（6.4.1）検証し、リビジョンは、ビルドが公開するリビジョンを検証するのと同じに（上記の「ビルドでの検証」の「取り込みとして」と「テーマを渡さない」。公開するのに足りない項目も確かめる。6.4.2）検証する。状態に問題があれば、それだけを示す（ビルドも同じ）。問題は、ビルドと同じ形で、状態は書き出したバイト列（1行）に、リビジョンはそのバイト列に付く。それから、またがる検証（上記の「保存の操作で」）を、操作の前と後のサイトの模型にかけ、増えた問題は、エラーで、何も保存せずに断る。例：スラッグの重なり（`revisions/rev_….json:4:3: /slug: slug "about" is also used by revisions/rev_….json`）、公開していない親（`revisions/rev_….json:5:3: /parent: entry "ent_…" is not published`）、出力パスの重なり（`revisions/rev_….json:4:3: /slug: output path "/en/feed/" is also that of the feed in en`）。増えた警告は、結果の `Warnings` に入れる。同じ問題のあるサイトで、公開の操作とビルドが、同じ行を示すことは、テストで確かめる（`internal/edit` の `TestPublishParity`・`TestUnpublishParity`・`TestScheduleParity`）。
  - すでにその状態のとき：同じ状態にする操作（公開中のエントリーを、公開中のリビジョンで公開する、下書きの公開をやめる、アーカイブしたものをアーカイブする、同じ予約をもう一度する）は、何も保存せず、いまの版を返す（`Publishes` は false）。
  - 公開をやめる・アーカイブ（`Unpublish`・`Archive`）：エントリーを `draft`・`archived` にして、`publishedRevision`・`scheduledRevision`・`scheduledAt` を外す。どの状態のエントリーからでもできる（予約を取り消すのは、公開をやめる操作）。リビジョンは残る。状態もリビジョンも検証しない（ビルドは、公開していないエントリーを検証しない。4.3）。公開しているものが要るものは、またがる検証が断る（サイト設定の `frontPage`・`postsPage` が指すエントリーは `site/settings.json:11:18: /frontPage/ja: entry "ent_…" is not published`、公開している固定ページの親は `revisions/rev_….json:5:3: /parent: entry "ent_…" is not published`）。そのエントリーを行き先とするリダイレクトは、ビルドが出力しなくなるので、警告にする（`redirects/rdr_….json:5:3: /to: entry "ent_…" is not published; the redirect is left out`）。ほかの、そのエントリーを指すもの（リンク・メニューの項目）は、警告しない（6.12の180）。
  - 予約（案。`Schedule`）：公開していないエントリー（`draft`・`archived`・`scheduled`）の最後のリビジョンを、予約の日時に公開するよう予約する。状態は `scheduled` で、`scheduledRevision` に予約したリビジョン、`scheduledAt` に予約の日時（サイトのタイムゾーン。秒まで）を持つ。公開しているエントリーは、予約できない（`entries/ent_….json:8:3: /status: a published entry cannot be scheduled; unpublish it first`。公開中のエントリーの差し替えを予約することは6.12の179）。予約の日時は、操作の時刻より後にする（`entries/ent_….json:1:225: /scheduledAt: 2026-11-09T09:00:00+09:00 is not after the time of the operation, 2026-11-10T09:00:00+09:00; publish it instead`）。確かめは、公開するときと同じ（状態とリビジョンの検証と、そのエントリーを、そのリビジョンで公開したときのサイトの模型での、またがる検証）で、増えた問題は、エラーで断る（6.12の187）。予約は、公開するものを変えないので、ビルドを起こさない。別のリビジョンか別の日時で予約し直すのも、同じ操作。予約を取り消すのは、公開をやめる操作。予約したリビジョンは、公開中のものと同じに守る（上記の「削除」と「参照する文書の検証」と、下記の「取り込み（案）」）。
  - 予約の日時の公開（案。`PublishScheduled`）：予約の日時が来たエントリーを、予約したリビジョンで公開する。公開（`Publish`）と同じ確かめと保存をする。呼ぶのは、公開の仕組み（4.4）で、いまの時刻（`now`）を渡す。保存した人は、予約を保存した版の保存した人（予約した人）になる。エントリーが `scheduled` でないとき、または予約の日時が `now` より後のときは、何も保存せず、`ErrNotDue` を包むエラーで失敗する（`entries/ent_….json: not scheduled`、`entries/ent_….json: scheduled at 2026-11-10T09:00:00+09:00, after 2026-11-10T08:00:00+09:00`）。先にエントリーの状態を検証するので、`scheduledAt` が読めない、`scheduledRevision` のリビジョンが無い、サイト設定が変わって言語が無くなった、などは、文書の問題として失敗する（`entries/ent_….json:1:1: /scheduledAt: missing scheduledAt of a scheduled entry`、`entries/ent_….json:8:3: /scheduledRevision: revision "rev_…" does not exist`。位置は、保存先のバイト列）。公開するときの問題も、同じに失敗する。どちらも、エントリーは `scheduled` のままで、何も保存しない。成功すれば `published` で、予約の2つの項目は外れる。旧URLからのリダイレクトは登録しない（公開していなかったので、旧URLが無い）が、新しいパスからのリダイレクトは消す（6.6.6）。予約したリビジョンに `date` の無い投稿（保存先のAPIでしか入らない）には、予約の日時を入れた新しいリビジョンを足す。
  - 予約の一覧（`Schedules`）：`scheduled` のエントリーと予約の日時を、日時の順に、同じ日時はIDの順に返す。`scheduledAt` が読めないものは、日時を零にして、先頭に並べる（その公開が、文書の問題を示すため）。保存先の要約から読む（3.4の「索引」）。
  - 結果と知らせ（案）：結果（`Result`）の `Publishes` は、その操作が公開するものを変えたか、`Status` は、公開・公開をやめる・アーカイブ・予約・予約の日時の公開が決めた状態（ほかの操作では空）。`Editor.Notify` で登録した関数は、操作が成功してコミットした後に、その結果を受け取る（何も保存しなかった操作も。失敗した操作と、操作のIDの再送で記録を返したものは、呼ばない）。公開の仕組み（4.4）が、これでビルドと予約の確認を起こす。費用は、サイトの大きさに比例する（6.12の150）。
- 取り込み（案）：サイトのディレクトリ（4.3）を、保存先に取り込む（`edit.Import`）。サイトは、ビルドの読み込みの口（`build.Source`）と同じ形の口（`edit.Source`。サイトのディレクトリは、その1つ）から、ビルドと同じに読む。WordPressからの取り込み（6.10）とは別のもの（WordPressからの取り込みは、サイトのディレクトリを書く。6.10.5。ここでいう取り込みは、そのサイトのディレクトリや、手で書いたサイトを、保存先に入れる）。操作した人のID（`by`）は、保存した人になる。
  - 保存先：文書が1つも無いものだけ（設定の文書も。消した文書は数えない）。あれば、何も読まず、何も書かずに、`the store is not empty: Import needs a store without documents` で断る（確かめは、原本を保存する前と、`Update` の中の2回。ほかの操作が、読んでいる間に文書を保存したときも、断る）。
  - IDと `number`：ファイルのIDと `number` を、そのまま使う（作り直さない）。保存先の最大の番号（3.4の「索引」）は、取り込んだエントリーの最大の `number` になり、次に作るエントリーは、その次の番号（6.4.1）。番号が重ならないことは、確かめない（6.12の155）。
  - 取り込むもの：設定の文書、すべての文書（エントリー・ターム・メディア・著者プロフィール・メニュー・フォーム・リダイレクト）、公開しているエントリーが公開しているリビジョンと、予約しているエントリーが予約したリビジョン、すべてのメディアの原本。同じリビジョンを2つのエントリーが公開（または予約）していれば、IDの順で最初のエントリーのものとして、1回だけ入れる。どのエントリーも公開も予約もしていないリビジョンは、取り込まない（サイトのディレクトリは、どのリビジョンが、どのエントリーのものかを持たず、ビルドも読まない。4.3の「求められたものだけ」）ので、下書きのエントリーは、リビジョンの無いまま入る（6.12の161）。テーマとスキーマのファイルは、検証にだけ読み、保存しない（3.4）。
  - 段階：ビルドの段階（4.3）のとおり、段階ごとに問題をすべて集め、あれば、その段階の終わりで止まる（何も保存しない）。段階は、読む、文書の読み込み（上記の「ビルドでの検証」の「読み込み」。ファイル名のIDと、文書の中の `id` の一致も）、サイト設定とテーマ、検証、原本、またがる検証（下記の1回の `Update` の中）の順。問題は、ビルドと同じファイル・行・列・JSON Pointer・文で、口が渡したファイルに付く。成功したときは、リダイレクトの警告を返す。
  - 検証：すべてのエントリーの状態と、公開しているエントリーが公開しているリビジョンと、予約しているエントリーが予約したリビジョンを、取り込みとして検証する（上記の「取り込みと前のリビジョン」。テーマは渡さない。`legacy` と、`alt` の無い画像を受け付ける）。予約したリビジョンが無ければ、`entries/ent_….json:8:3: /scheduledRevision: revision "rev_…" does not exist`。ほかの文書は、保存の操作と同じに、正規化してから検証する。
  - 原本：すべてのメディアの原本を、保存先に原本として保存し（`Update` の前に。3.4の「原本は先に書く」）、メディアの文書と照らす。`/hash: no original with this hash`（使われないメディアも断る。6.12の156）、`/size: the original has <n> bytes, not <m>`、`/hash: the original has the hash sha256:…`。画像は、`internal/mediafile` が読む形式と、表示するときの大きさ（`/mimeType: the original is image/png, not image/jpeg`、`/width: the original is 64x48 pixels as displayed, not 65x48`。読めなければ、文書の先頭に `cannot read the original: <理由>`）。PDFは、`%PDF-` と版（`/mimeType: the original is not application/pdf: <理由>`）。ビルドが、公開するファイルを作るときに見つける問題（辺が65535画素を超えるなど）は、ここでは断らない（6.12の105）。失敗した取り込みは、保存した原本を残す（使われない。6.12の125）。
  - 1回の `Update`：設定の文書・すべての文書・リビジョンを、同じ `Update` で保存し、保存先の索引から作ったサイトの模型を、またがる検証にかける（上記の「保存の操作で」。前のサイトが無いので、見つかった問題は、すべてエラー）。予約しているエントリーは、ビルドと同じく、またがる検証にかからない（予約の日時の公開が、問題を見つける。6.12の187）。失敗すれば、何も残らない。1回の `Update` の上限（3.4の「上限」）が、取り込めるサイトの大きさを決める（6.12の136）。
  - 保存するバイト列：文書とリビジョンは、ファイルのバイト列のまま。ただし、正規化で変わるものは、正規化した値の書き出したもの（上記の「保存の操作（案）」の「保存するバイト列」。設定の文書は、正規化しない）。
  - ビルドとの違い（6.12の162）：公開していないエントリーの状態も検証する（ビルドは、公開しているものだけ。言語や翻訳グループの無い下書きは、取り込みが断る）。正規化してから検証して、正規化した値を保存する（ビルドは、正規化していない値を、エラーにする）。すべてのメディアの原本を確かめる（ビルドは、公開するもの）。原本の問題を、またがる検証より先に示す（ビルドは、またがる検証が先）。画像の `hash` が合わないものと、読めないものの文が違う（ビルドは、原本のハッシュと、画像を調べた理由を、前に付ける。6.6.2）。書いた後に分かる出力パスの重複と、描画の警告・メニューとテーマの警告は、取り込みでは見つけない。
- URL：許可したスキームだけを通す。`//` で始まるURLは不可。制御文字（途中にあるものも）と前後の空白は取り除く。6.5.2の `href` の追加の規則（案）のとおり、`\` と認証情報を含むURLは拒否し、URLにはNFCをかけない。リダイレクトの `from` は、サイト内のパスだけで、6.6.6の正規の形にそろえる（案）。
- メールアドレス（案）：フォームの通知先（`notify`。6.6.5）と、送られた `email` の項目の値（8.2）に使う。ASCIIだけを受け付け、ローカル部（`@` の前）は、英数字と、RFC 5322の `atext` の記号（`` !#$%&'*+-/=?^_`{|}~ ``）と `.` で書く。`.` は先頭と末尾に置けず、2つ続けられない。ドメイン（`@` の後ろ）は、英数字と `-` からなるラベルを `.` で区切って2つ以上並べ、ラベルの先頭と末尾に `-` は置けない。最後のラベル（トップレベルドメイン）は、数字だけにはできない（RFC 3696。`192.0.2.1` のようなIPアドレスを拒むため）。長さは、ローカル部が64バイト、ラベルが63文字、全体が254バイトまで（RFC 5321とDNSの制限）。引用符で囲んだローカル部（`"a b"@example.com`）と、ドメインの代わりのIPアドレス（`[192.0.2.1]` など）は受け付けない。正規化では、URLと同じく制御文字と前後の空白を取り除き、ドメインの英字を小文字にする（ローカル部の大文字と小文字は変えず、`Info@example.com` と `info@example.com` は別のアドレスとして扱う）。検証では、正規化していないもの（ドメインの大文字など）をエラーにする。国際化ドメイン名は、`xn--` の形で書く（Unicodeのドメインを `xn--` の形に変えるIDNAの処理は、いまは持たない）。ローカル部にUnicodeを使う国際化メールアドレスは、使うSMTPサーバーと相手のサーバーがSMTPUTF8（RFC 6531）に対応していないと送れないので、いまは受け付けない（6.12の54）。
- テキスト：制御文字を取り除いてから、Unicodeの正規化（NFC）を行う。ただし、段落などのテキストの改行（`\n`・`\r`・U+2028などの改行に当たる文字）とタブは、取り除かずにエラーにする（改行は `hardBreak` で表す）。`code` は例外で、改行とタブを残し、`\r\n` と `\r` を `\n` にそろえる（改行とタブの扱いは案）。NFCは、外部のライブラリに頼らず自前で実装し（`internal/nfc`）、Unicodeの版はGoの `unicode` パッケージに合わせる（いまは17.0.0。決定済み。6.1）。Unicodeの公式の適合テスト `NormalizationTest.txt` をgzipで圧縮して `testdata` に置き、NFCに関わる条件をすべて確かめる。検証では、NFCでないテキストをエラーにする。NFCは `text` ごとにかけるので、隣り合う `text` をつなげた文字列はNFCになるとは限らない（扱いは6.12の14）。結合文字が続く数に上限は設けず、ストリームセーフ形式（30個ごとにU+034Fを挟む）も使わない（案。上限は6.12の9）。ここでいう制御文字は、Unicodeの一般カテゴリーCc（C0制御文字・DEL・C1制御文字）で、双方向の上書き（U+202E）やゼロ幅接合子（U+200D）などの書式文字は含まない（扱いは6.12の15）。`alt`・`label`・`reason` などの1行テキストも、段落と同じく改行とタブをエラーにする（案）。`html` と `legacy` の `html` は、`code` と同じく改行とタブを残して改行をそろえ、制御文字を取り除くが、NFCはかけない（中の `src`・`href` のURLが変わり、リンクが切れることがあるため。案）。
- 見た目：色・長さ・数値の書式を厳密に検証する。`blockGap` は、子ブロックを持つ種類（`list`・`quote`・`buttons`・`columns`・`column`・`group`）だけが持てる。テーマの許可との照合は6.5.3のとおり（保存では、検証にテーマの設定を渡すと、テーマが許さない項目・テーマに無いプリセット・許されない直接指定をエラーにし、取り込みと、前のリビジョンから変えていない値は受け付ける。ビルドでは、警告して無視する）。
- 名前：`className`・`anchor` は、ASCIIの英数字・ハイフン・アンダースコアだけを許可する。プリセット名・`variant` にも同じ規則を使う（案）。画像の `size`、`code` の `language`、固定ページの `template`、タイプ・タクソノミー・フィールドの名前、メニューの `location` も同じ。テーマの設定ファイルの名前（プリセット・バリエーション・表示場所・ページのテンプレート・画像のサイズ）、翻訳ファイルのキーと置き換えの名前、部品の名前と `define`・`block` の名前（`/` で区切った部分ごと）も同じ（5.4。`assets/` のファイルの名前は5.4.7）。カスタムタイプとカスタムタクソノミーの名前は、既定のURLの規則にも使う（`works` は `/works/{slug}/`。6.6.8）。フォームの入力の項目の `name` も同じ規則で、ASCIIの英字で始める（案。`_` で始まる名前は、迷惑送信の対策と、ページの言語を送る `_language` などに本体が使う。6.6.5・8.2）。ブロックの `id`（6.5.1）とエンティティのID（上記）は、それぞれの書式にする。メディアのファイル名は、6.6.2の規則にする（案）。`className` には、さらに、本体が値から作るクラスの形（`b-` と小文字の英数字8文字、`hl-` と小文字の16進数8桁。6.5.3の出力）を書けない（`reserved className "b-0paragr1": the core gives classes of the forms b-xxxxxxxx and hl-xxxxxxxx`。案）。ほかの本体のクラス（`has-text-align-center`・`alignwide` など。6.5.4）は書けて、書けば、属性で付けたときと同じCSSが効く。
- 多言語：言語コードはサイト設定にあるものだけ（書式は6.4.5）。言語ごとの値（6.3）のキーも同じ（案）。翻訳グループの中に同じ言語は1件まで。エントリーとタームのスラッグの一意性は、言語ごとに確認する。
