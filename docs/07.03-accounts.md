### 7.3 ログインアカウントと権限（案）

管理画面にログインする人のアカウントと、ロールごとの権限を、#45 で作った（`internal/account`）。アカウントは、保存先（3.4）の表 `accounts` に、1アカウントにつき1行で持つ。公開される著者プロフィール（6.6.3）とは別のもので（決定済み。6.1）、必要なら、アカウントの側から紐付ける。この節は、アカウントの項目、ロールごとの権限、作り方、パスワードの規則とハッシュ、招待と再設定のトークン、無効と削除、保存の形を決め、多要素認証やパスキーを足すときの形も示す。ログインとセッション、多要素認証・パスキーは #46、ログイン履歴とアクティビティログは #47、管理のAPIと画面は #48、`whiteroom init` などのコマンドは #49 で作る。この節の規則は、「決定済み」と書いたもの（6.1）のほかは、どれも仮に決めたもの（案）。

**項目**

アカウントの項目（`account.Account` と、保存する行。行の形は下記の「保存」）：

| 項目 | 値 | 規則 |
| --- | --- | --- |
| `id` | アカウントのID（`usr_` とULID。6.7） | アカウントの操作が作る。作り方は、保存の操作が作るIDと同じ（6.7）で、呼ぶ側は書けない |
| `login` | ログイン名 | 英小文字・数字・`.`・`-`・`_` の64文字まで。先頭は英小文字か数字。正規化で、制御文字と前後の空白を取り除き、ASCIIの大文字を小文字にそろえる。アカウントの中で一意。ログインに使う（#46） |
| `name` | 表示する名前 | 1行テキスト（6.7）で、256文字（コードポイント）まで。正規化は、制御文字を取り除き、NFCにする（前後の空白は取り除かない。著者プロフィールの `name` と同じ）。いまのUnicodeの版（17.0.0）で割り当ての無い文字を含むものは、書くときに断る（理由は、下記の「パスワード」の「割り当ての無い文字を断る理由」）。ほかのアカウントと同じでもよい |
| `email` | メールアドレス | 必須。6.7の規則（ASCIIだけ。ドメインの英字は小文字にそろえる）。アカウントの中で一意で、ASCIIの大文字と小文字を区別せずに比べる（6.7は、ローカル部の大文字と小文字を別のアドレスとして扱うが、アカウントでは同じとみなす）。ログインには使わない。通知や、後で足す招待と再設定のメール（8.2。6.12の202）に使う |
| `role` | ロール | `admin`・`editor`・`author`・`viewer`（下記の「ロールと権限」）。`Admin` のように、大文字を含むものは、知らないロールとして断る |
| `author` | 紐付ける著者プロフィールのID（`aut_`） | 任意。下記の「著者プロフィールとの紐付け」 |
| 状態 | `active`（有効）・`pending`（保留）・`disabled`（無効） | 行から決める（下記） |
| `createdAt` | 作った日時 | UTCのRFC 3339 |
| `createdBy` | 招待した人のアカウントのID | 最初の管理者と、システムの操作（下記の「作る」）が作ったものは、空 |
| `credentialsChangedAt` | 認証の手段を、設定・変更・削除した日時 | いまは、パスワードを決めた・変えた日時と、再設定で消した日時。認証の手段を一度も持ったことが無ければ、空。下記の「セッション」 |
| `password` | パスワードのハッシュ | 行だけが持つ（`Account` には出ない）。下記の「パスワード」。パスワードそのものは、どこにも持たない |
| `token` | トークンの用途（`invitation`・`reset`）・SHA-256・期限 | 行だけがハッシュを持つ（`Account` は、用途と期限だけ）。下記の「招待と再設定」 |

状態（案）：

- 有効（`active`）：無効でなく、認証の手段を1つ以上持つ。認証の手段は、いまはパスワードだけ。ログインできるのは、有効なアカウントだけ（#46）。
- 保留（`pending`）：無効でなく、認証の手段をまだ持たない。招待したばかりのアカウントと、再設定の後のアカウント。トークンで認証の手段を決めると、有効になる。
- 無効（`disabled`）：admin が無効にしたアカウント。認証の手段を持っていても、ログインできない。トークンは持てず、再設定もできない。有効にし直す（`Enable`）と、認証の手段があれば有効に、無ければ保留に戻る。

行に持つのは、無効かどうか（`disabled`）だけで、状態は、行から決める。認証の手段を持つかの判定は、コードの1か所にあるので、認証の手段を足しても、状態の規則は変わらない（下記の「強い認証を足すとき（#46 以降）」）。

**ロールと権限**

ロールは、次の4つ（`account.Roles()`）。

- `admin`：すべて。サイト設定・アカウントの管理（招待・再設定・変更・無効・有効・削除）・ビルドのやり直しと戻す操作・ログを見ることは、admin だけ。
- `editor`：どの人のエントリーも、作る・編集する・公開する（予約・公開をやめる・アーカイブも）・消す。メディア・著者プロフィール・ターム・メニュー・フォーム・リダイレクトも、作る・変える・消す。サイト設定・アカウント・ビルド・ログは不可。
- `author`：エントリーを作り（翻訳も）、自分のエントリーを編集・公開・消す。メディアを追加し、自分のメディアを編集・差し替え・消す。自分に紐付けた著者プロフィールを編集する。ターム・メニュー・フォーム・リダイレクトの作成と変更と、ほかの人のエントリーとメディアの変更は不可（エントリーにタームを付けることは、エントリーの編集なので、できる）。書く人が自分で公開できるので、承認の段階は要らない（4.4）。
- `viewer`：見るだけ（下書きも）。

どのロールも、管理画面のすべての文書を見られ、自分の表示する名前・メールアドレス・パスワードを変えられる。ログイン名・ロール・著者プロフィールの紐付けを変えられるのは、admin だけ。

| --- | --- | --- | --- | --- | --- |
| `view` | 管理画面を開き、管理画面のすべての文書を読む | ○ | ○ | ○ | ○ |
| `entry.create` | エントリーの作成と翻訳の作成（`CreateEntry`・`CreateTranslation`。6.7） | ○ | ○ | ○ | × |
| `entry.edit` | 下書きのリビジョンの保存（`SaveRevision`） | ○ | ○ | 自分の | × |

| `entry.delete` | エントリーの削除 | ○ | ○ | 自分の | × |

自分のものとは、次のとおり（`account.Target`）。

- エントリー：`createdBy` がそのアカウントのID（6.4.1）。取り込んだエントリーの `createdBy` は、取り込んだアカウントなので、取り込んだ人のものになる。
- メディア：`uploadedBy` がそのアカウントのID（6.6.2）。
- 著者プロフィール：そのアカウントの `author` と同じID。紐付けの無いアカウントのものは、無い。
- アカウント：そのアカウント自身。admin も、ほかのアカウントは `accounts.manage` で変え、`account.self` ではしない。
- 空の `createdBy`・`uploadedBy`・紐付け・IDは、だれのものでもない。

確かめの規則（案）：

- 何も許さないもの：有効でないアカウント（保留と無効。ほかの値も）は、どの操作もできない。知らないロール（空も）と、知らない操作は、だれにも許さない。
- `account.Check(p, action, target)` は、許さないときに、`account.ErrForbidden`（文は `not allowed`）を包んだエラーを返し、`account.Allowed` は、許すかどうかだけを返す。`p` は `account.Principal` で、いまはアカウントだけを持つ。#46 が、セッションをどう認証したか（使った要素と、最後に認証し直した時刻）を足し、一部の操作に、強い認証を求められるようにする（下記の「強い認証を足すとき（#46 以降）」）。呼ぶ側は、`Principal` をそのまま渡すので、足しても変わらない。
- `Check` は、保存先も時計も読まない、副作用の無い関数で、同時に呼んでよい。アカウントのうち、見るのはID・ロール・状態・紐付けだけで、ログイン名・名前・メールアドレス・日時・トークンは見ない。
- 呼ぶ側が渡す対象（`Target`）：エントリーの `createdBy`（`entry.edit`・`entry.publish`・`entry.delete`）、メディアの `uploadedBy`（`media.edit`・`media.delete`）、著者プロフィールのID（`author.edit`）、アカウントのID（`account.self`）。`entry.create`・`media.add` と、自分のものの規則の無い操作は、対象を見ない。
- 保存の操作と公開の操作（6.7）の前に `Check` を呼ぶのは、管理のAPI（#48）。#45 は、アカウントの操作にだけ組み込んだ（下記の「作る」）。
- 見た目の直接指定（6.5.3）には、操作が無い。ロールでは絞らず、どのロールも、テーマが決める範囲（`custom`・`styles`。5.4.2）で使える（6.12の62）。
- 予約の日時の公開（`PublishScheduled`）にも、操作が無い。公開の権限は、予約のとき（`Schedule`）に、`entry.publish` として確かめる（下記の「予約」）。
- 細かいロール（サイトごとに作るロール、タイプや言語ごとの権限）は、いまは無い（6.12の205）。権限の表は、コードの1つの表（`account` の `rules`）で、足すときは、列と行を足す。

**作る**

- 自己登録は行わない（7.2）。アカウントを作る道は、次の2つだけ。
  - 招待（`Invite`）：admin（かシステム）が、ログイン名・名前・メールアドレス・ロール（と、任意で著者プロフィール）を決めて作る。アカウントは保留で、トークンを1つ返す（下記の「招待と再設定」）。本人は、そのトークンでパスワードを決め（`SetPassword`）、有効になる。メールでは送らず、トークンを本人に渡すのは admin の手作業（URLの形は #48。メールで送ることは6.12の202）。
  - 最初の管理者（`CreateFirst`）：アカウントが1つも無い保存先（保留と無効のアカウントも数える）にだけ、パスワードつきの有効な admin を作る。ロールは admin だけ（空なら admin）で、`createdBy` は空。コマンド `whiteroom init`（9.2・9.4。#49）が、端末でパスワードを入れさせて呼ぶ。アカウントがあれば、`the store has accounts: CreateFirst needs a store without any` で断る。
- 操作者：アカウントの操作は、操作者（`Actor`）を取る。`account.By(アカウントのID)` か、システム（`account.System`）。システムは、サーバー上のコマンド（#49）が使う。どのアカウントの操作もできるが、最後の有効な admin を、無効にも、削除にも、ほかのロールにもできない（下記の「無効と削除」）。最後の有効な admin の再設定だけは、システムならできる（下記の「招待と再設定」）。システムが作ったアカウントの `createdBy` は、空。
- 操作者がアカウントのときは、その `Update` の中で読んだ行のアカウントについて、`Check` が許す必要がある。保留・無効のアカウントと、行の無いIDと、ゼロ値の操作者（`By("")`）は、何もできない。
- 確かめの順：すべての行を読み（読めない行があれば、ここで断る。例外は、下記の「保存」の「読めない行」）、操作者、入力、行どうしの問題（ログイン名とメールアドレスの重なり、紐付けるプロフィール）、最後の有効な admin の規則、の順に確かめ、最初に当たったものを返す。権限の無い操作者には、入力や行の問題を知らせない。操作者を取らない `CreateFirst` は、入力とパスワードの問題を、まとめて返す。

操作と、できる人：

| 操作 | できる人 | 内容 |
| --- | --- | --- |
| `CreateFirst` | 操作者を取らない | アカウントの無い保存先に、最初の admin を作る |
| `Invite` | `accounts.manage`、システム | 保留のアカウントと、トークンを作る |
| `SetPassword` | トークンを持つ人 | トークンで、パスワードを決める |
| `Reset` | `accounts.manage`、システム（最後の有効な admin は、システムだけ） | 認証の手段をすべて消し、トークンを作る |
| `ChangePassword` | 現在のパスワードを知る人 | パスワードを変える。操作者を取らないので、呼ぶ側（#48）は、ログインしているアカウントのIDだけを渡す |
| `VerifyPasswordFactor` | だれでも | パスワードを確かめる（ログインではない） |
| `Update` | 自分の名前とメールアドレス：`account.self`。ログイン名・ロール・紐付けと、ほかのアカウント：`accounts.manage`、システム | 項目を変える |
| `Disable`・`Enable`・`Delete` | `accounts.manage`、システム | 無効にする・有効にする・消す |
| `Get`・`List`・`Find`・`Read` | 確かめない（呼ぶ側が決める。#48） | アカウントを読む。`Read` は、呼ぶ側のトランザクション（`Update` など）の中で読む関数（`account.Read`） |

**パスワード**

規則（案）：

- 大きさ：打たれたテキストが8KiB（8192バイト）を超えるものは、ほかの確かめより先に断る（`too long: <n> bytes (max 8192)`。`<n>` は打たれたバイト数）。NFCにもハッシュにもする前に断るので、長いテキストを送られても、読む以上の時間とメモリを使わない。保存できるパスワード（NFCにして256文字まで）と正準等価なテキストは、いまのUnicodeの表では、1文字が4コードポイントまでにしか分解されないので、最長でも4096バイトで、8KiBはその2倍。保存できるパスワードを打つときに、これで断られることは無い。
- 文字：不正なUTF-8（`invalid UTF-8`）と、制御文字（タブ・改行・NUL・DELなど。`contains control characters`）は断る。前後の空白も、中の空白も、取り除かず、切り詰めず、数える。文字の種類の組み合わせの規則と、定期的な変更の要求は、設けない。
- 割り当ての無い文字：いまのUnicodeの版（Goの `unicode` パッケージの版で、`internal/nfc` の表が従う。いまは17.0.0）で割り当ての無い文字（一般カテゴリー `Cn`。U+FFFE のようなノンキャラクターも含み、私用文字は含まない）を含むものは断る（`contains a code point that is not assigned in Unicode 17.0.0`。メッセージには、コードポイントを入れない）。名前（上記の「項目」）にも、同じ規則を当てる（`contains U+1ADE, which is not assigned in Unicode 17.0.0`）。当てるのは、名前とパスワードを書くとき（`CreateFirst`・`Invite`・`Update`・`SetPassword`・`ChangePassword`）だけで、照合（`matchHash`）と、行を読むときには、当てない（下記の「保存」）。文書のテキストに当てるかは、6.12の16。
- 割り当ての無い文字を断る理由：NFCの文字列は、割り当ての無い文字を含まなければ、後のUnicodeの版でもNFCのままで、NFCの形も変わらない（UAX #15 の「安定した文字列」）。そのため、Goと `internal/nfc` の表を新しい版にしても、書いた名前はNFCのままで、パスワードのハッシュを求めたNFCの形は同じになり、打たれたパスワードは同じハッシュに合う。割り当ての無い文字を許すと、後の版でその文字が結合文字になったときに、NFCの形が変わり、そのパスワードは、打っても合わなくなる（再設定が要る）。
- 長さ：NFCにしてから、コードポイントで数えて、15文字以上256文字以下（`too short: <n> characters (min 15)`・`too long: <n> characters (max 256)`）。
- 同じもの：ログイン名・メールアドレス・表示する名前のどれかと、大文字と小文字を区別せずに同じもの（`the same as the login name, the email address or the name`）と、1つの文字だけの繰り返し（`one character repeated`）は断る。
- 確かめる順は、大きさ、不正なUTF-8、制御文字、割り当ての無い文字、長さ、同じもの、1つの文字の繰り返し、の順で、最初の問題を、`/password` の問題（`content.Errors`）にする。メッセージには、パスワードを入れない。確かめるのは、パスワードを決める・変えるとき（`CreateFirst`・`SetPassword`・`ChangePassword`）だけで、ログインのときの照合では、確かめない（8KiBを超える打たれたパスワードだけは、照合が、下記の「費用」のとおり、先に断る）。
- 漏えいしたパスワードの一覧との照合は、まだ無い（6.12の198）。

NIST SP 800-63B-4（2025年7月。2026-11-08に確かめた）の、次の点に合わせた：単一の要素として使うパスワードに15文字以上を求めること（SHALL。多要素認証の一部なら8文字。6.12の201）、文字をコードポイントで数えること、組み合わせの規則と定期的な変更を求めないこと（SHALL）、64文字以上とUnicodeを受け付けること（SHOULD）、ハッシュの前にNFCにすること（SHOULD）、32ビット以上のソルト（SHALL）、SP 800-132 の方式と、できるだけ高い費用（SHOULD）。まだ合わせていない点は、ブロックリストとの照合（SHALL。6.12の198）、試行の回数の制限（SHALL。#46）、秘密の鍵による追加のハッシュ（SHOULD。6.12の199）。7.3は、この規則がNISTの要件を満たすとも、認証の保証の水準（AAL）に当たるとも言わない。

ハッシュ（案）：保存先には、パスワードのハッシュだけを置く。

- 方式：PBKDF2のHMAC-SHA-256（標準ライブラリの `crypto/pbkdf2`）。回数は600000、ソルトは16バイト（`crypto/rand`）、値は32バイト。元にするのは、パスワードのNFCの形。
- 形：`$pbkdf2-sha256$i=600000$<ソルト>$<値>`。ソルトと値は、パディングの無い標準のbase64。方式と回数を持つので、回数を上げるときや、方式を替えるときに、読む側が見分けられる（作り直しは6.12の200）。
- 読み方：この形だけを受け付ける。回数は1〜10000000の数字だけ（符号・空白・先頭の0は不可）、ソルトは16バイト以上、値は32バイトちょうど、base64は、書き戻して同じになるもの（改行・パディング・0でない余りのビットは不可）。読めないハッシュは、`unreadable password hash`（ハッシュの中身は示さない）。
- 照合：保存したハッシュのソルトと回数で、打たれたパスワードのNFCの形から値を求め、`crypto/subtle` の `ConstantTimeCompare` で比べる（比べる時間が、一致した長さを示さない）。保存したハッシュの回数が、いまの回数より少なくても、ハッシュに書かれた回数で照合でき、一致したときに限り、作り直すべきだと知らせる（`matchHash`。使うのは #46。6.12の200）。
- 費用：1つのハッシュに、開発のマシンで約80ミリ秒かかる（作るときも、照合するときも）。打たれたパスワードのNFCとハッシュは、長さに比例するので、ログインの要求の本文には、上限が要る（#46・#48。6.12の24）。そのうえで、8KiB（8192バイト）を超える打たれたパスワードは、照合（`matchHash`）が、保存したハッシュを解析せず、NFCにもハッシュにもせずに、一致しないものとして断る。保存できるパスワードと正準等価なテキストは、上記の「大きさ」のとおり、4096バイトまでなので、一致するものが、これで断られることは無い。どのログイン名でも同じに断る。
- 照合の性質：HMACは、ブロックの長さ（64バイト）より短い鍵を、0のバイトで埋めるので、パスワードの後ろにNULを足したものも、同じ鍵になり、一致する。64バイトより長いパスワードは、先にSHA-256にされる。保存するパスワードは、NULを含む制御文字を断る（`contains control characters`）ので、保存したパスワードがこれに当たることは無いが、打たれたパスワードの照合は、制御文字を断らない（テストが、この動きを記録している）。

OWASP の Password Storage Cheat Sheet（2026-11-08に確かめた）は、Argon2id（19MiB・2回・1並列）を第一に勧め、使えなければ scrypt、bcrypt は古いシステムだけ（入力は72バイトまで）、FIPS-140 が要るときは PBKDF2（HMAC-SHA-256で600000回）とする。パスワードのハッシュに使える方式で、Goの標準ライブラリにあるのは PBKDF2 だけで、Argon2id・scrypt・bcrypt は `golang.org/x/crypto` にある。外部のモジュールは、足す前にメンテナーに確かめる（1.2）ので、いまは足さず、標準ライブラリの PBKDF2 を、OWASP の回数で使う。メモリを多く使う Argon2id に比べると、GPUや専用の回路での総当たりに強くないので、15文字以上の長さを求めて補う。秘密の鍵による追加のハッシュ（ペッパー）は、鍵の置き場所とバックアップを決める必要があるので、使わない（6.12の199）。

変更と確かめ：

- 変更（`ChangePassword`）：現在のパスワードを知る人が、変える。アカウントが有効でないか、パスワードを持たないか、現在のパスワードが違うときは、`wrong login name or password`。新しいパスワードは、上記の規則に照らす。ハッシュは `Update` の外で作る（時間がかかるため）ので、`Update` の中で、保存したハッシュがそのままか（変わっていれば、`the password of usr_… changed since it was read`。`ErrConflict` を包む）、アカウントがまだ有効か、規則をもう一度確かめる。書くのは、ハッシュと `credentialsChangedAt` で、トークンは消す。
- 確かめ（`VerifyPasswordFactor`）：ログイン名（正規化する）のアカウントのパスワードを確かめ、一致すればアカウントを返す。ログインではなく、ログインの1つの要素の確かめで、#46 が、アカウントのほかの要素（いまは無い）、試行の回数の制限、セッションと組み合わせる。失敗は、どれも `wrong login name or password`（ログイン名が無い・有効でない・パスワードが無い・行が読めない・パスワードが違う・パスワードが8KiBを超える・照合の間に変わった、を区別しない）。保存先の失敗（取り消されたコンテキストなど）だけは、そのまま返す（#46 は、サーバーの失敗として答える）。何も書かず、試行は制限せず、一致したときのハッシュの作り直しもしない（#46）。
- 照合の後の読み直し：パスワードが一致した後に、そのアカウントの行を読み直し（1つの `View`）、行がまだあり、読めて、パスワードのハッシュが一致したものと同じで、有効なときだけ、成功にして、そのときの行のアカウント（そのときの名前・メールアドレス・ロール・ログイン名・`credentialsChangedAt`）を返す。照合に約80ミリ秒かかり、その間に、`ChangePassword`・`Reset`・`Disable`・`Delete` が書き終わっていることがあるため（読み直さないと、変えた（再設定した・無効にした・消した）直後に、前の状態でログインが成功することがある）。パスワードを変える操作は、同じパスワードに変えるときも、ソルトが新しくなってハッシュが変わるので、その間なら、ログインは失敗する。名前・メールアドレス・ロール・ログイン名の変更と、ほかのアカウントの操作と、`Disable` の後の `Enable`（ハッシュは変わらない）では、失敗しない。読み直しの後、#46 がセッションを作るまでの間の変更は、セッションの規則で終わらせる（下記の「セッション」）。
- だれにも一致しないハッシュ：有効でパスワードを持つアカウントが無いログイン名（行が無い・保留・無効・読めない行）でも、だれにも一致しないハッシュを確かめるので、時間で、ログイン名の有無が分からない。このハッシュは、`account.New` が `Manager` を作るときに、そのときの回数で1つ作る（ログインのときには作らず、乱数も読まない）ので、最初の呼び出しも、ほかと同じ、1つのハッシュの時間で済む。8KiBを超える打たれたパスワードだけは、どのログイン名でも、ハッシュを作らずに断る（上記の「費用」）。

**招待と再設定**

トークンは、アカウントに認証の手段を設定する権利で、どの手段のためかは知らない。いまの認証の手段はパスワードだけなので、`SetPassword` で使う。パスキーなどを足すときも、同じトークンと規則で使う（下記の「強い認証を足すとき（#46 以降）」）。

- 作り方：256ビットの乱数（`crypto/rand`）を、パディングの無いbase64url（43文字）で書く。作った操作（`Invite`・`Reset`）が、呼ぶ側へ一度だけ返し、保存先には、そのテキストのSHA-256（`sha256:` と小文字の16進数64桁）だけを置く。256ビットの乱数なので、パスワードのように総当たりされることはなく、鍵の無いSHA-256で足りる。
- 期限：招待は7日、再設定は24時間（作った時刻から数え、期限の時刻を過ぎれば使えない）。認証の手段を一度も持ったことの無いアカウント（招待したままのもの）の `Reset` は、招待として7日。
- 一度だけ：使うと消える。新しいトークン（もう一度の `Reset`）を作ると、前のものは使えなくなる（1アカウントに1つ）。無効にする（`Disable`）ときと、パスワードを変える（`ChangePassword`）ときも消える。
- 使い方（`SetPassword`）：トークンを持つアカウントを探す。すべての行のトークンのハッシュを、一定の時間で比べる。期限を過ぎたもの、無効のアカウントのもの、トークンの形でないもの（43文字でない長さのテキストは、復号の前に断る）は、理由によらず `invalid or expired token`。パスワードを、そのアカウントのログイン名などに照らして確かめる（問題は `/password` の問題で、トークンは残る）。ハッシュは `Update` の外で作り、`Update` の中で、トークンとパスワードの規則をもう一度確かめて、ハッシュと `credentialsChangedAt` を書き、トークンを消す。
- 再設定（`Reset`）：そのアカウントの認証の手段を、すべて、一度に使えなくし（いまはパスワードを消す）、`credentialsChangedAt` をいまにして、新しいトークンを作る。アカウントは保留になる。無効のアカウントは再設定できない（`usr_… is disabled: enable it first`）。パスワードが漏れた疑いのあるときも、同じ操作でよいように、古いパスワードは、その場で使えなくなる。第2要素やパスキーを足したときに、再設定がそれらも消すか（消さないと、乗っ取られたアカウントに、攻撃者の登録したものが残る）は、6.12の206。
- 最後の有効な admin：再設定は、最後の有効な admin には断る（`usr_… is the last active administrator: its credentials cannot be reset`）。その人は、現在のパスワードを使う変更（`ChangePassword`）で、パスワードを変える。admin が全員ログインできなくなったときの復旧は、システムの再設定（`Reset(ctx, System, id)`）で、最後の有効な admin にもできる。そのアカウントは、パスワードを決める（`SetPassword`）まで保留になる。サーバー上のコマンド（#49）が、続けて呼ぶ。

**無効と削除**

- 無効（`Disable`）：ログインできなくする。トークンを消すほかは、何も変えない。`credentialsChangedAt` も変えないので、#46 は、無効にするときに、そのアカウントのセッションを消す（下記の「セッション」）。有効にし直す（`Enable`）と、認証の手段があれば有効に、無ければ保留になる。すでにその状態なら、何も書かない。
- 削除（`Delete`）：行を、認証の手段ごと消す。ログイン名とメールアドレスは、ほかのアカウントが使えるようになる。文書は変えない：エントリーの `createdBy`、メディアの `uploadedBy`、版とリビジョンの保存した人は、消したアカウントのIDのまま残り、著者プロフィールにも触れない（6.6.3）。消したIDの示し方は、6.12の204。消す前の行の値は、ログに残り、圧縮まで読める（3.5の「個人情報の削除」）。読めない行は、システムが、ほかの行を読まずに消せる（下記の「保存」の「読めない行」）。
- 最後の有効な admin の規則：書き込みの前後で、有効な（無効でなく、認証の手段を持つ）admin の数を数え、前にいて後にいなくなるものを断る。最後の有効な admin の無効・削除・ほかのロールへの変更・再設定（システムの再設定を除く）が、これに当たる。メッセージは、`usr_… is the last active administrator: it cannot be disabled`・`… it cannot be deleted`・`… its role cannot be changed`・`… its credentials cannot be reset`（`ErrLastAdmin` を包む）。保留と無効の admin は、ログインできないので、数えない。ロールが4つのどれでもないアカウントも、admin ではないので、数えない。システムも従う（再設定を除く）。読めない行をシステムが消すときは、その行を数えられないので、この規則を当てない。規則は、アカウントを書くすべての道が通る1か所にあるので、後で足す操作（最後の認証の手段を消す操作など）も、同じ規則で断られる。
- 同時の操作：アカウントを書く操作は、どれも、保存先の1回の `Update`（3.4）で、はじめにすべての行を読む。`Update` は1つずつ動く（3.4の「同時に使う」）ので、最後の有効な admin の規則と、ログイン名とメールアドレスの一意は、操作が同時に動いても守られる。

**記録**

行に持つのは、作った日時（`createdAt`）・作った人（`createdBy`）・認証の手段を変えた日時（`credentialsChangedAt`）だけ。だれが、いつ、何を変えたか（ロールの変更・無効・削除など）は、アクティビティログ（7.1）に記録する。それは #47 で作り、#45 の操作は、記録を書かない。

**セッション**

セッションのために行に持つのは、`credentialsChangedAt` だけ（日時1つ。世代の番号などは持たない）。#46 のセッションの規則（案）：

- セッションは、ログインのときに `VerifyPasswordFactor` が返したアカウントの `credentialsChangedAt` の値を持ち、アカウントのいまの値と違えば、終わる（パスワードを変えた・再設定した後に、前のセッションが残らないようにする）。セッションを作った時刻とは比べない。`VerifyPasswordFactor` が行を読み直してから、セッションを作るまでの間に、パスワードが変わっても、セッションが持つ値は古いままなので、終わる（作った時刻と比べると、その変更は、作った時刻より前になり、セッションが残る）。
- セッションは、アカウントを読み直して、状態（有効か）も確かめる（無効にしたアカウントのセッションを使えなくする）。
- 無効にする（`Disable`）ときは、そのアカウントのセッションを消す。`Disable` は `credentialsChangedAt` を変えないので、消さないと、有効にし直した（`Enable`）ときに、持つ値がいまの値のままなので、前のセッションが、また使えるようになる。消せば、有効にし直しても、前のセッションは戻らない。
- パスワードを変えた本人のセッションを、残すか、終わらせるかは、#46 が決める。

**予約**

予約の日時の公開（`PublishScheduled`。4.4・6.7）は、予約した人の保存として記録する（予約を保存した版の保存した人）。公開の権限（`entry.publish`）は、予約するとき（`Schedule`）に確かめ（#48）、日時の公開では確かめない（案）。そのため、予約した人のアカウントを、無効にしても、消しても、ロールを変えても（権限を失っても）、予約は残り、日時に、そのIDのまま公開される。予約を止めたいときは、予約を取り消す（`Unpublish`。そのときの権限で確かめる）。システムの操作として保存するか、操作の記録（#47）の「だれが」をどうするかは、6.12の186。

**著者プロフィールとの紐付け**

- 紐付けは、アカウントの側に持つ（`author`。決定済み。6.1・6.6.3）。投稿の `author` の初期値や、自分のプロフィールを編集できるかの判断に使う（7.2）。
- 紐付けるとき（招待・最初の管理者・`Update` で紐付けを変えるとき）に、そのプロフィールがあることを、その `Update` の中で確かめる（無ければ、`/author: author profile "aut_…" does not exist`）。IDの書式は、`invalid author ID "…": use "aut_" and a ULID (26 characters in upper case)`。
- 後でプロフィールが消されても、消すことを断らず、アカウントはIDを持ったまま、紐付けが無いものとして扱う（案）。そのプロフィールを編集する操作は、起きない。紐付けを変えない変更では、確かめ直さない（確かめ直すと、プロフィールを消した後、そのアカウントの名前も変えられなくなる）。消したプロフィールへの紐付けを、どうするかは、6.12の204。
- 1つのプロフィールを、いくつのアカウントにも紐付けられる（「編集部」など。6.6.3）。紐付けを変えられるのは、admin だけ（`Update` の `Author`。空にすると外れる）。

**強い認証を足すとき（#46 以降）**

#46 で、ログインとセッションを作る。その先に、多要素認証（MFA）、パスキー（WebAuthn）、一部のロールに強い認証を求めること、機微な操作の前の再認証を足せるように、#45 の規則を作った。ここに書くのは、足すときの形（案）で、#46 が何を作るかを決めるものではない。どれを #46 で作るか、WebAuthn に1.2の例外が要るか（6.12の212）は、#46 が決める。

足せるもの（案）：

- 第2要素：TOTP（RFC 6238）と、回復用のコード。
- パスキー（WebAuthn の資格情報）：ユーザー検証（本人であることの確認）を必須にして使う。パスワードを持たず、パスキーだけでログインするアカウントも、同じ形で足せる（6.12の208）。
- 一部のロールに、多要素認証かパスキーを求めること（6.12の207）。
- アカウントの管理などの機微な操作の前に、最近の再認証を求めること（6.12の211）。

#45 の規則との合わせ方（案）：

- 状態：認証の手段を持つかの判定（コードの1か所）に、新しい手段を数える。有効＝無効でなく、認証の手段を1つ以上持つ、という規則と、保留・無効は、変わらない。
- 最後の有効な admin：認証の手段を消す操作（パスキーの削除など）も、アカウントを書く道を通るので、最後の有効な admin のものは断られる。MFA かパスキーを求めるロールがあるとき、規則が数えるのは、求める強さでログインできる admin か（6.12の207）。
- トークン：招待と再設定のトークンは、どの手段のためかを知らないので、パスキーの登録にも、同じトークン・同じ使い方（一度だけ・期限・置き換え・ハッシュだけを保存）を使える。ただし、認証の手段を持つアカウントに2つ目を足すときは、トークンではなく、ログインしている人の認証で足す形が考えられる。NIST SP 800-63B-4 は、新しい認証器を結びつけるときに、アカウントで使える最も高い AAL か、新しい認証器の AAL の、低いほうでの認証を求める（SHALL）。どうするかは、#46 が決める（6.12の211）。
- `credentialsChangedAt`：認証の手段を足す・変える・消すたびに更新し、セッションが持つ値と違えば、そのセッションを終わらせる基準にする（上記の「セッション」）。
- `VerifyPasswordFactor`：1つの要素の確かめで、#46 のログインが、第2要素やパスキーの確かめと組み合わせる。パスワードの無いアカウントでの扱いは、6.12の208。
- 権限：`account.Principal` に、セッションの認証の強さ（使った要素・最後に認証し直した時刻）を足し、権限の表（コードの `rules`）に、その操作が求める強さの列を足す。`Check` が、許す条件に加えて読む。呼ぶ側は `Principal` をそのまま渡すので、変わらない。
- 再認証：操作者（`Actor`）にも、同じ強さの情報を持たせ、アカウントの管理などの操作が、最近の再認証を求められるようにする。いまの `Actor` は、アカウントのIDかシステムだけで、組み立てられるのは `account` パッケージだけ。

どこに持つか（案）：

- アカウントの行の、省ける項目として足す（新しい `logSchemaVersion`。3.4）。#45 が書いた行は、書き直さずに、そのまま読める。状態と最後の有効な admin の規則が、1つの行だけから決まる関数のままでいられる（別の表に持つと、2つの表を同時に読む必要が出る）。行の上限（64KiB）が、1つのアカウントのパスキーの数を決める。
- パスキーが持つもの：資格情報のID・公開鍵（COSE形式）・署名の回数・トランスポート・BE と BS のフラグ・uvInitialized・AAGUID・名前（本人が付ける）・作った日時と最後に使った日時。
- TOTP の秘密：ハッシュにできない（確かめるたびに、秘密から値を求めるため）ので、暗号化して持ち、鍵は保存先の外に置く。鍵の置き場所とバックアップは、鍵つきのハッシュ（6.12の199）と個人情報の暗号化の鍵（6.12の138）と同じ問題なので、あわせて決める（6.12の210）。
- 回復用のコード：トークンと同じに、ハッシュだけを保存先に置き、使ったら無効にする。長さは、NIST SP 800-63B-4 が求める64ビット以上（承認された乱数生成器から）を下回らない。実際の長さは #46 が決める。
- ユーザーハンドル：最初のパスキーを登録するときに作る64バイトの乱数で、アカウントの行に持つ。ログイン名とメールアドレスは変えられ、個人を特定する値なので使わない。アカウントのIDは、作った時刻を含み（6.7）、文書にも書かれる値なので、認証器に持たせない。
- 認証器の証明（attestation）の扱いは、6.12の209。

**保存**

アカウントは、保存先の表 `accounts`（9。3.4の「表」）に、アカウントのIDをキーに、1行ずつ持つ。値は、`internal/account` が書くJSONで、保存先は読まない。この表は、表の版4で足した（#45。3.4の「エンジンと設定」）。表の版1・2・3の保存先は、書くプロセスとして開くと、版4になり、アカウントの行は無い状態から始まる。

行のキー（この順で書く。省ける項目は省く）：`id`・`login`・`name`・`email`・`role`・`author`（紐付けがあるとき）・`disabled`（無効のときだけ。`true`）・`createdAt`・`createdBy`（あるとき）・`password`（あるとき）・`credentialsChangedAt`（あるとき）・`token`（あるとき。`purpose`・`hash`・`expiresAt`）。

例（実際は1行で、空白を入れない。`<…>` は、実際の値に置き換える。ハッシュとトークンの実際の値は、ここに書かない）。招待したばかりの行：

```json
{"id":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","login":"yamada","name":"山田 太郎","email":"yamada@example.com","role":"editor","author":"aut_01JBA4C7N9Q3T6W9Z3C6F9H2K5","createdAt":"2026-11-08T01:02:03Z","createdBy":"usr_01JB8T7H4MA2C5E8G1J4K7N3P5","token":{"purpose":"invitation","hash":"sha256:<64桁の小文字の16進数>","expiresAt":"2026-11-15T01:02:03Z"}}
```

本人がパスワードを決めた後の行（トークンは消え、ハッシュと `credentialsChangedAt` が入る）：

```json
{"id":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","login":"yamada","name":"山田 太郎","email":"yamada@example.com","role":"editor","author":"aut_01JBA4C7N9Q3T6W9Z3C6F9H2K5","createdAt":"2026-11-08T01:02:03Z","createdBy":"usr_01JB8T7H4MA2C5E8G1J4K7N3P5","password":"$pbkdf2-sha256$i=600000$<ソルト>$<値>","credentialsChangedAt":"2026-11-08T11:02:03.456789Z"}
```

規則（案）：

- 日時：UTCのRFC 3339で、小数の秒を持つことがある（文書の日時は、小数の秒を使えない。6.7）。秒の下は、0でない最後の桁まで書き、ちょうどの秒には書かない。
- 書く形：書くのは1通りの形だけ（`encodeRow`。キーの順と日時は上記）で、書く前に、その行が読めることを確かめる（読めない行を書くと、あとの操作が止まるため）。JSONの書き出しには `encoding/json/v2` を使う。Goの版が変わって、書き方（エスケープなど）が変わっても、すでに書いた行は、下記のとおり読める。
- 読み方：読むとき（`decodeRow`）は、行の保存の形だけを確かめる。確かめるのは、JSONのオブジェクトであること（知らないキー・同じキー・型の違う値・不正なUTF-8・後ろに続くデータは断る）、`id` が表のキーと同じアカウントのIDであること、`login`・`name`・`email`・`role`・`createdAt` があって、空でないこと、`createdBy` が空かアカウントのID、`author` が空か著者プロフィールのIDであること、`password` が空か、ハッシュの形（上記の「ハッシュ」の「読み方」）であること、`token` が無いか、用途（`invitation`・`reset`）・ハッシュの形（`sha256:` と小文字の16進数64桁）・期限を持つこと、日時がUTCにして0〜9999年に入ること（JSONに書けて、書き直せる範囲）。
- 読めるもの：これ以外は確かめない。キーの順・空白・エスケープ・UTC以外の日時・秒の下の桁・空の値と `null` の違いは、読める。値の規則（上記の「項目」・「パスワード」）は、書くときに当て、読むときには当てないので、書くときの規則が断る値（大文字を含むログイン名・NFCでない名前・割り当ての無い文字を含む名前・メールアドレスでない値・知らないロール・無効のアカウントのトークン）も、読める。書き直したバイト列との一致も、確かめない。規則を読むときに当てないのは、ほかのビルド（Unicodeの版や規則の違うもの）が書いた行や、あとで厳しくなった規則に合わない行を、読めない行にしないため（読めない行があると、下記の「読めない行」のとおり、その行のアカウントはログインできず、書く操作と `List` は、どれも止まる）。読んだ行を書き直すときは、書く形になる（名前を変えない操作は、名前をそのまま書く）。
- 知らないロール：読めるが、`Check` は何も許さず（メッセージは、ロールを引用符で囲む。下記の「エラー」）、最後の有効な admin の数にも入らない。admin が、`Update` で、知っているロールにできる。
- 読めない行：保存の形を満たさない行（保存先のAPIを通さずに書かれたもの、壊れたもの、このビルドが知らないキーを持つもの）は、`accounts "usr_…": invalid value`（データの中身は示さない）になる。扱いは、次のとおり（案）：
  - `VerifyPasswordFactor`・`Find`：その行を飛ばす。読めない行は、どのログイン名のアカウントでもないので、ほかのアカウントのログインと検索は、止まらない。
  - システムの `Delete`：対象の行だけを先に読み、読めなければ、ほかの行を読まずに、その行を消す。最後の有効な admin の規則は当てない（読めない行は数えられないため）。読めない行が何行あっても、1行ずつ消せる。サーバー上の復旧のコマンド（#49）が使う。
  - ほかの書く操作（`CreateFirst`・`Invite`・`SetPassword`・`Reset`・`ChangePassword`・`Update`・`Disable`・`Enable`と、読める行の `Delete`。システムの `Delete` も、読める行には）：断る。ログイン名とメールアドレスの一意と、最後の有効な admin の規則が、すべての行を読む必要があるため。操作者の確かめより先に断り、エラーは、IDの順で最初の読めない行を指す。アカウントの操作者は、読めない行を消せない。
  - `List`：読めない行が1つでもあれば、失敗する。`Get`・`Read`：読めない行を指したときだけ、失敗する。
- 秘密を出さない：公開する型 `Account` は、パスワード・ハッシュ・トークンを持たない（持つ項目を固定するテストがある）。内部の行を表示しても（`%v`・`%+v`・`%#v`）、IDだけが出る。エラーの文にも、パスワード・トークン・ハッシュは入らない。データのディレクトリのどのファイルにも、パスワードとトークンの文字列は残らない（テストで走査する）。
- 大きさ：1行は64KiB（65536バイト）まで（3.4の「表」）。
- 数：アカウントの数の上限は無い。書く操作は、毎回すべての行を読む。想定は、管理画面にログインする人で、数人から数十人。
- 変えるとき：省ける項目を足す変更は、すでに書いた行を書き直さずに、新しい `logSchemaVersion` で足す（上記の「強い認証を足すとき（#46 以降）」）。省けない項目や、意味を変える変更は、行を変換する更新が要る（3.4の「索引」の「表の版の更新」と同じ形）。行を読むときは保存の形だけを確かめるので、入力の規則（ログイン名の文字、名前やパスワードの長さなど）を変えるときは、行の更新が要らない（書くときから当たる）。

**置き場所**

- `internal/account`：アカウントの型と入力の検証、行の形、権限の確かめ（`Check`・`Allowed`）、パスワードとトークン、アカウントの操作（`Manager`。`account.New(s)` で作る）。`internal/store`・`internal/content`・`internal/nfc` を使い、外部のモジュールは使わない。時計・乱数・ハッシュの回数は、テストのために替えられる（本番は `time.Now`・`crypto/rand`・600000回）。
- `account.New(s)` は、`(*Manager, error)` を返す。だれにも一致しないハッシュ（上記の「パスワード」の「変更と確かめ」）を1つ作り、開発のマシンで約80ミリ秒かかるので、#46 は、プロセスごとに `Manager` を1つ作る。失敗するのは、乱数を読めないときだけ（`cannot read a token: …`・`cannot read a salt: …`）。
- いまは、ほかのパッケージは `internal/account` を使わない。#46（ログイン）、#48（管理のAPI。`account.Check` と `account.Read`）、#49（コマンド）が使う。`internal/store` は `internal/account` を使わない。
- アカウントのIDは、保存の操作が作るIDと同じ実装（`internal/content` の `IDSource`）で作る。

**エラー**

メッセージは、コードが書くとおり（英語）。呼ぶ側は、文ではなく、`errors.Is`・`errors.As` で分ける：`account.ErrForbidden`・`content.Errors`・`fs.ErrNotExist`・`account.ErrLastAdmin`・`account.ErrConflict`・`account.ErrInvalidToken`・`account.ErrBadCredentials`。

- 操作者：`<id> (<role>): not allowed to <phrase>`（有効でないアカウントは、`<id> (<status>): …`）、`not allowed: the operation has no actor`、`usr_…: not allowed: no such account`。どれも `account.ErrForbidden` を包む。アカウントのIDとロールか状態のほかに、アカウントと対象のことは入らない。有効なアカウントのロールが、4つのどれでもないとき（ほかのビルドが書いた行など）は、ロールを引用符で囲む：`<id> ("<role>"): …`（改行などは `\n` のように書くので、メッセージに改行は入らない）。
- `<phrase>`（操作ごと。自分のものだけを許すロールが、自分のものでないものに当たるときは、括弧の中の文）：`view the admin screen`・`create entries`・`edit entries`（`edit entries that other accounts made`）・`publish entries`（`publish entries that other accounts made`）・`delete entries`（`delete entries that other accounts made`）・`add media`・`edit media`（`edit media that other accounts uploaded`）・`delete media`（`delete media that other accounts uploaded`）・`create author profiles`・`edit author profiles`（`edit author profiles other than its own`）・`delete author profiles`・`edit terms`・`edit menus`・`edit forms`・`edit redirects`・`edit the site settings`・`manage builds and releases`・`manage accounts`・`edit its own account`（`edit another account`）・`view the logs`。知らない操作は、`do "<操作>"`。
- 入力の問題（`content.Errors`。`/login`・`/name`・`/email`・`/role`・`/author`・`/password` の順）：`/login: missing login`、`/login: invalid login name "<v>": use up to 64 lower case ASCII letters, digits, ".", "-" and "_", starting with a letter or a digit`、`/name: missing name`、`/name: contains <U+XXXX>, which is not assigned in Unicode 17.0.0`（`<U+XXXX>` は、名前の中で最初に当たった、割り当ての無いコードポイント。`17.0.0` は、ビルドのUnicodeの版で、パスワードのメッセージも同じ）、`/name: too long: <n> characters (max 256)`、`/email: missing email`、`/email: invalid email address "<v>": <理由>`、`/role: missing role`、`/role: unknown role "<v>"; use admin, editor, author or viewer`、`/author: invalid author ID "<v>": use "aut_" and a ULID (26 characters in upper case)`、`/password` は、次のうち最初の1つ（上記の「パスワード」の順）：`too long: <n> bytes (max 8192)`・`invalid UTF-8`・`contains control characters`・`contains a code point that is not assigned in Unicode 17.0.0`・`too short: <n> characters (min 15)`・`too long: <n> characters (max 256)`・`the same as the login name, the email address or the name`・`one character repeated`。`/name` と `/email` には、1行テキストとメールアドレスの規則（6.7）の問題（`/name: contains a line break or tab` など）も出る。
- 行どうしの問題（`content.Errors`）：`/login: login name "<v>" is already used by usr_…`、`/email: email address "<v>" is already used by usr_…`、`/author: author profile "aut_…" does not exist`、`/role: the first account is an administrator`（`CreateFirst`）。自分の名前とメールアドレスだけを変える `Update`（`account.self`。ログイン名・ロール・紐付けを含まない変更。admin も）が、ほかのアカウントのメールアドレスと重なるときは、そのアカウントのIDを示さない：`/email: email address "<v>" is already used by another account`（重なること自体は伝える）。admin が、ほかのアカウントや、ロール・ログイン名・紐付けを含む変更をするときと、システムは、IDを示す。
- 規則：`usr_… is the last active administrator: …`（上記の「無効と削除」。`account.ErrLastAdmin` を包む）、`usr_… is disabled: enable it first`、`the password of usr_… changed since it was read`（`account.ErrConflict` を包む）、`the store has accounts: CreateFirst needs a store without any`。
- トークンとパスワード：`invalid or expired token`（`account.ErrInvalidToken`）、`wrong login name or password`（`account.ErrBadCredentials`）、`unreadable password hash`。
- 無いもの：`accounts "usr_…": not found`（`fs.ErrNotExist` を包む。`Get`・`Read` が、IDの書式の誤りに返すのは、保存先の `invalid user ID "x": use "usr_" and a ULID (26 characters in upper case)`）、`no account has the login name "<v>"`（`Find`。`fs.ErrNotExist` を包む）。
- 読めない行：`accounts "usr_…": invalid value`（どの操作が失敗し、どれが飛ばし、どれが消せるかは、上記の「保存」の「読めない行」）、書こうとした行が読めないとき `cannot write usr_…: accounts "usr_…": invalid value`。
- 作る（`account.New`）：`cannot read a token: <理由>`・`cannot read a salt: <理由>`（乱数を読めないとき。`<理由>` は、乱数の読み手のエラー）。
- 保存先（3.4）：`accounts "usr_…": empty value`、`accounts "usr_…": too large: 65537 bytes (max 65536)`、`accounts "x": invalid key`、`read-only transaction`、`the transaction has ended`。
