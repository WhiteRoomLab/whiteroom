### 7.3 ログインアカウントと権限（案）

管理画面にログインする人のアカウントと、ロールごとの権限と、ログインとセッションを、`internal/account` に作った。アカウントは、保存先（3.4）の表 `accounts` に、1アカウントにつき1行で持ち、セッションは、表 `sessions` に、1セッションにつき1行で持つ。公開される著者プロフィール（6.6.3）とは別のもので（決定済み。6.1）、必要なら、アカウントの側から紐付ける。ログインとセッションのHTTPの側（Cookie・CSRFの対策・試行の制限）は9.6。まだ無いものは、下記の「まだ無いもの」。この節の規則は、「決定済み」と書いたもの（6.1）のほかは、どれも仮に決めたもの（案）。

**項目**

アカウントの項目（`account.Account` と、保存する行。行の形は下記の「保存」）：

| 項目 | 値 | 規則 |
| --- | --- | --- |
| `id` | アカウントのID（`usr_` とULID。6.7） | アカウントの操作が作る。作り方は、保存の操作が作るIDと同じ（6.7）で、呼ぶ側は書けない |
| `login` | ログイン名 | 英小文字・数字・`.`・`-`・`_` の64文字まで。先頭は英小文字か数字。正規化で、制御文字と前後の空白を取り除き、ASCIIの大文字を小文字にそろえる。アカウントの中で一意。ログインに使う（下記の「ログインとセッション」） |
| `name` | 表示する名前 | 1行テキスト（6.7）で、256文字（コードポイント）まで。正規化は、制御文字を取り除き、NFCにする（前後の空白は取り除かない。著者プロフィールの `name` と同じ）。いまのUnicodeの版で割り当ての無い文字を含むものは、書くときに断る（理由は、下記の「パスワード」の「割り当ての無い文字を断る理由」）。ほかのアカウントと同じでもよい |
| `email` | メールアドレス | 必須。6.7の規則（ASCIIだけ。ドメインの英字は小文字にそろえる）。アカウントの中で一意で、ASCIIの大文字と小文字を区別せずに比べる（6.7は、ローカル部の大文字と小文字を別のアドレスとして扱うが、アカウントでは同じとみなす）。ログインには使わない。通知や、後で足す招待と再設定のメール（8.2。6.12の202）に使う |
| `role` | ロール | `admin`・`editor`・`author`・`viewer`（下記の「ロールと権限」）。`Admin` のように、大文字を含むものは、知らないロールとして断る |
| `author` | 紐付ける著者プロフィールのID（`aut_`） | 任意。下記の「著者プロフィールとの紐付け」 |
| 状態 | `active`（有効）・`pending`（保留）・`disabled`（無効） | 行から決める（下記） |
| `createdAt` | 作った日時 | UTCのRFC 3339 |
| `createdBy` | 招待した人のアカウントのID | 最初の管理者と、システムの操作（下記の「作る」）が作ったものは、空 |
| `credentialsChangedAt` | 認証の手段を、設定・変更・削除した日時 | いまは、パスワードを決めた・変えた日時と、再設定で消した日時。認証の手段を一度も持ったことが無ければ、空。ログインでのハッシュの作り直しでは変えない。セッションが持つ値と比べる（下記の「ログインとセッション」） |
| `password` | パスワードのハッシュ | 行だけが持つ（`Account` には出ない）。下記の「パスワード」。パスワードそのものは、どこにも持たない |
| `token` | トークンの用途（`invitation`・`reset`）・SHA-256・期限 | 行だけがハッシュを持つ（`Account` は、用途と期限だけ）。下記の「招待と再設定」 |

状態（案）：

- 有効（`active`）：無効でなく、認証の手段を1つ以上持つ。認証の手段は、いまはパスワードだけ。ログインできるのは、有効なアカウントだけ（下記の「ログインとセッション」）。
- 保留（`pending`）：無効でなく、認証の手段をまだ持たない。招待したばかりのアカウントと、再設定の後のアカウント。トークンで認証の手段を決めると、有効になる。
- 無効（`disabled`）：admin が無効にしたアカウント。認証の手段を持っていても、ログインできない。トークンは持てず、再設定もできない。有効にし直す（`Enable`）と、認証の手段があれば有効に、無ければ保留に戻る。

行に持つのは、無効かどうか（`disabled`）だけで、状態は、行から決める。

**ロールと権限**

ロールは、次の4つ。

- `admin`：すべて。サイト設定・アカウントの管理（招待・再設定・変更・無効・有効・削除）・ビルドのやり直しと戻す操作・ログを見ることは、admin だけ。
- `editor`：どの人のエントリーも、作る・編集する・公開する（予約・公開をやめる・アーカイブも）・消す。メディア・著者プロフィール・ターム・メニュー・フォーム・リダイレクトも、作る・変える・消す。サイト設定・アカウント・ビルド・ログは不可。
- `author`：エントリーを作り（翻訳も）、自分のエントリーを編集・公開・消す。メディアを追加し、自分のメディアを編集・差し替え・消す。自分に紐付けた著者プロフィールを編集する。ターム・メニュー・フォーム・リダイレクトの作成と変更と、ほかの人のエントリーとメディアの変更は不可（エントリーにタームを付けることは、エントリーの編集なので、できる）。書く人が自分で公開できるので、承認の段階は要らない（4.4）。
- `viewer`：見るだけ（下書きも）。

どのロールも、管理画面のすべての文書を見られ、自分の表示する名前・メールアドレス・パスワードを変えられる。ログイン名・ロール・著者プロフィールの紐付けを変えられるのは、admin だけ。

自分のものとは、次のとおり。

- エントリー：`createdBy` がそのアカウントのID（6.4.1）。取り込んだエントリーの `createdBy` は、取り込んだアカウントなので、取り込んだ人のものになる。
- メディア：`uploadedBy` がそのアカウントのID（6.6.2）。
- 著者プロフィール：そのアカウントの `author` と同じID。紐付けの無いアカウントのものは、無い。
- アカウント：そのアカウント自身。admin も、ほかのアカウントは `accounts.manage` で変え、`account.self` ではしない。
- 空の `createdBy`・`uploadedBy`・紐付け・IDは、だれのものでもない。

確かめの規則（案）：

- 何も許さないもの：有効でないアカウント（保留と無効。ほかの値も）は、どの操作もできない。知らないロール（空も）と、知らない操作は、だれにも許さない。
- `account.Check` は、許さないときに、`account.ErrForbidden`（文は `not allowed`）を包んだエラーを返す。保存先も時計も読まない、副作用の無い関数で、同時に呼んでよい。見るのはアカウントのID・ロール・状態・紐付けだけで、ログイン名・名前・メールアドレス・日時・トークンと、セッションは見ない（セッションは、強い認証を求める規則を足すときに読む。下記の「強い認証を足すとき（#46 以降）」）。
- 呼ぶ側が渡す対象（`Target`）：エントリーの `createdBy`（`entry.edit`・`entry.publish`・`entry.delete`）、メディアの `uploadedBy`（`media.edit`・`media.delete`）、著者プロフィールのID（`author.edit`）、アカウントのID（`account.self`）。`entry.create`・`media.add` と、自分のものの規則の無い操作は、対象を見ない。
- 保存の操作と公開の操作（6.7）の前に `Check` を呼ぶのは、管理のAPI（#48）。いまは、アカウントの操作だけが `Check` を呼ぶ（下記の「作る」）。
- 見た目の直接指定（6.5.3）には、操作が無い。ロールでは絞らず、どのロールも、テーマが決める範囲（`custom`・`styles`。5.4.2）で使える（6.12の62）。
- 予約の日時の公開（`PublishScheduled`）にも、操作が無い。公開の権限は、予約のとき（`Schedule`）に、`entry.publish` として確かめる（下記の「予約」）。
- 細かいロール（サイトごとに作るロール、タイプや言語ごとの権限）は、いまは無い（6.12の205）。

**作る**

- 自己登録は行わない（7.2）。アカウントを作る道は、次の2つだけ。
  - 招待（`Invite`）：admin（かシステム）が、ログイン名・名前・メールアドレス・ロール（と、任意で著者プロフィール）を決めて作る。アカウントは保留で、トークンを1つ返す（下記の「招待と再設定」）。本人は、そのトークンでパスワードを決め（`SetPassword`）、有効になる。メールでは送らず、トークンを本人に渡すのは admin の手作業（URLの形は #48。トークンは、URLのパスにもクエリにも入れない：9.6の「記録」。メールで送ることは6.12の202）。
  - 最初の管理者（`CreateFirst`）：アカウントが1つも無い保存先（保留と無効のアカウントも数える）にだけ、パスワードつきの有効な admin を作る。ロールは admin だけ（空なら admin）で、`createdBy` は空。コマンド `whiteroom init`（9.2・9.4。#49）が、端末でパスワードを入れさせて呼ぶ。アカウントがあれば、`the store has accounts: CreateFirst needs a store without any` で断る。
- 操作者：アカウントの操作は、操作者（`Actor`）を取る。`account.By(アカウントのID)` か、システム（`account.System`）。システムは、サーバー上のコマンド（#49）が使う。どのアカウントの操作もできるが、最後の有効な admin を、無効にも、削除にも、ほかのロールにもできない（下記の「無効と削除」）。最後の有効な admin の再設定だけは、システムならできる（下記の「招待と再設定」）。システムが作ったアカウントの `createdBy` は、空。
- 操作者がアカウントのときは、その `Update` の中で読んだ行のアカウントについて、`Check` が許す必要がある。保留・無効のアカウントと、行の無いIDと、ゼロ値の操作者（`By("")`）は、何もできない。
- 確かめの順：すべての行を読み（読めない行があれば、ここで断る。例外は、下記の「保存」の「読めない行」）、操作者、入力、行どうしの問題（ログイン名とメールアドレスの重なり、紐付けるプロフィール）、最後の有効な admin の規則、の順に確かめ、最初に当たったものを返す。権限の無い操作者には、入力や行の問題を知らせない。操作者を取らない `CreateFirst` は、入力とパスワードの問題を、まとめて返す。

| --- | --- | --- |
| `CreateFirst` | 操作者を取らない | アカウントの無い保存先に、最初の admin を作る |
| `Invite` | `accounts.manage`、システム | 保留のアカウントと、トークンを作る |
| `SetPassword` | トークンを持つ人 | トークンで、パスワードを決める |
| `Reset` | `accounts.manage`、システム（最後の有効な admin は、システムだけ） | 認証の手段をすべて消し、トークンを作る |
| `ChangePassword` | 現在のパスワードを知る人 | パスワードを変える |
| `VerifyPasswordFactor` | だれでも | パスワードを確かめる（ログインではない） |
| `Login` | だれでも | ログイン名とパスワードで、セッションを始める（下記の「ログインとセッション」） |

**パスワード**

規則（案）：

- 大きさ：打たれたテキストが8KiB（8192バイト）を超えるものは、ほかの確かめより先に断る（`too long: <n> bytes (max 8192)`。`<n>` は打たれたバイト数）。NFCにもハッシュにもする前に断るので、長いテキストを送られても、読む以上の時間とメモリを使わない。保存できるパスワード（NFCにして256文字まで）と正準等価なテキストは、いまのUnicodeの表では、1文字が4コードポイントまでにしか分解されないので、最長でも4096バイトで、8KiBはその2倍。保存できるパスワードを打つときに、これで断られることは無い。
- 文字：不正なUTF-8（`invalid UTF-8`）と、制御文字（タブ・改行・NUL・DELなど。`contains control characters`）は断る。前後の空白も、中の空白も、取り除かず、切り詰めず、数える。文字の種類の組み合わせの規則と、定期的な変更の要求は、設けない。
- 割り当ての無い文字：いまのUnicodeの版（Goの `unicode` パッケージの版で、`internal/nfc` の表が従う。いまは17.0.0）で割り当ての無い文字（一般カテゴリー `Cn`。U+FFFE のようなノンキャラクターも含み、私用文字は含まない）を含むものは断る（`contains a code point that is not assigned in Unicode 17.0.0`。メッセージには、コードポイントを入れない）。名前（上記の「項目」）にも、同じ規則を当てる（`contains U+1ADE, which is not assigned in Unicode 17.0.0`）。当てるのは、名前とパスワードを書くとき（`CreateFirst`・`Invite`・`Update`・`SetPassword`・`ChangePassword`・`ChangeOwnPassword`）だけで、照合と、行を読むときには、当てない（下記の「保存」）。文書のテキストに当てるかは、6.12の16。
- 割り当ての無い文字を断る理由：NFCの文字列は、割り当ての無い文字を含まなければ、後のUnicodeの版でもNFCのままで、NFCの形も変わらない（UAX #15 の「安定した文字列」）。そのため、Goと `internal/nfc` の表を新しい版にしても、書いた名前はNFCのままで、パスワードのハッシュを求めたNFCの形は同じになり、打たれたパスワードは同じハッシュに合う。割り当ての無い文字を許すと、後の版でその文字が結合文字になったときに、NFCの形が変わり、そのパスワードは、打っても合わなくなる（再設定が要る）。
- 長さ：NFCにしてから、コードポイントで数えて、15文字以上256文字以下（`too short: <n> characters (min 15)`・`too long: <n> characters (max 256)`）。
- 同じもの：ログイン名・メールアドレス・表示する名前のどれかと、大文字と小文字を区別せずに同じもの（`the same as the login name, the email address or the name`）と、1つの文字だけの繰り返し（`one character repeated`）は断る。
- 確かめる順は、大きさ、不正なUTF-8、制御文字、割り当ての無い文字、長さ、同じもの、1つの文字の繰り返し、の順で、最初の問題を、`/password` の問題（`content.Errors`）にする。メッセージには、パスワードを入れない。確かめるのは、パスワードを決める・変えるとき（`CreateFirst`・`SetPassword`・`ChangePassword`・`ChangeOwnPassword`）だけで、ログインのときの照合では、確かめない。

NIST SP 800-63B-4（2025年7月。2026-11-08に確かめた）のうち、まだ合わせていない点は、ブロックリストとの照合（SHALL。6.12の198）、続けての失敗を100回以下にして、超えたら使えなくすること（SHALL。6.12の213）、秘密の鍵による追加のハッシュ（SHOULD。6.12の199）。7.3は、この規則がNISTの要件を満たすとも、認証の保証の水準（AAL）に当たるとも言わない。

ハッシュ（案）：保存先には、パスワードのハッシュだけを置く。

- 方式：PBKDF2のHMAC-SHA-256（標準ライブラリの `crypto/pbkdf2`）。回数は600000、ソルトは16バイト（`crypto/rand`）、値は32バイト。元にするのは、パスワードのNFCの形。
- 形：`$pbkdf2-sha256$i=600000$<ソルト>$<値>`。ソルトと値は、パディングの無い標準のbase64。方式と回数を持つので、回数を上げるときや、方式を替えるときに、読む側が見分けられる（作り直しは、下記の「ログインとセッション」の「ハッシュの作り直し」。方式を替えるのは6.12の200）。
- 読み方：この形だけを受け付ける。回数は1〜10000000の数字だけ（符号・空白・先頭の0は不可）、ソルトは16バイト以上、値は32バイトちょうど、base64は、書き戻して同じになるもの（改行・パディング・0でない余りのビットは不可）。読めないハッシュは、`unreadable password hash`（ハッシュの中身は示さない）。
- 照合：保存したハッシュのソルトと回数で、打たれたパスワードのNFCの形から値を求め、`crypto/subtle` の `ConstantTimeCompare` で比べる（比べる時間が、一致した長さを示さない）。保存したハッシュの回数が、いまの回数より少なくても、ハッシュに書かれた回数で照合でき、一致したときに限り、作り直すべきだと知らせる（使うのは `Login`。下記の「ログインとセッション」の「ハッシュの作り直し」）。
- 費用：1つのハッシュに、開発のマシン（16のCPU。Go 1.27.3）で約80ミリ秒かかる（作るときも、照合するときも。1つのハッシュを10回作った平均。2026-11-11）。打たれたパスワードのNFCとハッシュは、長さに比例するので、ログインの要求の本文は64KiBまでにする（9.6の「上限」。ほかの口の上限は #48。6.12の24）。同時に計算するハッシュの数は、`Manager` が制限する（下記の「ログインとセッション」の「パスワードのハッシュの順番」）。そのうえで、8KiB（8192バイト）を超える打たれたパスワードは、照合が、保存したハッシュを解析せず、NFCにもハッシュにもせずに、一致しないものとして断る。保存できるパスワードと正準等価なテキストは、上記の「大きさ」のとおり、4096バイトまでなので、一致するものが、これで断られることは無い。どのログイン名でも同じに断る。

OWASP の Password Storage Cheat Sheet（2026-11-08に確かめた）は、Argon2id（19MiB・2回・1並列）を第一に勧め、使えなければ scrypt、bcrypt は古いシステムだけ（入力は72バイトまで）、FIPS-140 が要るときは PBKDF2（HMAC-SHA-256で600000回）とする。パスワードのハッシュに使える方式で、Goの標準ライブラリにあるのは PBKDF2 だけで、Argon2id・scrypt・bcrypt は `golang.org/x/crypto` にある。外部のモジュールは、足す前にメンテナーに確かめる（1.2）ので、いまは足さず、標準ライブラリの PBKDF2 を、OWASP の回数で使う。メモリを多く使う Argon2id に比べると、GPUや専用の回路での総当たりに強くないので、15文字以上の長さを求めて補う。秘密の鍵による追加のハッシュ（ペッパー）は、鍵の置き場所とバックアップを決める必要があるので、使わない（6.12の199）。

変更と確かめ：

- 変更（`ChangePassword`）：現在のパスワードを知る人が、変える。アカウントが有効でないか、パスワードを持たないか、現在のパスワードが違うときは、`wrong login name or password`。新しいパスワードは、上記の規則に照らす。ハッシュは `Update` の外で作る（時間がかかるため）ので、`Update` の中で、保存したハッシュがそのままか（変わっていれば、`the password of usr_… changed since it was read`。`ErrConflict` を包む）、アカウントがまだ有効か、規則をもう一度確かめる。書くのは、ハッシュと `credentialsChangedAt` で、トークンは消す。同じ `Update` で、そのアカウントのセッションをすべて消す（変えた人のものも。自分のパスワードを変えるときは、`ChangeOwnPassword`）。
- 確かめ（`VerifyPasswordFactor`）：ログイン名（正規化する）のアカウントのパスワードを確かめ、一致すればアカウントを返す。ログインではなく、ログインの1つの要素の確かめで、`Login`（下記の「ログインとセッション」）が、同じ確かめをして、セッションを作る。失敗は、どれも `wrong login name or password`（ログイン名が無い・有効でない・パスワードが無い・行が読めない・パスワードが違う・照合の間に変わった、を区別しない）。保存先の失敗（取り消されたコンテキスト、ハッシュの順番を待つ間に終わったコンテキストなど）だけは、そのまま返す（管理用のサーバーは、サーバーの失敗として答える。9.6）。何も書かず（記録もしない。6.12の238）、試行は制限せず（試行の制限は、HTTPの側。9.6）、一致したときのハッシュの作り直しもしない（`Login` がする）。
- 照合の後の読み直し：パスワードが一致した後に、そのアカウントの行を読み直し（1つの `View`）、行がまだあり、読めて、パスワードのハッシュが一致したものと同じで、有効なときだけ、成功にして、そのときの行のアカウント（そのときの名前・メールアドレス・ロール・ログイン名・`credentialsChangedAt`）を返す。照合の間に、`ChangePassword`・`Reset`・`Disable`・`Delete` が書き終わっていることがあるため（読み直さないと、変えた（再設定した・無効にした・消した）直後に、前の状態でログインが成功することがある）。パスワードを変える操作は、同じパスワードに変えるときも、ソルトが新しくなってハッシュが変わるので、その間なら、ログインは失敗する。名前・メールアドレス・ロール・ログイン名の変更と、ほかのアカウントの操作と、`Disable` の後の `Enable`（ハッシュは変わらない）では、失敗しない。`Login` は、同じ読み直しを、セッションを書く `Update` の中でして、読み直しとセッションの書き込みの間に、変更が入らないようにする（下記の「ログインとセッション」）。
- だれにも一致しないハッシュ：有効でパスワードを持つアカウントが無いログイン名（行が無い・保留・無効・読めない行）でも、だれにも一致しないハッシュを確かめるので（`Login` も同じ）、時間で、ログイン名の有無が分からない。このハッシュは、`account.New` が `Manager` を作るときに、そのときの回数で1つ作る（ログインのときには作らず、乱数も読まない）ので、最初の呼び出しも、ほかと同じ、1つのハッシュの時間で済む。

**招待と再設定**

トークンは、アカウントに認証の手段を設定する権利で、どの手段のためかは知らない。いまの認証の手段はパスワードだけなので、`SetPassword` で使う。パスキーなどを足すときも、同じトークンと規則で使う（下記の「強い認証を足すとき（#46 以降）」）。

- 作り方：256ビットの乱数（`crypto/rand`）を、パディングの無いbase64url（43文字）で書く。作った操作（`Invite`・`Reset`）が、呼ぶ側へ一度だけ返し、保存先には、そのテキストのSHA-256（`sha256:` と小文字の16進数64桁）だけを置く。256ビットの乱数なので、パスワードのように総当たりされることはなく、鍵の無いSHA-256で足りる。
- 期限：招待は7日、再設定は24時間（作った時刻から数え、期限の時刻を過ぎれば使えない）。認証の手段を一度も持ったことの無いアカウント（招待したままのもの）の `Reset` は、招待として7日。
- 一度だけ：使うと消える。新しいトークン（もう一度の `Reset`）を作ると、前のものは使えなくなる（1アカウントに1つ）。無効にする（`Disable`）ときと、パスワードを変える（`ChangePassword`）ときも消える。
- 使い方（`SetPassword(ctx, c, token, password)`。`c` は `account.Client`）：トークンを持つアカウントを探す。すべての行のトークンのハッシュを、一定の時間で比べる。期限を過ぎたもの、無効のアカウントのもの、トークンの形でないもの（43文字でない長さのテキストは、復号の前に断る）は、理由によらず `invalid or expired token`（ログイン履歴には、理由を `token.failure` に記録する。7.4）。パスワードを、そのアカウントのログイン名などに照らして確かめる（問題は `/password` の問題で、トークンは残る）。ハッシュは `Update` の外で作り、`Update` の中で、トークンとパスワードの規則をもう一度確かめて、ハッシュと `credentialsChangedAt` を書き、トークンを消す。
- 再設定（`Reset`）：そのアカウントの認証の手段を、すべて、一度に使えなくし（いまはパスワードを消す）、`credentialsChangedAt` をいまにして、新しいトークンを作る。アカウントは保留になる。無効のアカウントは再設定できない（`usr_… is disabled: enable it first`）。パスワードが漏れた疑いのあるときも、同じ操作でよいように、古いパスワードは、その場で使えなくなる。
- 最後の有効な admin：再設定は、最後の有効な admin には断る（`usr_… is the last active administrator: its credentials cannot be reset`）。その人は、現在のパスワードを使う変更（`ChangePassword`）で、パスワードを変える。admin が全員ログインできなくなったときの復旧は、システムの再設定（`Reset(ctx, System, id)`）で、最後の有効な admin にもできる。そのアカウントは、パスワードを決める（`SetPassword`）まで保留になる。サーバー上のコマンド（#49）が、続けて呼ぶ。

**無効と削除**

- 無効（`Disable`）：ログインできなくする。トークンを消すほかは、何も変えない。`credentialsChangedAt` も変えないので、同じ `Update` で、そのアカウントのセッションを消す（下記の「ログインとセッション」）。有効にし直す（`Enable`）と、認証の手段があれば有効に、無ければ保留になる。すでにその状態なら（`Enable` も）、行は書かず、変えなかった印の記録（7.4）だけを書く。
- 削除（`Delete`）：行を、認証の手段ごと消す。そのアカウントのセッションも、同じ `Update` で消す。ログイン名とメールアドレスは、ほかのアカウントが使えるようになる。文書は変えない：エントリーの `createdBy`、メディアの `uploadedBy`、版とリビジョンの保存した人は、消したアカウントのIDのまま残り、著者プロフィールにも触れない（6.6.3）。消したIDの示し方は、6.12の204。消す前の行の値は、ログに残り、圧縮まで読める（3.5の「個人情報の削除」）。読めない行は、システムが、ほかの行を読まずに消せる（下記の「保存」の「読めない行」）。
- 最後の有効な admin の規則：書き込みの前後で、有効な（無効でなく、認証の手段を持つ）admin の数を数え、前にいて後にいなくなるものを断る。最後の有効な admin の無効・削除・ほかのロールへの変更・再設定（システムの再設定を除く）が、これに当たる。メッセージは、`usr_… is the last active administrator: it cannot be disabled`・`… it cannot be deleted`・`… its role cannot be changed`・`… its credentials cannot be reset`（`ErrLastAdmin` を包む）。保留と無効の admin は、ログインできないので、数えない。ロールが4つのどれでもないアカウントも、admin ではないので、数えない。システムも従う（再設定を除く）。読めない行をシステムが消すときは、その行を数えられないので、この規則を当てない。
- 同時の操作：アカウントを書く操作は、どれも、保存先の1回の `Update`（3.4）で、はじめにすべての行を読む。`Update` は1つずつ動く（3.4の「同時に使う」）ので、最後の有効な admin の規則と、ログイン名とメールアドレスの一意は、操作が同時に動いても守られる。

**記録**

行に持つのは、作った日時（`createdAt`）・作った人（`createdBy`）・認証の手段を変えた日時（`credentialsChangedAt`）だけ。だれが、いつ、何を変えたか（ロールの変更・無効・削除など）は、アクティビティログ（7.1）に、ログインとログアウト・セッション・ログインの失敗は、ログイン履歴（7.1）に記録する。どちらも、保存先に、操作と同じコミットで足す（7.4）。アカウントの操作は、成功したものを、何も変えなかったものも、1件ずつ、アクティビティログに記録する。記録には、パスワード・トークン・それらのハッシュ・名前とメールアドレスの値は入らない。

**ログインとセッション（#46）**

セッションは、サーバー側に持つ。ログインで、保存先の表 `sessions`（10。3.4の「表」）に1行を書き、ブラウザーには、その行を引く秘密のトークンだけを、Cookie（9.6）で渡す。要求のたびに、トークンから行を引き、アカウントを読み直して、使えるかを確かめる。入る道は、ログイン名とパスワードだけ（第2要素とパスキーは、下記の「まだ無いもの」）。ログインの試行の制限は、HTTPの側（9.6の「試行の制限」）にあり、制限する側が使う関数は、下記の「ログイン」。規則（案）：

トークンと行：

- トークン：256ビットの乱数（`crypto/rand`）を、パディングの無いbase64url（43文字）で書く。招待と再設定のトークンと同じ作り方で作る。ログインのたびに、新しいトークンを作る。
- 保存先に置くのは、トークンの文字列（43文字）のSHA-256の、小文字の16進数64桁だけで、これが表 `sessions` のキーになる（`sha256:` は付けない）。トークンそのものも、その一部も、保存先に残らない。256ビットの乱数なので、鍵の無いSHA-256で足りる（招待のトークンと同じ。上記の「招待と再設定」）。43文字でない長さのテキストと、43文字でも、32バイトのbase64urlの正準の書き方でないテキストは、保存先を読まずに、トークンでないものとして断る。
- 行のキー（この順で書く）：`account`（アカウントのID）・`createdAt`・`authenticatedAt`・`lastSeenAt`・`credentialsChangedAt`（ログインのときの、アカウントの値。零なら省く）・`factors`（ログインで使った要素の一覧。いまは `["password"]`）。例（実際は1行で、空白を入れない）：

```json
{"account":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","createdAt":"2026-11-09T01:02:03.456789Z","authenticatedAt":"2026-11-09T01:02:03.456789Z","lastSeenAt":"2026-11-09T01:02:03.456789Z","credentialsChangedAt":"2026-11-08T11:02:03.456789Z","factors":["password"]}
```

- 行は、トークンも、IPアドレスも、User-Agentも、要求のことを何も持たない（アドレスと User-Agent は、ログイン履歴が持つ。7.4）。大きさは265バイトまで（日時の秒の下の桁で変わる）で、保存先は4096バイトまで（3.4の「表」）。日時は、UTCのRFC 3339で、秒の下は、0でない最後の桁まで書き、ちょうどの秒には書かない。
- 読み方：JSONのオブジェクトであること（知らないキー・同じキー・型の違う値・不正なUTF-8・後ろに続くデータは断る）、`account` がアカウントのID、3つの日時があって、書き直せる範囲（0〜9999年）にあること、`factors` が1つ以上で、空の文字列を含まないことを確かめる。読めない行は、`sessions "<キー>": invalid value`（データの中身は示さない）。アカウントがあるかと、要素の意味は、行を使う側が確かめる。書く前にも、その行が読めることを確かめる（`cannot write a session of usr_…: invalid value`）。

期限と数：

- 操作の無い時間：最後の要求から1時間（`account.SessionIdleTimeout`）。最後の要求の時刻（`lastSeenAt`）は、保存した値が5分以上古いときだけ書く（毎回書くと、ログが増える。書くときは、ログイン履歴の `session.seen` の記録（7.4）も足す。6.12の219）ので、実際には、最後の要求から55分より後、60分までに終わる。時計が戻っても、書いた時刻は戻らない。
- 全体：ログイン（`authenticatedAt`）から12時間（`account.SessionLifetime`）。要求では延びない。再び入るには、ログインし直す。
- どちらも、期限の時刻ちょうどで終わる。Cookieには `Max-Age` を付けない（9.6の「Cookie」）が、期限は、サーバーが確かめる。
- 数：1アカウントに10個まで（`account.SessionsPerAccount`）。11個目のログインは、断らずに、最後に使った時刻（`lastSeenAt`。同じなら `createdAt`、それも同じならキー）が最も古いセッションを消す。
- 値の根拠は、下記の「確かめた事実（#46）」の NIST の再認証の期限と、OWASP の例（7.3の規則がNISTの要件を満たすとも、AALに当たるとも言わない）。管理のAPI（#48）の後の段階で作る管理画面は、下書きを失わない作りにする。

ログイン（`Login(ctx, c, login, password, previous)`。`c` は、要求の出どころ（`account.Client`。アドレスと User-Agent。7.4））：

- ログイン名を正規化（`account.NormalizeLogin`）し、パスワードを `VerifyPasswordFactor` と同じに確かめる。合わない理由は、どれも（ログイン名のアカウントが無い・有効でない・パスワードを持たない・行が読めない・パスワードが違う・8KiBを超える）、`wrong login name or password`（`ErrBadCredentials`）で、セッションの行は書かない（呼ぶ側への答えは変わらず、ログイン履歴に、理由とともに、失敗の記録だけを書く。7.4）。ログイン名に使えるアカウントが無いときも、だれにも一致しないハッシュを確かめる（上記の「パスワード」の「変更と確かめ」）。
- 一致した後、1回の `Update` で、アカウントの行を読み直し（まだあり、読めて、有効で、一致したハッシュのままであること。そうでなければ `wrong login name or password`）、次の順に、セッションの行を消してから、新しい行を書く（消した行ごとの `session.end` と、新しい行の `login` の記録も、同じ `Update` で足す。7.4）。
  1. 使えない行のすべて（どのアカウントのものでも）：期限が切れたもの、読めないもの、アカウントが無い・読めない・有効でないもの、アカウントの `credentialsChangedAt` が行のものと違うもの。
  2. `previous` のトークンの行（トークンでなければ、何もしない。どのアカウントのものでも）。ブラウザーが続けてログインしたときに、前のセッションを残さないため。
  3. このアカウントの行のうち、新しい行を足すと10個を超えるときは、最後に使ったのが古いものから、9個になるまで。
  4. 新しい行：`createdAt`・`authenticatedAt`・`lastSeenAt` はいま、`credentialsChangedAt` は読み直した行の値、`factors` は `["password"]`。
- 返すもの：`Principal`（アカウントは、読み直した行のもの。`Session` は、`AuthenticatedAt` がいま、`ExpiresAt` が12時間後、`Factors` が `[password]`。時刻はUTC）と、新しいトークン。
- エラー：保存先の失敗と、`ctx` の終わりは、そのまま返す（パスワードのハッシュの順番を待つ間に `ctx` が終わっても、`context.Canceled` か `context.DeadlineExceeded` で、`ErrBadCredentials` にはしない）。乱数が読めないときは `cannot read a token: <理由>`（照合の後）。作ったトークンのキーが、使える行のキーと同じになるとき（乱数が繰り返すとき）は、何も書かずに `cannot make a session: the token is already in use`（`crypto/rand` では起きない）。
- 比べた後のエラー：パスワードをハッシュと比べた後に出会ったエラー（新しいハッシュを作れないこと、乱数が読めないこと（`cannot read a token`）、セッションを書く `Update` が失敗すること。どれも `ctx` が終わった場合を含む）には、印を付ける。文と、`errors.Is`・`errors.As` で辿れる連鎖は、そのままで、`ErrBadCredentials` には印を付けない（それだけで、比べたことを示すため）。`account.PasswordCompared(err)` は、`ErrBadCredentials` と、印の付いたエラーで真、比べる前のエラー（保存先を読めない・ハッシュの順番を待つ間の `ctx` の終わり・保存したハッシュを読めない）で偽になる。ログインの回数を制限する側は、これが偽のときだけ、試行を戻す（理由は9.6の「試行の制限」の「試しの終わり」）。
- `account.PasswordTooLong(p)`：打たれたパスワードが、8KiB（8192バイト。上記の「パスワード」の「費用」）を超えるとき、真。そのパスワードは、`Login` が、ハッシュを作らずに `ErrBadCredentials` にするので、回数を制限する側は、`Login` を呼ばずに、同じ答えを返し、数えずにすませてよい（管理用のサーバーは、そうする。9.6）。照合の8KiBの確かめも、この関数を使う。

ハッシュの作り直し：

- 一致したハッシュの回数が、`Manager` の回数（既定は600000）より少ないとき、`Login` は、打たれたパスワードから、いまの回数でハッシュを作り直す。作るのは、セッションを書く `Update` の前で、順番を待つので、そのログインだけ、時間が約2倍になる。
- 作り直したハッシュは、セッションを書く `Update` の中で、読み直した行に書く。`credentialsChangedAt` も、ほかの項目も変えないので、そのアカウントのほかのセッションは続き、新しいセッションが持つ `credentialsChangedAt` も、同じ値。パスワードの規則（上記の「パスワード」）は当てない（すでに保存されたパスワードのため）。回数が `Manager` の回数以上のハッシュは、書き直さない。`VerifyPasswordFactor` は、作り直さない。既定の回数では、回数を上げるまで、何も書き直さない。
- ハッシュかセッションが作れなければ、ハッシュも行も書かない（ログイン履歴に、失敗の記録 `error` だけを、別の `Update` で書く。7.4）。作り直しが書き終わった後に、同じアカウントの `Login` か `VerifyPasswordFactor` が、古いハッシュに一致して、読み直すと、一度だけ `wrong login name or password` で失敗する（ハッシュが変わったため）。同じ呼び出しを、もう一度すれば通る。
- 回数を上げる基準と、方式を替えること、まだ作り直していない行がある間の、ログインにかかる時間の差は、6.12の200。

確かめ（`Authenticate(ctx, c, token)`）：

- トークンでないテキストは、保存先を読まずに `account.ErrNoSession`（文は `no valid session`）。ほかは、1回の `View` で行とアカウントを読み、次のどれかなら `ErrNoSession`：行が無い、行が読めない、期限が切れた、アカウントが無い・読めない・有効でない、アカウントの `credentialsChangedAt` が、行が持つ値と違う。パスワードを変えた・再設定した後に、前のセッションが残らず、無効にしたアカウントのセッションが使えなくなる。セッションを作った時刻とは比べない。使えない行は、`Update` で消し、`session.end` の記録（7.4）を足す（行の無いトークンは、何もコミットしない）。
- 使えるセッションの `lastSeenAt` が、5分以上古ければ、`Update` で書く。その `Update` の中で、行とアカウントを読み直し、期限も含めて同じ確かめを、新しい時計の読みでしてから、書く（`session.seen` の記録（7.4）も、同じ `Update` で足す）。書くものと答えるものが、1つの状態から来るためで、確かめてから書くまでの間に `Disable` などが書かれても、有効として答えない。5分より新しければ書かない（時計が戻っていても）ので、多くの要求は読むだけで済み、同時に来た要求は、1回だけコミットする。
- 答えるもの：`Principal`（アカウントは、いまの行）。
- `Authenticate` は書くことがある。書ける保存先（書くプロセスとして開いたもの）の `Manager` が要り、読み手として開いた保存先では、書くときに `read-only transaction` で失敗する。GET の要求でも、コミットすることがある（9.6）。

ログアウト（`Logout(ctx, c, token)`）：

- 1回の `Update` で、そのトークンの行を消し、`logout` の記録（7.4）を足す。トークンでないテキストと、行の無いトークンは、エラーにせず、何も書かない（記録も足さない。ブラウザーは、どちらにしてもログアウトする）。保存先の失敗と `ctx` の終わりは、そのまま返す。

セッションを終わらせる操作：

- 次の操作は、そのアカウントのセッションの行を、操作の `Update` の中で消す。すべての確かめを通った後なので、断られた操作は、何も消さない。消せなければ（保存先の失敗）、`Update` ごと失敗する。消した行ごとに、ログイン履歴に `session.end` の記録（理由：`password`・`role`・`disabled`・`deleted`。7.4）を、同じ `Update` で足す。

| 操作 | 消すセッション |
| --- | --- |
| `Disable` | 無効にするときだけ。`Enable` と、すでに無効のアカウントへの `Disable` は消さない |
| `Delete` | 消すアカウントのもの。システムが、読めない行を消すときは、その行のIDを指すセッションも |
| `Update` | ロールを変えるときだけ（自分のロールを変えるときも）。ログイン名・名前・メールアドレス・著者プロフィールの紐付けの変更と、何も変えない `Change` は消さない |
| `ChangePassword` | すべて（だれが呼んでも） |
| `Reset` | すべて（保留のアカウントも） |
| `SetPassword` | すべて |
| `ChangeOwnPassword` | すべて。そのあとで、新しいセッションを足す（下記） |

- 消さない操作：`Enable`・`Invite`・`CreateFirst`・`VerifyPasswordFactor`・`Authenticate`・`Logout`（渡したトークンのセッションだけを消す）。`Login` は、`previous` と、上限を超える分と、使えない行を消す。
- 理由：`Disable` は `credentialsChangedAt` を変えないので、消さないと、有効にし直した（`Enable`）ときに、持つ値がいまの値のままで、前のセッションが、また使えるようになる。ロールの変更も `credentialsChangedAt` を変えない。セッションは、要求のたびにアカウントを読み直すので、ロールを変えれば、次の要求から、新しいロールで権限を確かめる。それでも消すのは、ロールを上げたときに、盗まれたセッションが、そのまま強いロールで使われないようにするためと、ロールごとに強い認証を求める（6.12の207）ときに、ログインし直しで、その強さを確かめられるようにするため。OWASP も、権限の変更で、セッションの識別子を作り直すことを求める。
- 読めない行は、だれのものでもないので消さない。次の `Login` の掃除か、そのトークンの `Authenticate` が消す。

本人のパスワードの変更（`ChangeOwnPassword(ctx, c, token, current, next)`）：

- セッションを持つ人が、現在のパスワードを入れて、自分のパスワードを変える。`Principal` と、新しいトークンを返す。呼ぶ側（#48の口）は、Cookieを新しいトークンで置き換える。古いトークンも、そのアカウントのほかのトークンも、`ErrNoSession` になる。
- 1回の `Update` で、新しいハッシュと `credentialsChangedAt` を書き（`ChangePassword` と同じ確かめ）、そのアカウントのすべてのセッションを消し（質問したセッションも）、新しいセッション（`authenticatedAt` はいま、新しい `credentialsChangedAt`）を書く。ほかの端末や、盗まれたCookieのセッションは終わり、変えた人は、そのまま作業を続けられる。消したセッションごとの `session.end`（理由 `password`）と、新しいセッションの `session.start`（7.4）、アクティビティログの `account.changePassword`（7.4）を、同じ `Update` で足す。
- 断る理由の順：トークンでない、またはセッションが使えない（`Authenticate` の確かめ）→ `ErrNoSession`。読めないアカウントの行 → `accounts "usr_…": invalid value`。`Check` が、自分のアカウントの変更（`account.self`）を許さない → `ErrForbidden` を包んだエラー（`usr_… ("owner"): not allowed to edit its own account` のように。いまは、知らないロールだけ）。パスワードが無い、または `current` が違う（8KiBを超えるものも）→ `wrong login name or password`。`next` の問題 → `/password` の問題（`content.Errors`）。そのあと、新しいハッシュとトークンを作って、`Update` に入る。`Update` の中で、セッションとアカウントを、もう一度読む（セッションが使えなければ `ErrNoSession` が先）。ハッシュが変わっていれば `the password of usr_… changed since it was read`（`ErrConflict` を包む）、パスワードか状態が変わっていれば `wrong login name or password`。
- ハッシュは、`current` の照合と新しいパスワードの2つで、順番を待つ。断った呼び出しは、何も書かず、セッションはそのまま。
- `Authenticate` は呼ばない（最後の要求の時刻を書かない）。セッションとアカウントを、1つの `View` で読み、`Update` の中でも読み直すので、同時に別のパスワードの変更や再設定が書き終わっていれば、`ErrNoSession` になる（`wrong login name or password` ではない）。
- 試行の制限は、この操作に無い。`current` を確かめるので、HTTPの口（#48）が、独自の制限を持つ（6.12の215）。

セッションの認証の強さ（`account.Principal`）：

- セッションは、ログインの時刻・全体の期限（12時間後）・使った要素（いまは `password` だけ）を持ち、確かめる側に渡る（操作の無い時間は持たない。管理用のサーバーが答える。9.6）。

パスワードのハッシュの順番：

- `Manager` は、パスワードのハッシュを同時に計算する数を、`GOMAXPROCS` の4分の1（1以上）に制限し、ほかの呼び出しは、順番を待つ（`VerifyPasswordFactor`・`Login`・`ChangePassword`・`ChangeOwnPassword`・`SetPassword`・`CreateFirst` が通る。`account.New` が作る1つのハッシュは通らない）。ログインの洪水が、すべてのCPUを使い切れないようにするため。待つ間に `ctx` が終われば、ハッシュを作らずに、`ctx` のエラーを返す。
- 開発のマシン（16のCPU）では、同時に4つで、これが、ログインの毎秒の上限（約35件）になる（PBKDF2のハッシュを、4つのゴルーチンで3秒ずつ作って測った）。順番に入る数の上限は、9.6の「試行の制限」。

ほかの口：

- `account.NormalizeLogin(s)`：ログイン名の読み方（制御文字と前後の空白を取り除き、ASCIIの大文字を小文字にする）を、すべての操作と同じに、外から使えるようにしたもの。管理用のサーバーが、試行を数えるキーに使う。
- `account.NewWithIterations(s, 回数)`：ハッシュの回数を決めて `Manager` を作る。ほかのパッケージのテストが、速いハッシュ（回数は1〜10000000。ほかは `invalid iteration count <n>`）を使うためのもの。本番のコードは `account.New` を使う。
- 秘密を出さない：セッションのトークンの平文は、保存先にも、エラーの文にも、表示（`%v`・`%+v`・`%#v`・`%s`・`%q`）にも出ない。保存先のログには、トークンのSHA-256のキーが、ログアウトの後も残る（ログは、書いたものを圧縮まで残す）が、キーから、トークンは求まらない（ログイン履歴の記録（7.4）にも、このキーが残る）。

**予約**

予約の日時の公開（`PublishScheduled`。4.4・6.7）は、予約した人の保存として記録する（予約を保存した版の保存した人）。公開の権限（`entry.publish`）は、予約するとき（`Schedule`）に確かめ（#48）、日時の公開では確かめない（案）。そのため、予約した人のアカウントを、無効にしても、消しても、ロールを変えても（権限を失っても）、予約は残り、日時に、そのIDのまま公開される。予約を止めたいときは、予約を取り消す（`Unpublish`。そのときの権限で確かめる）。アクティビティログの記録は、`actor` を `system` にし、予約した人を `scheduledBy` に持つ（7.4）。版の保存した人は、予約した人のままで、これも、システムの操作として保存するかは、6.12の186。

**著者プロフィールとの紐付け**

- 紐付けは、アカウントの側に持つ（`author`。決定済み。6.1・6.6.3）。
- 紐付けるとき（招待・最初の管理者・`Update` で紐付けを変えるとき）に、そのプロフィールがあることを、その `Update` の中で確かめる（無ければ、`/author: author profile "aut_…" does not exist`）。IDの書式は、`invalid author ID "…": use "aut_" and a ULID (26 characters in upper case)`。
- 後でプロフィールが消されても、消すことを断らず、アカウントはIDを持ったまま、紐付けが無いものとして扱う（案）。そのプロフィールを編集する操作は、起きない。紐付けを変えない変更では、確かめ直さない（確かめ直すと、プロフィールを消した後、そのアカウントの名前も変えられなくなる）。消したプロフィールへの紐付けを、どうするかは、6.12の204。
- 1つのプロフィールを、いくつのアカウントにも紐付けられる（「編集部」など。6.6.3）。紐付けを変えられるのは、admin だけ（`Update` の `Author`。空にすると外れる）。

**強い認証を足すとき（#46 以降）**

多要素認証（MFA）、パスキー（WebAuthn）、一部のロールに強い認証を求めること、機微な操作の前の再認証は、まだ無い。いまのセッションは、使った要素と、認証した時刻を持つ（上記の「ログインとセッション（#46）」）。ここに書くのは、足すときの形（案）で、足す issue が決める。パスキーを足すときに、WebAuthn に1.2の例外が要るか（6.12の212）も、そこで決める。

足せるもの（案）：

- 第2要素：TOTP（RFC 6238）と、回復用のコード。
- パスキー（WebAuthn の資格情報）：ユーザー検証（本人であることの確認）を必須にして使う。パスワードを持たず、パスキーだけでログインするアカウントも、同じ形で足せる（6.12の208）。
- 一部のロールに、多要素認証かパスキーを求めること（6.12の207）。
- アカウントの管理などの機微な操作の前に、最近の再認証を求めること（6.12の211）。

いまの規則との合わせ方（案）：

- 状態：認証の手段を持つかの判定（コードの1か所）に、新しい手段を数える。有効＝無効でなく、認証の手段を1つ以上持つ、という規則と、保留・無効は、変わらない。
- 最後の有効な admin：認証の手段を消す操作（パスキーの削除など）も、アカウントを書く道を通るので、最後の有効な admin のものは断られる。MFA かパスキーを求めるロールがあるとき、規則が数えるのは、求める強さでログインできる admin か（6.12の207）。
- トークン：招待と再設定のトークンは、どの手段のためかを知らないので、パスキーの登録にも、同じトークン・同じ使い方（一度だけ・期限・置き換え・ハッシュだけを保存）を使える。ただし、認証の手段を持つアカウントに2つ目を足すときは、トークンではなく、ログインしている人の認証で足す形が考えられる。NIST SP 800-63B-4 は、新しい認証器を結びつけるときに、アカウントで使える最も高い AAL か、新しい認証器の AAL の、低いほうでの認証を求める（SHALL）。どうするかは、足す issue が決める（6.12の211）。
- `credentialsChangedAt`：認証の手段を足す・変える・消すたびに更新し、セッションが持つ値と違えば、そのセッションを終わらせる基準にする（上記の「ログインとセッション」）。
- `VerifyPasswordFactor`：1つの要素の確かめで、`Login` が、第2要素やパスキーの確かめと組み合わせる（下記の「ログインの形」）。パスワードの無いアカウントでの扱いは、6.12の208。
- 権限：`account.Principal` は、もう、セッションの認証の強さ（使った要素・認証した時刻。`Session`）を持つ。権限の表（コードの `rules`）に、その操作が求める強さの列を足し、`Check` が、許す条件に加えて、`Session` を読む。呼ぶ側は `Principal` をそのまま渡すので、変わらない。
- 再認証：操作者（`Actor`）にも、同じ強さの情報を持たせ、アカウントの管理などの操作が、最近の再認証を求められるようにする。いまの `Actor` は、アカウントのIDかシステムだけで、組み立てられるのは `account` パッケージだけ。

ログインの形（案。足す issue が決める）：

- `Login` は、いまのとおり、パスワードを確かめる。第2要素を持つアカウントには、全部のセッションを作らず、短い期限の、途中のセッション（`Factors` が `[password]` だけで、第2の段階の口のほかには、どの口も受け付けないもの）を作って返す。
- 第2の段階は、第2要素（TOTP の値か、回復用のコード）を確かめ、途中のセッションを、全部のセッションに置き換える（新しいトークン。`Factors` は `[password, totp]` など）。トークンを作り直すので、途中のトークンは使えなくなる。
- パスキーだけで入るアカウントは、パスワードの段階を飛ばし、パスキーの確かめだけで、全部のセッション（`Factors` は `[passkey]`）を作る（6.12の208）。
- `Principal.Session` の `Factors` と `AuthenticatedAt` が、一部のロールに強い認証を求める規則（6.12の207）と、機微な操作の前の再認証（6.12の211）が読むもの。
- 第2の段階にも、試行の制限（9.6）が要る。

どこに持つか（案）：

- アカウントの行の、省ける項目として足す（新しい `logSchemaVersion`。3.4）。いま書いている行は、書き直さずに、そのまま読める。状態と最後の有効な admin の規則が、1つの行だけから決まる関数のままでいられる（別の表に持つと、2つの表を同時に読む必要が出る）。行の上限（64KiB）が、1つのアカウントのパスキーの数を決める。
- パスキーが持つもの：資格情報のID・公開鍵（COSE形式）・署名の回数・トランスポート・BE と BS のフラグ・uvInitialized・AAGUID・名前（本人が付ける）・作った日時と最後に使った日時。
- TOTP の秘密：ハッシュにできない（確かめるたびに、秘密から値を求めるため）ので、暗号化して持ち、鍵は保存先の外に置く。鍵の置き場所とバックアップは、鍵つきのハッシュ（6.12の199）と個人情報の暗号化の鍵（6.12の138）と同じ問題なので、あわせて決める（6.12の210）。
- 回復用のコード：トークンと同じに、ハッシュだけを保存先に置き、使ったら無効にする。長さは、NIST SP 800-63B-4 が求める64ビット以上（承認された乱数生成器から）を下回らない。実際の長さは、足す issue が決める。
- ユーザーハンドル：最初のパスキーを登録するときに作る64バイトの乱数で、アカウントの行に持つ。ログイン名とメールアドレスは変えられ、個人を特定する値なので使わない。アカウントのIDは、作った時刻を含み（6.7）、文書にも書かれる値なので、認証器に持たせない。
- 認証器の証明（attestation）の扱いは、6.12の209。

**保存**

アカウントは、保存先の表 `accounts`（9。3.4の「表」）に、アカウントのIDをキーに、1行ずつ持つ。値は、`internal/account` が書くJSONで、保存先は読まない。表の版ごとの違いと更新は、3.4の「エンジンと設定」の「表の版」と、「索引」の「表の版の更新」。

行のキー（この順で書く。省ける項目は省く）：`id`・`login`・`name`・`email`・`role`・`author`（紐付けがあるとき）・`disabled`（無効のときだけ。`true`）・`createdAt`・`createdBy`（あるとき）・`password`（あるとき）・`credentialsChangedAt`（あるとき）・`token`（あるとき。`purpose`・`hash`・`expiresAt`）。

例（実際は1行で、空白を入れない。`<…>` は、実際の値に置き換える。ハッシュとトークンの実際の値は、ここに書かない）。招待したばかりの行：

```json
{"id":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","login":"yamada","name":"山田 太郎","email":"yamada@example.com","role":"editor","author":"aut_01JBA4C7N9Q3T6W9Z3C6F9H2K5","createdAt":"2026-11-08T01:02:03Z","createdBy":"usr_01JB8T7H4MA2C5E8G1J4K7N3P5","token":{"purpose":"invitation","hash":"sha256:<64桁の小文字の16進数>","expiresAt":"2026-11-15T01:02:03Z"}}
```

本人がパスワードを決めた後の行（トークンは消え、ハッシュと `credentialsChangedAt` が入る）：

```json
{"id":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","login":"yamada","name":"山田 太郎","email":"yamada@example.com","role":"editor","author":"aut_01JBA4C7N9Q3T6W9Z3C6F9H2K5","createdAt":"2026-11-08T01:02:03Z","createdBy":"usr_01JB8T7H4MA2C5E8G1J4K7N3P5","password":"$pbkdf2-sha256$i=600000$<ソルト>$<値>","credentialsChangedAt":"2026-11-08T11:02:03.456789Z"}
```

規則（案）：

- 日時：UTCのRFC 3339で、小数の秒を持つことがある（文書の日時は、小数の秒を使えない。6.7）。秒の下は、0でない最後の桁まで書き、ちょうどの秒には書かない。
- 書く形：書くのは1通りの形だけ（キーの順と日時は上記）で、書く前に、その行が読めることを確かめる（読めない行を書くと、あとの操作が止まるため）。Goの版が変わって、書き方（エスケープなど）が変わっても、すでに書いた行は、下記のとおり読める。
- 読み方：読むときは、行の保存の形だけを確かめる。確かめるのは、JSONのオブジェクトであること（知らないキー・同じキー・型の違う値・不正なUTF-8・後ろに続くデータは断る）、`id` が表のキーと同じアカウントのIDであること、`login`・`name`・`email`・`role`・`createdAt` があって、空でないこと、`createdBy` が空かアカウントのID、`author` が空か著者プロフィールのIDであること、`password` が空か、ハッシュの形（上記の「ハッシュ」の「読み方」）であること、`token` が無いか、用途（`invitation`・`reset`）・ハッシュの形（`sha256:` と小文字の16進数64桁）・期限を持つこと、日時がUTCにして0〜9999年に入ること（JSONに書けて、書き直せる範囲）。
- 読めるもの：これ以外は確かめない。キーの順・空白・エスケープ・UTC以外の日時・秒の下の桁・空の値と `null` の違いは、読める。値の規則（上記の「項目」・「パスワード」）は、書くときに当て、読むときには当てないので、書くときの規則が断る値（大文字を含むログイン名・NFCでない名前・割り当ての無い文字を含む名前・メールアドレスでない値・知らないロール・無効のアカウントのトークン）も、読める。書き直したバイト列との一致も、確かめない。規則を読むときに当てないのは、ほかのビルド（Unicodeの版や規則の違うもの）が書いた行や、あとで厳しくなった規則に合わない行を、読めない行にしないため（読めない行があると、下記の「読めない行」のとおり、その行のアカウントはログインできず、書く操作と `List` は、どれも止まる）。読んだ行を書き直すときは、書く形になる（名前を変えない操作は、名前をそのまま書く）。
- 知らないロール：読めるが、`Check` は何も許さず（メッセージは、ロールを引用符で囲む。下記の「エラー」）、最後の有効な admin の数にも入らない。admin が、`Update` で、知っているロールにできる。
- 読めない行：保存の形を満たさない行（保存先のAPIを通さずに書かれたもの、壊れたもの、このビルドが知らないキーを持つもの）は、`accounts "usr_…": invalid value`（データの中身は示さない）になる。扱いは、次のとおり（案）：
  - `VerifyPasswordFactor`・`Find`：その行を飛ばす。読めない行は、どのログイン名のアカウントでもないので、ほかのアカウントのログインと検索は、止まらない。
  - システムの `Delete`：対象の行だけを先に読み、読めなければ、ほかの行を読まずに、その行を消す。最後の有効な admin の規則は当てない（読めない行は数えられないため）。読めない行が何行あっても、1行ずつ消せる。サーバー上の復旧のコマンド（#49）が使う。
  - ほかの書く操作（`CreateFirst`・`Invite`・`SetPassword`・`Reset`・`ChangePassword`・`Update`・`Disable`・`Enable`と、読める行の `Delete`。システムの `Delete` も、読める行には）：断る。ログイン名とメールアドレスの一意と、最後の有効な admin の規則が、すべての行を読む必要があるため。操作者の確かめより先に断り、エラーは、IDの順で最初の読めない行を指す。アカウントの操作者は、読めない行を消せない。
  - `List`：読めない行が1つでもあれば、失敗する。`Get`・`Read`：読めない行を指したときだけ、失敗する。
- 秘密を出さない：公開する型 `Account` は、パスワード・ハッシュ・トークンを持たない。内部の行を表示しても（`%v`・`%+v`・`%#v`）、IDだけが出る。エラーの文にも、パスワード・トークン・ハッシュは入らない。データのディレクトリのどのファイルにも、パスワードとトークンの文字列は残らない。
- 大きさ：1行は64KiB（65536バイト）まで（3.4の「表」）。
- 数：アカウントの数の上限は無い。書く操作は、毎回すべての行を読む。想定は、管理画面にログインする人で、数人から数十人。
- 変えるとき：省ける項目を足す変更は、すでに書いた行を書き直さずに、新しい `logSchemaVersion` で足す（上記の「強い認証を足すとき（#46 以降）」）。省けない項目や、意味を変える変更は、行を変換する更新が要る（3.4の「索引」の「表の版の更新」と同じ形）。行を読むときは保存の形だけを確かめるので、入力の規則（ログイン名の文字、名前やパスワードの長さなど）を変えるときは、行の更新が要らない（書くときから当たる）。セッションの行のキー（上記の「ログインとセッション」）を変えるときも、新しい `logSchemaVersion` が要る。

**置き場所**

- `internal/account`：アカウントの型と入力の検証、行の形、権限の確かめ（`Check`・`Allowed`）、パスワードとトークン、アカウントの操作（`Manager`。`account.New(s)` で作る）、セッション（ログイン・確かめ・ログアウト・本人のパスワードの変更と、セッションの行）。
- 管理用のサーバー（9.6）は、プロセスごとに `Manager` を1つ作る（パスワードのハッシュの順番は `Manager` ごとなので、複数作ると、同時に計算する数が、その数だけ増える）。
- `internal/admin`（9.6）が、ログインとセッションのために使う。#48（管理のAPI。`account.Check` と `account.Read`）と #49（コマンド）も使う。
- ログイン履歴とアカウントの操作の記録（7.4）も、`internal/account` が、保存先に足す。`Manager` は、書けなかった記録を知らせる関数（`OnRecordError`）と、数えただけの失敗の記録を書く口（`FlushSuppressed`）を持つ。

**エラー**

メッセージは、コードが書くとおり（英語）。本文に引いたものは、ここに書かない。呼ぶ側は、文ではなく、`errors.Is`・`errors.As` で分ける：`account.ErrForbidden`・`content.Errors`・`fs.ErrNotExist`・`account.ErrLastAdmin`・`account.ErrConflict`・`account.ErrInvalidToken`・`account.ErrBadCredentials`・`account.ErrNoSession`。

- 操作者：`<id> (<role>): not allowed to <phrase>`（有効でないアカウントは、`<id> (<status>): …`）、`not allowed: the operation has no actor`、`usr_…: not allowed: no such account`。どれも `account.ErrForbidden` を包む。アカウントのIDとロールか状態のほかに、アカウントと対象のことは入らない。有効なアカウントのロールが、4つのどれでもないとき（ほかのビルドが書いた行など）は、ロールを引用符で囲む：`<id> ("<role>"): …`（改行などは `\n` のように書くので、メッセージに改行は入らない）。
- `<phrase>` は、操作ごとの文（`edit entries` など）で、自分のものだけを許すロールが、自分のものでないものに当たるときは、別の文（`edit entries that other accounts made` など）。知らない操作は、`do "<操作>"`。
- 入力の問題（`content.Errors`。`/login`・`/name`・`/email`・`/role`・`/author`・`/password` の順）：`/login: missing login`、`/login: invalid login name "<v>": use up to 64 lower case ASCII letters, digits, ".", "-" and "_", starting with a letter or a digit`、`/name: missing name`、`/name: contains <U+XXXX>, which is not assigned in Unicode 17.0.0`（`<U+XXXX>` は、名前の中で最初に当たった、割り当ての無いコードポイント。`17.0.0` は、ビルドのUnicodeの版で、パスワードのメッセージも同じ）、`/name: too long: <n> characters (max 256)`、`/email: missing email`、`/email: invalid email address "<v>": <理由>`、`/role: missing role`、`/role: unknown role "<v>"; use admin, editor, author or viewer`。`/author` と `/password` のメッセージは、上記の「著者プロフィールとの紐付け」と「パスワード」。`/name` と `/email` には、1行テキストとメールアドレスの規則（6.7）の問題（`/name: contains a line break or tab` など）も出る。
- 行どうしの問題（`content.Errors`）：`/login: login name "<v>" is already used by usr_…`、`/email: email address "<v>" is already used by usr_…`、`/role: the first account is an administrator`（`CreateFirst`）。自分の名前とメールアドレスだけを変える `Update`（`account.self`。ログイン名・ロール・紐付けを含まない変更。admin も）が、ほかのアカウントのメールアドレスと重なるときは、そのアカウントのIDを示さない：`/email: email address "<v>" is already used by another account`（重なること自体は伝える）。admin が、ほかのアカウントや、ロール・ログイン名・紐付けを含む変更をするときと、システムは、IDを示す。
- 無いもの：`accounts "usr_…": not found`（`fs.ErrNotExist` を包む。`Get`・`Read` が、IDの書式の誤りに返すのは、保存先の `invalid user ID "x": use "usr_" and a ULID (26 characters in upper case)`）、`no account has the login name "<v>"`（`Find`。`fs.ErrNotExist` を包む）。
- 読めない行：書こうとした行が読めないとき `cannot write usr_…: accounts "usr_…": invalid value`（上記の「保存」の「読めない行」）。
- 作る（`account.New`）：`cannot read a token: <理由>`・`cannot read a salt: <理由>`（乱数を読めないとき。`<理由>` は、乱数の読み手のエラー）。
- 保存先：行の大きさ・キー・トランザクションの問題は、3.4の「表」のメッセージのまま返る。

- 自分のセッションの一覧と、ほかのセッションを終わらせる操作（6.12の216）。
