### 6.6 本文以外のエンティティ

#### 6.6.1 タクソノミーとターム

- タクソノミー：`category`（階層あり）と `tag`（階層なし）を標準で持つ。独自のものはサイト設定で定義し（6.4.4）、`hierarchical` で階層の有無を決める。標準の `category`・`tag` も、サイト設定で `label`（管理画面での名前）とURLの規則を変えられる（階層の有無は変えられない。6.6.8）。
- ターム：1つの言語版を1つのタームとし、各言語版を翻訳グループで結ぶ（エントリーと同じ。6.4.5）。

タームの項目（案）：

| 項目 | 値 | 必須 |
| --- | --- | --- |
| `id` | タームのID（6.7） | ○ |
| `taxonomy` | `category`・`tag` か、サイト設定で定義したタクソノミー（6.4.4） | ○ |
| `language` | サイト設定にある言語コード（6.4.5） | ○ |
| `translationGroup` | 翻訳グループのID。翻訳の無いタームも、自分だけのグループを持つ | ○ |
| `name` | 1行テキスト（表示する名前） | ○ |
| `slug` | スラッグ（6.4.2と同じ規則）。同じタクソノミー・同じ言語の中で一意 | ○ |
| `parent` | 親のタームのID。階層ありのタクソノミーだけで、同じタクソノミー・同じ言語のターム。自分自身は不可 | |
| `description` | 複数行テキスト（装飾なし）。タームの一覧ページなどに表示する | |

規則（案）：

- タームは `schemaVersion` つきの1つのJSONの文書にし（例は6.11.3）、エントリー（6.4.1）と違って状態とリビジョンに分けず、下書き・公開の状態も持たない。保存した内容は、次のビルドから使われる。古い版を残すかは保存先（3.2）で、変更の記録はアクティビティログ（7章）で扱う（WordPressにもタームの履歴は無い）。
- 下書きが無く、保存がそのまま公開に当たるので、必須の項目は保存のたびに確かめる（6.1）。
- `parent` のタームが存在するか、タクソノミーと言語が同じかは、照会の関数で確かめる（6.7）。スラッグの一意性、翻訳グループの中で同じ言語は1件まで、親をたどった循環は、複数のエンティティにまたがる検証で扱う（6.7）。

#### 6.6.2 メディア

- アップロードした画像・PDFなどのファイルと、そのメタデータ。1つのメディアが1つのファイルを持ち、言語では分けない（`alt` と `caption` だけを言語ごとの値で持つ。6.3）。

メディアの項目（案）：

| 項目 | 値 | 必須 |
| --- | --- | --- |
| `id` | メディアのID（6.7） | ○ |
| `hash` | ファイルの中身のハッシュ（SHA-256）で、`sha256:` と小文字の16進数64文字。ファイルはこれで保存して指す（下記） | ○ |
| `fileName` | アップロードしたときのファイル名（規則は下記） | ○ |
| `mimeType` | ファイルの形式を表すMIMEタイプ（下記の5つ） | ○ |
| `size` | ファイルのバイト数（1以上の整数。上限は下記） | ○ |
| `width`、`height` | 画像の幅と高さの画素数（1以上の整数）。EXIFの向きを反映した、表示するときの大きさ（下記）。画像だけ | ○（画像） |
| `alt` | 言語ごとの値（6.3）で、1行テキスト。画像の既定の代替テキスト（描画での使い方は下記）。画像だけ | |
| `caption` | 言語ごとの値（6.3）で、複数行テキスト（装飾なし）。画像の既定のキャプション。画像だけ | |
| `uploadedAt` | 日時（6.7） | ○ |
| `uploadedBy` | ログインアカウント（7章）のID | ○ |

規則（案）：

- ターム（6.6.1）と同じく、`schemaVersion` つきの1つのJSONの文書にし（例は6.11.5）、状態とリビジョンに分けず、下書き・公開の状態も持たない。必須の項目は保存のたびに確かめる。
- 形式と種類：段階1で受け付ける形式は、JPEG、PNG、WebP、GIF、PDF。`mimeType` は `image/jpeg`・`image/png`・`image/webp`・`image/gif`（種類は `image`）と `application/pdf`（種類は `pdf`）だけで、ほかはエラーにする（種類は、照会の関数が返すメディアの種類。6.7）。`width`・`height`・`alt`・`caption` は画像だけに書け、PDFに書くとエラーにする。SVGは受け付けない（スクリプトを含められるため。無害化して受け付けるかは段階2で検討する）。AVIF・HEICなど、ほかの形式を受け付けるかは6.12の44。
- 形式は中身から決める：`mimeType`・`width`・`height` は、ファイルの中身から読んだ値にする。申告されたMIMEタイプと拡張子は使わず、中身と食い違うときは、アップロードのときに警告する。形式はファイルの先頭のバイト列から決め、PDFは `%PDF-` と版（`1.7` など）で始まるファイルだけにする（前に空白などがあるものは不可）。中身を読む処理は、外部のライブラリに頼らず実装した（`internal/mediafile`）。JPEG・PNG・GIFの大きさはGoの標準ライブラリで、WebPのヘッダーとEXIFは自前で読み、画像のデータは展開しない。メディアの文書の検証では、ファイルを読まない（値がファイルと合うかは確かめない）。
- 向き：EXIFの向き（Orientation）は、JPEGではSOFより前でEXIFを含む最初のAPP1、PNGでは最初のIDATより前のeXIfチャンク、WebPでは拡張形式（VP8X）でEXIFがあると示されているときの最初のEXIFチャンクから読む。IFD0の向き（SHORTの値1つで、1〜8）だけを使い、無いときと正しくないときは1（そのまま）にして、エラーにはしない。向きが5〜8（縦と横が入れ替わるもの）なら、ファイルの幅と高さを入れ替えて `width`・`height` にする。向きを探すのは、JPEGとPNGではファイルの先頭の128KiB、WebPではEXIFチャンクの先頭の64KiBの中だけで、それより後ろにある向きと、XMPに書かれた向きは読まない（6.12の48）。GIFには向きが無い。
- ハッシュで指す：ファイルは中身のハッシュ（`hash`）で保存して指す（3.2）。本文などからはメディアのIDで参照する（6.2）ので、ファイルを差し替えても参照はそのままで、変わるのはメディアの `hash` などだけ。同じ中身のファイルは1つだけ保存すればよく、差し替える前のファイルを上書きしないので、前のリリース（4.2）が使うファイルも残せる（使われなくなったファイルの回収は3.3）。
- ファイル名：`fileName` はアップロードしたときの名前で、拡張子が形式と違っても付け替えない（公開するファイルの拡張子は形式から付ける。下記）。保存するときの名前には使わず（ファイルは `hash` で保存する）、公開するURLに使うかは6.12の41。正規化では、制御文字（改行の `\n`・`\r` とタブも）を取り除き、前後の空白（全角スペースも）を除いてから、NFCをかける。`/`・`\` と、Unicodeの双方向の書式文字（Bidi_Control。U+061C、U+200E、U+200F、U+202A〜U+202E、U+2066〜U+2069。拡張子を偽装できるため）を含むものと、`.`・`..` という名前は使えない。制御文字や前後の空白を含むものと、NFCでないものも、検証ではエラーにする。長さはUTF-8で255バイトまで。拡張子は無くてもよく、日本語や絵文字も使える。WordPressの旧URLからの転送は、NFCにそろえた `fileName` ではなく、WXRに書かれたままのパスから作る（6.10.1）。
- 上限：1つのファイルは64MiBまで（画像もPDFも）、画像は幅×高さが1億画素まで（6.7）。
- 原本と公開：アップロードしたファイル（原本）はそのまま保存し（`hash` は原本のもの）、画像の原本は公開しない。公開する画像はビルドで原本から作り直し、EXIFの向きを画素に反映して、位置情報などのメタデータを含めない（作り直し方は6.12の42・45・46）。縮小版やWebPなどの派生ファイルはモデルに持たず、ビルド時にハッシュをキーにして生成・キャッシュする。公開するファイルの拡張子は、`fileName` ではなく形式から付ける（Nginxなどは拡張子からContent-Typeを決めるため）。PDFはそのまま公開する（作成者などのメタデータも残る。扱いは6.12の43）。
- 描画に使う `alt`：画像ブロックが `decorative` なら空にする。そうでなければブロックの `alt` を、それも無ければ（取り込んだ画像など。6.5.4）、メディアの `alt` のうちそのページの言語の値を使う（ほかの言語の値は代わりに使わない。6.3）。どれも無いときは、`alt` の属性を付けずに描画して、警告する（6.5.4）。メディアの `alt` があるときに画像ブロックの `alt` を省けるようにするかは、6.12の19。

#### 6.6.3 著者プロフィール

- 公開される著者の情報で、ログインアカウント（管理ユーザー）とは別のもの（6.3）。著者ページのURL（サイト設定の `authorUrl` の規則で、既定は `/author/{slug}/`。6.6.8）を維持するためにも使う。

著者プロフィールの項目（案）：

| 項目 | 値 | 必須 |
| --- | --- | --- |
| `id` | 著者プロフィールのID（6.7） | ○ |
| `name` | 1行テキスト（表示する名前。言語で分けない） | ○ |
| `slug` | スラッグ（6.4.2と同じ規則）。著者ページのURLに使う。サイト内で一意 | ○ |
| `bio` | 言語ごとの値（6.3）で、複数行テキスト（装飾なし） | |
| `avatar` | 画像のメディア参照 | |
| `links` | SNSのプロフィールなどの、`http`・`https` のURLの列。`href` の規則（6.5.2）に従う（NFCはかけない）。同じURLは1回まで。書いた順に表示し、構造化データ（6.8）の `sameAs` にも使う。サービスの種類（アイコン）は持たず、描画のときにURLのホストから判断する | |

規則（案）：

- ターム（6.6.1）と同じく、`schemaVersion` つきの1つのJSONの文書にし（例は6.11.4）、状態とリビジョンに分けず、下書き・公開の状態も持たない。必須の項目は保存のたびに確かめる。スラッグの一意性は、複数のエンティティにまたがる検証で扱う（6.7）。
- ログインアカウントとの紐付け：アカウントの側（7.2）にプロフィールのIDを持たせ、プロフィールの文書には持たない（公開する情報に、認証に関わる情報を入れないため。6.3）。複数のアカウントで1つのプロフィール（「編集部」など）を使え、アカウントを消しても、プロフィールと、それを `author` で参照するエントリーは変わらない。

#### 6.6.4 メニュー

- ヘッダー・フッターなどのナビゲーション。リンクの項目を木構造で持つ。
- 1つの言語版を1つのメニューとする。ページには、そのページの言語のメニューのうち、表示場所（テーマが定義する `header`・`footer` など。テーマの設定ファイルの `locations`。5.4.2）が合うものを表示する。言語版どうしは表示場所と言語の組で対応するので、エントリーやタームと違い、翻訳グループでは結ばない（案）。その言語のメニューが無い表示場所には、ほかの言語のメニューを代わりに表示しない（6.4.5と同じ）。

メニューの項目（案）：

| 項目 | 値 | 必須 |
| --- | --- | --- |
| `id` | メニューのID（6.7） | ○ |
| `title` | 1行テキスト（管理画面での名前） | ○ |
| `location` | 表示場所の名前（6.7の名前の規則）。省くと、どこにも表示しない | |
| `language` | サイト設定にある言語コード（6.4.5） | ○ |
| `items` | 項目（下記）の列 | |

項目（`items`）の値（案）：

| 項目 | 値 |
| --- | --- |
| `label` | 1行テキスト（表示する文字）。`entry`・`term` の項目では省ける（下記） |
| `entry` | 行き先のエントリーのID |
| `term` | 行き先のタームのID（タームの一覧ページへのリンクになる） |
| `href` | 行き先のURL。6.5.2の `href` の規則に従う（`mailto`・`tel` も可） |
| `newTab` | 真偽値（新しいタブで開く。省略は `false`）。行き先のある項目だけに書ける |
| `children` | 子項目の列 |

規則（案）：

- ターム（6.6.1）と同じく、`schemaVersion` つきの1つのJSONの文書にし（例は6.11.6）、状態とリビジョンに分けず、下書き・公開の状態も持たない。必須の項目（`id`・`title`・`language`）は、保存のたびに確かめる。
- 行き先：`entry`・`term`・`href` のうち多くても1つ。行き先の無い項目は、子項目をまとめる見出し（リンクにしない）で、子項目が要る（WordPressで、URLを `#` にしたカスタムリンクに当たる）。行き先のある項目も、子項目を持てる。
- `label`：省けるのは `entry`・`term` の項目だけで、省くと、行き先のエントリーのタイトルかタームの名前を表示する（WordPressでも、ラベルが空の項目は行き先のタイトルを表示する）。`href` の項目と見出しには、`label` が要る。
- 行き先の言語は問わない。リンク（6.4.5）と同じく、ほかの言語のエントリーも、ほかの言語のタームも指せる（言語を切り替えるリンクなど）。エントリーのタイプとタームのタクソノミーも問わない。存在するかは、照会の関数で確かめる（6.7）。公開していないエントリー（下書きなど）を指す項目は、ビルドで警告して表示しない。
- 表示場所：`location` は、名前の書式（6.7）だけを確かめ、テーマの `locations`（5.4.2）にあるかは確かめない（6.5.3のプリセット名と同じ。テーマを替えても、メニューは読み込める）。テーマに無い表示場所のメニューは、ビルドで警告して表示しない（6.2の4）。同じ言語・同じ表示場所のメニューは1つまでにする（複数のエンティティにまたがる検証で扱う。6.7）。
- 上限：入れ子の深さは8段（最上位の項目が1段目）、項目は1つのメニューで1000個（子項目も数える）まで。ブロックと同じく、JSONの読み込みでも確かめ、超えたところで読むのをやめる（6.7。値の見直しは6.12の9）。
- 見せ方（何段目までを表示するか、子項目をどう開くかなど）は、テーマが決める。項目には、CSSクラスや説明などの属性と、リンク（6.5.2）の `anchor`・`rel` は持たない（6.12の50）。

#### 6.6.5 フォーム

- お問い合わせフォームの定義。言語では分けず（6.3）、項目のラベル（同意の文を含む）、選択肢の表示名、送信ボタンの文字、送信後のメッセージを言語ごとの値で持つ。送信後に表示するページとプライバシーポリシーも、言語ごとにエントリーを指す。
- 本文には `form` ブロック（6.5.4）で置き、どの言語のページでも同じフォームを使う（表示する文字は、ページの言語の値）。
- フォームの定義は公開時に書き出し、お問い合わせのプロセスはそれだけを読む（管理用のDBには触れない）。送られた内容の受け付け・保存・通知は8章で扱う。

フォームの項目（案）：

| 項目 | 値 | 必須 |
| --- | --- | --- |
| `id` | フォームのID（6.7） | ○ |
| `title` | 1行テキスト（管理画面での名前） | ○ |
| `fields` | 入力の項目（下記）の列 | ○ |
| `submitLabel` | 言語ごとの値（6.3）で、1行テキスト。送信ボタンの文字 | ○（サイトのすべての言語で） |
| `message` | 言語ごとの値（6.3）で、複数行テキスト（装飾なし）。送信した後に表示するメッセージ | ○（言語ごとに、`thanksPage` とどちらか1つ） |
| `thanksPage` | 言語ごとの値（6.3）で、その言語のエントリーのID。送信した後に表示するページ（サンクスページ） | ○（言語ごとに、`message` とどちらか1つ） |
| `notify` | 送られた内容を通知するメールアドレス（6.7）の列。同じアドレスは1回まで | |

入力の項目（`fields`）の定義（案）：

| 項目 | 使える型 | 値 |
| --- | --- | --- |
| `name` | すべて | 名前（必須）。6.7の名前の規則に従い、ASCIIの英字で始める。フォームの中で一意 |
| `type` | すべて | 下の表の型（必須） |
| `label` | すべて | 言語ごとの値（6.3）で、1行テキスト（必須。サイトのすべての言語で要る）。`consent` では同意の文 |
| `required` | `consent` 以外 | 真偽値（省略は `false`）。入力を必須にする（`consent` は常に必須） |
| `minLength`、`maxLength` | `text`、`textarea` | 1以上の整数。入力の文字数（コードポイントで数える。6.12の33）の下限と上限で、`minLength` は `maxLength` 以下 |
| `options` | `select`、`radio`、`checkbox` | 選択肢の列（必須）。選択肢の `value` は言語で分けない1行テキストで、送られた値として保存し、通知する（項目の中で一意）。`label` は言語ごとの値（6.3）で、1行テキストの表示名（サイトのすべての言語で必須） |
| `policy` | `consent` | 言語ごとの値（6.3）で、その言語のプライバシーポリシーのエントリーのID |

項目の型（案。Contact Form 7 からの取り込みは6.10.1）：

| 型 | 内容 | Contact Form 7 のタグ |
| --- | --- | --- |
| `text` | 1行のテキスト | `text` |
| `email` | メールアドレス | `email` |
| `tel` | 電話番号 | `tel` |
| `textarea` | 複数行のテキスト | `textarea` |
| `select` | ドロップダウンで、選択肢から1つを選ぶ | `select` |
| `radio` | ラジオボタンで、選択肢から1つを選ぶ | `radio` |
| `checkbox` | チェックボックスで、選択肢からいくつでも選ぶ（選択肢が1つなら、1つのチェックボックス） | `checkbox` |
| `consent` | 個人情報の取り扱いなどへの同意。常に必須で、プライバシーポリシーへのリンクを付けられる | `acceptance` |

規則（案）：

- ターム（6.6.1）と同じく、`schemaVersion` つきの1つのJSONの文書にし（例は6.11.8）、状態とリビジョンに分けず、下書き・公開の状態も持たない。必須の項目は保存のたびに確かめる（`required` にした入力の項目に値があるかは、送られたときに確かめる。8章）。
- 送信後の表示：サイトの言語ごとに、`message` か `thanksPage` のちょうど1つを書く。言語ごとに違ってよい（例：日本語はメッセージ、英語はサンクスページ）。
- 言語ごとのエントリー：`thanksPage` と `policy` は、キーと同じ言語のエントリーだけを指せる（タイプは問わない）。存在と言語は、照会の関数で確かめる（6.7）。`policy` は任意で、書いた言語のページだけでリンクを付ける。
- 同意：`consent` の項目では、同意の文（`label`）と、プライバシーポリシーへのリンク（文字はそのページのタイトル）を表示する。並べ方はテーマが決める（本体の既定のテンプレートは、下記の描画のとおり）。
- 書式は型で決める。正規表現の書式（`pattern`）・説明・プレースホルダーは持たない（6.12の51）。送られた値は、お問い合わせの処理が型に従って確かめる（8章）。`email` の項目の値は、通知先と同じ規則で確かめる（6.7）。
- 定義の検証：型が使わない項目（`text` の `options`、`consent` の `required` など）はエラーにする。
- `notify`：お問い合わせのプロセスだけが使い、公開するHTMLには出さない。省けば、メールでは通知しない（送られた内容は保存し、管理画面で確かめる。8.2）。通知のメールの件名・本文と、送った人への自動返信は、8章で決める（6.12の52）。
- 上限：項目は1つのフォームで100個、選択肢は1つの項目で1000個、通知先は10個まで。メニュー（6.6.4）と違い、検証だけで確かめる（6.7。値の見直しは6.12の9）。
- 迷惑送信の対策は、フォームの定義には持たず、お問い合わせの処理がすべてのフォームで行う（8.2）。そのための項目と、ページの言語を送る `_language`（下記の描画）に、本体が `_` で始まる名前を使うので、項目の名前は英字で始める。

描画（案）：

- `form` ブロックは、フォームの定義から、ページの言語の文字でHTMLにする（本体の既定のテンプレート。テーマは `blocks/form.html` で変えられる。5.4.4）。6.11.8のフォームを、日本語のページで描画したもの（プライバシーポリシーのページは、パスを `/privacy/` とした）：

```html
<form action="/_forms/frm_01JB8Z3K5VP1D4G7J2M5Q8T3W6" method="post">
<input type="hidden" name="_language" value="ja">
<p><label>お名前<br><input type="text" name="your-name" required maxlength="100"></label></p>
<p><label>メールアドレス<br><input type="email" name="your-email" required></label></p>
<p><label>電話番号<br><input type="tel" name="your-tel"></label></p>
<fieldset>
<legend>ご用件</legend>
<label><input type="radio" name="topic" value="quote" required>お見積もり</label>
<label><input type="radio" name="topic" value="recruit" required>採用について</label>
<label><input type="radio" name="topic" value="other" required>その他</label>
</fieldset>
<p><label>お問い合わせ内容<br><textarea name="your-message" required maxlength="2000"></textarea></label></p>
<p><label><input type="checkbox" name="privacy" required>個人情報の取り扱いに同意する</label> <a href="/privacy/">プライバシーポリシー</a></p>
<p><button type="submit">送信</button></p>
</form>
```

- 送り先：`action` は `/_forms/<フォームのID>` で、ほかのリンクと同じく、サイトのURLのパスを前に付ける（`https://example.com/blog` のサイトでは `/blog/_forms/…`。6.5.2）。`method` は `post`。隠しの項目 `_language` で、ページの言語を送る。このパスも、ビルドで、出力パスの重複（4.1）の検査に加える（リダイレクトの `from` などと重ならないように）。受け付ける処理は8章（6.12の86）。
- 入力欄：`<label>` の中に、項目の `label` と入力欄を置く（入力欄に `id` を付けないので、アンカーと重ならない）。`text`・`email`・`tel` は `<input>`（`type` は項目の型）、`textarea` は `<textarea>`、`select` は `<select>`（Contact Form 7 と同じく、空の選択肢は置かない）。`radio` と `checkbox` は、`<fieldset>` の中に、`label` の `<legend>` と、選択肢ごとの `<label>` を並べる。`consent` は、`value` の無いチェックボックス（ブラウザーは `on` を送る）と同意の文の `<label>` で、プライバシーポリシーへのリンクは、その後ろに置く（`policy` の無い言語では付けず、そのページが無いときと、公開していないときは、警告して付けない）。
- 必須：`required` の項目の `text`・`email`・`tel`・`textarea`・`select` と、`radio` のすべての選択肢に、`required` の属性を付ける。`required` の `checkbox` には、選択肢が1つのときだけ付ける（HTMLでは、いくつかのうち1つ以上を選ぶことを必須にできないので、お問い合わせの処理だけが確かめる。6.12の86）。`consent` には、いつも付ける。
- 文字数：`minLength`・`maxLength` は、`minlength`・`maxlength` の属性にする（数え方の違いは6.12の33）。
- 送信ボタン：`<button type="submit">` で、文字は `submitLabel`。
- 文字の無い言語：ページの言語の値が無い `label`・選択肢の `label`・`submitLabel`（サイトに言語を足して、まだ訳していないものなど）は、空の文字にして、警告する。

#### 6.6.6 リダイレクト

- 旧URLから新しいURLへの転送。言語では分けない（6.3）。
- 公開済みエントリーのスラッグを変えたときと、WordPressから取り込んだときに自動で登録する（6.4.2・6.10.4）。
- 内蔵サーバーで処理するほか、Nginx・Apache（`.htaccess`）向けの設定も書き出せるようにする。

リダイレクトの項目（案）：

| 項目 | 値 | 必須 |
| --- | --- | --- |
| `id` | リダイレクトのID（6.7） | ○ |
| `from` | 転送の元。`/` で始まるサイト内のパスで、`/?p=123` のようなクエリつきも可。正規の形（下記）で持つ | ○ |
| `to` | 転送の先。エントリー・ターム・著者プロフィール・メディアのID、`/` で始まるサイト内のパス、`http`・`https` のURL（ほかのサイトも可） | ○ |
| `status` | `301`（恒久的な転送）か `302`（一時的な転送） | ○ |

規則（案）：

- ターム（6.6.1）と同じく、1つのリダイレクトを `schemaVersion` つきの1つのJSONの文書にし（例は6.11.7）、状態とリビジョンに分けず、下書き・公開の状態も持たない。項目はすべて必須で、保存のたびに確かめる。
- 行き先のID：ビルドで、そのエンティティのURL（エントリーのページ、タームの一覧ページ、著者ページ、公開するメディアのファイル。エントリー・タームの一覧・著者ページのパスは6.6.8で求める）に変える。スラッグなどが変わっても、行き先が古くならない（URLで書くと、古いままになる）。自動で登録するリダイレクトは、行き先をIDで持つ。メディアは画像もPDFも指せる。行き先が存在するかは、照会の関数で確かめる（6.7）。行き先のエントリーを公開していないとき（下書きなど）は、ビルドで警告して、そのリダイレクトを出力しない。行き先のエンティティを消したときの扱いは6.12の40、メディアの公開URLの形は6.12の41、言語ごとにある著者ページ（6.6.8）のどれへ転送するかは6.12の39。
- `to` の書き方：`/` で始まるか `:` を含むものはURLとして、6.5.2の `href` の規則で確かめ、サイト内のパスと `http`・`https` だけを受け付ける（リンクと違い、`mailto`・`tel` は使えない）。ほかはIDとして、接頭辞（`ent_`・`trm_`・`aut_`・`med_`）で種類を決め、ほかの種類のIDや `about/` のような文字列はエラーにする。正規化では、URL（6.7）と同じく制御文字と前後の空白を取り除くだけで、正規の形にはしない。
- `from` の正規の形：書き方の違い（パーセントエンコードの有無、16進の大文字と小文字、クエリの順序）をなくした形。正規化でこの形にし、検証では、この形でないものをエラーにする。
  - パーセントエンコードは、ASCIIの非予約文字（英数字と `-`・`.`・`_`・`~`）と、表示できるASCII以外の文字（文字・結合文字・数字・句読点・記号。Unicodeの一般カテゴリーのL・M・N・P・S）では戻し（例：`/%E4%BC%9A%E7%A4%BE/` は `/会社/`）、ほかは16進を大文字にして残す。
  - 空白（全角スペースも）、書式文字（双方向の上書きなど）、私用文字、未割り当ての文字は、エンコードした形にする（エンコードされていなければエンコードする）。UTF-8として正しくないバイト列（`%FF` など）と、ASCIIの `"`・`<`・`>`・`[`・`]`・`^`・`` ` ``・`{`・`|`・`}` も同じ。
  - `/`・`?`・`&`・`=`・`+`・`,` などの区切りの文字は、エンコードしたものとしないものを別のものとして扱う（`%2F` と `/`、`%2B` と `+` は違う）。`+` を空白（`%20`）とも見なさない。クエリの `'` は、ブラウザーと同じく `%27` にする（パスではそのまま）。
  - NFCはかけない（6.5.2と同じく、NFDで書かれたファイル名の旧URLと合わなくなるため）。大文字と小文字と、末尾の `/` は書いたままにする。
  - クエリのパラメーターは、名前（最初の `=` より前）の順に並べ、空のパラメーター（`&&` の間など）と空のクエリ（末尾の `?`）を除く。
- `from` に書けないもの：`/` で始まらないもの（`https://…` のURLも）、`//` で始まるもの、`\` を含むもの、`#` を含むもの（ブラウザーは `#` 以降を送らない）、正しくないパーセントエンコード（`/100%` のように、`%` の後に16進2桁が無いもの）、`.` と `..` の区切り（`%2E` で書いたものも）、名前の空のパラメーター（`/?=1`）、同じ名前のパラメーター（`/?a=1&a=2`。`a` と `a=1` も同じ名前）。
- 照合：リクエストのパスとクエリ（ブラウザーが送る、パーセントエンコードされた形）も正規の形にして、`from` と比べる。大文字と小文字は区別し（`/About/` は `/about/` に一致しない）、NFCとNFDも区別する。末尾の `/` の有無は区別しない（`/about/` は `/about` にも一致する）。パスが違えば、クエリが同じでも一致しない（`/?p=123` は `/index.php?p=123` に一致しない）。リクエストの `#` 以降は無視する。
- クエリの照合：`from` のパラメーターが、どれも同じ文字列でリクエストにあれば一致し（`a` と `a=` は別）、リクエストの余分なパラメーター（`utm_source` など）は無視する。クエリの無い `from` は、どのクエリにも一致する。複数のリダイレクトが一致したときは、パラメーターの多いものを、同じ数なら `from` の文字列の順で先のものを使う。リクエストのクエリは、行き先に付けない（6.12の55）。
- 自分自身への転送（`to` のサイト内のパスに、`from` が一致するもの。`/about/` から `/about` や `/about/?ref=top` への転送など）は、エラーにする。`to` がサイトのURL（6.6.8）の中の `http`・`https` のURLのときも、サイトのURLからのパスにして同じく確かめる（`https://example.com/blog` のサイトでは、`https://example.com/blog/about/` は `/about/`）。サイトの中とみなすのは、スキームとホストが大文字と小文字を区別せずに同じで、ポートが数として同じ（書かないものは既定の番号）で、パスがサイトのURLのパスか、その下のもの（`from` の正規の形にして比べる）。サイトのURLが正しくないときは、URLを比べない。ホストの別名（`www.` の付くものなど）は、ほかのサイトとみなす。リダイレクトのループ、`from` の重複と、出力するパスとの重複（4.1）は、複数のエンティティにまたがる検証で扱う（6.7）。重複は、照合と同じく末尾の `/` を除いて比べる（クエリつきの `from` は、同じパスのページとは重ならない）。
- `status`：`301` と `302` だけ。整数の属性（6.7）と同じく、読み込みでも確かめる（`0` は省略と区別できないため）。`307`・`308` は、メソッド（POSTなど）を変えずに転送する点だけが `302`・`301` と違い、静的に公開するページへのリクエストはGETなので、持たない。転送ではなく、ページが無くなったことを返す `410` は、アーカイブしたエントリーのURLの扱いとあわせて決める（6.12の7）。

#### 6.6.7 共有ブロック（段階2）

- `id`、`language`、`translationGroup`、`title`、`body`（ブロックの列）。
- 共有ブロックの中から別の共有ブロックを呼ぶことは禁止する（循環を防ぐため）。

#### 6.6.8 サイト設定

- サイト全体の設定。一般設定・言語・トップページと一覧・URLの規則・SEOの既定値と、タイプ・タクソノミー・フィールドの定義（6.4.4）を持つ。`html` ブロックを有効にするか（`allowHtml`。6.5.4）も持つ。
- 2つのファイルに分けて持つ（案）。管理画面で変える項目は、設定の文書（エントリーなどと同じJSONの文書。6.9）に持つ。その保存先は、エントリーなどと合わせて決める（6.12の1。12章の論点2・3）。開発者が書く項目（`authorUrl`・`taxonomies`・`types`）は、スキーマのファイル（`site/schema.yaml`。YAMLで書く）に持つ。どちらの形も下記。下書き・公開の状態は持たず、必須の項目は検証のたびに確かめる。
- 分ける理由：管理画面の項目には、メディアや固定ページのIDを指すもの（`logo`・`frontPage` など）があるので、それらのコンテンツと一緒に保存するのがよい。スキーマを変えると、保存済みのコンテンツが検証を通らなくなることがあり（6.9）、URLの規則を変えると、公開済みのページのURLが変わる（6.12の60）。そこで、どちらも開発者がファイルで管理する。本体はスキーマのファイルを読むだけで書き換えないので、ファイルに書いたコメントも消えない。WordPressでは、パーマリンク設定は管理画面にあり、カスタム投稿タイプはコードで登録する（このCMSでは、URLの規則も、タイプの定義と一緒にスキーマのファイルに書く）。

サイト設定の項目（案）：

| 項目 | 値 | 必須 | 置き場所 |
| --- | --- | --- | --- |
| `name` | 言語ごとの値（6.3）で、1行テキスト（サイト名） | ○（サイトのすべての言語で） | 設定の文書 |
| `tagline` | 言語ごとの値（6.3）で、1行テキスト（キャッチフレーズ） | | 設定の文書 |
| `url` | サイトのURL（例：`https://example.com`、`https://example.com/blog`。規則は下記） | ○ | 設定の文書 |
| `timeZone` | タイムゾーンのIANAの名前（例：`Asia/Tokyo`、`UTC`。規則は下記） | ○ | 設定の文書 |
| `logo`、`icon` | 画像のメディア参照（ロゴと、サイトアイコン） | | 設定の文書 |
| `languages` | 使う言語の言語コード（6.4.5）の列。同じ言語は1回まで | ○ | 設定の文書 |
| `defaultLanguage` | 既定の言語。`languages` の1つ | ○ | 設定の文書 |
| `prefixDefaultLanguage` | 真偽値（既定の言語にも言語のパスを付ける。省略は `false`。下記） | | 設定の文書 |
| `frontPage` | 言語ごとの値（6.3）で、その言語のトップページにする固定ページのID（下記） | | 設定の文書 |
| `postsPage` | 言語ごとの値（6.3）で、その言語の投稿の一覧を出力する固定ページのID（下記） | | 設定の文書 |
| `postsPerPage` | 1〜100の整数（一覧の1ページの件数。省略は10。下記） | | 設定の文書 |
| `authorUrl` | 著者ページ（6.6.3）のURLの規則（省略は `/author/{slug}/`。下記） | | スキーマのファイル |
| `seo` | SEOの既定値で、`titleFormat`・`ogImage`・`noindex` を持つ（下記） | | 設定の文書 |
| `allowHtml` | 真偽値（`html` ブロックを有効にする。省略は `false`。6.5.4） | | 設定の文書 |
| `taxonomies`、`types` | タクソノミーとタイプの定義（6.4.4）。URLの規則（`url`）と、カスタムタイプの一覧のパス（`archive`）も書く（下記） | | スキーマのファイル |

規則（案）：

- 言語ごとの値（6.3）：`name` は、サイトのすべての言語で要る（訳さないサイト名も、言語ごとに書く。6.12の37）。ほかの言語ごとの値（`tagline`・`frontPage`・`postsPage`・`seo.titleFormat`・`seo.ogImage`）は、書いた言語の値だけを持てばよい。欠けた言語で、ほかの言語の値を代わりに使うことはしない（6.3）。
- サイトのURL（`url`）：`href` の規則（6.5.2）に従う `http`・`https` のURL。スキームとホストは小文字で書き、ホストはASCIIだけにする（国際化ドメイン名は `xn--` の形。メールアドレスと同じ。6.7）。ポートは書かなくてよく、書くときは1〜65535で、既定の番号（`http` の80、`https` の443）は書かない。パスも書ける（サブディレクトリに置くサイト。`https://example.com/blog`）。パスにはASCII以外の文字も使えるが、空の区切りと `.`・`..` の区切り（`%2E` で書いたものも）は書けない。`/` で終わるもの（`https://example.com/` も）と、クエリ・フラグメント・認証情報を含むものは不可。ホストがドメイン名として正しいか（`-` で始まるラベルや、末尾の `.` など）は、いまは確かめない。出力するパス（下記）は、このURLからのパスにする（`https://example.com/blog` のサイトの `/about/` は、`https://example.com/blog/about/`）。リダイレクトの自分自身への転送の検査にも使う（6.6.6）。
- タイムゾーン（`timeZone`）：IANAのタイムゾーンデータベースの名前（`Asia/Tokyo`、`UTC`、`America/New_York` など）。名前の形（英数字と `+`・`-`・`_` からなる部分を `/` で区切ったもの）と、Goの `time.LoadLocation` で読めることを確かめる。`Local`（動かすマシンのタイムゾーン）と、`+09:00` のような時差は書けない。時刻のデータ（Goの `time/tzdata`）を本体に埋め込むので、データの無いシステムでも同じ名前を受け付ける。ただし、システムにデータがあればそちらを先に使うので、受け付ける名前と時差の規則が、システムによって違うことがある（6.12の57）。日時の表示と、管理画面で入力する日時に付ける時差に使い、URLの日付には使わない（下記）。
- ロゴとサイトアイコン（`logo`・`icon`）：画像のメディアだけを指せる（照会の関数で確かめる。6.7）。大きさ（サイトアイコンが正方形かなど）は確かめない（6.12の58）。
- 言語のパス：各言語のページは、言語のパスの下に置く。言語のパスは、言語コードを小文字にしたもの（`/en/`。`en-US` は `/en-us/`、`zh-Hant` は `/zh-hant/`）。既定の言語には付けない（`/`）。`prefixDefaultLanguage` が `true` なら、既定の言語にも付ける（`/ja/`。そのときに `/` に何を出力するかは6.12の59）。URLの規則（下記）はすべての言語で共通で、言語のパスの後ろに続く（英語の固定ページで、スラッグが `about` のものは `/en/about/`）。規則を言語ごとに変えるかと、言語のパスを言語コードと違うもの（`/tw/` など）にできるようにするかは6.12の30、言語ごとに別のドメインを使うかは6.12の2。
- トップページ（`frontPage`）：言語のパスに出力するページ。`frontPage` の無い言語では、その言語の最新の投稿の一覧を出力する。`frontPage` と `postsPage` は、キーと同じ言語の固定ページだけを指せる（照会の関数で確かめる。6.7）。`frontPage` の固定ページは言語のパスに出力し、規則のパス（既定の `/{path}/` で、スラッグが `home` なら `/home/`）には出力しない。その子の固定ページは、規則のとおりのパスに出力する（`/home/child/`）。規則のパスから転送するかと、`frontPage` を変えたときの旧URLの扱いは6.12の60。
- 投稿ページ（`postsPage`）：WordPressの「投稿ページ」（`page_for_posts`）に当たる。`frontPage` のある言語でだけ、`frontPage` と別の固定ページを指定できる。そのページのパス（`/news/` など）に、その言語の投稿の一覧を出力する（固定ページの本文を一覧と一緒に出すかは、テーマが決める）。固定ページの規則が `.html` で終わるサイトでは使えない（一覧のパスにページ送りを足すため）。`frontPage` があって `postsPage` の無い言語には、投稿の一覧のページが無い（タームの一覧などはある）。
- ページ送り：一覧（トップページの最新の投稿・投稿ページ・タームの一覧・タイプの一覧・著者ページ）の1ページの件数は、どれも `postsPerPage`（省略は10で、WordPressの既定と同じ）。2ページ目からは、一覧のパスの後ろに、`page/` とページの番号と `/` を続ける（`/page/2/`、`/category/news/page/2/`、`/en/page/2/`。WordPressのページ送りと同じ形）。1ページ目は一覧のパスのままで、`page/1/` は作らない。日付のアーカイブやフィードなど、ほかの一覧は6.12の39。
- タイトルの書式（`seo.titleFormat`）：言語ごとの値（6.3）で、ページのタイトル（`<title>`）の書式。1行テキストで、`{title}`（ページのタイトル）をちょうど1つ、`{siteName}`（その言語の `name`）を多くても1つ書く。`{` から次の `}` までを置き換えとみなすので、ほかの名前（大文字小文字も区別し、`{Title}` も不可）と、対にならない `{`・`}` は書けない（`{`・`}` を文字として書く方法は無い）。無い言語では、本体の既定の書式 `{title} | {siteName}` を使う。トップページ（最新の投稿の一覧にはタイトルが無い）や、2ページ目からの一覧で、書式をどう使うかは6.12の61。
- 既定のOGP画像（`seo.ogImage`）と `seo.noindex`：`seo.ogImage` は、言語ごとの値（6.3）で、画像のメディア参照（照会の関数で確かめる。6.7）。OGPの画像を持たないページ（6.4.2の `seo.ogImage` も `featuredImage` も無いエントリーなど）に使う。`seo.noindex` は、言語では分けない真偽値。`true` にすると、すべての言語のすべてのページを、検索エンジンに載せないようにする（公開前の確認用）。
- 見た目の直接指定を使えるロール（6.5.3の「サイト設定で決められること」）は、ロールの権限モデル（7章）と合わせて決めるので、いまはサイト設定に持たない（6.12の62）。

URLの規則は、エントリー・タームの一覧・著者ページのパスを、置き換え（`{slug}` など）を含む形で書いたもの（案。6.4.4の例の `url: /works/{slug}/`）。エントリーの規則はタイプごとに、タームの一覧の規則はタクソノミーごとに `url` に書き、著者ページの規則は `authorUrl` に書く。どれも、スキーマのファイルに書く。省いたものには、既定の規則（下記）を使う。どの規則も、言語のパスの後ろに続く（上記）。

置き換え（案）：

| 置き換え | 値 | 使える規則 |
| --- | --- | --- |
| `{slug}` | スラッグ（エントリーは6.4.2、タームは6.6.1、著者プロフィールは6.6.3） | すべて |
| `{path}` | 最上位の祖先から順に、祖先と自分のスラッグを `/` でつないだもの（親が `about` の `access` は `about/access`） | 固定ページと、階層ありのタクソノミー（`category` など） |
| `{number}` | エントリーの `number`（6.4.1） | エントリー（すべてのタイプ） |
| `{yyyy}`、`{mm}`、`{dd}` | 投稿の `date` の年（4桁）・月（2桁）・日（2桁）。`date` に書いた時差で数える（下記） | 投稿 |
| `{category}` | `terms` の `category` の最初のタームの、`{path}` と同じ形のパス（`news/press-release`。下記） | 投稿と、`category` を使うカスタムタイプ（6.4.4） |

置き換えは、この7つだけ。WordPressのパーマリンク設定のタグとの対応は6.10.4、持たないタグを足すかは6.12の63。

既定の規則（案。WordPressの列は、パーマリンク設定を「日付と投稿名」にしたときに同じURLになるもので、ほかの設定との対応は6.10.4）：

| 対象 | 書く項目 | 省いたときの規則 | WordPress |
| --- | --- | --- | --- |
| 投稿（`post`） | `types` の `url` | `/{yyyy}/{mm}/{dd}/{slug}/` | 「日付と投稿名」（`/%year%/%monthnum%/%day%/%postname%/`）。新しいサイトで試す設定 |
| 固定ページ（`page`） | `types` の `url` | `/{path}/` | 固定ページのURL（祖先のスラッグを前に付ける） |
| カスタムタイプ | `types` の `url` | `/{slug}/` の前にタイプの名前（`works` は `/works/{slug}/`） | カスタム投稿タイプの既定（`rewrite` の `slug` が投稿タイプの名前） |
| カスタムタイプの一覧 | `types` の `archive` | なし（一覧を出力しない） | カスタム投稿タイプの既定（`has_archive` が `false` で、一覧が無い） |
| カテゴリー（`category`） | `taxonomies` の `url` | `/category/{path}/` | カテゴリーベースが空（既定）のとき。祖先のスラッグを含む |
| タグ（`tag`） | `taxonomies` の `url` | `/tag/{slug}/` | タグベースが空（既定）のとき |

| 著者ページ | `authorUrl` | `/author/{slug}/` | 投稿者のページ（`author/%author%`） |

規則の書き方（案）：

- 始まりと終わり：`/` で始める。エントリーの規則は、`/` か `.html` で終わる（`.htm`・`.HTML` は不可。`/.html`・`/{slug}/.html` のように、`.html` の前に名前の無いものも不可）。タクソノミーと著者ページの規則と、一覧のパス（`archive`。下記）は、`/` で終わる（ページ送りの `page/2/` を足すため。上記）。
- 区切り：`/` で区切った区切りは、空にできない（`//` は不可）。`.`・`..` の区切りと、`.` で始まる区切り（`/.news/`。隠しファイルになり、Webサーバーが返さないことが多い）も書けない。
- 文字：置き換えの外に書けるのは、ASCIIの英字（大文字も）・数字・`-`・`_`・`.` と区切りの `/`、ASCII以外では文字・結合文字・数字・句読点・記号（Unicodeの一般カテゴリーのL・M・N・P・S）だけ（`/お知らせ/{slug}/` も書ける）。スラッグ（6.4.2）と違い、全角スペースは書けない。ほかの空白・制御文字・書式文字・私用文字・未割り当ての文字も書けない。ASCIIの記号も、`-`・`_`・`.` のほか（`%`・`~`・`?`・`#` など）は書けず、パーセントエンコードした形では書けない（文字をそのまま書く）。NFCで書く（NFCでないものはエラーにする）。
- 置き換えの書き方：`{` から次の `}` までを置き換えとみなし、対にならない `{`・`}` は書けない（`{`・`}` を文字として書く方法は無い）。名前は大文字と小文字も区別し、知らない名前（`{Slug}`、`{year}` など）と、その規則で使えない置き換え（置き換えの表の「使える規則」。投稿の `{path}`、固定ページの `{yyyy}` など）は書けない。同じ置き換えは1回までで、`{slug}` と `{path}` は一緒に使えない。`{path}` と `{category}` は区切りの全体に置く（`/{category}/{slug}/`。最後の区切りだけは `{path}.html` にもできる）。ほかの置き換えは、文字やほかの置き換えと同じ区切りに並べてよい（`/{yyyy}{mm}{dd}/{number}.html`、`/news-{number}/`）。
- 要る置き換え：エントリー・ターム・著者ごとにパスを分けるため、エントリーの規則には `{slug}`・`{path}`・`{number}` のどれか（`{path}` は固定ページだけ）、タクソノミーの規則には `{slug}` か `{path}`（`{path}` は階層ありのタクソノミーだけ）、著者ページの規則には `{slug}` が要る。日付だけの規則（`/{yyyy}/{mm}/{dd}/`）は書けない。
- 言語のパスとの重なり：規則は、言語のパス（`/en/` など。`prefixDefaultLanguage` が `true` なら、既定の言語の `/ja/` も）で始められない（既定の言語のページが `/en/` の下に入るなど、言語のパスと紛らわしいため）。比べるのは最初の区切りの全体で（`/english/`、`/en-{slug}/` は書ける）、大文字と小文字は区別する（言語のパスは小文字なので、`zh-Hant` のサイトでも `/zh-Hant/` は書ける）。
- 一覧のパス（`archive`）：カスタムタイプのエントリーの一覧を出力するパス（`/works/`。`/works/all/` のように区切りが2つ以上でもよい）。置き換えは書けず、`/` で始めて `/` で終わる。区切り・文字・NFC・言語のパスとの重なりは、規則と同じく確かめる。トップページのパス（`/`）にはできない。投稿と固定ページには書けない（投稿の一覧は、トップページか投稿ページに出す。上記）。
- 標準のタイプとタクソノミー：投稿と固定ページの規則は、`types` に同じ名前で書いて変える（6.4.4）。標準の `category`・`tag` も、`taxonomies` に同じ名前で書いて、`label` と `url` を変えられる。`hierarchical` は書けず、`category` は階層あり、`tag` は階層なしのまま（`category` の規則は、`hierarchical` を書かなくても `{path}` を使える）。
- 検証：サイト設定の検証では、規則ごとに、最初に見つけた問題だけを報告する。`types`・`taxonomies` に書いたタイプとタクソノミーは、名前が正しければ、`url` を省いても既定の規則を確かめる（`en` という名前のカスタムタイプは、既定の規則が `/en/{slug}/` になるので、エラーになる）。

出力するパス（案）：

- 求め方：エントリーのパスは、状態（`id`・`type`・`language`・`number`）と、公開するリビジョン（`slug`・`parent`・`date`・`terms`）から、そのタイプの規則の置き換えを埋めて求め、言語のパスの後ろに続ける（上記）。タームの一覧のパスは、ターム（`taxonomy`・`language`・`slug`・`parent`）から同じく求める。著者ページのパスは、著者プロフィールの `slug` から、サイトの言語ごとに求める。`frontPage` の固定ページは、規則を使わずに言語のパスにする（上記）。
- パスの形：求めたパスは、サイトのURL（上記）からのパスで、`/` で始まり、`/` か `.html` で終わる。パーセントエンコードはせず、日本語のスラッグもそのままにする（`/2026/10/26/新サービス/`）。リンクなどに出力するときにエンコードする（6.5.2）。
- 祖先とカテゴリー：`{path}` の祖先と、`{category}` のタームとその祖先は、IDからスラッグと親のIDを返す照会の関数で調べる。調べるのは公開中のサイトのもの（固定ページは、公開中のリビジョンのスラッグと親）。見つからないもの（照会の関数を渡さないときも同じ）、スラッグの無いものと正しくないもの、親をたどると循環するもの（自分自身を親にするものも）は、エラーにする。
- 日付：`{yyyy}`・`{mm}`・`{dd}` は、`date` に書いた時差での年・月・日（`2026-10-26T00:30:00+09:00` は、UTCでは25日だが、`2026/10/26`）。サイトのタイムゾーン（`timeZone`）には直さないので、タイムゾーンを変えても、公開済みの投稿のURLは変わらない。WordPressから取り込んだ投稿のURLの日付は6.10.4。
- カテゴリーの順序：`{category}` には `terms` の `category` の最初のタームを使うので、`category` のタームの順序に意味がある（2つ目からは、URLに使わない）。`{category}` を規則に使うタイプでは、公開（予約を含む）するときに `category` が要る（6.4.2。下書きでは確かめない）。
- 求められないとき：規則に使うスラッグ・日付・`{category}` のタームが無いものと、その書式が正しくないもの、サイト設定に無い言語・タイプ・タクソノミーのものは、エラーにする。公開（予約を含む）するリビジョンでは、スラッグと投稿の `date`（6.4.2・6.4.3）と、`category`（上記）が要るので、値が無いことは起きない。祖先が見つからないことと循環は、ほかのエンティティによって起きうる。
- 出力するファイル：`/` で終わるパスは、そのディレクトリの `index.html` に出力する（`/` は `index.html`、`/about/` は `about/index.html`、`/news/page/2/` は `news/page/2/index.html`）。`.html` で終わるパスは、そのファイルに出力する（`/archives/123.html` は `archives/123.html`）。どれも、出力先のディレクトリからの相対パス。区切りは、ファイル名の上限の255バイト（UTF-8）までで、超えるパスはエラーにする（6.4.2のとおりスラッグは200バイトまでだが、規則の文字と同じ区切りに並べると超えることがある）。出力先の外や隠しファイル（`.htaccess` のように、Webサーバーが設定として読むものもある）に書かないよう、空の区切り、`.`・`..` の区切り、`.` で始まる区切りのパスも、ここで改めてエラーにする（規則とスラッグの書き方でも防いでいる）。
- 末尾の `/`：末尾が `/` でも `.html` でもないパス（`/archives/123`）は作れない。そうしたURLを保つときは、`/` で終わる規則（`/archives/{number}/`）にする。末尾の `/` の無いURLへのリクエストは、サーバーが、ディレクトリと同じく `/` を付けたURLへ転送する（リダイレクトの照合も、末尾の `/` の有無を区別しない。6.6.6）。WordPressの「数字ベース」の取り込みは6.10.4。
- 言語ごとの一覧：カスタムタイプの一覧は、言語のパスの後ろに `archive` を続けたパスに出す。タイプの一覧と著者ページは、サイトの言語ごとに、その言語のエントリー（著者ページは、その著者の投稿）を並べて出す（`/works/`・`/en/works/`、`/author/yamada/`・`/en/author/yamada/`）。タームの一覧は、タームの言語だけに出す（タームは言語ごと。6.6.1）。その言語のエントリーが無い一覧（投稿の無い著者のページなど）も出すかは6.12の39。
- 重複と変更：出力パスの重複（4.1）は、ここで求めたパスとリダイレクトの `from` を集めて検査する（複数のエンティティにまたがる検証。6.7）。規則の検査では見つからない重なり（スラッグが `en` の固定ページの `/en/` と、英語のトップページなど）も、ここで見つける。親の固定ページやカテゴリーのスラッグ、URLの規則を変えると、ほかのエンティティのパスも変わる（旧URLの扱いは6.12の60）。

設定の文書（案）：

- 形：最上位に `"schemaVersion": 1`（6.9）と、上の表で置き場所が「設定の文書」の項目を持つ、JSONのオブジェクト（例は6.11.9）。本番とステージングで `url` を変えるなど、環境ごとに変える値をどこに持つかは6.12の68。
- 読み込み：6.7のJSONの読み込みと同じく、定義にないキー・重複したキー・`null`・空の値などをエラーにし、値は変えない。スキーマのファイルの項目（`authorUrl`・`taxonomies`・`types`）を書くと、スキーマのファイルに書くよう示すエラーにする。`postsPerPage` は、整数の属性（6.7）と同じく、読み込みでも書き方（`2.0` は不可）と範囲（1〜100）を確かめる（0は省略と区別できず、書き出すと消えるため）。
- 書き出し：キーは、`schemaVersion` の後ろに上の表の順で並べ（`seo` の中は `titleFormat`・`ogImage`・`noindex` の順）、言語ごとの値は言語コードの順（6.3）に並べて、空白を入れずに1行で書く。`false` と空の値は書かない（`seo` も、中に書くものが無ければ書かない）。省いた `postsPerPage` は書かず、書いた `postsPerPage` は、省略と同じ10でも書く。読み込んで書き出しても、値は変わらない。
- 正規化：管理画面が保存する前に行う（読み込みでは行わず、正規化していない値は検証でエラーにする。6.7）。`name`・`tagline`・`seo.titleFormat` は、1行テキスト（6.7）と同じく、制御文字を取り除いてNFCにし（改行とタブは取り除かずに、検証でエラーにする）、何も残らない言語は消す。`url` は、URL（6.7）と同じく制御文字と前後の空白を取り除き、スキームとホストのASCIIの英字を小文字にする（`HTTPS://Example.COM/Blog` は `https://example.com/Blog`。末尾の `/` や既定のポートは取り除かず、検証でエラーにする）。ID・言語コード・タイムゾーン・真偽値・数は変えない。

スキーマのファイル（案）：

- 置き場所：`site/schema.yaml` の1つのファイル（タイプごとのファイルにも分けられるようにするかは6.12の64）。
- 形：最上位に `schemaVersion: 1`（必須。6.9）を書き、`authorUrl`・`taxonomies`・`types` を書ける（最上位のキーの順は問わない）。`taxonomies`・`types`・`fields` は、キーを名前にしたマッピングで書き、書いた順に読む（管理画面での並びにも使う）。定義の項目は6.4.4のとおり（例は6.4.4・6.11.9）。エディタでの補完と検査は6.12の67。

エラーの位置（案）：

- 形：読み込みと検証のエラーには、ファイルの名前と、行と列を付け、その後ろに、エラーのある項目のJSON Pointer（RFC 6901）とエラー文を続ける（`site/schema.yaml:5:5: /types/works/url: invalid URL rule "/works/{id}/": unknown placeholder "{id}" (use {slug}, {number})`）。ファイルの名前は、読み込むときに渡す（設定の文書の名前は、保存先と合わせて決める）。設定の文書にも、JSONの行と列を付ける。
- 行と列：どちらも1から数える。列は文字（コードポイント）で数えるので、エディタの列と違うことがある。本体が書き出した設定の文書は1行なので、行はいつも1になる。
- 位置：項目のキーの最初の文字（キーの無いもの、`taxonomies: [works_category]` の `works_category` などは、値の最初の文字）。無い項目のエラーは、それを持つはずの親の位置にする（`/url: missing url` は設定の文書の最初の `{`、`/types/works/fields/client/type: missing type` は `client` のキー）。構文の誤りと、YAMLの範囲の外の書き方は、問題の文字の位置で示し、JSON Pointer を付けない。
- 振り分け：検証のエラーは、JSON Pointer の最初のキーが `authorUrl`・`taxonomies`・`types` ならスキーマのファイルに、ほかは設定の文書に付ける。原因がもう一方のファイルにあっても同じ（固定ページの規則が `.html` で終わるときの `postsPage` のエラーは、設定の文書に付く）。
- 順：どちらかのファイルを読み込めなければ、検証はせず、読み込みのエラー（ファイルごとに最初の1つ）を、設定の文書・スキーマのファイルの順に並べる。両方を読めたら、2つを合わせたサイト設定を検証し、そのエラーを検証の順に並べる（2つのファイルのものが混ざる）。
