### 3.6 保存の層のデーモンと、エンジンの核（案）

保存の層（3.4・3.5）を、管理のサーバーとは別のプロセス（DBのデーモン）にし、エンジンの核を、Ada/SPARKで書く。この節は、その決定と、規則。デーモンは作った（`cmd/whiteroom-db`・`internal/dbserver`・`internal/dbwire`・`internal/dbclient`。issue #109。下記の「進める順」の2）。核は、まだ作っていない（下記の「進める順」の3.1以降）。この節の規則は、作ったものについては、コードのとおり。

**目的と状態**

- 決定（決定済み。3.1。メンテナーの判断。2026-11-12）：(1) 保存の層を、管理のサーバーとは別のプロセス（DBのデーモン）にする。(2) エンジンは、Goのデーモンに、I/Oを持たないAda/SPARKの核を、cgoで入れる形にする。(3) 核の範囲は、「判断に、メモリの状態（表やオブジェクトの索引）が要らないものは、すべて核に入れる」という線で決める。
- この節の規則：見出しか文に「決定済み」と書いたものは、メンテナーの判断（2026-11-12 と 2026-11-15。13章）。「仮置き」と書いたものは、作るときに見直す。ほかは、案（issue #109 の計画への答え（2026-11-15）で決めたものも、案）。
- 状態：デーモン（下記の「進める順」の2）は、作った：エンジンは、ファイルの形を変えず、デーモンの中で動く（`whiteroom-db`）。管理のサーバーと、ほかのコマンドは、データのディレクトリを開かず、ソケットで繋ぐ。核（Ada/SPARK。3.1・3.2）は、まだ作っていない（#110・#111・#112）。同期に失敗した後の再起動の強制（#68）と、修復・リストア・形の移行の道具（#70）も、まだ無い。作っていないものは、下記の各所に書く。
- 検討の記録（初めの総括、SPARKが示すものと示さないもの、ほかに検討した形、Goのコードへの形式手法）は、#90。

**分ける理由**

- 監査：いまの鎖と、頭の書き出し（7.4の「改ざんの検知」）は、書き換えを見つける仕組み。分けると、管理のサーバーからは、過去の記録を、書き換えられなくなる。2つは補い合う。
- サルベージ：管理のサーバーが破られても、それより前の履歴は信頼できる。保存先は、すべての版を持つ（3.4の「表」）ので、復旧は、バックアップからの復元ではなく、「ある連番より前の版に戻す」操作になる。分けないと、ログのファイルを、直接書き換えられた可能性が残る。
- DoS：資源を、サービスごとに区切れる。書き込みの上限を、デーモンで強制できる（足すだけの保存先では、ディスクを埋められるのが、いちばんのDoS）。公開サイトは、静的なので、もともと影響を受けない。

**プロセスと境界**

| プロセス | Unixユーザー | 開くもの |
| --- | --- | --- |
| 管理のサーバー（`whiteroom serve admin`。9.6） | 管理用のユーザー | デーモンの書き手用のソケット（接続は1つ）と、書き手のロック（下記の「接続」）、読み手用のソケット（要るだけ）、出力先（4.3）、一時のファイルのディレクトリ（設定の `tmp`。9.4・9.7） |
| 読み手のコマンド（`whiteroom build -db`・`whiteroom backup`・`whiteroom doctor`。9.4） | 読み手用のソケットに繋げるユーザー | デーモンの、読み手用のソケット |
| 書くコマンド（`whiteroom init`・`whiteroom account`。9.4） | 書き手用のソケットに繋げるユーザー（書き手のユーザー） | デーモンの、書き手用のソケットと、書き手のロック |
| DBのデーモン（`whiteroom-db serve`） | デーモンのユーザー（管理用とも、公開用とも別） | データのディレクトリ（`logdb/` と `files/`。3.4）と、2つのソケットのファイル（書き手のロックのファイルは、作るだけ） |
| 公開用のサーバー（`whiteroom serve public`。9.5） | 公開用のユーザー | 出力先だけ。DBには繋がらない（いまと同じ） |

- 境界（決定済み。13章）：境界は、プロセスとUnixユーザー。データのディレクトリを開くのは、デーモンだけ。管理のサーバーも、読み手（ビルド・バックアップ・検査）も、Unixドメインソケットのプロトコルで繋ぐ。
- 機械で確かめる（案）：エンジン（`internal/logdb`）とデーモンのサーバー（`internal/dbserver`）を import してよい本番のコードは、`cmd/whiteroom-db` と、その2つのパッケージだけ。`.golangci.yml` の depguard の規則 `to-engine` が確かめる（`AGENTS.md`）。`whiteroom` は、エンジンなしでビルドできる（`internal/logdb` も `internal/dbserver` も、依存に出ない）。
- 管理のサーバーの中の `store`（案）：検証・索引・監査の記録（鎖の計算も）は、いまと同じGoのコードで、管理のサーバーの中で動く。`internal/store` は、デーモンのクライアント（`internal/dbclient`）の上に載る。デーモンに送るのは、できあがった操作の束（`Commit`）。デーモンは、`internal/content` を import しない（コンテンツのモデルを知らない）。
- 書くコマンド（案）：書き手として繋ぎ、動いている間、書き手のロック（下記の「接続」）を持つ。書き手は1つなので、`whiteroom account` は、`whiteroom serve admin` を止めて動かす（動いている間は、断られる）。データのディレクトリを作るのは、`whiteroom-db init`（下記の「実行ファイル」）で、`whiteroom-db serve` は作らない。`whiteroom init` は、`whiteroom-db init` が作った、動いているデーモンの保存先に、最初の管理者とサイトを入れる（9.4）。

**デーモンが守る規則**

中身を知らずに守れるものに限る（案）。断ったとき、保存先は何も変えない。相手が見る符号は、下記の「バイトの並び」の符号の表のとおりで、文は、コード（`internal/dbserver`）のとおり（文に、キー・値・オブジェクトの中身は入らない。入るのは、長さ・種類・符号・表の番号）。

| 規則 | 断るとき（符号。文） |
| --- | --- |
| 書き手の接続は、1つだけ | `Hello` に `busy`。`another writer is connected` |
| 書く要求（`PutObject`・`PutOriginal`・`Commit`）は、書き手の接続だけ | `denied`。`only the writer may commit`（`put an object`・`put an original`） |
| 書き手のUnixユーザーは、設定の1つだけ（下記の「接続」） | `Hello` に `denied`。`the user 1001 is not the writer of this daemon` |
| スナップショットを持ってから、`Get`・`Scan`・`Object`・`Events`・`PutObject`・`Commit` を送る（`Original`・`PutOriginal`・`Verify`・`Backup` は、要らない） | `no snapshot`。`no snapshot is held; send a Snapshot first` |
| 期待する連番が合うときだけ、確定する | `seq`。`the last sequence number is 12, not the expected 11` |
| オブジェクトと原本は、中身のSHA-256が、名前と合い、大きさが、上限までであること | `hash`。`the data do not have the hash that was given`（原本は `the data do not have the hash and the size that were given`）。大きさの上限は、下記の「上限」 |
| 原本は、空でない | `rule`。`the original is empty` |
| 足すだけの表（`history`・`revisions`・`entryRevisions`。3.4の「表」）の行は、消さず、書き換えない | `rule`。`op 3: table 3 is append-only: a row is not deleted`（書き換えは `…: a row is not changed`） |
| 行を足す・書き換える・消すコミットには、監査イベントが要る（7.4の「記録の無い書き込みを断る」を、デーモンでも守る） | `rule`。`a commit that puts or deletes a row needs an audit event` |
| イベントは、空でなく、デーモンの印の1バイト目（`0x00`。下記の「印」）で始まらない | `rule`。`op 1: an event is empty`・`op 1: an event starts with the byte that is the daemon's` |
| 何もしないコミット（操作も、置いたオブジェクトも無い）は、断る | `rule`。`a commit with no op and no staged object` |
| 書き出し用の表 `heads`（下記の「頭の書き出し」）の行は、頭の行の形で、消さず、16行まで | `rule`。`op 2: not a valid row of table 11`・`op 2: a row of table 11 is not deleted`・`the table of the heads would have more than 16 rows` |
| 確定した後の `meta` の `schema` の行は、あり、正しく、デーモンの知る版より新しくなく、前より低くない（デーモンが、開き直せない状態を、確定しない） | `rule`。`the commit would leave the store without its schema version`・`the commit would leave an invalid schema version`・`the commit would set the schema version 8, newer than this daemon knows (7)`・`the commit would lower the schema version from 7 to 6` |
| 表の番号は、0でない | `limit`。`op 0: invalid table 0` |
| 同期に失敗したら、書くのを止める（下記の「同期の失敗」） | `stopped`。`the store has stopped after a sync failed; restart the machine before starting the daemon again` |
| 上限を守る（下記の「上限」。ソケットは、新しい攻撃の面になる） | `limit`・`no space`・`busy` |

- 規則の外のこと（案）：コミットごとに、印を付ける（下記の「印」）。鎖の頭を、保存先の外に書き出す（下記の「頭の書き出し」）。
- 守る順（案）：書く要求（`PutOriginal` は、スナップショットを除く）は、書き手か、スナップショットがあるか、止まっていないか、の順に確かめ、断るときも、要求の残りを（上限まで）読んでから答える。`Commit` は、規則・空き・頻度の枠・連番の順に確かめる。
- 起動のときの確かめ（案）：デーモンは、コミットのあるデータのディレクトリが、`meta` の `schema` の行を持たなければ、`<DIR>/logdb: not a store of whiteroom (no schema version)` で、行が正しくなければ `<DIR>/logdb: meta "schema": invalid value` で、行が、デーモンの知る版（`dbwire.TableVersion`）より新しければ `<DIR>/logdb: the store schema is of version 8, newer than this program knows (7)` で、始まらない。エンジンがファイルを変える前に断る。コミットが無い（`whiteroom-db init` の直後の）ものは、開く。

デーモンが知らないことと、限界：

- 知らないこと：コンテンツの型と検証（`internal/content`）、索引の行の意味、アカウントと権限、監査の記録の中身と鎖の計算。これらは、管理のサーバーの中の `store` から上に残る。`meta` の `schema` の行は、uvarint として読む。`heads` の行は、形だけ確かめる。
- 限界：破られた管理のサーバーは、新しい偽の記録を足せる。できないのは、過去の履歴と記録を、消すことと書き換えること。偽の頭（`heads` の行）を置いて、確かめを失敗させることもできる（下記の「頭の書き出し」）。

**接続**

- ソケット（決定済み。13章）：デーモンは、Unixドメインソケットを、2つ作る（書き手用・読み手用）。繋げる人は、ソケットのファイルのモード（0660）とグループで決める（管理用のサーバーのソケットと同じやり方。9.4の「`whiteroom serve admin`」）。
- 名前と置き場所（案）：ソケットは、`writer.sock` と `reader.sock`。置くディレクトリは、`-db DIR`（設定ファイルの `db`）で渡す。デーモンは、そのディレクトリを作らない（無ければ、`DIR: the directory of the sockets does not exist; make it first, which serve does not` で、始まらない）。ソケットのパスは、107バイトまで（`listen unix …: the path of a socket has at most 107 bytes, and this one has 120`）。`@` で始まるパスは断る（抽象ソケットで、ファイルが無いため）。前のデーモンが残した、だれも待ち受けていないソケットのファイルは、置き換える。ほかのプロセスが待ち受けているか、ソケットでないファイルがあれば、何も変えずに失敗する。デーモンは、止まるときに、2つのファイルを消す。
- グループ（案）：`-writer-group`・`-reader-group`（設定の `writerGroup`・`readerGroup`）で、それぞれのソケットのファイルのグループを替える（名前か数。言わなければ、システムが付けるグループ）。ディレクトリのモードと持ち主は、デーモンは変えない。
- 相手のUnixユーザー（決定済み。13章）：デーモンは、繋いだ相手のUnixユーザーを、OSから受け取って（Linuxの `SO_PEERCRED`）確かめ、書き手は、設定で決めた1つのユーザーだけにする。モードを誤って緩めても、書き手は増えない。
- 書き手のユーザー（案）：`-writer-user`（設定の `writerUser`。名前か数）。言わなければ、デーモンのプロセスのユーザー。書き手用のソケットに、別のユーザーが繋いでも、`Hello` に `denied` で答える（書き手の席は取らない）。読み手用のソケットは、繋いだ相手を、みな読み手にする（ユーザーは見ない）。
- 管理のサーバー（案）：書き手用の接続を1つ持ち、読むための接続（読み手用のソケット）を、要るだけ持つ。読み手の接続の数の上限は、デーモンの `-max-readers`。1つのトランザクション（`View`・`Update`）の要求は、窓も、1つの接続の、1つのスナップショットに行く。
- 待ちと繋ぎ直し（案）：クライアント（`internal/dbclient`）は、デーモンに届かないときと、書き手の接続が `busy` のとき（前の書き手の接続が、いま終わったばかりのとき）、50ミリ秒おきに、2秒まで、繋ぎ直す（`Options.DialWait`。負の数は、1回だけ）。それでも繋がらなければ、`cannot reach the daemon` を包むエラー（`store.ErrUnavailable`）か、`DIR: another process is connected as the writer` で失敗する。デーモンが止まって、また動いたときは、クライアントの次の `View` と `Update` が、新しい接続で動く（`Open` し直さない）。止まりかけのデーモンが、開いている接続の要求を `busy`（`the daemon is closing`）で断ったときは、クライアントは、その接続を閉じ、`cannot reach the daemon` を包むエラーにする（`DIR: cannot reach the daemon: the daemon is closing`。管理のAPIは、503で答える）。読み手の `Hello` が、待ちの間ずっと、読み手の数の上限の `busy` で断られたときも、同じエラーにする（書き手の `busy` は、`another process is connected as the writer` のままで、`store.ErrUnavailable` ではない。書き手のロック（下記）を持つクライアントのものは、下記のとおり `store.ErrUnavailable`）。書き手の接続が、`Update` か `PutOriginal` の途中で終わったとき（要求のコンテキストが、要求の途中で終わったときなど）は、クライアントは、その呼び出しから戻る前に、書き手として繋ぎ直す（繋ぎ直しは2秒まで試し、答えを待つのは、合わせて7秒まで。繋げなければ、次の書き込みが繋ぐ）：接続の無い間は、デーモンに書き手がいなくて、書き手のロック（下記）を取らないプログラムが、書き手として繋げるため。その分、失敗した呼び出しは、遅く戻る（2026-11-17に測った）：デーモンが途中で無くなったときは2秒、接続を受けて答えないデーモンでは7秒、要求と要求の間でコンテキストが終わったときは、スナップショットを返す後始末の5秒と合わせて12秒まで。デーモンが `PutOriginal` を断ったときも、クライアントは、書き手の接続を取り直す（原本を最後まで読まずに断ったデーモンは、そのセッションを終えるため）。原本を送っている途中で断られたとき（クライアントの書き込みは、切れた接続で失敗する）は、クライアントは、届いている答えを読んで、デーモンの断りを返す（`cannot reach the daemon` にしない。空きが足りないときの `no space` など）。デーモンが、接続を受けて、答えないとき（止められたプロセス・返らないディスクの読みなど）のための、クライアントの側の時間の上限は、無い：呼び出しのコンテキストが終わるまで待つ（`store.Open`・`OpenReader`・`Create`・`OpenOriginal` も、コンテキストを取る。3.4。6.12の267）。ソケットのファイルが無いことは、文書や原本が無いこと（`fs.ErrNotExist`）にならない。
- 書き手のロック（案。#126）：デーモンは、ソケットを作る前に、同じディレクトリに `writer.lock` を作る（無いときだけ。モードは0660、グループは `-writer-group`。ふつうのファイルでなければ、`DIR/writer.lock: not a regular file; it is the lock of the writer` で、デーモンのユーザーがモードとグループを替えられないもの（別のユーザーのファイル）なら、`chmod DIR/writer.lock: operation not permitted` で始まらない。起動に失敗したら、その起動が作ったものは消す）。止めても消さず、作り直さない。書き手のクライアント（`internal/dbclient` の、ソケットのディレクトリで繋ぐもの。`whiteroom serve admin`・`init`・`account`）は、繋ぐ前に、そのファイルを、パスで開いてロック（`flock(2)` の排他）を取り、`Close` まで持つ（ソケットと同じく、ディレクトリは、通れれば足り、読めなくてよい）。そのため、デーモンを動かし直しても、同じファイルのロックを持ち続け、サーバーの書き手の接続が無い間（デーモンを動かし直した後、サーバーの次の書き込みまで）も、2つ目のサーバーと `whiteroom init`・`account` は断られる（デーモンを入れる前の、エンジンの書くロックと同じ）。ほかのプロセスがロックを持っていれば、50ミリ秒おきに、2秒まで試し、`DIR: another process is connected as the writer` で失敗する（デーモンの `busy` と同じ文。`store.ErrUnavailable` ではない）。ロックを取れない、ほかの理由（ファイルが無い：デーモンが、そのディレクトリで、まだ1度も動いていないとき）では、同じく2秒まで試し、書き手として繋いでみて、繋がらなければ、その理由で失敗する（`DIR: cannot reach the daemon: dial unix DIR/writer.sock: connect: no such file or directory`。デーモンの断りは、試し直さない）。繋がったときは、試し直さず、その接続を閉じ、`DIR: cannot reach the daemon: open DIR/writer.lock: no such file or directory` で失敗する（動いているデーモンは、ソケットの前にロックのファイルを作るので、後から作ることはない）。読み手は、ロックを取らない。ロックを持つクライアントの `Hello` が `busy` で断られるのは、自分の前の接続か、終わったばかりの書き手の接続を、デーモンが、まだ終えていない間（その接続の `Commit` を、`Verify` が待たせている間など）なので、`DIR: cannot reach the daemon: the last connection of the writer has not ended yet`（`store.ErrUnavailable`。管理のAPIは503）で失敗する。ソケットのディレクトリと `writer.lock` は、デーモンを動かし直しても残す：作り直すと、前のロックを持つ書き手がいても、別の書き手が、新しいファイルのロックを取れる（systemd の `RuntimeDirectory=` は、止めるときにディレクトリを消すので、`RuntimeDirectoryPreserve=yes` が要る）。理由（2026-11-17に、直す前の実行ファイルで確かめた）：デーモンを動かし直した後、2つ目の `whiteroom serve admin` は起動し、先のサーバーのログインは、4.1秒待って500、2つ目のログインは200だった。直した後は、2つ目は、ロックで断られた。限界：ロックを取らないプログラム（`whiteroom` のコマンドでないクライアント）は、ロックでは止まらない。データは、デーモンの書き手1つの規則が守る（下記の「答えが来ないとき」の取り違えは、そのプログラムとの間では残る）。
- デーモンは、データのディレクトリごとに1つ（案）：同じディレクトリを開く2つ目のデーモンは、エンジンの書くロックで、2秒の後に断られる（`<DIR>/logdb: another process holds the writer lock`。3.5の「ロック」）。保守のサブコマンドが動いていれば、すぐに断られる（`<DIR>/logdb: maintenance is running`）。
- 起動の順（案）：デーモンが先で、管理のサーバーと、ほかのコマンドが後。止めるのは、逆の順。systemdのユニットは、まだ書いていない（6.12の262・269）。

**プロトコル**

- 版と互換（決定済み。13章）：プロトコルの版は、1つの数（いまは2）。繋ぐとき（`Hello`）に比べ、同じ版でなければ、何も変えずに拒む（両方の版を示す。`protocol version 1, but the daemon speaks version 2`）。交渉はしない。2つの実行ファイルは、同じリリースで配り、一緒に入れ替える。長く保つ互換は、ディスクの形（エンジンの形の版と、表の版。3.4の「エンジンと設定」・3.5の「ファイルの形」）が受け持つ。
- 出した版のバイトの並びは、書き換えない（案）。変えるときは、新しい版にする（`AGENTS.md`）。版2（#124）は、`Hello` の答えの終わりに、データのディレクトリの識別を足した（下記の「バイトの並び」）。ほかのバイトは、版1と同じ。
- メッセージ（決定済み。13章）：次の13個。

| 使えるもの | メッセージ | 内容 |
| --- | --- | --- |
| 書き手と読み手 | `Hello` | 版を確かめる。答えは、版・接続の役・デーモンの起動ごとのID・いまの連番・止まっているか・上限・データのディレクトリの識別 |
| 書き手と読み手 | `Snapshot`・`Release` | いまの連番の時点を固定する（答えは、その連番）・放す。接続ごとに1つ |
| 書き手と読み手 | `Get`・`Scan` | 表とキーで、値を1つ・接頭辞で、キーの順に（途中のキーの後から続けて、ページごとに） |
| 書き手と読み手 | `Object`・`Original` | ハッシュで、オブジェクト・原本の中身 |
| 書き手と読み手 | `Events` | 監査イベントを、番号の順に（スナップショットの連番まで。デーモンの印も含む） |
| 書き手と読み手 | `Verify`・`Backup` | エンジンの確かめ・写しのファイルを、順に返す（下記の「保守の口」） |
| 書き手だけ | `PutObject`・`PutOriginal` | 置く。デーモンが、SHA-256と大きさを確かめる |
| 書き手だけ | `Commit` | 期待する連番・操作の束（行の書き込み・削除と、監査イベント）。答えは、新しい連番と、印の時刻 |

- 送り方（決定済み。13章）：1つの接続では、要求と答えを、順に送り、多重にしない（答えの枠は、ほかの要求の答えと混ざらない）。デーモンは、1つの接続の要求に、受けた順に答える。同時に読むには、接続を増やす。大きいもの（オブジェクト・原本・`Scan`・`Events`・`Commit`・`Backup`）は、枠に分けて流す。
  - 窓（案）：クライアントは、読みの要求（`Get`・`Scan` の最初のページ・`Object`）を、256個まで、合わせて32KiBまで（`dbwire.WindowRequests`・`dbwire.WindowBytes`。デーモンが、1度に読む量 `dbwire.ReadBuffer` と同じ）、答えを読む前に、続けて送ってよい。窓は、1回の書き込みで送り、その答えを、すべて読んでから、ほかのものを書く。デーモンは、受けた順に答え、後ろに要求が届いている読みの答えは、まとめて（32KiBまで）、1回の書き込みで書く。読みでない要求の前には、まとめた答えを書く。窓の中の断りは、その要求だけの答えで、後ろの要求には、ふつうに答える（接続を閉じる断りは、前の答えを書いてから、閉じる）。窓に入るのは読みだけで、ほかの要求（`Snapshot`・`Release`・`Events`・`PutObject`・`Commit` など）は、前の要求の答えを読んでから送る。窓は、枠とメッセージのバイトを変えない。
- 操作のID：プロトコルの欄にしない。いまと同じく、操作の束の中の1行（表 `operations`。3.4の「索引」）。
- 壊れた要求（案）：枠の見出しが正しくない・メッセージの本体が、決まりより長い・順が違う（`Hello` の前の要求・答えの種類の枠・`Hello` の2回目）ときは、`protocol` で答えて（答えられるとき）、接続を閉じる。終わりの印の枠まで届いたメッセージの本体が、決まりより短いときは、答えずに、接続を閉じる（読む側は、途中で切れた接続と、見分けない）。大きさが、読む前の上限を超えるときは、`limit`。デーモンは、読んだ長さを、相手の言う長さでなく、届いたバイトで確かめる（大きい長さを言って、メモリを取らせられない）。

**バイトの並び**

整数は、固定の幅で、ビッグエンディアン（案）。コードは `internal/dbwire`（枠は `frame.go`・`stream.go`、値の形は `codec.go`、メッセージは `message.go`、符号は `errors.go`、印は `mark.go`）。

枠：メッセージは、同じ種類の1つ以上の枠で、最後の枠が終わりの旗を持つ。メッセージの本体は、その枠の中身をつなげたもの。

| 位置 | 大きさ | 内容 |
| --- | --- | --- |
| 0 | 1 | 種類（下の表） |
| 1 | 1 | 旗。`0x01`（終わり）だけを決める。ほかのビットは0 |
| 2 | 2 | 予約。0 |
| 4 | 4 | 中身の長さ（uint32） |
| 8 | 長さ | 中身 |

- 中身の上限は、`Hello` の答えまでは1MiB。そのあとは、`Hello` の答えの枠の値（下記の「上限」。1以上、1GiB（`dbwire.MaxFrame`）まで）。超える長さの枠は、読む前に、断る（`limit`）。長さが0の枠は、終わりの旗が要る。
- 読む側は、すべての枠の見出しを確かめる：予約が0、旗が決めたもの、種類が決めたもの、1つのメッセージの枠が、同じ種類（答えの途中の `Error` を除く）。

種類（要求は、`0x01` から `0x0D`）：

| 値 | 種類 | 値 | 種類 |
| --- | --- | --- | --- |
| `0x01` | `Hello` | `0x08` | `Events` |
| `0x02` | `Snapshot` | `0x09` | `Verify` |
| `0x03` | `Release` | `0x0A` | `Backup` |
| `0x04` | `Get` | `0x0B` | `PutObject` |
| `0x05` | `Scan` | `0x0C` | `PutOriginal` |
| `0x06` | `Object` | `0x0D` | `Commit` |
| `0x07` | `Original` | `0x80`・`0x81` | 答え（OK）・エラーの答え |

値の形：

| 形 | 書き方 |
| --- | --- |
| 整数 | `u8`・`u16`・`u32`・`u64`（符号なし）、`i64`（`u64` の2の補数）。ビッグエンディアン |
| 真偽 | 1バイト。`0` か `1`（ほかは `protocol`） |
| バイト列 | 長さ（`u32`）と、そのバイト |
| 短い文字列 | 長さ（`u16`）と、そのバイト（`Backup` の道と頭の行だけ） |
| ハッシュ | SHA-256の32バイト |
| 大きさ・数 | `u64`（`int64` に収まるもの） |
| 一覧 | 要素の前に1バイトの印（`1` は要素、`0` は終わり）。`Commit` の操作と `Backup` の項目は、種類のバイトが、これを兼ねる（`0` が終わり） |

メッセージの本体（要求は、書くものの順）。答えは、OKの答えの本体。本体が空のものは「なし」：

| メッセージ | 要求の本体 | 答え（OK）の本体 |
| --- | --- | --- |
| `Hello` | `WRDB`（4バイト）・版（`u32`） | 版（`u32`）・役（`u8`。`1` 読み手、`2` 書き手）・起動のID（16バイト）・いまの連番（`u64`）・止まっているか（真偽）・枠（`u32`）・`Commit` の上限（大きさ）・オブジェクトの上限（大きさ）・置いたオブジェクトの上限（大きさ）・キーの上限（`u32`。4096）・データのディレクトリのデバイス番号（`u64`）と inode（`u64`）（`stat(2)` の値。どちらも0なら、分からない。版2） |
| `Snapshot` | なし | 連番（`u64`） |
| `Release` | なし | なし |
| `Get` | 表（`u32`）・キー（バイト列） | 見つかったか（真偽）。見つかったときだけ、値（バイト列） |
| `Scan` | 表（`u32`）・接頭辞（バイト列）・続きか（真偽）・このキーの後から（バイト列。続きでなければ空）・行の数の上限（`u32`。0は無し） | 行：（`1`・キー・値）の並び、`0`、まだ続くか（真偽）。1ページは、行の大きさ（`9` と、キーと値の長さの和）の和が枠の値に届くか、行の数の上限に届いたところまで |
| `Object` | ハッシュ | 見つかったか（真偽）。見つかったときだけ、大きさ（`u64`）と中身 |
| `Original` | ハッシュ | 大きさ（`u64`）と、その大きさのバイト（枠に分けて）。無ければ、`not found` |
| `Events` | なし | イベント：（`1`・番号（`u64`）・連番（`u64`）・データ（バイト列））の並び、`0` |
| `Verify` | なし | なし |
| `Backup` | なし | 項目の並び（下記） |
| `PutObject` | ハッシュ・大きさ（`u64`）・中身 | なし |
| `PutOriginal` | 塊の並び（長さ（`u32`。1以上）とそのバイト。長さ `0` で終わり）・ハッシュ・大きさ（`u64`） | なし |
| `Commit` | 期待する連番（`u64`）・操作の並び・`0` | 新しい連番（`u64`）・印の時刻（秒（`i64`）・ナノ秒（`u32`）） |

- `Scan` の続き：続きのページは、前のページの最後のキーを、「このキーの後から」に入れて頼む。デーモンは、ページの間に、位置を覚えない（下記の「ファイルの形」）。
- `Commit` の操作：種類（`u8`）と本体。`1` 書き込み：表（`u32`）・キー・値。`2` 削除：表（`u32`）・キー。`3` イベント：データ（バイト列）。`0` が終わり。1つの操作の大きさは、送るバイト数（書き込みは `1+4+4+キー+4+値`、削除は `1+4+4+キー`、イベントは `1+4+データ`。長さの4バイトを含む）で、`Commit` の上限は、この和に当たる。
- `Backup` の項目：種類（`u8`）と本体。`0` 終わり。`1` ディレクトリ：道（短い文字列）。`2` ファイル：道（短い文字列）と、続く塊の並び（`PutOriginal` と同じ。終わりは長さ `0`）。`3` 頭の行：行（短い文字列）。`4` 位置：世代・セグメント・位置・連番（それぞれ `u64`）・CRC（`u32`）。送る順は、位置・頭の行・`files` のディレクトリとその中（名前の順）・`logdb` のディレクトリとその中（エンジンの `Backup` が作る順）・終わり。道は、`files` か `logdb` か、その下の、`/` で区切る相対の道で、空・`.`・`..` の名前、バックスラッシュ・コロン・NULを含まず、4096バイトまで。頭の行は、1〜255バイトの、印字できるASCII。
- 答えの途中のエラー：長いOKの答え（`Scan`・`Original`・`Events`・`Backup`）の途中で失敗すると、デーモンは、そこまでの枠を残して、エラーの答えの枠で、答えを終える。

エラーの答え：1つの枠で、種類 `0x81`、終わりの旗つき、中身は、符号（`u16`）・文の長さ（`u16`）・文（UTF-8。1024バイトまで。長ければ、文字の切れ目で切る）。中身の長さは、4〜1028。OKの答えが始まった後でも、続く枠の代わりに置けて、その答えを終える。

| 符号 | 名前 | いつ |
| --- | --- | --- |
| 1 | `protocol` | 壊れた枠・メッセージ、順の違うもの。答えの後、デーモンは接続を閉じる |
| 2 | `version` | `Hello` の版が違う |
| 3 | `denied` | その役では送れない要求。書き手のUnixユーザーでない |
| 4 | `busy` | 書き手が、もう繋がっている。読み手が、上限に届いている。デーモンが閉じようとしている（`the daemon is closing`） |
| 5 | `no snapshot` | スナップショットが無い |
| 6 | `not found` | 無い原本 |
| 7 | `seq` | 期待する連番が、いまの連番でない |
| 8 | `rule` | デーモンの規則（上記の「デーモンが守る規則」） |
| 9 | `limit` | 上限を超えた（下記の「上限」） |
| 10 | `no space` | 空きが足りない |
| 11 | `stopped` | 同期に失敗して、書くのを止めている |
| 12 | `hash` | 中身が、言われたハッシュか大きさと合わない |
| 13 | `failed` | エンジンの失敗か、壊れたものを見つけた。文は、OSのエラーの文か、壊れたファイルの文（道と位置）か、エンジンの確かめの文に限り、行の値は入らない（それ以外は、`the engine failed`） |
| 14 | `internal` | 答えを書けなかった |

- 印の1バイト目の `0x00` は、デーモンのイベントのために取ってある（下記の「印」）。

**1回の保存の流れ**

メッセージの使い方（案）。

1. `Snapshot` で、いまの連番の時点を固定し、`Get`・`Scan` で、いまの版と索引を読む（読むものが先に分かっているときは、窓で、まとめて頼んでよい。下記の「持つもの」）。
2. 管理のサーバーの中で、検証し、索引と監査の記録を作る（いまと同じGoのコード）。関数の中の読みは、その関数の書いたものを見る。関数がエラーを返したとき、取り消されたとき、パニックしたときは、何も送らない。
3. `PutObject` で、オブジェクトを置く（デーモンが、SHA-256を確かめる）。置いたオブジェクトは、デーモンのメモリに、その接続のスナップショットとともに持つ：`Commit` までは、ログに入れない（`Object` で、置いた書き手には見える）。別の `Snapshot` か `Release`、`Commit` の答え、スナップショットを放すとき（最後の要求から5分）、接続が終わると、捨てる。原本は、`PutOriginal` で置く（下記の「原本」）。
4. `Commit`（期待する連番・操作の束）を送る。デーモンは、規則・空きの確かめと、頻度の枠（下記の「上限」）を通し、連番を確かめ、置いたオブジェクトをエンジンに渡し、操作を当て、印のイベントを足し、ログに追記して同期してから、答える（新しい連番と、印の時刻）。どの答えでも、答えの後、スナップショットと、置いたオブジェクトは捨てる。

- 1回の `Commit` は、エンジンの1つのコミット（ログの1つのレコード。3.5の「コミット」）。
- `store` の形：トランザクションの中で、Goの関数が走る（`Update`。3.4の「操作」）形は、変わらない。`Update` は、1つずつ動く（書き手の接続が1つのため）。
- 持つもの（案。クライアント。`internal/dbclient`）：クライアントが、トランザクションの間、持つのは、`Get` の答え（見つかったかと値。同じキーは、1つのトランザクションで、1度だけ頼む。`Update` が書いたキーには、書いたものを返す）、先に読んだオブジェクト（`Tx.PrefetchObjects`。`Object` が、1度だけ渡す。2度目は、デーモンに頼む）、先に読んだ `Scan` の最初のページ（`Tx.PrefetchScans`。`Tx.DropPrefetched` か、トランザクションの終わりまで）。`Get` の答えには、上限は無い。オブジェクトとページは、合わせて64MiBまで（`prefetchBudget`。設定は無い）：超える答えは、読んで捨て、その後の `Object` と `Scan` が、デーモンに頼む。窓での先読み（`Tx.GetMany`・`PrefetchObjects`・`PrefetchScans`）は、ヒント：断りと、無いオブジェクトは持たず、後の読みが、先読みが無いときと同じ答えを、同じ所で返す。トランザクションが終われば、すべて捨てる。保存先は、これを使う（`Tx.ReadAhead`。3.4の「操作」）。
- 答えが来ないとき（案）：書き手は1つで、デーモンは、前の接続の要求が終わってから、新しい書き手を入れるので、繋ぎ直した `Hello` の連番で、自分のコミットが確定したかが分かる。スナップショットの連番に1を足したものなら、確定している。同じなら、確定していない（`the transaction was not committed`）。ほかなら、分からない（`it is not known whether the commit was made`）。繋ぎ直せなければ、分からない。この見分け方は、書き手のプロセスが1つであることによる：クライアントが繋ぎ直すまでの間に、別の書き手のプロセスが繋いで、ちょうど1回コミットすると、連番は、同じく1つ進むので、クライアントは、自分のコミットが確定したと取り違える（2回以上なら、「分からない」になる。`Hello` の答えには、どのセッションのコミットかを見分けるものが無い）。書き手のロック（上記の「接続」）が、これを防ぐ：ロックを持つクライアントが開いている間は、ほかの `whiteroom` のコマンドは、書き手として繋がない（ロックを取らないプログラムとの間では、残る）。前の接続の `Commit` を、デーモンが、まだ持っている間（`Verify` が `Commit` を待たせている間など）は、繋ぎ直しは、2秒の後、`DIR: cannot reach the daemon: the last connection of the writer has not ended yet` で断られ（答えは「分からない」）、そのクライアントの次の書き込みも、その `Commit` が終わるまで、同じ文で失敗する（管理のAPIは503）。管理のAPIの再送は、いまと同じく、操作のIDで、2度しない（3.5の「冪等性の責務」）。

**上限（仮置き）**

上限を置くことと、その種類は、決めた（決定済み。13章）。値は、仮置き：デーモンの設定で変えられるものは、フラグか設定ファイルの項目で変える（下記の表。`whiteroom-db serve`）。見直しは、6.12の267。測った値は、下記の「測った値」。

| もの | 仮の値 | フラグ（設定の項目） | もと |
| --- | --- | --- | --- |
| 枠（メッセージの切れ端） | 1MiB | なし | デーモンが、1度にメモリに持つ量。続けて届いた読みの答えを、まとめて持つ分（32KiBまで）は、この1つの枠のバッファに入る |
| 1回の `Commit` | 操作が、送るバイトで268435446バイトまで（256MiBより10バイト少ない） | なし | エンジンのコミットのレコードの上限（3.5の「制限」）のまま |
| 1回の `Commit` の操作の数 | 4194304 | なし | 小さい操作が多いと、バイトの上限より、メモリを使うため |
| オブジェクト・原本 | 64MiB | なし | 文書と原本の上限（3.4の「上限」）のまま |
| 置いたオブジェクトの合計（`Commit` まで） | 268435446バイト（仮置き） | `-max-staged BYTES`（`maxStaged`）。1以上 | `Commit` の上限と同じ。デーモンのメモリの、接続ごとの上限（下の数と合わせて） |
| 置いたオブジェクトの数（`Commit` まで） | 4194304 | なし | 小さいオブジェクトが多いと、バイトの上限より、メモリを使うため（1つにつき約130バイト。2026-11-16に、4バイトのオブジェクト20万個で測った） |
| 接続 | 書き手1、読み手64 | `-max-readers N`（`maxReaders`）。1以上 | 管理のサーバーの同時の読み・ビルド・コマンド |
| スナップショット | 接続ごとに1つ。最後の要求から5分で放す（測り方は、下記の「時間の2つの上限の測り方」） | `-snapshot-idle DURATION`（`snapshotIdle`）。0は放さない | 止まった相手が、メモリを持ち続けない |
| 進まない要求 | 30秒で切る（測り方は、下記の「時間の2つの上限の測り方」） | `-stall DURATION`（`stall`）。0は切らない | 遅い相手が、接続を塞がない |

- 枠・`Commit` のバイト・オブジェクトと原本の大きさの値は、エンジンと文書の上限に結びついているので、フラグも設定の項目も無い。ほかの値の既定は、フラグと設定の項目の説明にも書く。デーモンが相手に伝える（`Hello` の答え）上限は、枠・`Commit`・オブジェクトと原本・置いたオブジェクトの合計・キーだけで、ほかの上限は、デーモンだけが守る。値は、フラグ、設定の項目、既定の順に決まる（9.4）。
- 超えたとき、相手が見るもの（案）：
  - 枠・`Commit` のバイト・操作の数・オブジェクトと原本の大きさ・キー：デーモンは、上限を超えたところで読むのをやめ、`limit` で答えて、接続を閉じる（`malformed message: a frame of 2097152 bytes, over the limit of 1048576`・`the ops of a Commit are over 268435446 bytes`・`a Commit of more than 4194304 ops`・`malformed message: an object of 70000000 bytes, over the limit of 67108864`・`the original is larger than 67108864 bytes`・キーは `malformed message: a byte string of 4097 bytes, over the limit of 4096`。読むときに `internal/dbwire` が断るものは、`malformed message: ` で始まる。1つの操作の値が、`Commit` の上限の残りより長いときも、この形）。クライアントは、先に確かめて、送らずに失敗する（`the transaction is too large: 300000000 bytes (max 268435446)`）。エンジンのコミットの上限に届いたときは、`limit`（同じ文）で、接続は閉じない。
  - 置いたオブジェクトの合計と数：`limit`。`the staged objects would be over 268435446 bytes`・`more than 4194304 objects would be staged`。接続は閉じず、スナップショットと、置いたオブジェクトも残る。同じオブジェクトを、もう1度置いても、数えない。クライアントも、合計は、先に確かめる（数は、確かめず、デーモンが断る）。
  - 接続：`busy`。`another writer is connected`・`64 readers are connected, the most that the daemon serves`。デーモンは、待ち受けごとに、開いている接続を、読み手は `-max-readers` に16、書き手は1に16まで数え（`Hello` の前のものも。1つは、`-stall` の間まで）、数に届いたら、受け付けるのをやめる。
  - スナップショット：放した後の読む要求は、`no snapshot`。接続は、そのまま使える。放すまでの時間は、要求と要求の間の待ちに掛かり、読み始めた要求には、掛からない（`-stall 0` のときも、読んでいる途中の要求を、この時間で切らない）。放すまでの時間（5分）の測り方は、下記の「時間の2つの上限の測り方」。
  - 進まない要求：要求を読む間と、答えを書く間（64KiBごと）、`-stall` の間に進まなければ、答えずに、接続を切る。`Hello` の前の接続にも、同じ。上限の測り方は、下記の「時間の2つの上限の測り方」。
  - 全体の量：`no space`。`the free space is 900000000 bytes; a write of 1000 bytes must leave 1073741824`。確かめる書き込みは、`PutObject`、`PutOriginal`（初めに1バイト、そのあと8MiBごと）、`Commit`（操作と置いたオブジェクトの合計）。確かめるのは、Linuxのデータのディレクトリのファイルシステムで、ほかのシステムでは、確かめない。
  - 全体の量（inode。#128）：`no space`。`the free inodes are 65536; a write that may make a file must leave 65536`。どの書き込みも、ファイルを1つ作りうるとして数え、書き込みの後に、下限が残らなければ拒む（空きが下限と同じなら、拒む）。確かめる書き込みは、`PutObject`・`PutOriginal`（初めだけ。8MiBごとの確かめは、原本のファイルを作った後なので、バイトだけを見る）・`Commit`。inode を数えないファイルシステム（`statfs` の総数が0か、総数か空きが-1。btrfs、`nr_inodes` の無い tmpfs など）では、確かめない（btrfs のメタデータの不足は、`statfs` から見えない）。理由（2026-11-17に測った）：原本は、1バイトでも、`files/` の中の1つのファイルで、ext4 では、inode を1つと4KiBを使う。ext4 の既定（`mke2fs.conf` の `inode_ratio = 16384`）では、小さい原本だけで、バイトの約4分の3が空いたまま、inode が尽きる。inode を2000にした tmpfs で、数バイトの原本を置き続けると、空きが249MiB残ったまま、1732個目で `no space left on device` になり、その後、64KiB以上のオブジェクト（`objects/` の中のファイル）、次のセグメント、圧縮（`whiteroom-db compact`）が、同じ失敗をした（小さい `Commit` は、セグメントに空きがある間は通った）。下限を500にすると、原本は、inode が500残る所で拒まれ、エンジンの書き込みと圧縮は、通った。開発のマシン（NVMe の上の ext4）では、テストのプロセスの中のデーモンに、1つの書き手が、数バイトの原本を1秒に294個置いた（同期を含む）。この速さで、空いている5665万の inode は、約53時間で尽きる（空の25GiBの ext4 の inode、約164万なら、約93分）。`PutOriginal` に、頻度と数の上限は置かない（6.12の125）。
- `Commit` の頻度（案）：1秒に50回を、かごで数える：かごは、50まで貯まり、頻度の分だけ戻る。`Commit` は1つ取り、空なら、順番が来るまで待つ（後ろの `Commit` も待つ）。拒まない。取り消されれば、取るのをやめる。
- 時間の2つの上限（30秒と5分）の測り方（案）：デーモンは、1つの時計から、接続の期限を決める。時計は、1つのゴルーチンが、1ティックに1度だけ読む（ティックは、短いほうの上限の16分の1で、1ミリ秒以上、半秒（`internal/dbserver` の `maxTick`）まで。既定では半秒）。期限は、上限より早くならず、遅くても4ティック後（既定では2秒。30秒の上限は30〜32秒、5分の上限は5分0秒〜5分2秒）。要求が続くときは、時計が動くまで、期限を決め直さない（読みの要求ごとに、時計を読まない。クロックソースが `hpet` だと、時計を読むのは、システムコール。下記の「測った値」）。時計の読みが、前の読みから2ティックを超えて遅れたとき（プロセスが止められたときなど）と、最後の読みが、2ティックより古いときは、時間切れを、本物の時計で、1度だけ決め直して確かめる（`Server.lateAt`・`timedConn` の `early`）：上限は、早くは切れず、その場合は、上限の長さまで、遅れうる。期限が、数えられる長さ（約292年）を超える上限（`-snapshot-idle`・`-stall` に、書けるいちばん長い期間を書いたときなど）は、期限なしとして扱う。

- 届く：`Commit` の頻度。頻度の上限なしで毎秒579〜684回の `Update` が、既定では毎秒50.8回（初めの50回の後）になる。サンプルサイトだけの保存（`CreateEntry` は4.88ミリ秒で、毎秒約205回）は、届く。投稿が1,000件以上の保存は、届かない（いちばん速い `SaveRevision` の中央値が30.8ミリ秒で、毎秒32.5回）。保存の操作のベンチマークは、上限なしで動かした。
- 1MiBより大きいものは、枠に分けるので、必ず届く（`Scan` の19.5MiB、8MiBの `Object`、64MiBの原本）。枠の数は、数えていない。続けて届いた読みの答えを、まとめて持つ分（32KiBまで）は、1つの枠の分のバッファに入るので、デーモンが答えのために持つ量は、増えない。
- 届かない：`Commit` の大きさ（いちばん大きかった `Commit` は、1,031バイトの5,000行で5.2MB。上限の1.9%）、置いたオブジェクトの合計（サンプルサイトの取り込みは、40,170バイト。上限の0.015%。1,000件を足す最大の `Update` は、9.5MiBで3.7%）、スナップショットの5分（ビルドの初めの読みが持つのは、サンプルサイトで0.868ミリ秒、1,000件で4.44ミリ秒、5,000件で24.1ミリ秒、20,000件で99.9ミリ秒。その中の、1回の呼び出しの最長は、20,000件で99.3ミリ秒、呼び出しの間の最長は0.006ミリ秒。保存の操作のベンチマークで最長は、20,000件の `SaveTermRefused` の12.7秒（最大12.7秒）で、5分の約24分の1。保存先からのビルドそのものは、動かしていない）、進まない要求の30秒（いちばん遅い1つの要求は、`Backup` の0.77〜0.86秒）、空き1GiB（空きは693GB。`df -h` で、測った後に見た。確かめを入れた300回の `Update` も、断られなかった）。
- 64MiBの上限には、64MiBちょうどの原本を、わざと置いた3回が届き、通った。ふつうのオブジェクトは、10KBより小さい。
- 接続の数（書き手1・読み手64）は、同時に開いた数を、数えていない。
- 時間の2つの上限（30秒と5分）は、早くは切れず、既定では、最大2秒遅れる（測り方は、上記の「上限」）。測ったものは、どちらにも届かなかった。

**印（決定済み。13章）**

- 中身：デーモンが、コミットごとに付ける、デーモンの時計の時刻（UTC）だけ。連番は、レコードにある。時計が戻っても、そのまま記す（順は、連番が決める）。
- 理由：いまは、保存した日時（3.4の「表」）と、記録の時刻（7.4の「番号と時刻と鎖」）を、管理のサーバーの中の `store` が付けるので、破られると偽れる。印があれば、破られた期間を特定でき、サルベージの起点になる。
- 置き方：デーモンが、コミットごとに、自分のイベント（3.5の「イベント・操作のID・暗号化の封筒」）を、そのコミットの最後に足す。エンジンのファイルの形は、変えない（下記の「ファイルの形」）。イベントは、ログにだけあり（メモリには数だけ）、圧縮でも、書き直しで落とさなければ残る。
- バイトの並び（案）：14バイト。

| 位置 | 大きさ | 内容 |
| --- | --- | --- |
| 0 | 1 | `0x00`：デーモンのイベント |
| 1 | 1 | `0x01`：印（ほかの値は、まだ決めていない） |
| 2 | 8 | 1970-01-01T00:00:00Z からの秒（`i64`） |
| 10 | 4 | 秒の下のナノ秒（`u32`。10億より小さい） |

- 書き手のイベントとの区別（案）：監査の記録のJSONは `{` で始まる。デーモンは、書き手のイベントが、空か、`0x00` で始まれば、断る（上記の「デーモンが守る規則」）。印の時刻は、`Commit` の答えにも返る。
- 読む側：記録を読む口と確かめる口（7.4）は、印を飛ばす。`0x00` で始まるのに、印の形（14バイト・`0x01`・ナノ秒が範囲内）でないイベントは、壊れているとする（`audit event 7: not a record of the audit log`）。イベントの番号は、印も数える（記録の番号とは別。7.4の「番号と時刻と鎖」）。そのため、表の版（3.4の「エンジンと設定」）を、7に上げた。

**頭の書き出し（仮置き）**

- 決めたこと（決定済み。13章）：鎖の頭を、保存先の外に書き出すこと（7.4の「改ざんの検知」）を、デーモンの側に移す。管理のサーバーに残すと、破られたときに、止められる。管理のサーバー（`whiteroom serve admin`）は、頭を書かない。
- 形（仮置き。6.12の268）：デーモンは、監査の鎖の計算を知らない。そこで、管理のサーバーの中の `store` が、ログごとの頭の行（7.4の形。`audit head <ログ> <番号> sha256:<64桁の小文字の16進数>`）を、その記録と同じコミットで、表 `heads`（11）に置く（キーは、ログの名前の `login`・`activity`）。デーモンは、その表の行の値を、中身を読まずに、そのまま、自分の標準エラーに、1行ずつ書く。デーモンが確かめるのは、行の形だけ：キーは1〜64バイトの `A-Z`・`a-z`・`0-9`・`.`・`_`・`-`、値は1〜255バイトの、印字できるASCII。形に合わない行は、書かず、そのことを、エラーのログに1回書く（`a row of the table of the heads is not a head line, and is not written`）。
- いつ書くか（案）：起動のとき、すべての行を1回。そのあと、1分ごとに、前に書いてから値が変わった行。止めるとき、要求が終わった後に、変わった行をもう1回（その最後の読みは、5秒まで）。書けなかった行は、次の合図に、また試す（エラーのログ：`cannot write a head: …`）。書く間、読みも `Commit` も止まらない。
- 書く先が詰まったとき（案）：標準エラーへの書き込みが返らない間は、頭の書き出しだけが止まる（コミットと読みは続く）。その間に来た合図は、1つまで待ち、書き込みが返った後に取る。デーモンを止めるときは、書き込みが返るのを待つので、返らない書き出し先は、デーモンが止まるのを妨げる（サービスの管理が、プロセスを終わらせる。その場合、最後の頭は書かれない。6.12の286）。
- 読む側が終わったとき（案。#130）：標準エラー（と標準出力）がパイプで、読む側が終わっているときは、書き込みが失敗する（`EPIPE`）だけで、デーモンは動き続ける。書けなかった頭は、ほかの失敗と同じに、次の合図に、また試すが、パイプの読む側は戻らないので、デーモンを動かし直すまで、頭も、ログの行も、どこにも出ない（詰まらない場所にも書くかは、6.12の286）。止める合図で止めたときの終了コードは、0。そのために、`whiteroom-db serve` は、SIGPIPE を受け取る（`os/signal` の `Notify`）：受け取らないと、Goのランタイムは、標準出力と標準エラーへの書き込みの `EPIPE` で、プロセスを終わらせる。親が SIGPIPE を受け流していても（systemd の既定の `IgnoreSIGPIPE=yes`）、終わる（Goのランタイムは、受け継いだ受け流しを、SIGHUP と SIGINT のほかには使わない。2026-11-17に、直す前の `whiteroom-db serve` で、頭が変わった後の1分ごとの合図に、SIGPIPE で終わり、ソケットのファイルが残ることを確かめた）。`whiteroom serve admin`・`serve public` も、同じに動き続ける（9.4の「終了コード」）。`cmd/whiteroom` の `TestProcesses` が、読む側の無いパイプを標準エラーにして、3つを動かす。
- 標準エラー：デーモンのログの行（日時つき。キーと値は書かない）も、同じ標準エラーに出る。頭の行は、そのまま読める（`audit.ParseHead` は、行の末尾の形を読む。7.4の「改ざんの検知」）。`whiteroom backup` は、写しの鎖の頭を、標準出力に書く（下記の「保守の口」）。
- 限界：破られた管理のサーバーは、偽の頭を置ける。頭の形でない行も、上の形（印字できるASCII）に合えば、16行まで、デーモンの標準エラーに書かせられる（日時つきのログの行に似せた行も。制御文字は、入らない）。できるのは、確かめを失敗させること（誤った警報）だけで、書き換えは隠せない（7.4の「改ざんの検知」の、偽の頭の行と同じ）。破られる前に書き出した頭は、変えられない。
- 決めていないこと：デーモンが、中身に依らない自分の鎖（イベントのバイト列のハッシュの鎖）を持って、それを書き出す形にするか（6.12の268）。

**原本（決定済み。13章）**

- デーモンが持つ：メディアの原本（`files/`。3.4の「原本」）も、デーモンが持つ。分ける理由（サルベージ）は、原本にも当たる：管理のサーバーが `files/` を直接書けると、破られたときに、原本を消せる。
- 送り方（案）：原本は、ソケットで、塊に分けて送り（`PutOriginal`。管理のサーバーの `Update` の外）、受ける（`Original`）。置くとき、デーモンは、受けながら `files/` の一時のファイル（`.tmp-` とランダムな16進数16桁）に書き、SHA-256と大きさを求め、最後に付いてきたものと比べる。合わなければ、`hash`（`the data do not have the hash and the size that were given`）。空は `rule`（`the original is empty`）。上限（64MiB）を超えるところで、読むのをやめる（`the original is larger than 67108864 bytes`）。それから、一時のファイルを同期して閉じ、`files/<16進数2桁>/<16進数64桁>` に名前を変える（ディレクトリが無ければ作り、`files/` を同期する）。そのディレクトリも同期する。そのため、原本のファイルは、すべてあるか、無いか。同じ名前があれば、置き換える（同じ中身）。失敗したら、一時のファイルを消す。
- 読む：`Original` は、名前のファイルが、ふつうのファイルで、64MiBまでであることを確かめ（無ければ、符号 `not found` で、`files/9f/9f86…: not found`。ほかは、符号 `failed` で、`files/…: symbolic links are not allowed`・`files/…: must be a regular file`・`files/…: too large: 70000000 bytes (max 67108864)`）、大きさと、バイトを、そのまま送る。デーモンは、読むときにハッシュを確かめない：受け取る側（`store`。3.4の「原本」）が、終わりまで読んだときに確かめる。
- 起動のときの片付け（案）：デーモンは、エンジンの書くロックを取った後に、`files/` の直下の、`.tmp-` と16進数16桁のふつうのファイル（`PutOriginal` が途中で止まったもの）を、すべて消す。消せなければ、起動に失敗し、保存先は変わらない（`<DIR>/files/<名前>: cannot remove: …`・`<DIR>/files: cannot read: …`）。ほかの名前・ディレクトリ・原本は消さない。`Backup` は、一時のファイルを送らない。
- 一時のファイル（案）：管理のAPIの、メモリに乗らない本文と答えの一時のファイルは、デーモンの `files/` に置かない：管理のサーバーの側の、設定 `tmp` のディレクトリに置く（9.4・9.7）。デーモンの `files/` の一時のファイルは、書いている途中の原本だけ。
- 同期の失敗：原本の同期（一時のファイル・`files/`・原本のディレクトリ）の失敗は、エンジンの同期の失敗と同じ印で、デーモンの書くのを止める（下記の「同期の失敗」。`PutOriginal` だけでなく、文書の書き込みも止まる）。

**保守の口（決定済み。13章）**

- 書き換えるもの（圧縮・回収。3.5の「保守モード」）：デーモンの実行ファイルのサブコマンド（`whiteroom-db compact`・`whiteroom-db gc`）。デーモンを止めて、サーバーの上で動かす。ソケットには出さない：履歴を消せる操作なので、ソケットに出すと、破られた管理のサーバーが、履歴を消す口になる。データのディレクトリを開いているプロセス（デーモンなど）があれば、2秒待って、何も変えずに失敗する（`whiteroom-db compact: <DIR>: the data directory is in use; stop whiteroom-db serve on it first`）。保守が動いている間は、デーモンは、すぐに始まれない（`maintenance is running`）。保守が待つ2秒の間も、`lock/entry` を持つので、動いているデーモンの `Backup` は、その間、`failed` で終わる。`compact` は、いまの状態を、新しい世代のログに書き直して、古い世代を消す（何も落とさない）。`gc` は、いまの世代でないセグメントと、状態が持たないオブジェクトのファイルと、一時のファイルを消す（原本は消さない。6.12の125）。修復は、まだ無い（6.12の131）。
- 読むだけのもの（検査・バックアップ）：読み手の接続のメッセージ（`Verify`・`Backup`）。`whiteroom doctor`・`whiteroom backup`（9.4）は、ソケットで繋ぐ。
- `Verify`（案）：デーモンが、エンジンの `Verify`（3.5の「保守モード」）を動かして、すべてのログをディスクから読み直し、メモリの状態と比べ、オブジェクトのハッシュを確かめる。答えは、OKか、`failed`（`the state in memory differs from the log (the detail is not sent: it may hold values of rows)`・`object <ハッシュ>: the data has the hash <ハッシュ>` など）。エンジンの `Verify` は、`Commit` と同じ順番（エンジンの書く順番）を取るので、動いている間、`Commit` は待つ（読みは続く）。読み手の `whiteroom doctor` も、書き手を待たせる。待つ長さは、下記の「測った値」。
- `Backup`（案）：1つの要求の答えが、写しのすべて。デーモンは、エンジンの読み手を、デーモンの中で開き（状態を、もう1つ、メモリに持つ。3.5の「ほかのプロセス」の読み手は、いま、ここだけが使う。6.12の281）、その最後の同期したコミット（位置）を決める。`Commit` は、この読み手が開く間だけ待たせる：位置が決まるまで（その後、ファイルを送る間は、止めない）。頭の行は、デーモン自身の状態（`heads` の行）から、位置のコミットのものを読み、位置の連番と合わなければ、`failed` で終える（`the engine's head is behind its last commit; take the backup again after the next commit`）。それから、位置・頭の行・`files/`（一時のファイルは除く。位置より後に置いた原本が入ることもある）・エンジンのファイル（セグメントを位置まで、組になるときのチェックポイント、状態のオブジェクトのファイル、`head`）の順に送る（上記の「バイトの並び」）。クライアントは、空のディレクトリに、0700と0600で作り、道を確かめ（`files` か `logdb` の下だけ）、すべてのファイルを同期して、それからディレクトリを（深いほうから）同期する。失敗したら、書いたものは残るので、呼ぶ側が消す。
- 写しの確かめ（案。リストアの前）：写しは、データのディレクトリなので、もう1つのデーモンを、別のソケットのディレクトリで、写しの上で動かし（`whiteroom-db serve -data COPY -db OTHER`）、`whiteroom doctor -db OTHER` で確かめる。写しの上のデーモンは、書き手として開くので、切れかけの末尾を切る（3.5の「復旧」）。写しを戻すのは、デーモンを止めて、写しをデータのディレクトリの場所に置くこと（9.4の「`whiteroom backup`」）。リストアの道具（6.12の131）は、まだ無い。
- コピー先（案。#124）：デーモンは、`Hello` の答えで、データのディレクトリの識別（デバイス番号と inode。Linuxだけ）を伝える。`store.Backup`（`whiteroom backup`）は、デーモンに繋ぎ、表の版を確かめた後、コピー先と、その親を、シンボリックリンクと `..` をカーネルのとおりに解いて、たどって比べ（コピー先が無ければ、親から）、データのディレクトリそのものか、その中なら、何も作らずに断る（`DEST is the data directory of the daemon`・`DEST is in the data directory of the daemon`）。コマンドは、その後に、コピー先を作る。理由：デーモンは、`files/` を、名前の順にたどって送るので、コマンドが `files/` の中に書いたものも送り、写しに、原本が重なって入った（2026-11-17に、直す前の実行ファイルで、`files/b` に写すと、終了コード0で終わり、次に `files/c` に写すと、`c/` の中に、`b/` と原本が入り、原本の6つが12になった。測りの残りは、9.4の「`whiteroom backup`」）。限界：別のマウント名前空間で動くデーモン（コンテナーなど）は、デバイス番号が違いうるので、確かめが効かない。識別を伝えないデーモン（テストの、ファイルシステムの模型の上のもの）でも、確かめない。
- 書きながらの圧縮と回収は、変わらず、決めていない（6.12の133）。

**同期の失敗（決定済み。13章）**

同期に失敗した後の、再起動の強制（6.12の129）のうち、デーモンの形に依るもの。作るのは #68。

- 拒む範囲（決定済み。13章。作るのは #68）：止まった印があって、同じ起動（マシンを再起動していない）なら、デーモンは起動しない。書き手も読み手も繋げず、保守のサブコマンドも動かない。
- 同じ印（決定済み。13章）：エンジンの同期の失敗（3.5の「失敗の扱い」）も、原本の同期の失敗（3.4の「原本」）も、同じ印で、デーモンの全体が止まる（これまでは、原本の同期の失敗では、原本の保存だけが止まり、文書の書き込みは続いた）。
- 置き場所と形（決定済み。13章）：データのディレクトリの直下の、デーモン（Goの側）のファイル。エンジンの形の版にも、表の版にも入らない。
- 作ったもの（案。#109）：プロセスの中の印が1つ。エンジンか原本の同期が失敗すると、デーモンは、印を立て（ログに1行：`the store has stopped after a sync failed (<理由>); writes are refused until the daemon is started again after a restart of the machine`）、それからの書く要求（`PutObject`・`PutOriginal`・`Commit`）を、`stopped` で断る。読みは続き、デーモンは動き続ける。`Hello` の答えの「止まっているか」が真になる。同期に失敗した原本の `PutOriginal` と、同時に動いていた原本の `PutOriginal` も、`stopped` で失敗する。デーモンを起動し直すと、印は消える。
- 作っていないもの（#68）：ディスクの印のファイルと、それがあるときに起動を拒むこと。そのため、いまは、マシンを再起動せずに、デーモンを起動し直せ、再起動を強制しない：運用の規則（3.5の「運用の制約」）に任せる。
- 方法（起動ごとのIDなど）、同期のほかの失敗の扱い、印を残すこと自体の失敗、印のファイルの名前と中身は、決めていない（6.12の129）。

**ファイルの形（決定済み。13章）**

- エンジンのファイルの形は、3.5のまま（形の版は1）。変えなかった。デーモンの印は、形を変えずに、デーモンが足すイベントで持つ（上記の「印」）。

- エンジンに足したもの（案）：読むだけの `Tx.ScanAfter(表, 接頭辞, 後のキー, 関数)`：接頭辞を持つキーのうち、後のキーより大きいものを、順に渡す（後のキーは、表にあっても、渡さない。後のキーが空でも、空のキーは渡さない：最初のページは `Scan`）。木を、そのキーの所まで降りるので、前のキーを通らない。書く道と、ファイルの形は、変えない。
- 理由（案）：デーモンは、`Scan` のページを、位置を覚えずに答える。続きのページは、前のページの最後のキーの後から頼む。エンジンの `Scan` だけでは、続きのたびに、先頭から行を飛ばすので、ページの数の2乗の費用になる。測った値（開発のマシン。2026-11-15）：行を1つ飛ばすのに約72ナノ秒。エントリーの要約（1行903バイト）の5万件を、44ページで読むと、1,075,000行を読み直し（77ミリ秒。1回の通しの3.7倍）、100万行の表は、4億3000万行（31秒）。`ScanAfter` では、100万キーの表の最後の100キーを読むのに8,535ナノ秒で、前から飛ばす `Scan` の85.8ミリ秒の、約1万分の1（`BenchmarkScanAfter`）。デーモンに、位置を持たせる案（読む途中の状態を、接続ごとに持つ）は、採らなかった。
- 形を変えるときの道（仮置き。作るのは #70）：書き直して移す（保守の圧縮が、新しい世代を、いまの版で書く。3.5の「移行・バックアップ・リストアの条件」）。読めるのは、いまの版と1つ前の版で、書くのは、いまの版だけ。読む版を2つに限るのは、核の復号と証明が、版の数だけ増え続けないため。プログラムを前の版に戻すときの扱いは、決めていない（6.12の131）。

**エンジンの形（決定済み。3.1）**

| 形 | Adaで書く範囲 | `simfs` の行列（3.5の「テスト」） | ビルド | 扱い |
| --- | --- | --- | --- | --- |
| Goのまま（いまのエンジンを、デーモンに入れる） | 無い | そのまま使える | いまのまま（`CGO_ENABLED=0` も通る） | 下記の「進める順」の2で使い（作った。ファイルの形は変えず、エンジンに足したのは、読むだけの `Tx.ScanAfter` の1つ：下記の「ファイルの形」）、核ができるまで、正解の役をする |
| Goのデーモンに、Ada/SPARKの核を、cgoで入れる（I/OはGo） | 下記の「核の範囲」 | そのまま使える（I/Oが `vfs` を通る） | Goのビルドに、GNATとCのリンクが要る。`CGO_ENABLED=0` は使えず、クロスビルドが難しくなる | 決めた（まだ作っていない） |
| すべてAdaのデーモン | エンジン・サーバー・接続・並行・I/Oの束縛 | Adaで作り直す | Goの側は、いまのまま。Adaは別にビルドし、実行ファイルが2つになる | 採らない。Adaの範囲が広く、証明しにくい部分（サーバーと並行）が入る |

決めた形の中身：

- 核は、エンジンのうち、ファイルを触らずに、判断と計算だけをする部分。Goから、関数として呼ぶ。
- 「どのファイルに、どの順で、書く・同期する・名前を変えるか」は、核が、指示の列として返す。Goの側が、いまの `vfs`（3.5の「構成」）で、そのとおりにI/Oをし、成功か失敗かを、核に返す。
- いまの証拠が残る：`simfs` のクラッシュ・失敗の差し込みの行列を、そのまま核に流せる。Goのエンジンと核を、同じテストの中で比べられる。
- 証明が届く範囲が広がる：書く順の規則を、指示の列の性質として、SPARKで証明できる（ファイルシステムの模型は、仮定のまま）。
- Adaの側が小さい：ソケットも、並行も、`fsync` の束縛も要らない。
- 分担：Goは、サーバー・並行・I/Oの標準ライブラリと、いまのテスト。Ada/SPARKは、間違えるとデータが壊れる部分（形の符号化と復号、復旧の判断、書く順）の証明と、範囲つきの型。
- 前提（メンテナーが置いた。13章）：リリースが無いので、作り直しは、いとわない。cgoを使わない制約は、サードパーティの依存を無くすためのもので、自作のコードを繋ぐcgoは、別に扱う（1.2）。

引き受けるもの：

- cgoの継ぎ目は、だれも証明しない：SPARKの証明は、呼ぶ側が事前条件を守ることを前提にする。Goの側には、その保証が無いので、核の入り口で、引数を、実行時に確かめ直す。長さと寿命の取り違えは、こういう継ぎ目に集まりやすい。
- 証明するのは「指示」で、「実行」ではない：Goの側が、指示のとおりに実行したかは、証明の外で、いまと同じく、`simfs` の行列で確かめる。クラッシュの後の整合性は、順序の証明と、実行のテストの合わせ技になる。
- 設計が素直でなくなる：書く側は、「指示を返し、結果を受け取る」状態機械になる。同期の失敗のようなエラーの道も、継ぎ目を2回通る。
- 2つの言語と道具を、持ち続ける：ファイルの形を変えるたびに、Adaの証明と、Goの実行とテストの両方を直す。ビルドには、GNATが要る。
- 条件：中心の部分で、証明をやり切ること。証明をしないAdaは、動的なメモリと並行の安全性・先例・テストの道具で、Rustに劣る。

**核の範囲（決定済み。3.1）**

線：判断に、メモリの状態（表やオブジェクトの索引）が要らないものは、すべて核に入れる。

| 核に入れる | Goに残す |
| --- | --- |
| 形の符号化と復号のすべて：セグメント・枠・レコード・`head`・チェックポイント・オブジェクトの見出し、CRC（いまの `format.go`・`ops.go` と、`checkpoint.go` の符号化と復号に当たる） | 実際のI/O（`vfs`）、ロック、サーバー、接続、並行 |
| ログを読むときの判断：レコードの順、末尾がちぎれているのか壊れているのか、どの世代を使うか、チェックポイントがログと合うか（いまの `recover.go` の、何も変えずに決める側に当たる） | 受け入れたレコードを、表と索引に当てはめること（`state.go`・`pmap.go`）、スナップショット |
| 書く順の指示：コミット、セグメントの切り替え、オブジェクトのファイル、チェックポイント、復旧の後始末（いまの `commit.go`・`checkpoint.go` と、`recover.go` の、決めたことを実行する側の、順を決める部分に当たる） | メモリの状態を見る検査（同じオブジェクトが、もうあるか。ベースの終わりの数が合うか） |
| | 保守（圧縮・回収・バックアップ・検査）の進行。核の符号化と復号は使う |

- 量：いまのエンジン（テストを除いて約4,800行）の、3分の1ほど。
- この線にする理由：
  - いまのコードに、同じ継ぎ目がある：復旧は、「何も変えずに決める」と、「決めたことを実行する」に分かれている。
  - 状態を見る検査は、核の判断に戻ってこない：「切るか、壊れているとして拒むか」は、枠のCRCが合うかどうかだけで決まる。CRCが合った後に、Goの側の検査に落ちたものは、必ず「壊れている」で、切ることはない。だから、核は、表を知らなくて済む。
  - 核は、メモリを確保しない：核は、Goが渡したバッファを読み、位置と数だけを返す。キーと値は、Goが、自分のバッファから取り出す。Adaの側のメモリの管理が無くなり、継ぎ目で寿命を取り違える危険が、ほぼ消える。
- 入れないもの：
  - メモリの状態（表と、書き換えない木。3.5の「スナップショット」）：移すと、共有する構造を、SPARKの所有権のモデルで作り直すことになり、証明が重くなる割に、得るものが小さい。
  - 保守の進行：圧縮にも、「新しい世代が揃うまで、古い世代を消さない」という順の規則があるので、後から核に入れる候補。最初は入れない（6.12の272）。

**証明**

対象の候補：

1. どんなバイト列を渡しても、実行時エラーにならない。
2. 符号化したものを復号すると、元に戻る。
3. CRCが合ったレコードは、決して切らない（切ると、確定したコミットを失う）。
4. 切るのは、最後のセグメントの末尾だけ。受け入れた連番は、続いている。
5. 名前を変えるのは、同期の後。レコードを足すのは、それが指すオブジェクトのファイルが残ると決まった後。新しいセグメントに初めのレコードを足すのは、その見出しと名前が残ると決まった後。
6. 同期に失敗した後は、書く指示を、二度と出さない。

- 3から後は、いまは、テストだけで守っている規則。
- 水準（決定済み。13章）：6つすべてを、目標にする。Goのエンジンから差し替える（下記の「進める順」の4）条件は、1〜4と、6。5（書く順）は、電源断の確かめ（6.12の130）の結果で、規則を確かめた後に証明し、証明できなかった部分は、3.5に「証明の外」と書く。
- SPARKが示さないもの：クラッシュの後の整合性は、ファイルシステムの振る舞いの模型の上の性質で、証明しても、`simfs` と同じ前提を、仮定として書くことになる。電源断（6.12の130）、同期に失敗した後の再起動（129）、検出と修復と移行の道具（131）、メモリと開く時間（132）の危険は、言語を替えても減らない。
- 核を作り始めるときに確かめること（GNATのランタイムと、Goのランタイムの共存など）は、6.12の271。

**テスト（案）**

デーモンを通すテストは、データのディレクトリを開かず、プロセスの中のデーモンに繋ぐ。

- プロセスの中のデーモン：`internal/dbserver/dbtest` が、エンジンを開いて、デーモンのサーバーを、テストのプロセスの中で動かし、クライアントは、`net.Pipe` か、ソケットのファイル（短いパスのディレクトリ）で繋ぐ。`internal/store`・`internal/dbclient`・`cmd/whiteroom` のテストは、`dbtest` を使い、ほかのパッケージのテストは、`internal/store/storetest`（ディレクトリで、保存先を開く）を使う（`AGENTS.md`）。`cmd/whiteroom` の `TestProcesses` だけは、2つの実行ファイルを、実プロセスで動かす。
