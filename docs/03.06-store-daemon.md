### 3.6 保存の層のデーモンと、エンジンの核（案）

保存の層（3.4・3.5）を、管理のサーバーとは別のプロセス（DBのデーモン）にし、エンジンの核を、Ada/SPARKで書く。この節は、その決定と、仮に決めた規則。どれも、まだ作っていない：3.4・3.5・7.4・9章の、いまの実装の記述は、デーモンができるまで、そのまま正しい（どこが変わるかは、それぞれの節の「デーモンで変わる所」）。

**目的と状態**

- 決定（決定済み。3.1。メンテナーの判断。2026-11-12）：(1) 保存の層を、管理のサーバーとは別のプロセス（DBのデーモン）にする。(2) エンジンは、Goのデーモンに、I/Oを持たないAda/SPARKの核を、cgoで入れる形にする。(3) 核の範囲は、「判断に、メモリの状態（表やオブジェクトの索引）が要らないものは、すべて核に入れる」という線で決める。
- この節の規則：見出しに「決定済み」と書いたものは、メンテナーの判断（2026-11-12 と 2026-11-15。13章）。「仮置き」と書いたものは、作るときに見直す。ほかは、案。
- 状態：まだ作っていない。作る順は、下記の「進める順」。
- 検討の記録（初めの総括、SPARKが示すものと示さないもの、ほかに検討した形、Goのコードへの形式手法）は、#90。

**分ける理由**

- 監査：いまの鎖と、頭の書き出し（7.4の「改ざんの検知」）は、書き換えを見つける仕組み。分けると、管理のサーバーからは、過去の記録を、書き換えられなくなる。2つは補い合う。
- サルベージ：管理のサーバーが破られても、それより前の履歴は信頼できる。保存先は、すべての版を持つ（3.4の「表」）ので、復旧は、バックアップからの復元ではなく、「ある連番より前の版に戻す」操作になる。分けないと、ログのファイルを、直接書き換えられた可能性が残る。
- DoS：資源を、サービスごとに区切れる。書き込みの上限を、デーモンで強制できる（足すだけの保存先では、ディスクを埋められるのが、いちばんのDoS）。公開サイトは、静的なので、もともと影響を受けない。

**プロセスと境界**

| プロセス | Unixユーザー | 開くもの |
| --- | --- | --- |
| 管理のサーバー（`whiteroom serve admin`。9.6） | 管理用のユーザー | デーモンのソケット（書き手用と読み手用）と、出力先（4.3） |
| 読み手（`whiteroom build -data`・`whiteroom backup`・`whiteroom doctor`。9.4） | 読み手用のソケットに繋げるユーザー | デーモンの、読み手用のソケット |
| DBのデーモン | デーモンのユーザー（管理用とも、公開用とも別） | データのディレクトリ（`logdb/` と `files/`。3.4） |
| 公開用のサーバー（`whiteroom serve public`。9.5） | 公開用のユーザー | 出力先だけ。DBには繋がらない（いまと同じ） |

- 境界（決定済み。13章）：境界は、プロセスとUnixユーザー。データのディレクトリを開くのは、デーモンだけ。管理のサーバーも、読み手（ビルド・バックアップ・検査）も、Unixドメインソケットのプロトコルで繋ぐ。
- 管理のサーバーの中の `store`：検証・索引・監査の記録（鎖の計算も）は、いまと同じGoのコードで、管理のサーバーの中で動く。デーモンに送るのは、できあがった操作の束。
- 書くコマンド（`whiteroom init`・`whiteroom account`。9.4）：書き手として繋ぐ。書き手の接続は1つなので、`whiteroom account` は、いまと同じく、管理のサーバーを止めて動かす。データのディレクトリを作る手順（いまは `whiteroom init` が作る）は、決めていない（6.12の269）。

**デーモンが守る規則**

中身を知らずに守れるものに限る（案）。

- 書き手の接続は、1つだけ。
- オブジェクトと原本は、中身のSHA-256が、名前と合い、大きさが、上限までであること。
- 足すだけの表（`history`・`revisions`・`entryRevisions`。3.4の「表」）では、書き換えと削除を断る。
- 表を変えるコミットには、監査イベントが要る（7.4の「記録の無い書き込みを断る」を、デーモンでも守る）。
- 期待する連番が合うときだけ、確定する。
- 同期に失敗したら、止まる（下記の「同期の失敗」）。
- 上限を守る（下記の「上限」）。ソケットは、新しい攻撃の面になる。
- コミットごとに、印を付ける（下記の「印」）。
- 鎖の頭を、保存先の外に書き出す（下記の「頭の書き出し」）。

デーモンが知らないことと、限界：

- 知らないこと：コンテンツの型と検証（`internal/content`）、索引の行の意味、アカウントと権限、監査の記録の中身と鎖の計算。これらは、管理のサーバーの中の `store` から上に残る。
- 限界：破られた管理のサーバーは、新しい偽の記録を足せる。できないのは、過去の履歴と記録を、消すことと書き換えること。

**接続（決定済み。13章）**

- ソケット：デーモンは、Unixドメインソケットを、2つ作る（書き手用・読み手用）。繋げる人は、ソケットのファイルのモード（0660）とグループで決める（管理用のサーバーのソケットと同じやり方。9.4の「`whiteroom serve admin`」）。
- 相手のUnixユーザー：デーモンは、繋いだ相手のUnixユーザーを、OSから受け取って（Linuxの `SO_PEERCRED`）確かめ、書き手は、設定で決めた1つのユーザーだけにする。モードを誤って緩めても、書き手は増えない。
- 管理のサーバー（案）：書き手用の接続を1つと、読むための接続（読み手用のソケット）を、要るだけ持つ（1つの接続は、多重にしないため。下記の「プロトコル」）。
- ソケットのパスと、グループの決め方の例は、決めていない（6.12の269）。

**プロトコル（決定済み。13章）**

- 版と互換：プロトコルの版は、1つの数。繋ぐとき（`Hello`）に比べ、同じ版でなければ、何も変えずに拒む（両方の版を示す）。交渉はしない。2つの実行ファイル（下記の「実行ファイル」）は、同じリリースで配り、一緒に入れ替える。長く保つ互換は、ディスクの形（エンジンの形の版と、表の版。3.4の「エンジンと設定」・3.5の「ファイルの形」）が受け持つ。
- メッセージ：次の13個。

| 使えるもの | メッセージ | 内容 |
| --- | --- | --- |
| 書き手と読み手 | `Hello` | 版を確かめる。答えは、デーモンの起動ごとのID・いまの連番・上限 |
| 書き手と読み手 | `Snapshot`・`Release` | ある連番の時点を固定する・放す |
| 書き手と読み手 | `Get`・`Scan` | 表とキーで、値を1つ・接頭辞で、キーの順に |
| 書き手と読み手 | `Object`・`Original` | ハッシュで、オブジェクト・原本の中身 |
| 書き手と読み手 | `Events` | 監査イベントを、番号の順に |
| 書き手と読み手 | `Verify`・`Backup` | エンジンの確かめ・写しのファイルを、順に返す（下記の「保守の口」） |
| 書き手だけ | `PutObject`・`PutOriginal` | 置く。デーモンが、SHA-256と大きさを確かめる |
| 書き手だけ | `Commit` | 期待する連番・操作の束・監査イベント。答えは、新しい連番と、印の時刻 |

- 送り方：1つの接続では、要求と答えを、1つずつ、順に送る（多重にしない）。同時に読むには、接続を増やす。大きいもの（オブジェクト・原本・`Scan`・`Events`・`Commit`・`Backup`）は、枠に分けて流す。
- 操作のID：プロトコルの欄にしない。いまと同じく、操作の束の中の1行（表 `operations`。3.4の「索引」）。
- バイトの並び（枠の見出し、整数の形、エラーの答えの形）は、決めていない。デーモンを作るときに、コードと一緒に決める（6.12の266）。

**1回の保存の流れ**

メッセージの使い方（案）。

1. `Snapshot` で、ある連番の時点を固定し、`Get`・`Scan` で、いまの版と索引を読む。
2. 管理のサーバーの中で、検証し、索引と監査の記録を作る（いまと同じGoのコード）。
3. `PutObject` で、オブジェクトを先に置く（デーモンが、SHA-256を確かめる）。原本は、`PutOriginal` で置く。
4. `Commit`（期待する連番・操作の束・監査イベント）を送る。デーモンは、連番と規則を確かめ、印のイベントを足し、ログに追記して同期してから、答える。

- `store` の形：いまは、トランザクションの中で、Goの関数が走る（`Update`。3.4の「操作」）ので、`store` の中の、エンジンを使う口の形は変わる。
- 答えが来ないとき：書き手は1つなので、繋ぎ直したときの連番が進んでいれば、自分のコミットが確定している。管理のAPIの再送は、いまと同じく、操作のIDで、2度しない（3.5の「冪等性の責務」）。

**上限（仮置き）**

上限を置くことと、その種類は、決めた（決定済み。13章）。値は、仮置き：デーモンの設定で変えられるようにし、デーモンを作るときに、測って見直す（6.12の267）。

| もの | 仮の値 | もと |
| --- | --- | --- |
| 枠（メッセージの切れ端） | 1MiB | デーモンが、1度にメモリに持つ量 |
| 1回の `Commit` | 268435446バイト（256MiBより10バイト少ない） | エンジンのコミットのレコードの上限（3.5の「制限」）のまま |
| オブジェクト・原本 | 64MiB | 文書と原本の上限（3.4の「上限」）のまま |
| 接続 | 書き手1、読み手64 | 管理のサーバーの同時の読み・ビルド・コマンド |
| スナップショット | 接続ごとに1つ。最後の要求から5分で放す | 止まった相手が、メモリを持ち続けない |
| 進まない要求 | 30秒で切る | 遅い相手が、接続を塞がない |
| `Commit` の頻度 | 1秒に50回。超えたら、拒まずに待たせる | セッションの書き込みは、5分に1回まで（6.12の219）。人の保存は、それより少ない |
| 全体の量 | ファイルシステムの空きが、1GiBを下回る書き込みを拒む | 埋まると、圧縮も修復もできなくなる |

**印（決定済み。13章）**

- 中身：デーモンが、コミットごとに付ける、デーモンの時計の時刻（UTC）だけ。連番は、レコードにある。時計が戻っても、そのまま記す（順は、連番が決める）。
- 理由：いまは、保存した日時（3.4の「表」）と、記録の時刻（7.4の「番号と時刻と鎖」）を、管理のサーバーの中の `store` が付けるので、破られると偽れる。印があれば、破られた期間を特定でき、サルベージの起点になる。
- 置き方：デーモンが、コミットごとに、自分のイベント（3.5の「イベント・操作のID・暗号化の封筒」）を足す。エンジンのファイルの形は、変えない（下記の「ファイルの形」）。イベントは、ログにだけあり（メモリには数だけ）、圧縮でも、書き直しで落とさなければ残る。
- 読む側：記録を読む口と確かめる口（7.4）は、印のイベントを飛ばす。そのため、表の版（3.4の「エンジンと設定」）を、7に上げる。
- 印のイベントのバイトの並びは、決めていない（6.12の266）。

**頭の書き出し（仮置き）**

- 決めたこと（決定済み。13章）：鎖の頭を、保存先の外に書き出すこと（7.4の「改ざんの検知」）を、デーモンの側に移す。管理のサーバーに残すと、破られたときに、止められる。
- 形（仮置き）：デーモンは、監査の鎖の計算を知らない。そこで、管理のサーバーの中の `store` が、ログごとの頭の行（7.4の形。`audit head <ログ> <番号> sha256:<64桁の小文字の16進数>`）を、その記録と同じコミットで、書き出し用の表に置く。デーモンは、その表の行を、中身を読まずに、そのまま、自分の標準エラーに書く：起動のときに、すべての行を1回、そのあと、1分ごとに、変わった行、止めるときに、もう1回（いまの `whiteroom serve admin` と同じ間隔。9.4）。デーモンが確かめるのは、行の形（長さと、使える文字）だけ。
- 限界：破られた管理のサーバーは、偽の頭を置ける。できるのは、確かめを失敗させること（誤った警報）だけで、書き換えは隠せない（7.4の「改ざんの検知」の、偽の頭の行と同じ）。破られる前に書き出した頭は、変えられない。
- 決めていないこと：デーモンが、中身に依らない自分の鎖（イベントのバイト列のハッシュの鎖）を持って、それを書き出す形にするか（6.12の268）。

**原本（決定済み。13章）**

- デーモンが持つ：メディアの原本（`files/`。3.4の「原本」）も、デーモンが持つ。分ける理由（サルベージ）は、原本にも当たる：管理のサーバーが `files/` を直接書けると、破られたときに、原本を消せる。
- 送り方：原本は、ソケットで、枠に分けて送り（`PutOriginal`）、受ける（`Original`）。デーモンが、SHA-256と大きさを確かめる。
- 一時のファイル：管理のAPIの一時のファイル（いまは `files/.tmp-…`。3.4の「原本」の `CreateTemp`）は、管理のサーバーの側の場所に移す。置き場所は、決めていない（6.12の270）。

**保守の口（決定済み。13章）**

- 書き換えるもの（圧縮・回収・修復。3.5の「保守モード」）：デーモンの実行ファイルのサブコマンド。デーモンを止めて、サーバーの上で動かす。ソケットには出さない：履歴を消せる操作なので、ソケットに出すと、破られた管理のサーバーが、履歴を消す口になる。
- 読むだけのもの（検査・バックアップ）：読み手の接続のメッセージ（`Verify`・`Backup`）。`whiteroom doctor`・`whiteroom backup`（9.4）は、いまのコマンドのまま、ソケットで繋ぐ。
- 写しの確かめ（リストアの前）の口は、決めていない。写しは、デーモンが開いていないディレクトリなので、候補は、デーモンの実行ファイルのサブコマンド（6.12の131）。
- 書きながらの圧縮と回収は、変わらず、決めていない（6.12の133）。

**同期の失敗（決定済み。13章）**

同期に失敗した後の、再起動の強制（6.12の129）のうち、デーモンの形に依るもの。作るのは #68。

- 拒む範囲：止まった印があって、同じ起動（マシンを再起動していない）なら、デーモンは起動しない。書き手も読み手も繋げず、保守のサブコマンドも動かない。
- 同じ印：エンジンの同期の失敗（3.5の「失敗の扱い」）も、原本の同期の失敗（3.4の「原本」）も、同じ印で、デーモンの全体が止まる（いまは、原本の同期の失敗では、原本の保存だけが止まり、文書の書き込みは続く）。
- 置き場所と形：データのディレクトリの直下の、デーモン（Goの側）のファイル。エンジンの形の版にも、表の版にも入らない。
- 方法（起動ごとのIDなど）、同期のほかの失敗の扱い、印を残すこと自体の失敗、印のファイルの名前と中身は、決めていない（6.12の129）。

**ファイルの形（決定済み。13章）**

- エンジンのファイルの形は、3.5のまま（形の版は1）。デーモンの印は、形を変えずに、デーモンが足すイベントで持つ（上記の「印」）。
- 理由：形を変えないので、Goのエンジンと核を、同じディレクトリで比べられ（下記の「進める順」の4）、形の版の移行（6.12の131）を待たない。
- 形を変えるときの道（仮置き。作るのは #70）：書き直して移す（保守の圧縮が、新しい世代を、いまの版で書く。3.5の「移行・バックアップ・リストアの条件」）。読めるのは、いまの版と1つ前の版で、書くのは、いまの版だけ。読む版を2つに限るのは、核の復号と証明が、版の数だけ増え続けないため。プログラムを前の版に戻すときの扱いは、決めていない（6.12の131）。

**お問い合わせ（決定済み。13章）**

- お問い合わせを受け付けるプロセス（8章）は、このデーモンに、役割を絞った書き手として繋がない。別のデータのディレクトリに、同じデーモンを、もう1つ動かす。
- 理由：迷惑送信で埋まるのは、お問い合わせの保存先だけ。保持の期間で消す個人情報を、小さい保存先の圧縮で消せる。デーモンの規則は、書き手1つのまま。
- 細部は、お問い合わせを作るときに決める（8章）。

**実行ファイル（決定済み。9.1）**

- 2つ：`whiteroom`（Goだけ）と、DBのデーモン（Goと核。名前は、仮に `whiteroom-db`）。デーモンの数と、実行ファイルの数は、別のもの（権限は、プロセスとUnixユーザーで決まる）。
- 理由：cgoが要るのは、デーモンだけ。公開用のサーバーを含む `whiteroom` は、cgoなしのビルド（`CGO_ENABLED=0`。3.4の「依存」）を保てる。1つの実行ファイルにすると、公開用のサーバーも、cgoでリンクしたファイルになり、cgoなしの静的なビルド（6.12の126）ができなくなる。
- 引き受けるもの：2つの版を、揃えて入れる。繋ぐときに、版を確かめる（上記の「プロトコル」）。
- 実行ファイルの名前、コードの置き場所、保守のサブコマンドの名前、systemdのユニットと起動の順は、決めていない（6.12の269）。

**エンジンの形（決定済み。3.1）**

| 形 | Adaで書く範囲 | `simfs` の行列（3.5の「テスト」） | ビルド | 扱い |
| --- | --- | --- | --- | --- |
| Goのまま（いまのエンジンを、デーモンに入れる） | 無い | そのまま使える | いまのまま（`CGO_ENABLED=0` も通る） | 下記の「進める順」の2で使い、核ができるまで、正解の役をする |
| Goのデーモンに、Ada/SPARKの核を、cgoで入れる（I/OはGo） | 下記の「核の範囲」 | そのまま使える（I/Oが `vfs` を通る） | Goのビルドに、GNATとCのリンクが要る。`CGO_ENABLED=0` は使えず、クロスビルドが難しくなる | 決めた |
| すべてAdaのデーモン | エンジン・サーバー・接続・並行・I/Oの束縛 | Adaで作り直す | Goの側は、いまのまま。Adaは別にビルドし、実行ファイルが2つになる | 採らない。Adaの範囲が広く、証明しにくい部分（サーバーと並行）が入る |

決めた形の中身：

- 核は、エンジンのうち、ファイルを触らずに、判断と計算だけをする部分。Goから、関数として呼ぶ。
- 「どのファイルに、どの順で、書く・同期する・名前を変えるか」は、核が、指示の列として返す。Goの側が、いまの `vfs`（3.5の「構成」）で、そのとおりにI/Oをし、成功か失敗かを、核に返す。
- いまの証拠が残る：`simfs` のクラッシュ・失敗の差し込みの行列を、そのまま核に流せる。Goのエンジンと核を、同じテストの中で比べられる。
- 証明が届く範囲が広がる：書く順の規則を、指示の列の性質として、SPARKで証明できる（ファイルシステムの模型は、仮定のまま）。
- Adaの側が小さい：ソケットも、並行も、`fsync` の束縛も要らない。
- 分担：Goは、サーバー・並行・I/Oの標準ライブラリと、いまのテスト。Ada/SPARKは、間違えるとデータが壊れる部分（形の符号化と復号、復旧の判断、書く順）の証明と、範囲つきの型。
- 前提（メンテナーが置いた。13章）：リリースが無いので、作り直しは、いとわない。cgoを使わない制約は、サードパーティの依存を無くすためのもので、自作のコードを繋ぐcgoは、別に扱う（1.2）。

引き受けるもの：

- cgoの継ぎ目は、だれも証明しない：SPARKの証明は、呼ぶ側が事前条件を守ることを前提にする。Goの側には、その保証が無いので、核の入り口で、引数を、実行時に確かめ直す。長さと寿命の取り違えは、こういう継ぎ目に集まりやすい。
- 証明するのは「指示」で、「実行」ではない：Goの側が、指示のとおりに実行したかは、証明の外で、いまと同じく、`simfs` の行列で確かめる。クラッシュの後の整合性は、順序の証明と、実行のテストの合わせ技になる。
- 設計が素直でなくなる：書く側は、「指示を返し、結果を受け取る」状態機械になる。同期の失敗のようなエラーの道も、継ぎ目を2回通る。
- 2つの言語と道具を、持ち続ける：ファイルの形を変えるたびに、Adaの証明と、Goの実行とテストの両方を直す。ビルドには、GNATが要る。
- 条件：中心の部分で、証明をやり切ること。証明をしないAdaは、動的なメモリと並行の安全性・先例・テストの道具で、Rustに劣る。

**核の範囲（決定済み。3.1）**

線：判断に、メモリの状態（表やオブジェクトの索引）が要らないものは、すべて核に入れる。

| 核に入れる | Goに残す |
| --- | --- |
| 形の符号化と復号のすべて：セグメント・枠・レコード・`head`・チェックポイント・オブジェクトの見出し、CRC（いまの `format.go`・`ops.go` と、`checkpoint.go` の符号化と復号に当たる） | 実際のI/O（`vfs`）、ロック、サーバー、接続、並行 |
| ログを読むときの判断：レコードの順、末尾がちぎれているのか壊れているのか、どの世代を使うか、チェックポイントがログと合うか（いまの `recover.go` の、何も変えずに決める側に当たる） | 受け入れたレコードを、表と索引に当てはめること（`state.go`・`pmap.go`）、スナップショット |
| 書く順の指示：コミット、セグメントの切り替え、オブジェクトのファイル、チェックポイント、復旧の後始末（いまの `commit.go`・`checkpoint.go` と、`recover.go` の、決めたことを実行する側の、順を決める部分に当たる） | メモリの状態を見る検査（同じオブジェクトが、もうあるか。ベースの終わりの数が合うか） |
| | 保守（圧縮・回収・バックアップ・検査）の進行。核の符号化と復号は使う |

- 量：いまのエンジン（テストを除いて約4,800行）の、3分の1ほど。
- この線にする理由：
  - いまのコードに、同じ継ぎ目がある：復旧は、「何も変えずに決める」と、「決めたことを実行する」に分かれている。
  - 状態を見る検査は、核の判断に戻ってこない：「切るか、壊れているとして拒むか」は、枠のCRCが合うかどうかだけで決まる。CRCが合った後に、Goの側の検査に落ちたものは、必ず「壊れている」で、切ることはない。だから、核は、表を知らなくて済む。
  - 核は、メモリを確保しない：核は、Goが渡したバッファを読み、位置と数だけを返す。キーと値は、Goが、自分のバッファから取り出す。Adaの側のメモリの管理が無くなり、継ぎ目で寿命を取り違える危険が、ほぼ消える。
- 入れないもの：
  - メモリの状態（表と、書き換えない木。3.5の「スナップショット」）：移すと、共有する構造を、SPARKの所有権のモデルで作り直すことになり、証明が重くなる割に、得るものが小さい。
  - 保守の進行：圧縮にも、「新しい世代が揃うまで、古い世代を消さない」という順の規則があるので、後から核に入れる候補。最初は入れない（6.12の272）。

**証明**

対象の候補：

1. どんなバイト列を渡しても、実行時エラーにならない。
2. 符号化したものを復号すると、元に戻る。
3. CRCが合ったレコードは、決して切らない（切ると、確定したコミットを失う）。
4. 切るのは、最後のセグメントの末尾だけ。受け入れた連番は、続いている。
5. 名前を変えるのは、同期の後。レコードを足すのは、それが指すオブジェクトのファイルが残ると決まった後。新しいセグメントに初めのレコードを足すのは、その見出しと名前が残ると決まった後。
6. 同期に失敗した後は、書く指示を、二度と出さない。

- 3から後は、いまは、テストだけで守っている規則。
- 水準（決定済み。13章）：6つすべてを、目標にする。Goのエンジンから差し替える（下記の「進める順」の4）条件は、1〜4と、6。5（書く順）は、電源断の確かめ（6.12の130）の結果で、規則を確かめた後に証明し、証明できなかった部分は、3.5に「証明の外」と書く。
- SPARKが示さないもの：クラッシュの後の整合性は、ファイルシステムの振る舞いの模型の上の性質で、証明しても、`simfs` と同じ前提を、仮定として書くことになる。電源断（6.12の130）、同期に失敗した後の再起動（129）、検出と修復と移行の道具（131）、メモリと開く時間（132）の危険は、言語を替えても減らない。
- 核を作り始めるときに確かめること（GNATのランタイムと、Goのランタイムの共存など）は、6.12の271。

**進める順**

Goのエンジンは、捨てる前に、正解の役として使う。
