### 3.6 保存の層のデーモンと、エンジンの核（案）

保存の層（3.4・3.5）を、管理のサーバーとは別のプロセス（DBのデーモン）にし、エンジンの核を、Ada/SPARKで書く。この節は、その決定と、規則。デーモンは作った（`cmd/whiteroom-db`・`internal/dbserver`・`internal/dbwire`・`internal/dbclient`。issue #109。下記の「進める順」の2）。核は、まだ作っていない（下記の「進める順」の3.1以降）。この節の規則は、作ったものについては、コードのとおり。

**目的と状態**

- 決定（決定済み。3.1。メンテナーの判断。2026-11-12）：(1) 保存の層を、管理のサーバーとは別のプロセス（DBのデーモン）にする。(2) エンジンは、Goのデーモンに、I/Oを持たないAda/SPARKの核を、cgoで入れる形にする。(3) 核の範囲は、「判断に、メモリの状態（表やオブジェクトの索引）が要らないものは、すべて核に入れる」という線で決める。
- この節の規則：見出しか文に「決定済み」と書いたものは、メンテナーの判断（2026-11-12 と 2026-11-15。13章）。「仮置き」と書いたものは、作るときに見直す。ほかは、案（issue #109 の計画への答え（2026-11-15）と、issue #68 の計画への答え（2026-11-23）と、issue #70 の計画への答え（2026-11-23）で決めたものも、案）。
- 状態：デーモン（下記の「進める順」の2）は、作った：エンジンは、ファイルの形を変えず、デーモンの中で動く（`whiteroom-db`）。管理のサーバーと、ほかのコマンドは、データのディレクトリを開かず、ソケットで繋ぐ。核（Ada/SPARK。3.1・3.2）は、まだ作っていない（#110・#111・#112）。同期に失敗した後の再起動の強制（#68）は、作った：デーモンが、止まったときのマシンの起動ごとのID（Linux の boot ID）を、データのディレクトリの印に残し、マシンを再起動するまで、`serve`・`compact`・`gc`・`accept-break` は、そのデータのディレクトリを断る（下記の「同期の失敗」）。検出の穴を埋め、写しの確かめ（`whiteroom-db check`）と、ログイン履歴の古い記録を消すこと（`whiteroom-db compact`）と、読める鎖の切れ目を認める口（`whiteroom-db accept-break`）は、作った（#70。下記の「保守の口」）。エンジンの修復（#144）と、形の版の移行（#145）は、まだ無い。作っていないものは、下記の各所に書く。
- 検討の記録（初めの総括、SPARKが示すものと示さないもの、ほかに検討した形、Goのコードへの形式手法）は、#90。

**分ける理由**

- 監査：いまの鎖と、頭の書き出し（7.4の「改ざんの検知」）は、書き換えを見つける仕組み。分けると、管理のサーバーからは、過去の記録を、書き換えられなくなる。2つは補い合う。
- サルベージ：管理のサーバーが破られても、それより前の履歴は信頼できる。保存先は、すべての版を持つ（3.4の「表」）ので、復旧は、バックアップからの復元ではなく、「ある連番より前の版に戻す」操作になる。分けないと、ログのファイルを、直接書き換えられた可能性が残る。
- DoS：資源を、サービスごとに区切れる。書き込みの上限を、デーモンで強制できる（足すだけの保存先では、ディスクを埋められるのが、いちばんのDoS）。公開サイトは、静的なので、もともと影響を受けない。

**プロセスと境界**

| プロセス | Unixユーザー | 開くもの |
| --- | --- | --- |
| 管理のサーバー（`whiteroom serve admin`。9.6） | 管理用のユーザー | デーモンの書き手用のソケット（接続は1つ）と、書き手のロック（下記の「接続」）、読み手用のソケット（要るだけ）、出力先（4.3）、一時のファイルのディレクトリ（設定の `tmp`。9.4・9.7） |
| 読み手のコマンド（`whiteroom build -db`・`whiteroom backup`・`whiteroom doctor`。9.4） | 読み手用のソケットに繋げるユーザー | デーモンの、読み手用のソケット |
| 書くコマンド（`whiteroom init`・`whiteroom account`。9.4） | 書き手用のソケットに繋げるユーザー（書き手のユーザー） | デーモンの、書き手用のソケットと、書き手のロック |
| DBのデーモン（`whiteroom-db serve`） | デーモンのユーザー（管理用とも、公開用とも別） | データのディレクトリ（`logdb/` と `files/`。3.4）と、2つのソケットのファイル（書き手のロックのファイルは、作るだけ） |
| 公開用のサーバー（`whiteroom serve public`。9.5） | 公開用のユーザー | 出力先だけ。DBには繋がらない（いまと同じ） |

- 境界（決定済み。13章）：境界は、プロセスとUnixユーザー。データのディレクトリを開くのは、デーモンだけ。管理のサーバーも、読み手（ビルド・バックアップ・検査）も、Unixドメインソケットのプロトコルで繋ぐ。
- 機械で確かめる（案）：エンジン（`internal/logdb`）とデーモンのサーバー（`internal/dbserver`）を import してよい本番のコードは、`cmd/whiteroom-db` と、その2つのパッケージだけ。`.golangci.yml` の depguard の規則 `to-engine` が確かめる（`AGENTS.md`）。`whiteroom` は、エンジンなしでビルドできる（`internal/logdb` も `internal/dbserver` も、依存に出ない）。
- 管理のサーバーの中の `store`（案）：検証・索引・監査の記録（鎖の計算も）は、いまと同じGoのコードで、管理のサーバーの中で動く。`internal/store` は、デーモンのクライアント（`internal/dbclient`）の上に載る。デーモンに送るのは、できあがった操作の束（`Commit`）。デーモンは、`internal/content` を import しない（コンテンツのモデルを知らない）。
- 書くコマンド（案）：書き手として繋ぎ、動いている間、書き手のロック（下記の「接続」）を持つ。書き手は1つなので、`whiteroom account` は、`whiteroom serve admin` を止めて動かす（動いている間は、断られる）。データのディレクトリを作るのは、`whiteroom-db init`（下記の「実行ファイル」）で、`whiteroom-db serve` は作らない。`whiteroom init` は、`whiteroom-db init` が作った、動いているデーモンの保存先に、最初の管理者とサイトを入れる（9.4）。

**デーモンが守る規則**

中身を知らずに守れるものに限る（案）。断ったとき、保存先は何も変えない。相手が見る符号は、下記の「バイトの並び」の符号の表のとおりで、文は、コード（`internal/dbserver`）のとおり（文に、キー・値・オブジェクトの中身は入らない。入るのは、長さ・種類・符号・表の番号）。

| 規則 | 断るとき（符号。文） |
| --- | --- |
| 書き手の接続は、1つだけ | `Hello` に `busy`。`another writer is connected` |
| 書く要求（`PutObject`・`PutOriginal`・`Commit`）は、書き手の接続だけ | `denied`。`only the writer may commit`（`put an object`・`put an original`） |
| 書き手のUnixユーザーは、設定の1つだけ（下記の「接続」） | `Hello` に `denied`。`the user 1001 is not the writer of this daemon` |
| スナップショットを持ってから、`Get`・`Scan`・`Object`・`Events`・`PutObject`・`Commit` を送る（`Original`・`PutOriginal`・`Verify`・`Backup` は、要らない） | `no snapshot`。`no snapshot is held; send a Snapshot first` |
| 期待する連番が合うときだけ、確定する | `seq`。`the last sequence number is 12, not the expected 11` |
| オブジェクトと原本は、中身のSHA-256が、名前と合い、大きさが、上限までであること | `hash`。`the data do not have the hash that was given`（原本は `the data do not have the hash and the size that were given`）。大きさの上限は、下記の「上限」 |
| 原本は、空でない | `rule`。`the original is empty` |
| 足すだけの表（`history`・`revisions`・`entryRevisions`。3.4の「表」）の行は、消さず、書き換えない | `rule`。`op 3: table 3 is append-only: a row is not deleted`（書き換えは `…: a row is not changed`） |
| 行を足す・書き換える・消すコミットには、監査イベントが要る（7.4の「記録の無い書き込みを断る」を、デーモンでも守る） | `rule`。`a commit that puts or deletes a row needs an audit event` |
| イベントは、空でなく、デーモンの印の1バイト目（`0x00`。下記の「印」）で始まらない | `rule`。`op 1: an event is empty`・`op 1: an event starts with the byte that is the daemon's` |
| 何もしないコミット（操作も、置いたオブジェクトも無い）は、断る | `rule`。`a commit with no op and no staged object` |
| 書き出し用の表 `heads`（下記の「頭の書き出し」）の行は、頭の行の形で、消さず、16行まで | `rule`。`op 2: not a valid row of table 11`・`op 2: a row of table 11 is not deleted`・`the table of the heads would have more than 16 rows` |
| 鎖の始まりと認めた切れ目の表 `chains`（12。3.4の「表」）の行は、書き手が、足さず、書き換えず、消さない（書くのは、デーモンの保守だけ。下記の「保守の口」）。ほかの表の規則より先に確かめる | `rule`。`op 2: table 12 is written only by the maintenance of the daemon` |
| 確定した後の `meta` の `schema` の行は、あり、正しく、デーモンの知る版より新しくなく、前より低くない（デーモンが、開き直せない状態を、確定しない） | `rule`。`the commit would leave the store without its schema version`・`the commit would leave an invalid schema version`・`the commit would set the schema version 9, newer than this daemon knows (8)`・`the commit would lower the schema version from 8 to 7` |
| 表の番号は、0でない | `limit`。`op 0: invalid table 0` |
| 同期に失敗したら、書くのを止め、印のファイルを残す（マシンを再起動するまで、デーモンは起動しない。下記の「同期の失敗」） | `stopped`。`the store has stopped after a sync failed; restart the machine before starting the daemon again` |
| 上限を守る（下記の「上限」。ソケットは、新しい攻撃の面になる） | `limit`・`no space`・`busy` |

- 規則の外のこと（案）：コミットごとに、印を付ける（下記の「印」）。鎖の頭を、保存先の外に書き出す（下記の「頭の書き出し」）。
- 守る順（案）：書く要求（`PutOriginal` は、スナップショットを除く）は、書き手か、スナップショットがあるか、止まっていないか、の順に確かめ、断るときも、要求の残りを（上限まで）読んでから答える。`Commit` は、規則・空き・頻度の枠・連番の順に確かめる。
- 起動のときの確かめ（案）：デーモンは、まず、マシンの起動ごとのID（Linux の boot ID）が読めないか、データのディレクトリの、同期に失敗した後の印（`stopped`）が、いまの起動のものか、読めないものなら、始まらない（文は、下記の「同期の失敗」）。次に、データのディレクトリそのものに、このユーザーが書けなければ（`access(2)`）、始まらない（下記の「同期の失敗」の「書けるかの確かめ」）。次に、コミットのあるデータのディレクトリが、`meta` の `schema` の行を持たなければ、`<DIR>/logdb: not a store of whiteroom (no schema version)` で、行が正しくなければ `<DIR>/logdb: meta "schema": invalid value` で、行が、デーモンの知る版（`dbwire.TableVersion`）より新しければ `<DIR>/logdb: the store schema is of version 9, newer than this program knows (8)` で、始まらない。どれも、エンジンがファイルを変える前に断る。コミットが無い（`whiteroom-db init` の直後の）ものは、開く。

デーモンが知らないことと、限界：

- 知らないこと：コンテンツの型と検証（`internal/content`）、索引の行の意味、アカウントと権限、監査の記録の中身と、鎖の確かめ（`VerifyAudit`）。これらは、管理のサーバーの中の `store` から上に残る。`meta` の `schema` の行は、uvarint として読む。`heads` の行は、形だけ確かめる。表 `chains` の行は、書き手からは受け付けないので、読まない。デーモンが、記録を読むのは、保守（`whiteroom-db compact`・`accept-break`）の中だけで、`serve` は、記録を読まない（案。#70 の計画への答え（2026-11-23）で決めた）。保守が読むのは、記録のJSONの `log`・`n`・`prev` の3つのメンバーだけ（`dbwire.ReadRecordID`。`encoding/json/v2`。メンバーの名前は、一字一句、合わせる。重なった名前・不正なUTF-8・1から2^64-1の整数でない `n` は、記録として読めないとして、読まない）で、記録の、保存したバイト列の SHA-256 を、鎖の計算のために求める。ほかのメンバー（時刻・操作・対象・クライアントなど）は、読まない。`internal/audit` も `internal/content` も、import しない（depguard）。
- 限界：破られた管理のサーバーは、新しい偽の記録を足せる。できないのは、過去の履歴と記録を、消すことと書き換えること。偽の頭（`heads` の行）を置いて、確かめを失敗させることもできる（下記の「頭の書き出し」）。

**接続**

- ソケット（決定済み。13章）：デーモンは、Unixドメインソケットを、2つ作る（書き手用・読み手用）。繋げる人は、ソケットのファイルのモード（0660）とグループで決める（管理用のサーバーのソケットと同じやり方。9.4の「`whiteroom serve admin`」）。
- 名前と置き場所（案）：ソケットは、`writer.sock` と `reader.sock`。置くディレクトリは、`-db DIR`（設定ファイルの `db`）で渡す。デーモンは、そのディレクトリを作らない（無ければ、`DIR: the directory of the sockets does not exist; make it first, which serve does not` で、始まらない）。ソケットのパスは、107バイトまで（`listen unix …: the path of a socket has at most 107 bytes, and this one has 120`）。`@` で始まるパスは断る（抽象ソケットで、ファイルが無いため）。前のデーモンが残した、だれも待ち受けていないソケットのファイルは、置き換える。ほかのプロセスが待ち受けているか、ソケットでないファイルがあれば、何も変えずに失敗する。デーモンは、止まるときに、2つのファイルを消す。
- グループ（案）：`-writer-group`・`-reader-group`（設定の `writerGroup`・`readerGroup`）で、それぞれのソケットのファイルのグループを替える（名前か数。言わなければ、システムが付けるグループ）。ディレクトリのモードと持ち主は、デーモンは変えない。
- 相手のUnixユーザー（決定済み。13章）：デーモンは、繋いだ相手のUnixユーザーを、OSから受け取って（Linuxの `SO_PEERCRED`）確かめ、書き手は、設定で決めた1つのユーザーだけにする。モードを誤って緩めても、書き手は増えない。
- 書き手のユーザー（案）：`-writer-user`（設定の `writerUser`。名前か数）。言わなければ、デーモンのプロセスのユーザー。書き手用のソケットに、別のユーザーが繋いでも、`Hello` に `denied` で答える（書き手の席は取らない）。読み手用のソケットは、繋いだ相手を、みな読み手にする（ユーザーは見ない）。
- 管理のサーバー（案）：書き手用の接続を1つ持ち、読むための接続（読み手用のソケット）を、要るだけ持つ。読み手の接続の数の上限は、デーモンの `-max-readers`。1つのトランザクション（`View`・`Update`）の要求は、窓も、1つの接続の、1つのスナップショットに行く。上限の64は、管理用のサーバーだけの数ではなく、ほかの読み手（`whiteroom doctor`・`backup`・`build -db`）の接続も含む。管理用のサーバーが持つ読み手の接続は、`View` が同時に使う16まで（`Options.Readers`）と、使っていないもの（プールに戻した、スナップショットの無い接続）の16まで。原本の読み（`Original`）と `Backup` の接続は、この16に数えず（原本を開いたまま `View` を始めても、自分を待たないため。`Backup` は、いつも新しい接続）、デーモンの64には数える。スナップショットを持たない読み手の接続は、デーモンが、`-snapshot-idle`（5分）で、答えずに閉じる（#129。下記の「上限」）ので、使っていない接続は、5分使わなければ閉じられ、止まったコマンドや、接続を返さないプログラムの席も、5分（スナップショットを持っていたものは、放してから、さらに5分で、10分）で空く。次の `View`・`Verify`・原本の読みは、閉じられた接続の最初の要求が失敗した後、新しい接続で1回やり直す（失敗する1回の書き込みと、繋ぐ時間が、足されるだけ。やり直すのは、副作用の無い要求だけ。`Backup` は、いつも新しい接続）。最後の要求から10分（スナップショットを放す5分と、その後の5分）を超えて何も読まない `View` の、次の読みは、`cannot reach the daemon`（`store.ErrUnavailable`）で失敗する（前は `no snapshot`）。64と、クライアントの16・16・数えない接続の関係は、設計し直さず、同時に開いた数も、測っていない（6.12の267・287）。
- 待ちと繋ぎ直し（案）：クライアント（`internal/dbclient`）は、デーモンに届かないときと、書き手の接続が `busy` のとき（前の書き手の接続が、いま終わったばかりのとき）、50ミリ秒おきに、2秒まで、繋ぎ直す（`Options.DialWait`。負の数は、1回だけ）。それでも繋がらなければ、`cannot reach the daemon` を包むエラー（`store.ErrUnavailable`）か、`DIR: another process is connected as the writer` で失敗する。デーモンが止まって、また動いたときは、クライアントの次の `View` と `Update` が、新しい接続で動く（`Open` し直さない）。止まりかけのデーモンが、開いている接続の要求を `busy`（`the daemon is closing`）で断ったときは、クライアントは、その接続を閉じ、`cannot reach the daemon` を包むエラーにする（`DIR: cannot reach the daemon: the daemon is closing`。管理のAPIは、503で答える）。読み手の `Hello` が、待ちの間ずっと、読み手の数の上限の `busy` で断られたときも、同じエラーにする（書き手の `busy` は、`another process is connected as the writer` のままで、`store.ErrUnavailable` ではない。書き手のロック（下記）を持つクライアントのものは、下記のとおり `store.ErrUnavailable`）。書き手の接続が、`Update` か `PutOriginal` の途中で終わったとき（要求のコンテキストが、要求の途中で終わったときなど）は、クライアントは、その呼び出しから戻る前に、書き手として繋ぎ直す（繋ぎ直しは2秒まで試し、答えを待つのは、合わせて7秒まで。繋げなければ、次の書き込みが繋ぐ）：接続の無い間は、デーモンに書き手がいなくて、書き手のロック（下記）を取らないプログラムが、書き手として繋げるため。その分、失敗した呼び出しは、遅く戻る（2026-11-17に測った）：デーモンが途中で無くなったときは2秒、接続を受けて答えないデーモンでは7秒、要求と要求の間でコンテキストが終わったときは、スナップショットを返す後始末の5秒と合わせて12秒まで。デーモンが `PutOriginal` を断ったときも、クライアントは、書き手の接続を取り直す（原本を最後まで読まずに断ったデーモンは、そのセッションを終えるため）。原本を送っている途中で断られたとき（クライアントの書き込みは、切れた接続で失敗する）は、クライアントは、届いている答えを読んで、デーモンの断りを返す（`cannot reach the daemon` にしない。空きが足りないときの `no space` など）。デーモンが、接続を受けて、答えないとき（止められたプロセス・返らないディスクの読みなど）は、下記の「答えを待つ時間」。ソケットのファイルが無いことは、文書や原本が無いこと（`fs.ErrNotExist`）にならない。
- 答えを待つ時間（案。#127）：クライアントは、デーモンの答えを待つ時間に、進み具合で測る上限を持つ（長い要求にも掛かる。デーモンが、合図を送る。下記の「長い要求の合図」）。読む側は、接続の `Read` の1回が、30秒、1バイトも動かなければ、書く側は、`Write` の1回（枠1つ。1MiBまで。窓は32KiBまで）が、30秒で終わらなければ、その接続を閉じ、呼び出しを、`cannot reach the daemon` を包むエラー（`store.ErrUnavailable`）で失敗させる。文は、答えを読む間なら `<DIR>: cannot reach the daemon: the daemon has sent nothing for 30s`、要求を書く間なら `<DIR>: cannot reach the daemon: the daemon has not read the request for 30s`（キーも値も入らない。`whiteroom` のコマンドは、前に `whiteroom <コマンド>: ` を付ける。9.4。管理のAPIは503。9.6・9.7）。値は、デーモンの `-stall` の既定と同じ30秒だが、向きの違う別の上限で、デーモンの `-stall` を変えても、クライアントの30秒は変わらない。変える口は、`dbclient.Options.Stall`（0は30秒、負は上限なし。`DialWait` と同じ形）だけで、変えるのはテスト。`whiteroom` のフラグと設定の項目は無い。
  - 書く側の上限（要求を書く間）：`Write` は、渡したバイトのすべてを書くまで戻らないので、バイトが動いていても、1回が30秒で終わらなければ切る：デーモンが読み続けていても、遅ければ、止まったものとして扱う。枠が1MiBのとき、1MiBを30秒で割ると約35KB/sで、ソケットの送信バッファ（約208KiB）の分は、読まれる前に書けるので、それを引くと約28KB/s：これより遅く読むデーモンも、切る（計算した値で、測っていない）。デーモンは、ふつう、これよりずっと速く読む。デーモンの側は、答えを64KiBずつ書き（`writeStep`。下記の「上限」の「進まない要求」）、64KiBが `-stall`（既定は30秒）で終わらないとき（既定では、約2KB/sより遅いとき）に切るので、向きによって、切る遅さが違う。読む側は、1バイトでも動けば、その `Read` は戻って、次の1回になるので、遅くても、動いている間は、切らない。
  - 掛けるもの：要求を書く間のすべて（`Write` の1回ごと）と、答えを待つ間のすべて（`Read` の1回ごと）：`Hello`・`Snapshot`・`Release`・`Get`・`Scan`・`Object`・窓の読み・`Original` を開くとき・`PutObject`・`PutOriginal`（デーモンが、原本をディスクに同期してから答える間も、この中。下記）・`Verify`・`Commit`・`Events` の答えのすべて・`Backup`（この4つは、デーモンが、動いている間は、合図のバイトを送る。下記の「長い要求の合図」）。`Original` の本体は、`Read` と `Close` の中だけ（呼び出す側が読まない間は、数えない）。`PutOriginal` が送る本体を、呼び出す側の `Reader` から読む間と、`Backup` が写しをディスクに書く間も、数えない（`Read` と `Write` の外の時間は、数えない）。
  - `PutOriginal` の答えを、上限の下に置く理由：デーモンは、本体をすべて受けた後に、一時のファイルの同期と、原本のディレクトリの同期（ディレクトリが新しいときは、`files/` の同期も）と、名前の変更をしてから答える（下記の「原本」）。ファイル1つとディレクトリ2つの同期なので、ふつうは、30秒に届かない。返らないディスクの同期で止まったデーモンの答えも、この上限で、30秒で切れる（掛けないと、呼び出しのコンテキストが終わるまで待つ。`Verify` の答えのように、待つ時間が保存先の大きさで決まるのではないので、合図は要らず、上限を、そのまま掛ける）。超えたとき：クライアントは、`store.ErrUnavailable` で失敗し（管理のAPIは503、コマンドは1）、続けて、書き手の繋ぎ直し（7秒まで。下記の「後始末と繋ぎ直しとの関係」）をする。デーモンは、同期が終われば、原本を置き終え、置かれた原本は残る（同期に、上限の3倍かかるデーモンで確かめた。試しは残していない）。クライアントは、置けたかを知らないので、やり直してよく、やり直すと、デーモンは、同じ名前の原本を書き直して、同期し直す（同じ中身。下記の「原本」）。
  - 長い要求の合図（案。#136・#138・#140）：`Verify`・`Commit`・`Events` の答えと、`Backup` の位置が決まるまでは、待つ時間が、保存先の大きさで決まる（2.6GBの保存先で、`Verify` は3.27〜4.35秒。大きい保存先と遅いディスクでは、30秒を超えうる。下記の「測った値」）：`Verify` は、エンジンの `Verify` が終わった後に、1つだけ答え、`Commit` は、頻度のかごと、`Backup` の読み手が開く間と、ほかの接続の `Verify` を待ち、`Events` は、ログを頭から読み、イベントで枠が満ちるごとに（1MiBまで）送り（合図が、書きかけの枠もそのまま送るので、枠は、1MiBとは限らない）、`Backup` は、位置が決まるまで、何も送らない。そこで、デーモンは、この4つの間、5秒ごとに、その間に、その要求の進み具合（順番かゲートを待つ間は、待つ相手のもの、`Commit` は、`Update` の間、自分の操作と書き込みのもの。下記の「進み具合に数えるもの」）が進んでいれば、答えの中に、合図の枠を1つ書く（長さ0の、終わりの旗の無い OK の枠で、8バイト。プロトコルの版3。下記の「バイトの並び」）。クライアントの読み手は、合図を読み飛ばし、メッセージの本体には何も足さないが、バイトは届くので、30秒の上限は、動いているものとして数える。クライアントは、この4つも、ほかの要求と同じ、30秒の上限の下に置く。
  - 合図を書く範囲と間隔：`Verify` は、答えを始めてから、エンジンの `Verify` が返るまで（デーモンの順番を待つ間も）。`Commit` は、規則・空きの確かめで断らなかった後（断りは、合図の前の、エラーの枠だけの答え）から、`Update` が返るまで（頻度のかごと、`Backup` のゲートと、デーモンの順番を待つ間も。頻度のかごを待つ間は、何も数えず、合図も出ない：書き手は1つで、`Commit` は1つずつなので、待ちは、頻度（1秒に何回か）の逆数の秒以下で、既定の50で20ミリ秒。5秒に届かない。導いた数で、測っていない）。`Events` は、答えを始めてから、エンジンの `Events` が返るまで（イベントの枠が出る間も）。`Backup` は、位置の項目を書く前まで（ゲートを待つ間も。位置の後の、写しの枠が出る間は、送らない）。ほかの要求は、合図を送らない。間隔の5秒は、クライアントの30秒の6分の1で、デーモンの定数（`internal/dbserver` の `defaultPulse`）。変える口は、テストの `dbserver.Options.Pulse`（`dbtest.Options.Pulse`）だけで、`whiteroom-db` のフラグと設定の項目は、足していない。デーモンは、クライアントの30秒を知らない（`Hello` の要求は、版だけを送る）。
  - 合図が書けないとき：合図が書けないのは、クライアントが、接続を閉じたか、壊れたか、30秒読まない（デーモンの `-stall`）ときで、答えを読む相手は、もう居ない。`Verify`・`Events`・`Backup`（位置が決まるまで）は、そのセッションのコンテキストを終え、エンジンが次に記録かファイルを読むところで止まり、答えを書かずに、セッションを終える（待つ相手が進んで、合図を書こうとして書けなければ、デーモンの順番を待つ `Verify` は、待つのをやめる。`Verify` が持つデーモンの順番とエンジンの待ちと、`Backup` のゲートは、そこで放され、後ろで待つ要求を、読む相手のいない要求のために、待たせ続けない）。`Commit` は止めない：始まった `Update` は、最後まで動き、確定する（クライアントが接続を閉じても、デーモンの要求は、終わっていない。下記の「`Commit` が切れたとき」）。デーモンが、相手の切断に気付くのは、その要求（順番かゲートを待つ間は、待つ相手）が進んで、合図を書こうとしたときなので、合図の間隔（5秒）の後までは、要求は、そのまま動く。待つ相手が止まっている間は、ほかの接続が動いていても、待つ要求は、合図を書こうとしないので、クライアントが閉じた（30秒で切った）要求も、相手が進むまで、デーモンの中で待ち続ける（`Verify` と `Backup` は、読み手の席を1つ使う）。相手が戻った後は、順番を取った `Verify` は、次の確かめ（5秒まで）で、エンジンの `Verify` を止め、ゲートを取った `Backup` は、読み手が開いた後に止まるので、上の「後ろで待つ要求を、読む相手のいない要求のために、待たせ続けない」は、その分（`Verify` は5秒まで）だけ、弱まる。`Backup` の、エンジンが読み手を開く間（ログを読み直す間）は、エンジンがコンテキストを見ない（エンジンは変えない）ので、位置が決まった後に止まる。
  - 進み具合に数えるもの：デーモンは、5秒前の確かめから、その要求の数が変わっていれば、その要求は進んだとする（`internal/logdb` は変えない）。数は、要求の、どの間かで、3つある。(1) 自分のエンジンの呼び出しが始まった後の、`Verify`・`Events`・ゲートを取った後の `Backup` は、その要求自身の数：`Verify` と `Events` は、エンジンが、ログの記録ごと（`Verify` は、オブジェクトごとにも）に呼ぶ、コンテキストの `Err` の回数（デーモンが、`Err` を数えるコンテキストを渡す。`internal/dbserver` の `progressCtx`。`Done` は、エンジンが待つ所で呼ぶので、数えない。エンジンは、セグメントを1回の `ReadAt` で読むので、`Err` は、その後に、記録の数だけ続く）。`Backup` は、`logdb.Backup` が、自分の読み手を開くのに使うファイルシステムの呼び出しの回数（デーモンが、ゲートを取った後、要求ごとに、呼び出しが返るたびに数を足すもの（`internal/dbserver` の `progressFS`）で包んで渡す。数えるのは、ファイルシステムの呼び出し（`Open`・`OpenFile`・`Mkdir`・`Remove`・`Rename`・`Lstat`・`ReadDir`・`SyncDir`・`Sub`・`Lock`）と、ファイルの呼び出し（`Read`・`ReadAt`・`Write`・`WriteAt`・`Seek`・`Sync`・`Truncate`・`Stat`・`ReadDir`・`Close`）で、失敗した呼び出しも、返れば数える）。この数え方は、エンジンが、記録とオブジェクトごとにコンテキストを見ることに、黙って依るので、デーモンのテスト（`TestProgressCtx`）が、`Err` の回数が、記録とオブジェクトの数以上であることを確かめ、エンジンが見る間を粗くすれば、落ちる（エンジンを替えるときも、同じ間を求める）。(2) 順番かゲートを待つ間は、待つ相手の数：`Verify` と `Commit` が、デーモンの順番を待つ間と、`Commit` と `Backup` が、ゲートを待つ間。エンジンも、`Verify` と `Update` を1つずつ通すが、その順番を待つ間は、`Err` が呼ばれず、デーモンから、待っているのか読んでいるのかが見えない。エンジンの順番で `Update` を待つ `Verify` は、自分の数が進まないので、`Update` が長く書く間、合図が出ない。そこで、デーモンが、同じ並びで、`Verify` と `Update` を1つずつ通す順番を持つ（`internal/dbserver` の `turn`）：`Verify` は、エンジンの `Verify` が動く間、`Commit` は、`Update` が動く間、これを持つので、順番を持つ `Verify` は、エンジンの順番を待たない（動いているデーモンで、エンジンの順番を取るのは、`Update` と `Verify` だけ。デーモンは `Checkpoint` を呼ばず、裏のチェックポイントは、エンジンの順番を取らない）。さらに、デーモンは、順番とゲートを持つ要求を覚える（`internal/dbserver` の `Server.turnBy`・`Server.gateBy`。持つ要求が、取った後に、自分を入れ、放す前に消す）。ゲートは、`Commit` が、`Update` の間と、デーモンの順番を待つ間、`Backup` が、読み手を開き、頭の行を読む間、持つ。待つ要求は、確かめのたびに、持ち主の数が、前の確かめから変わっていれば、進んだとする。持ち主も待っていれば、その先の持ち主の数を見る：ゲートを待つ `Backup` の持ち主は、ゲートの中で順番を待つ `Commit` で、その `Commit` の持ち主は、順番を持つ `Verify` なので、2段まで（辿るのは4段まで。`maxChain`）。持ち主が替われば、数が同じでも、合図を1つ書く（5秒より長く待った要求は、合図が1つ多くなりうる）。持ち主のいない間（持つ要求が放してから、次の要求が取るまで）は、書かない。記録は、どれも `atomic` で、確かめは、自分のセッションのロックだけを取る。鎖の終わりの要求（順番を持つ `Verify`・`Update` の間の `Commit`・ゲートを持つ `Backup`）の数が進めば、その後ろで、順番を待つ `Verify` にも `Commit` にも、その `Commit` の後ろで、ゲートを待つ `Backup` にも、合図が出る（待つ相手が進めば、その要求も、動いているものとして扱う）。待つ相手が止まれば、ほかの接続が読んでいても、合図は出ない。(3) `Commit` が、デーモンの順番を取った後、`Update` の間：自分が適用した操作と置いたオブジェクトの数と、自分の `Update` の書き込みの呼び出しの数。`f`（規則の確かめと、操作の適用）は、メモリの上だけで動き、エンジンは、`Tx` の操作で `Err` を呼ばないので、`f` の数は、デーモンが、操作ごと・置いたオブジェクトごとに、1つ数える（`internal/dbserver` の `apply`）。書き込みの呼び出しは、デーモンが、エンジンが開く `logdb/` のファイルシステムを、書き込みの呼び出しが返るたびに、順番を持つ `Commit` の数に、1つ足すもの（`internal/dbserver` の `writeFS`）で包んで、数える。数えるのは、ファイルシステムの呼び出し（`OpenFile`・`Mkdir`・`Remove`・`Rename`・`SyncDir`）と、`OpenFile` で開いたファイルの呼び出し（`Write`・`WriteAt`・`Sync`・`Truncate`）で、失敗した呼び出しも、返れば数える。読みは、数えない：ほかの接続の `Object`・`Events`・`Verify` と、`Backup` の写しの読みでは、進まない。`files/`（原本）の呼び出しと、エンジンの中の計算も、数えない。エンジンは、`Update` の間に、前の `Update` が始めた、裏のチェックポイント（1つずつ）を、同じファイルシステムに書くので、その呼び出しは、エンジンが使う名前（`.tmp-checkpoint-` **プロトコル**

- 版と互換（決定済み。13章）：プロトコルの版は、1つの数（いまは3）。繋ぐとき（`Hello`）に比べ、同じ版でなければ、何も変えずに拒む（両方の版を示す。版2のクライアントが、版3のデーモンに繋ぐと、`protocol version 2, but the daemon speaks version 3`）。交渉はしない。2つの実行ファイルは、同じリリースで配り、一緒に入れ替える。長く保つ互換は、ディスクの形（エンジンの形の版と、表の版。3.4の「エンジンと設定」・3.5の「ファイルの形」）が受け持つ。動いている古い `whiteroom serve admin` のまま、`whiteroom-db` だけを入れ替えると（一緒に入れ替える決まりに反する）、デーモンが動き直した後の、サーバーの繋ぎ直しの `Hello` が、デーモンの版の断り（`version`）になる：`store.ErrUnavailable` ではないので、保存先を使う要求は、サーバーを新しい実行ファイルで起動し直すまで、500（`internal`）で答える（503 ではない。コードから導いたことで、動かしては確かめていない。9.4の「`whiteroom serve admin`」の「実行ファイルの入れ替え」）。版の違う組で動かしたコマンドは、`Hello` の断りで、1で終わり、`whiteroom serve admin` は、起動しない。
- 出した版のバイトの並びは、書き換えない（案）。変えるときは、新しい版にする（`AGENTS.md`）。版2（#124）は、`Hello` の答えの終わりに、データのディレクトリの識別を足した（下記の「バイトの並び」）。ほかのバイトは、版1と同じ。版3（#136）は、`Hello` の版の数（4バイト。要求と答え）を3にし、答えの中の合図の枠（下記の「バイトの並び」）を足した。合図を送らない答えのバイトは、版2と同じ。版2の読み手は、合図の枠を、`protocol` の誤りとして断る（互換の道は持たない。上記）。
- メッセージ（決定済み。13章）：次の13個。

| 使えるもの | メッセージ | 内容 |
| --- | --- | --- |
| 書き手と読み手 | `Hello` | 版を確かめる。答えは、版・接続の役・デーモンの起動ごとのID・いまの連番・止まっているか・上限・データのディレクトリの識別 |
| 書き手と読み手 | `Snapshot`・`Release` | いまの連番の時点を固定する（答えは、その連番）・放す。接続ごとに1つ |
| 書き手と読み手 | `Get`・`Scan` | 表とキーで、値を1つ・接頭辞で、キーの順に（途中のキーの後から続けて、ページごとに） |
| 書き手と読み手 | `Object`・`Original` | ハッシュで、オブジェクト・原本の中身 |
| 書き手と読み手 | `Events` | 監査イベントを、番号の順に（スナップショットの連番まで。デーモンの印も含む） |
| 書き手と読み手 | `Verify`・`Backup` | エンジンの確かめ・写しのファイルを、順に返す（下記の「保守の口」） |
| 書き手だけ | `PutObject`・`PutOriginal` | 置く。デーモンが、SHA-256と大きさを確かめる |
| 書き手だけ | `Commit` | 期待する連番・操作の束（行の書き込み・削除と、監査イベント）。答えは、新しい連番と、印の時刻 |

- 送り方（決定済み。13章）：1つの接続では、要求と答えを、順に送り、多重にしない（答えの枠は、ほかの要求の答えと混ざらない）。デーモンは、1つの接続の要求に、受けた順に答える。同時に読むには、接続を増やす。大きいもの（オブジェクト・原本・`Scan`・`Events`・`Commit`・`Backup`）は、枠に分けて流す。
  - 窓（案）：クライアントは、読みの要求（`Get`・`Scan` の最初のページ・`Object`）を、256個まで、合わせて32KiBまで（`dbwire.WindowRequests`・`dbwire.WindowBytes`。デーモンが、1度に読む量 `dbwire.ReadBuffer` と同じ）、答えを読む前に、続けて送ってよい。窓は、1回の書き込みで送り、その答えを、すべて読んでから、ほかのものを書く。デーモンは、受けた順に答え、後ろに要求が届いている読みの答えは、まとめて（32KiBまで）、1回の書き込みで書く。読みでない要求の前には、まとめた答えを書く。窓の中の断りは、その要求だけの答えで、後ろの要求には、ふつうに答える（接続を閉じる断りは、前の答えを書いてから、閉じる）。窓に入るのは読みだけで、ほかの要求（`Snapshot`・`Release`・`Events`・`PutObject`・`Commit` など）は、前の要求の答えを読んでから送る。窓は、枠とメッセージのバイトを変えない。
- 操作のID：プロトコルの欄にしない。いまと同じく、操作の束の中の1行（表 `operations`。3.4の「索引」）。
- 壊れた要求（案）：枠の見出しが正しくない・メッセージの本体が、決まりより長い・順が違う（`Hello` の前の要求・答えの種類の枠・`Hello` の2回目）ときは、`protocol` で答えて（答えられるとき）、接続を閉じる。終わりの印の枠まで届いたメッセージの本体が、決まりより短いときは、答えずに、接続を閉じる（読む側は、途中で切れた接続と、見分けない）。大きさが、読む前の上限を超えるときは、`limit`。デーモンは、読んだ長さを、相手の言う長さでなく、届いたバイトで確かめる（大きい長さを言って、メモリを取らせられない）。

**バイトの並び**

整数は、固定の幅で、ビッグエンディアン（案）。コードは `internal/dbwire`（枠は `frame.go`・`stream.go`、値の形は `codec.go`、メッセージは `message.go`、符号は `errors.go`、印は `mark.go`）。

枠：メッセージは、同じ種類の1つ以上の枠で、最後の枠が終わりの旗を持つ。メッセージの本体は、その枠の中身をつなげたもの。

| 位置 | 大きさ | 内容 |
| --- | --- | --- |
| 0 | 1 | 種類（下の表） |
| 1 | 1 | 旗。`0x01`（終わり）だけを決める。ほかのビットは0 |
| 2 | 2 | 予約。0 |
| 4 | 4 | 中身の長さ（uint32） |
| 8 | 長さ | 中身 |

- 中身の上限は、`Hello` の答えまでは1MiB。そのあとは、`Hello` の答えの枠の値（下記の「上限」。1以上、1GiB（`dbwire.MaxFrame`）まで）。超える長さの枠は、読む前に、断る（`limit`）。長さが0の枠は、終わりの旗が要る。ただし、答えの中の、種類 `0x80`（OK）の、終わりの旗の無い、長さ0の枠は、合図で（版3。`80 00 0000 00000000`）、読む側は、読み飛ばし、メッセージの本体に何も足さない。合図は、答えの最後の枠（終わりの旗つき）か、エラーの枠の前だけに置け、最後の枠の後には置かない。デーモンが書くのは、`Verify`・`Commit`・`Events`・`Backup` の答えの中だけ（上記の「接続」の「長い要求の合図」）。要求の枠と、OK 以外の種類の、終わりの旗の無い、長さ0の枠は、いまと同じく、断る（`protocol`。遅い相手が、空の枠で、要求を引き延ばせない。合図が要求の位置に来たときも、デーモンは、`protocol` で答えて、接続を閉じる）。
- 読む側は、すべての枠の見出しを確かめる：予約が0、旗が決めたもの、種類が決めたもの、1つのメッセージの枠が、同じ種類（答えの途中の `Error` を除く）。

種類（要求は、`0x01` から `0x0D`）：

| 値 | 種類 | 値 | 種類 |
| --- | --- | --- | --- |
| `0x01` | `Hello` | `0x08` | `Events` |
| `0x02` | `Snapshot` | `0x09` | `Verify` |
| `0x03` | `Release` | `0x0A` | `Backup` |
| `0x04` | `Get` | `0x0B` | `PutObject` |
| `0x05` | `Scan` | `0x0C` | `PutOriginal` |
| `0x06` | `Object` | `0x0D` | `Commit` |
| `0x07` | `Original` | `0x80`・`0x81` | 答え（OK）・エラーの答え |

値の形：

| 形 | 書き方 |
| --- | --- |
| 整数 | `u8`・`u16`・`u32`・`u64`（符号なし）、`i64`（`u64` の2の補数）。ビッグエンディアン |
| 真偽 | 1バイト。`0` か `1`（ほかは `protocol`） |
| バイト列 | 長さ（`u32`）と、そのバイト |
| 短い文字列 | 長さ（`u16`）と、そのバイト（`Backup` の道と頭の行だけ） |
| ハッシュ | SHA-256の32バイト |
| 大きさ・数 | `u64`（`int64` に収まるもの） |
| 一覧 | 要素の前に1バイトの印（`1` は要素、`0` は終わり）。`Commit` の操作と `Backup` の項目は、種類のバイトが、これを兼ねる（`0` が終わり） |

メッセージの本体（要求は、書くものの順）。答えは、OKの答えの本体。本体が空のものは「なし」：

| メッセージ | 要求の本体 | 答え（OK）の本体 |
| --- | --- | --- |
| `Hello` | `WRDB`（4バイト）・版（`u32`） | 版（`u32`）・役（`u8`。`1` 読み手、`2` 書き手）・起動のID（16バイト）・いまの連番（`u64`）・止まっているか（真偽）・枠（`u32`）・`Commit` の上限（大きさ）・オブジェクトの上限（大きさ）・置いたオブジェクトの上限（大きさ）・キーの上限（`u32`。4096）・データのディレクトリのデバイス番号（`u64`）と inode（`u64`）（`stat(2)` の値。どちらも0なら、分からない。版2） |
| `Snapshot` | なし | 連番（`u64`） |
| `Release` | なし | なし |
| `Get` | 表（`u32`）・キー（バイト列） | 見つかったか（真偽）。見つかったときだけ、値（バイト列） |
| `Scan` | 表（`u32`）・接頭辞（バイト列）・続きか（真偽）・このキーの後から（バイト列。続きでなければ空）・行の数の上限（`u32`。0は無し） | 行：（`1`・キー・値）の並び、`0`、まだ続くか（真偽）。1ページは、行の大きさ（`9` と、キーと値の長さの和）の和が枠の値に届くか、行の数の上限に届いたところまで |
| `Object` | ハッシュ | 見つかったか（真偽）。見つかったときだけ、大きさ（`u64`）と中身 |
| `Original` | ハッシュ | 大きさ（`u64`）と、その大きさのバイト（枠に分けて）。無ければ、`not found` |
| `Events` | なし | イベント：（`1`・番号（`u64`）・連番（`u64`）・データ（バイト列））の並び、`0` |
| `Verify` | なし | なし |
| `Backup` | なし | 項目の並び（下記） |
| `PutObject` | ハッシュ・大きさ（`u64`）・中身 | なし |
| `PutOriginal` | 塊の並び（長さ（`u32`。1以上）とそのバイト。長さ `0` で終わり）・ハッシュ・大きさ（`u64`） | なし |
| `Commit` | 期待する連番（`u64`）・操作の並び・`0` | 新しい連番（`u64`）・印の時刻（秒（`i64`）・ナノ秒（`u32`）） |

- `Scan` の続き：続きのページは、前のページの最後のキーを、「このキーの後から」に入れて頼む。デーモンは、ページの間に、位置を覚えない（下記の「ファイルの形」）。
- `Commit` の操作：種類（`u8`）と本体。`1` 書き込み：表（`u32`）・キー・値。`2` 削除：表（`u32`）・キー。`3` イベント：データ（バイト列）。`0` が終わり。1つの操作の大きさは、送るバイト数（書き込みは `1+4+4+キー+4+値`、削除は `1+4+4+キー`、イベントは `1+4+データ`。長さの4バイトを含む）で、`Commit` の上限は、この和に当たる。
- `Backup` の項目：種類（`u8`）と本体。`0` 終わり。`1` ディレクトリ：道（短い文字列）。`2` ファイル：道（短い文字列）と、続く塊の並び（`PutOriginal` と同じ。終わりは長さ `0`）。`3` 頭の行：行（短い文字列）。`4` 位置：世代・セグメント・位置・連番（それぞれ `u64`）・CRC（`u32`）。送る順は、位置・頭の行・`files` のディレクトリとその中（名前の順）・`logdb` のディレクトリとその中（エンジンの `Backup` が作る順）・終わり。道は、`files` か `logdb` か、その下の、`/` で区切る相対の道で、空・`.`・`..` の名前、バックスラッシュ・コロン・NULを含まず、4096バイトまで。頭の行は、1〜255バイトの、印字できるASCII。
- 答えの途中のエラー：長いOKの答え（`Scan`・`Original`・`Events`・`Backup`）の途中で失敗すると、デーモンは、そこまでの枠を残して、エラーの答えの枠で、答えを終える。`Verify` と `Commit` も、合図を送った後に断るときは、同じ形になる（合図の後の、OK の枠の後のエラーの枠。クライアントは、本体の読みで、断りを受け取る）。合図の前の断りは、エラーの枠だけの答えで、版2と同じ。

エラーの答え：1つの枠で、種類 `0x81`、終わりの旗つき、中身は、符号（`u16`）・文の長さ（`u16`）・文（UTF-8。1024バイトまで。長ければ、文字の切れ目で切る）。中身の長さは、4〜1028。OKの答えが始まった後でも、続く枠の代わりに置けて、その答えを終える。

| 符号 | 名前 | いつ |
| --- | --- | --- |
| 1 | `protocol` | 壊れた枠・メッセージ、順の違うもの。答えの後、デーモンは接続を閉じる |
| 2 | `version` | `Hello` の版が違う |
| 3 | `denied` | その役では送れない要求。書き手のUnixユーザーでない |
| 4 | `busy` | 書き手が、もう繋がっている。読み手が、上限に届いている。デーモンが閉じようとしている（`the daemon is closing`） |
| 5 | `no snapshot` | スナップショットが無い |
| 6 | `not found` | 無い原本 |
| 7 | `seq` | 期待する連番が、いまの連番でない |
| 8 | `rule` | デーモンの規則（上記の「デーモンが守る規則」） |
| 9 | `limit` | 上限を超えた（下記の「上限」） |
| 10 | `no space` | 空きが足りない |
| 11 | `stopped` | 同期に失敗して、書くのを止めている |
| 12 | `hash` | 中身が、言われたハッシュか大きさと合わない |
| 13 | `failed` | エンジンの失敗か、壊れたものを見つけた。文は、OSのエラーの文か、壊れたファイルの文（道と位置）か、エンジンの確かめの文に限り、行の値は入らない（それ以外は、`the engine failed`） |
| 14 | `internal` | 答えを書けなかった |

- 印の1バイト目の `0x00` は、デーモンのイベントのために取ってある（下記の「印」）。

**1回の保存の流れ**

メッセージの使い方（案）。

1. `Snapshot` で、いまの連番の時点を固定し、`Get`・`Scan` で、いまの版と索引を読む（読むものが先に分かっているときは、窓で、まとめて頼んでよい。下記の「持つもの」）。
2. 管理のサーバーの中で、検証し、索引と監査の記録を作る（いまと同じGoのコード）。関数の中の読みは、その関数の書いたものを見る。関数がエラーを返したとき、取り消されたとき、パニックしたときは、何も送らない。
3. `PutObject` で、オブジェクトを置く（デーモンが、SHA-256を確かめる）。置いたオブジェクトは、デーモンのメモリに、その接続のスナップショットとともに持つ：`Commit` までは、ログに入れない（`Object` で、置いた書き手には見える）。別の `Snapshot` か `Release`、`Commit` の答え、スナップショットを放すとき（最後の要求から5分）、接続が終わると、捨てる。原本は、`PutOriginal` で置く（下記の「原本」）。
4. `Commit`（期待する連番・操作の束）を送る。デーモンは、規則・空きの確かめと、頻度の枠（下記の「上限」）を通し、連番を確かめ、置いたオブジェクトをエンジンに渡し、操作を当て、印のイベントを足し、ログに追記して同期してから、答える（新しい連番と、印の時刻）。どの答えでも、答えの後、スナップショットと、置いたオブジェクトは捨てる。

- 1回の `Commit` は、エンジンの1つのコミット（ログの1つのレコード。3.5の「コミット」）。
- `store` の形：トランザクションの中で、Goの関数が走る（`Update`。3.4の「操作」）形は、変わらない。`Update` は、1つずつ動く（書き手の接続が1つのため）。
- 持つもの（案。クライアント。`internal/dbclient`）：クライアントが、トランザクションの間、持つのは、`Get` の答え（見つかったかと値。同じキーは、1つのトランザクションで、1度だけ頼む。`Update` が書いたキーには、書いたものを返す）、先に読んだオブジェクト（`Tx.PrefetchObjects`。`Object` が、1度だけ渡す。2度目は、デーモンに頼む）、先に読んだ `Scan` の最初のページ（`Tx.PrefetchScans`。`Tx.DropPrefetched` か、トランザクションの終わりまで）。`Get` の答えには、上限は無い。オブジェクトとページは、合わせて64MiBまで（`prefetchBudget`。設定は無い）：超える答えは、読んで捨て、その後の `Object` と `Scan` が、デーモンに頼む。窓での先読み（`Tx.GetMany`・`PrefetchObjects`・`PrefetchScans`）は、ヒント：断りと、無いオブジェクトは持たず、後の読みが、先読みが無いときと同じ答えを、同じ所で返す。トランザクションが終われば、すべて捨てる。保存先は、これを使う（`Tx.ReadAhead`。3.4の「操作」）。
- 答えが来ないとき（案）：書き手は1つで、デーモンは、前の接続の要求が終わってから、新しい書き手を入れるので、繋ぎ直した `Hello` の連番で、自分のコミットが確定したかが分かる。スナップショットの連番に1を足したものなら、確定している。同じなら、確定していない（`the transaction was not committed`）。ほかなら、分からない（`it is not known whether the commit was made`）。繋ぎ直せなければ、分からない。`Commit` の答えを、30秒待っても、デーモンから何も届かないとき（合図が途切れたとき。上記の「接続」の「長い要求の合図」）も、クライアントが接続を切るので、同じ見分け方で確かめる。この見分け方は、書き手のプロセスが1つであることによる：クライアントが繋ぎ直すまでの間に、別の書き手のプロセスが繋いで、ちょうど1回コミットすると、連番は、同じく1つ進むので、クライアントは、自分のコミットが確定したと取り違える（2回以上なら、「分からない」になる。`Hello` の答えには、どのセッションのコミットかを見分けるものが無い）。書き手のロック（上記の「接続」）が、これを防ぐ：ロックを持つクライアントが開いている間は、ほかの `whiteroom` のコマンドは、書き手として繋がない（ロックを取らないプログラムとの間では、残る）。前の接続の `Commit` を、デーモンが、まだ持っている間（`Verify` が `Commit` を待たせている間など）は、繋ぎ直しは、2秒の後、`DIR: cannot reach the daemon: the last connection of the writer has not ended yet` で断られ（答えは「分からない」）、そのクライアントの次の書き込みも、その `Commit` が終わるまで、同じ文で失敗する（管理のAPIは503）。管理のAPIの再送は、いまと同じく、操作のIDで、2度しない（3.5の「冪等性の責務」）。

**上限（仮置き）**

- 超えたとき、相手が見るもの（案）：
  - 枠・`Commit` のバイト・操作の数・オブジェクトと原本の大きさ・キー：デーモンは、上限を超えたところで読むのをやめ、`limit` で答えて、接続を閉じる（`malformed message: a frame of 2097152 bytes, over the limit of 1048576`・`the ops of a Commit are over 268435446 bytes`・`a Commit of more than 4194304 ops`・`malformed message: an object of 70000000 bytes, over the limit of 67108864`・`the original is larger than 67108864 bytes`・キーは `malformed message: a byte string of 4097 bytes, over the limit of 4096`。読むときに `internal/dbwire` が断るものは、`malformed message: ` で始まる。1つの操作の値が、`Commit` の上限の残りより長いときも、この形）。クライアントは、先に確かめて、送らずに失敗する（`the transaction is too large: 300000000 bytes (max 268435446)`）。エンジンのコミットの上限に届いたときは、`limit`（同じ文）で、接続は閉じない。
  - 置いたオブジェクトの合計と数：`limit`。`the staged objects would be over 268435446 bytes`・`more than 4194304 objects would be staged`。接続は閉じず、スナップショットと、置いたオブジェクトも残る。同じオブジェクトを、もう1度置いても、数えない。クライアントも、合計は、先に確かめる（数は、確かめず、デーモンが断る）。
  - 接続：`busy`。`another writer is connected`・`64 readers are connected, the most that the daemon serves`。デーモンは、待ち受けごとに、開いている接続を、読み手は `-max-readers` に16、書き手は1に16まで数え（`Hello` の前のものも。1つは、`-stall` の間まで）、数に届いたら、受け付けるのをやめる。読み手の席は、スナップショットを持たない接続が、下記のとおり、`-snapshot-idle` で閉じられると、空く（#129）。
  - スナップショット：放した後の読む要求は、`no snapshot`。接続は、そのまま使える。放すまでの時間は、要求と要求の間の待ちに掛かり、読み始めた要求には、掛からない（`-stall 0` のときも、読んでいる途中の要求を、この時間で切らない）。放すまでの時間（5分）の測り方は、下記の「時間の2つの上限の測り方」。放された読み手の接続は、もう1度、同じ時間、何も送らなければ、閉じられる（次の項。合わせて10分）。書き手の接続は、放した後も、残る。
  - スナップショットを持たない読み手の接続（案。#129）：最後の要求（まだ要求が無ければ、`Hello` の答え）から、`-snapshot-idle` の間、何も送らなければ、デーモンは、答えずに（エラーの枠も書かずに）接続を閉じ、読み手の席を空ける。放された後の接続も、同じ。相手は、次の書き込みか読みで、切れた接続を見る（`broken pipe`・`connection reset`・`EOF`）。クライアントは、プールの接続の最初の要求なら、新しい接続でやり直す（上記の「接続」）。読み始めた要求には、掛けない（`-stall` だけが掛かる）。書き手の接続は、閉じない：書き手の接続が無い間に、書き手のロック（上記）を取らないプログラムが、書き手として繋げて、「答えが来ないとき」（上記の「1回の保存の流れ」）の連番の見分けを、取り違えうるため（呼び出しの中で書き手の接続が終わったときの、クライアントの繋ぎ直しも、同じ理由。上記の「待ちと繋ぎ直し」）。`-snapshot-idle 0` は、スナップショットを放さず、読み手の接続も閉じない。
  - 進まない要求：要求を読む間と、答えを書く間（64KiBごと）、`-stall` の間に進まなければ、答えずに、接続を切る。`Hello` の前の接続にも、同じ。上限の測り方は、下記の「時間の2つの上限の測り方」。
  - 全体の量：`no space`。`the free space is 900000000 bytes; a write of 1000 bytes must leave 1073741824`。確かめる書き込みは、`PutObject`、`PutOriginal`（初めに1バイト、そのあと8MiBごと）、`Commit`（操作と置いたオブジェクトの合計）。確かめるのは、Linuxのデータのディレクトリのファイルシステムで、ほかのシステムでは、確かめない。
  - 全体の量（inode。#128）：`no space`。`the free inodes are 65536; a write that may make a file must leave 65536`。どの書き込みも、ファイルを1つ作りうるとして数え、書き込みの後に、下限が残らなければ拒む（空きが下限と同じなら、拒む）。確かめる書き込みは、`PutObject`・`PutOriginal`（初めだけ。8MiBごとの確かめは、原本のファイルを作った後なので、バイトだけを見る）・`Commit`。inode を数えないファイルシステム（`statfs` の総数が0か、総数か空きが-1。btrfs、`nr_inodes` の無い tmpfs など）では、確かめない（btrfs のメタデータの不足は、`statfs` から見えない）。理由（2026-11-17に測った）：原本は、1バイトでも、`files/` の中の1つのファイルで、ext4 では、inode を1つと4KiBを使う。ext4 の既定（`mke2fs.conf` の `inode_ratio = 16384`）では、小さい原本だけで、バイトの約4分の3が空いたまま、inode が尽きる。inode を2000にした tmpfs で、数バイトの原本を置き続けると、空きが249MiB残ったまま、1732個目で `no space left on device` になり、その後、64KiB以上のオブジェクト（`objects/` の中のファイル）、次のセグメント、圧縮（`whiteroom-db compact`）が、同じ失敗をした（小さい `Commit` は、セグメントに空きがある間は通った）。下限を500にすると、原本は、inode が500残る所で拒まれ、エンジンの書き込みと圧縮は、通った。開発のマシン（NVMe の上の ext4）では、テストのプロセスの中のデーモンに、1つの書き手が、数バイトの原本を1秒に294個置いた（同期を含む）。この速さで、空いている5665万の inode は、約53時間で尽きる（空の25GiBの ext4 の inode、約164万なら、約93分）。`PutOriginal` に、頻度と数の上限は置かない（6.12の125）。
- `Commit` の頻度（案）：1秒に50回を、かごで数える：かごは、50まで貯まり、頻度の分だけ戻る。`Commit` は1つ取り、空なら、順番が来るまで待つ（後ろの `Commit` も待つ）。拒まない。取り消されれば、取るのをやめる。
- 時間の2つの上限（30秒と5分）の測り方（案）：デーモンは、1つの時計から、接続の期限を決める。時計は、1つのゴルーチンが、1ティックに1度だけ読む（ティックは、短いほうの上限の16分の1で、1ミリ秒以上、半秒（`internal/dbserver` の `maxTick`）まで。既定では半秒）。期限は、上限より早くならず、遅くても4ティック後（既定では2秒。30秒の上限は30〜32秒、5分の上限は5分0秒〜5分2秒）。要求が続くときは、時計が動くまで、期限を決め直さない（読みの要求ごとに、時計を読まない。クロックソースが `hpet` だと、時計を読むのは、システムコール。下記の「測った値」）。時計の読みが、前の読みから2ティックを超えて遅れたとき（プロセスが止められたときなど）と、最後の読みが、2ティックより古いときは、時間切れを、本物の時計で、1度だけ決め直して確かめる（`Server.lateAt`・`timedConn` の `early`）：上限は、早くは切れず、その場合は、上限の長さまで、遅れうる。期限が、数えられる長さ（約292年）を超える上限（`-snapshot-idle`・`-stall` に、書けるいちばん長い期間を書いたときなど）は、期限なしとして扱う。スナップショットを持たない読み手の接続を閉じる期限（#129）も、同じ時計の、同じ精度（5分の上限は、5分0秒〜5分2秒。放した後の接続は、さらに同じだけで、合わせて10分0秒〜10分4秒）。クライアントの30秒の上限（上記の「接続」の「答えを待つ時間」）は、デーモンの時計ではなく、クライアントの見張りが、同じ形（ティックに1度。要求ごとに時計を読まない）で測る。長い要求の合図（5秒。上記の「接続」の「長い要求の合図」）は、この2つの上限とも、`-stall`・`-snapshot-idle` とも、別のもの：長い4つの要求ごとに、タイマーが1つ（`time.AfterFunc`）、答えの始めから、答えが決まるまで動き、鳴るたびに、数を見て、進んでいれば、合図を1つ書き、次を5秒後に置く。デーモンの時計のティックは、使わない。読みと置く要求には、タイマーを持たせず、時計の読みを足さない（長い要求は、始めるときと、5秒ごとに、時計を1回読む。`hpet` のこのマシンで、`Update` の中央値は、前後とも1.40〜1.41ミリ秒だった。下記の「測った値」）。合図の書き込みは、ほかの答えと同じに、`timedConn` の `Write` を通り、`-stall` の下にある（期限は、ティックの時計から決まり、書き込みごとに時計を読まない）。`-snapshot-idle` は、要求を読み始めた後には掛からないので、合図とは関わらない。

**印（決定済み。13章）**

- 中身：デーモンが、コミットごとに付ける、デーモンの時計の時刻（UTC）だけ。連番は、レコードにある。時計が戻っても、そのまま記す（順は、連番が決める）。
- 理由：いまは、保存した日時（3.4の「表」）と、記録の時刻（7.4の「番号と時刻と鎖」）を、管理のサーバーの中の `store` が付けるので、破られると偽れる。印があれば、破られた期間を特定でき、サルベージの起点になる。
- 置き方：デーモンが、コミットごとに、自分のイベント（3.5の「イベント・操作のID・暗号化の封筒」）を、そのコミットの最後に足す。エンジンのファイルの形は、変えない（下記の「ファイルの形」）。イベントは、ログにだけあり（メモリには数だけ）、圧縮でも、書き直しで落とさなければ残る。
- バイトの並び（案）：14バイト。

| 位置 | 大きさ | 内容 |
| --- | --- | --- |
| 0 | 1 | `0x00`：デーモンのイベント |
| 1 | 1 | `0x01`：印（`0x02`・`0x03` は、下記。ほかの値は、まだ決めていない） |
| 2 | 8 | 1970-01-01T00:00:00Z からの秒（`i64`） |
| 10 | 4 | 秒の下のナノ秒（`u32`。10億より小さい） |

- 書き手のイベントとの区別（案）：監査の記録のJSONは `{` で始まる。デーモンは、書き手のイベントが、空か、`0x00` で始まれば、断る（上記の「デーモンが守る規則」）。印の時刻は、`Commit` の答えにも返る。
- 読む側：記録を読む口と確かめる口（7.4）は、印を飛ばす。`0x00` で始まるのに、印の形（14バイト・`0x01`・ナノ秒が範囲内）でも、下記の削除と認めた切れ目の形でもないイベントは、壊れているとする（`audit event 7: not a record of the audit log`）。イベントの番号は、印も数える（記録の番号とは別。7.4の「番号と時刻と鎖」）。そのため、表の版（3.4の「エンジンと設定」）を、7に上げた。印のほかに、保守が足す2つの種類（下記）を足したときは、8に上げた（#70）。
- 保守が足すイベント（案。#70 の計画への答え（2026-11-23）で決めた）：印のほかに、2つの種類がある。足すのは、保守（`whiteroom-db compact`・`accept-break`。下記の「保守の口」）だけで、表 `chains`（12。3.4の「表」）の行を書く1回の書き込みに、その行と一緒に足す（そのコミットの最後に、印が付く）。書き手は、`0x00` で始まるイベントを断られる（上記の「デーモンが守る規則」）ので、足せない。どちらも、時刻を持たない（削除の `cutoff` のほかは）：時刻は、同じコミットの印が持つ。数は、すべてビッグエンディアン。ログの1バイトは、`1` が `login`、`2` が `activity`（ほかの値は、読めないとする）。記録を読む口と確かめる口（7.4）は、この2つも、印と同じに飛ばす（`dbwire.ValidEvent`）。イベントの番号は、この2つも数える。
  - `0x02` 削除（55バイト）：ログの、番号が `first` より前の記録を、削除した。`first` は、残る最初の記録の番号（2以上）、`prev` は、その1つ前の（削除した最後の）記録の、保存したバイト列のSHA-256、`cutoff` は、削除が基準にした時刻（これより前の印を持つ記録を、落とした。7.4の「保持の期間と個人の情報」）。

    | 位置 | 大きさ | 内容 |
    | --- | --- | --- |
    | 0 | 1 | `0x00`：デーモンのイベント |
    | 1 | 1 | `0x02`：削除 |
    | 2 | 1 | ログ（`1` か `2`） |
    | 3 | 8 | `first`（`u64`。2以上） |
    | 11 | 32 | `prev`（SHA-256） |
    | 43 | 8 | `cutoff` の、1970-01-01T00:00:00Z からの秒（`i64`） |
    | 51 | 4 | `cutoff` の、秒の下のナノ秒（`u32`。10億より小さい） |

  - `0x03` 認めた切れ目（43バイト）：ログの、番号 `n` の記録で、鎖が切れている（前の記録に続かない）ことを、操作する人が見たうえで、認めた。`hash` は、そのとき、番号 `n` の記録が持つ、保存したバイト列のSHA-256（表 `chains` の行にも、同じ値を置く）。

    | 位置 | 大きさ | 内容 |
    | --- | --- | --- |
    | 0 | 1 | `0x00`：デーモンのイベント |
    | 1 | 1 | `0x03`：認めた切れ目 |
    | 2 | 1 | ログ（`1` か `2`） |
    | 3 | 8 | `n`（`u64`。1以上） |
    | 11 | 32 | `hash`（SHA-256） |

**頭の書き出し（仮置き）**

- 決めたこと（決定済み。13章）：鎖の頭を、保存先の外に書き出すこと（7.4の「改ざんの検知」）を、デーモンの側に移す。管理のサーバーに残すと、破られたときに、止められる。管理のサーバー（`whiteroom serve admin`）は、頭を書かない。
- 形（仮置き。6.12の268）：サービスしているデーモン（`serve`）は、監査の鎖の計算を知らない（保守は、`compact` と `accept-break` のために、記録の `log`・`n`・`prev` を読み、バイト列のハッシュを求める。上記の「デーモンが守る規則」の「知らないこと」）。そこで、管理のサーバーの中の `store` が、ログごとの頭の行（7.4の形。`audit head <ログ> <番号> sha256:<64桁の小文字の16進数>`）を、その記録と同じコミットで、表 `heads`（11）に置く（キーは、ログの名前の `login`・`activity`）。デーモンは、その表の行の値を、中身を読まずに、そのまま、自分の標準エラーに、1行ずつ書く。デーモンが確かめるのは、行の形だけ：キーは1〜64バイトの `A-Z`・`a-z`・`0-9`・`.`・`_`・`-`、値は1〜255バイトの、印字できるASCII。形に合わない行は、書かず、そのことを、エラーのログに1回書く（`a row of the table of the heads is not a head line, and is not written`）。
- いつ書くか（案）：起動のとき、すべての行を1回。そのあと、1分ごとに、前に書いてから値が変わった行。止めるとき、要求が終わった後に、変わった行をもう1回（その最後の読みは、5秒まで）。書けなかった行は、次の合図に、また試す（エラーのログ：`cannot write a head: …`）。書く間、読みも `Commit` も止まらない。
- 書く先が詰まったとき（案）：標準エラーへの書き込みが返らない間は、頭の書き出しだけが止まる（コミットと読みは続く）。その間に来た合図は、1つまで待ち、書き込みが返った後に取る。デーモンを止めるときは、書き込みが返るのを待つので、返らない書き出し先は、デーモンが止まるのを妨げる（サービスの管理が、プロセスを終わらせる。その場合、最後の頭は書かれない。6.12の286）。
- 読む側が終わったとき（案。#130）：標準エラー（と標準出力）がパイプで、読む側が終わっているときは、書き込みが失敗する（`EPIPE`）だけで、デーモンは動き続ける。書けなかった頭は、ほかの失敗と同じに、次の合図に、また試すが、パイプの読む側は戻らないので、デーモンを動かし直すまで、頭も、ログの行も、どこにも出ない（詰まらない場所にも書くかは、6.12の286）。止める合図で止めたときの終了コードは、0。そのために、`whiteroom-db serve` は、SIGPIPE を受け取る（`os/signal` の `Notify`）：受け取らないと、Goのランタイムは、標準出力と標準エラーへの書き込みの `EPIPE` で、プロセスを終わらせる。親が SIGPIPE を受け流していても（systemd の既定の `IgnoreSIGPIPE=yes`）、終わる（Goのランタイムは、受け継いだ受け流しを、SIGHUP と SIGINT のほかには使わない。2026-11-17に、直す前の `whiteroom-db serve` で、頭が変わった後の1分ごとの合図に、SIGPIPE で終わり、ソケットのファイルが残ることを確かめた）。`whiteroom serve admin`・`serve public` も、同じに動き続ける（9.4の「終了コード」）。`cmd/whiteroom` の `TestProcesses` が、読む側の無いパイプを標準エラーにして、3つを動かす。
- 標準エラー：デーモンのログの行（日時つき。キーと値は書かない）も、同じ標準エラーに出る。頭の行は、そのまま読める（`audit.ParseHead` は、行の末尾の形を読む。7.4の「改ざんの検知」）。`whiteroom backup` は、写しの鎖の頭を、標準出力に書く（下記の「保守の口」）。
- 限界：破られた管理のサーバーは、偽の頭を置ける。頭の形でない行も、上の形（印字できるASCII）に合えば、16行まで、デーモンの標準エラーに書かせられる（日時つきのログの行に似せた行も。制御文字は、入らない）。できるのは、確かめを失敗させること（誤った警報）だけで、書き換えは隠せない（7.4の「改ざんの検知」の、偽の頭の行と同じ）。破られる前に書き出した頭は、変えられない。
- 決めていないこと：デーモンが、中身に依らない自分の鎖（イベントのバイト列のハッシュの鎖）を持って、それを書き出す形にするか（6.12の268）。

**原本（決定済み。13章）**

- デーモンが持つ：メディアの原本（`files/`。3.4の「原本」）も、デーモンが持つ。分ける理由（サルベージ）は、原本にも当たる：管理のサーバーが `files/` を直接書けると、破られたときに、原本を消せる。
- 送り方（案）：原本は、ソケットで、塊に分けて送り（`PutOriginal`。管理のサーバーの `Update` の外）、受ける（`Original`）。置くとき、デーモンは、受けながら `files/` の一時のファイル（`.tmp-` とランダムな16進数16桁）に書き、SHA-256と大きさを求め、最後に付いてきたものと比べる。合わなければ、`hash`（`the data do not have the hash and the size that were given`）。空は `rule`（`the original is empty`）。上限（64MiB）を超えるところで、読むのをやめる（`the original is larger than 67108864 bytes`）。それから、一時のファイルを同期して閉じ、`files/<16進数2桁>/<16進数64桁>` に名前を変える（ディレクトリが無ければ作り、`files/` を同期する）。そのディレクトリも同期する。そのため、原本のファイルは、すべてあるか、無いか。同じ名前があれば、置き換える（同じ中身）。失敗したら、一時のファイルを消す。
- 読む：`Original` は、名前のファイルが、ふつうのファイルで、64MiBまでであることを確かめ（無ければ、符号 `not found` で、`files/9f/9f86…: not found`。ほかは、符号 `failed` で、`files/…: symbolic links are not allowed`・`files/…: must be a regular file`・`files/…: too large: 70000000 bytes (max 67108864)`）、大きさと、バイトを、そのまま送る。デーモンは、読むときにハッシュを確かめない：受け取る側（`store`。3.4の「原本」）が、終わりまで読んだときに確かめる。
- 起動のときの片付け（案）：デーモンは、エンジンの書くロックを取った後に、`files/` の直下の、`.tmp-` と16進数16桁のふつうのファイル（`PutOriginal` が途中で止まったもの）を、すべて消す。消せなければ、起動に失敗し、保存先は変わらない（`<DIR>/files/<名前>: cannot remove: …`・`<DIR>/files: cannot read: …`）。ほかの名前・ディレクトリ・原本は消さない。`Backup` は、一時のファイルを送らない。
- 一時のファイル（案）：管理のAPIの、メモリに乗らない本文と答えの一時のファイルは、デーモンの `files/` に置かない：管理のサーバーの側の、設定 `tmp` のディレクトリに置く（9.4・9.7）。デーモンの `files/` の一時のファイルは、書いている途中の原本だけ。
- 同期の失敗：原本の同期（一時のファイル・`files/`・原本のディレクトリ）の失敗は、エンジンの同期の失敗と同じ印で、デーモンの書くのを止める（下記の「同期の失敗」。`PutOriginal` だけでなく、文書の書き込みも止まる）。

**保守の口（決定済み。13章）**

- 書き換えるもの（圧縮・回収・鎖の切れ目を認めること。3.5の「保守モード」）：デーモンの実行ファイルのサブコマンド（`whiteroom-db compact`・`whiteroom-db gc`・`whiteroom-db accept-break`）。デーモンを止めて、サーバーの上で動かす。ソケットには出さない：履歴を消せる操作なので、ソケットに出すと、破られた管理のサーバーが、履歴を消す口になる。データのディレクトリを開いているプロセス（デーモンなど）があれば、2秒待って、何も変えずに失敗する（`whiteroom-db compact: <DIR>: the data directory is in use; stop whiteroom-db serve on it first`）。保守が動いている間は、デーモンは、すぐに始まれない（`maintenance is running`）。保守が待つ2秒の間も、`lock/entry` を持つので、動いているデーモンの `Backup` は、その間、`failed` で終わる。`compact` は、いまの状態を、新しい世代のログに書き直して、古い世代を消し、ログイン履歴の、1年より古い記録を落とす（下記の「`compact` が落とすもの」）。`gc` は、いまの世代でないセグメントと、状態が持たないオブジェクトのファイルと、一時のファイルを消す（原本は消さない。6.12の125）。エンジンの修復は、まだ無い（#144。6.12の131）：チェックポイントより前のセグメントが壊れていると、`compact` は、古い世代のイベントを、ログのすべてから読むので、同じ傷で失敗し（保存先は、古い世代のまま開ける。`gc` は動く）、エンジンが開けない保存先には、どの保守も動かない（保守も、エンジンを開くため）。いまの直し方は、写しから戻すこと（2026-11-23に、`main`（`6983bcb`）で確かめた。3.5の「復旧」）。同期に失敗した後の印（下記の「同期の失敗」）も、保守は、デーモンと同じに守る：マシンを再起動する前の印があれば、エンジンのファイルを何も変えずに、`whiteroom-db compact: <DIR>: a sync failed at …, and the machine has not restarted since; restart the machine before starting whiteroom-db on this directory again` で断り（終了コード1）、データのディレクトリそのものに、このユーザーが書けなければ、同じに、何も変えずに断り（下記の「書けるかの確かめ」）、保守の中で、エンジンが `ErrFailed` で失敗したら、印を残し、マシンを再起動した後の保守は、印を消して、標準エラーに1行書く。
- `compact` が落とすもの（案。#70 の計画への答え（2026-11-23）で決めた。規則は7.4の「保持の期間と個人の情報」）：ログイン履歴の、1年より古い記録だけ。表・オブジェクト・ほかのイベントは、番号ごと、そのまま残す。アクティビティログは、落とさない。
  - 古さ：記録の古さは、同じコミットの最後に、デーモンが付けた印（上記の「印」）の時刻で決める。記録の `at` は、管理のサーバーの中の `store` が付けるので、使わない。切り捨ての時刻は、コマンドの時刻と、最も新しい印の時刻の、早いほうの、暦で1年前（UTC。`time.AddDate(-1, 0, 0)`）。印が、切り捨ての時刻より前の記録が、古い（同じ時刻は、残す）。最も新しい印を使うので、新しいコミットが、長く無い保存先は、それ以上、消えない。期間（1年）を、変えるフラグも、設定の項目も、無い。書き手は、削除を頼めず、切り捨ての時刻も動かせない（切り捨ては、保守のコマンドの時計と、デーモンの印だけで決まる）。
  - 前のほうだけ：番号の順に、最初の、古くない記録（か、印の無い記録）まで。後ろは、古くても残す。鎖の始まりを、1つの行で言えるようにするため。
  - 順：(1) 鎖を、鎖の始まり（無ければ、記録1）から、たどる（記録から読むのは、`log`・`n`・`prev` だけ。上記の「知らないこと」）。(2) 新しい鎖の始まり（残る最初の記録の番号 K と、その1つ前の記録のハッシュ P）を、表 `chains` の行と、イベント `0x02` と、印として、保守の `Update` 1回で、先に書く（7.4の「改ざんの検知」）。(3) 圧縮の書き直し（`Rewrite.Event`）が、落とすと決めた記録のイベントだけを、落とす。(2) の後、(3) の前で止まっても、記録は、そのまま残り（鎖の始まりの行は、K より前の記録が、まだあっても、通る）、次の `compact` が、(3) を終える（K より前に残った記録は、古さによらず、落とす。そのときの標準出力の行も、その分を含む）。
  - 止まる所：記録が、前の記録に続かないとき（番号か `prev` が合わない）、記録として読めないイベントのとき、表 `chains` の行が読めないとき。そこで、落とすのを止め、その記録と、その1つ前の記録は、残す（その切れ目を、`accept-break` が認められる形にするため）。最初に読む記録が、切れていて、そこで止まったときは、その記録が切れ目なので、`accept-break` も断り、どちらも進めない（エンジンの修復の仕事。#144。6.12の289）。止まった所は、標準出力に書き、終了コードは 0。書くのは、止めたのが、古さでなく、その証拠のときだけ（通した記録が、どれも、切り捨ての時刻より古く、古さは、そこまで落とすのを許していたとき。古さが止めたはずのときは、書かない）。記録でないイベントで止まったときは、そのイベントの後に、ログイン履歴の記録が、まだあるときだけ書く（記録でないイベントが、あるだけの保存先で、`compact` のたびに言わないため）。何が悪いかは、`whiteroom doctor` が示す。認めた切れ目（下記）は、その行があり、行のハッシュが、記録のハッシュと同じで、記録の番号が、通った番号より大きいときだけ、続ける（番号が戻る記録は、切れ目とは読まず、止まる所にする）。切る所が、認めた切れ目が飛ばした穴の後の記録（前の番号の記録が無いもの）になるときは、前の番号の記録を持つ所まで、切る所を戻す（鎖の始まりは、1つ前の記録のハッシュを持つので、前の番号の記録が要る）。
  - 認めた切れ目：認めた切れ目（`accept-break`。下記）の記録も、古ければ、落とす。落とした記録の、表 `chains` の行と、イベント `0x03` は、残り、`VerifyAudit` は、鎖の始まりより前の記録の切れ目を、告げない（7.4）。`accept-break` は、鎖の始まりより前の記録を、認めない（下記）。
  - 出力：成功したとき、標準出力に `compacted DATA`。続けて、落としたときは `deleted the login records A to B, from before TIME`（A と B は、今回、消した番号の範囲で、前の削除が、途中で止まって残した記録の分も含む。TIME は、切り捨ての時刻の、RFC 3339、UTC、秒まで）、止まったときは `the deletion of login records stopped at WHERE; check the store with whiteroom doctor`。
  - 表の版が8より古い保存先：落とさず、保守の `compact` の後に、`kept the login records older than one year: the store has the table schema S, and the first writer that connects through whiteroom-db serve (whiteroom serve admin, for one) upgrades it to 8` を、`compacted DATA` の次の行に書く（古い記録が、無いときは、書かない）。理由：保守の書き込みは、デーモンの表の版の規則（上記の「デーモンが守る規則」）の外にあり、鎖の始まりと、イベント `0x02` は、表の版8のものなので、版8にするのは、書き手（`store.Open`。`whiteroom serve admin`・`whiteroom account`・`whiteroom init` が、書き手として開く。`whiteroom doctor`・`build`・`backup` は、開かない。`whiteroom-db serve` だけでは、上がらない）の、更新の `Update` に任せる。上がった後の `compact` が、落とす。
  - 費用：記録 20万件（600,000のイベント。93MB）で、落とすものが無いとき、ただの圧縮の約1.5倍、半分を落とすとき、約+0.6秒（下記の「測った値」）。記録を、1件、80バイト、メモリに持つのは、最初の、古くない記録までに、通った記録だけ。
- `accept-break`（案。#70 の計画への答え（2026-11-23）で決めた）：デーモンの実行ファイルのサブコマンド（`whiteroom-db accept-break [-config FILE] [-data DIR] -log LOG -record N`）。デーモンを止めて、サーバーの上で動かす。ソケットには出さない：出すと、破られた管理のサーバーが、自分の書き換えを、認める口にできる（表 `chains` への書き込みは、書き手からは、断られる。上記の「デーモンが守る規則」）。記録が読める鎖の切れ目を、操作する人が調べたうえで、認める。記録は、書き換えず、落とさず、足さない。
  - 切れ目とは：`VerifyAudit` が、そのログを、イベントの順に、たどって、失敗する所（`prev` が、前の記録のハッシュでない。か、番号が、前の記録の番号に1を足したものでない）。`LOG` と `N` は、`whiteroom doctor` の問題の行（`audit log "login": record 7 (event 31): prev is not the hash of record 6`）の、ログと、記録の番号。前の記録は、同じログの、1つ前に読んだ記録で、記録でないイベント（記録として読めないもの・デーモンの不正なイベント・別のログの記録）は、飛ばす。番号の規則でなく、`VerifyAudit` が失敗する所で決めるので、順が前後した記録（1、3、2の順の、2）と、番号が飛んで、ハッシュが合うもの（4の後の、4のハッシュを持つ6）も、切れ目。
  - 書くもの：保守の `Update` 1回（同期して返る）に、この順で、(1) 表 `chains` の行（キーは、ログの名前・0x00・N の8バイト。値は、記録 N の、保存したバイト列のSHA-256と、コマンドの時刻）、(2) イベント 0x03（上記の「印」）、(3) 印（コマンドの時刻）。圧縮はしない：ログは、同じ世代のまま、新しいコミットを持つ。標準出力に、`accepted the break at record N of the audit log LOG in DATA; whiteroom doctor checks the log again from it`（`DATA` は、`-data` か設定ファイルの値のまま）。成功したとき、標準エラーには、何も書かない（前の起動の印を消したときの1行は除く）。
  - 認めた後：`VerifyAudit` は、その行があり、行のハッシュが、いまの記録 N のハッシュと同じなら、記録 N の、番号と `prev` の確かめを飛ばして、続ける（後ろの記録と、頭と、外の頭は、いつもどおり）。`whiteroom doctor` は、問題としてでなく、告げる（7.4の「告げること」）。記録 N が、認めた後に、書き換わると、行のハッシュが合わず、認めたことにならない：問題に戻る。もう1度認めると、行は、新しいハッシュに置き換わり、2つ目のイベント 0x03 が足される（最初のイベントも、跡として、残る）。記録 N の書き換えは、記録 N+1 が持つハッシュも変えるので、記録 N+1 が、続けて、認める切れ目になる。書き換わっていない記録を、2度認めることは、断る。
  - 断るもの（何も書かない。標準エラーに `whiteroom-db accept-break: <文>`、終了コード1。この順に調べる）：(1) 鎖の行が読めない：`the chain of the audit log LOG cannot be read, so no break of it is accepted (the table chains: the chain start cannot be read)`、`(… a row of an accepted break cannot be read)`、アクティビティログに鎖の始まりの行がある `(… a chain start for a log of which only the login records are ever deleted)`。(2) 鎖の始まり K より前の記録：`record N of the audit log LOG is not in the store: the records before record K were deleted`。(3) 記録が無い：`record N of the audit log LOG is not in the store`。(4) 同じ番号の記録が、2つ以上ある：`record N of the audit log LOG is in the store more than once, so a break at it cannot be named by its number`（ハッシュを、1つに決められないため）。(5) 最初に読む記録（番号によらず。記録1・削除の後に残る最初の記録・先頭が欠けたログの最初の記録。前の記録が無いので、切れ目として見られない）：`record N is the first record that the audit log LOG is checked from: a break there is not accepted`。(6) 切れ目でない記録：`record N follows record N-1: there is no break to accept`。(7) 認めてある：`the break at record N of the audit log LOG is already accepted`。(8) 表の版が、このプログラムの版より古い：`the store has the table schema S, and the first writer that connects through whiteroom-db serve (whiteroom serve admin, for one) upgrades it to T: accept the break then`（切れ目であることを確かめた後に断る。表 `chains` の行と、イベント 0x03 は、表の版8のものなので、`compact` と同じに、書き手が繋いで、表の版を上げてから）。`-log` が `login` でも `activity` でもないことと、`-record` が無いか、1より小さいことは、使い方の誤り（終了コード2。9.4）。データのディレクトリを開いているプロセスがあるとき（約2秒待つ）と、同期に失敗した後の印と、書けないデータのディレクトリは、`compact`・`gc` と同じに断る（上記の「同期の失敗」）。
  - 認めないもの：記録として読めないイベント（エンジンの傷が残す。番号を持たない）は、飛ばされ、認められず、`whiteroom doctor` は、そのイベントを、問題として、示し続ける。失われた記録は、戻らない：欠けた記録の、次の記録（`prev` が、無い記録を指す）の切れ目は、認められ、失った記録を指す外の頭は、照らせず、数が告げられる（7.4）。読めないイベントと、最初に読む記録の切れ目と、読めない鎖の行を、直すのは、エンジンの修復（#144。6.12の289）。
  - 費用：イベントを、1回、通す（時間は、イベントの数に比例し、メモリは、一定。測っていない）。
- 読むだけのもの（検査・バックアップ）：読み手の接続のメッセージ（`Verify`・`Backup`）。`whiteroom doctor`・`whiteroom backup`（9.4）は、ソケットで繋ぐ。
- `Verify`（案）：デーモンが、エンジンの `Verify`（3.5の「保守モード」）を動かして、すべてのログをディスクから読み直し、メモリの状態と比べ、オブジェクトのハッシュを確かめる。答えは、OKか、`failed`（`the state in memory differs from the log (the detail is not sent: it may hold values of rows)`・`object <ハッシュ>: the data has the hash <ハッシュ>` など）。エンジンの `Verify` は、`Commit` と同じ順番（エンジンの書く順番）を取るので、動いている間、`Commit` は待つ（読みは続く）。読み手の `whiteroom doctor` も、書き手を待たせる。待つ長さは、下記の「測った値」。
- `Backup`（案）：1つの要求の答えが、写しのすべて。デーモンは、エンジンの読み手を、デーモンの中で開き（状態を、もう1つ、メモリに持つ。3.5の「ほかのプロセス」の読み手は、いま、ここだけが使う。6.12の281）、その最後の同期したコミット（位置）を決める。`Commit` は、この読み手が開く間だけ待たせる：位置が決まるまで（その後、ファイルを送る間は、止めない）。頭の行は、デーモン自身の状態（`heads` の行）から、位置のコミットのものを読み、位置の連番と合わなければ、`failed` で終える（`the engine's head is behind its last commit; take the backup again after the next commit`）。それから、位置・頭の行・`files/`（一時のファイルは除く。位置より後に置いた原本が入ることもある）・エンジンのファイル（セグメントを位置まで、組になるときのチェックポイント、状態のオブジェクトのファイル、`head`）の順に送る（上記の「バイトの並び」）。クライアントは、空のディレクトリに、0700と0600で作り、道を確かめ（`files` か `logdb` の下だけ）、すべてのファイルを同期して、それからディレクトリを（深いほうから）同期する。失敗したら、書いたものは残るので、呼ぶ側が消す。
- `check`（案。#70 の計画への答え（2026-11-23）で決めた）：デーモンが開いていないデータのディレクトリ（`whiteroom backup` の写し、止めたデーモンのデータのディレクトリ）を、何も変えずに確かめる、デーモンの実行ファイルのサブコマンド（`whiteroom-db check [-config FILE] [-data DIR]`。9.4）。読み手の接続のメッセージではない：写しは、どのデーモンにも開かれておらず、ソケットが無い（#70 の issue が、候補にしたとおり）。
  - 見るもの：(1) `engine`：エンジンのファイルを、`Inspect` の `Check`（3.5の「保守モード」）で。デーモンが開くときの復旧が、変えるもの・使わないもの（書きかけの末尾・作りかけのセグメント・チェックポイント・`head` のずれ）と、ログ・状態・すべてのオブジェクトのハッシュの問題を、すべて、場所つきで。(2) `original`：`files/` の、名前が原本の形（`files/<小文字の16進数2桁>/<小文字の16進数64桁>`で、2桁は、その上のディレクトリの名前）のものを、すべて、最後まで読み、ふつうのファイルで（シンボリックリンクでも、ほかのものでもない）、データの SHA-256 が、名前のハッシュと同じか。`.tmp-*` など、ほかの名前は、見ない。
  - 見ないもの：表の行（索引・履歴・監査・アカウント）と、文書が指す原本の有無（どの文書も指さない原本も）：デーモンの上の `store` が読むので、写しの上で、もう1つのデーモンを動かして、`whiteroom doctor` で確かめる。表の版（`meta` の `schema`）：`Inspect` は、デーモンの確かめ（`Accept`）を呼ばないので、デーモンの知る版（`dbwire.TableVersion`）より新しい版の写しも、`check` は通し、起動を断るのは、`serve`（と `compact`・`gc`・`accept-break`）だけ。`check` の範囲の残りは、6.12の288。
  - クラッシュで止まったデーモン：書くプロセスが、閉じずに止まったデータのディレクトリは、デーモンの `Open` が直すもの（書きかけの末尾・`head` のずれ）を持つので、`check` は、問題として示す（直す前に示すため。そう決めた）。デーモンを1度動かして、閉じる（直させる）と、通る。
  - 出力：問題を、1行ずつ、標準出力に（`engine: <ファイル> at offset N: <理由>`・`original: files/<2桁>/<ハッシュ>: <理由>`。キーも値も、オブジェクトと原本のデータも入らない）。最後に、まとめの1行（`no problems found in DATA`・`N problems found in DATA`・1000件で止めたときは `stopped after 1000 problems in DATA`）。終了コードは、問題が無ければ 0、あるときと、確かめを動かせなかったときが 1、使い方の誤りが 2（9.4の「終了コード」）。
  - 動かせるとき：データのディレクトリを開いているプロセス（デーモン・保守）が無いこと。あれば、約2秒待って、何も変えずに、1で失敗する。同期に失敗した後の印（下記の「同期の失敗」）は、保守と同じに守る：同じ起動の印と、読めない印は、断り、前の起動の印は、消さずに、そのまま残す（何も書かない確かめなので。`serve`・`compact`・`gc`・`accept-break` は、消す）。マシンの起動ごとのIDを読めなければ、何も変えずに失敗する。データのディレクトリに、このユーザーが書けなくても、動く（印を書かないので）。
  - 何も書かない：エンジンのファイルは、書く呼び出しをすべて断る包み（`writeFS`）を通して開き、`files/` も、別の同じ包みで読む。デーモンが残した一時のファイル（`files/.tmp-*`）も、消さない。
- 写しの確かめ（案。リストアの前。#70 の計画への答え（2026-11-23）で決めた）：写しは、データのディレクトリなので、まず、デーモンを動かさずに、`whiteroom-db check -data COPY` で、何も変えずに確かめる（上記の `check`）。続けて、表の行（索引・監査・文書が指す原本）を確かめるために、もう1つのデーモンを、別のソケットのディレクトリで、写しの上で動かし（`whiteroom-db serve -data COPY -db OTHER`）、`whiteroom doctor -db OTHER -heads HEADS` で確かめる。この順にする理由（2026-11-23に、`main`（`6983bcb`）で、再現した）：写しの上のデーモンは、書き手として開くので、切れかけの末尾を切り、`head` を書き直し（3.5の「復旧」）、写しを、確かめる前に変える。最後のセグメントが無い写しと、最後のレコードが切れている写しは、デーモンが、1つ前のコミットまでで開け（後者は、切れた末尾を、写しから消してから）、そのあとの `whiteroom doctor` は、`-heads` に、写しを取ったときの頭を渡さなければ、問題を示さない（渡せば、記録の頭が、ログの終わりより先だと示す）。`check` は、どちらも、デーモンが開く前に、問題として示し、写しを変えない：`check` が通る写しは、`Open` が直すものを持たないので、デーモンは、何も切らずに開ける。`check` が示せないものは、上記の `check` の「見ないもの」と、3.5の「移行・バックアップ・リストアの条件」。写しを戻すのは、デーモンを止めて、写しをデータのディレクトリの場所に置くこと（9.4の「`whiteroom backup`」）。写しから戻すコマンドは、まだ無い（6.12の131・258）。
- コピー先（案。#124）：デーモンは、`Hello` の答えで、データのディレクトリの識別（デバイス番号と inode。Linuxだけ）を伝える。`store.Backup`（`whiteroom backup`）は、デーモンに繋ぎ、表の版を確かめた後、コピー先と、その親を、シンボリックリンクと `..` をカーネルのとおりに解いて、たどって比べ（コピー先が無ければ、親から）、データのディレクトリそのものか、その中なら、何も作らずに断る（`DEST is the data directory of the daemon`・`DEST is in the data directory of the daemon`）。コマンドは、その後に、コピー先を作る。理由：デーモンは、`files/` を、名前の順にたどって送るので、コマンドが `files/` の中に書いたものも送り、写しに、原本が重なって入った（2026-11-17に、直す前の実行ファイルで、`files/b` に写すと、終了コード0で終わり、次に `files/c` に写すと、`c/` の中に、`b/` と原本が入り、原本の6つが12になった。測りの残りは、9.4の「`whiteroom backup`」）。限界：別のマウント名前空間で動くデーモン（コンテナーなど）は、デバイス番号が違いうるので、確かめが効かない。識別を伝えないデーモン（テストの、ファイルシステムの模型の上のもの）でも、確かめない。
- 書きながらの圧縮と回収は、変わらず、決めていない（6.12の133）。

**同期の失敗（決定済み。13章）**

同期に失敗した後の、再起動の強制（6.12の129）のうち、デーモンの形に依るもの（決定済み）と、#68 で作ったもの（案。#68 の計画への答え（2026-11-23）で決めた）。

- 拒む範囲（決定済み。13章）：止まった印があって、同じ起動（マシンを再起動していない）なら、デーモンは起動しない。書き手も読み手も繋げず、保守のサブコマンドも動かない（何も変えない確かめの `check` も、断る。前の起動の印は、消さない）。
- 同じ印（決定済み。13章）：エンジンの同期の失敗（3.5の「失敗の扱い」）も、原本の同期の失敗（3.4の「原本」）も、同じ印で、デーモンの全体が止まる（これまでは、原本の同期の失敗では、原本の保存だけが止まり、文書の書き込みは続いた）。
- 置き場所と形（決定済み。13章）：データのディレクトリの直下の、デーモン（Goの側）のファイル。エンジンの形の版にも、表の版にも入らない。
- 止まるとき（案。#109）：エンジンか原本の同期が失敗すると、デーモンは、印を立て（ログに1行：`the store has stopped after a sync failed (<理由>); writes are refused until the daemon is started again after a restart of the machine`）、それからの書く要求（`PutObject`・`PutOriginal`・`Commit`）を、`stopped` で断る。印のファイル（下記）も、このときに書く。読みは続き、デーモンは動き続ける。`Hello` の答えの「止まっているか」が真になる。同期に失敗した原本の `PutOriginal` と、同時に動いていた原本の `PutOriginal` も、`stopped` で失敗する。プロセスの中の印は、デーモンを起動し直すと無くなるので、起動し直せるかは、下記のディスクの印が決める。
- 方法（案）：止まったときの、マシンの起動ごとのID（Linux の boot ID。`/proc/sys/kernel/random/boot_id` の中身で、マシンを起動するたびに変わるUUID。`Hello` の答えの、デーモンの起動ごとのIDとは別）を、印に書く。`whiteroom-db serve`・`compact`・`gc`・`accept-break`・`check` は、始めるときに、いまのマシンのIDを読み、印のIDと同じなら（印が読めないときも）、エンジンを開く前に、何も変えずに断る（ソケットのファイルも、書き手のロックのファイルも作らず、エンジンのファイルも、`files/` の一時のファイルも変えない）。違えば、マシンを再起動した後なので、開く。IDは、始めるときに1度だけ読み、動き出した後は読まない（同期に失敗した後に、`/proc` を読まない）。`init` は、印を書かず、見ない：印のあるディレクトリは、空でないので、いまも `not empty` で断る。デーモンに繋ぐ `whiteroom` のコマンドは、デーモンが起動を断ると、デーモンに届かず、いまと同じ `cannot reach the daemon` で終わる。
- 採らなかった方法（案）：開くときに、ログの末尾を書き直して同期する方法は、書けなかったページが、ログの末尾のほかに、オブジェクトのファイル・ディレクトリの名前・原本（`files/`）にもありうるが、どれかは分からないので、守れない（エンジンの形も変わる）。印を、再起動で空になる場所（`/run` などの tmpfs）だけに置く方法は、決めた置き場所（データのディレクトリの直下）を変え、データのディレクトリごとの場所を設定で決める要がある。IDを使わず、印があればいつも断って、人が消す方法は、再起動の後も、人が消すまで起動せず、無人のサーバーは、止まったままになる。
- どの失敗で印を残すか（案）：エンジンの `ErrFailed` のすべて（同期の失敗・切り戻しの失敗・圧縮の確定点の後の失敗・開くときの同期の失敗。3.5の「失敗の扱い」）と、原本の同期の失敗。デーモンは、エンジンのファイルの名前を知らずには、`ErrFailed` の原因を分けられず、エンジンの文も、マシンを再起動するように言うので、分けない（同じ起動で開き直せるものにも、印が残る。たとえば、`compact` が、ベースの終わりのレコードの書き込みで、空きを使い切ったときも、マシンを再起動するまで、開けない）。`serve` のほか、`compact`・`gc`・`accept-break` も、保守の中の `ErrFailed` で、印を残す（`check` は、何も書かないので、残さない）。`ErrFailed` でない失敗（切り戻せた書き込みの失敗・取り消し・規則の断り・保守の使用中）では、残さない。`init` は、残さない。
- 印（案）：`<DATA>/stopped`（`stopped` の符号と文に合わせた名前）。モードは0600。UTF-8の4行：1行目は人のための文（`whiteroom-db stopped after a sync failed; restart the machine before starting it again`）、続けて `boot: <マシンの起動ごとのID>`・`time: <UTCの時刻。RFC 3339、秒まで。例：2026-11-23T08:49:00Z>`・`cause: <理由>`。理由は、止まったときのログの行と同じ、値の入らない文で、改行は `; ` にし、1024バイトで切る。読むのは `boot:` の行（時刻と理由は、断る文に使う）で、知らない行は読み飛ばす（後の版が、行を足せる）。時刻が読めない・理由が無い（か、印字できない文字がある）印は、その部分を、文から外して断る。読めない印（空・正しい `boot:` の行が無い（途中で切れて、その行まで届かなかったものも）・4096バイトを超える・ふつうのファイルでない（シンボリックリンクも））は、どの起動のものか分からないので、いつも断り、マシンを再起動した後に、人が消すように言う。エンジンの形の版にも、表の版にも入らず、`Backup` は、写さない（データのディレクトリのうち、写すのは `files/` とエンジンのファイルだけ）。
- 書き方と、書くとき（案）：書き方は、名前を先に作って1回で書く。`O_CREATE|O_TRUNC` で開いて、1回で書き、同期して閉じ、データのディレクトリを同期する。一時のファイルと名前の変更は使わない：書く途中で殺されても、空か途中の印が残り、起動を断る。ファイルの同期が失敗しても、ディレクトリの同期までは続け（名前は、ディスクに届くかもしれない）、失敗は、まとめて返す。書くとき：(1) 動いているデーモンは、止まるとき（ログの1行の後）に、止める原因の要求に答える前に書く。同期の失敗が同時に複数あっても、1回だけ書き、どの要求も、印を書いた後に答える。(2) `serve` が、エンジンを開くときに、`ErrFailed` で失敗したとき（開くときの同期の失敗）は、エンジンが閉じた後に書き、起動は、そのエラーで失敗する。(3) `compact`・`gc`・`accept-break` は、`f`（圧縮・回収・認める書き込み）が `ErrFailed` で失敗したとき、エンジンがロックを放す前に、保守の中で書く：その間に、デーモンが開くことは無い。エンジンを開くとき自体の失敗は、エンジンがロックを放した後に書く。
- 書けなかったとき（案）：ログに1行（`cannot leave the mark <DATA>/stopped (<理由>); do not start the daemon on <DATA> again before the machine restarts`）を足し、`serve` は、止まったまま動き続ける（書く要求を断り、読みは続く。いまと同じ）。開くときの同期の失敗と、`compact`・`gc`・`accept-break` は、エラーの文に、この文を `; ` で足して、1で終わる。同期に失敗した後なので、印の書き込みも失敗することがある。同期が失敗しても、印はページキャッシュにあり、同じ起動の次のデーモンは、ふつう、それを見る（印が要るのは、再起動までの間だけ）。始めるときに、データのディレクトリに書けなければ、断る（下記の「書けるかの確かめ」）。残る危険（始めた後に、印の名前を置けなくなる・書き戻しに失敗した印のページを、カーネルが捨てた後に、同じ起動で起動し直す・同期の失敗から印を書くまでの間に、デーモンが殺される）は、3.5の「残る危険」。
- 書けるかの確かめ（案）：印を残せないデータのディレクトリで動かさないために、`serve`・`compact`・`gc`・`accept-break` は、始めるときに、データのディレクトリそのもの（`logdb/` と `files/` の親）に、このユーザーが書けるかを、`access(2)` の `W_OK` で確かめる（ファイルは作らない）。書けなければ、エンジンを開く前に、何も変えずに断る。確かめるのは、起動ごとのIDと、`logdb/` と `files/` と、印の後なので、同じ起動の印があれば、その断りが先に出る。`check` は、確かめない：何も書かないので、書けないデータのディレクトリでも、動く。Linux だけで確かめ、プロセスの中の模擬のファイルシステムでは確かめない（`dbserver.OpenDir` と `dbserver.Maintain` だけ。`dbserver.Open` は、ファイルシステムを渡される）。理由：エンジンは、`logdb/` と `files/` の中にだけ書くので、直下に書けなくても、開いて動くが、止まるときに、印を置けず、同じ起動で開き直せてしまう（たとえば、root が `cp -a` で戻したディレクトリの、`logdb/` と `files/` だけを、デーモンのユーザーに替えたとき）。確かめた後に、書けなくなる場合と、満杯のファイルシステムは、確かめられず、3.5の「残る危険」に残る。
- 断る文（案）：コマンドの名前を前に付けて、標準エラーに書き、終了コード1で終わる（ほかの失敗と同じ。9.4の「終了コード」）。同じ起動の印：`<DATA>: a sync failed at 2026-11-23T08:49:00Z (sync <DATA>/logdb/log/…: input/output error), and the machine has not restarted since; restart the machine before starting whiteroom-db on this directory again`（理由と、すること。時刻と理由は、印にあるときだけ入る）。読めない印：`<DATA>/stopped: the mark of a failed sync has no boot ID that this program can read; restart the machine if it has not restarted since the sync failed, and then remove the mark`。印を読めない（権限など）：`<DATA>/stopped: cannot read: <理由>`。データのディレクトリに書けない：`<DATA>: whiteroom-db cannot write in the data directory (permission denied); it must be able to leave the mark of a failed sync there: give the directory to the user of the daemon`（括弧の中は、`access(2)` の理由。読み取り専用のマウントでは、`read-only file system`）。Goの側では、同じ起動の印の断りだけが、`dbserver.ErrNotRestarted` を包む。
- 再起動の後（案）：デーモン（`serve`・`compact`・`gc`・`accept-break`）は、始めるときに、マシンの起動ごとのIDの違う印を見つけたら、エンジンを開いた後（保守では、`f` を呼ぶ前、エンジンのロックの中）に、印を消し、1行書く：`<DATA>: a sync failed at <時刻> (<理由>) before the machine restarted; the mark <DATA>/stopped is removed: check the store with whiteroom doctor`（時刻と理由は、印にあるときだけ）。`check` は、前の起動の印を、消さず、1行も書かない（何も書かないため。次の `serve`・`compact`・`gc`・`accept-break` が、消す）。`serve` は、ログ（日時つき）に、`compact`・`gc`・`accept-break` は、標準エラーに、`whiteroom-db compact: `・`whiteroom-db gc: `・`whiteroom-db accept-break: ` のどれかを前に付けて書く。データのディレクトリは同期しない：クラッシュで印が戻っても、前の起動のものなので、次の起動が、また消す。消せなければ、`cannot remove the mark <DATA>/stopped: <理由>` を1行書き、そのまま続ける。エンジンを開く前には消さない：開けなければ、印は残る。保存先に傷が無いかは、人が、`whiteroom doctor`（9.4）で確かめる。
- 調べてから開くまでの間（案）：印を調べるのは、エンジンがロックを取る前で（断るときに、ファイルを何も変えないため）、エンジンは、その後、書くロックを2秒まで待つ（保守も、2秒待つ）。その間に、動いていたデーモンが同期に失敗して印を残し、止められると、待っていた側は、印を見ずに開ける（2つ目の `serve` か、デーモンが動いている間に始めた `compact`・`gc`・`accept-break` が、ちょうどその2秒の間に、という、ごくまれな場合）。そのため、エンジンを開いた後（保守では、`f` を呼ぶ前。`check` では、ロックを取った後）に、印をもう一度見て、同じ起動のもの（か、読めない印）があれば断る。そのとき、デーモンは、エンジンのファイルへの書き込みを止めてから（`writeFS` が、書く呼び出しを断る。読みは続く）、エンジンを閉じる：止めないと、閉じるときのチェックポイントが、ページキャッシュにだけあるレコードを含み、再起動の後、ログと組にならず、開けなくなる。開くときの復旧の書き込み（壊れた最後のセグメントを消すことと、壊れた末尾を切り詰めることがあり、続けて、その同期と `head`。3.5の「復旧」）は、この確かめの前に済んでいて、取り消せない。費用は、エンジンの書き込みの呼び出しごとに、原子的な読みが1つ。
- 起動ごとのIDの無いシステム（案）：`serve`・`compact`・`gc`・`accept-break`・`check` は、始めるときにIDを読み、読めなければ（Linux のほか、`/proc` を入れないコンテナーや chroot）、何も変えずに、`cannot read the boot ID of the machine: open /proc/sys/kernel/random/boot_id: no such file or directory; whiteroom-db needs it to know whether the machine has restarted since a sync failed` のように言って、1で終わる。IDが、カーネルの形（36バイトの、小文字の16進数とハイフン）でなければ、`the boot ID of the machine is not valid: "<ID>"`。`serve` は、もう Linux だけなので（上記の「実行ファイル」）、`compact`・`gc`・`accept-break`・`check` も、実際は、Linux だけになる（3.5の「対象のOSとファイルシステム」）。Linux では、変わらない。
- 変えないもの（案）：プロトコルとその版（`dbwire.Version`）、表の版（`dbwire.TableVersion`）、エンジンの形の版、`stopped` の符号と文、`Hello` の答えの「止まっているか」、止まった後も読みが続き、デーモンが動き続けること。印は、ソケットのプロトコルに出ない。

  - `serve` は、`-config`・`-data`・`-db`（ソケットのディレクトリ）・`-writer-user`・`-writer-group`・`-reader-group`・`-max-readers`・`-commit-rate`・`-min-free`・`-min-free-inodes`・`-snapshot-idle`・`-stall`・`-max-staged`（意味は、上記の「接続」と「上限」）。設定の項目は、`data`・`db`・`writerUser`・`writerGroup`・`readerGroup`・`maxReaders`・`commitRate`・`minFree`・`minFreeInodes`・`snapshotIdle`・`stall`・`maxStaged`。値は、フラグ、設定の項目、既定の順に決まる。設定ファイルは、`whiteroom` と共用でき（`db` は、どちらも読む）、それぞれ、相手の項目も型と範囲を確かめて、使わない（9.4）。
  - `serve` の動き：標準出力に `serving the data directory <DIR> on the sockets in <DIR> (writer: user <番号>)` を書き、`SIGINT`・`SIGTERM` で止まる（2回目の合図は、プロセスをすぐに終わらせる）。止まるときは、待ち受けを閉じ（ソケットのファイルを消す。書き手のロックのファイルは残す）、動いている要求を10秒まで待ち、頭を書き、エンジンを閉じて、0で終わる。10秒の後も終わらない要求（長い `Backup` など）は、途中で切る（相手には、切れた接続に見える）。その場合も、頭を書き、エンジンを閉じて、0で終わる。Linuxだけで動く：ほかのシステムでは、`runs on Linux only: it needs SO_PEERCRED to know the user of a peer` で失敗する（相手のユーザーを知れないため。6.12の283）。始めるときに、マシンの起動ごとのIDを読み、データのディレクトリの印を確かめ、同期に失敗した後、マシンを再起動していなければ、ソケットのファイルも、書き手のロックのファイルも作らずに、1で終わる（下記の「同期の失敗」）。
  - エンジンの設定（`serve`・`init`・`compact`・`gc`・`check`・`accept-break` が使う。変えるフラグは無い）は、3.4の「エンジンと設定」。

**エンジンの形（決定済み。3.1）**

| 形 | Adaで書く範囲 | `simfs` の行列（3.5の「テスト」） | ビルド | 扱い |
| --- | --- | --- | --- | --- |
| Goのまま（いまのエンジンを、デーモンに入れる） | 無い | そのまま使える | いまのまま（`CGO_ENABLED=0` も通る） | 下記の「進める順」の2で使い（作った。ファイルの形は変えず、エンジンに足したのは、読むだけの `Tx.ScanAfter` の1つ：下記の「ファイルの形」）、核ができるまで、正解の役をする |

決めた形の中身：

- 核は、エンジンのうち、ファイルを触らずに、判断と計算だけをする部分。Goから、関数として呼ぶ。
- 「どのファイルに、どの順で、書く・同期する・名前を変えるか」は、核が、指示の列として返す。Goの側が、いまの `vfs`（3.5の「構成」）で、そのとおりにI/Oをし、成功か失敗かを、核に返す。
- いまの証拠が残る：`simfs` のクラッシュ・失敗の差し込みの行列を、そのまま核に流せる。Goのエンジンと核を、同じテストの中で比べられる。
- 証明が届く範囲が広がる：書く順の規則を、指示の列の性質として、SPARKで証明できる（ファイルシステムの模型は、仮定のまま）。
- Adaの側が小さい：ソケットも、並行も、`fsync` の束縛も要らない。
- 分担：Goは、サーバー・並行・I/Oの標準ライブラリと、いまのテスト。Ada/SPARKは、間違えるとデータが壊れる部分（形の符号化と復号、復旧の判断、書く順）の証明と、範囲つきの型。
- 前提（メンテナーが置いた。13章）：リリースが無いので、作り直しは、いとわない。cgoを使わない制約は、サードパーティの依存を無くすためのもので、自作のコードを繋ぐcgoは、別に扱う（1.2）。

引き受けるもの：

- cgoの継ぎ目は、だれも証明しない：SPARKの証明は、呼ぶ側が事前条件を守ることを前提にする。Goの側には、その保証が無いので、核の入り口で、引数を、実行時に確かめ直す。長さと寿命の取り違えは、こういう継ぎ目に集まりやすい。
- 証明するのは「指示」で、「実行」ではない：Goの側が、指示のとおりに実行したかは、証明の外で、いまと同じく、`simfs` の行列で確かめる。クラッシュの後の整合性は、順序の証明と、実行のテストの合わせ技になる。
- 設計が素直でなくなる：書く側は、「指示を返し、結果を受け取る」状態機械になる。同期の失敗のようなエラーの道も、継ぎ目を2回通る。
- 2つの言語と道具を、持ち続ける：ファイルの形を変えるたびに、Adaの証明と、Goの実行とテストの両方を直す。ビルドには、GNATが要る。
- 条件：中心の部分で、証明をやり切ること。証明をしないAdaは、動的なメモリと並行の安全性・先例・テストの道具で、Rustに劣る。

**核の範囲（決定済み。3.1）**

線：判断に、メモリの状態（表やオブジェクトの索引）が要らないものは、すべて核に入れる。

| 核に入れる | Goに残す |
| --- | --- |
| 形の符号化と復号のすべて：セグメント・枠・レコード・`head`・チェックポイント・オブジェクトの見出し、CRC（いまの `format.go`・`ops.go` と、`checkpoint.go` の符号化と復号に当たる） | 実際のI/O（`vfs`）、ロック、サーバー、接続、並行 |
| ログを読むときの判断：レコードの順、末尾がちぎれているのか壊れているのか、どの世代を使うか、チェックポイントがログと合うか（いまの `recover.go` の、何も変えずに決める側に当たる） | 受け入れたレコードを、表と索引に当てはめること（`state.go`・`pmap.go`）、スナップショット |
| 書く順の指示：コミット、セグメントの切り替え、オブジェクトのファイル、チェックポイント、復旧の後始末（いまの `commit.go`・`checkpoint.go` と、`recover.go` の、決めたことを実行する側の、順を決める部分に当たる） | メモリの状態を見る検査（同じオブジェクトが、もうあるか。ベースの終わりの数が合うか） |
| | 保守（圧縮・回収・バックアップ・検査）の進行。核の符号化と復号は使う |

- 量：いまのエンジン（テストを除いて約4,800行）の、3分の1ほど。
- この線にする理由：
  - いまのコードに、同じ継ぎ目がある：復旧は、「何も変えずに決める」と、「決めたことを実行する」に分かれている。
  - 状態を見る検査は、核の判断に戻ってこない：「切るか、壊れているとして拒むか」は、枠のCRCが合うかどうかだけで決まる。CRCが合った後に、Goの側の検査に落ちたものは、必ず「壊れている」で、切ることはない。だから、核は、表を知らなくて済む。
  - 核は、メモリを確保しない：核は、Goが渡したバッファを読み、位置と数だけを返す。キーと値は、Goが、自分のバッファから取り出す。Adaの側のメモリの管理が無くなり、継ぎ目で寿命を取り違える危険が、ほぼ消える。
- 入れないもの：
  - メモリの状態（表と、書き換えない木。3.5の「スナップショット」）：移すと、共有する構造を、SPARKの所有権のモデルで作り直すことになり、証明が重くなる割に、得るものが小さい。
  - 保守の進行：圧縮にも、「新しい世代が揃うまで、古い世代を消さない」という順の規則があるので、後から核に入れる候補。最初は入れない（6.12の272）。

**証明**

対象の候補：

1. どんなバイト列を渡しても、実行時エラーにならない。
2. 符号化したものを復号すると、元に戻る。
3. CRCが合ったレコードは、決して切らない（切ると、確定したコミットを失う）。
4. 切るのは、最後のセグメントの末尾だけ。受け入れた連番は、続いている。
5. 名前を変えるのは、同期の後。レコードを足すのは、それが指すオブジェクトのファイルが残ると決まった後。新しいセグメントに初めのレコードを足すのは、その見出しと名前が残ると決まった後。
6. 同期に失敗した後は、書く指示を、二度と出さない。

- 3から後は、いまは、テストだけで守っている規則。
- 水準（決定済み。13章）：6つすべてを、目標にする。Goのエンジンから差し替える（下記の「進める順」の4）条件は、1〜4と、6。5（書く順）は、電源断の確かめ（6.12の130）の結果で、規則を確かめた後に証明し、証明できなかった部分は、3.5に「証明の外」と書く。
- SPARKが示さないもの：クラッシュの後の整合性は、ファイルシステムの振る舞いの模型の上の性質で、証明しても、`simfs` と同じ前提を、仮定として書くことになる。電源断（6.12の130）、同期に失敗した後の再起動（129）、検出と修復と移行の道具（131）、メモリと開く時間（132）の危険は、言語を替えても減らない。
- 核を作り始めるときに確かめること（GNATのランタイムと、Goのランタイムの共存など）は、6.12の271。

**テスト（案）**

デーモンを通すテストは、データのディレクトリを開かず、プロセスの中のデーモンに繋ぐ。
