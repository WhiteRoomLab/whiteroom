### 9.6 管理用のサーバー（案）

管理用のサーバー（9.2）の土台を、`internal/admin` に作った（#46）。公開用の内蔵サーバー（9.5。`internal/serve`）とは別のサーバーで、JSONだけを返す（ログインの画面は作らない。画面は、管理のAPI（9.7）の後の段階で作る管理画面）。いまあるのは、サーバーの土台（オリジンとHostの確かめ・パスの振り分け・エラーの形・上限・ヘッダー・CSRFの対策・クライアントのアドレス）と、ログイン・ログアウト・いまのセッションの口（`/api/session`）と、ログインの試行の制限。保存の操作・公開の操作・アカウントの管理を呼ぶ管理のAPIは、9.7。コマンド `whiteroom serve admin` と、待ち受けの設定（`-addr`・`-socket`・`-origin`・`-trusted-proxy`）は、作った（9.4）。サーバー自身はTLSを終えない（9.3。リバースプロキシで終えるか、localhost の http で開く）。アカウントとセッションの規則は7.3にあり、この節は、その上のHTTPの側を決める。この節の規則は、「決定済み」と書いたもの（9.1）のほかは、どれも仮に決めたもの（案）。

**置き場所**

- `internal/admin`。公開用の内蔵サーバー（9.5）とは別のサーバー（依存の向きは、`.golangci.yml` の depguard の規則）。

`New` が断るときのメッセージは、`admin: invalid origin "<v>": <理由>`（`<理由>` は、`use https, or http on localhost`・`use only a scheme, a host and a port`・`it has no host`・`invalid port` のどれか）、`admin: invalid trusted proxy invalid Prefix`（正しくない範囲があるとき）、`admin: invalid trusted proxy <範囲>: it covers every address`（固定のビットが0の範囲があるとき。`<範囲>` は、渡された範囲を `%v` で書いたもの：`0.0.0.0/0`・`::/0`・`10.0.0.0/0`。`/1` 以上は受け付ける。範囲は、一覧の順に1つずつ確かめる）、`admin: Config.Accounts is required`。

**経路とオリジン**

- 経路：ブラウザーは、設定した1つのオリジンで、管理用のサーバーを開く。次のどちらか。
  - TLSを終えるリバースプロキシ（Nginx・Apache・Caddyなど）の背後。管理用のサーバーは、localhost かUnixドメインソケットで待ち受ける。VPNの中でも、httpsの背後に置く。コマンド `whiteroom serve admin`（9.4）は、loopbackのTCP（`-addr`。既定は `127.0.0.1:8081`）か、Unixドメインソケット（`-socket`）の、どちらか1つで待ち受け、loopbackでないアドレスは、断る（案）。設定の例は9.4の「設定の例」。
  - SSHのポート転送などで、同じマシンの localhost の http を開く。既定で待ち受けて、`-origin` を省くと、オリジンは `http://<待ち受けたアドレス>`（`127.0.0.1:8081` なら `http://127.0.0.1:8081`）になる（9.4。手元のポートや、ホストの書き方を変えるときは、`-origin` に、ブラウザーで開くものを書く）。
- オリジン：スキームとホストと、あればポートだけ（パス・クエリ・ユーザー情報は不可。末尾の `/` は許す）。httpsは任意のホスト、httpは `localhost`・`127.0.0.0/8` のIPv4アドレス・`[::1]` だけ。ほかのhttpは、起動のときに断る（`use https, or http on localhost`）。Cookieに `Secure` を付ける（下記の「Cookie」）ので、平文のhttpのまま、ネットワーク越しには開けない。NIST SP 800-63B-4 の5.1.1も、Cookieを HTTPS だけで送ることを求める（SHALL）。
- 受け付ける書き方：ホストは、ASCIIの英数字・`-`・`_` の、63バイトまでのラベルを `.` でつないだ253バイトまでの名前、四つの十進数のIPv4アドレス、ブラケットで囲んだIPv6アドレス。最後のラベルが数字のホストは、IPv4アドレスでなければならない（ブラウザーは `127.1` を `127.0.0.1` と読むため）。ポートは1〜65535（先頭の `0` は、そろえるときに落とす。`:08443` は `:8443`）。ASCII以外のホストは、punycode（`xn--`）で書く。httpで使えるIPv6アドレスは `[::1]` だけ（IPv4射影のアドレスは不可）。受け付けた値は、ブラウザーが送る形にそろえる（スキームとホストは小文字、既定のポートは省く、IPv6アドレスは正準の書き方。`http://[0:0:0:0:0:0:0:1]` は `http://[::1]`）。例：`https://admin.example.com`・`http://localhost:8081`。
- 公開サイトと別のオリジンにする：公開サイトのページと、管理のAPIが、同じオリジンで動かないようにする。別のホスト名にする。同じホスト名の別のポートだけで分けるのは勧めない（Cookieはポートで分かれない。下記の「Cookie」）。
- Hostの確かめ：`Host` ヘッダーが、オリジンのホスト（既定のポートでないときは、ホストとポート）と、大文字と小文字を区別せずに等しくない要求は、メソッドによらず、421（`misdirected`）で断る。既定のポートのオリジンは、ポートの無い `Host` と、既定のポートを書いた `Host`（`admin.example.com:443`）の両方を受け付ける。ほかのドメインを管理用のサーバーのアドレスに向けて、ブラウザーから管理のAPIを呼ばせること（DNSリバインディング）を断つ。

**リバースプロキシ**

- HTTPSかどうか：`X-Forwarded-Proto` や `Forwarded` では判断せず（これらは読まない）、設定したオリジンで決める。httpsのオリジンのときだけ、Cookieの名前が `__Host-session` になり、`Strict-Transport-Security` を返す（下記）。
- クライアントのアドレス：試行の制限（下記）が使う。接続の相手が、`TrustedProxies` のどれかに入るか、Unixドメインソケットのとき（相手は、ファイルの権限で入れるプロキシとして、いつも信じる）だけ、`X-Forwarded-For`（複数の行も、コンマで区切った複数の値も）を右から（後ろの値から）見て、最初の、信頼するプロキシでないアドレスを、クライアントにする。すべてが信頼するプロキシなら、いちばん左。ほかのときは、接続の相手のアドレス。`Forwarded`（RFC 7239）と `X-Real-IP` は読まない。IPv4射影のIPv6アドレスはIPv4にそろえ、ゾーンは落とす。
  - 読めない要素（空・アドレスでない・ポートの無い `[addr]`）がある、接続の相手のアドレスが読めない、`X-Forwarded-For` を付けないUnixドメインソケットの相手、のどれかのときは、クライアントを区別せず、全員が1つのクライアント（`::`）になる。
  - `TrustedProxies` に、IPv4射影のIPv6の範囲（`::ffff:10.0.0.0/104` など）を書いても、一致しない（アドレスをIPv4にそろえてから比べるため）。IPv4の範囲で書く。
  - 接続の相手が、信頼するプロキシでなく（`TrustedProxies` に無く、Unixドメインソケットでもない）、`X-Forwarded-For` を持つ（空でも）要求は、その行を読まず、相手のアドレスをクライアントにして、ログに1行書く（サーバー全体で1分に1行まで。下記の「記録」）。リバースプロキシを `TrustedProxies` に入れ忘れた誤りに、運用する人が気づけるようにするため（下記の「設定の責務」）。クライアントのアドレスは、ログイン履歴の記録（7.4）のために、要求ごとに求める（本文を読めた `POST /api/session`（8KiBを超えるパスワードも）と、`Sec-Fetch-Site` の確かめを通った `GET`・`HEAD`・`DELETE` の `/api/session`。管理のAPI（9.7）の、ログインを要する口も同じ）ので、行は、これらの要求が来たときに出る（Cookieの無い要求も）。
- 設定の責務（9.4）：リバースプロキシの背後で動かすときは、`TrustedProxies` にそのプロキシのアドレスを入れる（Unixドメインソケットなら、そのソケットから来た接続は、いつも信頼するプロキシなので、要らない。書くのは、`X-Forwarded-For` の中の、その先のプロキシだけ）。コマンド `whiteroom serve admin` では、`-trusted-proxy`（設定ファイルの `trustedProxies`）が `TrustedProxies` に、`-origin`（`origin`）が `Origin` になる。TCPのときは、同じマシンのリバースプロキシのアドレス（`127.0.0.1`）を書く（コマンドは、待ち受けを見て、信頼するプロキシを足さない。オリジンが `https` で、待ち受けがTCPで、信頼するプロキシが1つも無いと、起動のときに、標準エラーに警告を1行書く）。入れないと、全員が、プロキシのアドレスの1つのクライアントになり、クライアントごとの枠（30回、30秒に1回戻る。下記の「試行の制限」）を全員で分け合い、同じログイン名の組（下記）も1つになる。プロキシでないアドレスを入れると、そのアドレスから送る人が、`X-Forwarded-For` を偽って、クライアントごとの枠を逃れられる。すべてのアドレスを含む範囲を入れると、どの接続の相手もプロキシとして信じられ、1つの接続から、偽ったアドレスをいくつでも名乗れるので、起動のときに断る。それより狭い範囲は、プロキシのアドレスかどうかを、サーバーは確かめられない。入れ忘れは、信頼しない相手の `X-Forwarded-For` の行（上記。下記の「記録」）が示す。ログイン履歴に残るアドレス（7.4）も、ここで決まる（入れ忘れれば、全員がプロキシのアドレスで残り、プロキシでないアドレスを入れれば、偽られたアドレスが残る）。ソケットに繋げるプロセスは、どれも `X-Forwarded-For` を書けるので、ソケットのモード（0660）とグループで、繋げるものを、プロキシだけにする。loopbackのTCPのポートには、同じマシンのどのユーザーのプロセスも繋げ、`127.0.0.1` を信頼していれば、`X-Forwarded-For` も書けるので、ほかのユーザーのいるマシンでは、ソケットを使う（9.4の「設定の例」）。設定のアドレスが実際のプロキシのものかなど、さらに調べることは、コマンドの側でもしない（loopbackでないアドレスでの待ち受けは、コマンドが断る。平文のhttpを、ネットワークに出さないため。`whiteroom doctor` は、設定を調べない。6.12の254）。`-origin` と `-trusted-proxy` の説明は、9.4と、`whiteroom serve admin -h` に書いた。
- プロキシが渡すもの：次の2つ。設定の例で、設定のすべてではない（確かめたドキュメントは、下記の「確かめた事実」）。

| 渡すもの | 理由 | Nginx | Apache（`mod_proxy`） | Caddy（`reverse_proxy`） |
| --- | --- | --- | --- | --- |
| `Host`（クライアントが送ったまま） | Hostの確かめと、CSRFの確かめ（`Origin` と `Host` を比べる）が使う。変わると、421か403になる | `proxy_set_header Host $http_host;`（既定は、`Host` を `$proxy_host` にする） | `ProxyPreserveHost On`（既定は `Off`） | 既定のまま（上流がhttpのとき、`Host` を変えずに渡す） |
| `X-Forwarded-For`（クライアントのアドレスを、右に足したもの） | クライアントのアドレス | `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` | 既定（`ProxyAddHeaders On`）が足す | 既定が足す（`trusted_proxies` を設定しないと、クライアントが送った値は使わない） |

- プロキシの上限と待ち（管理のAPI。設定の例は9.4の「設定の例」。理由と出典は、9.7の「上限」の「リバースプロキシ」と「確かめた事実」）：
  - 本文の上限：Nginx の `client_max_body_size`（既定は1MiB）を、文書の口の本文（64MiBと64KiB）が通る大きさ以上（例：`65m`）にする。アップロードは64MiB。
  - 上流を待つ時間：Nginx の `proxy_read_timeout`（既定は60秒）と、Apache の `ProxyTimeout`（既定は `TimeOut` の値で、60秒）を、120秒以上にする。ログを読む口は、最大120秒、何も送らない。重い仕事の口も、場所を待つ30秒と処理の30秒で、答えの最初のバイトまで最大約60秒かかり、既定の60秒の境にある。
  - アップロードと原本の取得は、最大10分かかる（サーバーの側の期限）が、プロキシの時間を10分以上にする必要は無い：Nginx の `proxy_read_timeout`・`client_body_timeout`・`send_timeout`（どれも既定は60秒）は、2回の読み書きの間の時間で、データが流れ続ける間は、既定のままでも切られない。Nginx は、既定で、本文と答えをバッファーするので、遅い相手は Nginx が受け持つ。Apache の、これらの点は、確かめていない。

**パスと応答**

| パス | メソッド | 内容 |
| --- | --- | --- |
| `/api/session` | `POST` | ログイン |
| `/api/session` | `GET`・`HEAD` | いまのセッション |
| `/api/session` | `DELETE` | ログアウト |

- パスに版（`/api/v1/…`）は付けない（9.7）。
- 管理のAPIのほかの口（文書・メディア・公開とビルド・アカウント・ログ・定義）は、9.7。
- 応答の順（どれかで答えたら、そこで終わる）：
  1. ヘッダー：どの応答にも、下記の「ヘッダー」を付ける（エラーとパニックの応答にも）。
  2. パニックの回復：以降の処理がパニックしたら、記録して（下記の「記録」）、500（`internal`）で答える。応答を書き始めた後なら、`http.ErrAbortHandler` でもう一度パニックして、接続を閉じる（途中までの本文が、全部とみなされないため）。
  3. Host：上記の「経路とオリジン」。421。
  4. パス：パスが `/` で始まらない、空の区切りがある（末尾の `/` も）、区切りが `.`・`..`・空にパーセントデコードされる（`%2e%2e`）ときは、404（`not-found`）。`ServeMux` は、これらを、掃除したパスへ転送するので、転送が起きないように、先に断る。`%2F` は区切りにならない（`a%2Fb` は1つの区切り）。
  5. CSRF：下記の「CSRF」。403。
  6. 期限と振り分け：以降の処理に、30秒の期限（要求のコンテキストの期限）をかけて、口に渡す。口が無いパスは404、メソッドが違えば405（`method-not-allowed`。`ServeMux` が決める `Allow` を付ける。GET のある口は `HEAD` も並ぶ。例：`Allow: DELETE, GET, HEAD, POST`）。
- `HEAD` は、GET と同じヘッダーと `Content-Length` で、本文なしに答える。
- CORS は許さない：`Access-Control-*` のヘッダーを返さない。`OPTIONS` も、ほかのメソッドと同じに、405を返すので、事前の確認（preflight）は通らない。`OPTIONS *` は、Goの自動の応答（200）にせず（`DisableGeneralOptionsHandler`）、サーバーに届いて404になる。

**エラー**

- 形：RFC 9457（2023年7月）の `application/problem+json`。`type`（`about:blank`）・`title`（ステータスの名前）・`status`・`detail`・`code` を、この順に、空白なしの1行で書く（`code` は、プログラムが読む拡張のメンバー）。`detail` は固定の文で、要求の値も、デコーダーのメッセージも入れない。例：

```json
{"type":"about:blank","title":"Unauthorized","status":401,"detail":"wrong login name or password","code":"bad-credentials"}
```

| `code` | ステータス | `detail` | 付けるヘッダー |
| --- | --- | --- | --- |
| `misdirected` | 421 | `the Host of the request is not that of this server` | |
| `not-found` | 404 | `there is no such resource` | |
| `method-not-allowed` | 405 | `the resource does not take this method` | `Allow` |
| `cross-origin` | 403 | `the request does not come from the origin of this server` | |
| `too-large` | 413 | `the body is too large` | （応答の後に、接続を閉じる） |
| `unsupported-media-type` | 415 | `the body must be application/json` | |
| `bad-request` | 400 | `the body is not the JSON that this resource takes` | |
| `unreadable-body` | 400 | `the body could not be read to its end` | |
| `too-many-attempts` | 429 | `too many failed logins; try again later` | `Retry-After`（秒） |
| `bad-credentials` | 401 | `wrong login name or password` | `WWW-Authenticate: Session` |
| `unauthenticated` | 401 | `not logged in` | `WWW-Authenticate: Session` |
| `busy` | 503 | `the server could not answer in time; try again later` | `Retry-After: 5` |
| `internal` | 500 | `the server failed to answer` | |

- 管理のAPIの `code`（`too-many-requests`・`forbidden`・`conflict`・`invalid` など）は、9.7の「エラー」。
- 401の `WWW-Authenticate`：RFC 9110の15.5.2は、401の応答に `WWW-Authenticate` を付けることを求める（MUST）。ここの認証は、Cookieのセッションなので、チャレンジのスキーム名を `Session` にした。`Session` は、IANA の HTTP の認証スキームの登録に無い。ブラウザーは、このスキームでは何もしない（ログインの画面を出さない）と考えているが、実際のブラウザーでは確かめていない。別のスキーム名にするかは6.12の218。
- 503：要求のコンテキストが終わったとき（30秒の期限、クライアントが切ったとき）と、ログインの順番の上限（下記）に当たったときの応答で、`ErrorLog` には書かない（運用する人は、リバースプロキシの記録で見る）。ログインの順番の上限に当たったログインは、ログイン履歴に `busy` として残る（7.4）。
- 500：保存先の失敗など。記録する（下記の「記録」）。
- ネットワークの層が先に返すもの：Goの `net/http` は、壊れた要求に `400 Bad Request` を返して接続を閉じ、ヘッダーが大きすぎる要求（上限の64KiBに、約4KiBの余裕を足したもの）に431を返し、ヘッダーを受け取る時間（10秒）を過ぎた接続を閉じる。これらは口より前の応答で、上記のヘッダーも、problem の形も付かない。

**上限**

| 上限 | 値 |
| --- | --- |
| ログインの要求の本文 | 64KiB（65536バイト）。65536バイトは通り、65537バイトは413。ハッシュにするパスワードは、8KiBまで（7.3）で、すべてのバイトをJSONでエスケープしても（`\u00XX` で1バイト6バイト）収まる |
| 本文の形 | `Content-Type` が `application/json`（大文字と小文字は区別せず、`charset` などの引数は許す）。違えば、本文を読む前に415。空・JSONでない・知らないメンバー・同じメンバーが2つ・メンバーの名前の大文字と小文字の違い・型の違い・不正なUTF-8・値の後ろに続くデータは400（`bad-request`）。本文を終わりまで読めなければ（宣言された長さより前に接続が切れた・チャンクが壊れた・受け取る期限が過ぎた）、`unreadable-body` の400。JSONの `null` はログインの口が400にする |
| 1つの要求の処理 | 30秒（`Server` の期限）。過ぎたら、口は503で答える |
| 同時のログイン | 32（試行の制限を通ったもの）。33個目は、順番には待たせず、503（下記の「試行の制限」）。答える前に、ログイン履歴に記録を書く（7.4） |
| ログインのパスワード | 8KiB（8192バイト）まで（超えるものは、下記の「ログインとセッションの口」） |
| ヘッダーを受け取るまで（`ReadHeaderTimeout`） | 10秒 |
| 本文も含めて、要求を受け取るまで（`ReadTimeout`） | 30秒 |
| 応答を送り終えるまで（`WriteTimeout`） | 60秒 |
| 次の要求を待つ接続（`IdleTimeout`） | 120秒 |
| ヘッダーの大きさ（`MaxHeaderBytes`） | 65536バイト |

- 公開用の内蔵サーバー（9.5）は、大きいファイルのために、応答を送る時間に上限を付けない。ここの応答は小さいので、60秒の上限を付ける。大きい本文を受け取る口と、大きい応答を返す口（管理のAPI。9.7）は、`http.ResponseController` で、自分の期限を延ばす。
- 口ごとの本文の上限：ログインは64KiB。管理のAPIの口の上限は、9.7の「上限」。

**ヘッダー**

どの応答にも付ける（`Server` が書く応答のすべて。エラーとパニックの応答も。上記の「エラー」の、`net/http` が先に返すものには付かない）。口が、必要なら上書きできる（管理のAPIの原本の取得は、上書きせず、`Cache-Control: no-store` のまま返す。9.7）。

| ヘッダー | 値 | ねらい |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'` | 応答はJSONで、何も読み込まない。ブラウザーが文書として開いても、何も読み込まず・実行せず・枠に入れない |
| `X-Content-Type-Options` | `nosniff` | `Content-Type` のとおりに扱い、中身から推測しない |
| `X-Frame-Options` | `DENY` | `frame-ancestors` を知らない古いブラウザーでも、枠に入れない |
| `Referrer-Policy` | `no-referrer` | 管理用のサーバーのURLを、リンク先に送らない |
| `Cache-Control` | `no-store` | セッションや個人情報を含む応答を、ブラウザーやプロキシに保存させない（OWASPのSession Management Cheat Sheetも、セッションを含む応答に求める） |
| `Cross-Origin-Opener-Policy` | `same-origin` | ほかのオリジンのページと、ウィンドウの参照を共有しない |
| `Cross-Origin-Resource-Policy` | `same-origin` | ほかのオリジンのページが、`<img>` などで（CORSを使わずに）、この応答を読み込めないようにする |
| `Strict-Transport-Security` | `max-age=31536000`（1年） | httpsのオリジンのときだけ。`includeSubDomains` と `preload` は付けない（6.12の220） |

- 応答の `Content-Type`：成功は `application/json`、problem は `application/problem+json`。

**CSRF**

ほかのサイトのページが、ログインしている人のブラウザーに、管理のAPIを呼ばせる攻撃（攻撃する人のアカウントにログインさせる、ログインのCSRFも）を断つ。規則（案）：

- 対象：`GET`・`HEAD`・`OPTIONS` 以外のメソッド（`POST`・`DELETE` など）。この3つは、ここでは何も確かめない。ただし、セッションを使う口は、メソッドによらず、下記の `withSession` の確かめを通る（`GET /api/session` が、セッションの最後の要求の時刻を書くことがあるため。7.3）。
- `Sec-Fetch-Site` がある書く要求：Goの `net/http.CrossOriginProtection` が決める。`same-origin` と `none` は通し、ほかの値（`same-site`・`cross-site`・知らない値）は、`Origin` が設定したオリジンと同じでも、403（`cross-origin`）。値は、小文字のまま比べる。
- `Sec-Fetch-Site` が無い書く要求：`Origin` が、設定したオリジンと完全に等しい（大文字と小文字・末尾の `/`・`null` も区別する）こと。そのうえで、`CrossOriginProtection` が、`Origin` のホストを `Host` ヘッダーと、文字列として（ポートを含み、大文字と小文字を区別して）比べる。どちらかが違えば、403。
- どちらのヘッダーも無い書く要求：403。`CrossOriginProtection` は、これを、ブラウザーでない要求として通す（Go 1.27.3のソースで確かめた）ので、ここで断る。OWASP の CSRF Prevention Cheat Sheet は、機微な口では、どちらも無い要求を、不明として断ることを勧める。
- セッションを使う口（`withSession`。`GET /api/session` も）：メソッドによらず、`Sec-Fetch-Site` があって、`same-origin` でも `none` でもない要求（`same-site`・`cross-site`・知らない値。値は、書く要求と同じく、そのまま比べる）は、Cookieを読む前に、403（`cross-origin`）で断る。`Authenticate` を呼ばず、保存先に何も書かず、終わったセッションも消さず、`Set-Cookie` も付けない。`Sec-Fetch-Site` が無い要求は、プログラムの要求と見分けられないので、通す。理由：`SameSite=Strict` は、オリジンでなくサイトで分けるので、同じサイトの別のオリジンのページ（たとえば、同じドメインの公開サイトのページ）から送る `GET` にも、Cookieが付く（RFC 6265bis の5.2から。下記の「確かめた事実」。実際のブラウザーでは確かめていない）。そのページは、応答を読めない（CORSを許さず、`Cross-Origin-Resource-Policy: same-origin` を返す）が、`Authenticate` が最後の要求の時刻を書くので、そのページが5分おきに `GET` を送れば、本人が何もしなくても、操作の無い時間の期限（1時間）が来ず、セッションが全体の期限（12時間）まで続く。`Sec-Fetch-Site` を送らないブラウザーの、同じサイトのページからの `GET` は、見分けられず、まだセッションを延ばせる。
- ブラウザーでないプログラム（スクリプト・テスト）：`Origin: <設定したオリジン>` を付け、`Host` を設定したオリジンのものにする。`Host` に既定のポートを書き（`admin.example.com:443`）、`Origin` にポートが無く、`Sec-Fetch-Site` が無い要求は、403になる（ブラウザーは、`Host` に既定のポートを書かず、`Sec-Fetch-Site` を送る）。
- 本文は `application/json` だけ（上記の「上限」）。ほかのサイトのページは、CORSの事前の確認なしには、これを送れず、サーバーはCORSを許さない。ただし、これだけには頼らない（OWASP の CSRF Prevention Cheat Sheet も、`Content-Type` だけを守りとしては勧めない）。
- Cookieは `SameSite=Strict`（下記の「Cookie」）。OWASP は `SameSite` を多層の守りの1つとし、これだけでCSRFの対策にはしないので、上の確かめと重ねる。
- トークン（同期トークン・二重送信）は使わない：サーバーに状態が増えず、APIの呼び方が簡単。`Sec-Fetch-Site` を送らない古いブラウザーも、`Origin` の一致で確かめる。
- ブラウザーが `Sec-Fetch-Site` を送るのは、「信頼できる可能性のあるURL」への要求だけ（Fetch Metadata）で、`127.0.0.0/8` と `::1` のホストは、これに当たり、`localhost` の名前も、ユーザーエージェントが `localhost` を外のアドレスに解決しないときは、当たる（Secure Contexts）。そのため、localhost の http でも、ブラウザーは `Sec-Fetch-Site` を送ると考えられる（実際のブラウザーでは確かめていない）。送らないブラウザーは、`Origin` の一致で通る。
- 順は、上記の「パスと応答」の「応答の順」のとおり。そのため、Hostが違えばメソッドによらず421、空の区切りのあるパスへの `POST` は403でなく404、ほかのサイトからの、口の無いパスへの `POST` は、404・405でなく403になる。セッションを使う口の `Sec-Fetch-Site` の確かめ（403）は、振り分けの後、口の中（`withSession`）でする。

**Cookie**

セッションのCookie（7.3）の規則（案）：

| 項目 | 値 |
| --- | --- |
| 名前 | httpsのオリジンでは `__Host-session`、httpのオリジン（localhost）では `session` |
| 値 | セッションのトークン（base64urlの43文字。7.3） |
| 設定（ログイン） | `<名前>=<トークン>; Path=/; HttpOnly; Secure; SameSite=Strict` |
| 消す（ログアウト・無効なセッション） | `<名前>=; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Strict` |

- `Domain` は付けない。`Max-Age` と `Expires` も付けない（ログインのとき）：ブラウザーを閉じると消える、セッションのCookieにする。ただし、ブラウザーのセッションの復元では、閉じても戻ることがある（MDN）。期限は、サーバーが確かめる（7.3）。NIST SP 800-63B-4 の5.1.1は、Cookieが期限のころに消えることを勧める（SHOULD）が、期限の強制には頼らないことを求める（SHALL NOT）。OWASP は、持続しないCookieを勧める。
- `__Host-`（httpsのとき）：`Secure`・`Path=/`・`Domain` なしでなければ、ブラウザーが断る（MDN。RFC 6265bis）。そのため、このCookieは、ホストにだけ結び付き、同じドメインの別のホストが、`Domain` を付けて、同じ名前のCookieを置くことも、別の `Path` で置くこともできない。NIST の5.1.1と OWASP が勧める。
- `HttpOnly`：スクリプトから読めない。`Secure`：httpsだけで送る（NISTの5.1.1。SHALL）。`SameSite=Strict`：同じサイトからの要求にだけ付く（NISTは Lax か Strict を勧める（SHOULD）。OWASP は Strict を勧める）。
- `Secure` は、localhost の http でも付け、名前を `__Host-` にしない（ブラウザーの扱いの根拠は、下記の「確かめた事実」の MDN と issue 2605。実際のブラウザーでは確かめていない。ログインできないときは、httpsの背後で開く。6.12の217）。
- Cookieはポートで分かれない（RFC 6265bis -22。2025年12月1日のInternet-Draft）：同じホスト名の別のポートで動くものにも、Cookieが送られ、置き換えられる。公開サイトと同じホスト名の別のポートにしない。localhost で試すときは、同じ localhost の別のポートで、信用できないプログラムを動かさない。
- 同じ名前のCookieが2つ以上ある要求（1行にも、複数の行にも）は、セッションが無く、`previous` のトークンも無いものとして扱う（このサーバーが付けたのでないものがあるため）。httpsのオリジンで、`session` という名前のCookieは、読まない。
- トークンは、Cookieだけから読む。クエリ・`Authorization`・ほかのヘッダーからは読まない（下記の「記録」）。
- 失敗したログイン（401・429・503・500）と、拒んだ要求（421・404・403・405・413・415・400）は、Cookieもセッションも、そのままにする。

**ログインとセッションの口**

- `POST /api/session`（ログイン）：
  - 要求：`Content-Type: application/json`、本文は `{"login": "…", "password": "…"}`。2つとも必須で、`null`・知らないメンバー・同じメンバーが2つ・型の違いは400。ここまでの問題は、試行として数えない。
  - 順：本文を読む → クライアントを求める（7.4） → パスワードの長さを確かめる（8KiBを超えれば、下の401で終わる） → 試行を数える → ログインの順番に入る（下記の「試行の制限」） → `Login`（7.3） → 試行の終わり。
  - 成功（200）：`Content-Type: application/json`、`Set-Cookie` を1つ付ける。ログインのCookieを持って来た要求なら、そのトークンを `previous` として渡し、前のセッションを終わらせる（Cookieが1つのときだけ）。
  - `ErrBadCredentials`（401 `bad-credentials`）：何も呼ばない（試行は数えたまま）。ログイン名が無い・パスワードが違う・保留のアカウント・無効のアカウント・8KiBを超えるパスワードのどれも、同じ応答。
  - 8KiB（8192バイト）を超えるパスワード：`Login` の前に、上と同じ401で答える。長さは、打たれたテキストのバイト数（文字の数でも、NFCにした後の長さでもない）。試行として数えず（どの表にも入れず）、`Login` を呼ばない。そのため、ハッシュを作らず、パスワードの照合も、アカウントの行を読むこともせず、ログイン名にもアカウントにも依らない。答える前に、ログイン履歴に `too-long` の記録を書く（7.4。比べる前に断ったログインと無効なトークンの枠で、1分に10件まで。超えた分は、数えるだけで、保存先に何も書かない。保存先の書き手が別の `Update` で塞がっていると、記録に最大5秒待ち、答えが、その分遅れる）。8192バイトちょうどは、数えて、照合する。理由：そのパスワードは、どのアカウントのパスワードにもなれず（7.3の「パスワード」の「費用」）、ハッシュも作らない安い要求なので、数えると、安い要求で表を埋められる。
  - 試行の制限（429）：下記。ログイン名があるかによらず、どの枠が断ったかによらず、同じ本文。`Login` は呼ばない。答える前に、`LoginRefused` で、ログイン履歴に `rate-limited` を記録する（7.4）。
  - ログインの順番の上限（32）：試行を返して、503（`busy`）。答える前に、`LoginRefused` で、ログイン履歴に `busy` を記録する（7.4）。
  - ほかのエラー：コンテキストの終わり（30秒の期限・クライアントが切ったとき）は503（`busy`）、ほか（保存先の失敗・乱数の失敗など）は500（`internal`。記録する）。試行は、パスワードを一度も比べなかったときだけ返し（`account.PasswordCompared` が偽のとき）、比べた後なら数えたままにする（下記の「試行の制限」の「試しの終わり」）。
- 答えの本文（ログインの200と `GET /api/session` の200）：

```json
{"account":{"id":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","login":"yamada","name":"山田 太郎","email":"yamada@example.com","role":"editor","author":"aut_01JBA4C7N9Q3T6W9Z3C6F9H2K5"},"session":{"authenticatedAt":"2026-11-09T01:02:03.456789Z","expiresAt":"2026-11-09T13:02:03.456789Z","idleTimeout":3600,"factors":["password"]}}
```

  - `author` は、紐付けが無いとき、書かない。日時は、UTCのRFC 3339で、時計の持つ秒の下の桁まで書く（`2026-11-09T12:00:00Z` か `…:00.123456Z`）。`expiresAt` は `authenticatedAt` の12時間後。`idleTimeout` は、操作の無い時間の上限（秒。7.3の `SessionIdleTimeout`）。`factors` は、ログインで使った要素（いまは `password` だけ）。パスワードも、パスワードのハッシュも、トークンも、本文に入れない（トークンは `Set-Cookie` だけ）。
- `GET /api/session`（`HEAD` も）：`Sec-Fetch-Site` があって、`same-origin` でも `none` でもなければ、Cookieを読まずに403（`cross-origin`。`withSession`。上記の「CSRF」）。そうでなければ、Cookieのトークンで `Authenticate`（7.3）する。200は上と同じ本文で、`Set-Cookie` は付けない。セッションが無ければ401（`unauthenticated`）で、要求にこのCookieがあれば（2つあっても）、消す `Set-Cookie` を付ける。Cookieの無い要求と、トークンの形でないCookieは、保存先を読まずに答える。コンテキストの終わりは503（Cookieはそのまま）、ほかのエラーは500（記録する）。
- `DELETE /api/session`：Cookieのトークンのセッションを終わらせ（`Logout`）、204で、消す `Set-Cookie` を付け、本文は無い。Cookieが無い・知らないトークン・トークンでないもの・2つあるCookie（このときは何も終わらせない）でも、同じ204（ブラウザーは、どちらにしてもログアウトする）。保存先の失敗は、500（記録する）で、Cookieを消さない。コンテキストの終わりは503。
- 管理のAPI（9.7）の、ログインを要する口も、`GET /api/session` と同じ確かめ（上記の「CSRF」の「セッションを使う口」）を通る。
- 本人のパスワードの変更の口は `PUT /api/session/password`（9.7。Cookie の置き換えは7.3の「ログインとセッション（#46）」の「本人のパスワードの変更」。制限は、セッションごとで、9.7）。
- ログイン履歴（7.4）：口は、要求ごとに、クライアント（上記の「リバースプロキシ」のアドレスと、`User-Agent` のヘッダー。`account.Client`）を、`Login`・`Logout`・`Authenticate`（`withSession`）に渡す。HTTPの側で断ったログイン（8KiBを超えるパスワード・429・503）は、答える前に `Manager.LoginRefused` で知らせ、ログイン履歴に記録させる。どちらも、答え（ステータス・本文・ヘッダー）は変えない。

**試行の制限**

ログインの失敗が続いたときに、試せなくする。アカウントをロックしない（ロックすると、ログイン名を知る人が、わざと失敗させて、本人を使えなくできる。OWASP の Authentication Cheat Sheet も、ロックが、ほかの人を締め出す道具にならないように求める）。待ち時間を延ばし、枠で数える。数えるのは、メモリの中だけ（再起動で忘れる）。ログイン名は、そのままは持たず（ログイン名のSHA-256と、ログイン名のキーとクライアントの範囲を合わせたSHA-256で持つ）、クライアントは、アドレスの範囲で持つ。

数える3つ（案）：

| 数えるもの | 自由な回数 | そのあと | 忘れる |
| --- | --- | --- | --- |
| 組：ログイン名と、クライアントの組ごと | 5回 | 最後に数えた試しから30秒たつまで待つ。試しを数えるたびに待ちが倍（30秒・1分・2分・4分・8分・16分・32分）になり、1時間まで | 最後の試しから24時間。成功したらすぐ |
| ログイン名：すべてのクライアントを合わせて | 100回 | 15分に1回ずつ、枠が戻る（1日に96回） | 100回分すべてが戻ったら |
| クライアント：すべてのログイン名を合わせて | 30回 | 30秒に1回ずつ、枠が戻る | 30回分すべてが戻ったら |

- クライアント：IPv4は1つのアドレス、IPv6は /64 の範囲（顧客が持つ大きさ）。アドレスの決め方は、上記の「リバースプロキシ」。
- ログイン名：`account.NormalizeLogin`（7.3）で正規化し、アカウントがあるかによらず、同じに数える。アカウントは読まない。
- 数えるのは、パスワードを確かめる前で、同時に送られた要求も、枠を超えない。3つのどれかが断れば、何も数えず、429を返す。`Retry-After` は、3つの待ちのうち最も長いものを、秒に切り上げた値（組は最長3600、ログイン名は最長900、クライアントは最長30、ログイン名かクライアントの表が、新しいキーを入れられないときは60。下記の「表」）。応答の本文は、どの枠が断ったかも、ログイン名のアカウントがあるかも示さない。8KiBを超えるパスワードは、その前に断る（上記の「ログインとセッションの口」）ので、数えない。
- 試しの終わり：パスワードが合ったときは、その組を忘れ、ログイン名の枠とクライアントの枠から、1回分ずつ戻す。ほかのクライアントの失敗は、消さない。パスワードを一度も比べなかったときだけ、組の数と、2つの枠を1回分ずつ戻す：ログインの順番の上限に当たったとき（503）と、`Login` が、比べる前に失敗したとき（保存先を読めない・ハッシュの順番を待つ間に要求が終わった・保存したハッシュを読めない）。比べた後は、そのあとがどうなっても、数えたままにする：間違ったパスワード（401）も、合ったパスワードで、要求が切られた（クライアントが切った・30秒の期限が来た。503）ときも、新しいハッシュやトークンを作れなかったとき・セッションを書けなかったとき（500）も。数えたままにするのは、戻すと、戻り方で、パスワードが合っていたかが分かるためと、切って、やり直す人に、試しを返さないため。`Login` は、比べた後のエラーに印を付け（7.3の「ログインとセッション（#46）」の「ログイン」）、サーバーは、`account.PasswordCompared` で見分ける。
- 1つの組が、1つのアドレスから続けると、5回のあと、最初の64分で7回、そのあとは1時間に1回（1日に24回）。別のアドレスは、別の組なので、本人が別のアドレスから入るのは、止まらない。
- 表：組・ログイン名・クライアントの3つで、それぞれ10万件まで覚える（3つが全部いっぱいで約39MiB。1組・1ログイン名・1クライアントで約410バイト。`TestAttemptsMemory` が測って書く）。表がいっぱいでも、全員を止めない（案）：
  - 組の表は、新しい組を断らない。いっぱいのときは、期限が切れた組（最後の試しから24時間）を、なければ、5回未満の組のうち、最後に使ったのが最も古いものを、それもなければ、待たせている組のうち、最後に使ったのが最も古い（最後の試しが最も古い）ものを忘れて、新しい組を入れる。忘れた組は、また来たときに、新しい組として、5回の自由な回数から数え直す。ログイン名とクライアントの枠は、忘れた組の分も数えているので、当てられる回数の上限は変わらない。何も断らず、ログにも書かない。
  - ログイン名とクライアントの表は、新しいキーが来て、いっぱいのときは、期限が切れたもの（数えた分がすべて戻ったもの）を、なければ、数えた分が5回未満のものの、最後に使ったのが最も古いものを忘れて、新しいキーを入れる。数えた分が5回以上のものは、期限が来るまで忘れない：忘れると、ログイン名の枠が守る、当てられる回数の上限（100回と、1日に96回）が、5回未満の分だけ上がる。忘れてよいものが1つも無いときだけ、その試しを断り（429。`Retry-After` は60秒。何も数えない）、ログに書く（下記の「記録」）。
  - 「5回未満」は、試しを数えたときと、戻したときの数で決める。時間がたって5回未満に下がったものは、次に数えるまで、期限が来るまで残る（5回未満に下がってから期限までは、ログイン名で最長1時間、クライアントで最長2分）。
- ログインの順番：試行の制限は、パスワードのハッシュの順番（7.3の「パスワードのハッシュの順番」。`GOMAXPROCS` の4分の1、1以上）より前に数える。順番に上限が無いと、洪水が、数えるための表を、待っているログインでいっぱいにする。そこで、試行の制限を通ったログインを、同時に32までにして、33個目は、順番には待たせずに、試行を返して、503で答える（案。待たせる案は6.12の214）。答える前に、ログイン履歴に `busy` を記録するので、保存先の書き手が別の `Update` で塞がっていると、記録に最大5秒待ち、答えが、その分遅れる（7.4の「記録できなかったとき」）。32は、`GOMAXPROCS` によらない定数（ハッシュ1つが約80ミリ秒かかるので、順番が1つなら、32個の待ちは最長で約2.6秒、4つ（毎秒約35件。7.3）なら約0.9秒）。32の場所は、アドレスごとにも、ログイン名ごとにも分けない、サーバーに1組で、すべて塞がると、本人のログインも503になる（下記の「残る弱点」）。503で断った試しは、数えない（返す）ので、塞ぐ側に費用がかからない。

残る弱点（案）：承知のうえで、仮に決めたもの。直す方法は6.12の213・214・215・219。

- 多数のアドレスから、ログイン名の枠を満たされる：1つのアドレスの組は5回まで自由なので、20個ほどのアドレスから5回ずつ試せば、ログイン名の枠（100回）を満たせる。満たしたあと、どのアドレスからでも、15分に1回の要求を続ければ、枠は満たされたままで（1日に96回）、本人のログインは429（最長900秒）になる。戻ってくる1回分を、本人が先に取れなければ、止められる。
- 同時のログインの上限（32）を、塞がれる：数えられる試しが、パスワードのハッシュの速さ（毎秒約35件。7.3）と同じ速さで続けば、32の場所は塞がり、そのあいだ、本人も含む全員のログインが、順番を待たずに、503になる（答える前の、ログイン履歴の記録は、断りの枠の、1分に10件まで。7.4）。場所は、アドレスごとにも、ログイン名ごとにも分けていない。503で断った試しは数えない（返す）ので、塞ぐ側の費用は、ハッシュまで進む試しだけ（断った試しの記録は、1分に10件までで、超えた分は数えるだけ。7.4）。計算（測っていない）：続けて塞ぐには、毎秒約35件の、数えられる試しが要り、1つのクライアントは、30回のあと30秒に1回なので、約1,050のクライアント（35 × 30。IPv4アドレス、またはIPv6の /64）が要る。IPv6の /48 を持つ人は、/64 を65,536持つので、1人で足りる。この弱点は、承知のうえで受け入れる（決めた（案）。待たせる案は6.12の214）。ログイン済みの人の要求は、ハッシュを作らないので、影響を受けない。
- 同じNATの中の人は、クライアントの枠を分け合い、同じログイン名への試しは、組も分け合う。
- 表が、数えた分が5回以上のもので埋まると、新しいログイン名と新しいクライアントは、断られる（429。`Retry-After` は60秒。ログに書く）。そのとき、数えた分が残っていないログイン名の、本人のログインも、断られる。5回未満のものは古いものから忘れ、8KiBを超えるパスワードは数えないので、安い要求では埋められない：数えられる試しはどれも、パスワードのハッシュまで進むので、速さは、ハッシュの速さ（毎秒約35件）を超えない。計算（測っていない）：5回以上に保てるのは、ログイン名が約31,500個（毎秒35件 × 900秒。15分に1回ずつ数えるとき）、クライアントが約1,050個（毎秒35件 × 30秒）までで、10万の表は埋まらない。ログイン名の表を埋めるには、10万のログイン名に、15分に1回ずつ数える毎秒約111件（はじめに500,000件を75分のうちに）、クライアントの表を埋めるには、10万のクライアントに、30秒に1回ずつ数える毎秒約3,300件が要る。毎秒111件は、開発のマシンのハッシュの速さの約3倍で、ハッシュを同時に計算する数（`GOMAXPROCS` の4分の1）が約3倍（CPUが約50）のマシンなら、ログイン名の表には届きうる。
- IPv6は /64 で数えるので、/48 を持つ人は、65,536のクライアントの枠を持つ。そのときも、ログイン名の枠（100回と、1日に96回）と、パスワードのハッシュの順番は効く。
- 再起動で、数えていたものをすべて忘れる。
- NIST SP 800-63B-4 の3.2.2は、1つのアカウントの、1つの認証の手段の、続けての失敗を100回以下にし、超えたらその手段を使えなくすることを求める（SHALL）。この制限は、これを満たさない：ログイン名ごとに、100回まで続けて試せ、そのあと1日に約96回まで試せて、使えなくならない。延びる待ち時間（例：30秒から1時間）は取り入れた。成功したら前の失敗を数えないこと（SHOULD）は、組だけに取り入れた（ログイン名の枠とクライアントの枠は、1回分しか戻さない）。
- ログイン以外の、パスワードを確かめる口は、ここでは数えない：本人のパスワードの変更（`current` を確かめる。7.3）は、管理のAPIの口が、セッションごとの独自の制限を持つ（9.7。6.12の215）。
- ログアウトは、行の無いトークンでも、保存先の書き込みのロックを取る（何も書かずに戻す）ので、トークンの形をした文字列を大量に送られると、ログインのコミットと競う。影響が小さいので、直していない（先に `View` で行を見れば避けられる。6.12の219）。

**記録**

- 要求のエラーと、ログイン履歴の記録と断った要求の記録（9.7）を書けなかったことと、警告（下記の2つ）は、`Config.ErrorLog`（nil なら捨てる）に書く。`net/http` 自身のエラーは、`NewHTTPServer` に渡した `*log.Logger` に書く。
  - 500：`fail` が、`<メソッド> "<要求のURI>": <エラー>` を1行で書く（例：`POST "/api/session": cannot read a token: …`）。要求のURIは、パスとクエリを、クライアントが送ったとおりに書いたもの。
  - 再設定の後にアカウントを読めなかったとき（9.7）：`<メソッド> "<要求のURI>": cannot read the account after its reset: <エラー>`。答えは200で、トークンを返す（トークンは、行に書かない）。要求の終わりと、アカウントが無いことは、書かない。
  - パニック：`panic serving <メソッド> "<要求のURI>": <値>` と、次の行から、スタックを書く。ヘッダーも本文も書かない。
  - 試行の表に、新しいキーを入れる場所が無いとき（ログイン名かクライアントの表の10万件が、どれも数えた分が5回以上のとき。上記の「表」）：`too many <表> to keep count of; refusing new ones`。`<表>` は、`login names`・`clients` のどちらか。2つの表を合わせて、1分に1行まで。組の表は、あふれないので、書かない。
  - 信頼しない相手の `X-Forwarded-For`：`X-Forwarded-For comes from a peer that is not in TrustedProxies, and is not read; if a reverse proxy sends it, add the proxy to TrustedProxies`。接続の相手のアドレスが読めて、`TrustedProxies` に無く、Unixドメインソケットでもない要求が、`X-Forwarded-For` を（空でも）持つとき。サーバー全体で、1分に1行まで（相手ごとではない）。要求のことは何も書かない（相手のアドレスも、ヘッダーの値も）。クライアントのアドレスを求めるときに書く（上記の「リバースプロキシ」）。
  - ログイン履歴の記録を書けなかったとき：`cannot record <操作>: <理由>`。`<操作>` は、`login.failure`（失敗したログインと、断ったログイン）・`token.failure`（無効なトークン）。応答は変えない（7.4の「記録できなかったとき」）。1分に70行まで：失敗の記録の上限（7.4）の、2つの枠（比べた失敗の60件と、断りとトークンの10件）の数の和。保存先の書き手が別の `Update` で塞がっていると、記録が最大5秒待つので、`<理由>` は `context deadline exceeded` になり、断る応答（8KiBを超えるパスワード・429・503）が、その分遅れる。`admin.New` は、渡された `Manager` の `OnRecordError` を設定し直すので、同じ `Manager` で複数のサーバーを作ると、最後に作ったサーバーの `ErrorLog` が残る（`Manager` を使う前に作る）。
  - 断った要求の記録を書けなかったとき：`cannot record access.denied: <理由>`。管理のAPIが、権限で断った要求（403）を、答える前に記録するときに、書けなかった場合。応答は変えない。記録は、1分に10件までなので、行も1分に10行まで（9.7の「記録」）。
  - 書かないもの：4xx、503（`busy`）、失敗したログイン、成功したログインの、要求ごとの行（上の警告と、記録を書けなかったときの行は別）。アクセスログは、まだ無い。ログインの試し（断ったものも）と、ログアウト・セッションは、ログイン履歴に残る（7.4）ので、ここには書かない。
- URLに秘密を入れない：`fail` とパニックの記録は、要求のURIをそのまま書く。口が、パスやクエリから、トークンやパスワードを読むと、記録に残る。そこで、どの口も、秘密を、パスにもクエリにも入れない。招待と再設定のトークン（7.3。admin が本人に渡すURLに入れるもの）は、管理のAPIが、招待（201）と再設定（200）の答えの本文で返し（9.7）、本人がパスワードを決めるときも、本文で送る（`POST /api/password`。9.7）。URLの形は決めていない：管理のAPIの後の段階で作る管理画面は、URLの `#` の後ろ（フラグメント。ブラウザーはサーバーに送らない）に置いて、本文に入れて送る形にする。セッションのトークンは、Cookieだけ。リバースプロキシのアクセスログも、パスとクエリを書くので、同じ理由。
- 秘密を出さない：パスワードも、トークンも、応答にも、ヘッダーにも、エラーの文にも、ログにも、保存先の記録にも、URLにも出さない。例外は2つだけ：セッションのトークンを渡す `Set-Cookie`（ログインの200と、本人のパスワードの変更の200。渡すことが目的の答え）と、招待（201）と再設定（200）の答えの本文の `token`（9.7。admin が本人に渡すための、一度だけの答え）。ほかの答え・ヘッダー・エラーの文・ログ・記録・URLには出ない（管理のAPIのテストが、答え・ヘッダー・ログ・記録のすべてを調べる）。
