## 3. ストレージ設計

### 3.1 決定済み：専用Content Storeと自作の保存の層

**単一の汎用RDBにすべてを入れる案ではなく、CMS専用Content Storeを、自作の保存の層の上に作る。**

- **保存の層**：Goの標準ライブラリだけで作ったエンジン（`internal/logdb`。3.5）。
- **CMS専用Content Store**：記事・固定ページなどのコンテンツを扱う独立したストレージ領域／抽象化層として設ける（`internal/store`。3.4）。
- **内部形式**は、3.5のエンジンの形（ログ・オブジェクト・チェックポイント）にした（案。形の版の移行は6.12の131）。
- **文書とリビジョンのJSON**は、CAS（内容のSHA-256で指す、書き換えないオブジェクト）に置き、どのIDがどのオブジェクトかは、別の表に持つ（3.4の「表」。別の形式にするかは6.12の1）。CASは、エンジンのオブジェクトにする。
- **メディアの原本**は、中身のSHA-256を名前にしたファイルに置き、本文などからはメディアのIDで参照する（3.4の「原本」・6.6.2。回収は6.12の125）。
- 管理の側のデータ（文書とリビジョンと索引とログインアカウント・セッション（7.3）と、ログイン履歴・アクティビティログ（7.4））は、データのディレクトリの**1つのエンジン**（`logdb/`）に入れる（3.4の「エンジンと設定」。お問い合わせは8章）。
- **外部のモジュール**は使わない（1.2）。

### 3.2 提案段階：専用Content Storeの内部方式

- **Content-addressable Storage（CAS）**：本文・リビジョンなどを内容のハッシュで識別し、原則として不変オブジェクトとして保存。メディアのファイルは、内容のハッシュで保存して指す（決定済み。3.1・6.6.2）。
- **ファイルシステム + メタデータ**：実体データをファイルに、記事ID・スラッグ・リビジョン・参照先を表に保持。
- **Append-only / スナップショット**：過去データを上書きせず、特定時点のサイト状態を再現可能にする。
- **ContentStoreインターフェース**：物理保存形式をCMSコアから隠蔽し、将来、独自バイナリ形式や独自インデックス方式への置換を可能にする。
- **媒体別分離**：画像・添付ファイルをファイルシステムに保管する案。

これらは**専用Content Storeの実装候補**。文書とリビジョンのCASと、ハッシュを名前にした原本は、採用した（決定済み。3.1）。保存のたびに版を足して、過去の版を残すこと（Append-only）も、採用した（案。3.4の「表」。回収は6.12の125）。

### 3.3 未決定：トランザクションと整合性

保存先のデータ（エンジン）と原本（ファイル）は、異なる永続化領域なので、以下の扱いを定義する必要がある。

- オブジェクト書き込み成功／メタデータ更新失敗時の回復
- 未参照オブジェクトの回収（GC）
- リビジョンと公開スナップショットの整合性
- クラッシュ時の復旧・バックアップ・リストア
- DBやデータファイルを壊した際の検出・修復

3.4の「壊れない書き込み」で仮に決めた（案）。残るのは、回収（GC。6.12の125）、バックアップとリストア（9.2。#49）、壊れたものの検出と修復（`whiteroom doctor`。9.2。6.12の131）。

### 3.4 保存先（案）

管理の側の保存先（3.1）を、`internal/store` に作った。`internal/store` はContent Storeで、文書（6.9のJSONの文書）とそのすべての版、エントリーのリビジョン（6.4.1）、メディアの原本（6.6.2）を、データのディレクトリ（下記）に保存して読み、文書とリビジョンから決まる索引（下記の「索引」）も持つ。ログインアカウントの行とセッションの行（7.3）も、同じエンジンの表（`accounts`・`sessions`）に持つが、値は読まず、`internal/account` が読み書きする（下記の「表」）。ログイン履歴とアクティビティログの記録（7.4）は、エンジンの監査イベントに、鎖をつなぎながら足して持ち、読む口と確かめる口も持つ（下記の「操作」）。保存の層は、3.5のエンジン（`internal/logdb`）の上の自作の層（3.5の「構成」）。3.2のContentStoreインターフェースは、`internal/store` の口（下記の「操作」）にした。使う側は、ビルドの読み込みの口（`build.Source`。4.3）のように、要るものだけの口を持つ。この節の規則は、「決定済み」と書いたもの（3.1・6.1）のほかは、どれも仮に決めたもの（案）。

**データのディレクトリ**

保存先は、1つのディレクトリ（データのディレクトリ）に置く。この節のメッセージの例は、データのディレクトリが `/srv/data` のときのもの。

| 名前 | 内容 |
| --- | --- |
| `logdb/` | エンジンのディレクトリ（下記の「エンジンと設定」）。中のファイルは、3.5の「構成」 |
| `files/` | メディアの原本（下記の「原本」） |
| `files/<16進数2桁>/<16進数64桁>` | 原本。名前は、メディアの `hash`（6.6.2）の `sha256:` の後ろ（小文字の16進数64桁）で、ディレクトリの名前は、その初めの2桁（ディレクトリは、初めて使うときに作る） |
| `files/.tmp-<ランダムな16進数16桁>` | 書いている途中の原本。プロセスが途中で止まったときだけ残る |

規則：

- モード：ディレクトリは0700、ファイルは0600で作る（エンジンのファイルも。3.5の「構成」）。
- 作る：`Create` は、無いディレクトリ（親も作る）か、空のディレクトリに作る（あるディレクトリのモードは変えない）。空でなければ、何も変えずに、エラーにする（`/srv/data: not empty; a new data directory needs a missing or empty directory`）。途中で失敗すると、作ったものが残るので、中を空にしてから作り直す。作ったばかりの保存先は、アクティビティログの最初の記録（`store.create`。7.4）を持つ。
- 開く：`Open` と `OpenReader` は、ディレクトリ（シンボリックリンクなら、たどる）の中の `logdb` と `files` が、どちらもディレクトリであることを確かめる。どちらも、シンボリックリンクは不可（`/srv/data/logdb: missing directory`、`/srv/data/files: symbolic links are not allowed`、`/srv/data/files: must be a directory`）。それから、エンジンが、`logdb/` の形を確かめ、ロックを取り、状態を作る（3.5の「復旧」と「ほかのプロセス」）。上の表に無いもの（`README` など）は見ない。
- 外を読まない：`files/` の中からは、`files/` の外を読まない（外を指すシンボリックリンクは、たどらない）。
- 開発者のファイル：スキーマのファイル（6.6.8）とテーマ（5.4）は、データのディレクトリに置かず、開発者のディレクトリ（Gitなどで管理する）に置く。保存先に置くのは、管理画面が書く設定の文書（6.6.8）だけ。これらとデータのディレクトリの場所の渡し方は、コマンド（9.4）で決める（まだ無い）。

**エンジンと設定**

- 1つのエンジン：管理の側のデータは、データのディレクトリの1つのエンジン（`logdb/`）に入れる（決定済み。3.1）。お問い合わせ（8章）は、作るときに、別の保存先にする。
- 設定：`Create`・`Open`・`OpenReader` は、次の設定でエンジンを使う（変える口は無い）。

| 設定 | 値 |
| --- | --- |
| オブジェクトの置き場所 | 混合：64KiB（65536バイト）以上のオブジェクト（文書とリビジョンのJSON）は、ファイル（`logdb/objects/`）に、ほかはログのレコードに入れる（3.5の「オブジェクトの置き場所」。6.12の137） |
| セグメントの大きさ | 64MiB（3.5の「コミット」） |
| チェックポイント | ログが64MiB増えるたびに、バックグラウンドで書く。閉じるときにも書く（3.5の「チェックポイント」。6.12の132） |
| 書くロックを待つ時間 | 2秒（下記の「同時に使う」。3.5の「ロック」。6.12の135） |

- 設定はファイルに残らない：置き場所は、新しいオブジェクトだけに効き、あるオブジェクトは、その置き場所のまま（圧縮でも）。そのため、設定を変えても、移すものは無い。
- 表の版：表の版（`meta` の `schema`。いまは6。下記の「表」）は、エンジンの形の版（3.5の「ファイルの形」。いまは1）と、文書の `schemaVersion`（6.9）とは別に数える。表を変えるときは、表の版を上げ、一度出した版の表は、書き換えない（その版で書いたファイルを、後の版でも読むため）。版1は、索引（下記の「索引」）が無い表（#43 の前）、版2は、索引はあるが、予約（役割 `scheduled` と、エントリーの要約の `scheduledRevision`・`scheduledAt`）が無い表（#44 の前）、版3は、ログインアカウントの表（`accounts`）が無い表（#45 の前）、版4は、セッションの表（`sessions`）が無い表（#46 の前）、版5は、監査の記録（7.4）の鎖の頭（`meta` の `loginLog`・`activityLog`）が無い表（#47 の前）で、版1〜版5の保存先は、書くプロセスとして開くと、版6になる（版1は索引も作り、版2〜版5は表の版の行と、更新の記録（`store.upgrade`）と、その鎖の頭だけを書く。下記の「索引」の「表の版の更新」）。
- 開くときの確かめ：エンジンが状態を作った後、ファイルを変える前に、表の版を確かめる（`/srv/data/logdb: not a store of whiteroom (no schema version)`、`/srv/data/logdb: the store schema is of version 7, newer than this program knows (6)`）。拒んだときは、ファイルを何も変えない。形の版の新しいファイルも、何も変えずに拒む（3.5の「ファイルの形」）。
- ローカルのファイルシステム：エンジンは、`flock(2)` のロックと、ファイルとディレクトリの同期を使う（3.5の「対象のOSとファイルシステム」）。データのディレクトリは、Linuxのローカルのファイルシステムに置く（NFSなどのネットワークのファイルシステムは、対象の外）。
- 版を上げるとき：プログラムを新しい版に替えるときは、同じデータのディレクトリを開いているプロセス（書くプロセスと読み手）を、先に止める（動いているプロセスは、開いたときの版の表のつもりで使い続けるため）。古い版のプログラムは、新しい版の表と形のファイルを、何も変えずに拒む（表の版を上げる更新（1から2、2から3、3から4、4から5、5から6）の後は、前の版しか知らないプログラムは、開けない）。

**表**

自作の層の表（表の版6）：

| 表（番号） | 内容 | キー | 値 |
| --- | --- | --- | --- |
| `meta`（1） | 表の版と、最後の番号と、監査の記録の鎖の頭 | `schema`・`versions`・`revisions`・`numbers`・`loginLog`・`activityLog` | uvarint（表の版、最後の版の番号、最後のリビジョンの番号、エントリーが持ったことのある最大の `number`。無ければ0）。`loginLog`・`activityLog` は、そのログの最後の記録の番号（uvarint）と、その記録の保存したバイト列のSHA-256（32バイト）。記録の無いログには、行が無い（7.4） |
| `documents`（2） | いまある文書の、いまの版（種類とIDごとに1つ） | 種類・0x00・ID | いまの版（`history` の値と同じ形） |
| `history`（3） | すべての文書の、保存したすべての版。消したときは、内容の無い版（消した印）を足す | 種類・0x00・ID・0x00・版の番号（8バイト、ビッグエンディアン） | 版 |
| `revisions`（4） | エントリーのリビジョン（下記の「リビジョン」） | リビジョンのID | リビジョン |
| `entryRevisions`（5） | エントリーごとの、リビジョンのIDの並び（保存した順） | エントリーのID・0x00・リビジョンの番号（8バイト、ビッグエンディアン） | リビジョンのID |
| `summaries`（6） | いまある文書の要約（種類とIDごとに1つ。下記の「索引」） | 種類・0x00・ID（設定の文書は `settings`・0x00） | 要約と、参照するIDの一覧を持つJSON |
| `references`（7） | どの文書が、どのIDを参照しているか（下記の「索引」） | 参照先のID・0x00・参照元の種類・0x00・参照元のID・0x00・役割 | なし（キーだけ） |
| `operations`（8） | 保存の操作が記録する、操作のIDごとのデータ（下記の「索引」） | 操作のID（1〜256バイト） | 呼ぶ側が持たせたデータ |
| `accounts`（9） | ログインアカウントの行（7.3） | アカウントのID（`usr_` とULID） | `internal/account` が書くJSON（7.3の「保存」）。保存先は読まない |
| `sessions`（10） | ログインのセッションの行（7.3） | トークンの文字列のSHA-256（小文字の16進数64桁） | `internal/account` が書くJSON（7.3の「ログインとセッション（#46）」）。保存先は読まない |

規則：

- オブジェクト：文書とリビジョンのJSONは、エンジンのオブジェクト（3.5の「オブジェクトの置き場所」）。内容のハッシュ（SHA-256。`sha256:` と小文字の16進数64桁）で指し、同じ内容は1つだけ持つ（3.2のCAS。決定済み。3.1）。
- 値：版は、番号（uvarint）と、JSONのSHA-256（消した印は0バイト）・保存した日時・保存した人（それぞれ、長さ（uvarint）の後に）。リビジョンは、番号（uvarint）、エントリーのID（長さの後に）、JSONのSHA-256（32バイト）、保存した日時と保存した人（それぞれ、長さの後に）。
- 番号：版とリビジョンの番号は、`meta` の最後の番号に1を足したもの。取り消した `Update` の番号は、次の `Update` が使う。
- 足すだけ：`history`・`revisions`・`entryRevisions` には、キーを足すだけで、書き換えて消す口は、保存の層に無い。オブジェクトは、書き換えられない（エンジンのCAS）。
- いまの版：`documents` の値は、同じ文書の最後の版の写しで、消した印にはならない（消したときは、キーを消す）。読むときに、消した印なら、壊れているとする（`documents "…": invalid value`）。
- 壊れた値：読めない値と、無いオブジェクトやリビジョンを指す値は、表とキーを付けたエラーにする（`meta "versions": invalid value` など）。無いことの分かるエラー（`fs.ErrNotExist`）にはしない（壊れたものを、無い文書とみなさないため）。
- 前の版を残す：どの種類の文書も、保存のたびに版を足し、前の版を残す。消しても、それまでの版は残る（回収は、まだ無い。下記の「まだ無いもの」）。前と同じ内容の版は、同じオブジェクトを指す。
- 保存した日時：UTCのRFC 3339で、秒の下を9桁にそろえて書く（`2026-11-03T08:00:00.120000000Z`。文字列の順が、時刻の順になるように）。1回の `Update`（下記の「操作」）で保存した版とリビジョンは、どれも同じ日時（そのトランザクションを始めたときの時刻）になる。
- 種類：文書の種類は、ビルドの読み込みの口（4.3）の7つ（`entry`・`term`・`media`・`author`・`menu`・`form`・`redirect`）と、設定の文書の `settings`。設定の文書は、1つだけで、IDを空にして持つ。
- アカウントの行とセッションの行（案。7.3）：キーは、アカウントの行がアカウントのID（`usr_` とULID）、セッションの行がトークンの文字列のSHA-256（小文字の16進数64桁。保存先はトークンを見ない）。値は `internal/account` が書くJSONで、保存先は読まない。保存先は、トランザクション、キー（`invalid user ID "usr_x": use "usr_" and a ULID (26 characters in upper case)`・`invalid session key "<キー>": use 64 lower case hexadecimal digits`）、大きさ（`accounts "usr_…": empty value`・`sessions "<キー>": too large: 4097 bytes (max 4096)`。アカウントの行は1〜65536バイト、セッションの行は1〜4096バイト）を、この順に確かめ、消すときは、その行があること（`accounts "usr_…": not found`。`fs.ErrNotExist` を包む）も確かめる。行は、キーの順に返す。キーの形でない行が表にあれば、`Accounts`・`Sessions` が `accounts "x": invalid key` で失敗する（保存先のAPIを通さずに書かれた場合だけ）。索引には入れず、`RebuildIndex` は読みも書きもしない。表の版によらず読み書きできる（表の版1の読み手も、`ErrNoIndex` にならない）。行どうしの規則（ログイン名とメールアドレスの一意、アカウントのセッションの数）は、`internal/account` が、書く `Update` の中で、すべての行を読んで確かめる（`Update` は1つずつ動く）。
- 監査の記録（案。7.4）：表ではなく、エンジンの監査イベント（3.5の「イベント・操作のID・暗号化の封筒」）に置く。ログイン履歴とアクティビティログの記録を、`Record` で、同じ `Update` に足し、そのログの鎖の頭を、`meta` に置く。メモリに持つのは、イベントの数だけで、記録は、ログから読む（`ReadAudit`）。保存先自身も、作るときと表の版を上げるときに、記録を足す（`store.create`・`store.upgrade`）。表の版5以下の保存先には、記録も鎖の頭も無い（`ErrNoAuditLog`）。

**索引**

索引は、いまある文書とエントリーのリビジョンから決まる表（`summaries`・`references`）で、正本ではない（案）。ビルドと同じ検証（6.7）が読む項目と、どの文書がどのIDを参照しているかを、保存先のすべての文書を読まずに引くためにある。保存の操作（6.7）は、サイト全体の模型を、ここから作る。エンジンの中の索引（ハッシュからオブジェクトの位置を引くもの。3.5の「構成」）とは別のもの。

- 更新：`Put`・`Delete`・`AddRevision` は、確かめた後に、同じ `Update` の中で、索引を更新する（文書と索引は、同じコミット。下記の「壊れない書き込み」）。`RebuildIndex` は、文書とリビジョンだけから、`summaries` と `references` の行を作り直す（`Put`・`Delete`・`AddRevision` が作ったはずの行と比べて、無い行と値の違う行を書き、余る行を消す。正しい索引には、何も書かない。行の無い表（表の版の更新）には、すべての行を書く）。操作のIDの記録（`operations`）は、そのまま残す。索引の行は、文書の更新に合わせて、書き換え・削除する（`history` などと違い、足すだけではない）。保存した索引は、いつも、`RebuildIndex` が作るものと同じ。
- 要約：いまある文書ごとに1行で、次の項目だけを持つ（どれも、スキーマのファイルとテーマに依らない値）。
  - エントリー：状態のすべての項目（6.4.1。予約の `scheduledRevision`・`scheduledAt` も）。公開中のリビジョン（`publishedRevision` が指すもの。`status` は見ない）の `slug`・`parent`・`date`・`author`・`sticky`・`terms`（そのリビジョンが保存先にあり、読めるときだけ。どのエントリーのリビジョンでもよい）。最後のリビジョンのID（無ければ空）。
  - ターム：`id`・`taxonomy`・`language`・`translationGroup`・`slug`・`parent`。メディア：`id`・`hash`・`mimeType`。著者プロフィール：`id`・`slug`。メニュー：`id`・`language`・`location`。フォーム：`id`。リダイレクト：`id`・`from`・`to`・`status`。
  - 設定の文書：行はあるが、項目は無い。
  - このプログラムの読み込み（6.7）で読めない文書（後のプログラムが書いたものなど）には、要約が無い（そのために、`Put`・`Delete`・`AddRevision`・`RebuildIndex`・表の版の更新は、失敗しない）。
- 参照：文書のJSONと、エントリーの公開中のリビジョンと予約したリビジョンと最後のリビジョンのJSONにある、エントリー・ターム・メディア・著者プロフィール・フォームのIDを、参照として数える。数えるのは、JSONの文字列の値で、入れ子の深さによらず、カスタムフィールドと本文のテキストの中のものも数える（オブジェクトのキーは数えない。JSONのエスケープで書いたものは、戻した値で数える。6.12の152）。自分のIDは数えない（リビジョンは、そのエントリーのID）。リビジョン・翻訳グループ・ユーザー・メニュー・リダイレクトのIDは、参照としては数えない（メニューとリダイレクトは、参照されない）。`html`・`legacy` のHTMLの中のURLも、数えない（6.12の115）。役割は、`document`（文書のJSON。エントリーの状態と設定の文書も）、`published`（エントリーの公開中のリビジョンのJSON）、`scheduled`（エントリーの予約したリビジョンのJSON）、`latest`（エントリーの最後のリビジョンのJSON）。公開中の（または予約した）リビジョンが最後のリビジョンでもあるエントリーは、同じIDを、2つの役割で持つ（6.12の160）。公開中や予約したリビジョンが、保存先に無いか、読めないときは、その役割の参照を数えない。ほかに、内部の役割 `publishes` で、エントリーの `publishedRevision` と `scheduledRevision`（リビジョンのIDの形のもの）を持ち、`AddRevision` が、足すリビジョンを公開中または予約したものとして持つエントリーを見つけるのに使う（`Referrers` は返さない）。
- 番号：`meta` の `numbers` は、エントリーが持ったことのある最大の `number`（6.4.1）。エントリーの `Put` が上げ、`Delete` は下げない（消したエントリーの番号を、使い回さないため）。`RebuildIndex` と、表の版1の更新は、いまあるエントリーの最大まで上げる。そのため、表の版1から更新した保存先は、更新の前に消したエントリーの番号を覚えていない（6.12の155）。
- 操作のID：`operations` は、保存の操作（6.7の「保存の操作（案）」）が、操作のIDごとに、要求のハッシュと結果を記録する表。ほかから作れない記録なので、`RebuildIndex` は変えない。保存先は、データの中身を読まず、IDの長さ（1〜256バイト。`invalid operation ID: it is empty`・`invalid operation ID: it has 257 bytes (max 256)`）だけを確かめる。`PutOperation` は、あるデータを置き換える。ほかの書き込みと同じ `Update` で書くので、`Update` が失敗すれば、何も残らない。いまは消さない（残す期間は6.12の153）。
- 読み：`Summary`・`Summaries`・`Referrers`・`LastNumber` は、トランザクション・種類・IDを、`Document` と同じ順に確かめ、それから、索引があるかを確かめて、読む。`Update` の中では、その `Update` の書き込みが見える。索引の作らない行は、読み飛ばさずに、エラーにする。要約の行が読めないとき（その種類のものでない項目を持つ行も）は、`summaries "…": invalid value`（上記の「壊れた値」と同じ形）で失敗し、その文書の `Put`・`Delete` も、`RebuildIndex` するまで失敗する。要約のキーのIDが、その種類のIDでなければ、`Summaries` が `summaries "…": invalid key` で失敗する。参照のキーの、参照元の種類・ID・役割と参照先が合わなければ（`published`・`latest`・`publishes` はエントリーだけが持ち、`publishes` の参照先はリビジョンだけ）、`Referrers` と、そのリビジョンを足す `AddRevision` が、`references "…": invalid key` で失敗する。`Operation`・`PutOperation` は、索引の有無によらず動く。
- 表の版の更新：表の版1〜5の保存先を、書くプロセスとして開く（`Open`）と、1回の `Update` で、表の版を6にし、更新の記録（アクティビティログの `store.upgrade`。`detail` に、更新の前の版 `from` と、後の版 `to`。7.4）と、その鎖の頭を書く（データは移さない）。版1の保存先には、索引の行が無いので、同じ `Update` で、`RebuildIndex` が、すべての行を書く。版2〜版5の保存先の索引は、版6のプログラムが作る行と同じ（版2のプログラムは、予約の項目を持つエントリーを保存できなかった。版4〜版6が足したのは、索引の外の表と記録）なので、版2〜版5の更新は、表の版の行と、更新の記録と鎖の頭だけを書き、文書・リビジョン・オブジェクトを読まない。`RebuildIndex` は、すべての文書を読んでハッシュを確かめるので、壊れた文書のオブジェクトがあると、版1の保存先の更新は、直すまで失敗する。版2〜版5の保存先では、壊れたオブジェクトがあっても、更新も `Open` も失敗せず、その文書を読む操作だけが失敗する（下記の「壊れない書き込み」の「読むたびに確かめる」）。また、更新は、版2〜版5の保存先の索引が食い違っていても、直さない（直すのは `RebuildIndex`）。版2の保存先には、`status` が `scheduled` で、予約の2つの項目（`scheduledRevision`・`scheduledAt`）の無いエントリーが入っていることがある（版2のプログラムは、取り込みも保存先のAPIも、予約の項目を知らないまま `scheduled` を受け付けた）。更新は、これを変えず、エントリーの文書は検証し直さない。版3以降のプログラムでは、予約の一覧（`Schedules`）が、日時を零にして先頭に並べ、その予約の日時の公開は、文書の問題（`entries/ent_….json:1:1: /scheduledAt: missing scheduledAt of a scheduled entry`。6.7）で毎回失敗して、公開の仕組みの `Status` に出る（4.4）。公開をやめる（`Unpublish`）かアーカイブすると、予約でなくなる。失敗すれば、元の版のままで、ロックを放し、`Open` は、`/srv/data/logdb: cannot upgrade the table schema to 6, so the store is unchanged: …`（`…` は理由）で失敗する（版2〜版5では、更新のコミットへの書き込みが失敗したときが、これに当たる。次の `Open` が、改めて更新する）。更新の要らない保存先は、`Open` でも何も書かない（2回目の `Open` は、`head` のほかのファイルを変えない）。読み手として開いた（`OpenReader`）版1の保存先は、文書・リビジョン・原本・操作のIDを読めるが、索引の読み（`Summary`・`Summaries`・`Referrers`・`LastNumber`）は、`ErrNoIndex`（`the store has the table schema 1, which has no index; open it as its writer once to build it`）で失敗する。版2〜版5の保存先は、読み手でも、索引を読める（版3の保存先には、アカウントの行が無く、版3と版4の保存先には、セッションの行が無い。どちらの行も、索引によらず読めるので、行が無いと返す）。版5以下の保存先には、監査の記録が無く、読み手でも、記録を読む口・鎖の頭を返す口・確かめる口は、`ErrNoAuditLog`（`the store has a table schema before 6, which has no audit log; open it as its writer once to upgrade it`）で失敗する（7.4）。版7以上は、いまどおり、何も変えずに拒む。版1の更新は、索引のすべての行を1つのレコードに書くので、1回の `Update` の上限（下記の「上限」）が、更新できる大きさを決める（参照を持つエントリーの行は、1件で約2KBなので、約10万件まで。6.12の136）。版2〜版5の更新は、表の版の行と1件の記録だけなので、この上限に当たらない。
- 行の形：`summaries` の値のJSONは、文書の `schemaVersion`（6.9）つきの、上記の項目だけの書き出しと、参照するIDの一覧（役割ごとに、IDの順で、重複なし）を持つ。そのため、語彙の版（6.9）か、要約の項目を変えるときは、表の版を上げ、索引を作り直す更新を足す（それまでに書いた行は、新しい項目が空で読まれるか、`invalid value` で失敗する。6.12の131）。

**操作**

保存先の口（`internal/store`）の操作：

| 操作 | 内容 |
| --- | --- |
| `Create`・`Open`・`Close` | データのディレクトリを作る・開く・閉じる（上記） |
| `OpenReader` | ほかのプロセスから、読み手として開く（下記の「同時に使う」）。`Update` は `read-only transaction`、`PutOriginal` は `the store is opened to read only` で失敗する |
| `View` | 読むトランザクションで、渡した関数を動かす。関数が初めに読んだときの時点の保存先を見る（その後のコミットは見えない）。書く操作は、エラーにする（`read-only transaction`） |
| `Update` | 書くトランザクションで、渡した関数を動かし、関数が成功すれば、コミットする。関数がエラーを返したとき（パニックと取り消しも）は、書いたものを何も残さない。関数が成功しても、記録（7.4）のほかに何かを書き、記録を1件も足していないときは、何もコミットせずに、`ErrUnrecorded` で失敗する（下記の「書くときの確かめ」） |
| `Document`・`Documents` | 文書のいまの版とJSON。1つの文書（種類とIDで指す）か、1つの種類のすべて（IDの順）。無い文書は、無いことの分かるエラー（Goの `fs.ErrNotExist`。`entries/ent_….json: not found`） |
| `History` | 1つの文書のすべての版（消した印も）を、保存した順に（JSONは含めない） |
| `Object` | ハッシュで指した、版かリビジョンのJSON |
| `Put` | 文書を保存する（下記の「書くときの確かめ」）。いまの版と同じバイト列なら、いまの版を返し、何も足さない |
| `Delete` | 文書を消す（消した印の版を足す）。無い文書はエラー。設定の文書は消せない（`the settings document cannot be deleted`） |
| `AddRevision` | エントリーにリビジョンを足す（下記の「リビジョン」） |
| `Revision`・`Revisions` | 1つのリビジョンとJSON。1つのエントリーのすべてのリビジョンを、保存した順に（JSONは含めない） |
| `Summary`・`Summaries` | 文書の要約（上記の「索引」）。1つの文書（種類とIDで指す）か、1つの種類のすべて（IDの順）。無い文書は、無いことの分かるエラー（`entries/ent_….json: not found`） |
| `Referrers` | IDを参照している、いまある文書を、参照元の種類・ID・役割の順に。消した文書のIDにも使え、残っている文書の参照を返す（消す前の確かめのため。6.7）。設定の文書・メニュー・リダイレクトは、参照されない（空） |
| `LastNumber` | エントリーが持ったことのある最大の `number`（上記の「索引」） |
| `RebuildIndex` | 索引を、文書とリビジョンから作り直す（書くトランザクション） |
| `Operation`・`PutOperation` | 操作のIDのデータを読む（無ければ、無いと返す）・置く（上記の「索引」。`PutOperation` は書くトランザクション） |
| `Account`・`Accounts` | アカウントの行のデータ（上記の「表」。7.3）。1つ（アカウントのIDで指す。無ければ、無いと返し、エラーにはしない）か、すべて（IDの順）。索引の有無によらず読める |
| `PutAccount`・`DeleteAccount` | アカウントの行を置く（あれば置き換える。1〜65536バイト）・消す（無ければ、無いことの分かるエラー）。どちらも書くトランザクション |
| `Session`・`Sessions` | セッションの行のデータ（上記の「表」。7.3）。1つ（トークンのSHA-256のキーで指す。無ければ、無いと返し、エラーにはしない）か、すべて（キーの順）。索引の有無によらず読める |
| `PutSession`・`DeleteSession` | セッションの行を置く（あれば置き換える。1〜4096バイト）・消す（無ければ、無いことの分かるエラー）。どちらも書くトランザクション |
| `Record` | 同じ `Update` のコミットに、監査の記録（ログイン履歴かアクティビティログ。7.4）を1件足す。番号・前の記録のハッシュ・時刻は、保存先が付ける。書くトランザクションだけ |
| `Changed` | そのトランザクションが、記録（と鎖の頭）のほかに、何かを書いたか。同じバイト列の `Put` のように、何も書かなかったものは数えない |
| `ReadAudit` | 記録を、古い順に、絞り込み（ログ・期間・アカウント・操作・対象）に合うものだけ、関数が `false` を返すまで渡す。読み手として開いた保存先でも読める（7.4の「読む口と費用」）。表の版5以下の保存先は、`ErrNoAuditLog` |
| `AuditHeads` | ログごとの鎖の頭（最後の記録の番号とハッシュ）。記録のあるログだけ |
| `VerifyAudit` | 鎖を初めからたどり直し、表の頭と、呼ぶ側が渡す、外に書き出した頭と照らす（7.4の「改ざんの検知」） |
| `PutOriginal`・`OpenOriginal` | 原本を保存する・開く（下記の「原本」）。トランザクションの外で使う |

**書くときの確かめ**

`Put` は、次の順に確かめ、最初の問題をエラーにする（そのときは、何も書かない）。

1. トランザクション：書けるトランザクションか（上記の「操作」）。
2. 種類：上記の「表」の8つのどれか（`unsupported kind "page"`）。
3. ID：その種類のID（6.7。`invalid entry ID "ent_x": use "ent_" and a ULID (26 characters in upper case)`）。設定の文書には、IDを渡さない（`the settings document has no ID`）。
4. 保存した人：ログインアカウント（7.3）のIDの書式（`invalid user ID "usr_x": use "usr_" and a ULID (26 characters in upper case)`）。アカウントは、表 `accounts` にあるが、あるかと、その操作の権限があるかは確かめない（管理のAPI（#48）が、7.3の確かめ（`account.Check`）で確かめる）。
5. 大きさ：64MiBまで（下記の「上限」）。
6. 読み込み：ビルドと同じ読み込み（6.7の「JSONの読み込み」。`schemaVersion` は6.9）で、その種類の文書として読む。エラーには、ファイル・行・列とJSON Pointerを付ける（`entries/ent_….json:1:22: /foo: unknown key`）。
7. 文書の `id`：あれば、渡したIDと同じこと（ビルドと同じ。6.7の「ビルドでの検証」。`entries/ent_….json:1:22: /id: id "ent_…" differs from the ID of the document, "ent_…"`）。

`Delete` は、1〜3、設定の文書でないこと、4、文書がいまあること（無ければ `entries/ent_….json: not found`）の順に確かめる。`AddRevision` は、下記の「リビジョン」。

規則：

- 文書の名前：エラーの中の文書の名前は、サイトのディレクトリ（4.3）でのファイルの名前にする（`entries/<ID>.json`・`terms/<ID>.json` など、`revisions/<ID>.json`、`site/settings.json`）。そのため、ビルドのエラーと同じ形になる。
- 形だけ：読み込みは、文書の形だけを確かめ、必須の項目と参照は確かめない（6.7。`{"schemaVersion": 1}` だけの文書も保存できる）。サイト設定との検証（6.7）と正規化は、保存の操作（`internal/edit`。6.7）でする。
- バイト列のまま：JSONは、渡されたバイト列のまま持ち、書き直さない（6.12の1）。そのため、意味が同じでも、バイト列が違えば（末尾の改行など）、新しい版になる。
- 索引：確かめた後に、同じ `Update` の中で、索引を更新する（上記の「索引」）。更新できなければ（索引や、オブジェクトが壊れているときも）、エラーを返す。呼ぶ側は、そのエラーで `Update` の関数を終える（そうしないと、書きかけの文書がコミットされる）。
- 記録の無い書き込み：`Update` は、関数が成功した後に、記録のほかに何かを書き（`Changed`）、記録（7.4）を1件も足していないものを、何もコミットせずに、`ErrUnrecorded`（`the transaction writes but adds no audit record`）で失敗させる。記録だけの `Update` と、何も書かない `Update`（同じバイト列の `Put` など）は、そのまま。保存先の中の書き込み（作る・表の版の更新）は、自分の記録を同じコミットに書く。`PutOriginal` は、例外（7.4の「記録の無い書き込みを断る」）。

**リビジョン**

- ID：リビジョンのIDは、ほかのエンティティと同じく、`rev_` とULID（6.7）にする（内容のハッシュにはしない。決定済み。6.1）。内容は、エンジンのオブジェクトに、ハッシュで持つ。
- 表に持つもの：どのエントリーのものか・保存した日時・保存した人は、JSONに入れず、`revisions` の表に持つ（リビジョンのJSONは、内容だけ。6.4.1。決定済み。6.1）。
- 足すとき（`AddRevision`）：書けるトランザクションか、エントリーのID、リビジョンのID、保存した人、大きさ、読み込み（名前は `revisions/<ID>.json`）を、この順に `Put` と同じく確かめる。それから、エントリーがいまあること（無いものと、消したものは `entries/ent_….json: not found`）と、IDが新しいこと（`revisions/rev_….json: already exists`）を確かめる。同じ内容でも、同じIDのリビジョンは足せない（`Put` と違い、何もしないことにはならない）。
- 書き換えない：リビジョンは、書き換えず、消さない（6.4.1）。エントリーを消しても、そのリビジョンは読める。
- 更新の日時：エントリーを更新した日時は持たず、公開しているリビジョンの保存した日時で代える。サイトマップの `lastmod` と構造化データの `dateModified`（6.8）に使うかは、6.12の26。

**原本**

- ハッシュで指す：原本は、中身のハッシュ（メディアの `hash`。6.6.2）を名前にして、`files/` に置く（上記の「データのディレクトリ」。ハッシュを名前にすることは決定済み。3.1）。同じ中身の原本は、1つのファイルになる。
- 書く（`PutOriginal`）：渡したものを終わりまで読みながら、一時ファイル（`files/.tmp-<ランダムな16進数16桁>`）に書き、ハッシュと大きさを求めて返す。一時ファイルをディスクに同期して閉じてから、原本の名前に変え（`<16進数2桁>` のディレクトリが無ければ作って、`files/` を同期する）、そのディレクトリも同期する。ディレクトリがあっても、開いてから、そのディレクトリのために `files/` を同期していなければ、同期する（強制終了したプロセスが作ったディレクトリは、名前がまだディスクに無いことがある）。そのため、原本のファイルは、すべてあるか、無いかのどちらか。取り消し（Goの `context`）は、渡したものを読むたびに、その前に確かめる。名前を変える前に失敗したら、一時ファイルを消す。
- 同期の失敗：`PutOriginal` の同期（一時ファイル・`files/`・原本のディレクトリ）が1つでも失敗したら、そのストアでは、原本の保存を止める。それからの `PutOriginal` は、何もせずに失敗し（`saving originals has stopped after a sync failed; restart the machine before opening the store again`）、同時に動いていたものも、終わる前に同期が失敗していれば、失敗する。同期に失敗した変更を、Linuxは、ディスクに書かないまま、書いたものとして扱うことがあり、後の同期は、それを書かない。そのため、続けると、原本の名前がディスクに無いのに、`PutOriginal` が成功することがある。マシンを再起動してから、ストアを開き直す（プロセスを再起動するだけでは足りない）。文書の書き込み（`Update`）は止めない。
- 同じ原本：原本の名前のファイルがあれば、置き換える（壊れていなければ、同じ中身）。そのため、同じ原本を同時に書いてもよく、壊れたファイル（中身がハッシュと合わないもの）も、同じ原本を書き直せば直る。
- 受け付けないもの：空のもの（`the original is empty`）と、64MiBを超えるもの（`the original is larger than 67108864 bytes`。超えたところで、読むのをやめる）。
- 開く（`OpenOriginal`）：ハッシュの形（`sha256:` と小文字の16進数64桁）と、ファイルがふつうのファイルで、64MiBまでであることを、開く前に確かめる（シンボリックリンク・ディレクトリ・名前付きパイプなどは、エラーにする）。無ければ、無いことの分かるエラー（`files/9f/9f86…: not found`）。
- 読むときの確かめ：開いたファイルは、終わりまで読んだときに、読んだもののハッシュを確かめ、違えば、終わりの代わりに、エラーを返す（`original sha256:…: the data has the hash sha256:…`）。読んでいる間に64MiBを超えたもの（開いた後で大きくなったもの）も、エラーにする。
- 大きさまで読むとき：ファイルの大きさまでしか読まない読み方（Goの `io.ReadFull` など）では、終わりに届かないので、この確かめが働かない。そう読むときは、自分でハッシュを確かめる（ビルドは、そうしている。6.6.2の「原本を読むとき」）。
- メディアの文書：メディアの文書と原本が合うか（`size`・`mimeType` など）は、ここでは確かめない。保存の操作のメディアの追加と差し替え（6.6.2）は、保存した原本から `mimeType`・`width`・`height` を読んで、文書にし、サイトのディレクトリの取り込み（6.7の「取り込み（案）」）は、すべてのメディアの原本を、文書と照らす。ビルドは、公開するメディアの原本を、文書と照らす（6.6.2の「原本の確かめ」）。

**壊れない書き込み**

- 1つのコミット：1回の `Update` は、エンジンの1つのコミット（ログの1つのレコード。3.5の「コミット」）。関数がエラーを返したとき、パニックしたとき、取り消したとき、コミットの前にプロセスが止まったときは、何も残らない。そのため、プロセスが途中で止まっても、保存先は、前の内容か新しい内容のどちらかになる。止まった後は、次に開くときに、エンジンが、確定したコミットだけを使う（3.5の「復旧」）。
- 片方だけ残ることは無い：オブジェクトと、それを指す版とリビジョンは、同じコミットに入る。文書とリビジョンの書き込みと、その索引の行（上記の「索引」）も、同じコミットに入るので、索引が、文書と食い違うことは無い。ファイルにするオブジェクトは、それを指すレコードより先に書いて同期する（3.5の「コミット」）。そのため、無いオブジェクトを指す版やリビジョンはできず、3.3の「オブジェクト書き込み成功／メタデータ更新失敗」でも、保存先の状態は壊れない（コミットしなかったオブジェクトのファイルは、使われずに残ることがあり、保守モードの回収で消す。3.5の「保守モード」）。監査の記録（7.4）も、同じ `Update` の、ほかの書き込みと同じコミットに入る（記録だけの `Update` は、記録だけのコミット）。記録の無い書き込みは、断る（上記の「書くときの確かめ」）。
- 原本は先に書く：原本は、それを使うメディアの文書より先に書く（`PutOriginal` の後で、メディアの文書を `Put` する）。そのため、途中で止まっても、使われない原本か一時ファイルが残るだけで、無い原本を指すメディアの文書はできない（残ったものの回収は、まだ無い）。
- 同期の失敗：エンジンの同期が1つでも失敗したら、それからの `Update` は、`the store has stopped after a sync failed; restart the machine before opening it again` で失敗する（3.5の「失敗の扱い」。6.12の129）。マシンを再起動してから、開き直す。原本の同期の失敗は、上記の「原本」。
- 読むたびに確かめる：文書とリビジョンのJSONは、読むたびにハッシュと照らし、原本は、終わりまで読んだときに照らす（上記の「原本」）。壊れていれば、エラーにする（`object sha256:…: the data has the hash sha256:…`）。

**同時に使う**

- 同じプロセス：`View` は、同時にいくつも動く。`View` は、`Update` を待たず、そのコミットしていないものも見ない。`Update` は、1つずつ動く。待っている `Update` が動く順は、決めていない。待つのに時間の上限は無く、取り消されれば、関数を呼ばずに、取り消しのエラー（`context canceled` など）を返す。
- 原本：`PutOriginal` と `OpenOriginal` は、トランザクションとも、同じ原本の `PutOriginal` とも、同時に動いてよい（開いたファイルは、置き換える前のものか後のもので、どちらも同じ中身）。
- 書くプロセスは1つ：`Open` は、エンジンの書くロックを取る（3.5の「ロック」）。ほかのプロセスが書くプロセスとして開いていれば、2秒（上記の「エンジンと設定」）の後に失敗する（`/srv/data/logdb: another process holds the writer lock`）。保守モード（3.5の「保守モード」）が動いていれば、すぐに失敗する（`/srv/data/logdb: maintenance is running`）。書くプロセスとして開くのは、管理のサーバーだけにする（3.5の「運用の制約」）。
- 読み手：ほかのプロセス（後のビルド・`whiteroom backup`・`whiteroom doctor` など。9.2）は、`OpenReader` で、読み手として開く。読み手は、書くプロセスを待たず、開いたときと `View` のたびに、ディスクに同期したコミットだけを見る。ファイルを書かない（3.5の「ほかのプロセス」）。書くプロセスが無い間に、読み手がログの終わりを読んでいると、書くプロセスの `Open` は、2秒まで待つ（6.12の135）。

**上限**

- 文書：1つの文書（リビジョンと設定の文書も）は、64MiB（67108864バイト）まで（`entries/ent_….json: too large: 67108865 bytes (max 67108864)`）。サイトのディレクトリ（4.3）と同じ上限を、保存先でも確かめる（APIの層で確かめるかは6.12の24）。
- 原本：64MiBまで（6.6.2。上記の「原本」）。
- 1回の `Update`：エンジンのレコードの本体が256MiB（268435456バイト）まで（`the transaction is too large: 300000000 bytes (max 268435456)`）。64KiB以上のJSONは、ファイルのオブジェクトになり、レコードには、ハッシュと大きさだけが入る（上記の「エンジンと設定」。3.5の「制限」。6.12の136）。

**依存**

- cgo：要らない。`CGO_ENABLED=0` でもビルドでき、すべてのテストが通る（CIの `build without cgo`・`test without cgo`）。cgoが要るのは、テストの `-race` だけ（開発シェルのCコンパイラーを使う）。cgoが有効なビルド（開発シェルの既定）では、Goの `net` などがcgoを使う（6.12の126）。
- 配布：実行ファイルの静的リンク、ほかのシステム向けのビルド（クロスビルド）、配る実行ファイルに付けるライセンスの表示は、6.12の126。
- 使う側：どのパッケージが保存先を使うかは、`.golangci.yml` の depguard の規則が正（`AGENTS.md`）。保存先からのビルドは、`internal/publish` を通る（4.4）。

**まだ無いもの**

- 回収（GC。3.3）：無い。オブジェクトと原本を消す処理は無く、エンジンの保守モードの圧縮と回収（3.5の「保守モード」）も、保存先からは使わない。何を、いつ消すかは、6.12の125。
- バックアップとリストア：エンジンのバックアップ（3.5の「保守モード」）はあるが、保存先の口とコマンド（9.2の `whiteroom backup`）は、まだ無い（#49）。リストアの道具と、壊れたものの検出と修復（9.2の `whiteroom doctor`）も、まだ無い（6.12の131）。バックアップの記録（`backup`）は、書く口ができるときに足す（7.4。6.12の234）。
- 保存の操作と公開の操作を呼ぶ管理のAPI、`Publisher` を動かす管理のサーバー（#48。4.4）。管理のAPI（#48）の後の段階で作る管理画面。保存の操作と公開の操作の前に、操作する人のアカウントがあるかと、権限の確かめ（#48。7.3の `account.Check`）。記録を読む管理のAPI（#48。7.4）。ログイン履歴と鎖の頭の書き出しを、サーバーのプロセスにつなぐこと（#49。7.4）。保存先からのビルドを動かすコマンドと、戻す・再開するコマンド（#49。9.4）。
