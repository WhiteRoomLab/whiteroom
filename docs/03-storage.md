## 3. ストレージ設計

### 3.1 決定済み：SQLite + 専用Content Store

**単一の汎用RDBにすべてを入れる案ではなく、SQLiteとCMS専用Content Storeを併用する。**

- **SQLite**：管理ユーザー・権限・ログイン履歴・アクティビティログなど、整合性・検索・関連性が重要なデータを管理するためのRDBとして採用。
- **CMS専用Content Store**：記事・固定ページなどのコンテンツを扱う独立したストレージ領域／抽象化層として設ける。
- 専用Content Storeを採用することは決定したが、**内部形式を完全自作することまでは決めていない**。
- **文書とリビジョンのJSON**は、SQLiteの中のCAS（内容のSHA-256で指す、書き換えないオブジェクト）に置き、どのIDがどのオブジェクトかは、別の表に持つ（3.4の「表」。別の形式にするかは6.12の1）。
- **メディアの原本**は、中身のSHA-256を名前にしたファイルに置き、本文などからはメディアのIDで参照する（3.4の「原本」・6.6.2。回収は6.12の125）。
- 管理の側のデータは、**1つのSQLiteのファイル**に入れる（3.4の「SQLiteのファイル」。お問い合わせのファイルは8章）。
- SQLiteの**ドライバー**は、`github.com/mattn/go-sqlite3`（cgoで、SQLiteのCのソースを使う）にする（3.4の「依存」。配布は6.12の126）。

### 3.2 提案段階：専用Content Storeの内部方式

- **Content-addressable Storage（CAS）**：本文・リビジョンなどを内容のハッシュで識別し、原則として不変オブジェクトとして保存。メディアのファイルは、内容のハッシュで保存して指す（決定済み。3.1・6.6.2）。
- **ファイルシステム + SQLiteメタデータ**：実体データをファイルに、記事ID・スラッグ・リビジョン・参照先をSQLiteに保持。
- **Append-only / スナップショット**：過去データを上書きせず、特定時点のサイト状態を再現可能にする。
- **ContentStoreインターフェース**：物理保存形式をCMSコアから隠蔽し、将来、独自バイナリ形式や独自インデックス方式への置換を可能にする。
- **媒体別分離**：画像・添付ファイルをファイルシステムに保管する案。

これらは**専用Content Storeの実装候補**であり、CASとAppend-onlyの採用は、次の段落のとおり。

3.4で、次のように決めた：文書とリビジョンは、SQLiteの中のCASにし、メディアの原本は、ハッシュを名前にしたファイルにする（決定済み。3.1）。どの文書も、保存のたびに版を足して、過去の版を残す（Append-only。案。履歴の保持と回収は6.12の125）。

### 3.3 未決定：トランザクションと整合性

SQLiteとContent Storeは異なる永続化領域になり得るため、以下の扱いを定義する必要がある。

- オブジェクト書き込み成功／メタデータ更新失敗時の回復
- 未参照オブジェクトの回収（GC）
- リビジョンと公開スナップショットの整合性
- クラッシュ時の復旧・バックアップ・リストア
- DBやデータファイルを壊した際の検出・修復

3.4で、次のように仮に決めた（案）：オブジェクトと、それを指すメタデータ（版とリビジョン）は、同じSQLiteのファイルに、1つのトランザクションで書くので、プロセスが止まっても、片方だけが残ることは無い。原本は、それを使うメディアの文書より先に書く。残るのは、回収（GC。6.12の125）、バックアップとリストア、壊れたものの検出と修復（`whiteroom doctor`。9.2）。

### 3.4 保存先（案）

管理の側の保存先（3.1のSQLiteと専用Content Store）を、`internal/db` と `internal/store` に作った。`internal/db` は、SQLiteのファイルを作って開き、表の定義を最新の版にして、トランザクションを動かす。`internal/store` はContent Storeで、文書（6.9のJSONの文書）とそのすべての版、エントリーのリビジョン（6.4.1）、メディアの原本（6.6.2）を、データのディレクトリ（下記）に保存して読む。3.2のContentStoreインターフェースは、`internal/store` の口（下記の「操作」）にした。使う側は、ビルドの読み込みの口（`build.Source`。4.3）のように、要るものだけの口を持つ。いまは読み書きの土台だけで、索引と、保存の操作（6.7の検証をしてから保存するもの）と、保存先からのビルドは、まだ無い（ビルドは、サイトのディレクトリ（4.3）から読む）。この節の規則は、「決定済み」と書いたもの（3.1・6.1）のほかは、どれも仮に決めたもの（案）。

**データのディレクトリ**

保存先は、1つのディレクトリ（データのディレクトリ）に置く。この節のメッセージの例は、データのディレクトリが `/srv/data` のときのもの。

| 名前 | 内容 |
| --- | --- |
| `whiteroom.db` | SQLiteのファイル（下記）。開いている間は、SQLiteの `whiteroom.db-wal`・`whiteroom.db-shm` もある（最後に閉じると消える） |
| `files/` | メディアの原本（下記の「原本」） |
| `files/<16進数2桁>/<16進数64桁>` | 原本。名前は、メディアの `hash`（6.6.2）の `sha256:` の後ろ（小文字の16進数64桁）で、ディレクトリの名前は、その初めの2桁（ディレクトリは、初めて使うときに作る） |
| `files/.tmp-<ランダムな16進数16桁>` | 書いている途中の原本。プロセスが途中で止まったときだけ残る |

規則：

- モード：ディレクトリは0700、ファイルは0600で作る（`whiteroom.db-wal`・`whiteroom.db-shm` も、SQLiteが `whiteroom.db` と同じモードで作る）。
- 作る：`Create` は、無いディレクトリ（親も作る）か、空のディレクトリに作る（あるディレクトリのモードは変えない）。空でなければ、何も変えずに、エラーにする（`/srv/data: not empty; a new data directory needs a missing or empty directory`）。途中で失敗すると、作ったものが残るので、中を空にしてから作り直す。
- 開く：`Open` は、ディレクトリ（シンボリックリンクなら、たどる）の中の `whiteroom.db` がふつうのファイルで、`files` がディレクトリであることを確かめる。どちらも、シンボリックリンクは不可（`/srv/data/whiteroom.db: missing file`、`/srv/data/files: symbolic links are not allowed`、`/srv/data/files: must be a directory`）。上の表に無いもの（`README` など）は見ない。
- 外を読まない：`files/` の中からは、`files/` の外を読まない（外を指すシンボリックリンクは、たどらない）。
- 開発者のファイル：スキーマのファイル（6.6.8）とテーマ（5.4）は、データのディレクトリに置かず、開発者のディレクトリ（Gitなどで管理する）に置く。保存先に置くのは、管理画面が書く設定の文書（6.6.8）だけ。これらとデータのディレクトリの場所の渡し方は、コマンド（9.4）で決める（まだ無い）。

**SQLiteのファイル**

- 1つのファイル：管理の側のデータは、1つのSQLiteのファイル（`whiteroom.db`）に入れる（決定済み。3.1）。いまはContent Storeの表（下記の「表」）だけで、後で、索引と、ログインアカウント・セッション・ログ（7章）も入れる。お問い合わせ（8章）は、作るときに、別のファイルにする。
- 設定（`journal_mode` は、ファイルに残るので、一度だけ設定する。ほかは、接続を開くたびに設定する）：

| 設定 | 値 |
| --- | --- |
| `journal_mode` | `WAL` |
| `synchronous` | `FULL`（コミットのたびに、WALをディスクに同期する） |
| `foreign_keys` | 有効（外部キーの制約を確かめる） |
| `recursive_triggers` | 有効（`INSERT OR REPLACE` が、書き換えを拒むトリガー（下記の「表」）をくぐらないように） |
| `busy_timeout` | 5秒（下記の「同時に使う」） |
| `query_only` | 読む接続だけ有効（書けない） |

- 接続：書く接続は1つで、書くトランザクションは、初めに書くロックを取る（`BEGIN IMMEDIATE`。途中でロックを取れずに失敗することが無いように）。読む接続は、別の組で、書けない（上の表の `query_only`）。
- 印：ファイルの印（`application_id`）は `0x5768526D`（ASCIIで `WhRm`）で、このCMSのファイルであることを示す。
- 表の版：表の定義の版は `user_version` に持ち、文書の `schemaVersion`（6.9）とは別に数える（いまは1）。表の定義は、どの表のものも、`internal/db/schema.go` の `migrations` に、版ごとの変更として足していく（ファイルの版を1つにするため）。一度出した版の変更は、書き換えない（その版の表を持つファイルがあるため）。
- 作る（`Create`）：新しいファイルを作り（あるファイルとシンボリックリンクには作らない）、WALにして、1つのトランザクションで、印と最新の版の表を書く。
- 開く（`Open`）：次の順に確かめる。
  1. ふつうのファイルで、書けること（SQLiteは、書けないファイルを読み出し専用で開き、初めて書くときに失敗するため）。
  2. SQLiteのファイルで（でなければ `/srv/data/whiteroom.db: file is not a database`）、印が `0x5768526D` であること（違えば `/srv/data/whiteroom.db: not a database of whiteroom (application_id 0x0)`。空のファイルと、ほかのプログラムのSQLiteのファイルも、こうなる）。
  3. 表の版が、負でなく、このプログラムの知っている版より新しくないこと（`/srv/data/whiteroom.db: the tables are of version 2, newer than this program knows (1)`）。ここまでで拒んだファイルは、変えない（バイト列もそのままで、`-wal`・`-shm` も作らない）。
  4. WALでなければ、WALにする。できなければ、エラーにする（`/srv/data/whiteroom.db: cannot use WAL mode: journal_mode is "delete"`）。
  5. 表の版が古ければ、1つのトランザクションで、最新の版にする（失敗すれば、前の版のまま）。最新の版なら、書くロックを取らない（ほかのプロセスが書いていても、待たずに開ける）。
- ローカルのファイルシステム：WALでは、同じファイルを開くプロセスが、共有メモリ（`whiteroom.db-shm`）を使う。そのため、データのディレクトリは、ローカルのファイルシステムに置く（NFSなどのネットワークのファイルシステムでは使えない）。
- 版を上げるとき：プログラムを新しい版に替えるときは、同じデータのディレクトリを開いているプロセスを、先に止める（動いているプロセスは、開いたときの版の表のつもりで使い続けるため）。古い版のプログラムは、新しい版の表のファイルを開かない（上記の3）。

**表**

| 表 | 内容 |
| --- | --- |
| `objects` | 文書とリビジョンのJSON。内容のハッシュ（SHA-256。`sha256:` と小文字の16進数64桁）で指し、同じ内容は1つだけ持つ（3.2のCAS。決定済み。3.1） |
| `versions` | すべての文書の、保存したすべての版。保存した順の番号・種類・ID・内容（`objects` のハッシュ）・保存した日時・保存した人（ログインアカウント（7章）のID）を持つ。消したときは、内容の無い版（消した印）を足す |
| `documents` | いまある文書の、いまの版（種類とIDごとに1つ） |
| `revisions` | エントリーのリビジョン。保存した順の番号（版とは別の番号）・リビジョンのID・エントリーのID・内容・保存した日時・保存した人を持つ（下記の「リビジョン」） |

規則：

- 足すだけ：`objects`・`versions`・`revisions` には、行を足すだけで、行の書き換えと削除は、トリガーが拒む（`objects are immutable` など。`INSERT OR REPLACE` での置き換えも拒む）。
- いまの版：`documents` の版は、同じ文書の版のうち、消した印でないもの（外部キーの制約とトリガー。`a deletion cannot be the current version`）。
- 前の版を残す：どの種類の文書も、保存のたびに版を足し、前の版を残す。消しても、それまでの版は残る（回収は、まだ無い。下記の「まだ無いもの」）。前と同じ内容の版は、同じオブジェクトを指す。
- 保存した日時：UTCのRFC 3339で、秒の下を9桁にそろえて書く（`2026-11-03T08:00:00.120000000Z`。文字列の順が、時刻の順になるように）。1回の `Update`（下記の「操作」）で保存した版とリビジョンは、どれも同じ日時（そのトランザクションを始めたときの時刻）になる。
- 種類：文書の種類は、ビルドの読み込みの口（4.3）の7つ（`entry`・`term`・`media`・`author`・`menu`・`form`・`redirect`）と、設定の文書の `settings`。設定の文書は、1つだけで、IDを空にして持つ。

**操作**

保存先の口（`internal/store`）の操作：

| 操作 | 内容 |
| --- | --- |
| `Create`・`Open`・`Close` | データのディレクトリを作る・開く・閉じる（上記） |
| `View` | 読むトランザクションで、渡した関数を動かす。関数が初めに読んだときの時点の保存先を見る（その後のコミットは見えない）。書く操作は、エラーにする（`read-only transaction`） |
| `Update` | 書くトランザクションで、渡した関数を動かし、関数が成功すれば、コミットする。関数がエラーを返したとき（パニックと取り消しも）は、書いたものを何も残さない |
| `Document`・`Documents` | 文書のいまの版とJSON。1つの文書（種類とIDで指す）か、1つの種類のすべて（IDの順）。無い文書は、無いことの分かるエラー（Goの `fs.ErrNotExist`。`entries/ent_….json: not found`） |
| `History` | 1つの文書のすべての版（消した印も）を、保存した順に（JSONは含めない） |
| `Object` | ハッシュで指した、版かリビジョンのJSON |
| `Put` | 文書を保存する（下記の「書くときの確かめ」）。いまの版と同じバイト列なら、いまの版を返し、何も足さない |
| `Delete` | 文書を消す（消した印の版を足す）。無い文書はエラー。設定の文書は消せない（`the settings document cannot be deleted`） |
| `AddRevision` | エントリーにリビジョンを足す（下記の「リビジョン」） |
| `Revision`・`Revisions` | 1つのリビジョンとJSON。1つのエントリーのすべてのリビジョンを、保存した順に（JSONは含めない） |
| `PutOriginal`・`OpenOriginal` | 原本を保存する・開く（下記の「原本」）。トランザクションの外で使う |

- `Document` から `Revisions` までは、トランザクションの操作で、渡した関数の中だけで使える（関数が返った後は `the transaction has ended`）。1つのトランザクションの操作を、同時に呼ばない。
- `Update` の関数の中では、同じ保存先の `Update` を呼ばない（自分の終わりを待つことになる）。
- 保存先の操作（`View`・`Update`・`PutOriginal`・`OpenOriginal` など）は、同時に呼んでもよい（下記の「同時に使う」）。

**書くときの確かめ**

`Put` は、次の順に確かめ、最初の問題をエラーにする（そのときは、何も書かない）。

1. トランザクション：書けるトランザクションか（上記の「操作」）。
2. 種類：上記の「表」の8つのどれか（`unsupported kind "page"`）。
3. ID：その種類のID（6.7。`invalid entry ID "ent_x": use "ent_" and a ULID (26 characters in upper case)`）。設定の文書には、IDを渡さない（`the settings document has no ID`）。
4. 保存した人：ログインアカウント（7章）のIDの書式（`invalid user ID "usr_x": use "usr_" and a ULID (26 characters in upper case)`）。アカウントは、まだ無いので、あるかは確かめない。
5. 大きさ：64MiBまで（下記の「上限」）。
6. 読み込み：ビルドと同じ読み込み（6.7の「JSONの読み込み」。`schemaVersion` は6.9）で、その種類の文書として読む。エラーには、ファイル・行・列とJSON Pointerを付ける（`entries/ent_….json:1:22: /foo: unknown key`）。
7. 文書の `id`：あれば、渡したIDと同じこと（ビルドと同じ。6.7の「ビルドでの検証」。`entries/ent_….json:1:22: /id: id "ent_…" differs from the ID of the document, "ent_…"`）。

`Delete` は、1〜3、設定の文書でないこと、4、文書がいまあること（無ければ `entries/ent_….json: not found`）の順に確かめる。`AddRevision` は、下記の「リビジョン」。

規則：

- 文書の名前：エラーの中の文書の名前は、サイトのディレクトリ（4.3）でのファイルの名前にする（`entries/<ID>.json`・`terms/<ID>.json` など、`revisions/<ID>.json`、`site/settings.json`）。そのため、ビルドのエラーと同じ形になる。
- 形だけ：読み込みは、文書の形だけを確かめ、必須の項目と参照は確かめない（6.7。`{"schemaVersion": 1}` だけの文書も保存できる）。サイト設定との検証（6.7）と正規化は、保存の操作（まだ無い）でする。
- バイト列のまま：JSONは、渡されたバイト列のまま持ち、書き直さない（6.12の1）。そのため、意味が同じでも、バイト列が違えば（末尾の改行など）、新しい版になる。

**リビジョン**

- ID：リビジョンのIDは、ほかのエンティティと同じく、`rev_` とULID（6.7）にする（内容のハッシュにはしない。決定済み。6.1）。内容は、`objects` にハッシュで持つ。
- 表に持つもの：どのエントリーのものか・保存した日時・保存した人は、JSONに入れず、`revisions` の表に持つ（リビジョンのJSONは、内容だけ。6.4.1。決定済み。6.1）。
- 足すとき（`AddRevision`）：書けるトランザクションか、エントリーのID、リビジョンのID、保存した人、大きさ、読み込み（名前は `revisions/<ID>.json`）を、この順に `Put` と同じく確かめる。それから、エントリーがいまあること（無いものと、消したものは `entries/ent_….json: not found`）と、IDが新しいこと（`revisions/rev_….json: already exists`）を確かめる。同じ内容でも、同じIDのリビジョンは足せない（`Put` と違い、何もしないことにはならない）。
- 書き換えない：リビジョンは、書き換えず、消さない（6.4.1）。エントリーを消しても、そのリビジョンは読める。
- 更新の日時：エントリーを更新した日時は持たず、公開しているリビジョンの保存した日時で代える。サイトマップの `lastmod` と構造化データの `dateModified`（6.8）に使うかは、保存先からのビルドで決める（6.12の26）。

**原本**

- ハッシュで指す：原本は、中身のハッシュ（メディアの `hash`。6.6.2）を名前にして、`files/` に置く（上記の「データのディレクトリ」。ハッシュを名前にすることは決定済み。3.1）。同じ中身の原本は、1つのファイルになる。
- 書く（`PutOriginal`）：渡したものを終わりまで読みながら、一時ファイル（`files/.tmp-<ランダムな16進数16桁>`）に書き、ハッシュと大きさを求めて返す。一時ファイルをディスクに同期して閉じてから、原本の名前に変え（`<16進数2桁>` のディレクトリが無ければ作って、`files/` を同期する）、そのディレクトリも同期する。ディレクトリがあっても、開いてから、そのディレクトリのために `files/` を同期していなければ、同期する（強制終了したプロセスが作ったディレクトリは、名前がまだディスクに無いことがある）。そのため、原本のファイルは、すべてあるか、無いかのどちらか。取り消し（Goの `context`）は、渡したものを読むたびに、その前に確かめる。名前を変える前に失敗したら、一時ファイルを消す。
- 同期の失敗：`PutOriginal` の同期（一時ファイル・`files/`・原本のディレクトリ）が1つでも失敗したら、そのストアでは、原本の保存を止める。それからの `PutOriginal` は、何もせずに失敗し（`saving originals has stopped after a sync failed; restart the machine before opening the store again`）、同時に動いていたものも、終わる前に同期が失敗していれば、失敗する。同期に失敗した変更を、Linuxは、ディスクに書かないまま、書いたものとして扱うことがあり、後の同期は、それを書かない。そのため、続けると、原本の名前がディスクに無いのに、`PutOriginal` が成功することがある。マシンを再起動してから、ストアを開き直す（プロセスを再起動するだけでは足りない）。文書の書き込み（`Update`）は止めない。
- 同じ原本：原本の名前のファイルがあれば、置き換える（壊れていなければ、同じ中身）。そのため、同じ原本を同時に書いてもよく、壊れたファイル（中身がハッシュと合わないもの）も、同じ原本を書き直せば直る。
- 受け付けないもの：空のもの（`the original is empty`）と、64MiBを超えるもの（`the original is larger than 67108864 bytes`。超えたところで、読むのをやめる）。
- 開く（`OpenOriginal`）：ハッシュの形（`sha256:` と小文字の16進数64桁）と、ファイルがふつうのファイルで、64MiBまでであることを、開く前に確かめる（シンボリックリンク・ディレクトリ・名前付きパイプなどは、エラーにする）。無ければ、無いことの分かるエラー（`files/9f/9f86…: not found`）。
- 読むときの確かめ：開いたファイルは、終わりまで読んだときに、読んだもののハッシュを確かめ、違えば、終わりの代わりに、エラーを返す（`original sha256:…: the data has the hash sha256:…`）。読んでいる間に64MiBを超えたもの（開いた後で大きくなったもの）も、エラーにする。
- 大きさまで読むとき：ファイルの大きさまでしか読まない読み方（Goの `io.ReadFull` など）では、終わりに届かないので、この確かめが働かない。そう読むときは、自分でハッシュを確かめる（ビルドは、そうしている。6.6.2の「原本を読むとき」）。
- メディアの文書：メディアの文書と原本が合うか（`size`・`mimeType` など）は、ここでは確かめない（保存の操作（まだ無い）と、ビルド（6.6.2の「原本の確かめ」）で確かめる）。

**壊れない書き込み**

- 1つのトランザクション：1回の `Update` は、1つのSQLiteのトランザクション。関数がエラーを返したとき、パニックしたとき、取り消したとき、コミットの前にプロセスが止まったときは、何も残らない。そのため、プロセスが途中で止まっても、保存先は、前の内容か新しい内容のどちらかになる（コミットの直前と、`Update` を続けている途中に、プロセスを強制終了（`SIGKILL`）してから開き直すテストで確かめた）。止まった後は、次に開くときに、SQLiteが、WALのうちコミットしたものだけを使うので、ほかの手順は要らない。
- 片方だけ残ることは無い：オブジェクトと、それを指す版とリビジョンは、同じファイルに、同じトランザクションで書く。そのため、3.3の「オブジェクト書き込み成功／メタデータ更新失敗」は起きない。
- 原本は先に書く：原本は、それを使うメディアの文書より先に書く（`PutOriginal` の後で、メディアの文書を `Put` する）。そのため、途中で止まっても、使われない原本か一時ファイルが残るだけで、無い原本を指すメディアの文書はできない（残ったものの回収は、まだ無い）。
- 読むたびに確かめる：文書とリビジョンのJSONは、読むたびにハッシュと照らし、原本は、終わりまで読んだときに照らす（上記の「原本」）。壊れていれば、エラーにする（`object sha256:…: the data has the hash sha256:…`）。壊れたものを見つけて直す操作（9.2の `whiteroom doctor`）は、まだ無い。

**同時に使う**

- 同じプロセス：`View` は、同時にいくつも動く（読む接続は、Goの `GOMAXPROCS` の値と4の大きいほうの数まで。それより多いものは、空くのを待つ）。`View` は、`Update` を待たず、そのコミットしていないものも見ない。`Update` は、1つずつ動く（書く接続が1つのため）。待っている `Update` は、来た順ではなく、決まらない順に動く。待つのに時間の上限は無く、取り消されれば、関数を呼ばずに、取り消しのエラー（`context canceled` など）を返す。
- 原本：`PutOriginal` と `OpenOriginal` は、トランザクションとも、同じ原本の `PutOriginal` とも、同時に動いてよい（開いたファイルは、置き換える前のものか後のもので、どちらも同じ中身）。
- ほかのプロセス：ほかのプロセス（後の `whiteroom backup`・`whiteroom doctor` など。9.2）も、同じデータのディレクトリを、同時に開ける（SQLiteのファイルのロックによる）。読むのは、ほかのプロセスが書いていても待たない。書くのは、ほかのプロセスが書くロックを持っている間、5秒（`busy_timeout`）まで待ち、過ぎれば失敗する（`database is locked`）。
- 順番は無い：ほかのプロセスとの間では、書くロックを待つ順番が無い。SQLiteは、ロックが空いたかを、少しずつ間を空けて（1・2・5ミリ秒…、後は100ミリ秒ごとに）試し直すだけで、5秒を過ぎれば失敗する。そのため、書き続けるプロセスがあると、ほかのプロセスの書き込みは、5秒の後に `database is locked` で失敗することがある（約2ミリ秒の `Update` を続けて書くプロセスの横で、ほかのプロセスの `Update` は、3回のうち2回、5秒で失敗した）。この待ちは、取り消し（Goの `context`）では止まらない（6.12の127）。

**上限**

- 文書：1つの文書（リビジョンと設定の文書も）は、64MiB（67108864バイト）まで（`entries/ent_….json: too large: 67108865 bytes (max 67108864)`）。サイトのディレクトリ（4.3）と同じ上限を、保存先でも確かめる（APIの層で確かめるかは6.12の24）。
- 原本：64MiBまで（6.6.2。上記の「原本」）。

**依存**

- ドライバー：SQLiteのドライバーには、`github.com/mattn/go-sqlite3`（いまはv1.14.52で、SQLite 3.53.4を含む）を使う（決定済み。3.1）。リポジトリで初めての外部のモジュールで、ライセンスはMIT（SQLiteは、パブリックドメイン）。ドライバーを使うのは、`internal/db` だけ。
- cgo：ドライバーの含むSQLiteのCのソースを、cgoでコンパイルするので、ビルドとテストに、Cコンパイラーが要る（開発シェルにある）。`CGO_ENABLED=0` では、ビルドはできても、データベースを開けない（開くと、エラーになる）。
- 配布：SQLiteの版は、ドライバーの版で決まる。実行ファイルの静的リンク、ほかのシステム向けのビルド（クロスビルド）、配る実行ファイルに付けるライセンスの表示、SQLiteの更新の取り込み方は、6.12の126。
- コマンド：コマンド `whiteroom`（9.4）は、まだ保存先を使わない（実行ファイルに、SQLiteは入っていない）。

**まだ無いもの**

- 回収（GC。3.3）：すべての版を残すので、いまは、オブジェクトと、メディアの文書の古い版が使う原本（差し替える前のファイルなど）は、消せない。どのメディアの文書のどの版にも使われない原本（メディアの文書を保存しなかったもの）と、プロセスが止まって残った一時ファイルは、消せるが、消す処理は無い。履歴をどれだけ残すか（消した文書の個人情報を、履歴からも消すことも）と、回収の仕方（バックアップと、原本を書いてメディアの文書をまだコミットしていない書き込みの間は、動かさないことなど）は、6.12の125。
- 読み出し専用で開くこと（バックアップなどの道具のため。6.12の127）、バックアップとリストア（9.2の `whiteroom backup`）、壊れたものの検出と修復（9.2の `whiteroom doctor`）。
- 索引と、保存の操作（6.7の検証と正規化をしてから保存するもの。出力パスの重複の検査（4.1）も）。
- 保存先からのビルド（保存先が、ビルドの読み込みの口（4.3）を作る）。
- WALのファイルの大きさ：大きな書き込みの後、`whiteroom.db-wal` は、その大きさのまま、最後の接続を閉じるまで残る（64MiBの文書を1つ書けば、約64MiB）。6.12の128。

**テスト**

- `internal/db`：作ることと開くこと（シンボリックリンク・ディレクトリ・SQLiteでないファイル・ほかのプログラムのSQLiteのファイル・新しい版の表のファイルを、変えずに拒むこと）、表の版を上げること（失敗すれば前の版のまま）、接続の設定、表の制約とトリガー、読むトランザクションが書けないことと、その時点、書くトランザクションが1つずつ動くこと、ほかのプロセスに当たるもの（同じファイルを別に開いたもの）が書くロックを持つ間は待って、`database is locked` で失敗すること。
- `internal/store`：正常系と異常系（すべての種類と設定の文書、確かめの順とメッセージ、データのディレクトリの問題、壊れたJSONと原本）。見本のサイト（6.11。`internal/build/testdata/site/`）の文書・リビジョン・原本を保存して、同じバイト列とハッシュで読めること。
- 失敗と強制終了：書き込みの途中（コミットの直前、原本を同期した後と名前を変えた後）に失敗を差し込むテストと、テストの実行ファイルを別のプロセスで動かして、書いている途中で強制終了してから開き直すテスト（SQLiteの `integrity_check`、すべてのオブジェクトのハッシュ、`documents` が `versions` の最後の版と合うこと）。原本のディレクトリの同期は、模擬のファイルシステム（`internal/logdb/simfs`。同期したものだけが、クラッシュの後に残る）で確かめる（強制終了したプロセスがディレクトリを作った後）。同期に失敗した後に、原本の保存が止まること（同時に動いていたものも）も、模擬のファイルシステムで確かめる。
- 同時に使う：同時の読み書き（`-race`）と、ほかのプロセスとの同時の書き込み。
- 確かめていないもの：電源の断（ディスクへの同期）と、WALを使えないファイルシステム。
