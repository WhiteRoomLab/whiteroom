## 3. ストレージ設計

### 3.1 決定済み：SQLite + 専用Content Store

**単一の汎用RDBにすべてを入れる案ではなく、SQLiteとCMS専用Content Storeを併用する。**

- **SQLite**：管理ユーザー・権限・ログイン履歴・アクティビティログなど、整合性・検索・関連性が重要なデータを管理するためのRDBとして採用。
- **CMS専用Content Store**：記事・固定ページなどのコンテンツを扱う独立したストレージ領域／抽象化層として設ける。
- 専用Content Storeを採用することは決定したが、**内部形式を完全自作することまでは決めていない**。

### 3.2 提案段階：専用Content Storeの内部方式

- **Content-addressable Storage（CAS）**：本文・リビジョンなどを内容のハッシュで識別し、原則として不変オブジェクトとして保存。メディアのファイルは、内容のハッシュで保存して指す（案。6.6.2）。
- **ファイルシステム + SQLiteメタデータ**：実体データをファイルに、記事ID・スラッグ・リビジョン・参照先をSQLiteに保持。
- **Append-only / スナップショット**：過去データを上書きせず、特定時点のサイト状態を再現可能にする。
- **ContentStoreインターフェース**：物理保存形式をCMSコアから隠蔽し、将来、独自バイナリ形式や独自インデックス方式への置換を可能にする。
- **媒体別分離**：画像・添付ファイルをファイルシステムに保管する案。

これらは**専用Content Storeの実装候補**であり、CASやAppend-onlyの採用自体は未決定。

### 3.3 未決定：トランザクションと整合性

SQLiteとContent Storeは異なる永続化領域になり得るため、以下の扱いを定義する必要がある。

- オブジェクト書き込み成功／メタデータ更新失敗時の回復
- 未参照オブジェクトの回収（GC）
- リビジョンと公開スナップショットの整合性
- クラッシュ時の復旧・バックアップ・リストア
- DBやデータファイルを壊した際の検出・修復
