## 3. ストレージ設計

### 3.1 決定済み：専用Content Storeと自作の保存の層

**単一の汎用RDBにすべてを入れる案ではなく、CMS専用Content Storeを、自作の保存の層の上に作る。**

- **保存の層**：Goの標準ライブラリだけで作ったエンジン（`internal/logdb`。3.5）。DBのデーモン（`whiteroom-db`。3.6）の中で動く。
- **CMS専用Content Store**：記事・固定ページなどのコンテンツを扱う独立したストレージ領域／抽象化層として設ける（`internal/store`。3.4）。
- **内部形式**は、3.5のエンジンの形（ログ・オブジェクト・チェックポイント）にした（案。形の版の移行は6.12の131）。
- **文書とリビジョンのJSON**は、CAS（内容のSHA-256で指す、書き換えないオブジェクト）に置き、どのIDがどのオブジェクトかは、別の表に持つ（3.4の「表」。別の形式にするかは6.12の1）。CASは、エンジンのオブジェクトにする。
- **メディアの原本**は、中身のSHA-256を名前にしたファイルに置き、本文などからはメディアのIDで参照する（3.4の「原本」・6.6.2。回収は6.12の125）。
- 管理の側のデータ（文書とリビジョンと索引とログインアカウント・セッション（7.3）と、ログイン履歴・アクティビティログ（7.4））は、データのディレクトリの**1つのエンジン**（`logdb/`）に入れる（3.4の「エンジンと設定」。お問い合わせは8章）。
- **外部のモジュール**は使わない（1.2）。
- **保存の層を、別のプロセスにする**：保存の層は、管理のサーバーとは別のプロセス（DBのデーモン）にし、データのディレクトリを開くのは、デーモンだけにする（3.6）。デーモンは、作った（`cmd/whiteroom-db`。issue #109）。
- **エンジンの核**：エンジンは、Goのデーモンに、I/Oを持たないAda/SPARKの核を、cgoで入れる形にする。核の範囲は、「判断に、メモリの状態（表やオブジェクトの索引）が要らないものは、すべて核に入れる」という線で決める（3.6。核は、まだ作っていない。それまで、デーモンの中のエンジンは、Goの標準ライブラリだけで作ったエンジンのまま）。

### 3.2 提案段階：専用Content Storeの内部方式

- **Content-addressable Storage（CAS）**：本文・リビジョンなどを内容のハッシュで識別し、原則として不変オブジェクトとして保存。メディアのファイルは、内容のハッシュで保存して指す（決定済み。3.1・6.6.2）。
- **ファイルシステム + メタデータ**：実体データをファイルに、記事ID・スラッグ・リビジョン・参照先を表に保持。
- **Append-only / スナップショット**：過去データを上書きせず、特定時点のサイト状態を再現可能にする。
- **ContentStoreインターフェース**：物理保存形式をCMSコアから隠蔽し、将来、独自バイナリ形式や独自インデックス方式への置換を可能にする。
- **媒体別分離**：画像・添付ファイルをファイルシステムに保管する案。

これらは**専用Content Storeの実装候補**。文書とリビジョンのCASと、ハッシュを名前にした原本は、採用した（決定済み。3.1）。保存のたびに版を足して、過去の版を残すこと（Append-only）も、採用した（案。3.4の「表」。回収は6.12の125）。

### 3.3 未決定：トランザクションと整合性

保存先のデータ（エンジン）と原本（ファイル）は、異なる永続化領域なので、以下の扱いを定義する必要がある。

- オブジェクト書き込み成功／メタデータ更新失敗時の回復
- 未参照オブジェクトの回収（GC）
- リビジョンと公開スナップショットの整合性
- クラッシュ時の復旧・バックアップ・リストア
- DBやデータファイルを壊した際の検出・修復

3.4の「壊れない書き込み」で仮に決めた（案）。バックアップ（`whiteroom backup`）と、壊れたものの検出（`whiteroom doctor`）と、壊れた保存先の修復（`whiteroom-db repair`。#144。#144 の計画への答え（2026-11-25）で決めた）は、作った（9.4。修復が直さない、監査の鎖の問題は、#147 で作り、失ったオブジェクトと原本を指す行は、#149 に分けた。6.12の290〜293）。残るのは、回収（GC。6.12の125）、バックアップの残りとリストアの道具（6.12の131・258）。

### 3.4 保存先（案）

管理の側の保存先（3.1）を、`internal/store` に作った。`internal/store` はContent Storeで、文書（6.9のJSONの文書）とそのすべての版、エントリーのリビジョン（6.4.1）、メディアの原本（6.6.2）を、データのディレクトリ（下記）に保存して読み（データのディレクトリを開くのは、DBのデーモンだけで、`internal/store` は、ソケットで繋ぐ。3.6）、文書とリビジョンから決まる索引（下記の「索引」）も持つ。ログインアカウントの行とセッションの行（7.3）も、同じエンジンの表（`accounts`・`sessions`）に持つが、値は読まず、`internal/account` が読み書きする（下記の「表」）。ログイン履歴とアクティビティログの記録（7.4）は、エンジンの監査イベントに、鎖をつなぎながら足して持ち、読む口と確かめる口も持つ（下記の「操作」）。保存の層は、3.5のエンジン（`internal/logdb`）の上の自作の層（3.5の「構成」）。3.2のContentStoreインターフェースは、`internal/store` の口（下記の「操作」）にした。使う側は、ビルドの読み込みの口（`build.Source`。4.3）のように、要るものだけの口を持つ。この節の規則は、「決定済み」と書いたもの（3.1・6.1）のほかは、どれも仮に決めたもの（案）。保存の層は、別のプロセス（DBのデーモン）にした（3.6）。この節は、保存先（`internal/store`）の規則と、データのディレクトリの中身で、デーモンの規則とプロトコルは、3.6。メッセージの例は、`/srv/data` がデーモンの側のデータのディレクトリで、`/run/whiteroom-db` が `store` を使う側のソケットのディレクトリのときのもの。

**データのディレクトリ**

保存先は、1つのディレクトリ（データのディレクトリ）に置く。開くのは、DBのデーモンだけ（3.6）。

| 名前 | 内容 |
| --- | --- |
| `logdb/` | エンジンのディレクトリ（下記の「エンジンと設定」）。中のファイルは、3.5の「構成」 |
| `files/` | メディアの原本（下記の「原本」） |
| `files/<16進数2桁>/<16進数64桁>` | 原本。名前は、メディアの `hash`（6.6.2）の `sha256:` の後ろ（小文字の16進数64桁）で、ディレクトリの名前は、その初めの2桁（ディレクトリは、初めて使うときに作る） |
| `files/.tmp-<ランダムな16進数16桁>` | デーモンの一時のファイル：書いている途中の原本（`PutOriginal`。3.6の「原本」）。書き終われば消え、デーモンが途中で止まったときだけ残る。デーモンが、起動のとき（エンジンの書くロックを取った後）に消す。管理のAPI（9.7）の一時のファイルは、ここに置かない（管理のサーバーの `tmp`。9.4） |
| `stopped` | デーモンの印：同期に失敗して止まったときに、デーモン（`serve`・`compact`・`gc`・`accept-break`・`repair -apply`）が残し、止まったときのマシンの起動ごとのID（Linux の boot ID）・時刻・理由を持つ（3.6の「同期の失敗」）。マシンを再起動した後の起動が消す。エンジンの形の版にも、表の版にも入らず、`Backup` は写さない |

規則：

- モード：ディレクトリは0700、ファイルは0600で作る（エンジンのファイルも。3.5の「構成」）。
- 作る：`whiteroom-db init`（`dbserver.CreateDir`）が作る。無いディレクトリ（親も作る）か、空のディレクトリに作る（あるディレクトリのモードは変えない）。作ったディレクトリ（親も）は、外側から順に、その名前を、それを持つディレクトリの同期で、ディスクに置く（3.5の「対象のOSとファイルシステム」の前提。同期できなければ、失敗する：`open /srv: permission denied`）。あったディレクトリの名前は、同期しない。空でなければ、何も変えずに、エラーにする（`/srv/data: not empty; a new data directory needs a missing or empty directory`）。途中で失敗すると、作ったものが残るので、中を空にしてから作り直す。作るのは、`files/` と、コミットの無いエンジンの `logdb/` まで：最初のコミット（表の版と、アクティビティログの最初の記録 `store.create`。7.4）は、書き手として繋ぐ `store.Create`（`whiteroom init`。9.4）が作る。コミットのある保存先に `Create` すると、何も書かずに失敗する（`/run/whiteroom-db: the store is not new; a new store needs a data directory that whiteroom-db init has just made`）。`whiteroom-db serve` は、データのディレクトリを作らない。
- 開く（デーモン。`whiteroom-db serve`）：マシンの起動ごとのID（Linux の boot ID）を読み（読めなければ、何も変えずに失敗する）、ディレクトリ（シンボリックリンクなら、たどる）の中の `logdb` と `files` が、どちらもディレクトリであることを確かめる。どちらも、シンボリックリンクは不可（`/srv/data/logdb: missing directory`、`/srv/data/files: symbolic links are not allowed`、`/srv/data/files: must be a directory`）。それから、`stopped`（同期に失敗した後の印）が、いまのマシンの起動のものか、読めないものなら、何も変えずに断る（`/srv/data: a sync failed at …, and the machine has not restarted since; restart the machine before starting whiteroom-db on this directory again`。前の起動の印は、エンジンが開いた後に消す。3.6の「同期の失敗」）。それから、データのディレクトリそのものに、このユーザーが書けるか（`access(2)`。ファイルは作らない）を確かめ、書けなければ、何も変えずに断る（`/srv/data: whiteroom-db cannot write in the data directory (permission denied); it must be able to leave the mark of a failed sync there: give the directory to the user of the daemon`。印を残せないため。3.6の「同期の失敗」）。それから、エンジンが、`logdb/` の形を確かめ、ロックを取り、状態を作る（3.5の「復旧」と「ほかのプロセス」）。上の表に無いもの（`README` など）は見ない。`store` の `Open` と `OpenReader` は、データのディレクトリを開かず、デーモンのソケットに繋ぐ（下記の「操作」）。
- 外を読まない：デーモンは、`files/` の中からは、`files/` の外を読まない（外を指すシンボリックリンクは、たどらない）。
- 開発者のファイル：スキーマのファイル（6.6.8）とテーマ（5.4）は、データのディレクトリに置かず、開発者のディレクトリ（Gitなどで管理する）に置く。保存先に置くのは、管理画面が書く設定の文書（6.6.8）だけ。これらの場所の渡し方は、コマンド（9.4）の `SITE`・`-theme`（と、設定ファイルの `site`・`theme`）で、仮に決めた。データのディレクトリの場所は、デーモンの `-data`（設定の `data`）だけが受け取り、ほかのコマンドは、デーモンのソケットのディレクトリを、`-db`（設定の `db`）で受け取る（9.4）。

**エンジンと設定**

- 1つのエンジン：管理の側のデータは、データのディレクトリの1つのエンジン（`logdb/`）に入れる（決定済み。3.1）。お問い合わせ（8章）は、作るときに、別の保存先にする。
- 設定：デーモン（`whiteroom-db serve`・`init`・`compact`・`gc`・`check`・`accept-break`・`repair`）は、次の設定でエンジンを使う（変えるフラグは無い。デーモンの上限の設定は、3.6の「上限」）。

| 設定 | 値 |
| --- | --- |
| オブジェクトの置き場所 | 混合：64KiB（65536バイト）以上のオブジェクト（文書とリビジョンのJSON）は、ファイル（`logdb/objects/`）に、ほかはログのレコードに入れる（3.5の「オブジェクトの置き場所」。6.12の137） |
| セグメントの大きさ | 64MiB（3.5の「コミット」） |
| チェックポイント | ログが64MiB増えるたびに、バックグラウンドで書く。閉じるときにも書く（3.5の「チェックポイント」。6.12の132） |
| 書くロックを待つ時間 | 2秒（デーモンが開くときと、保守が、ほかのプロセスを待つ。3.5の「ロック」。6.12の135） |

- 設定はファイルに残らない：置き場所は、新しいオブジェクトだけに効き、あるオブジェクトは、その置き場所のまま（圧縮でも）。そのため、設定を変えても、移すものは無い。
- 表の版：表の版（`meta` の `schema`。いまは10。下記の「表」）は、エンジンの形の版（3.5の「ファイルの形」。いまは1）と、文書の `schemaVersion`（6.9）とは別に数える。表を変えるときは、表の版を上げ、一度出した版の表は、書き換えない（その版で書いたファイルを、後の版でも読むため）。版1は、索引（下記の「索引」）が無い表（#43 の前）、版2は、索引はあるが、予約（役割 `scheduled` と、エントリーの要約の `scheduledRevision`・`scheduledAt`）が無い表（#44 の前）、版3は、ログインアカウントの表（`accounts`）が無い表（#45 の前）、版4は、セッションの表（`sessions`）が無い表（#46 の前）、版5は、監査の記録（7.4）の鎖の頭（`meta` の `loginLog`・`activityLog`）が無い表（#47 の前）、版6は、書き出し用の表 `heads`（下記の「表」）が無く、デーモンの印（3.6の「印」）も無い表（#109 の前）、版7は、表 `chains`（下記の「表」）と、デーモンのイベント 0x02・0x03（3.6の「印」）が無い表（#70 の前）、版8は、表 `chains` の穴の行と、デーモンのイベント 0x04 が無い表（#144 の前）、版9は、表 `chains` の認めた飛びの行と、デーモンのイベント 0x05 が無い表（#147 の前）で、版1〜版9の保存先は、書き手として繋いだ `store.Open` が、版10にする（版1は索引も作り、版2〜版9は表の版の行と、更新の記録（`store.upgrade`）と、その鎖の頭と、頭の行だけを書く。下記の「索引」の「表の版の更新」）。版9が、版8に足したのは、穴の行と、イベント 0x04 だけで、版10が、版9に足したのは、認めた飛びの行と、イベント 0x05 だけで、前の版の行も、イベントも、書き換えない（#144 の計画への答え（2026-11-25）と、#147 の計画への答え（2026-11-25）で決めた）。書き手が繋ぐ前の保存先に、`whiteroom-db repair` が穴の行を書くときは、表の版の行を、8か9から10にする（更新の記録は足さない。データは移さない。3.6の「保守の口」）。
- 開くときの確かめ：表の版は、2か所で確かめる。デーモンが、起動のとき（エンジンが状態を作った後、ファイルを変える前）：コミットがあるのに版の行が無ければ `/srv/data/logdb: not a store of whiteroom (no schema version)`、行が正しくなければ `/srv/data/logdb: meta "schema": invalid value`、行が、デーモンの知る版（`dbwire.TableVersion`）より新しければ `/srv/data/logdb: the store schema is of version 11, newer than this program knows (10)`。拒んだときは、ファイルを何も変えず、デーモンは始まらない。クライアント（`store.Open`・`OpenReader`）が、繋いだとき：`/run/whiteroom-db: not a store of whiteroom (no schema version)`（`store.ErrNoStore`。`whiteroom-db init` の直後の、書き手がまだ最初のコミットを作っていない保存先）、`/run/whiteroom-db: the store schema is of version 11, newer than this program knows (10)`。形の版の新しいファイルも、何も変えずに拒む（3.5の「ファイルの形」）。
- ローカルのファイルシステム：エンジンは、`flock(2)` のロックと、ファイルとディレクトリの同期を使う（3.5の「対象のOSとファイルシステム」）。データのディレクトリは、Linuxのローカルのファイルシステムに置く（NFSなどのネットワークのファイルシステムは、対象の外）。デーモンは、Linuxだけで動く（3.6の「実行ファイル」。6.12の283）。
- 版を上げるとき：プログラムを新しい版に替えるときは、デーモンと、それに繋ぐプロセス（管理のサーバー・コマンド）を、先に止め、2つの実行ファイルを、同じリリースで一緒に入れ替える（3.6の「実行ファイル」）。古い版のデーモンは、新しい版の表と形のファイルを、起動のときに、何も変えずに拒み、古い版のクライアントは、繋いだときに拒む（表の版を上げる更新（1から2、2から3、3から4、4から5、5から6、6から7、7から8、8から9、9から10）の後は、前の版しか知らないプログラムは、開けない）。

| `chains`（12） | 監査の記録の鎖の始まりと、認めた切れ目と、穴と、認めた飛び（7.4の「改ざんの検知」）。書くのは、デーモンの保守だけ（3.6の「保守の口」） | 鎖の始まり：ログの名前（`login`。`dbwire.LogLogin`）。認めた切れ目：ログの名前・0x00・記録の番号（8バイト、ビッグエンディアン。`dbwire.ChainBreakKey`）。穴：ログの名前・0x01・失った最初の記録の番号（8バイト、ビッグエンディアン。`dbwire.ChainHoleKey`）。認めた飛び（案。#147 の計画への答え（2026-11-25）で決めた）：ログの名前・0x02・飛びの最初の記録の番号（8バイト、ビッグエンディアン。`dbwire.ChainGapKey`。この 0x02 は、キーの種類の1バイトで、デーモンのイベント 0x02（削除）とは別） | 鎖の始まり（52バイト。`dbwire.ChainStart`）：残る最初の記録の番号（8バイト、ビッグエンディアン。2以上）・その1つ前の記録の、保存したバイト列のSHA-256（32バイト）・書いた時刻（1970-01-01T00:00:00Z からの秒8バイトと、秒の下のナノ秒4バイト）。認めた切れ目（44バイト。`dbwire.ChainBreak`）：その番号の記録の、保存したバイト列のSHA-256（32バイト）・認めた時刻（秒8バイトと、ナノ秒4バイト）。穴（52バイト。`dbwire.ChainHole`。案。#144 の計画への答え（2026-11-25）で決めた）：失った最後の記録の番号（8バイト、ビッグエンディアン）・その記録の、保存したバイト列のSHA-256（32バイト。穴の次の記録の `prev` が指すハッシュで、ログの終わりの穴は、表 `meta` の頭のハッシュ）・記した時刻（秒8バイトと、ナノ秒4バイト）。認めた飛びの値は、穴の値と同じ（52バイト。`dbwire.ChainHole`）：飛びの最後の記録の番号（終わりの飛びは、頭の番号）・記録の、保存したバイト列のSHA-256（飛びの次の記録の `prev` が指すハッシュで、終わりの飛びは、頭のハッシュ）・認めた時刻。穴と認めた飛びの値は、鎖の始まりの値と同じ大きさ（52バイト）で、値では区別できず、キーが区別する。表の版7以下の保存先には、この表の行が無く、表の版8以下の保存先には、穴の行が、表の版9以下の保存先には、認めた飛びの行が、無い（版10にしても、書き手は、行を書かない） |

規則：

- オブジェクト：文書とリビジョンのJSONは、エンジンのオブジェクト（3.5の「オブジェクトの置き場所」）。内容のハッシュ（SHA-256。`sha256:` と小文字の16進数64桁）で指し、同じ内容は1つだけ持つ（3.2のCAS。決定済み。3.1）。
- 値：版は、番号（uvarint）と、JSONのSHA-256（消した印は0バイト）・保存した日時・保存した人（それぞれ、長さ（uvarint）の後に）。リビジョンは、番号（uvarint）、エントリーのID（長さの後に）、JSONのSHA-256（32バイト）、保存した日時と保存した人（それぞれ、長さの後に）。
- 番号：版とリビジョンの番号は、`meta` の最後の番号に1を足したもの。取り消した `Update` の番号は、次の `Update` が使う。
- 足すだけ：`history`・`revisions`・`entryRevisions` には、キーを足すだけで、書き換えて消す口は、保存の層に無い。オブジェクトは、書き換えられない（エンジンのCAS）。
- 保守だけが書く表（案。#70 の計画への答え（2026-11-23）で決めた）：`chains`（12）の行は、書き手が、足さず、書き換えず、消さない（デーモンが、`rule` で断る。3.6の「デーモンが守る規則」）。書くのは、デーモンの保守（`whiteroom-db compact`・`accept-break`・`repair`。3.6の「保守の口」）だけ。足すだけの表ではない：鎖の始まりの行は、次の削除が、置き換える。穴の行は、修復が足し、置き換えるのは、ログの終わりで、頭の番号で終わり、頭と別のハッシュを持つ穴の行だけ。認めた飛びの行は、`accept-break` が足し、置き換えるのは、飛びの最後が同じで、ハッシュが合わない飛びの行（もう1度認めるとき）だけ（穴の行は、置き換えず、同じ `first` の飛びの行を、別のキーに足す）（案。#147 のレビューへの答え（2026-11-25）で決めた）。認めた飛びは、ほかの行にかぶさらない（かぶさる飛びは、認めない）。修復の穴は、失った記録の範囲に、前からある穴の行か認めた飛びの行が入るときも、その行を含めて、1つの穴で覆い、その行は、置き換えず、そのまま残す（案。#147 のレビューへの答え（2026-11-25）で決めた）。
- いまの版：`documents` の値は、同じ文書の最後の版の写しで、消した印にはならない（消したときは、キーを消す）。読むときに、消した印なら、壊れているとする（`documents "…": invalid value`）。
- 壊れた値：読めない値と、無いオブジェクトやリビジョンを指す値は、表とキーを付けたエラーにする（`meta "versions": invalid value` など）。無いことの分かるエラー（`fs.ErrNotExist`）にはしない（壊れたものを、無い文書とみなさないため）。
- 前の版を残す：どの種類の文書も、保存のたびに版を足し、前の版を残す。消しても、それまでの版は残る（回収は、まだ無い。下記の「まだ無いもの」）。前と同じ内容の版は、同じオブジェクトを指す。
- 保存した日時：UTCのRFC 3339で、秒の下を9桁にそろえて書く（`2026-11-03T08:00:00.120000000Z`。文字列の順が、時刻の順になるように）。1回の `Update`（下記の「操作」）で保存した版とリビジョンは、どれも同じ日時（そのトランザクションを始めたときの時刻）になる。
- 種類：文書の種類は、ビルドの読み込みの口（4.3）の7つ（`entry`・`term`・`media`・`author`・`menu`・`form`・`redirect`）と、設定の文書の `settings`。設定の文書は、1つだけで、IDを空にして持つ。
- アカウントの行とセッションの行（案。7.3）：キーは、アカウントの行がアカウントのID（`usr_` とULID）、セッションの行がトークンの文字列のSHA-256（小文字の16進数64桁。保存先はトークンを見ない）。値は `internal/account` が書くJSONで、保存先は読まない。保存先は、トランザクション、キー（`invalid user ID "usr_x": use "usr_" and a ULID (26 characters in upper case)`・`invalid session key "<キー>": use 64 lower case hexadecimal digits`）、大きさ（`accounts "usr_…": empty value`・`sessions "<キー>": too large: 4097 bytes (max 4096)`。アカウントの行は1〜65536バイト、セッションの行は1〜4096バイト）を、この順に確かめ、消すときは、その行があること（`accounts "usr_…": not found`。`fs.ErrNotExist` を包む）も確かめる。行は、キーの順に返す。キーの形でない行が表にあれば、`Accounts`・`Sessions` が `accounts "x": invalid key` で失敗する（保存先のAPIを通さずに書かれた場合だけ）。索引には入れず、`RebuildIndex` は読みも書きもしない。表の版によらず読み書きできる（表の版1の読み手も、`ErrNoIndex` にならない）。行どうしの規則（ログイン名とメールアドレスの一意、アカウントのセッションの数）は、`internal/account` が、書く `Update` の中で、すべての行を読んで確かめる（`Update` は1つずつ動く）。
- 監査の記録（案。7.4）：表ではなく、エンジンの監査イベント（3.5の「イベント・操作のID・暗号化の封筒」）に置く。ログイン履歴とアクティビティログの記録を、`Record` で、同じ `Update` に足し、そのログの鎖の頭を、`meta` と、`heads`（頭の行。デーモンが書き出す）に置く。デーモンは、コミットごとに、自分のイベント（印。3.6の「印」）を足すので、記録のイベントの間に、印がある：記録を読む口と確かめる口は、印を飛ばす（イベントの番号は、印も数える。7.4の「番号と時刻と鎖」）。メモリに持つのは、イベントの数だけで、記録は、ログから読む（`ReadAudit`）。保存先自身も、作るときと表の版を上げるときに、記録を足す（`store.create`・`store.upgrade`）。表の版5以下の保存先には、記録も鎖の頭も無く（`ErrNoAuditLog`）、表の版6の保存先には、記録と鎖の頭はあり、頭の行（`heads`）が無い。ログイン履歴の古い記録を消した後の鎖の始まりと、認めた鎖の切れ目は、表 `chains`（12）に置く（7.4の「改ざんの検知」）。表の版7以下の保存先は、この表の行を持たず、読んでも、行が無いだけで、失敗しない。

**索引**

索引は、いまある文書とエントリーのリビジョンから決まる表（`summaries`・`references`）で、正本ではない（案）。ビルドと同じ検証（6.7）が読む項目と、どの文書がどのIDを参照しているかを、保存先のすべての文書を読まずに引くためにある。保存の操作（6.7）は、サイト全体の模型を、ここから作る。エンジンの中の索引（ハッシュからオブジェクトの位置を引くもの。3.5の「構成」）とは別のもの。

- 更新：`Put`・`Delete`・`AddRevision` は、確かめた後に、同じ `Update` の中で、索引を更新する（文書と索引は、同じコミット。下記の「壊れない書き込み」）。`RebuildIndex` は、文書とリビジョンだけから、`summaries` と `references` の行を作り直す（`Put`・`Delete`・`AddRevision` が作ったはずの行と比べて、無い行と値の違う行を書き、余る行を消す。正しい索引には、何も書かない。行の無い表（表の版の更新）には、すべての行を書く）。操作のIDの記録（`operations`）は、そのまま残す。索引の行は、文書の更新に合わせて、書き換え・削除する（`history` などと違い、足すだけではない）。保存した索引は、いつも、`RebuildIndex` が作るものと同じ。
- 要約：いまある文書ごとに1行で、次の項目だけを持つ（どれも、スキーマのファイルとテーマに依らない値）。
  - エントリー：状態のすべての項目（6.4.1。予約の `scheduledRevision`・`scheduledAt` も）。公開中のリビジョン（`publishedRevision` が指すもの。`status` は見ない）の `slug`・`parent`・`date`・`author`・`sticky`・`terms`（そのリビジョンが保存先にあり、読めるときだけ。どのエントリーのリビジョンでもよい）。最後のリビジョンのID（無ければ空）。
  - ターム：`id`・`taxonomy`・`language`・`translationGroup`・`slug`・`parent`。メディア：`id`・`hash`・`mimeType`。著者プロフィール：`id`・`slug`。メニュー：`id`・`language`・`location`。フォーム：`id`。リダイレクト：`id`・`from`・`to`・`status`。
  - 設定の文書：行はあるが、項目は無い。
  - このプログラムの読み込み（6.7）で読めない文書（後のプログラムが書いたものなど）には、要約が無い（そのために、`Put`・`Delete`・`AddRevision`・`RebuildIndex`・表の版の更新は、失敗しない）。
- 参照：文書のJSONと、エントリーの公開中のリビジョンと予約したリビジョンと最後のリビジョンのJSONにある、エントリー・ターム・メディア・著者プロフィール・フォームのIDを、参照として数える。数えるのは、JSONの文字列の値で、入れ子の深さによらず、カスタムフィールドと本文のテキストの中のものも数える（オブジェクトのキーは数えない。JSONのエスケープで書いたものは、戻した値で数える。6.12の152）。自分のIDは数えない（リビジョンは、そのエントリーのID）。リビジョン・翻訳グループ・ユーザー・メニュー・リダイレクトのIDは、参照としては数えない（メニューとリダイレクトは、参照されない）。`html`・`legacy` のHTMLの中のURLも、数えない（6.12の115）。役割は、`document`（文書のJSON。エントリーの状態と設定の文書も）、`published`（エントリーの公開中のリビジョンのJSON）、`scheduled`（エントリーの予約したリビジョンのJSON）、`latest`（エントリーの最後のリビジョンのJSON）。公開中の（または予約した）リビジョンが最後のリビジョンでもあるエントリーは、同じIDを、2つの役割で持つ（6.12の160）。公開中や予約したリビジョンが、保存先に無いか、読めないときは、その役割の参照を数えない。ほかに、内部の役割 `publishes` で、エントリーの `publishedRevision` と `scheduledRevision`（リビジョンのIDの形のもの）を持ち、`AddRevision` が、足すリビジョンを公開中または予約したものとして持つエントリーを見つけるのに使う（`Referrers` は返さない）。
- 番号：`meta` の `numbers` は、エントリーが持ったことのある最大の `number`（6.4.1）。エントリーの `Put` が上げ、`Delete` は下げない（消したエントリーの番号を、使い回さないため）。`RebuildIndex` と、表の版1の更新は、いまあるエントリーの最大まで上げる。そのため、表の版1から更新した保存先は、更新の前に消したエントリーの番号を覚えていない（6.12の155）。
- 操作のID：`operations` は、保存の操作（6.7の「保存の操作（案）」）が、操作のIDごとに、要求のハッシュと結果と書いた時刻（`at`）を記録する表。ほかから作れない記録なので、`RebuildIndex` は変えない。保存先は、データの中身を読まず、IDの長さ（1〜256バイト。`invalid operation ID: it is empty`・`invalid operation ID: it has 257 bytes (max 256)`）だけを確かめる。`PutOperation` は、あるデータを置き換える。ほかの書き込みと同じ `Update` で書くので、`Update` が失敗すれば、何も残らない。記録は24時間残す：保存の操作が、`Operations` で読んで、24時間以上たったものを `DeleteOperation` で消す（保存先自身は消さない。消し方と、`operations.expire` の記録は6.7・7.4）。値に `at` を足しても、表の版は6のまま：保存先は値を読まず、前の版のプログラムは、知らない `at` を読み飛ばし、新しいプログラムは、`at` の無い記録を古いものとして消す（理由は9.7の「再送」）。
- 読み：`Summary`・`Summaries`・`Referrers`・`LastNumber` は、トランザクション・種類・IDを、`Document` と同じ順に確かめ、それから、索引があるかを確かめて、読む。`Update` の中では、その `Update` の書き込みが見える。索引の作らない行は、読み飛ばさずに、エラーにする。要約の行が読めないとき（その種類のものでない項目を持つ行も）は、`summaries "…": invalid value`（上記の「壊れた値」と同じ形）で失敗し、その文書の `Put`・`Delete` も、`RebuildIndex` するまで失敗する。要約のキーのIDが、その種類のIDでなければ、`Summaries` が `summaries "…": invalid key` で失敗する。参照のキーの、参照元の種類・ID・役割と参照先が合わなければ（`published`・`latest`・`publishes` はエントリーだけが持ち、`publishes` の参照先はリビジョンだけ）、`Referrers` と、そのリビジョンを足す `AddRevision` が、`references "…": invalid key` で失敗する。`Operation`・`PutOperation` は、索引の有無によらず動く。
- 表の版の更新：表の版1〜9の保存先に、書き手として繋ぐ（`Open`）と、1回の `Update` で（デーモンへの1回の `Commit`）、表の版を10にし、更新の記録（アクティビティログの `store.upgrade`。`detail` に、更新の前の版 `from` と、後の版 `to`。7.4）と、その鎖の頭と、頭の行（`heads`）を書く（データは移さない）。版1の保存先には、索引の行が無いので、同じ `Update` で、`RebuildIndex` が、すべての行を書く。版2〜版9の保存先の索引は、版10のプログラムが作る行と同じ（版2のプログラムは、予約の項目を持つエントリーを保存できなかった。版4〜版10が足したのは、索引の外の表と記録）なので、版2〜版9の更新は、表の版の行と、更新の記録と鎖の頭と頭の行だけを書き、文書・リビジョン・オブジェクトを読まない。`RebuildIndex` は、すべての文書を読んでハッシュを確かめるので、壊れた文書のオブジェクトがあると、版1の保存先の更新は、直すまで失敗する。版2〜版9の保存先では、壊れたオブジェクトがあっても、更新も `Open` も失敗せず、その文書を読む操作だけが失敗する（下記の「壊れない書き込み」の「読むたびに確かめる」）。また、更新は、版2〜版9の保存先の索引が食い違っていても、直さない（直すのは `RebuildIndex`）。版2の保存先には、`status` が `scheduled` で、予約の2つの項目（`scheduledRevision`・`scheduledAt`）の無いエントリーが入っていることがある（版2のプログラムは、取り込みも保存先のAPIも、予約の項目を知らないまま `scheduled` を受け付けた）。更新は、これを変えず、エントリーの文書は検証し直さない。版3以降のプログラムでは、予約の一覧（`Schedules`）が、日時を零にして先頭に並べ、その予約の日時の公開は、文書の問題（`entries/ent_….json:1:1: /scheduledAt: missing scheduledAt of a scheduled entry`。6.7）で毎回失敗して、公開の仕組みの `Status` に出る（4.4）。公開をやめる（`Unpublish`）かアーカイブすると、予約でなくなる。失敗すれば、元の版のままで、`Open` は、`/run/whiteroom-db: cannot upgrade the table schema to 10: …`（`…` は理由）で失敗する（版2〜版9では、更新のコミットへの書き込みが失敗したときが、これに当たる。次の `Open` が、改めて更新する）。理由が、コミットの答えが来なかったこと（`it is not known whether the commit was made`。3.6の「1回の保存の流れ」）のときだけは、更新が確定していることがある：次の `Open` が、版を見て、決める。更新の要らない保存先は、`Open` でも何も書かない（2回目の `Open` は、`head` のほかのファイルを変えない）。読み手として開いた（`OpenReader`）版1の保存先は、文書・リビジョン・原本・操作のIDを読めるが、索引の読み（`Summary`・`Summaries`・`Referrers`・`LastNumber`）は、`ErrNoIndex`（`the store has the table schema 1, which has no index; open it as its writer once to build it`）で失敗する。版2〜版9の保存先は、読み手でも、索引を読める（版3の保存先には、アカウントの行が無く、版3と版4の保存先には、セッションの行が無い。どちらの行も、索引によらず読めるので、行が無いと返す）。版5以下の保存先には、監査の記録が無く、読み手でも、記録を読む口・鎖の頭を返す口・確かめる口は、`ErrNoAuditLog`（`the store has a table schema before 6, which has no audit log; open it as its writer once to upgrade it`）で失敗する（7.4）。版11以上は、いまどおり、何も変えずに拒む。版1の更新は、索引のすべての行を1つのレコードに書くので、1回の `Update` の上限（下記の「上限」）が、更新できる大きさを決める（参照を持つエントリーの行は、1件で約2KBなので、約10万件まで。6.12の136）。版2〜版9の更新は、表の版の行と1件の記録と頭の行だけなので、この上限に当たらない。
- 行の形：`summaries` の値のJSONは、文書の `schemaVersion`（6.9）つきの、上記の項目だけの書き出しと、参照するIDの一覧（役割ごとに、IDの順で、重複なし）を持つ。そのため、語彙の版（6.9）か、要約の項目を変えるときは、表の版を上げ、索引を作り直す更新を足す（それまでに書いた行は、新しい項目が空で読まれるか、`invalid value` で失敗する。6.12の131）。

**操作**

保存先の口（`internal/store`）の操作：

| 操作 | 内容 |
| --- | --- |
| `Create`・`Open`・`Close` | `Create(ctx, d)`：`whiteroom-db init` が作った（上記）、コミットの無い保存先に、書き手として繋ぎ、最初のコミットを作る。`Open(ctx, d)`：書き手として繋ぎ、表の版を確かめ、古ければ更新する（上記の「索引」）。読み手は、`OpenReader(ctx, d)`。`Close`：繋ぎを閉じる。`ctx` は、開く間（繋ぐ・`Hello`・版の確かめ・更新か作成）だけを区切り、開いた保存先は、それに依らない（答えないデーモンを待つコマンドを、止める合図で終えるため）。`d` は、デーモンへの繋ぎ方（`dbclient.Dialer`。ソケットのディレクトリは `dbclient.SocketDir`）で、データのディレクトリは開かない。デーモンに届かないときは、2秒まで繋ぎ直し（3.6の「接続」）、それでも届かなければ、`store.ErrUnavailable`（`cannot reach the daemon`）を包むエラーで失敗する。デーモンが止まって、また動けば、開いた保存先は、`Open` し直さずに、また動く |
| `OpenReader` | ほかのプロセスから、読み手として繋ぐ（読み手用のソケット。下記の「同時に使う」）。`Update` は `read-only transaction`、`PutOriginal` は `the store is opened to read only` で失敗する |
| `View` | 読むトランザクションで、渡した関数を動かす。関数が初めに読んだときの時点の保存先を見る（その後のコミットは見えない）。書く操作は、エラーにする（`read-only transaction`） |
| `Update` | 書くトランザクションで、渡した関数を動かし、関数が成功すれば、コミットする。関数がエラーを返したとき（パニックと取り消しも）は、書いたものを何も残さない。関数が成功しても、記録（7.4）のほかに何かを書き、記録を1件も足していないときは、何もコミットせずに、`ErrUnrecorded` で失敗する（下記の「書くときの確かめ」） |
| `Document`・`Documents` | 文書のいまの版とJSON。1つの文書（種類とIDで指す）か、1つの種類のすべて（IDの順）。無い文書は、無いことの分かるエラー（Goの `fs.ErrNotExist`。`entries/ent_….json: not found`）。`Documents` は、行を読んでから、オブジェクトを、256件ずつ、まとめて頼む（窓。3.6の「プロトコル」）。壊れたものがあれば、IDの順で、最初の問題を返す |
| `History` | 1つの文書のすべての版（消した印も）を、保存した順に（JSONは含めない） |
| `Object` | ハッシュで指した、版かリビジョンのJSON |
| `Put` | 文書を保存する（下記の「書くときの確かめ」）。いまの版と同じバイト列なら、いまの版を返し、何も足さない |
| `Delete` | 文書を消す（消した印の版を足す）。無い文書はエラー。設定の文書は消せない（`the settings document cannot be deleted`） |
| `AddRevision` | エントリーにリビジョンを足す（下記の「リビジョン」） |
| `Revision`・`Revisions` | 1つのリビジョンとJSON。1つのエントリーのすべてのリビジョンを、保存した順に（JSONは含めない）。`Revisions` は、リビジョンの行を、256件ずつ、まとめて頼む（窓） |
| `Summary`・`Summaries` | 文書の要約（上記の「索引」）。1つの文書（種類とIDで指す）か、1つの種類のすべて（IDの順）。無い文書は、無いことの分かるエラー（`entries/ent_….json: not found`） |
| `Referrers` | IDを参照している、いまある文書を、参照元の種類・ID・役割の順に。消した文書のIDにも使え、残っている文書の参照を返す（消す前の確かめのため。6.7）。設定の文書・メニュー・リダイレクトは、参照されない（空） |
| `LastNumber` | エントリーが持ったことのある最大の `number`（上記の「索引」） |
| `ReadAhead` | `Summary`・`Document`・`Revision` が、これから読むものを、先に、まとめて読む（`Tx.ReadAhead(Ahead{Summaries, Documents, Revisions})`。`Summaries` と `Documents` は、種類とIDで指す名前（`DocumentID`。設定の文書のIDは空）、`Revisions` はリビジョンのID）。行と、そこにある版とリビジョンのデータを、デーモンに、窓（256個ずつ。3.6の「プロトコル」）で頼み、トランザクションが持つ（`Summaries` があるときは、`Summary` が先に読む `meta` の `schema` の行も）。結果もエラーも変えない：その後の `Summary`・`Document`・`Revision` は、先読みが無いときと同じ結果とエラーを返し、デーモンには頼まない。無い名前は、無い行として持つ。デーモンが断った読みと、無いオブジェクトは、持たず、その呼び出しが、読み直して答える。前の `ReadAhead` が読み、まだ取られていないデータは、捨てる（呼ぶ側は、数百件ずつ呼び、次の前に読む）。トランザクションが持つのは、64MiBまで（3.6の「1回の保存の流れ」）。`View` でも `Update` でも動く（`Update` では、書いたものが先）。エラーは、デーモンへの繋ぎの失敗・取り消し・終わったトランザクションだけ。保存の操作（`internal/edit`）が、参照元の検証と、サイト全体の検証で使う（参照元と検証を、256件ずつ） |
| `RebuildIndex` | 索引を、文書とリビジョンから作り直す（書くトランザクション）。文書を256件ずつ扱い、そのエントリーのリビジョンと、比べる索引の行を、まとめて頼む（`Check` の `index` と同じ。窓。3.6の「プロトコル」） |
| `Operation`・`PutOperation` | 操作のIDのデータを読む（無ければ、無いと返す）・置く（上記の「索引」。`PutOperation` は書くトランザクション） |
| `Operations`・`DeleteOperation` | 操作のIDのデータを、IDの順に、すべて読む（データは写し。関数が `false` を返すまで。読む間に `DeleteOperation` を呼んでよく、読みは始めたときの状態を見る。`View` でも動く。操作のIDの形でないキーがあれば失敗する）・消す（無ければ何もしない。書くトランザクション。消したら、記録が要る。`ErrUnrecorded`） |
| `Account`・`Accounts` | アカウントの行のデータ（上記の「表」。7.3）。1つ（アカウントのIDで指す。無ければ、無いと返し、エラーにはしない）か、すべて（IDの順）。索引の有無によらず読める |
| `PutAccount`・`DeleteAccount` | アカウントの行を置く（あれば置き換える。1〜65536バイト）・消す（無ければ、無いことの分かるエラー）。どちらも書くトランザクション |
| `Session`・`Sessions` | セッションの行のデータ（上記の「表」。7.3）。1つ（トークンのSHA-256のキーで指す。無ければ、無いと返し、エラーにはしない）か、すべて（キーの順）。索引の有無によらず読める |
| `PutSession`・`DeleteSession` | セッションの行を置く（あれば置き換える。1〜4096バイト）・消す（無ければ、無いことの分かるエラー）。どちらも書くトランザクション |
| `Record` | 同じ `Update` のコミットに、監査の記録（ログイン履歴かアクティビティログ。7.4）を1件足す。番号・前の記録のハッシュ・時刻は、保存先が付ける。書くトランザクションだけ |
| `Changed` | そのトランザクションが、記録（と鎖の頭）のほかに、何かを書いたか。同じバイト列の `Put` のように、何も書かなかったものは数えない |
| `ReadAudit` | 記録を、古い順に、絞り込み（ログ・期間・アカウント・操作・対象）に合うものだけ、関数が `false` を返すまで渡す。読み手として開いた保存先でも読める（7.4の「読む口と費用」）。表の版5以下の保存先は、`ErrNoAuditLog` |
| `AuditHeads` | ログごとの鎖の頭（最後の記録の番号とハッシュ）。記録のあるログだけ |
| `VerifyAudit`・`VerifyAuditNotes` | 鎖を、ログの初めの記録（ログイン履歴は、古い記録を消した後は、表 `chains` の鎖の始まりの記録）から、たどり直し、表の頭と、呼ぶ側が渡す、外に書き出した頭と照らす（7.4の「改ざんの検知」）。`VerifyAuditNotes` は、同じ確かめで、問題ではないこと（消した記録・認めた切れ目・修復が落とした記録の穴・認めた飛び・照らせなかった頭）を、渡した関数に、1つずつ文で渡す。`VerifyAudit` は、それを渡さない形。表 `chains` は、表の版によらず読む（版7以下の保存先には、行が無く、版8以下の保存先には、穴の行が、版9以下の保存先には、認めた飛びの行が、無い） |
| `Check` | 保存先の問題を、1つずつ、渡した関数に渡す（`Problem{Area, Target, Detail}`。`String()` は1行で、`<領域>: <対象>: <理由>`。理由に、行の値は入らない。関数が `false` を返すと止まる）。何も書かず、記録を足さず、直さない。書き手として開いた保存先でも、読み手として開いた保存先でも動く（読み手が、書き手の書いている間に動かしても、正しい保存先に問題を示さない）。見る領域は、この順：`engine`（エンジンの確かめ `Verify`。3.5。最初の問題だけを示す：続けられなければ、問題は1つ。すべての問題は、`whiteroom-db check` が示す。3.6の「保守の口」）、`index`（索引の行が、文書とリビジョンから作る行と同じか。上記の「索引」。操作のID・アカウント・セッションの表は、見ない。文書を256件ずつ扱い、そのエントリーのリビジョンと、比べる索引の行を、窓でまとめて頼む。見つける問題とその順は、1件ずつ読むときと同じ）、`history`（案。#70 の計画への答え（2026-11-23）で決めた。`documents` の行が、その文書の履歴の最後の版と同じか（版の番号と値。行が無い・履歴が消した印で終わるのに行がある・履歴の無い行も、問題）、履歴の、消した印でないすべての版と、すべてのリビジョン（最後と公開中のものだけではない）が指すオブジェクトが、あり、ハッシュと合うか（ハッシュごとに1回。256件ずつ、窓でまとめて頼む）、`entryRevisions` と `revisions` が、両方向で合うか（挙げたリビジョンが無い・別のエントリーのもの・どの行にも挙げられていないリビジョン）。いまの文書と、最後と公開中のリビジョンのオブジェクトは、`index` と `history` の両方が読むので、1つの原因が、2行になることがある。読めない行は、表とキーで示し（値は示さない）、順は、`documents` の行（種類・ID・版の順）、`entryRevisions`、挙げられないリビジョン、オブジェクト（版、リビジョンの順）。費用のかかるオブジェクトの読みを、最後にするので、関数が `false` を返せば、読まずに止まる）、`original`（メディアの文書が指す原本を、ハッシュごとに1回、最後まで読み、ハッシュと合うか。いまの文書が指すものと、メディアの文書の前の版だけが指すものの、両方。後者は、問題の文に、`only of earlier versions: media <ID> version <番号>` を添える）。エラーは、`ctx` のものと、デーモンに届かないこと（`store.ErrUnavailable`。確かめを動かせなかったので、問題としては渡さない）だけ。エンジンの確かめ（デーモンの `Verify`。3.6の「保守の口」）の間は、どちらで呼んでも、デーモンの `Commit` は待つ（読みは続く）。待つ長さと、`Check` の長さは、3.6の「測った値」。コマンドは、9.4の「`whiteroom doctor`」 |
| `Backup`（関数。`Store` のメソッドではない） | `Backup(ctx, d, dstDir)`：デーモンのデータのディレクトリの写しを、`dstDir`（無いか、空のディレクトリ。無ければ、親も作り、作った名前を同期する）に、読み手として作る：デーモンが始めたときの、最後の永続的なコミットまでの `logdb/` と、そのコミットの原本を含む `files/`（3.6の「保守の口」）。ファイルと、作ったディレクトリは、同期する。返すのは、写しの鎖の頭（`audit.Head`）。表の版が7より前の保存先は、何も写さずに断る（`the store has a table schema before 7, which has no rows of the heads; open it as its writer once to upgrade it`）。保存先がまだ無いデータのディレクトリ（版の行が無い）も、何も写さずに断る（`store.ErrNoStore`。`Open` と同じ文）。`dstDir` が空でなければ、断る（`<dstDir>: not empty; a new data directory needs a missing or empty directory`）。失敗したら、`dstDir` を空にしてから、やり直す。写しは、元と同じ形で、表の版も、エンジンの形の版も、そのまま（上記の「表の版」のとおり、同じ版か、後の版のプログラムで開ける）。コマンドは、9.4の「`whiteroom backup`」 |
| `PutOriginal`・`OpenOriginal` | 原本を保存する・開く（下記の「原本」）。トランザクションの外で使う |

**書くときの確かめ**

`Put` は、次の順に確かめ、最初の問題をエラーにする（そのときは、何も書かない）。

1. トランザクション：書けるトランザクションか（上記の「操作」）。
2. 種類：上記の「表」の8つのどれか（`unsupported kind "page"`）。
3. ID：その種類のID（6.7。`invalid entry ID "ent_x": use "ent_" and a ULID (26 characters in upper case)`）。設定の文書には、IDを渡さない（`the settings document has no ID`）。
4. 保存した人：ログインアカウント（7.3）のIDの書式（`invalid user ID "usr_x": use "usr_" and a ULID (26 characters in upper case)`）。アカウントは、表 `accounts` にあるが、あるかと、その操作の権限があるかは確かめない（管理のAPI（9.7）が、7.3の確かめ（`account.Check`）で確かめる）。
5. 大きさ：64MiBまで（下記の「上限」）。
6. 読み込み：ビルドと同じ読み込み（6.7の「JSONの読み込み」。`schemaVersion` は6.9）で、その種類の文書として読む。エラーには、ファイル・行・列とJSON Pointerを付ける（`entries/ent_….json:1:22: /foo: unknown key`）。
7. 文書の `id`：あれば、渡したIDと同じこと（ビルドと同じ。6.7の「ビルドでの検証」。`entries/ent_….json:1:22: /id: id "ent_…" differs from the ID of the document, "ent_…"`）。

`Delete` は、1〜3、設定の文書でないこと、4、文書がいまあること（無ければ `entries/ent_….json: not found`）の順に確かめる。`AddRevision` は、下記の「リビジョン」。

規則：

- 文書の名前：エラーの中の文書の名前は、サイトのディレクトリ（4.3）でのファイルの名前にする（`entries/<ID>.json`・`terms/<ID>.json` など、`revisions/<ID>.json`、`site/settings.json`）。そのため、ビルドのエラーと同じ形になる。
- 形だけ：読み込みは、文書の形だけを確かめ、必須の項目と参照は確かめない（6.7。`{"schemaVersion": 1}` だけの文書も保存できる）。サイト設定との検証（6.7）と正規化は、保存の操作（`internal/edit`。6.7）でする。
- バイト列のまま：JSONは、渡されたバイト列のまま持ち、書き直さない（6.12の1）。そのため、意味が同じでも、バイト列が違えば（末尾の改行など）、新しい版になる。
- 索引：確かめた後に、同じ `Update` の中で、索引を更新する（上記の「索引」）。更新できなければ（索引や、オブジェクトが壊れているときも）、エラーを返す。呼ぶ側は、そのエラーで `Update` の関数を終える（そうしないと、書きかけの文書がコミットされる）。
- デーモンの確かめ（案）：上の確かめは、`store`（クライアントの側）の確かめ。デーモンは、コミットのとき、自分の規則を、さらに確かめる（足すだけの表の書き換えと削除・監査イベントの無い書き込み・`meta` の版の行・頭の行・上限。3.6の「デーモンが守る規則」）。`store` が作る書き込みは、これに当たらないので、デーモンが断るのは、`store` を通らない書き込みと、`store` の誤りに限る。
- 記録の無い書き込み：`Update` は、関数が成功した後に、記録のほかに何かを書き（`Changed`）、記録（7.4）を1件も足していないものを、何もコミットせずに、`ErrUnrecorded`（`the transaction writes but adds no audit record`）で失敗させる。記録だけの `Update` と、何も書かない `Update`（同じバイト列の `Put` など）は、そのまま。保存先の中の書き込み（作る・表の版の更新）は、自分の記録を同じコミットに書く。`PutOriginal` は、例外（7.4の「記録の無い書き込みを断る」）。

**リビジョン**

- ID：リビジョンのIDは、ほかのエンティティと同じく、`rev_` とULID（6.7）にする（内容のハッシュにはしない。決定済み。6.1）。内容は、エンジンのオブジェクトに、ハッシュで持つ。
- 表に持つもの：どのエントリーのものか・保存した日時・保存した人は、JSONに入れず、`revisions` の表に持つ（リビジョンのJSONは、内容だけ。6.4.1。決定済み。6.1）。
- 足すとき（`AddRevision`）：書けるトランザクションか、エントリーのID、リビジョンのID、保存した人、大きさ、読み込み（名前は `revisions/<ID>.json`）を、この順に `Put` と同じく確かめる。それから、エントリーがいまあること（無いものと、消したものは `entries/ent_….json: not found`）と、IDが新しいこと（`revisions/rev_….json: already exists`）を確かめる。同じ内容でも、同じIDのリビジョンは足せない（`Put` と違い、何もしないことにはならない）。
- 書き換えない：リビジョンは、書き換えず、消さない（6.4.1）。エントリーを消しても、そのリビジョンは読める。
- 更新の日時：エントリーを更新した日時は持たず、公開しているリビジョンの保存した日時で代える。サイトマップの `lastmod` と構造化データの `dateModified`（6.8）に使うかは、6.12の26。

**原本**

- ハッシュで指す：原本は、中身のハッシュ（メディアの `hash`。6.6.2）を名前にして、`files/` に置く（上記の「データのディレクトリ」。ハッシュを名前にすることは決定済み。3.1）。同じ中身の原本は、1つのファイルになる。
- 書く（`PutOriginal`）：渡したものを、終わりまで読みながら、ブロックに分けて、デーモンに送り（3.6の「原本」）、ハッシュと大きさを求めて返す。デーモンが、一時ファイル（`files/.tmp-<ランダムな16進数16桁>`）に書き、受けたハッシュと大きさを確かめ、一時ファイルをディスクに同期して閉じてから、原本の名前に変え（`<16進数2桁>` のディレクトリが無ければ作って、`files/` を同期する）、そのディレクトリも同期する。ディレクトリがあっても、デーモンが、そのディレクトリのために `files/` を同期していなければ、同期する（強制終了したプロセスが作ったディレクトリは、名前がまだディスクに無いことがある）。そのため、原本のファイルは、すべてあるか、無いかのどちらか。取り消し（Goの `context`）は、渡したものを読むたびに、その前に確かめる。送る途中で失敗したら（読む側の失敗・取り消し・上限を超える・接続が切れる）、デーモンには、原本も一時のファイルも残らない。`PutOriginal` は、書き手の接続を使うので、書き終わるまで、`Update` は待つ（管理のAPIは、受け取った本文を、一時のファイルに置いてから `PutOriginal` に渡し、遅い送り手が、書き手の接続を塞がないようにする。9.7）。
- 同期の失敗：デーモンの原本の同期（一時ファイル・`files/`・原本のディレクトリ）が1つでも失敗したら、デーモンは、書くのを止める（エンジンの同期の失敗と同じ印。3.6の「同期の失敗」）。それからの `PutOriginal` は、`the store has stopped after a sync failed; restart the machine before starting the daemon again` で失敗し（`stopped`）、同時に動いていたものも、終わる前に同期が失敗していれば、失敗する。文書の書き込み（`Update`）も、同じ文で失敗する。同期に失敗した変更を、Linuxは、ディスクに書かないまま、書いたものとして扱うことがあり、後の同期は、それを書かない。そのため、続けると、原本の名前がディスクに無いのに、`PutOriginal` が成功することがある。マシンを再起動してから、デーモンを起動し直す（プロセスを再起動するだけでは足りない。デーモンは、止まったときに、データのディレクトリに印（`stopped`）を残し、同じ起動の間は、起動を断る。3.6の「同期の失敗」）。
- 同じ原本：原本の名前のファイルがあれば、置き換える（壊れていなければ、同じ中身）。そのため、同じ原本を同時に書いてもよく、壊れたファイル（中身がハッシュと合わないもの）も、同じ原本を書き直せば直る。
- 受け付けないもの：空のもの（`the original is empty`）と、64MiBを超えるもの（`the original is larger than 67108864 bytes`。超えたところで、読むのをやめる）。
- ファイルシステムの失敗：`PutOriginal` が返す、デーモンの `files/` の失敗は、デーモンの答え（`failed`）の文で、`fs.ErrNotExist` を包まない（`files/` が無い・一時のファイルが消えたなど）。無い文書や原本の `fs.ErrNotExist`（`not found`）と、呼ぶ側が見分けるため：包むと、`files/` が消えたときの失敗が、管理のAPI（9.7）で「無い資源」の404になり、ログにも書かれない。デーモンに届かないこと（ソケットのファイルが無い）も、`fs.ErrNotExist` を包まない（`cannot reach the daemon`）。
- 開く（`OpenOriginal(ctx, hash)`）：ハッシュの形（`sha256:` と小文字の16進数64桁）を確かめてから、デーモンに頼む。`ctx` は、開くことと、開いたファイルの読みのすべてを区切る：終われば、読みは、そのエラーで失敗する（原本の取得の写しが、要求の期限の中で終わる。9.7）。デーモンが、ファイルがふつうのファイルで、64MiBまでであることを確かめ（シンボリックリンク・ディレクトリ・名前付きパイプなどは、エラーにする。3.6の「原本」）、送る。無ければ、無いことの分かるエラー（`files/9f/9f86…: not found`）。
- 読むときの確かめ：開いたファイルは、終わりまで読んだときに、読んだもののハッシュを確かめ、違えば、終わりの代わりに、エラーを返す（`original sha256:…: the data has the hash sha256:…`）。読んでいる間に64MiBを超えたもの（開いた後で大きくなったもの）も、エラーにする。
- 大きさまで読むとき：ファイルの大きさまでしか読まない読み方（Goの `io.ReadFull` など）では、終わりに届かないので、この確かめが働かない。そう読むときは、自分でハッシュを確かめる（ビルドは、そうしている。6.6.2の「原本を読むとき」）。
- 一時のファイルの片付け：デーモンが、起動のとき（エンジンの書くロックを取った後）、`files/` の直下にある、`.tmp-` と16進数16桁の名前のふつうのファイル（`PutOriginal` が途中で止まったもの）を、すべて消す。ほかの名前・ディレクトリ・シンボリックリンク・原本のディレクトリの中は消さない。消せなければ（`files/` を読めないときも）、デーモンは起動に失敗し（`/srv/data/files/<名前>: cannot remove: …`・`/srv/data/files: cannot read: …`）、保存先は変わらない。`store` の `Open` は、消さない。管理のAPI（9.7）の一時のファイルは、ここには無い（管理のサーバーの `tmp`。9.4）。
- メディアの文書：メディアの文書と原本が合うか（`size`・`mimeType` など）は、ここでは確かめない。保存の操作のメディアの追加と差し替え（6.6.2）は、保存した原本から `mimeType`・`width`・`height` を読んで、文書にし、サイトのディレクトリの取り込み（6.7の「取り込み（案）」）は、すべてのメディアの原本を、文書と照らす。ビルドは、公開するメディアの原本を、文書と照らす（6.6.2の「原本の確かめ」）。

**壊れない書き込み**

- 1つのコミット：1回の `Update` は、デーモンへの1回の `Commit` で、エンジンの1つのコミット（ログの1つのレコード。3.5の「コミット」）になる。関数がエラーを返したとき、パニックしたとき、取り消したとき、コミットの前に管理のサーバーが止まったときは、何も送らないか、デーモンが捨てる（置いたオブジェクトは、`Commit` まで、デーモンのメモリにだけある。3.6の「1回の保存の流れ」）ので、何も残らない。デーモンが途中で止まっても、保存先は、前の内容か新しい内容のどちらかになる。止まった後は、デーモンが開くときに、エンジンが、確定したコミットだけを使う（3.5の「復旧」）。答えを受ける前に、接続が切れたときは、`Update` は、確定したかを、繋ぎ直して確かめる（3.6の「1回の保存の流れ」）。
- 片方だけ残ることは無い：オブジェクトと、それを指す版とリビジョンは、同じコミットに入る。文書とリビジョンの書き込みと、その索引の行（上記の「索引」）も、同じコミットに入るので、索引が、文書と食い違うことは無い。ファイルにするオブジェクトは、それを指すレコードより先に書いて同期する（3.5の「コミット」）。そのため、無いオブジェクトを指す版やリビジョンはできず、3.3の「オブジェクト書き込み成功／メタデータ更新失敗」でも、保存先の状態は壊れない（コミットしなかったオブジェクトのファイルは、使われずに残ることがあり、保守モードの回収で消す。3.5の「保守モード」）。監査の記録（7.4）も、同じ `Update` の、ほかの書き込みと同じコミットに入る（記録だけの `Update` は、記録だけのコミット）。記録の無い書き込みは、断る（上記の「書くときの確かめ」）。
- 原本は先に書く：原本は、それを使うメディアの文書より先に書く（`PutOriginal` の後で、メディアの文書を `Put` する）。そのため、途中で止まっても、使われない原本か一時ファイルが残るだけで、無い原本を指すメディアの文書はできない（残った一時ファイルは、デーモンが起動するときに消す（上記の「原本」）。使われない原本の回収は、まだ無い。6.12の125）。
- 同期の失敗：デーモンのエンジンの同期が1つでも失敗したら、デーモンは、書くのを止め、それからの `Update` は、`the store has stopped after a sync failed; restart the machine before starting the daemon again` で失敗する（3.5の「失敗の扱い」。3.6の「同期の失敗」。6.12の129）。マシンを再起動してから、デーモンを起動し直す（同じ起動の間は、デーモンが、印（`stopped`）で、起動を断る。3.6の「同期の失敗」）。原本の同期の失敗も、同じ（上記の「原本」）。
- 読むたびに確かめる：文書とリビジョンのJSONは、読むたびにハッシュと照らし、原本は、終わりまで読んだときに照らす（上記の「原本」）。壊れていれば、エラーにする（`object sha256:…: the data has the hash sha256:…`）。

**同時に使う**

- 同じプロセス：`View` は、同時にいくつも動く（それぞれ、読み手用のソケットの接続で、スナップショットを持つ。同時に動く数には、クライアントの上限があり、超えるものは、取り消されるまで待つ）。`View` は、`Update` を待たず、そのコミットしていないものも見ない。`Update` は、1つずつ動く（書き手の接続は1つ）。待っている `Update` が動く順は、決めていない。待つのに時間の上限は無く、取り消されれば、関数を呼ばずに、取り消しのエラー（`context canceled` など）を返す。
- 原本：`OpenOriginal` は、トランザクションとも、`PutOriginal` とも、同時に動いてよい（開いたファイルは、置き換える前のものか後のもので、どちらも同じ中身）。`PutOriginal` は、書き手の接続を使うので、`Update` と同時には動かない（同じ原本の `PutOriginal` が続けて動いてもよい）。
- 書き手は1つ：デーモンは、書き手の接続を、1つしか許さない（3.6の「デーモンが守る規則」）。2つ目の書き手として繋ぐ `Create`・`Open` は、クライアントの待ち（3.6の「接続」の2秒）の後、`/run/whiteroom-db: another process is connected as the writer` で失敗する。書き手として繋ぐのは、管理のサーバーと、書くコマンド（`whiteroom init`・`whiteroom account`。9.4）だけで、同時には繋げない。エンジンの書くロック（3.5の「ロック」）は、デーモンを2つ動かさないためのもので、保守のサブコマンドが動いていれば、デーモンは、すぐに始まれない（`/srv/data/logdb: maintenance is running`）。
- 読み手：ほかのプロセス（ビルド・`whiteroom backup`・`whiteroom doctor` など。9.2）は、`OpenReader` で、デーモンの読み手用のソケットに繋ぐ。読み手の `View` は、書き手を待たず、始めたときに、デーモンが同期していたコミットだけを見る（スナップショット。3.6）。読み手は、ファイルを開かない。読み手の `Verify`（`Check`）と `Backup` は、書き手の `Commit` を、その間、待たせる（3.6の「保守の口」）。

**上限**

- 文書：1つの文書（リビジョンと設定の文書も）は、64MiB（67108864バイト）まで（`entries/ent_….json: too large: 67108865 bytes (max 67108864)`）。サイトのディレクトリ（4.3）と同じ上限を、保存先でも確かめる（管理のAPIは、本文の上限を、受け取る前に確かめる。9.7の「上限」。6.12の24）。
- 原本：64MiBまで（6.6.2。上記の「原本」）。
- 1回の `Update`：デーモンへ送る操作の束（3.6の「プロトコル」の `Commit`）が268435446バイト（256MiBより10バイト少ない）まで（`the transaction is too large: 300000000 bytes (max 268435446)`）。`Update` が置くオブジェクトの合計も、268435446バイトまで（`the staged objects would be over 268435446 bytes`。3.6の「上限」）。エンジンのコミットのレコードの本体の上限（3.5の「制限」）も、同じ値。64KiB以上のJSONは、ファイルのオブジェクトになり、レコードには、ハッシュと大きさだけが入る（上記の「エンジンと設定」。6.12の136）。

**依存**

- cgo：要らない（デーモンも）。`CGO_ENABLED=0` でもビルドでき、すべてのテストが通る（CIの `build without cgo`・`test without cgo`）。核を入れた後は、デーモンだけが、cgoでリンクする（3.6の「実行ファイル」）。cgoが要るのは、テストの `-race` だけ（開発シェルのCコンパイラーを使う）。cgoが有効なビルド（開発シェルの既定）では、Goの `net` などがcgoを使う（6.12の126）。
- 配布：実行ファイルの静的リンク、ほかのシステム向けのビルド（クロスビルド）、配る実行ファイルに付けるライセンスの表示は、6.12の126。
- 使う側：どのパッケージが保存先を使うかは、`.golangci.yml` の depguard の規則が正（`AGENTS.md`）。保存先からのビルドは、`internal/publish` を通る（4.4）。コマンド（`whiteroom init`・`serve admin`・`build -db`・`backup`・`doctor`・`account`。9.4）が、保存先を使う。保存先は、データのディレクトリを開かず、`internal/dbclient` でデーモンに繋ぐ。エンジンを開けるのは、デーモンだけ（depguard の規則 `to-engine`。3.6の「プロセスと境界」）。

**まだ無いもの**

- 回収（GC。3.3）：無い。オブジェクトと原本を消す処理は無く、エンジンの保守モードの圧縮と回収（3.5の「保守モード」）は、デーモンの実行ファイルのサブコマンド（`whiteroom-db compact`・`gc`。3.6の「保守の口」）で動かせるが、`gc` は、原本を消さない。何を、いつ消すかは、6.12の125。
- リストアの道具：写しから戻すコマンドは、まだ無い（リストアは、写しを、デーモンを止めて、データのディレクトリの場所に置くこと。9.4の「`whiteroom backup`」。6.12の131）。写しの確かめは、デーモンを動かす前に、`whiteroom-db check` で、何も変えずにする（案。#70 の計画への答え（2026-11-23）で決めた。3.6の「保守の口」）：表の行（索引・監査・文書が指す原本）は、写しの上で、もう1つのデーモンを動かして、`whiteroom doctor` で確かめる。形の版の移行の道具は、まだ無い（#145）。バックアップの記録（`backup`）は、保存先に足さない（バックアップは読み手がするため。7.4。6.12の234）。バックアップの残りは6.12の258。
- 壊れたものの修復（案。#144 の計画への答え（2026-11-25）で決めた）：エンジンの修復は、作った：`whiteroom-db repair`（デーモンを止めて動かす。9.4。3.5の「保守モード」。3.6の「保守の口」）が、壊れたログとオブジェクトを読み、読めないものを落として、新しい世代に書き直す。直す前に、何を落とすかを示し、`logdb/` の写しを残す。保存先の外の、`files/` の原本は、変えない。修復が、失ったオブジェクトと原本を指す行は、直さず、`Check`・`whiteroom doctor` が、その行を示し続ける（`index`・`history`・`original`。#149。#147 から分けた。6.12の291）。検出は、`Check`・`whiteroom doctor`・`whiteroom-db check`（9.4。6.12の131）。ほかに作ったのは、ログイン履歴の古い記録を消す `whiteroom-db compact` と、読める鎖の切れ目と、番号の飛びを認める `whiteroom-db accept-break`（7.4。飛びは、#147）。
- 管理のAPI（9.7）の後の段階で作る管理画面。ビルドを止めて再開するコマンド（9.4。6.12の108）。
