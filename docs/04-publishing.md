## 4. コンテンツ編集・ビルド・公開

### 4.1 決定済み

- 管理者はコンテンツを作成・編集できる。
- 閲覧者向けページは、コンテンツを**静的ビルドして生成した成果物**を公開する。
- 公開コンテンツの配信時に、原則として記事取得のためのRDBクエリやサーバーサイドテンプレート実行を必要としない。
- **出力パスの重複**（投稿と固定ページがどちらも `/{slug}/` で同じスラッグを持つ場合や、リダイレクトの `from` が既存のページと重なる場合など）は、ビルドで、出力するすべてのパス（エントリー・一覧・タクソノミー・フィードなど）とリダイレクトを集めて検査し、重複があればビルドを失敗させる（公開中の成果物は変えない）。保存・公開の操作でも、同じ規則で先に検査する（6.7。書いた後に分かる出力は、ビルドだけが確かめる。6.12の151）。スラッグの一意性は同じ言語・同じタイプの中だけなので（6.4.2）、それだけでは防げないため。
- ビルドは、新しいリリースを書き終えてから、公開中のリリースを、新しいリリースに**一度に切り替える**（4.3の「リリースと切り替え」。いくつ残すかと戻す操作は6.12の108）。
- 公開するものが**検証**（複数のエンティティにまたがる検証も）を通らなければ、ビルドを失敗させる（4.3・6.7。同期する項目の一致は6.12の27、公開中のものが通らなくなる変更は6.12の109）。

### 4.2 提案段階

- **保存と公開の分離**：下書きを保存しても直ちに公開せず、「公開」操作時にビルドする。
- **状態管理**：Draft / Published / Archived 等を管理する。
- **サイト全体のリリース管理**：ビルド成果物をリリース単位で管理し、切り替えとロールバックを行う（切り替えは決定済み。4.1。ロールバックは4.4。残る論点は6.12の108）。
- **ビルド対象スナップショット固定**：編集中のデータ更新とビルド結果が混在しないようにする。
- **フルビルドから開始し、将来差分ビルドに対応**：記事・一覧・タグなどの依存関係を追跡する。
- **公開前プレビュー**：本番ビルドと同じレンダリング処理を使用する。
- **ビルド失敗時は現行公開成果物を維持**する。

「編集を保存するたびに自動公開するか」「明示的な公開操作を必須とするか」は、4.4で仮に決めた（案。下書きの保存では公開せず、公開の操作をしたときに公開する。レビュー・承認は入れない）。決定済みにするかは、12章の論点4。

### 4.3 ビルド（案）

静的ビルド（4.1）を、`internal/build` に作った。サイトを読み込みの口から読み、公開するものを確かめて、出力先のディレクトリにリリースを書き、公開中のリリースを、新しいリリースに一度に切り替える。4.2の提案のうち、リリース単位の管理と切り替え（戻す操作は4.4）と、失敗したときに公開中の成果物を変えないことは、このとおりにした。ビルドを動かすコマンドは `whiteroom build`（9.4）。保存先（3.4）からビルドを1つずつ動かす仕組みは4.4。この節の規則は、「決定済み」と書いたもの（4.1）のほかは、どれも仮に決めたもの（案）。出力するパスとファイルは6.6.8、リダイレクトとサーバーの設定は6.6.6、メディアは6.6.2、メニューは6.6.4、ページの描画と `<head>` は6.8、ページのテンプレートに渡すデータは5.4.4。

**読み込みの口**

- ビルドは、サイトを、読み込みの口（`build.Source`）から読む。口は、保存の形（3章）を隠す狭いもので、サイト設定の2つのファイル（設定の文書とスキーマのファイル。6.6.8）、種類ごとの文書（エントリー・ターム・メディア・著者プロフィール・メニュー・フォーム・リダイレクト）のすべて、IDで指した1つのリビジョン、ハッシュ（`hash`。6.6.2）で指したメディアの原本、テーマのファイルを返す。無いリビジョンと原本は、無いことの分かるエラー（Goの `fs.ErrNotExist`）にする。同時に呼んでもよい。
- ビルドは、ディレクトリに置いたサイト（下記）からも、保存先（3.4）からも読む。保存先からのビルドでは、保存先のスナップショット（`internal/publish`）がこの口になる（4.4）。
- 文書は、ファイル（パスとバイト列）のまま返し、ビルドが、6.7の規則で読み込む。そのため、文書の問題には、ファイルと行・列を付けられる（下記の「エラーと警告」）。参照の照会（6.7）とパスの照会（6.6.8）の関数は、ビルドが、読んだ文書から作る。口のエラー（読めないファイルなど）は、ビルドのエラーにする（下記の「エラーと警告」）。
- 読む順：サイト設定と、すべての種類の文書（下書きも）と、テーマを、初めに読む。リビジョンは、公開しているエントリーのものだけを、検証のときに読み、ページとフィードを描画するときと、問題の位置を示すとき（下記の「エラーと警告」）に、読み直す（バイト列を持ち続けないため。下記の「メモリ」）。同じIDのリビジョンを何度も（同時にも）読むので、口は、同じIDには同じファイルを返す。読み直したファイルが、検証したもののSHA-256と違えば、ビルドを失敗させる（`rendering the pages: revisions/rev_….json: changed during the build`）。ただし、問題の位置を求めるための読み直しで違っていれば、失敗させず、その問題を、位置なしで示す。原本は、公開するメディアのものだけを、使うときに読む。リビジョンは書き換えず（6.4.1）、原本はハッシュで指すので、保存先がそれらを消さなければ、ビルドの途中で文書が変わっても、初めに読んだときのサイトでビルドする（4.2のスナップショットの固定）。保存先からのビルドでは、文書を、スナップショットの1つの `View` で初めに読み、リビジョンと原本は、求められたときに読む（4.4）。

**サイトのディレクトリ**

サイトを1つのディレクトリに置くこともできる（`internal/sitedir`。`whiteroom build`（9.4）とテストが読む。保存先からのビルドは4.4）。サイトのディレクトリは、保存先に取り込める（`edit.Import`。6.7の「取り込み（案）」。WordPressからの取り込み（6.10）とは別）。文書は、種類ごとのディレクトリに、IDをファイル名にして置く。

| 名前 | 内容 | 必須 |
| --- | --- | --- |
| `site/settings.json` | 設定の文書（6.6.8） | ○ |
| `site/schema.yaml` | スキーマのファイル（6.6.8） | ○ |
| `entries/` | エントリー（6.4.1）。`<ID>.json` のファイルを置く | |
| `terms/`、`media/`、`authors/`、`menus/`、`forms/`、`redirects/` | ターム・メディア・著者プロフィール・メニュー・フォーム・リダイレクト（6.6.1〜6.6.6）。`entries/` と同じく置く | |
| `revisions/` | リビジョン（6.4.1）。`<リビジョンのID>.json` のファイルを置く（リビジョンのJSONはIDを持たず、ファイル名がIDになる。6.12の26） | |
| `files/` | メディアの原本（6.6.2）。`hash` の `sha256:` の後ろ（小文字の16進数64桁）を名前にして置く | |
| `theme/` | テーマ（5.4） | ○ |

規則：

- 外を読まない：ディレクトリの外は読まない（`..` も、外へのシンボリックリンクも）。`site/`・種類ごとのディレクトリ・`revisions/`・`files/`・`theme/` と、読むファイルがシンボリックリンクなら、エラーにする（`entries/ent_….json: symbolic links are not allowed`）。`theme/` は、ほかの部分と切り離して開く（中のものから、サイトのほかのファイルは読めない）。中のシンボリックリンクは、テーマの読み込みがエラーにする（5.4.1）。
- 隠しファイル：種類ごとのディレクトリの、名前が `.` で始まるもの（`.DS_Store`・`.git/` など）は無視する。
- 直下のほかのもの：表に無いもの（`README.md`・`.git` など。`whiteroom build` の既定の出力先の `out/` と、キャッシュの `cache/` も。9.4）と、`site/` のほかのファイルも無視する。
- 必須：表の必須のものが無ければ、エラーにする（`site/settings.json: missing file`、`theme: missing directory`）。種類ごとのディレクトリが無ければ、その種類の文書が無いものとする。
- 種類と名前：種類ごとのディレクトリの中（隠しファイルを除く）は、すべてふつうのファイルで、名前は `<ID>.json`、IDはその種類の接頭辞を持つ正しいID（6.7）にする。ほかのもの（名前の違うもの、ディレクトリ、名前付きパイプなど）はエラーにする（`entries/foo.json: invalid name: use <ID>.json; invalid entry ID "foo": use "ent_" and a ULID (26 characters in upper case)`、`entries/ent_….json: must be a regular file`）。種類を名前より先に確かめ、すべてのものを確かめて、問題をまとめて示す。文書の中の `id` が、ファイル名のIDと同じかは、ビルドが確かめる（6.7の「ビルドでの検証」）。
- 求められたものだけ：`revisions/` と `files/` は一覧にせず、求められたファイル（公開しているエントリーのリビジョンと、公開するメディアの原本）だけを確かめて読む。ほかのファイル（古いリビジョン、下書きのリビジョン、使わない原本。壊れたものも）は見ない。
- 大きさ：1つの文書（リビジョンと、サイト設定の2つのファイルも）は、64MiB（67108864バイト）まで（メモリを使い切らないように。文書の大きさの上限は6.12の24）。読む前の大きさで確かめ、読みながらも確かめる（`entries/ent_….json: too large: 67108865 bytes (max 67108864)`）。原本は、ここでは大きさも中身も確かめず、ビルドが、メディアの文書と照らす（6.6.2）。
- エラー：サイトのディレクトリからのパス（`/` で区切る）をファイルとし、パスの順に並べる（読めないものは `entries/ent_….json: cannot read: permission denied` など）。

**公開するもの**

- エントリー：`status` が `published` のものを、その `publishedRevision` のリビジョンで公開する（6.4.1）。下書き・予約・アーカイブのものは、ページを作らず（そのURLは404。アーカイブしたもののURLを、410やリダイレクトにするかは6.12の7）、リビジョンも読まない。
- ターム・著者プロフィール・メニュー・フォーム・リダイレクト：下書きが無いので、保存したものを、次のビルドで公開する（保存すると、ビルドを起こす。4.4。残る論点は6.12の38）。ページ（タームの一覧・著者ページ）は6.6.8、メニューは6.6.4、フォームは6.6.5、リダイレクトは6.6.6。
- メディア：公開するもの（公開しているリビジョン、サイト設定、著者プロフィール、リダイレクト）が参照するものだけを公開し、その原本だけを開く（6.6.2）。参照されないメディアは、原本が無くてもエラーにしない。

**段階**

ビルドは、次の順に進む。サイトの問題（下記の「エラーと警告」）は、段階ごとにすべて集め、問題があれば、その段階の終わりで止まる（後の段階は確かめない）。サイトの問題でないエラー（口のエラー、テンプレートの実行のエラー（5.4.4）など）では、すぐに止まる。

1. 準備：渡したもの（下記の「渡すものと結果」）を確かめ、出力先とキャッシュのディレクトリが離れていることを確かめる（下記の「画像のキャッシュ」）。出力先を作り（無ければ）、中身を確かめて（下記の「出力先」）、ロックする（下記の「ロック」）。キャッシュのディレクトリを開く（6.6.2）。
2. 読む：読み込みの口から、サイト設定・種類ごとの文書・テーマを、この順に読む。口がエラーを返せば（サイトのディレクトリの問題も）、そこで止まって、そのエラーを返す。
3. 文書の読み込み：すべての種類のすべての文書を読み込む（6.7の「ビルドでの検証」）。
4. サイト設定とテーマ：サイト設定（6.6.8）とテーマ（5.4.8）を読み込んで確かめる。エラーは、サイト設定のもの、テーマのもの（`theme/` の下のパスにする。`theme/templates/list.html: missing file; every theme needs entry.html and list.html`）の順に、それぞれの順のまま並べる。
5. 検証：公開するものを検証する（6.7の「ビルドでの検証」）。
6. またがる検証：複数のエンティティにまたがる検証（6.7）。
7. ページの計画：ページとほかの出力のパスを求める（6.6.8）。
8. リダイレクトと重複：リダイレクトの行き先を決め（6.6.6）、出力パスの重複（4.1）を確かめる（6.6.8）。どちらの問題も、まとめて示す。ここまでは、リリースを書き始めない。
9. 書く：リリースの一時ディレクトリ（下記の「リリースと切り替え」）に、ページ（サイトのCSS・ページのCSS・テーマの `assets/` も。6.6.8・6.8）・フィード・サイトマップ・メディアのファイル（原本を確かめてから。6.6.2）を書く。原本の問題は、すべてのメディアのものをまとめて示す。
10. 重複をもう一度：書いて分かる出力（ページのCSSのファイル・メディアのファイル・分けたサイトマップ）を含めて、出力パスの重複を確かめる（6.6.8）。
11. サーバーの設定：`server.json`・`nginx.conf`・`public/.htaccess` を書く（6.6.6）。
12. 公開：リリースに名前を付けて、`current` を切り替え、古いリリースを消して、画像のキャッシュを掃除する（下記）。

6から8（またがる検証・ページとほかの出力の計画・リダイレクトの行き先と、書く前の出力パスの重複）は、`internal/siteplan` にあり、保存の操作（6.7）も、同じコードを使う（案）。ビルドは読んだ文書から、保存の操作は保存先の索引（3.4）から、同じ形のサイトの模型を作って、siteplan に渡す。書いて分かる出力パスの重複（10）は、ビルドだけが確かめる（6.6.8・6.12の151）。

取り消し（Goの `context`）は、`current` を切り替えた後は、受け付けない（公開は終わっている）。

**エラーと警告**

- 形：サイトの問題は、サイト設定のエラー（6.6.8の「エラーの位置」）と同じく、ファイル・行・列・JSON Pointer・英語の文で示し、1行に1つ並べる（`revisions/rev_….json:1:1: /title: missing title`）。ファイルは、サイトのディレクトリからのパス（テーマのファイルは `theme/` の下）。無い項目の問題は、それを持つはずの親の位置にする（多くは、文書の先頭の `1:1`）。スキーマのファイル（YAML）の問題にも、行と列を付ける。位置の無いもの（ディレクトリの問題など）は、ファイルだけを示す（`theme: missing directory`）。
- 順：段階ごとに、ファイル・行・列・JSON Pointer・文の順に並べ、まったく同じものは1つにする（サイト設定とテーマの段階だけは、上記の順のまま）。同じサイトからは、同じエラーになる。
- ほかのエラー：サイトの問題でないものは、サイトを読むとき（段階の2と5）の口のエラーなら、そのまま返す。書く段階のエラーには、何に失敗したかを前に付ける（`rendering the pages: page /about/: template: …`、`writing the feeds: …`、`publishing the media: …` など。原本を開けない口のエラーも、`publishing the media: …` になる）。出力先とリリースのディレクトリを確かめ、作り、名前を変え、消すときのエラーには、そのディレクトリのパスを前に付ける（`/srv/site: …`）。
- 警告：ビルドを止めない問題（描画の警告（6.5.3・6.8）、テーマに無いページのテンプレート（5.4.4）、出力しないメニュー・メニューの項目・リダイレクト（6.6.4・6.6.6）、原本の警告（6.6.2）、テーマの翻訳の無い文言（5.4.6）など）は、エラーと同じ形と順で、結果の `Warnings`（下記）に入れる。どの警告で公開を止めるかなどは6.12の82。例（6.11の例を集めた見本のサイト（6.11）をビルドしたときの警告の一部）：

```text
menus/mnu_01JC0000000000000000000002.json:5:3: /location: the theme has no location "sidebar"; the menu is left out
revisions/rev_01JB8X9Y3ZE5G8K1N4Q7S2V6W9.json:5:3: /template: the theme has no page template "standard"; rendered with entry.html
theme: no translation in en for the key "postedBy"; pages in en use its text in ja, the default language of the theme
```

- コマンド：`whiteroom build`（9.4）がサイトの問題とほかのエラーを示す形は、9.4の「ビルドの出力」。

**出力先**

出力先のディレクトリ（下記の `Out`）には、リリースと、公開中のリリースを指すリンクを置く。

| 名前 | 内容 |
| --- | --- |
| `.lock` | ビルドのロック（下記）。空のファイルで、消さない |
| `current` | 公開中のリリースを指す、相対のシンボリックリンク（`releases/<名前>`） |
| `releases/<名前>/` | リリース。名前は、中身から作る小文字の16進数16桁（下記） |
| `releases/<名前>/public/` | 公開ディレクトリ。ページ、サイトのCSSとページのCSS、テーマの `assets/`、フィード、サイトマップ、メディアのファイル（6.6.8・6.6.2）と、Apacheの `.htaccess`（6.6.6） |
| `releases/<名前>/server.json` | 内蔵サーバー（9.5）が読むもの（リダイレクト・404のページなど。6.6.6）。公開しない |
| `releases/<名前>/nginx.conf` | Nginxの設定に読み込ませるもの（6.6.6）。公開しない |

規則：

- 公開ディレクトリ：Webサーバーが配信するのは `<出力先>/current/public`（6.6.8と5.4.7の「出力先」は、この公開ディレクトリのこと）。内蔵サーバーでは、`whiteroom serve public <出力先>` とする（ビルドが `current` を切り替えると、次のリクエストから、新しいリリースを配信する。9.4・9.5）。Nginxでは、`server` の中で `root <出力先>/current/public; include <出力先>/current/nginx.conf;` とする（サイトのURLにパスがあるときと、設定を読み込み直すことは6.6.6）。Apacheは、公開ディレクトリの `.htaccess` を読む（6.6.6）。
- ビルドの作ったものだけ：出力先には、表のものだけを置く。ほかに受け付けるのは、終わらなかったビルドが残したもの（`releases/.tmp-<16進数16桁>/` と `current.tmp-<16進数16桁>`。次に成功したビルドが消す）だけ。ほかのもの（`README` などのファイル、名前が16進数16桁でないリリース、ディレクトリでない `releases`、シンボリックリンクでない `current`、`releases/<16進数16桁>` のほかを指す `current` など）は、それを示すエラーにして（パスの順に1行ずつ）、消さず、変えない。そのときは、ロックより前に止まるので、`.lock` も作らない。そのため、ほかのファイルのあるディレクトリや、`lost+found` のあるファイルシステムの最上位は、出力先にできない。例（出力先が `/srv/site` のとき）：`/srv/site/README: not made by the build; the output directory must hold only .lock, releases and current`、`/srv/site/current: not made by the build; it points to "/var/www", not to a release`。
- `current` が `releases/<16進数16桁>` を指していても、そのリリースが無ければ、`current` が無いものとして、置き換える。
- 出力先が無ければ作る。ファイルは0644、ディレクトリは0755で作る（umaskの許す範囲で）。

**ロック**

- ビルドは、`<出力先>/.lock`（無ければ作る）に、`flock(2)` の排他のロックを、待たずにかけ、終わるまで持つ（失敗しても、終われば外す）。同じ出力先のビルドがほかに動いていれば、すぐに失敗し（`another build is running in /srv/site`）、何も変えない。
- `flock(2)` のあるシステム（Linux・macOS・FreeBSD・NetBSD・OpenBSD・DragonFly BSD・illumos）だけで動く（対象はLinux。9章）。ほかのシステム（Windowsなど）では、ビルドは失敗する（`cannot lock <出力先>: builds need flock(2), which windows does not have`。6.12の107）。
- ロックは出力先だけにかかり、キャッシュのディレクトリにはかからない（下記の「画像のキャッシュ」）。

**リリースと切り替え**

新しいリリースを書き終えてから、公開中のリリースを、新しいリリースに一度に切り替える（決定済み。4.1）。

- 書き込み：リリースを、`releases/.tmp-<ランダムな16進数16桁>/` に書く。出力先の外には書かず、どのファイルも新しく作る（同じファイルを2回書けば、上書きせずにエラーにする）。ディスクへの同期はしない（6.12の106）。
- 名前：書き終えたら、すべてのファイルを読み直して、名前を作る。ファイルごとの行（リリースからのパスと、ファイルのSHA-256の小文字の16進数64桁を、タブでつないで改行を付けたもの）を、パスのバイト列の順に並べ、その全体のSHA-256の先頭の16進数16桁にする。パスは `/` で区切る（`nginx.conf`、`public/index.html`、`public/media/<メディアのID>/会社外観.jpg`、`server.json`）。ディレクトリ（空のものも）・モード・日時は数えない。そのため、同じサイトは同じ名前になり、1バイトでも違えば、違う名前になる。
- 置く：一時ディレクトリの名前を `releases/<名前>` に変える。同じ名前のリリースがすでにあれば、中身も同じなので（`releases/<名前>` は、いつもそろったリリース。下記の「残すもの」）、一時ディレクトリを消して、あるものを使う（編集を元に戻したときなど）。
- 切り替え：`current` がすでにそのリリースを指していなければ、そのリリースを指す新しいシンボリックリンク（`current.tmp-<ランダムな16進数16桁>`）を作り、名前を `current` に変える。名前の変更（`rename(2)`）は、`current` を一度に置き換えるので、`current` が無くなることはなく、いつも前のリリースか新しいリリースを指す（リンクそのものを読む `readlink(2)` と `lstat(2)` は、置き換えの間も失敗しない）。リンクをたどってファイルを開くリクエストは、前のリリースか新しいリリースの、どちらかのファイルを受け取るが、切り替えの瞬間に、まれに失敗する（下記の「切り替えの瞬間」）。結果の `Changed` は、`current` が変わったか。
- 残すもの：`current` が変わったら、新しいリリースと、それまで `current` が指していたリリース（戻すため）を残し、ほかのリリースを消す。変わらなければ（同じサイトのビルド）、リリースを消さない。リリースは、先に `releases/.tmp-<ランダムな16進数16桁>` に名前を変えてから消す。名前の変更（`rename(2)`）は一度に済むので、消している途中でプロセスが落ちても、消すのに失敗しても、`releases/<名前>` には、そろったリリースだけが残り、消しかけのものは、名前を変えた先に残る。そのため、リリースの一覧と戻す操作（4.4）や、同じ名前のリリースの使い回し（上記の「置く」）が、消しかけのものを使うことはない。終わらなかったビルドが残したもの（ビルドの初めに見つけた `releases/.tmp-*` と `current.tmp-*`。消しかけのリリースも、ここに入る）は、どちらでも消す。消すのは、ビルドの初めに確かめたもののうち、これらだけで、ほかのものには触れない。戻す操作は4.4（残すのは、このとおりの2つ。もっと残すかは6.12の108）。
- 公開の後の失敗：切り替えた後で、古いリリースを消すか、画像のキャッシュを掃除するのに失敗したら、結果（公開したリリース）とエラーの両方を返す。

**切り替えの瞬間**

`current` を置き換える `rename(2)` は一度に済み、`current` が無くなることも、リンクそのものが読めなくなることも無い（上記の「切り替え」）。ただし、その瞬間に `current` をたどってファイルを開く読み手は、まれに失敗する（#79）。

- 起きること：`current` を通してファイルを開くか調べると（`open(2)`・`stat(2)`）、まれに `ENOENT`（ファイルが無い）になる。どちらのリリースのファイルも、受け取れない。失敗するのはその1回の読み取りだけで、すぐに読み直せば、新しいリリースのファイルを読める（測った中では、同じ読み手の次の読み取りが失敗したことは無い）。リンクそのものを読む `readlink(2)` と `lstat(2)` は、失敗しない。
- 確かめた範囲：Linux 6.18.57のext4（開発のマシン）。GitHub Actionsのランナーでも、1回、同じ失敗が起きた（そのファイルシステムとカーネルの版は、確かめていない）。tmpfsとramfsでは、起きなかった。XFS・Btrfsなどのファイルシステム、ほかのカーネルの版、NginxとApache以外のWebサーバーは、確かめていない。
- 原因（公開されているカーネルのソース（v6.18.57）を読んで求めた）：置き換えで、古いリンクの最後の名前が消えると、ext4は、ほかに参照が無ければ、`rename(2)` の中でそのinodeを解放し（`ext4_evict_inode`）、inodeの中に持つ短い行き先（60バイト未満。`releases/<名前>` は25バイト）を0で埋め、どのリンクも大きさを0にする。ロックを取らずに名前をたどる探索（LinuxのRCU path walk）が、置き換えの直前に古いリンクを見つけていると、その後で行き先を読んで、空として扱い、残りのパス（`public/…`）を、リンクのあるディレクトリ（出力先）の中から探して、見つけられない。`readlink(2)` と `lstat(2)` は、リンクの参照を取ってから読むので、解放と重ならない。tmpfsは、そうした探索が終わってから、行き先を解放する。60バイト以上の行き先（ブロックに持つ）でも、ext4では失敗した（ソースからは、大きさを0にすることで説明できるが、どの処理で起きたかは、追跡していない）ので、行き先を長くしても避けられない。
- サーバー：内蔵サーバーは、影響を受けない（9.5）。`current` を自分で読み（`readlink(2)`）、リリースを名前で開くので、カーネルが `current` をたどることが無い。NginxとApacheは、リクエストのたびに、`<出力先>/current/public` の下のファイルを、`current` をたどって開く（上記の「出力先」）ので、切り替えの瞬間に当たると、そのリクエストは、ファイルが無いかのように答える。測った中では、Nginxは404（サイトの404のページ。それも開けなければ、Nginx自身の404のページ）、Apacheは403（Forbidden）か、Apache自身の404のページだった。切り替えの後のリクエストは、新しいリリースで答える。
- 見込み：切り替えは、ビルドか戻す操作（4.4）のたびに1回。失敗の数は、その瞬間に `current` をたどる読み取りの数に比例した。開発のマシンで測った値（2026-11-10）から、毎秒100件のサイトでは、1回の切り替えでリクエストが1件失敗する確率を、Nginxで約1億分の1、Apacheで約1000万分の1と見込んだ。
- 書く側で避けるかは、6.12の230（いまは避けていない）。

**失敗したとき**

- どの段階で失敗しても、出力先は、ファイルの中身もモードも、前のままにする（4.2。公開中のリリースも、残したリリースも変えない）。リリースの一時ディレクトリは消し、名前を変えて置いたリリースも、`current` を切り替えられなければ消す（消すのに失敗したときに残るものは、上記の「残すもの」）。出力先・`.lock`・`releases` だけは、無かったときに作ったまま残る。
- 失敗したビルドの後では、画像のキャッシュを掃除しない（作ったファイルは、次のビルドで使える）。
- エラーは、サイトの問題（検証・またがる検証・出力パスの重複・文書と合わない原本）なら、並べたもの（上記の「エラーと警告」）。取り消したときは、取り消しのエラー（`context canceled` など）。

**同じ入力から同じ出力**

- 同じサイトからは、ワーカーの数やキャッシュの有無によらず、同じファイルと、同じリリースの名前になる。並べるもの（文書・ページ・警告・エラー・出力）は、どれも決まった順にし、ビルドした日時や乱数を、出力に書かない（乱数は、一時のものの名前だけに使う）。
- ただし、画像のURLの版（`?v=`）は、Goのマイナー版を上げると変わり、ビルドが作る画像のファイルも変わることがある（6.6.2）ので、同じサイトでも、画像を使うページと、リリースの名前が変わる。

**画像のキャッシュ**

- ビルドは、渡したキャッシュのディレクトリ（6.6.2）に、画像のファイルと、原本を調べた結果を置き、次のビルドで使い回す。キャッシュのディレクトリは、出力先と同じもの、出力先の中のもの、出力先を中に持つものにはできない（`the output directory /srv/site and the cache directory /srv/site/cache must not be the same, or one in the other`。キャッシュの中の出力先は、掃除で消え、出力先の中のキャッシュは、出力先に置けないもの（上記）になるため）。シンボリックリンクをたどった絶対パスで比べる。
- 掃除：成功したビルドの後で（`current` の変わらないビルドでも）、そのビルドで使わなかったファイルを消す（6.6.2）。そのため、同時に動く2つのビルドには、別のディレクトリを渡す（ロックは、キャッシュのディレクトリにかからない。6.12の104）。
- メモリ：原本を調べるときと、PDFを確かめて書き出すときは、原本をメモリに読む。同時に読む原本は、`Workers` と4の小さいほうの数まで（原本は64MiBまでなので、256MiBまで。画像を展開するメモリの上限（`Memory`。6.6.2）の外。6.12の104）。

**メモリ**

ビルドのメモリは、文書の数に比例して増える。大きいサイト（WordPressから取り込んだ、数千から数万件の投稿など。6.10）をビルドできるように、持つものと目標を、次のとおり仮に決めた（案。残る論点は6.12の139から141）。

- ビルドの終わりまで持つもの：サイト設定とスキーマのファイル、テーマ（`assets/` のファイルも。5.4.7。数と合計の上限は6.12の81）、すべての種類の文書のバイト列（ファイルと同じ大きさの写し。問題の位置を示すため。上記の「エラーと警告」）と読み込んだもの、ページと出力の計画、リダイレクトの行き先、警告。公開しているエントリーのリビジョンは、本文（`body`）を除いたものと、抜粋（`excerpt`。無ければ自動の抜粋。6.8）、ファイルの名前とSHA-256だけを持ち、ファイルのバイト列は持たない。警告は、リビジョンのファイルの名前だけを持ち、位置（行と列）は、並べるときに、ファイルを読み直して求める。`fields` は、`blocks`・`richText` の値も、JSONのまま持つ（そのエントリーのページの描画だけが使うが、一覧のデータが使うほかのフィールドと、同じ `fields` にある）ので、これらのフィールドを多く使うサイトでは、その分が、1件ごとに増える。
- ページを描画する間だけ持つもの：リビジョンの本文（ブロックの配列）、読み直したリビジョンのバイト列、ページのデータ（一覧に並べるエントリーのデータも）、描画したHTML。ページを書いたら手放し、同時に持つのは、`Workers` の数のページだけ。ただし、投稿ページ（`postsPage`。6.6.8）の固定ページの本文のHTMLは、一覧のすべてのページに使うので、言語ごとに1回だけ描画して、ビルドの終わりまで持つ。ページのCSS（6.6.8。見た目の規則のあるページの分で、同じ内容は1つ）も、同じファイルを1回だけ書くために、すべてのページを描画し終えるまで持つ。
- 目標（案）：画像の無い投稿が2万件あるサイトを、最大RSS（プロセスが常駐したメモリの最大）512MiB以内でビルドできること（メモリが1GiBほどのVPSで、Webサーバーなどの余地を残す）。画像のファイルを作るメモリ（`Memory`。6.6.2。`-memory`（9.4）で決める）と、原本を調べるときに読むメモリ（256MiBまで。上記の「画像のキャッシュ」）は、この目標の外にある。

測った値の条件：`TestBenchmarks`（下記の「確かめるもの」）が、見本のサイト（6.11）に画像の無い投稿を足したサイトを、別のプロセスで3回ビルドして、時間と最大RSSの中央値を求める。サイトは、サイトのディレクトリ（`internal/sitedir`）と見本のテーマ（5.4.9）から読み、出力先とキャッシュは空にする。足した投稿は、20の段落（日本語の120文字ずつ）の本文と、カテゴリー・タグ・著者を1つずつ持ち（リビジョンのファイルは約9.4KiB）、画像は無い（画像は、見本のサイトの数枚の小さいものだけ）。プロセスの `GOMAXPROCS` は4で、`Workers`（下記の「渡すものと結果」）は0なので、ワーカーも4つ。`GOGC`・`GOMEMLIMIT`・`GODEBUG` は設定しない。時間は `Build` の呼び出しの間、最大RSSは `/proc/self/status` の `VmHWM`（3.5の「測るもの」と同じ）。マシン（CPU・メモリ・OS・ディスク・Go）は、3.5の「ベンチマークの条件」と同じ。

| 足した投稿 | ページ | 時間（秒） | 最大RSS（MiB） |
| ---: | ---: | ---: | ---: |
| 0 | 50 | 0.16 | 33.6 |
| 1000 | 1450 | 0.68 | 41.1 |
| 5000 | 7050 | 2.82 | 72.2 |
| 20000 | 28050 | 11.16 | 209.2 |

- 残るヒープ：ビルドの終わりに残るヒープ（GCの後に生きているもの）は、5000件と20000件の差から求めると、1件あたり約3.0KiB。リビジョンを持ち続けずに読み直すので、時間は少し延びる（6.12の140）。
- 残る上限：メモリも時間も、件数に比例して増える。20000件の最大RSSは209.2MiB（目標の約4割）で、ビルドの終わりに残るヒープ（60.6MiB）の約3.5倍になる（描画などで出るごみが、回収されるまで残る）。5000件から20000件の間では、1件あたり約9.4KiB増え、同じ割合で増えるとすれば、5万件で約480MiBになる（測っていない）。時間は、1件あたり約0.55ミリ秒（6.12の140）。
- ほかに増えるもの：警告は、1つあたり約0.3KiB（`TestBuildMemory` が測る）。ページのCSS（見た目を直接指定した投稿が多いサイト）、`fields` の `blocks`・`richText` の値、画像を使うサイトの、使うメディアごとの、原本を調べた結果と公開するファイルの一覧は、足した投稿には無いので、測っていない。大きい文書では、描画する間に持つもの（本文・読み直したバイト列・HTML）が、そのリビジョンの大きさで、`Workers` の数だけ、同時にある（測っていない）。
- `GOMEMLIMIT`（Goのランタイムが使うメモリの上限の目安。環境変数）：`whiteroom build` にも効き、下げると、回収が増えて、最大RSSが下がり、時間が延びる（`TestBenchmarks` に付けて測った。20000件で、`160MiB` なら、最大RSSは209.2MiBから168.2MiBに下がり、時間は約2%延びる。`128MiB` なら、139.7MiBに下がり、約8%延びる。最大RSSは、上限より8〜12MiB大きい）。既定は設けない（6.12の139）。
- 確かめるもの：CIで動く `TestBuildMemory`（見本のサイトに投稿を足してビルドし、段階の終わりに残るヒープが、1件あたり4KiBまでであることを確かめる）と、手で動かす `TestBenchmarks`（上の値を測る）。動かし方は `AGENTS.md`。最大RSSと時間は、CIで確かめない（6.12の141）。

**渡すものと結果**

ビルドに渡すもの（`build.Options`）：

| 項目 | 値 |
| --- | --- |
| `Source` | 読むサイト（読み込みの口） |
| `Out` | 出力先のディレクトリ（無ければ作る） |
| `CacheDir` | 画像のキャッシュのディレクトリ（上記） |
| `Memory` | 画像のファイルを作るときに、同時に使うメモリの見積もりの上限（6.6.2）。0は1GiB |
| `Workers` | ページの描画・メディアの公開・リリースのファイルの読み直しを、同時に行う数。0はGoの `GOMAXPROCS` の値 |

`Source`・`Out`・`CacheDir` は必須で、`Memory`・`Workers` の負の値はエラーにする。

ビルドの結果（`build.Result`）：

| 項目 | 値 |
| --- | --- |
| `Release` | `current` が指すリリースの名前 |
| `Changed` | `current` が、前と違うリリースを指すようになったか |
| `Pages` | 書いたページの数（エントリーのページ、一覧のページ、404のページ） |
| `Files` | リリースの公開ディレクトリのファイルの数（ページも含む） |
| `Warnings` | 警告（上記の「エラーと警告」） |

失敗したときは、結果を返さない（公開の後の失敗だけは、結果も返す）。

### 4.4 公開（案）

保存と公開の分け方（4.2）、保存先（3.4）からのビルド、予約、戻す操作を、仮に決めて、作った。4.2の提案のうち、保存と公開の分離（公開の操作で公開する）、ビルド対象のスナップショットの固定、ロールバック、失敗したときに公開中の成果物を維持することは、この節のとおりにした。差分ビルド（6.12の175）と公開前のプレビューは、まだ無い。ビルドが失敗しても公開中の成果物を変えないことは決定済み（4.1）で、この節の規則は、それ以外は、どれも仮に決めたもの（案）。エントリーの状態は6.4.1、公開の操作の確かめと結果は6.7、旧URLからのリダイレクトは6.6.6、保存先と索引は3.4。

**公開のモデル**

- 保存と公開を分ける：エントリーは、公開の操作（6.7の「公開の操作（案）」）をするまで、公開しない。下書きのリビジョンを保存しても、公開中のサイトは変わらない。
- レビュー・承認は、いまは入れない（12章の論点4）：状態は、`draft`・`published`・`scheduled`・`archived` の4つのまま（6.4.1）。公開の依頼や承認の段階は持たない。公開の操作を誰ができるかは、7.3の「ロールと権限」（案）。保存の操作と公開の操作（6.7）の前に、この確かめ（`account.Check`）を呼ぶのは、管理のAPI（#48）。

**ビルドを起こすもの**

公開するものを変えた操作は、成功すると、ビルドの要求を1つ出す（結果の `Publishes`。6.7）。

| 操作 | ビルドを起こすか |
| --- | --- |
| エントリーの公開（`Publish`）、予約の日時の公開（`PublishScheduled`） | 起こす |
| 公開中のエントリーの公開をやめる（`Unpublish`）・アーカイブ（`Archive`） | 起こす |
| ターム・著者プロフィール・メニュー・フォーム・リダイレクトの作成・保存・削除、メディアの保存・差し替え・削除、設定の保存 | 起こす（下書きが無く、保存したものを、次のビルドで公開する。4.3） |
| 公開していないエントリーの `Unpublish`・`Archive`、予約（`Schedule`） | 起こさない（公開するものは変わらない） |
| エントリーの作成、下書きのリビジョンの保存、翻訳の作成、エントリーの削除 | 起こさない（エントリーは、公開したリビジョンだけを公開し、公開中・予約中のエントリーは消せない。6.7） |
| メディアの追加 | 起こさない（公開するものが使うまで、公開しない。4.3） |

- 何も保存しなかった操作（同じバイト列の保存、すでにその状態にある公開の操作など）と、失敗した操作は、起こさない。
- `Editor` を通さない変更（`edit.Import`、保存先のAPIでの書き込み）は、要求を出さない。手でビルドし直す口（`Publisher.Rebuild`）で要求する（6.12の183）。

**要求とまとめ方**

- 要求：時刻・理由・操作の結果を持つ。理由は、`start`（`Publisher` を作ったとき）、`operation`（上記の操作）、`rebuild`（`Rebuild`）、`resume`（戻した後の再開。下記）。
- 1つずつ：同じ出力先に、ビルドは同時に1つしか動かさない。
- まとめ方：ビルドが動いていなければ、待っている要求のすべてを、1つのビルドが取る。ビルドが動いている間に来た要求は、そのビルドには入らず、そのビルドが終わった後の1つのビルドが、まとめて取る。そのため、続けて公開しても、ビルドは重ならない。
- 取る順：要求は、スナップショット（下記）を取る前に取る。そのため、取った要求の変更は、そのビルドが必ず見る。取った後、スナップショットを取る前に来た要求は、その変更をすでに見たビルドの後に、1回の余分なビルドを起こす（同じリリースになり、`Changed` は false。6.12の175）。
- 取り消し：`Publisher` を動かす `context`（`Run`）が終わると、動いているビルドを取り消し（4.3の「段階」）、待っている要求は、ビルドしない。`current` を切り替えた後のビルドは、公開を終わらせる。

**スナップショット**

- ビルドごとに、保存先の1つの `View`（3.4）で、設定の文書とすべての種類の文書（エントリーの状態も）を読み、ビルドの読み込みの口（4.3）にする（`publish.Snapshot`）。ビルドの間に保存したものは、そのビルドには見えない（4.2のスナップショットの固定）。
- リビジョンと原本は、ビルドが求めたときに、保存先から読む。保存先は、リビジョンも原本も、書き換えず、消さない（3.4）ので、後で読んでも、スナップショットの時点のサイトになる。`internal/edit` の操作は、文書と、それが指すリビジョンを、同じ `Update` に入れる（3.4）ので、スナップショットの文書が指すリビジョンは、いつもある（保存先のAPIで直接書くと、この限りでない）。回収（6.12の125）を作るときは、動いているビルドが読むものを消さないようにする。
- ファイルの名前は、サイトのディレクトリでの名前（`entries/<ID>.json`・`revisions/<ID>.json`・`site/settings.json`。3.4の「書くときの確かめ」）にする。ビルドの問題（4.3の「エラーと警告」）は、サイトのディレクトリからのビルドと同じ形で、行と列は、保存先が持つバイト列に付く。
- スナップショットは、すべての文書のバイト列を持ち、ビルドが終われば手放す。ビルドは、さらにその写しを持つ（4.3の「メモリ」。6.12の182）。
- テーマ（5.4）とスキーマのファイル（6.6.8）は、保存先に無い（3.4）ので、`Publisher` を作るときに渡す。テーマのファイルは、ビルドのたびに読み直す（6.12の181）。出力先・キャッシュのディレクトリ・`Memory`・`Workers` は、ビルドの設定（4.3の「渡すものと結果」）と同じ。

**結果**

- 状態（`Publisher.Status`）：動いているビルドと、最後に終わったビルド（始めた時刻と終わった時刻、取った要求、ビルドの結果（4.3の `build.Result`）、失敗したときのエラー）、待っている要求があるか、止めているか（下記の「戻す操作」）、公開できなかった予約（下記の「予約」）。ビルドを動かすプロセスのメモリにだけ持ち、保存先には書かない。プロセスを起動し直すと消える（6.12の177）。長く残す記録は、操作の記録（7章。#47）で決める。
- 起動：`Publisher` は、起動したときに1回ビルドする。プロセスが止まっていた間に公開されなかった変更（ビルドの途中で止まったときなど）も、これで公開する。

**失敗したとき**

- 公開の操作は、ビルドが失敗しても、取り消さない。操作は、保存先に残る（確かめは、操作でする。6.7）。ビルドが失敗すれば、公開中のリリースは前のままで（4.1・4.3の「失敗したとき」）、失敗は、最後のビルドの結果に出る。
- 操作の確かめは、ビルドと同じ規則と文なので、ビルドの失敗の多くは、操作が先に断る。それでも失敗するのは、ビルドだけが見つけるもの（書いた後に分かる出力パスの重複。6.12の151）、操作を通さない変更、出力先とディスクの問題。
- 失敗したビルドは、やり直さない。次の要求（操作・`Rebuild`・再開）が来るまで、ビルドしない（6.12の176）。次のビルドは、いまの保存先を、最初からビルドする。

**予約**

- 予約したエントリー（`scheduled`）は、予約の日時に、予約したリビジョンを公開する（`PublishScheduled`。6.7）。動かすのは、書くプロセス（管理のサーバー。3.4の「同時に使う」）の中の `Publisher` で、そのプロセスの時計を使う。
- ステップ：`Publisher` は、予約を調べて、日時が来たものを公開する処理（ステップ）を、次のときに、ビルドの間にする（ビルドが動いている間は待つ）。起動したとき（最初のビルドの前。日時が過ぎた予約も、最初のビルドで公開する）。まだ来ていない予約のうち、いちばん早い日時（タイマーは1つ）。エントリーの状態を変える操作の後。`Rebuild` の後。公開できなかった予約があるときの、`Options.Retry`（既定は1分）ごと。ビルドが動いている間に日時が来た予約は、そのビルドが終わってから公開する（サイトに出るのは、どちらにしても、そのビルドの次のビルド）。
- 公開：ほかの公開と同じに、ビルドを起こす。戻した後に止めている間（下記）も、ステップは動き、公開は保存先に入り、ビルドの要求は待つ。
- 保存した人：予約の日時の公開は、予約した人の保存として記録する（案。権限の確かめと、アカウントを変えたときの扱いは、7.3の「予約」。6.12の186）。
- `date` の無い投稿：予約の日時の公開が `date` を入れる（入れ方は6.7の「公開の操作（案）」の「日付（案）」）。
- 公開できなかった予約：エントリーは `scheduled` のままで、何も保存しない。問題（6.7の「公開の操作（案）」。ビルドと同じ形）は、`Status` に出す（最後のステップのものだけ。メモリにだけ持つ）。次のステップで、また公開しようとする（6.12の185）。公開できたとき、または予約でなくなったとき、`Status` から消える。

**戻す操作**

- 残すリリース：新しいリリースと、それまで公開していたリリースの2つ（4.3の「残すもの」。もっと残すかは6.12の108）。
- 一覧（`build.ListReleases`・`Publisher.Releases`）：出力先のリリースの名前と、公開中のもの。リリースは、どれもそろっている（消しかけのものは、`releases/.tmp-*` に名前が変わっていて、一覧に出ない。4.3の「残すもの」）。ロックを取らず、何も書かない。
- 戻す（`build.Rollback`）：残したリリースに、`current` を一度に向け直す（リリースの切り替えと同じ、シンボリックリンクの名前の変更。4.3）。ほかには何も変えず、何も消さない。向け直す前のリリースも、次のビルドが消すまで残るので、また向け直せる。ロックは待たずに取り、ビルドが動いていれば失敗する（`another build is running in /srv/site`）。リリースの名前は、小文字の16進数16桁で、残っているものにする（`invalid release name "x"`、`/srv/site/releases/<名前>: no such release`）。すでにそのリリースを公開していれば、何も変えない。内蔵サーバー（9.5）は、次のリクエストから、戻したリリースを配信する（4.3の「出力先」）。
- 止めて、再開する（`Publisher.Rollback`・`Publisher.Resume`）：戻したままだと、次のビルドが、戻したリリースを置き換えてしまうので、`Publisher` は、動いているビルドの終わりを待って（そのビルドは、自分のリリースを公開してから、戻される）、戻し、そのあとの自動のビルドを止める。止めている間も、操作は保存先に保存され、予約の公開も動き、ビルドの要求は待つ（`Status` の `Paused`）。再開は、待っていた要求をまとめて、いまの保存先の内容を1回ビルドして公開する（戻したリリースは、置き換わる）。`Publisher` を起こし直したときも、起動のビルドで、同じになる（止めたことは、保存しない。6.12の178）。
- 戻すのに失敗したとき（名前の誤り、別のプロセスのビルド）は、`current` も、止めているかどうかも、前のまま。同時に戻す操作は1つ（`another rollback is running`）。止めていないときの再開は、何もしない。
- コマンド：戻す・再開するコマンドは、まだ無い（9.4。#49）。

**置き場所**

- `internal/publish`：スナップショットと `Publisher`（要求・まとめ・結果・予約・戻すときの停止と再開）。保存先からのビルドは、`internal/publish` を通る（依存の向きは `.golangci.yml`）。
- プロセス：`Publisher` は、書くプロセス（管理のサーバー）の中で動き、ビルドも、その中で動かす。管理のAPI（#48）が、`Publisher` の `Editor` の操作を呼ぶ。ビルドを別のプロセスで動かして、上限をかけること（5.3）は、まだしない（6.12の182）。コマンド（9.4）が `Publisher` を動かすのは、#49。
