### 7.4 ログイン履歴とアクティビティログ（案）

管理画面にログインする人の出入りと、サイトと管理の側のデータを変えた操作を、保存先（3.4）に記録として残す。ログイン履歴とアクティビティログを実装し、監査にも使えるようにすることは決定済み（7.1）。この節は、その記録の形・鎖・保持・書けなかったときの動きを、仮に決めた規則として書く。記録の型・操作の一覧・鎖の頭の行は `internal/audit` に、記録を足す・読む・確かめる口は保存先（`internal/store`）に作った。鎖の頭の書き出しは、DBのデーモンが書く（`internal/dbserver` の `ExportHeads`。3.6）。記録を読む口は、管理のAPI（9.7）が作った。プロセスにつなぐこと（数えた失敗の書き出し・記録の失敗のログ）は、`whiteroom serve admin` が作った（9.4）。この節の規則は、「決定済み」と書いたもの（7.1）のほかは、どれも仮に決めたもの（案）。

**目的と状態**

- 目的：だれが、いつ、どこから、何をして、何が変わった（変わらなかった）かを、あとで調べられるようにする（7.1・7.2）。ログインの成功と失敗・セッション・アカウントの管理・文書の変更・公開・ビルドを記録する。7.2の記録対象・同一トランザクションでの記録・通常UIからの編集と削除の禁止・ハッシュチェーンと独立した検証値の保管は、この節の形にした。OWASP の Logging Cheat Sheet（下記の「確かめた事実（#47）」）が挙げる出来事のうち、認可（アクセス制御）の失敗（権限で断った要求）は、管理のAPIが、`access.denied` として記録する（下記の「記録する操作」・9.7）。
- 作ったもの：
  - 記録の型・操作の一覧・JSON・絞り込み・鎖の頭の行（`internal/audit`）。鎖の頭の書き出しは、デーモンの `ExportHeads`（3.6の「頭の書き出し」）。
  - 記録を足す口・読む口・鎖の頭を返す口・確かめる口と、記録の無い書き込みを断る規則（`internal/store`。3.4の「操作」）。表の版は8（鎖の始まりと認めた切れ目の表 `chains` と、デーモンのイベント 0x02・0x03 を足した。#70）。
  - ログイン履歴の古い記録を消すこと（`whiteroom-db compact`）と、読める鎖の切れ目を認める口（`whiteroom-db accept-break`）と、壊れた保存先を直すときに、失った記録の穴を記すこと（`whiteroom-db repair`。#144）：デーモンの保守（3.6の「保守の口」）と、鎖の始まりと認めた切れ目と穴を読む `VerifyAudit`（下記の「改ざんの検知」）。
  - 記録を足す側：保存の操作と公開の操作（`internal/edit`。6.7）、ログインとセッションとアカウントの操作（`internal/account`。7.3）、ビルドと戻す操作（`internal/publish`。4.4）、保存先自身の作成と更新（`internal/store`）。管理用のサーバー（`internal/admin`。9.6）は、クライアントのアドレスと User-Agent を、アカウントの口に渡す。管理のAPI（9.7）は、権限で断った要求を、記録だけの `Update` で記録し（`access.denied`）、記録を読む口を持つ。
- 作っていないもの：下記の「まだ無いもの」。

**2つのログ**

| ログ（`log`） | 残すもの | 個人の情報 |
| --- | --- | --- |
| ログイン履歴（`login`） | ログインの成功と失敗（HTTPの側で断ったものも）・ログアウト・セッションの始まりと終わりと、使い続けるセッションの最後の要求・無効なトークン | クライアントのアドレス・User-Agent・打たれたログイン名 |
| アクティビティログ（`activity`） | 保存の操作・公開の操作・アカウントの操作・ビルドと戻す操作・保存先自身の作成と更新・権限で断った要求・操作のIDの記録を消したこと | アドレスも User-Agent も、打たれたログイン名も、セッションのキーも持たない（`Record.Check` が断る。下記の「記録の形」）。アカウントのログイン名（変える前と後）は持つ（下記の「保持の期間と個人の情報」） |

- 2つは別の鎖にする（案）：番号（1から）・鎖の頭・絞り込みが、ログごとに別。個人の情報を、ログイン履歴の1か所にまとめ、ログイン履歴だけを、古いほうから消せるようにするため（下記の「保持の期間と個人の情報」）。
- どちらも、エンジンの監査イベント（3.5の「イベント・操作のID・暗号化の封筒」）として、1つの並びに置く（`log` で区別する）。エンジンの口と、エンジンの形の版（3.5の「ファイルの形」）は、変えていない。

**記録の形**

記録は、空白の無い1行のJSONで、キーは次の順。空の項目は書かない。

| キー | 内容 | 規則 |
| --- | --- | --- |
| `log` | ログ（`login`・`activity`） | |
| `n` | ログごとの番号 | 1から。保存先が付ける |
| `prev` | 同じログの1つ前の記録のSHA-256（`sha256:` と小文字の16進数64桁） | 保存先が付ける。最初の記録には無い |
| `at` | 時刻（UTCのRFC 3339。秒の下は、0でない最後の桁まで） | 保存先が付ける（下記の「番号と時刻と鎖」） |
| `actor` | した人。アカウントのID（`usr_` とULID）か、`system` | 呼ぶ側が渡した値が、そのまま入る（保存先は、形だけ確かめる）。管理のAPIは、要求の中の値でなく、確かめたセッションの `Principal`（`Authenticate` が返したアカウント）のIDを渡す（9.7）。空は、アカウントの分からない人（ログインしていない人の試しなど） |
| `action` | 操作の名前（下記の「記録する操作」） | どれか1つのログのもの |
| `result` | 結果の語。空は成功 | 64バイトまで |
| `target` | 何についての記録か：`kind` と `id` | `kind` は、`entry`・`term`・`media`・`author`・`menu`・`form`・`redirect`・`user`（アカウント）・`settings`・`release`。`id` は、その種類のID（6.7）で、`settings` は空、`release` は小文字の16進数16桁 |
| `account` | 関わるアカウントのID | |
| `session` | セッションのキー（表 `sessions` のキーと同じ、トークンのSHA-256の小文字の16進数64桁。7.3） | ログイン履歴だけ。トークンは、キーから求まらない |
| `client` | `addr`（クライアントのアドレス）と `userAgent` | ログイン履歴だけ。`addr` は `netip.Addr` の文字列の形。`userAgent` は512バイトまで |
| `login` | 打たれたログイン名 | ログインの失敗だけ。64バイトまで |
| `operation` | 操作のID（6.7） | 256バイトまで |
| `changed` | その `Update` が、記録のほかに何かを書いたか | `true` のときだけ書く |
| `before`・`after` | 文書の版：`seq` と `hash` | `hash` は `sha256:` と64桁。消した版は `seq` だけ |
| `revision` | リビジョンのID（`rev_` とULID） | |
| `status` | エントリーの状態（6.4.1） | 64バイトまで |
| `detail` | 操作ごとの項目（文字列の対） | 64個まで。キーは、英字で始まる英数字（64バイトまで）、値は2048バイトまで。キーは並べ替えて書く |

例（ハッシュとIDは、例のための値）。エントリーを公開した、アクティビティログの記録：

```json
{"log":"activity","n":1245,"prev":"sha256:71547e237559add83f6c9279fdb5762eafee857a1060e2d97c0316a70cefb6ba","at":"2026-11-12T01:02:03.456789Z","actor":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","action":"entry.publish","target":{"kind":"entry","id":"ent_01JB8W2N5KD3F6H9J1M4P7R2T5"},"operation":"op_01JBG3N6Y6A9D2F5H8K1N4Q7S0","changed":true,"before":{"seq":17},"after":{"seq":18,"hash":"sha256:43cc23fa52b87b4cc1d02b5b114154151d6adddb17c9fddc06b027fa99e24008"},"revision":"rev_01JB8X9Y3ZE5G8K1N4Q7S2V6W9","status":"published","detail":{"publishes":"true","redirect":"rdr_01JBG3N6Z7B0E3G6J9M2P5S8V1"}}
```

間違ったパスワードの、ログイン履歴の記録：

```json
{"log":"login","n":812,"prev":"sha256:71547e237559add83f6c9279fdb5762eafee857a1060e2d97c0316a70cefb6ba","at":"2026-11-12T01:02:03.456789Z","action":"login.failure","result":"wrong-password","account":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","client":{"addr":"203.0.113.7","userAgent":"Mozilla/5.0 (X11; Linux x86_64; rv:140.0) Gecko/20100101 Firefox/140.0"},"login":"yamada"}
```

- 文字列は、正しいUTF-8で、制御文字を含まない（`detail` の値だけは、改行を含められる）。外から来る値（User-Agent・ログイン名・ファイル名・失敗の文など）は、記録に入れる前に、UTF-8の切れ目で切り、不正なバイトと制御文字を U+FFFD に替える。双方向の制御文字（U+202E など）と、幅の無い文字（U+200B など）は、制御文字（`Cc`）ではないので、残る。記録はJSONなので、形は壊れない。管理画面（管理のAPI（9.7）の後の段階）が、打たれたログイン名と User-Agent を見せるときは、エスケープする（表示を並べ替える文字を、そのまま出さない）。記録の全体は、65536バイト（64KiB）まで。
- 書く前に確かめる（`Record.Check`）：合わない記録は、何も書かずに断る。エラーの文は、項目の名前だけで、記録の値を出さない（ログイン名の欄にパスワードを打った人がいるため）。アクティビティログの記録は、`client`・`login`・`session` を持てず、持つと、その項目の名前を付けたエラーで断る（個人の情報を、ログイン履歴の1か所にまとめるため。書く側の取りこぼしを、保存先が見つける）。
- 読むときは、JSONの形だけを確かめる：知らないキー・同じキー・型の違う値・不正なUTF-8・後ろに続くデータは断り、値の規則は当てない（ほかのビルドが書いた記録を、読めない記録にしないため。7.3の「保存」の「読み方」と同じ）。
- 入れないもの：パスワード・トークン（セッション・招待・再設定）・それらのハッシュ・アカウントの名前とメールアドレスの値。セッションは、キー（トークンのSHA-256）で指す。OWASP の「Data to exclude」は、セッションの識別子を、そのまま記録せず、ハッシュにした値に替えることを考えるよう求める。
- 値は写さず、指す：文書は、種類・ID・版の番号とハッシュ・リビジョンのID・状態だけを持ち、中身は写さない（中身は、保存先の履歴から読める。3.4）。アカウントの行には履歴が無いので、変えた項目の名前と、ロール・状態・ログイン名・著者プロフィールの紐付けの前と後の値を持つ（名前とメールアドレスは、変えたことだけ）。

**記録する操作**

規則（案）：

- 成功した操作は、1件ずつ記録する。何も変えなかった成功（同じバイト列の保存・すでにその状態の公開・何も変えないアカウントの変更）も、`changed` の無い記録を1件書く（記録だけのコミットを1つ作る）。何も変えなかった操作でも、だれが何をしようとしたかが分かり、「記録の無い書き込みを断る」（下記）とも合う。
- 失敗した操作（検証の問題・食い違いなど）は、何も書かないので、記録しない。権限で断った要求は、管理のAPIが、記録だけの `Update` で `access.denied` に残す（下記）。操作のIDの再送で前の結果を返したときも、記録しない（前の記録がある）。
- 保存の操作と公開の操作（6.7）の記録：`actor` は操作した人（`by`）。`target` は、操作の結果が指す文書（設定は種類 `settings` で `id` なし。サイトの取り込みは文書を指さないので、なし）。`operation` は、呼ぶ側が渡した操作のID。`changed` は、何かを保存したか。`before` は、呼ぶ側が読んだ版（元にした版を取る操作だけ）、`after` は、保存した版（版を足した操作だけ）、`revision` は、足した・公開した・予約したリビジョン、`status` は、公開・公開をやめる・アーカイブ・予約・予約の日時の公開が決めた状態。`detail` の共通のキーは、`warnings`（警告の数。0なら出さない）・`publishes`（公開するものを変えたときの `true`）・`redirect`・`number`（エントリーの番号）。
- アカウントの操作の記録：`target` は `user` と、対象のアカウントのID。`detail` の `fields` は、変えた項目の名前（`author`・`email`・`login`・`name`・`password`・`role`・`status`・`token`）を、名前の順に、`, ` でつないだもの。`login`・`role`・`status`・`author` は、変えたものだけ、`<項目>Before`・`<項目>After`（作る操作は After だけ、消す操作は Before だけ。空は出さない）。値は64バイトまで。トークンの用途は `tokenPurpose`（`invitation`・`reset`）、期限は `tokenExpiresAt`（UTC。トークンもそのハッシュも出ない）。

| `release.rollback` | `activity` | 操作した人 | 戻す先のリリース（名前の形のときだけ） | `detail`：`to`（戻す先。呼ぶ側の文字のまま、64バイトまで）・`from`（記録を書くときに公開中のリリース）。記録の後に失敗したときは、もう1件（`result` が `failed`。`detail`：`to`・`error`） |
| `build.resume` | `activity` | 操作した人 | なし | `changed`（止めていたとき）。止めていないときも1件書く |
| `access.denied` | `activity` | 断られたアカウント | 断られた対象（種類とID。口が知っているときだけ。IDの形でないパスの値は書かない） | `detail`：`permission`（断られた権限の名前。7.3）・`suppressed`（その前に、記録しなかった断りの数。0なら書かない）。管理のAPIが、答える前に、記録だけの `Update` で書く（下記の「断った要求の記録」・9.7） |
| `operations.expire` | `activity` | `system` | なし | 操作のIDの記録（6.7）を消したときの1件（消した数が1以上のとき）。`detail`：`expired`（消した数の10進数）。保存の操作が、消す `Update` に入れる |
| `store.create` | `activity` | `system` | なし | 保存先を作るコミットに入る（番号1） |
| `store.upgrade` | `activity` | `system` | なし | 表の版を上げるコミットに入る。`detail`：`from`・`to`（表の版の10進数） |
| `store.write` | `activity` | `system` か書いた人 | なし | 保存先の口で、直接書いた道具とテストが、書いた人を残す印（下記の「記録の無い書き込みを断る」）。本番のコードは書かない |
| `backup` | `activity` | | | 形だけ決めた。書く口は、いまも無い（バックアップは読み手がするので、保存先に記録しない。9.4。6.12の234） |

- 予約の日時の公開：`actor` は `system` で、予約した人は `detail` の `scheduledBy`（案）。版とリビジョンの保存した人は、予約した人のまま（7.3の「予約」。6.12の186）。
- ビルドの記録：ビルドが終わるたびに1件で、取った要求ごとではない。取り消されて終わったビルドは、`result` が `failed`、`detail` の `error` が `context canceled`（ビルドの段階の前置きが付くことがある）。サイトの問題の文は、ファイルの名前と、行・列・JSON Pointer・文を持ち、サイトの文書の値を引用することがある。
- 断った要求の記録（案。`access.denied`）：管理のAPI（9.7）が、権限の確かめ（`account.Check`）で断った要求（`account.ErrForbidden`。読む口も。本文を受け取る前の確かめと、操作の `Update` の中の確かめのどちらも）を、答える前に、記録だけの `Update` で書く。`actor` は、要求の中の値でなく、確かめたセッションのアカウントのID。記録の `Update` は、要求の取り消しから切り離し、保存先を最大5秒待つ。書けなくても、答え（403）は変えず、書けなかった断りは、記録しなかった断りに数える（下記の「記録できなかったとき」）。成功した読みと、権限の断りでない失敗（検証の問題・食い違い・上限など）は、記録しない。アクティビティログの記録は、「どこから」（アドレス・User-Agent・セッションのキー）を持たない（上記の「2つのログ」。6.12の237）。
- 断った要求の上限（案）：ログインしている人が、続けて起こせる（ハッシュを作らない安い要求）。サーバー全体で、管理のAPIの時計（`Config.Now`）の1分ごとに、10件まで1件ずつ記録する（ログインの断りの枠と同じ数。下記の「ログイン履歴」）。超えた断りは、記録を書かず、数える。数えた分は、次に書く `access.denied` の `detail` の `suppressed` に足す（プロセスのメモリだけ。止まると失う）。アクティビティログは消さないので、1分に60件にすると、攻撃が続くとき、1日に最大約8.6万件が残り、ログイン履歴の失敗の記録と合わせて、記録を読む口（9.7）が120秒で読める量に、約11か月で届く（見積もり）。10件なら、断りは1日に最大約1.44万件。OWASP の Logging Cheat Sheet は、記録が資源を使い尽くさないことを求める（9.7の「確かめた事実」）。
- 操作の名前を足しても、表の版は6のまま：読むとき（`Decode`）と `VerifyAudit` は、操作の名前を確かめない（書く前の確かめ（`Record.Check`）だけが、名前を知る必要がある）ので、前のプログラムも、`access.denied` と `operations.expire` の記録を読み、鎖を確かめられる。

**ログイン履歴**

ログイン履歴の記録は `internal/account` が足し、`internal/admin` は、要求ごとに、クライアントのアドレス（9.6の「リバースプロキシ」）と `User-Agent` のヘッダーを、`account.Client` にして、`Login`・`Logout`・`Authenticate`（セッションを使う口。9.6の「CSRF」）・`ChangeOwnPassword`・`SetPassword` に渡し、HTTPの側で断ったログインを `Manager.LoginRefused` で知らせる。規則（案）：

- 成功（`login`）：セッションを書く `Update` に入る。そのとき消す使えない行・`previous` のセッション・上限（1アカウント10個。7.3）を超えた分のセッションの `session.end` が先で、`login` が最後。パスワードのハッシュを、いまの回数で作り直したログイン（7.3の「ハッシュの作り直し」）は、アカウントの行も同じ `Update` で書き換える。その印として、`detail` の `rehashed` が `true`（作り直さなかったログインと、`session.start` には無い）。
- 失敗（`login.failure`）：`result` に理由、`login` に打たれたログイン名（正規化して、64バイトまで）、分かるときは `account`、`client`。応答は、理由によらず同じのまま（9.6。理由を持つのは記録だけ）。

| `result` | 理由 |
| --- | --- |
| `unknown-login` | そのログイン名のアカウントが無い（行が読めないものも） |
| `pending` | 保留のアカウント |
| `disabled` | 無効のアカウント |
| `wrong-password` | パスワードが違う |
| `too-long` | 8KiBを超えるパスワード（7.3の「パスワード」） |
| `changed` | パスワードを比べている間に、アカウントが変わった（セッションを書く `Update` が断った） |
| `error` | パスワードを比べた後の失敗（保存先の失敗・乱数・取り消された要求も） |
| `rate-limited` | 試行の制限（429。9.6）で断った |
| `busy` | ログインの順番の上限（503。9.6）で断った |
| `refused` | 知らない理由で `LoginRefused` に渡されたもの |

- HTTPの側で断ったログイン（8KiBを超えるパスワード・429・503）：`Login` を呼ばないので、`LoginRefused` が、答える前に、同じ形の `login.failure`（`too-long`・`rate-limited`・`busy`）を書く。ログイン名にアカウントがあるかを調べないので、`account` は持たない。答えは変えない。
- 記録しない失敗：パスワードを比べる前の失敗（保存先を読めない・ハッシュの順番を待つ間に要求が終わった）は、比べていないので、記録しない（呼ぶ側に、エラーを返す）。
- ログアウト（`logout`）：セッションの行があったときだけ（期限が切れた行も）。行の無いトークンと、トークンでない文字列は、何も書かない（7.3）。
- セッションの始まり：ログインは `login`。本人のパスワードの変更（`ChangeOwnPassword`）が作る、新しいセッションは `session.start`。
- 最後の要求の時刻（`session.seen`）：`Authenticate` が、最後の要求の時刻を書くとき（保存した値が5分以上古いとき。7.3）に、同じ `Update` で足す。1つのセッションで、5分に1回まで。使い続けるセッションの、アドレスの変わり（盗まれたCookieなど）が分かる。
- セッションの終わり（`session.end`）：セッションの行を消すたびに1件で、`result` に理由。期限で終わったものは、`detail` の `expiredAt` に、期限の時刻（UTCのRFC 3339、小数の秒つき。両方が過ぎていれば、先に過ぎたほう。同時なら `lifetime`）を持つ。期限を過ぎても、行を消すまで（次のログインの掃除か、そのトークンでの `Authenticate`）は書かれないので、`at` は消した時刻で、終わった時刻は `expiredAt`。`client` は、`Authenticate` が見つけて消したときだけ、その要求のものを持つ（ほかは、持たない）。

| `result` | 理由 |
| --- | --- |
| `idle` | 操作の無い時間（1時間）が来た |
| `lifetime` | 全体の期限（12時間）が来た |
| `credentials` | アカウントの `credentialsChangedAt` が、セッションが持つ値と違う |
| `inactive` | アカウントが有効でない（保留・無効） |
| `missing` | アカウントが無い、または読めない |
| `unreadable` | セッションの行が読めない |
| `replaced` | ログインの `previous` のトークンのセッション |
| `evicted` | 1アカウント10個の上限を超えるため、最後に使ったのが最も古いものを消した |
| `password` | パスワードの変更・再設定・`SetPassword` で、アカウントのすべてのセッションを消した |
| `role` | ロールを変えて、アカウントのすべてのセッションを消した |
| `disabled` | アカウントを無効にして、すべてのセッションを消した |
| `deleted` | アカウントを消して、すべてのセッションを消した |

- 無効なトークン（`token.failure`）：`SetPassword` が断った、招待と再設定のトークン。`result` は、`malformed`（トークンの形でない）・`unknown`（どのアカウントも持たない。使い終わったものも）・`expired`（期限切れ）・`disabled`（無効のアカウントのもの）。トークンは記録に入れない。遅れた招待や再設定と、でたらめなトークンの試しを、分けられる。
- ログインしていない人の失敗の上限（案）：`login.failure`（HTTPの側で断ったものも）と `token.failure` は、ログインしていない人が、いくらでも起こせるので、サーバー全体で、`Manager` の時計の分の区切り（毎分0秒）ごとに、次の2つの枠までを、それぞれ1件ずつ記録する。超えた分は、記録を書かず、`action` と `result` ごとに数える。
  - 比べた失敗の枠：パスワードをハッシュと比べた失敗（`Login` が記録する、`unknown-login`・`pending`・`disabled`・`wrong-password`・`changed`・`error`）は、60件まで。
  - 断りの枠：比べる前に断ったログイン（`LoginRefused` が記録する、`too-long`・`rate-limited`・`busy`・`refused`と、`Login` の中で断る `too-long`）と、無効なトークン（`token.failure`）は、10件まで。ハッシュを作らない安い要求で、ネットワークの速さで起こせるので、別の枠にする。1つの枠にすると、安い要求が枠を使い切り、本物の試しの、アドレスとログイン名が残らず、数だけになる。
  - 2つの枠は、分ごとに、別に数え直す。あふれた分は、どちらも同じ数えに入り、同じまとめ（下記）になる。1分に1件ずつ書く失敗の記録は、最大70件で、まとめは、1分に最大2件（`Update` が取る1件と、`FlushSuppressed` を1分ごとに呼ぶときの1件）。
  - まとめ（`login.suppressed`）：数えた分（枠を超えた分と、記録を書けなかった分）は、ログイン履歴を書く `Update` の最初の記録として（その `Update` の、ほかの記録の前に）書く。取る `Update` は、`Manager` の時計の分の区切りごとに、1回まで：その分に、すでに `Update` が取っていれば、取らず、その後に数えた分は、次の分の最初のログイン履歴の `Update` か、`FlushSuppressed` が書く。`detail` に、数えた分の初め（`from`）と終わり（`to`。どちらもUTCのRFC 3339、秒まで。複数の分にまたがるときは、1つにまとめる）と、理由ごとの数（キーは、`action` と `result` を camelCase でつないだもの。`loginFailureWrongPassword`・`loginFailureRateLimited`・`tokenFailureExpired` など。値は10進数の文字列）。2つの枠の分は、理由で分かれ、1つのまとめに入る。`FlushSuppressed` は、分によらず、数えた分をすべて取り、`Update` の1分に1回には数えない（その分に `Update` が取っていなければ、その後に数えた分を、`Update` が取る）。サーバーが、1分ごとと、止めるときに呼べば、攻撃が止まった後の、最後の分の数も書かれる（`whiteroom serve admin` が、そう呼ぶ。9.4。6.12の235）。書く `Update` がコミットしなかったときは、取った数と、取った分の印を戻す（同じ分のうちに、次の `Update` が、もう一度取れる）。ログイン履歴に何も書かない `Update`（行の無いトークンの `Logout` など）は、まとめを取らない。
  - 数えない：成功したログイン・ログアウト・セッションの記録は、どちらの枠にも入れず、数えない（使う人の操作の数で決まる）。
  - 書けなかった失敗：枠に入ったのに、記録を書けなかった失敗（保存先の失敗・5秒の期限。下記の「記録できなかったとき」）は、`OnRecordError` に知らせたうえで、数えた分に足し、次のまとめに入れる（その失敗が来た分の区切りで数える）。その枠は戻さない：戻すと、保存先が塞がっている間、記録を待つ要求の数が、枠の数（1分に70件）を超えて増える。
  - 数えた分は、プロセスのメモリにだけ持つ。まとめを書く前にプロセスが止まると失い、書く `Update` が失敗したときは、数えた分と、取った分の印を戻して、次に書く。`Update` が取った後に数えた分も、次の分か `FlushSuppressed` まで、メモリにだけある。
  - 理由（見積もり）：上限が無いと、パスワードを比べる速さ（開発のマシンで毎秒約35件。7.3）まで記録され、1日に約300万件、約1.4GBになる。ハッシュを作らない429と8KiBを超えるパスワードは、それより速く起こせる。この上限では、攻撃が続いても、1日に最大 72 × 1440 ≒ 10.4万件、約48MBで止まる：失敗の記録が1分に最大70件（1件約464バイト。User-Agent が約110バイトのとき）と、まとめが1分に最大2件（`Update` が取る1件と、`FlushSuppressed` を1分ごとに呼ぶときの1件。1件約320バイトで、理由が多いと約710バイトまで）。測った値：断りを10件送った後、断りと比べた失敗を交互に60組送り、`FlushSuppressed` を呼ぶ最悪の1分で、記録が72件（失敗70件とまとめ2件）、データのディレクトリが約31KB（User-Agent が約70バイトのとき）、約34KB（約110バイトのとき）増えた（2026-11-12）。`Update` が取る回数に上限が無いと、同じ場面（`FlushSuppressed` なし）で、比べた失敗の記録ごとに、断りの数を取るまとめが付き、記録が130件（失敗70件とまとめ60件）、約49KB（User-Agent が約70バイトのとき）になる。ディスクが埋まると、保存先が書けなくなり、すべての保存が失敗する。
  - 残る弱点：枠を超えた試しの、アドレスとログイン名は残らない（数だけ）。攻撃の間は、本人の失敗の記録も、枠を超えると数に入る（比べた失敗は61件目から、断りとトークンは11件目から）。枠は、サーバーに1組で、アドレスごとにも、ログイン名ごとにも分けない（6.12の235）。

例（`login.suppressed`）：

```json
{"log":"login","n":815,"prev":"sha256:71547e237559add83f6c9279fdb5762eafee857a1060e2d97c0316a70cefb6ba","at":"2026-11-12T01:04:12.345678Z","action":"login.suppressed","detail":{"from":"2026-11-12T01:03:00Z","loginFailureRateLimited":"1307","loginFailureWrongPassword":"412","to":"2026-11-12T01:04:00Z"}}
```

**番号と時刻と鎖**

- 番号（`n`）：ログごとに1から、1つずつ。保存先が、同じログの、前の記録（同じ `Update` で足したものも）の次の番号を付ける。失敗した `Update` と取り消した `Update` は、番号を空けない。呼ぶ側が `n`・`prev`・`at` を入れた記録は、断る。
- 鎖（`prev`）：各記録は、同じログの1つ前の記録の、保存したバイト列（上記の形のJSON）のSHA-256を持つ。最初の記録は持たない。保存先が書いたバイト列のままハッシュを求めるので、あとで読み直したときに、書き換わっていれば、合わなくなる。
- 鎖の頭：ログごとの、最後の記録の番号と、そのバイト列のSHA-256。表 `meta` の `loginLog`・`activityLog` と、書き出し用の表 `heads`（頭の行。3.6の「頭の書き出し」）に、その記録と同じコミットで置く（3.4の「表」）。記録の無いログには、行が無い。
- イベントの番号：エンジンの監査イベントの番号は、デーモンの印（3.6の「印」）も数える。記録の番号（`n`）とは別で、エラーの文の「event」の番号に出る（例：`audit log "login": record 12 (event 345): prev is not the hash of record 11`）。
- 時刻（`at`）：保存先の時計で、`Update` を始めた時刻。同じ `Update` で保存した版とリビジョンの保存した日時（3.4）と同じで、1つの `Update` に何件の記録を足しても、同じ。操作を呼ぶ側の時計（`Manager`・`Editor`）ではない。
- デーモンの時計：デーモンは、コミットごとに、自分の時計の時刻を、印として足す（決定済み。13章。3.6の「印」）。記録の `at` とは別で、`at` を偽られても、破られた期間は、印の時刻で特定できる。
- 2つのログの間の順は、意味を持たない。順を言えるのは、同じログの中だけ。
- 足す口だけがあり、書き換える口と消す口は無い（7.2）。

**改ざんの検知**

データのディレクトリを書けるのは、デーモンのUnixユーザーだけで、管理のサーバーが破られても、過去の記録を、消すことも、書き換えることもできない（新しい偽の記録は、足せる。3.6の「デーモンが守る規則」の限界）。それでも、デーモンのユーザーと、OSの管理者は、保存先のファイルを書き換えられる。そこで、見つける仕組みを、2つ重ねる（案）：保存先の中の鎖と、保存先の外に書き出す鎖の頭。2つは補い合う。

- 保存先の中の鎖：`Store.VerifyAudit` が、すべての記録を初めから読み、次を確かめる：記録として読めること、番号が1から（ログイン履歴の古い記録を消した後は、鎖の始まりの記録から。下記）続くこと、各記録の `prev` が、1つ前の記録のハッシュであること、ログごとの最後が、表の頭と同じこと、表の版7以上の保存先は、`heads` の行が、各ログの表の頭の行と同じこと（`audit log "activity": the row of the head for the export is not the head in the table`）、表の版6以上の保存先は、アクティビティログに記録が1件以上あること（`store.create` か `store.upgrade` が、記録1にあるので、記録も表の頭も無いのは、すべてを落とした書き換え。ログイン履歴は、ログインの無い保存先が記録を持たないので、空でもよい）。記録1の操作が、どちらであるかは、確かめない（下記の「保持の期間と個人の情報」）。問題は、`audit.ErrBroken` を包み、ログ・記録の番号・エンジンのイベントの番号・理由を示す（例：`audit log "login": record 12 (event 345): prev is not the hash of record 11`）。デーモンの印は、飛ばす（`0x00` で始まるのに、印の形でないイベントは、記録として読めないとして、断る）。読む失敗と、`ctx` の終わりは、そのまま返す。
- 外に書き出す鎖の頭（デーモンの `ExportHeads`。3.6の「頭の書き出し」）：鎖の頭を、保存先の外に、1行ずつ書く。形は `audit head <ログ> <番号> sha256:<64桁の小文字の16進数>`（例：`audit head activity 1245 sha256:…`）。個人の情報も、時刻も入らない。1行は、改行を含めて113バイトまで。デーモンは、頭の行を、表 `heads` の行の値から、そのまま書く（形だけを確かめる：1〜255バイトの、印字できるASCII）。書き出すのは、始めに、記録のあるログの頭を1回、そのあと、1分ごとの合図が来るたびに、前に書いたものから変わった頭だけ、止めるとき（動いている要求が終わった後）に、取り消しから切り離した5秒の期限で、もう1回。書けなかった頭は、次の回で書き直す。書き出しが失敗しても、操作は止めない（エラーは、デーモンのログに出る）。
- プロセスへのつなぎ（案）：デーモン（`whiteroom-db serve`）の標準エラー（systemd では journald）に書く。頭は、1分に2行まで（ログごとに1行）なので、journald の数の制限（1つのサービスで30秒に10000行）に当たらない。デーモンのログの行（日時つき）も、同じ標準エラーに出る。`whiteroom serve admin` は、頭を書かない：管理のサーバーに残すと、破られたときに、止められるため（決定済み。13章。3.6の「頭の書き出し」）。止めるときは、管理のサーバーを先に止め（HTTPのサーバーと `Publisher` を止め、数えた失敗の記録（`FlushSuppressed`）を書いた後に、保存先を閉じる）、それからデーモンを止める：デーモンの最後の頭に、すべての記録が入る。書き出し先が詰まったときは、頭の書き出しだけが止まる（コミットと読みは続く）。読む側の終わったパイプのときは、デーモンは動き続け、頭は、デーモンを動かし直すまで、書かれない（3.6の「頭の書き出し」）。デーモンは、止めるとき、書き込みが返るのを待つので、返らないときは、サービスの管理が、プロセスを終わらせ、最後の頭は書かれない（3.6の「頭の書き出し」。6.12の286）。
- 外に書き出した頭で確かめる：書き出した行を `audit.ParseHead` で読み、`VerifyAudit` の `anchors` に渡す。各頭は、その番号の記録のハッシュと同じで、ログが、その番号より先まで続いていること。確かめる道具（コマンド）は、`whiteroom doctor`（9.4）：`-heads` に、デーモンの標準エラーのログか、`whiteroom backup` の標準出力を、そのまま渡せる（`audit head ` を含む行だけを使う）。写しから戻した保存先では、写しを取ったときまでの頭を渡す（写しの後に書き出された頭は、戻した鎖に無いので、問題として示される）。
  - `ParseHead` は、行の前に何が付いていても（journald が付けた時刻やプロセスの名前など）、行の末尾の `audit head <ログ> <番号> sha256:<64桁>` を読むので、頭の形の行は、だれが書いたものでも読める。外の頭は、whiteroom のサービスが書いた行だけから取る（journald なら、`_SYSTEMD_UNIT` などの、書いたサービスを示す項目で絞る）。
  - 偽の頭の行を足されても、できるのは、`VerifyAudit` を失敗させる（誤った警報）ことだけで、書き換えは隠せない（隠すには、保存先を書ける力が要る）。渡す頭は、最後の1つだけにせず、古い時点のものも含める：古い本物の頭は、書き換えた鎖に合わないので、書き換えが見つかる。最後の1つだけだと、書き換えた鎖に合う偽の頭を足されて、見逃す。
- 鎖の始まり（案。#70 の計画への答え（2026-11-23）で決めた。6.12の233）：ログイン履歴の古い記録を、`whiteroom-db compact`（下記の「保持の期間と個人の情報」）が消すと、ログの最初の記録は、番号1でなくなる。そこで、残る最初の記録の番号 K（2以上）と、その1つ前の記録のバイト列のSHA-256（P）と、書いた時刻を、表 `chains`（3.4の「表」）の行（キーは `login`）に置き、削除のイベント（3.6の「印」の 0x02）と一緒に、1回の書き込みで書く。`VerifyAudit` は、これがあれば、次のように確かめる：最初に読む記録が、K より後なら、問題（`the chain starts at record K, which is not there`）。K より前の記録が、まだ残っていることがある（削除の途中で止まった後、次の `compact` まで）ので、通す：最初の記録が1なら、`prev` を持たず、そうでなければ、`prev` を持つことを確かめ、それ以降は、いつもどおり、K まで確かめる（最初の記録の `prev` は、何と照らせるものが無いので、確かめない）。その記録を、次の `compact` が落とすのは、番号が続き、最後が記録 K-1 でハッシュが P で、同じ番号 K と P を持つ、削除のイベントがあるときだけ：そうでなければ、証拠として残り、`VerifyAudit` が、続かない所を、示す（3.6の「保守の口」）。記録 K の `prev` が、P でなければ、問題（`prev is not the hash that the chain start has of record K-1`）。ログが、記録 K-1 で終わるなら、そのバイト列のハッシュが、P でなければ、問題。K-1 より前で終わるなら、問題。記録が1件も残らないとき（すべて消した）は、表 `meta` の頭（`loginLog`）が、記録 K-1 と P を持つことを確かめる（無い・K-1 より小さい・K以上・ハッシュが違うは、いずれも問題）。ただし、穴の行が、K から、頭の番号までを、頭のハッシュで覆うとき（下記の「修復が記した穴」）は、頭が K 以上でも、穴の行で通し、頭のハッシュと P の比べは、行わない（穴が、その間を覆うため）。`activity` の名前の行と、読めない行は、問題（アクティビティログは、消さない）。行は、書き手が書けない（3.6の「デーモンが守る規則」）。表の版7以下の保存先には、行が無く、番号1から、いつもどおり確かめる。
- 認めた切れ目（案。#70 の計画への答え（2026-11-23）で決めた。6.12の131・289）：鎖が切れている所を、操作する人が調べた後、`whiteroom-db accept-break -log LOG -record N`（3.6の「保守の口」）が、認める。切れている所とは、`VerifyAudit` が、そのログを、イベントの順にたどって、失敗する記録 N のうち、番号が、前の記録の番号に1を足したもので、`prev` が、前の記録のハッシュでないもの（前の記録は、同じログの、1つ前に読んだ記録）。番号が続かない記録は、穴で、切れ目ではなく、認めない（案。#70 のレビューへの答え（2026-11-24）で決めた）。修復が作る穴は、修復が記す（下記の「修復が記した穴」。#144）。`LOG` と `N` は、`whiteroom doctor` の問題の行（`audit log "login": record 7 (event 31): prev is not the hash of record 6`）のもの。残る跡は、3つ：表 `chains` の行（キーは、ログの名前・0x00・N。値は、記録 N の、保存したバイト列のSHA-256と、認めた時刻）、イベント 0x03（と、同じコミットの印）、標準出力の1行（`accepted the break at record N of the audit log LOG in DATA; whiteroom doctor checks the log again from it`）。記録は、書き換えず、落とさず、足さない。デーモンを止めて動かし、ソケットには出さないので、破られた管理のサーバーは、自分の書き換えを、認められない。
  - `VerifyAudit` の動き：その行があり、行のハッシュが、いまの記録 N のバイト列のSHA-256と同じなら、記録 N の、`prev` の確かめを飛ばして、続ける。行が使われるのは、次の3つが、すべて合うときだけで、`VerifyAudit`・`compact`・`accept-break` が、同じ規則を使う（案。#70 のレビューの後）：(a) 行のハッシュが、いまの記録 N のバイト列のSHA-256と同じ。(b) 記録 N が、そのログの最初に読む記録でも、鎖の始まりの記録 K でもない。(c) 記録 N の番号が、前の記録の番号に1を足したもの。そのため、認めた記録の複製（同じバイト列を、後で、もう1度足したもの。フォーク）と、先頭が失われた後の最初の記録は、行があっても、通らず、問題のまま。穴は、切れ目でないので、行があっても、通らない。後ろの記録のハッシュと、頭と、外の頭は、いつもどおり確かめる。告げる文は、上記の「告げること」で、使われた切れ目だけを告げる。鎖の始まりより前の記録の切れ目（記録が、まだあるとき）は、通すが、告げない。
  - 認めた記録の書き換え：記録 N が、認めた後に、書き換わると、行のハッシュが合わず、認めなかったことになり、問題に戻る。もう1度認めると、行は、新しいハッシュに置き換わり、2つ目のイベント 0x03 が足される（最初のイベントも、跡として、残る）。記録 N の書き換えは、記録 N+1 が持つ、記録 N のハッシュも変えるので、記録 N+1 も、切れ目になり、続けて、認める。書き換わっていない記録を、もう1度認めることは、断る。ほかの記録の書き換えは、これまでどおり、見つかる。
  - 断るもの（何も書かない。3.6の「保守の口」に、文と順）：鎖の行が読めない・鎖の始まりより前・記録が無い・同じ番号が2つ以上ある・修復が記した穴の次の記録（`record N comes after the records A to B that whiteroom-db repair dropped: there is no break to accept`。`VerifyAudit` が通す記録で、切れ目ではない）・最初に読む記録（記録1か、削除の後に残る最初の記録か、先頭が欠けたログの最初の記録）・穴（番号が、前の記録に続かず、穴の行も無い記録。`record N does not follow record M in number: a gap, which a lost record leaves, is not a break that can be accepted: whiteroom-db repair records as a hole a gap that it makes, and this one stays a problem`）・前の記録に続く記録・認めてある・表の版が古い（書き手が繋いで、表の版を9にしてから）。
  - 認めるのは、調べた人の判断で、書き換えか、エンジンの傷かは、`VerifyAudit` が、区別しない。番号で指せる、読める記録の切れ目だけ：記録として読めないイベントは、番号を持たず、認められず、`whiteroom doctor` が、問題として示し続ける。失われた記録は、戻らず、その後の記録も、認めない（案。#70 のレビューへの答え（2026-11-24）で決めた）：`whiteroom doctor` は、番号が続かない記録を、問題として、示し続け、失った記録を指す外の頭は、告げることにならず、問題のまま。修復（`whiteroom-db repair`）が、自分で作る穴は、記し（下記の「修復が記した穴」）、記録として読めないイベントは、`-drop-unreadable-records` で、落とせる。修復が作らない穴（前からある穴）と、最初に読む記録の切れ目と、読めない鎖の行は、直さず、問題のまま（#147。6.12の289・290）。
- 修復が記した穴（案。#144 の計画への答え（2026-11-25）で決めた。6.12の131・290）：エンジンの傷で、記録のイベントを失い、`whiteroom-db repair`（3.6の「保守の口」）が、それを落としたとき、ログの記録の番号が飛ぶ（記録 A から B までが、無い）。修復は、自分が作った穴を、直した世代の中に、2つの跡で記す：表 `chains` の行（キーは、ログの名前・0x01・A。値は、B と、記録 B の、保存したバイト列のSHA-256と、記した時刻。3.4の「表」）と、イベント 0x04（と、同じコミットの印。3.6の「印」）。記録 B は、失い、ハッシュだけが残る：穴の次の記録の `prev` が指すもの（ログの終わりの穴は、表 `meta` の頭のハッシュ）。穴を記す口は、修復だけ：書き手は、行を書けず（3.6の「デーモンが守る規則」）、`accept-break` は、穴を認めない（上記）。
  - `VerifyAudit` の動き：鎖を、イベントの順に歩き、次に見るはずの番号（前の記録の次。無ければ、鎖の始まりの K。それも無ければ1）より先の番号の記録に会ったとき、その番号を `first` に持つ穴の行があり、記録が、その行の `last` の次で、`prev` が、その行のハッシュのときは、その穴を通して、続ける。行より、1つ広い穴も、狭い穴も、ハッシュの違う行も、別のログの行も、通さず、問題のまま（`VerifyAudit`・`compact`・`accept-break` が、同じ規則を使う。`dbwire.HoleBefore`）。ログの終わり：表 `meta` の頭が、最後に読んだ記録より先を指すとき、`first` が、次に見るはずの番号、`last` が、頭の番号、ハッシュが、頭のハッシュの穴の行があれば、通す。書き手が、続けて記録を書くと、その記録の `prev` が、頭のハッシュなので、穴は、途中の穴になり、通り続ける。
  - 告げること：通した穴は、問題でなく、告げる（下記の「告げること」。終了コードは変わらない）。
  - 外の頭（案。#144 の計画への答え（2026-11-25）で決めた）：失った記録を指す、保存先の外の頭は、穴を記しても、告げることにならず、問題のまま：頭は、失った記録が、あったことの、保存先の外の証拠で、穴の行は、記録が、無くなったことを、記すだけで、頭を、照らせるようにはしないため。切り詰めで落とした記録を指す頭も、同じ。
  - 記録が残らないログ：アクティビティログは、記録が1件以上あることを確かめる（上記）ので、記録を1つも残さない修復は、穴を記しても、`whiteroom doctor` が、問題として示し続ける（#147）。ログイン履歴は、記録が無くてもよいので、鎖の始まり K の後の、すべての記録が失われ、穴の行が、K から、頭の番号まで、頭のハッシュで覆うときは、頭のハッシュと、鎖の始まりの `prev` の比べを、行わず、穴の行で通す（穴が、その間を覆うため）。
  - `compact` と穴：穴を通した記録は、認めた切れ目で通した記録と同じに、残る最初の記録にならず（切り捨てが、その1つ前に戻る）、穴の行は、残る。前の削除が残した記録の最後と、鎖の始まりの記録 K の間の穴は、`compact` は、通さず、そこで止まる（`VerifyAudit` は通すので、`compact` が、厳しい。安全な側。3.6の「保守の口」）。
  - 記せない穴と、前からある穴：穴の次の記録の `prev` が、`sha256:` と、小文字の16進数64桁の形でないときは、行に置くハッシュが無いので、修復は、行も、イベントも書かず、`hole:` の行に `not recorded` と示し、`whiteroom doctor` は、その穴を、問題として示し続ける（#147）。修復は、飛んだ記録の数以上のイベントを、その間で落とすときだけ、その飛びを穴として記し（1つの記録は、1つのイベント。ログの終わりは、頭が指す、最後に読んだ記録より後の記録の数と、残る状態の最後のイベントまでに落とすイベントの数を比べ、切り詰めで落とすコミットのイベントは、数えない）、それより少なければ、飛びの全体を、前からある穴とする（見分けの限りは、3.6の「保守の口」の `repair`）。修復の前から、保存先にあった穴（番号が続かない記録）は、修復も、記さず、`gap:` の行に示すだけで、`whiteroom doctor` が、問題として示し続ける（#147。6.12の289・290）。穴の行が、読めないときは、`audit log "LOG": a row of the table chains for a hole cannot be read` の問題で、`compact` は、そこで止まり、`accept-break` は、断る。
- 告げること（案。#70 の計画への答え（2026-11-23）で決めた）：`VerifyAuditNotes(ctx, anchors, note)` は、確かめの結果が問題でなくても、知っておくべきことを、文で `note` に渡す（`VerifyAudit` は、渡さない形）。順は、鎖の始まり（読む前）・認めた切れ目と、穴（読む順。ログの終わりの穴は、記録を読み終えた後で、前の削除が残した記録の前）・前の削除が残した記録・照らせなかった頭。問題があって失敗するときも、始まりと切れ目と穴の文は、渡す（残した記録と、照らせなかった頭の文は、問題が無いときだけ）。文は、ログの名前・番号・時刻（UTC、RFC 3339）・数だけを持ち、記録の中身を、入れない：
  - `audit log "login": the records before record K were deleted at TIME; the log is checked from record K`
  - `audit log "login": the records A to B are still in the store after the deletion of the records before record K; the next whiteroom-db compact removes them`（1件なら `record A is`）
  - `audit log "LOG": the break at record N was accepted at TIME; the log is checked again from that record`
  - `audit log "LOG": the records A to B were lost and dropped by whiteroom-db repair at TIME; the log is checked again from record B+1`（1件なら `record A was lost and dropped by …`）
  - `audit log "LOG": the records A to B were lost and dropped by whiteroom-db repair at TIME; the log ends with record A-1`（ログの終わりの穴。記録が1つも残らないログは、`the log has no record left`）
  - `N of the heads kept outside the store name records that the store no longer has, so they are not checked`（1件なら `1 of the heads kept outside the store names a record that the store no longer has, so it is not checked`）
  - 出力：`whiteroom doctor` は、これを、標準エラーに、`whiteroom doctor: note: TEXT` と書き、数えず、終了コードも変えない（9.4の「`whiteroom doctor`」）。
- 外に書き出した頭と、消した記録（案。#70 の計画への答え（2026-11-23）で決めた）：消した後も、番号 K-1 の記録を指す頭は、P と照らす（合わなければ、問題）。K-1 より前の記録を指す頭は、記録が、もう無いので、照らせず、数だけを、1つの文で告げる（上記）。まだ残っている記録（削除が止まったとき）を指す頭は、いつもどおり、照らす。ログの範囲の中の記録を指すのに、ログが、その記録を持たない頭（ログの読みが、穴で、先に失敗するので、外の頭の確かめを直接呼ぶテストでしか、起きない）は、問題（`audit log "LOG": the head kept outside the store is record N, which the log does not have`）：認めた切れ目は、これを、告げることに、変えない。

見つけるもの（案）：

- 保存先の中の鎖だけ（`anchors` なし）：記録のバイト列の書き換え・表の版7以上の保存先の、`heads` の行の書き換え・途中の記録を落とすこと・表の頭の書き換え・記録として読めないイベント・表の版6以上の保存先の、アクティビティログのすべての記録と表の頭を落とすこと（`store.create` か `store.upgrade` が残るはずなので。2つのログのすべてを落としても、同じ）。
- 外に書き出した頭も使う：上に加えて、鎖を作り直して、表の頭も合わせた書き換え（その番号までの記録の、内容・順・件数。その番号の記録のハッシュが変わるため）・その番号より前の記録を落とすことと足すこと（ログイン履歴を、鎖の始まりの行ごと書き換えて、前から落とすことは、見つからない：下記の「消した記録」）・その番号より後の末尾を落として、表の頭を合わせること・ログごと落とすこと（ログイン履歴をログごと落とすことは、外の頭でだけ見つかる：ログイン履歴は、空でもよいので、保存先の中だけでは、落としたのか、記録が無かったのか、分からない。アクティビティログは、上記のとおり、保存先の中だけで見つかる）。

見つけないもの（限界。案）：

- 最後に書き出した頭より後に足した記録の書き換えと削除：書き出しは、変わったときに1分に1回（と、止めるとき）なので、最大1分ほどの間の書き換えは、外の頭では見つけられない（止めるときの書き出しが無かったときは、もっと）。
- 外の写しも書き換えられる人の書き換え：OSの管理権限を奪われると、保存先も、手元の journal も書き換えられる（7.2の注意）。手元の journal だけでは、権限を奪った人が、両方を書き換えられる。
- 鍵の無い鎖なので、保存先を書ける人が、新しい記録を、正しい鎖で足すこと（偽の記録を足す成りすまし。書き換えではない）。鍵つきの鎖は、まだ無い（6.12の236）。
- 消した記録（案。#70）：ログイン履歴を、前から消すと、K-1 より前の記録を指す外の頭は、記録が無いので、照らせない（数を告げる）。保存先を書ける人が、鎖の始まりの行を進めて、さらに前の記録を落としても、鎖としては通り、その記録を指す外の頭が、告げられる数に回るだけになる。見つける手がかりは、`compact` の標準出力の行と、削除のイベント 0x02 が持つ、残る最初の記録の番号と切り捨ての時刻と、告げられる数の増え方。ログイン履歴を期間で消すことと引き換えに、引き受けるもの。
- 穴の行の判断（案。#144 の計画への答え（2026-11-25）で決めた）：穴の行は、修復が足すものだが、保存先を書ける人（デーモンのユーザーと、OSの管理者）も、同じ行を足せる。記録の途中を落とし、その幅と、次の記録の `prev` が指すハッシュで、行を足せば、`VerifyAudit` は、その穴を通し、番号が飛ぶ問題が、告げることに変わる。新しい点は、鎖を作り直さずに、落とした記録を、穴として記せることだけで、鎖を作り直した書き換えと同じに、外の頭は、それを見つける（失った記録を指す頭は、問題のまま）。跡は、行の時刻と、イベント 0x04 と、告げる文に、残る。管理のサーバーは、行を書けない（3.6の「デーモンが守る規則」）ので、破られても、穴を記せない。
- 認めた切れ目の判断：認めるのは、操作する人の判断で、`VerifyAudit` は、その切れ目が、エンジンの傷か、記録の書き換えかを、区別しない。認める前に、調べておく（認めた後は、その記録の番号と `prev` を、確かめない）。認めた後に、その記録が書き換わると、問題に戻る。

外への退避（運用で使う。案）：書き出した行を、権限を奪われても書き換えられない場所に置くには、次のどちらか（か、両方）を、運用で使う。whiteroom は、どちらも用意しない。どちらも、実際のマシンでは動かしておらず、出典の文書（下記の「確かめた事実（#47）」）だけを見た。

- journald の封（Forward Secure Sealing。FSS）：`journalctl --setup-keys` で鍵の組を作り、封をする鍵は、そのホストに残し、検証の鍵は、外に置く。封をする鍵を替える間隔（`--interval`。既定は15分）が短いほど、見つけられない書き換えの時間が短い。`journalctl --verify` に `--verify-key` を渡して、ジャーナルのファイルが本物かを確かめる。`journald.conf` の `Seal=` は、既定で有効で、鍵の組があるときに封をする。
- 別のマシンへの転送（syslog）：書き出した行を、別のマシンに送る。RFC 5424 の syslog は、届いたことを確かめず、書き換えも繰り返しも防がず、攻撃する人は、記録を途中で捨てて、行いを隠せる。署名つき syslog（RFC 5848）は、送り手の確かめ・書き換えの検出・繰り返しへの耐性・順番・欠けたメッセージの検出を足す仕組み。頭の1行は、113バイトまでと小さい（受け手が必ず受け付ける大きさは、見出しも含めて480オクテット。RFC 5424）。

**保持の期間と個人の情報**

保持（案）：

| ログ | 残す期間 | 古い記録の消し方 |
| --- | --- | --- |
| ログイン履歴 | 1年 | `whiteroom-db compact` が、1年より古い記録を落とす（下記） |
| アクティビティログ | 保存先の履歴（3.4）と同じだけ | 消さない（履歴から消す操作と合わせて決める。6.12の125） |

- 消す処理（案。#70 の計画への答え（2026-11-23）で決めた。6.12の233）：`whiteroom-db compact`（デーモンを止めて動かす。3.6の「保守の口」）が、圧縮の書き直し（3.5の「保守モード」）で、ログイン履歴の、1年より古い記録を落とす。ほかには、何も落とさない：アクティビティログの記録は、消さない。期間（1年）は、設定で変えられない（フラグも、設定の項目も無い）。
  - 古さ：記録の古さは、記録の `at` でなく、同じコミットの最後に、デーモンが付けた印（3.6の「印」）の時刻で決める（`at` は、管理のサーバーの中の `store` が付けるので、破られると偽れる）。切り捨ての時刻は、コマンドを動かした時刻と、最も新しい印の時刻の、早いほうの、暦で1年前（UTC）。印が、切り捨ての時刻より前の記録が、古い（同じ時刻は、残す）。最も新しい印は、書き手のコミットの印だけ：削除（イベント 0x02）と、認めた切れ目（イベント 0x03）と、同じコミットの印は、その跡の時刻なので、数えない（案。#70 のレビューの後）。書き手は、削除を頼めず、切り捨ての時刻も動かせない。
  - 前のほうだけ：番号の順に、最初の、古くない記録（か、印の無い記録）まで。後ろの記録は、古くても、残す。
  - 手順と、止まる所と、標準出力は、3.6の「保守の口」の「`compact` が落とすもの」。消した後の鎖は、下記の「改ざんの検知」の「鎖の始まり」。
  - 1つの記録は、1年と、`compact` を動かす間隔の分まで、残る。間隔は、運用が決める（3.5の「運用の制約」）。OWASP は、決めた期間を過ぎて持たないことを求める：その分だけ、期間を超えて残る。法令・規制・契約の義務が、期間を決めるときは、その義務に合わせて、間隔を決める。最も新しい印（書き手のコミットの印）が、コマンドの時刻より古い保存先（新しいコミットが、長く無い）は、最も新しい印から1年前までしか、消さない：`compact` を、続けて何度動かしても、`accept-break` の後でも、保守のコマンドの時計が進んでいても、同じ。
  - 表の版が9より古い保存先は、何も落とさず、そう言う（3.6の「保守の口」）：書き手が繋いで、表の版を9にした後の、次の `compact` が、落とす（#144 で、版が8から9になったので、版8の保存先も、書き手が繋ぐまで、落とさない）。
  - 見積もり：ふつうの使い方で、1年で約170MB（上記）のログイン履歴は、`compact` のたびに、1年より古い分が消える。200,000件の記録の保存先で、`compact` は、落とすものが無いとき約0.4秒、半分を落とすとき約0.9秒（3.6の「測った値」）。
- 消せる形：ログごとに別の鎖にしたので、ログイン履歴だけを、古いほうから消せる。消した後は、残る最初の記録から確かめる：そのために、鎖の始まり（残る最初の記録の番号と、その1つ前の記録のハッシュ）を、表 `chains`（3.4の「表」）に持つ（下記の「改ざんの検知」の「鎖の始まり」。6.12の233）。表の版6以上の保存先のアクティビティログは、記録が1件以上あることも求める（`store.create` か `store.upgrade` が、記録1にあるため）が、記録1の操作が、どちらであるかは、確かめない：鎖を作り直せる人は、`store.create` の記録も偽って足せるので、確かめても守りが増えず、番号が1から続くことと `prev` の確かめは、すでにある。アクティビティログは、消さず、鎖の始まりを持たない（行があれば、問題）ので、この確かめは、変わらない。消した後の、ログイン履歴の最初の記録の操作も、確かめない（同じ理由）。
- ログイン履歴を1年にしたのは、年に1度の見直し（更新の時期など）の調べに足りるため。90日では、足りないことがある。

個人の情報（案）：

- クライアントのアドレス（そのまま）・User-Agent（512バイトまで）・打たれたログイン名は、ログイン履歴だけが持つ。アクティビティログと、セッションの行（7.3）は、持たない。個人の情報を、ログイン履歴の1か所にまとめ、期間で消せるようにするため。アクティビティログの記録に `client`・`login`・`session` を入れると、`Record.Check` が断る（上記の「記録の形」。書く側の取りこぼしを、保存先が見つける）。アドレスは、そのままなので、調べるときに使える。
- アドレスは、9.6のクライアントのアドレスの決め方のとおり。リバースプロキシを `TrustedProxies` に入れ忘れると、全員がプロキシのアドレスになり、プロキシでないアドレスを入れると、偽られたアドレスが残る（9.6の「リバースプロキシ」の「設定の責務」）。
- 打たれたログイン名（残る弱点。案）：ログインの失敗の記録は、打たれたログイン名（正規化して、64バイトまで）を持つ。ログイン名の欄にパスワードを打った人がいると、それ（正規化した、先頭の64バイトまで）が、ログイン履歴に残る。応答は、理由によらず同じなので（9.6）、打った人にも、残ったことは見えない。読めるのは `logs.view` を持つ人（admin だけ。7.3）で、残る期間は、保持の期間の1年と、`compact` を動かす間隔の分まで（上記）。存在しないログイン名への試し（`admin` など）と、間違ったパスワードと、無効のアカウントを、あとで分けられることと引き換えに、承知のうえで、仮に決めた。減らす方法は、6.12の235。
- アクティビティログが持つ、アカウントのログイン名（残る弱点。案）：アカウントの操作の記録は、ログイン名（変える前と後。消す前）を持つ。アクティビティログは、保存先の履歴と同じだけ残す（上記）ので、アカウントを消した後も、そのログイン名が残る。個人の情報として数えたのは、ログイン履歴のアドレス・User-Agent・打たれたログイン名だけで、これは、期間（1年）で消す対象に入らない。消すには、記録を書き換える必要があり、その記録の後ろの鎖と、外に書き出した頭が、合わなくなる。どう消すかは、6.12の239。
- 文書の値の引用（残る弱点。案）：失敗したビルドの `error`（2048バイトまで）は、サイトの問題の文（`content.Errors`）を含み、スラッグなど、文書の値を引用することがある。それは、アクティビティログに残り、文書を履歴から消しても（6.12の125）、記録からは消えない。メディアの追加の `fileName` は、アップロードされたファイルの名前（整えた後）で、同じく残る。消し方は、6.12の239。
- 3.5の「個人情報の削除」の表の、ログ・チェックポイント・バックアップは、記録にも当たる。記録を消しても、バックアップの写しには残る。
- 暗号化して鍵を消す形（crypto-shredding）は、候補（3.5の「個人情報の削除」。6.12の138）。

**記録できなかったとき**

OWASP の Logging Cheat Sheet は、記録の仕組みの失敗が、アプリケーションの動きを止めないようにすることを求める。一方、変更の記録が無い変更は、残したくない。そこで、記録を、変更と同じ書き込みに入るものと、単独のものに分ける（案）。

- 変更と同じ書き込みの記録（保存の操作・公開の操作・アカウントの操作・セッションの行を書く操作）：記録を書けなければ、操作も失敗する（何も変わらない。3.4の「壊れない書き込み」）。外から来る値は、切ってから入れるので（上記の「記録の形」）、記録の形が合わずに失敗することは、ふつう無い。
- 単独の記録（変更の無い記録）：ログインの失敗・HTTPの側で断ったログイン・無効なトークン・まとめ（ログイン履歴）と、ビルドの結果（アクティビティログ）は、別の `Update` に書く。要求の取り消しから切り離し（`context.WithoutCancel`）、保存先を5秒まで待つ。書けなくても、応答も、ビルドの結果も、公開も変えない（401や429のまま。ログインの応答が、記録の成否で変わると、記録の書けない状態を、外から探れるため）。書けなかったことは、`Manager.OnRecordError`（ログイン履歴）と `publish.Options.OnRecordError`（ビルドの結果と、`Rollback` の2件目）に渡した関数が受け取る。管理用のサーバーは、前者を `Config.ErrorLog` につなぎ、`cannot record login.failure: <理由>` を1行書く（`token.failure` も。9.6の「記録」。1分に70行まで：失敗の記録の上限（上記）の、2つの枠の数の和）。後者は、`whiteroom serve admin`（9.4）が、同じエラーのログにつなぐ（`the record of <操作> was not written: <理由>` を1行。日時つき）。枠に入ったのに、書けなかった失敗は、その数（次の `login.suppressed`。上記）に足すので、ログインの失敗の記録は、保存先が書けない間は、エラーのログと、その数にしか残らない。
- 保存先の書く口が、別の `Update`（長い取り込みなど）で塞がっているとき：HTTPの側で断ったログイン（8KiBを超えるパスワード・429・503。33個目のログインの503も）は、答える前に記録を書く（ログインの順番には待たせない）ので、記録を書く要求は、最大5秒待ち、その分、答えが遅れて、`cannot record login.failure: context deadline exceeded` が書かれる。待たされるのは、失敗の記録の上限（上記）の枠の中の、記録を書く要求だけで（比べた失敗は1分に60件、断りとトークンは10件）、超えた分は、数えるだけで、保存先に何も書かず、待たない。書けなかった失敗も、枠を使ったままなので、保存先が塞がっていても、待つ要求は、1分に70件を超えて増えない。答えの内容は変わらない（9.6）。
- 権限で断った要求の記録（`access.denied`）：管理のAPIが、別の `Update` に書く。要求の取り消しから切り離し、保存先を5秒まで待つ。書けなくても、答え（403）は変えない。書けなかったことは、`Config.ErrorLog` に `cannot record access.denied: <理由>` と書き、その断りを、記録しなかった断りに数える（次の記録の `suppressed` に入る）。
- 公開の仕組みの、人の操作（`Rebuild`・`Rollback`・`Resume`）：先に記録を書き、書けなければ、何もせず、エラーを返す（`cannot record <操作>: <理由>`）。動く前に書くので、記録と動きの間でプロセスが止まると、動かなかった操作の記録が残りうる。`Rollback` は、記録の後に失敗したとき（プロセスが動いている間）だけ、`failed` の記録を、もう1件書く。
- ビルドの記録：ビルドが終わって、公開と状態（`Status`）の更新の後に、別の `Update` で書く。そのため、公開の直後にプロセスが止まると、そのビルドの記録は残らない。保存先が5秒より長く塞がっていると、記録を失い、`OnRecordError` に知らせる。記録を書く間、`Publisher` は、次のビルドを始めない（6.12の177）。
- 鎖の頭の書き出し：失敗しても、操作は止めない（上記の「改ざんの検知」）。

**記録の無い書き込みを断る**

- 規則（案）：保存先の `Update` は、関数が成功した後に、記録のほかに何かを書き（`Tx.Changed`）、記録を1件も足していないトランザクションを、何もコミットせずに、`ErrUnrecorded`（`the transaction writes but adds no audit record`）で失敗させる。版の番号も、記録の番号も進まない。関数がエラーを返したときは、そのエラーを返す。数えるのは記録の件数だけで、どちらのログの、何件目でも通る。
- 通るもの：記録だけの `Update`（ログインの失敗・ビルドの結果・何も変えなかった成功の記録など）と、何も書かない `Update`（読むだけ・同じバイト列の `Put`・正しい索引の `RebuildIndex`）。
- 守るもの：新しい書き込みの道を足して、記録を忘れると、その書き込みが、すぐに失敗する（構造で守る）。記録を残さずに変更できる経路を、作らないための、保存先の側の守り。デーモンも、行を足す・書き換える・消すコミットに、監査イベントを求める（`a commit that puts or deletes a row needs an audit event`。3.6の「デーモンが守る規則」）：`store` を通らない書き込みも、記録を持たずには通らない。
- 抜け道は、テストのためのものも無い。保存先の口で直接書く道具とテストは、`store.write` の記録（`actor` は、`system` か、書いた人）を足す（`DropIndexRow` もそう。3.4の「テスト」）。本番のコードは、`store.write` を書かない。
- 例外：
  - 保存先の中の書き込み（作る・表の版の更新）は、`store` の `Update` を通らず、デーモンのクライアントを直接使い、この規則の外だが、自分の記録（`store.create`・`store.upgrade`）を、同じコミットに書く（デーモンの規則は、これにも当たる）。
  - `PutOriginal`（メディアの原本。3.4の「原本」）は、デーモンを通り（`PutOriginal` のメッセージ。3.6の「原本」）、`Update` の外で `files/` に書き、記録を持たない。ハッシュの名前のファイルを足すだけで、書き換える口も消す口も無く（同じ名前は、同じバイト列）、記録を持つメディアの文書（`media.add`・`media.replace`）が指すまで、サイトにも何にも効かない。指されない原本は、回収の対象（6.12の125）。成功した追加と差し替えでは、だれが原本を置いたかは、メディアの文書を保存した記録が、ハッシュ・大きさ・形式で残す。失敗した追加（形式が読めない・検証の問題・食い違い・記録の確かめの失敗）は、記録しない（上記の「記録する操作」）ので、その追加が先に置いた原本（1つ64MiBまで）は、`files/` に残り、だれが置いたかの記録が無い（管理のAPI（9.7）は、知らない形式のファイルを、原本を書く前に断るので、それは残らない）。`media.add` ができる人（author も。7.3の権限の表）が、失敗する追加を続けると、記録されずに、ディスクを埋められる（回数と合計の上限は、いまは無い。6.12の125）。
- 保存先を書く本番のコードは、`internal/edit`・`internal/account`・`internal/publish` と、断った要求の記録だけを書く `internal/admin`（記録だけの `Update`）で、どれも、書き込みごとに記録を足す（`cmd/whiteroom` と `internal/serve` は、保存先を書かない）。

**読む口と費用**

- 記録は、エンジンの監査イベント（3.5）に置く。ディスクのログにだけあり、メモリには数だけを持つ。表にも、索引にも置かない。
- 読む口（`Store.ReadAudit(ctx, f, fn)`）：両方のログの記録を、古い順に、絞り込み `f`（`audit.Filter`）に合うものだけ、`fn` が `false` を返すまで渡す。絞り込みは、ログ・期間（`From` 以上 `To` 未満）・アカウント（`actor` か `account` がそれのもの、または `target` がそのアカウントのもの）・操作（名前か、`.` で終わる接頭辞。`entry.` など）・対象（種類と `id`。どちらかは空でよい）で、空のものは問わない。1つの `View` で読むので、書くプロセスが書いている間も止まらない。読み手として開いた保存先（`OpenReader`）でも読め、ディスクに同期したコミットだけを見る。表の版5以下の保存先は、`ErrNoAuditLog`。記録として読めないイベントに会うと、`audit.ErrBroken` を包むエラーで止まる。イベントは、デーモンの `Events`（読み手の接続のメッセージ）で読む：デーモンが、スナップショットの連番までの、すべてのイベント（印も）を、番号の順に、接続の上に流す（3.6の「バイトの並び」）。
- `Store.AuditHeads` は、記録のあるログの頭を、ログイン履歴、アクティビティログの順に返す。`Store.VerifyAudit` は、上記の「改ざんの検知」。どちらも、表の版5以下の保存先では、`ErrNoAuditLog`。
- 新しい順のページ送りは、管理のAPI（9.7の「ログ」）が、この口の上で作った：毎ページ、ログの全体を（`before` まで）読み、最後の `limit` 件を返す。費用と、読めなくなる時期は9.7の「上限」の「ログを読む口の最悪の形」（6.12の232・246）。
- 費用：絞り込みは、読んだ後に当てるので、毎回、ログの全体を、初めから読む（セグメントを1つずつ、メモリに読む。3.5の「制限」）。測った値：開発のマシン（16のCPU、メモリ30GB、NVMe SSD の ext4）、Go 1.27.3。ログインの失敗の形の記録（JSONで408バイト）200万件を、100件ずつの `Update` で書いた保存先（データのディレクトリは約887MiB）を、`OpenReader` で開いて測った（2026-11-12。保存先がエンジンを、プロセスの中で直接開いていたとき。デーモンを通した `Events` は、測っていない）。
  - 開く：25〜34ミリ秒。
  - すべて読む（絞り込みなし）：約3.7秒。アカウントと接頭辞で絞っても、約3.5秒（絞るのは、読んだ後）。`fn` が先頭の100件で止めれば、約35ミリ秒。
  - 確かめる（`VerifyAudit`）：約4.5秒。
  - 読む間のメモリ（最大RSS）：約211〜223MiB。セグメントを1つずつ読むので、ログの大きさに比例しない。
  - 1件を足す（記録だけの `Update`）：平均1.36ミリ秒、中央値1.30ミリ秒、99%点1.71ミリ秒、最大15.6ミリ秒（3,000回）。ログは、1件あたり約464バイト増える（記録のJSONに、約56バイトが足される）。
  - 文書が多いログ：8KiBの文書を保存した10万回に、1件ずつ記録が混ざった833MiBのログで、10万件を数えるのに0.41秒、デコードして絞るのに0.48秒（エンジンの `Events` で。2026-11-11）。
- 見積もり：記録が数千万件になると、1回に数十秒（200万件の約3.7秒から）。
- 消す処理との関係（案。#70 の計画への答え（2026-11-23）で決めた）：ログイン履歴の、1年より古い記録は、`whiteroom-db compact` が消す（上記の「保持の期間と個人の情報」）ので、ログイン履歴を読む量は、1年分と、`compact` を動かす間隔の分までに、抑えられる。アクティビティログは、消さないので、増え続ける。読む口は、両方のログを読む（上記）。6.12の232。
- 索引を持たない理由：時刻と番号の索引を表に持つと、期間で絞るのが速くなるが、表はメモリに乗り、1件約96バイト（200万件で183MiB。開くのが0.25秒延びる）が、記録とともに増える。攻撃の失敗の記録（上記の上限の中）でも増える。記録そのものを表に置くと、すべての記録がメモリに乗る（1件約400バイト以上）。どちらも、いまは取らない（6.12の232）。

**置き場所**

- `internal/audit`：記録の型（`Record`）・ログ（`Log`）・操作の名前（`Action`。どの操作がどのログのものかを、1か所で持つ）・JSON（`Encode`・`Decode`）・書く前の確かめ（`Record.Check`）・値を切る関数（`Truncate`）・絞り込み（`Filter`）・鎖の頭（`Head`・`ParseHead`）。標準ライブラリと `internal/content` だけを使う。鎖の頭の書き出しは、ここに無い：デーモンの `internal/dbserver` の `ExportHeads` が書く（3.6の「頭の書き出し」）。
- `internal/store`：`Tx.Record`・`Tx.Changed`・`Store.ReadAudit`・`Store.AuditHeads`・`Store.VerifyAudit`・`ErrNoAuditLog`・`ErrUnrecorded`（3.4の「操作」）。記録の番号・前の記録のハッシュ・時刻は、保存先が付け、呼ぶ側は書けない。`internal/store` は、エンジンを開かず、デーモンに繋ぐ（`internal/dbclient`。3.4）。記録の鎖の頭の行は、同じ `Update` で、表 `heads` に置く。エンジン（`internal/logdb`。3.5）は、監査イベントのまま使い、デーモンの印がその間に入る。
- `internal/dbwire`・`internal/dbserver`（案。#70）：鎖の始まりと認めた切れ目の行（表 `chains`）と、削除・認めた切れ目のイベントの形（`dbwire`。3.4の「表」。3.6の「印」）、記録を、`audit.Decode` が読むのと同じ形で読み、`log`・`n`・`prev` を返す `dbwire.ReadRecordID`（`encoding/json/v2`。形は、`internal/store` のテストが、`audit.Record` と揃っていることを確かめる。3.6の「デーモンが守る規則」の「知らないこと」）、ログイン履歴の古い記録を消す `dbserver.CompactLogin`（`whiteroom-db compact`）、鎖の切れ目を認める口（`whiteroom-db accept-break`。`dbserver.AcceptBreak`。削除の `CompactLogin` と、鎖の行の読みと、記録をたどる規則を、共有する）と、壊れた保存先を直す口（`whiteroom-db repair`。`dbserver.Repair`。穴の行と、イベント 0x04 と、記録の読みを、同じ形で使う）は、デーモンの保守で、`internal/audit` も `internal/content` も、import しない（3.6の「デーモンが守る規則」の「知らないこと」）。鎖の始まりと認めた切れ目を読んで確かめるのは、`internal/store` の `VerifyAudit`・`VerifyAuditNotes`。
- 記録を足すパッケージ：`internal/edit`（保存の操作と公開の操作の `Update`）、`internal/account`（ログイン履歴とアカウントの操作。`Manager` は、書けなかった記録を知らせる関数（`OnRecordError`）と、数えただけの失敗の記録を書く口（`FlushSuppressed`）を持つ）、`internal/publish`（ビルドと戻す操作。`Options.OnRecordError`）。`internal/admin` は、`account.Client` を渡し、`LoginRefused` を呼ぶほか、権限で断った要求の記録（`access.denied`）を、記録だけの `Update` で自分で書き（`internal/audit` と保存先を使う）、記録を読む口（`Store.ReadAudit`）を持つ（9.7）。import の向きは、`.golangci.yml` の depguard の規則が正（`AGENTS.md`）。
- 表の版：監査の記録のJSON（`internal/audit`）を変えるときは、表の版を上げる（`AGENTS.md`）。知らないキーを断る読み方なので、前の版のプログラムは、新しい記録を読めない。表の版8は、表 `chains` と、デーモンのイベント 0x02・0x03 を足したとき（#70）に上げた（3.4の「エンジンと設定」）：7以下の保存先は、書き手が繋ぐと、8になる。表の版9は、表 `chains` の穴の行と、デーモンのイベント 0x04 を足したとき（#144）に上げた：8以下の保存先は、書き手が繋ぐと、9になる（修復が穴を記すときは、その世代の中で、8から9にする）。表 `chains` の行は、書き手が書けず（3.6の「デーモンが守る規則」）、削除か、認めた切れ目か、修復の後にだけある（7以下の保存先には、無く、穴の行は、8以下の保存先に、無い）。
- コマンドが足す記録（9.4）：`whiteroom init` は、`store.create`（`system`）・`account.createFirst`（`system`）、`SITE` を取り込むときは、`site.import`（最初の管理者）。`whiteroom account reset` は、`account.reset`（`system`）と `account.setPassword`（そのアカウント）。`whiteroom account delete` は、`account.delete`（`system`）。終わったセッションは、ログイン履歴の `session.end`。`whiteroom build -db`・`whiteroom rollback`・`whiteroom backup`・`whiteroom doctor` は、記録を足さない（読み手のコマンドと、`Publisher` を通らないコマンド）。`whiteroom serve admin` は、書くプロセスとして、管理のAPIとビルドの記録を足す（上記）。

**まだ無いもの**

- 記録を読む画面：打たれたログイン名と User-Agent を、エスケープして見せる（上記の「記録の形」）。記録を読む管理のAPI（`logs.view`。新しい順のページ送りと絞り込み）は、9.7。
- サーバー上のコマンドからの、公開の仕組みの操作の記録（6.12の240）：`Rebuild`・`Rollback`・`Resume` は、`usr_` のアカウントのIDだけを取り（`system` を断る）、操作する人のアカウントが無いコマンドからは、`system` として記録できない。そのため、`whiteroom rollback`（9.4）は、`Publisher` を通さず、記録を書かない。
- アクティビティログの記録を消すこと（履歴から消す操作（6.12の125）と合わせて決める。6.12の233）と、そこに残る個人の情報（アカウントのログイン名・ビルドの失敗の文が引用する文書の値）を消すこと（6.12の239）。ログイン履歴の期間（1年）を、設定で変えられるようにするか（6.12の233）。
- バックアップの記録（`backup`。形だけ決めた。書く口は、いまも無い：バックアップは、読み手のプロセスがするので、保存先に記録しない。コマンドは、標準出力に、写しの場所と、写しの鎖の頭を書く。9.4。6.12の234）。
- アクティビティログの「どこから」（6.12の237）。権限で断った要求の記録は、管理のAPI（9.7）が作った（`access.denied`）。
- `VerifyPasswordFactor` の記録（6.12の238）。
- 修復が直さない、鎖の問題：記録として読めないイベントは、番号で指せず、`accept-break` では認められず、`repair -drop-unreadable-records` が、落とせる（その後の穴は、記す）。前からある穴（番号が続かない記録）と、最初に読む記録の切れ目と、読めない鎖の行と、記せない穴と、記録を1つも残さないアクティビティログは、直さず、`whiteroom doctor` が、問題として示し続ける（#147。6.12の289・290）。鎖の頭の書き出しの強さ（6.12の236）。
