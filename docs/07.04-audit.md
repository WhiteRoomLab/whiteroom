### 7.4 ログイン履歴とアクティビティログ（案）

管理画面にログインする人の出入りと、サイトと管理の側のデータを変えた操作を、保存先（3.4）に記録として残す。ログイン履歴とアクティビティログを実装し、監査にも使えるようにすることは決定済み（7.1）。この節は、その記録の形・鎖・保持・書けなかったときの動きを、仮に決めた規則として書く。記録の型・操作の一覧・鎖の頭の書き出しは `internal/audit` に、記録を足す・読む・確かめる口は保存先（`internal/store`）に作った。記録を読む口（管理のAPI。#48）と、プロセスにつなぐこと（#49）は、まだ無い（下記の「まだ無いもの」）。この節の規則は、「決定済み」と書いたもの（7.1）のほかは、どれも仮に決めたもの（案）。

**目的と状態**

- 目的：だれが、いつ、どこから、何をして、何が変わった（変わらなかった）かを、あとで調べられるようにする（7.1・7.2）。ログインの成功と失敗・セッション・アカウントの管理・文書の変更・公開・ビルドを記録する。7.2の記録対象・同一トランザクションでの記録・通常UIからの編集と削除の禁止・ハッシュチェーンと独立した検証値の保管は、この節の形にした。OWASP の Logging Cheat Sheet（下記の「確かめた事実（#47）」）が挙げる出来事のうち、認可（アクセス制御）の失敗（権限で断った要求）は、まだ記録しない（6.12の237）。
- 作ったもの：
  - 記録の型・操作の一覧・JSON・絞り込み・鎖の頭の行・鎖の頭の書き出し（`internal/audit`）。
  - 記録を足す口・読む口・鎖の頭を返す口・確かめる口と、記録の無い書き込みを断る規則（`internal/store`。3.4の「操作」）。表の版は6。
  - 記録を足す側：保存の操作と公開の操作（`internal/edit`。6.7）、ログインとセッションとアカウントの操作（`internal/account`。7.3）、ビルドと戻す操作（`internal/publish`。4.4）、保存先自身の作成と更新（`internal/store`）。管理用のサーバー（`internal/admin`。9.6）は、クライアントのアドレスと User-Agent を、アカウントの口に渡す。
- 作っていないもの：下記の「まだ無いもの」。

**2つのログ**

| ログ（`log`） | 残すもの | 個人の情報 |
| --- | --- | --- |
| ログイン履歴（`login`） | ログインの成功と失敗（HTTPの側で断ったものも）・ログアウト・セッションの始まりと終わりと、使い続けるセッションの最後の要求・無効なトークン | クライアントのアドレス・User-Agent・打たれたログイン名 |
| アクティビティログ（`activity`） | 保存の操作・公開の操作・アカウントの操作・ビルドと戻す操作・保存先自身の作成と更新 | アドレスも User-Agent も、打たれたログイン名も、セッションのキーも持たない（`Record.Check` が断る。下記の「記録の形」）。アカウントのログイン名（変える前と後）は持つ（下記の「保持の期間と個人の情報」） |

- 2つは別の鎖にする（案）：番号（1から）・鎖の頭・絞り込みが、ログごとに別。個人の情報を、ログイン履歴の1か所にまとめ、ログイン履歴だけを、古いほうから消せるようにするため（下記の「保持の期間と個人の情報」）。
- どちらも、エンジンの監査イベント（3.5の「イベント・操作のID・暗号化の封筒」）として、1つの並びに置く（`log` で区別する）。エンジンの口と、エンジンの形の版（3.5の「ファイルの形」）は、変えていない。

**記録の形**

記録は、空白の無い1行のJSONで、キーは次の順。空の項目は書かない。

| キー | 内容 | 規則 |
| --- | --- | --- |
| `log` | ログ（`login`・`activity`） | |
| `n` | ログごとの番号 | 1から。保存先が付ける |
| `prev` | 同じログの1つ前の記録のSHA-256（`sha256:` と小文字の16進数64桁） | 保存先が付ける。最初の記録には無い |
| `at` | 時刻（UTCのRFC 3339。秒の下は、0でない最後の桁まで） | 保存先が付ける（下記の「番号と時刻と鎖」） |
| `actor` | した人。アカウントのID（`usr_` とULID）か、`system` | 呼ぶ側が渡した値が、そのまま入る（保存先は、形だけ確かめる。決め方は #48。下記の「まだ無いもの」）。空は、アカウントの分からない人（ログインしていない人の試しなど） |
| `action` | 操作の名前（下記の「記録する操作」） | どれか1つのログのもの |
| `result` | 結果の語。空は成功 | 64バイトまで |
| `target` | 何についての記録か：`kind` と `id` | `kind` は、`entry`・`term`・`media`・`author`・`menu`・`form`・`redirect`・`user`（アカウント）・`settings`・`release`。`id` は、その種類のID（6.7）で、`settings` は空、`release` は小文字の16進数16桁 |
| `account` | 関わるアカウントのID | |
| `session` | セッションのキー（表 `sessions` のキーと同じ、トークンのSHA-256の小文字の16進数64桁。7.3） | ログイン履歴だけ。トークンは、キーから求まらない |
| `client` | `addr`（クライアントのアドレス）と `userAgent` | ログイン履歴だけ。`addr` は `netip.Addr` の文字列の形。`userAgent` は512バイトまで |
| `login` | 打たれたログイン名 | ログインの失敗だけ。64バイトまで |
| `operation` | 操作のID（6.7） | 256バイトまで |
| `changed` | その `Update` が、記録のほかに何かを書いたか | `true` のときだけ書く |
| `before`・`after` | 文書の版：`seq` と `hash` | `hash` は `sha256:` と64桁。消した版は `seq` だけ |
| `revision` | リビジョンのID（`rev_` とULID） | |
| `status` | エントリーの状態（6.4.1） | 64バイトまで |
| `detail` | 操作ごとの項目（文字列の対） | 64個まで。キーは、英字で始まる英数字（64バイトまで）、値は2048バイトまで。キーは並べ替えて書く |

例（ハッシュとIDは、例のための値）。エントリーを公開した、アクティビティログの記録：

```json
{"log":"activity","n":1245,"prev":"sha256:71547e237559add83f6c9279fdb5762eafee857a1060e2d97c0316a70cefb6ba","at":"2026-11-12T01:02:03.456789Z","actor":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","action":"entry.publish","target":{"kind":"entry","id":"ent_01JB8W2N5KD3F6H9J1M4P7R2T5"},"operation":"op_01JBG3N6Y6A9D2F5H8K1N4Q7S0","changed":true,"before":{"seq":17},"after":{"seq":18,"hash":"sha256:43cc23fa52b87b4cc1d02b5b114154151d6adddb17c9fddc06b027fa99e24008"},"revision":"rev_01JB8X9Y3ZE5G8K1N4Q7S2V6W9","status":"published","detail":{"publishes":"true","redirect":"rdr_01JBG3N6Z7B0E3G6J9M2P5S8V1"}}
```

間違ったパスワードの、ログイン履歴の記録：

```json
{"log":"login","n":812,"prev":"sha256:71547e237559add83f6c9279fdb5762eafee857a1060e2d97c0316a70cefb6ba","at":"2026-11-12T01:02:03.456789Z","action":"login.failure","result":"wrong-password","account":"usr_01JB8T7H4MA2C5E8G1J4K7N3P6","client":{"addr":"203.0.113.7","userAgent":"Mozilla/5.0 (X11; Linux x86_64; rv:140.0) Gecko/20100101 Firefox/140.0"},"login":"yamada"}
```

- 文字列は、正しいUTF-8で、制御文字を含まない（`detail` の値だけは、改行を含められる）。外から来る値（User-Agent・ログイン名・ファイル名・失敗の文など）は、記録に入れる前に、UTF-8の切れ目で切り、不正なバイトと制御文字を U+FFFD に替える。双方向の制御文字（U+202E など）と、幅の無い文字（U+200B など）は、制御文字（`Cc`）ではないので、残る。記録はJSONなので、形は壊れない。管理画面（#48 の後の段階）が、打たれたログイン名と User-Agent を見せるときは、エスケープする（表示を並べ替える文字を、そのまま出さない）。記録の全体は、65536バイト（64KiB）まで。
- 書く前に確かめる（`Record.Check`）：合わない記録は、何も書かずに断る。エラーの文は、項目の名前だけで、記録の値を出さない（ログイン名の欄にパスワードを打った人がいるため）。アクティビティログの記録は、`client`・`login`・`session` を持てず、持つと、その項目の名前を付けたエラーで断る（個人の情報を、ログイン履歴の1か所にまとめるため。書く側の取りこぼしを、保存先が見つける）。
- 読むときは、JSONの形だけを確かめる：知らないキー・同じキー・型の違う値・不正なUTF-8・後ろに続くデータは断り、値の規則は当てない（ほかのビルドが書いた記録を、読めない記録にしないため。7.3の「保存」の「読み方」と同じ）。
- 入れないもの：パスワード・トークン（セッション・招待・再設定）・それらのハッシュ・アカウントの名前とメールアドレスの値。セッションは、キー（トークンのSHA-256）で指す。OWASP の「Data to exclude」は、セッションの識別子を、そのまま記録せず、ハッシュにした値に替えることを考えるよう求める。
- 値は写さず、指す：文書は、種類・ID・版の番号とハッシュ・リビジョンのID・状態だけを持ち、中身は写さない（中身は、保存先の履歴から読める。3.4）。アカウントの行には履歴が無いので、変えた項目の名前と、ロール・状態・ログイン名・著者プロフィールの紐付けの前と後の値を持つ（名前とメールアドレスは、変えたことだけ）。

**記録する操作**

規則（案）：

- 成功した操作は、1件ずつ記録する。何も変えなかった成功（同じバイト列の保存・すでにその状態の公開・何も変えないアカウントの変更）も、`changed` の無い記録を1件書く（記録だけのコミットを1つ作る）。何も変えなかった操作でも、だれが何をしようとしたかが分かり、「記録の無い書き込みを断る」（下記）とも合う。
- 失敗した操作（検証の問題・食い違い・権限で断ったもの）は、何も書かないので、記録しない。操作のIDの再送で前の結果を返したときも、記録しない（前の記録がある）。
- 保存の操作と公開の操作（6.7）の記録：`actor` は操作した人（`by`）。`target` は、操作の結果が指す文書（設定は種類 `settings` で `id` なし。サイトの取り込みは文書を指さないので、なし）。`operation` は、呼ぶ側が渡した操作のID。`changed` は、何かを保存したか。`before` は、呼ぶ側が読んだ版（元にした版を取る操作だけ）、`after` は、保存した版（版を足した操作だけ）、`revision` は、足した・公開した・予約したリビジョン、`status` は、公開・公開をやめる・アーカイブ・予約・予約の日時の公開が決めた状態。`detail` の共通のキーは、`warnings`（警告の数。0なら出さない）・`publishes`（公開するものを変えたときの `true`）・`redirect`・`number`（エントリーの番号）。
- アカウントの操作の記録：`target` は `user` と、対象のアカウントのID。`detail` の `fields` は、変えた項目の名前（`author`・`email`・`login`・`name`・`password`・`role`・`status`・`token`）を、名前の順に、`, ` でつないだもの。`login`・`role`・`status`・`author` は、変えたものだけ、`<項目>Before`・`<項目>After`（作る操作は After だけ、消す操作は Before だけ。空は出さない）。値は64バイトまで。トークンの用途は `tokenPurpose`（`invitation`・`reset`）、期限は `tokenExpiresAt`（UTC。トークンもそのハッシュも出ない）。

- ビルドの記録：ビルドが終わるたびに1件で、取った要求ごとではない。取り消されて終わったビルドは、`result` が `failed`、`detail` の `error` が `context canceled`（ビルドの段階の前置きが付くことがある）。サイトの問題の文は、ファイルの名前と、行・列・JSON Pointer・文を持ち、サイトの文書の値を引用することがある。

**ログイン履歴**

ログイン履歴の記録は `internal/account` が足し、`internal/admin` は、要求ごとに、クライアントのアドレス（9.6の「リバースプロキシ」）と `User-Agent` のヘッダーを、`account.Client` にして、`Login`・`Logout`・`Authenticate`（セッションを使う口。9.6の「CSRF」）・`ChangeOwnPassword`・`SetPassword` に渡し、HTTPの側で断ったログインを `Manager.LoginRefused` で知らせる。規則（案）：

- 成功（`login`）：セッションを書く `Update` に入る。そのとき消す使えない行・`previous` のセッション・上限（1アカウント10個。7.3）を超えた分のセッションの `session.end` が先で、`login` が最後。パスワードのハッシュを、いまの回数で作り直したログイン（7.3の「ハッシュの作り直し」）は、アカウントの行も同じ `Update` で書き換える。その印として、`detail` の `rehashed` が `true`（作り直さなかったログインと、`session.start` には無い）。
- 失敗（`login.failure`）：`result` に理由、`login` に打たれたログイン名（正規化して、64バイトまで）、分かるときは `account`、`client`。応答は、理由によらず同じのまま（9.6。理由を持つのは記録だけ）。

| `result` | 理由 |
| --- | --- |
| `unknown-login` | そのログイン名のアカウントが無い（行が読めないものも） |
| `pending` | 保留のアカウント |
| `disabled` | 無効のアカウント |
| `wrong-password` | パスワードが違う |
| `too-long` | 8KiBを超えるパスワード（7.3の「パスワード」） |
| `changed` | パスワードを比べている間に、アカウントが変わった（セッションを書く `Update` が断った） |
| `error` | パスワードを比べた後の失敗（保存先の失敗・乱数・取り消された要求も） |
| `rate-limited` | 試行の制限（429。9.6）で断った |
| `busy` | ログインの順番の上限（503。9.6）で断った |
| `refused` | 知らない理由で `LoginRefused` に渡されたもの |

- HTTPの側で断ったログイン（8KiBを超えるパスワード・429・503）：`Login` を呼ばないので、`LoginRefused` が、答える前に、同じ形の `login.failure`（`too-long`・`rate-limited`・`busy`）を書く。ログイン名にアカウントがあるかを調べないので、`account` は持たない。答えは変えない。
- 記録しない失敗：パスワードを比べる前の失敗（保存先を読めない・ハッシュの順番を待つ間に要求が終わった）は、比べていないので、記録しない（呼ぶ側に、エラーを返す）。
- ログアウト（`logout`）：セッションの行があったときだけ（期限が切れた行も）。行の無いトークンと、トークンでない文字列は、何も書かない（7.3）。
- セッションの始まり：ログインは `login`。本人のパスワードの変更（`ChangeOwnPassword`）が作る、新しいセッションは `session.start`。
- 最後の要求の時刻（`session.seen`）：`Authenticate` が、最後の要求の時刻を書くとき（保存した値が5分以上古いとき。7.3）に、同じ `Update` で足す。1つのセッションで、5分に1回まで。使い続けるセッションの、アドレスの変わり（盗まれたCookieなど）が分かる。
- セッションの終わり（`session.end`）：セッションの行を消すたびに1件で、`result` に理由。期限で終わったものは、`detail` の `expiredAt` に、期限の時刻（UTCのRFC 3339、小数の秒つき。両方が過ぎていれば、先に過ぎたほう。同時なら `lifetime`）を持つ。期限を過ぎても、行を消すまで（次のログインの掃除か、そのトークンでの `Authenticate`）は書かれないので、`at` は消した時刻で、終わった時刻は `expiredAt`。`client` は、`Authenticate` が見つけて消したときだけ、その要求のものを持つ（ほかは、持たない）。

| `result` | 理由 |
| --- | --- |
| `idle` | 操作の無い時間（1時間）が来た |
| `lifetime` | 全体の期限（12時間）が来た |
| `credentials` | アカウントの `credentialsChangedAt` が、セッションが持つ値と違う |
| `inactive` | アカウントが有効でない（保留・無効） |
| `missing` | アカウントが無い、または読めない |
| `unreadable` | セッションの行が読めない |
| `replaced` | ログインの `previous` のトークンのセッション |
| `evicted` | 1アカウント10個の上限を超えるため、最後に使ったのが最も古いものを消した |
| `password` | パスワードの変更・再設定・`SetPassword` で、アカウントのすべてのセッションを消した |
| `role` | ロールを変えて、アカウントのすべてのセッションを消した |
| `disabled` | アカウントを無効にして、すべてのセッションを消した |
| `deleted` | アカウントを消して、すべてのセッションを消した |

- 無効なトークン（`token.failure`）：`SetPassword` が断った、招待と再設定のトークン。`result` は、`malformed`（トークンの形でない）・`unknown`（どのアカウントも持たない。使い終わったものも）・`expired`（期限切れ）・`disabled`（無効のアカウントのもの）。トークンは記録に入れない。遅れた招待や再設定と、でたらめなトークンの試しを、分けられる。
- ログインしていない人の失敗の上限（案）：`login.failure`（HTTPの側で断ったものも）と `token.failure` は、ログインしていない人が、いくらでも起こせるので、サーバー全体で、`Manager` の時計の分の区切り（毎分0秒）ごとに、次の2つの枠までを、それぞれ1件ずつ記録する。超えた分は、記録を書かず、`action` と `result` ごとに数える。
  - 比べた失敗の枠：パスワードをハッシュと比べた失敗（`Login` が記録する、`unknown-login`・`pending`・`disabled`・`wrong-password`・`changed`・`error`）は、60件まで。
  - 断りの枠：比べる前に断ったログイン（`LoginRefused` が記録する、`too-long`・`rate-limited`・`busy`・`refused`と、`Login` の中で断る `too-long`）と、無効なトークン（`token.failure`）は、10件まで。ハッシュを作らない安い要求で、ネットワークの速さで起こせるので、別の枠にする。1つの枠にすると、安い要求が枠を使い切り、本物の試しの、アドレスとログイン名が残らず、数だけになる。
  - 2つの枠は、分ごとに、別に数え直す。あふれた分は、どちらも同じ数えに入り、同じまとめ（下記）になる。1分に1件ずつ書く失敗の記録は、最大70件で、まとめは、1分に最大2件（`Update` が取る1件と、`FlushSuppressed` を1分ごとに呼ぶときの1件）。
  - まとめ（`login.suppressed`）：数えた分（枠を超えた分と、記録を書けなかった分）は、ログイン履歴を書く `Update` の最初の記録として（その `Update` の、ほかの記録の前に）書く。取る `Update` は、`Manager` の時計の分の区切りごとに、1回まで：その分に、すでに `Update` が取っていれば、取らず、その後に数えた分は、次の分の最初のログイン履歴の `Update` か、`FlushSuppressed` が書く。`detail` に、数えた分の初め（`from`）と終わり（`to`。どちらもUTCのRFC 3339、秒まで。複数の分にまたがるときは、1つにまとめる）と、理由ごとの数（キーは、`action` と `result` を camelCase でつないだもの。`loginFailureWrongPassword`・`loginFailureRateLimited`・`tokenFailureExpired` など。値は10進数の文字列）。2つの枠の分は、理由で分かれ、1つのまとめに入る。`FlushSuppressed` は、分によらず、数えた分をすべて取り、`Update` の1分に1回には数えない（その分に `Update` が取っていなければ、その後に数えた分を、`Update` が取る）。サーバーが、1分ごとと、止めるときに呼べば、攻撃が止まった後の、最後の分の数も書かれる（呼ぶのは #49。6.12の235）。書く `Update` がコミットしなかったときは、取った数と、取った分の印を戻す（同じ分のうちに、次の `Update` が、もう一度取れる）。ログイン履歴に何も書かない `Update`（行の無いトークンの `Logout` など）は、まとめを取らない。
  - 数えない：成功したログイン・ログアウト・セッションの記録は、どちらの枠にも入れず、数えない（使う人の操作の数で決まる）。
  - 書けなかった失敗：枠に入ったのに、記録を書けなかった失敗（保存先の失敗・5秒の期限。下記の「記録できなかったとき」）は、`OnRecordError` に知らせたうえで、数えた分に足し、次のまとめに入れる（その失敗が来た分の区切りで数える）。その枠は戻さない：戻すと、保存先が塞がっている間、記録を待つ要求の数が、枠の数（1分に70件）を超えて増える。
  - 数えた分は、プロセスのメモリにだけ持つ。まとめを書く前にプロセスが止まると失い、書く `Update` が失敗したときは、数えた分と、取った分の印を戻して、次に書く。`Update` が取った後に数えた分も、次の分か `FlushSuppressed` まで、メモリにだけある。
  - 理由（見積もり）：上限が無いと、パスワードを比べる速さ（開発のマシンで毎秒約35件。7.3）まで記録され、1日に約300万件、約1.4GBになる。ハッシュを作らない429と8KiBを超えるパスワードは、それより速く起こせる。この上限では、攻撃が続いても、1日に最大 72 × 1440 ≒ 10.4万件、約48MBで止まる：失敗の記録が1分に最大70件（1件約464バイト。User-Agent が約110バイトのとき）と、まとめが1分に最大2件（`Update` が取る1件と、`FlushSuppressed` を1分ごとに呼ぶときの1件。1件約320バイトで、理由が多いと約710バイトまで）。測った値：断りを10件送った後、断りと比べた失敗を交互に60組送り、`FlushSuppressed` を呼ぶ最悪の1分で、記録が72件（失敗70件とまとめ2件）、データのディレクトリが約31KB（User-Agent が約70バイトのとき）、約34KB（約110バイトのとき）増えた（2026-11-12）。`Update` が取る回数に上限が無いと、同じ場面（`FlushSuppressed` なし）で、比べた失敗の記録ごとに、断りの数を取るまとめが付き、記録が130件（失敗70件とまとめ60件）、約49KB（User-Agent が約70バイトのとき）になる。ディスクが埋まると、保存先が書けなくなり、すべての保存が失敗する。
  - 残る弱点：枠を超えた試しの、アドレスとログイン名は残らない（数だけ）。攻撃の間は、本人の失敗の記録も、枠を超えると数に入る（比べた失敗は61件目から、断りとトークンは11件目から）。枠は、サーバーに1組で、アドレスごとにも、ログイン名ごとにも分けない（6.12の235）。

例（`login.suppressed`）：

```json
{"log":"login","n":815,"prev":"sha256:71547e237559add83f6c9279fdb5762eafee857a1060e2d97c0316a70cefb6ba","at":"2026-11-12T01:04:12.345678Z","action":"login.suppressed","detail":{"from":"2026-11-12T01:03:00Z","loginFailureRateLimited":"1307","loginFailureWrongPassword":"412","to":"2026-11-12T01:04:00Z"}}
```

**番号と時刻と鎖**

- 番号（`n`）：ログごとに1から、1つずつ。保存先が、同じログの、前の記録（同じ `Update` で足したものも）の次の番号を付ける。失敗した `Update` と取り消した `Update` は、番号を空けない。呼ぶ側が `n`・`prev`・`at` を入れた記録は、断る。
- 鎖（`prev`）：各記録は、同じログの1つ前の記録の、保存したバイト列（上記の形のJSON）のSHA-256を持つ。最初の記録は持たない。保存先が書いたバイト列のままハッシュを求めるので、あとで読み直したときに、書き換わっていれば、合わなくなる。
- 鎖の頭：ログごとの、最後の記録の番号と、そのバイト列のSHA-256。表 `meta` の `loginLog`・`activityLog` に、その記録と同じコミットで置く（3.4の「表」）。記録の無いログには、行が無い。
- 時刻（`at`）：保存先の時計で、`Update` を始めた時刻。同じ `Update` で保存した版とリビジョンの保存した日時（3.4）と同じで、1つの `Update` に何件の記録を足しても、同じ。操作を呼ぶ側の時計（`Manager`・`Editor`）ではない。
- 2つのログの間の順は、意味を持たない。順を言えるのは、同じログの中だけ。
- 足す口だけがあり、書き換える口と消す口は無い（7.2）。

**改ざんの検知**

保存先のファイルを書ける人は、記録を書き換えられる。そこで、見つける仕組みを、2つ重ねる（案）：保存先の中の鎖と、保存先の外に書き出す鎖の頭。

- 保存先の中の鎖：`Store.VerifyAudit` が、すべての記録を初めから読み、次を確かめる：記録として読めること、番号が1から続くこと、各記録の `prev` が、1つ前の記録のハッシュであること、ログごとの最後が、表の頭と同じこと、表の版6以上の保存先は、アクティビティログに記録が1件以上あること（`store.create` か `store.upgrade` が、記録1にあるので、記録も表の頭も無いのは、すべてを落とした書き換え。ログイン履歴は、ログインの無い保存先が記録を持たないので、空でもよい）。記録1の操作が、どちらであるかは、確かめない（下記の「保持の期間と個人の情報」）。問題は、`audit.ErrBroken` を包み、ログ・記録の番号・エンジンのイベントの番号・理由を示す（例：`audit log "login": record 12 (event 345): prev is not the hash of record 11`）。読む失敗と、`ctx` の終わりは、そのまま返す。
- 外に書き出す鎖の頭（`audit.Export`）：鎖の頭を、保存先の外に、1行ずつ書く。形は `audit head <ログ> <番号> sha256:<64桁の小文字の16進数>`（例：`audit head activity 1245 sha256:…`）。個人の情報も、時刻も入らない。1行は、改行を含めて113バイトまで。書き出すのは、始めに、記録のあるログの頭を1回、そのあと、呼ぶ側が間隔ごとに送る合図（`ticks`）が来るたびに、前に書いたものから変わった頭だけ、終わるとき（`ctx` が終わった後）に、取り消しから切り離した5秒の期限で、もう1回。書けなかった頭は、次の回で書き直す。書き出しが失敗しても、操作は止めない（エラーは、渡した関数が受ける）。
- プロセスへのつなぎ（案。つなぐのは #49）：標準エラー（systemd では journald）に書く。`ticks` は1分ごと、止めるときは `ctx` を取り消して、`Export` の戻りを待つ。頭は、1分に2行まで（ログごとに1行）なので、journald の数の制限（1つのサービスで30秒に10000行）に当たらない。
- 外に書き出した頭で確かめる：書き出した行を `audit.ParseHead` で読み、`VerifyAudit` の `anchors` に渡す。各頭は、その番号の記録のハッシュと同じで、ログが、その番号より先まで続いていること。確かめる道具（コマンド）は、まだ無い（下記の「まだ無いもの」）。
  - `ParseHead` は、行の前に何が付いていても（journald が付けた時刻やプロセスの名前など）、行の末尾の `audit head <ログ> <番号> sha256:<64桁>` を読むので、頭の形の行は、だれが書いたものでも読める。外の頭は、whiteroom のサービスが書いた行だけから取る（journald なら、`_SYSTEMD_UNIT` などの、書いたサービスを示す項目で絞る）。
  - 偽の頭の行を足されても、できるのは、`VerifyAudit` を失敗させる（誤った警報）ことだけで、書き換えは隠せない（隠すには、保存先を書ける力が要る）。渡す頭は、最後の1つだけにせず、古い時点のものも含める：古い本物の頭は、書き換えた鎖に合わないので、書き換えが見つかる。最後の1つだけだと、書き換えた鎖に合う偽の頭を足されて、見逃す。

見つけるもの（案）：

- 保存先の中の鎖だけ（`anchors` なし）：記録のバイト列の書き換え・途中の記録を落とすこと・表の頭の書き換え・記録として読めないイベント・表の版6以上の保存先の、アクティビティログのすべての記録と表の頭を落とすこと（`store.create` か `store.upgrade` が残るはずなので。2つのログのすべてを落としても、同じ）。
- 外に書き出した頭も使う：上に加えて、鎖を作り直して、表の頭も合わせた書き換え（その番号までの記録の、内容・順・件数。その番号の記録のハッシュが変わるため）・その番号より前の記録を落とすことと足すこと・その番号より後の末尾を落として、表の頭を合わせること・ログごと落とすこと（ログイン履歴をログごと落とすことは、外の頭でだけ見つかる：ログイン履歴は、空でもよいので、保存先の中だけでは、落としたのか、記録が無かったのか、分からない。アクティビティログは、上記のとおり、保存先の中だけで見つかる）。

見つけないもの（限界。案）：

- 最後に書き出した頭より後に足した記録の書き換えと削除：書き出しは、変わったときに1分に1回（と、止めるとき）なので、最大1分ほどの間の書き換えは、外の頭では見つけられない（止めるときの書き出しが無かったときは、もっと）。
- 外の写しも書き換えられる人の書き換え：OSの管理権限を奪われると、保存先も、手元の journal も書き換えられる（7.2の注意）。手元の journal だけでは、権限を奪った人が、両方を書き換えられる。
- 鍵の無い鎖なので、保存先を書ける人が、新しい記録を、正しい鎖で足すこと（偽の記録を足す成りすまし。書き換えではない）。鍵つきの鎖は、まだ無い（6.12の236）。

外への退避（運用で使う。案）：書き出した行を、権限を奪われても書き換えられない場所に置くには、次のどちらか（か、両方）を、運用で使う。whiteroom は、どちらも用意しない。どちらも、実際のマシンでは動かしておらず、出典の文書（下記の「確かめた事実（#47）」）だけを見た。

- journald の封（Forward Secure Sealing。FSS）：`journalctl --setup-keys` で鍵の組を作り、封をする鍵は、そのホストに残し、検証の鍵は、外に置く。封をする鍵を替える間隔（`--interval`。既定は15分）が短いほど、見つけられない書き換えの時間が短い。`journalctl --verify` に `--verify-key` を渡して、ジャーナルのファイルが本物かを確かめる。`journald.conf` の `Seal=` は、既定で有効で、鍵の組があるときに封をする。
- 別のマシンへの転送（syslog）：書き出した行を、別のマシンに送る。RFC 5424 の syslog は、届いたことを確かめず、書き換えも繰り返しも防がず、攻撃する人は、記録を途中で捨てて、行いを隠せる。署名つき syslog（RFC 5848）は、送り手の確かめ・書き換えの検出・繰り返しへの耐性・順番・欠けたメッセージの検出を足す仕組み。頭の1行は、113バイトまでと小さい（受け手が必ず受け付ける大きさは、見出しも含めて480オクテット。RFC 5424）。

**保持の期間と個人の情報**

保持（案）：

| ログ | 残す期間 | 古い記録の消し方 |
| --- | --- | --- |
| ログイン履歴 | 1年 | 消す処理は、まだ無い（下記） |
| アクティビティログ | 保存先の履歴（3.4）と同じだけ | 消さない（履歴から消す操作と合わせて決める。6.12の125） |

- 消す処理は、まだ作っていない。規則（期間）と、消せる形だけを作った。作るのは、保守モードの圧縮（3.5の「保守モード」）を、保存先から使えるようにするとき（#70。6.12の133・233）。作るまで、ログイン履歴も、1年を超えて残る（ふつうの使い方：10人が毎日8時間使い、1人が1日に約100件（ほとんどが `session.seen`）で、1日に約1,000件、約0.5MB、1年で約170MB。見積もり）。OWASP は、決めた期間を過ぎて持たないことを求める（期間は、法令・規制・契約の義務で決まることがある）。消す処理ができるまで、これを満たさない。
- 消せる形：ログごとに別の鎖にしたので、ログイン履歴だけを、古いほうから消せる。消した後は、残る最初の記録から確かめる（案）。そのために、鎖の始まり（残る最初の記録の番号と、その前のハッシュ）を、表に持つ必要がある。いまの `VerifyAudit` は、ログの最初の記録が、番号1であることを求める（6.12の233）。表の版6以上の保存先のアクティビティログは、記録が1件以上あることも求める（`store.create` か `store.upgrade` が、記録1にあるため）が、記録1の操作が、どちらであるかは、確かめない：鎖を作り直せる人は、`store.create` の記録も偽って足せるので、確かめても守りが増えず、番号が1から続くことと `prev` の確かめは、すでにある。古い記録を消して、残る最初の記録が、記録1でなくなるときに、その記録の操作を確かめるかは、鎖の始まりと合わせて決める（6.12の233。#70）。
- ログイン履歴を1年にしたのは、年に1度の見直し（更新の時期など）の調べに足りるため。90日では、足りないことがある。

個人の情報（案）：

- クライアントのアドレス（そのまま）・User-Agent（512バイトまで）・打たれたログイン名は、ログイン履歴だけが持つ。アクティビティログと、セッションの行（7.3）は、持たない。個人の情報を、ログイン履歴の1か所にまとめ、期間で消せるようにするため。アクティビティログの記録に `client`・`login`・`session` を入れると、`Record.Check` が断る（上記の「記録の形」。書く側の取りこぼしを、保存先が見つける）。アドレスは、そのままなので、調べるときに使える。
- アドレスは、9.6のクライアントのアドレスの決め方のとおり。リバースプロキシを `TrustedProxies` に入れ忘れると、全員がプロキシのアドレスになり、プロキシでないアドレスを入れると、偽られたアドレスが残る（9.6の「リバースプロキシ」の「設定の責務」）。
- 打たれたログイン名（残る弱点。案）：ログインの失敗の記録は、打たれたログイン名（正規化して、64バイトまで）を持つ。ログイン名の欄にパスワードを打った人がいると、それ（正規化した、先頭の64バイトまで）が、ログイン履歴に残る。応答は、理由によらず同じなので（9.6）、打った人にも、残ったことは見えない。読めるのは `logs.view` を持つ人（admin だけ。7.3）で、残る期間は、保持の期間の1年（消す処理ができるまでは、それを超えて残る。上記）。存在しないログイン名への試し（`admin` など）と、間違ったパスワードと、無効のアカウントを、あとで分けられることと引き換えに、承知のうえで、仮に決めた。減らす方法は、6.12の235。
- アクティビティログが持つ、アカウントのログイン名（残る弱点。案）：アカウントの操作の記録は、ログイン名（変える前と後。消す前）を持つ。アクティビティログは、保存先の履歴と同じだけ残す（上記）ので、アカウントを消した後も、そのログイン名が残る。個人の情報として数えたのは、ログイン履歴のアドレス・User-Agent・打たれたログイン名だけで、これは、期間（1年）で消す対象に入らない。消すには、記録を書き換える必要があり、その記録の後ろの鎖と、外に書き出した頭が、合わなくなる。どう消すかは、6.12の239。
- 文書の値の引用（残る弱点。案）：失敗したビルドの `error`（2048バイトまで）は、サイトの問題の文（`content.Errors`）を含み、スラッグなど、文書の値を引用することがある。それは、アクティビティログに残り、文書を履歴から消しても（6.12の125）、記録からは消えない。メディアの追加の `fileName` は、アップロードされたファイルの名前（整えた後）で、同じく残る。消し方は、6.12の239。
- 3.5の「個人情報の削除」の表の、ログ・チェックポイント・バックアップは、記録にも当たる。記録を消しても、バックアップの写しには残る。
- 暗号化して鍵を消す形（crypto-shredding）は、候補（3.5の「個人情報の削除」。6.12の138）。

**記録できなかったとき**

OWASP の Logging Cheat Sheet は、記録の仕組みの失敗が、アプリケーションの動きを止めないようにすることを求める。一方、変更の記録が無い変更は、残したくない。そこで、記録を、変更と同じ書き込みに入るものと、単独のものに分ける（案）。

- 変更と同じ書き込みの記録（保存の操作・公開の操作・アカウントの操作・セッションの行を書く操作）：記録を書けなければ、操作も失敗する（何も変わらない。3.4の「壊れない書き込み」）。外から来る値は、切ってから入れるので（上記の「記録の形」）、記録の形が合わずに失敗することは、ふつう無い。
- 単独の記録（変更の無い記録）：ログインの失敗・HTTPの側で断ったログイン・無効なトークン・まとめ（ログイン履歴）と、ビルドの結果（アクティビティログ）は、別の `Update` に書く。要求の取り消しから切り離し（`context.WithoutCancel`）、保存先を5秒まで待つ。書けなくても、応答も、ビルドの結果も、公開も変えない（401や429のまま。ログインの応答が、記録の成否で変わると、記録の書けない状態を、外から探れるため）。書けなかったことは、`Manager.OnRecordError`（ログイン履歴）と `publish.Options.OnRecordError`（ビルドの結果と、`Rollback` の2件目）に渡した関数が受け取る。管理用のサーバーは、前者を `Config.ErrorLog` につなぎ、`cannot record login.failure: <理由>` を1行書く（`token.failure` も。9.6の「記録」。1分に70行まで：失敗の記録の上限（上記）の、2つの枠の数の和）。後者をつなぐのは #49。枠に入ったのに、書けなかった失敗は、その数（次の `login.suppressed`。上記）に足すので、ログインの失敗の記録は、保存先が書けない間は、エラーのログと、その数にしか残らない。
- 保存先の書く口が、別の `Update`（長い取り込みなど）で塞がっているとき：HTTPの側で断ったログイン（8KiBを超えるパスワード・429・503。33個目のログインの503も）は、答える前に記録を書く（ログインの順番には待たせない）ので、記録を書く要求は、最大5秒待ち、その分、答えが遅れて、`cannot record login.failure: context deadline exceeded` が書かれる。待たされるのは、失敗の記録の上限（上記）の枠の中の、記録を書く要求だけで（比べた失敗は1分に60件、断りとトークンは10件）、超えた分は、数えるだけで、保存先に何も書かず、待たない。書けなかった失敗も、枠を使ったままなので、保存先が塞がっていても、待つ要求は、1分に70件を超えて増えない。答えの内容は変わらない（9.6）。
- 公開の仕組みの、人の操作（`Rebuild`・`Rollback`・`Resume`）：先に記録を書き、書けなければ、何もせず、エラーを返す（`cannot record <操作>: <理由>`）。動く前に書くので、記録と動きの間でプロセスが止まると、動かなかった操作の記録が残りうる。`Rollback` は、記録の後に失敗したとき（プロセスが動いている間）だけ、`failed` の記録を、もう1件書く。
- ビルドの記録：ビルドが終わって、公開と状態（`Status`）の更新の後に、別の `Update` で書く。そのため、公開の直後にプロセスが止まると、そのビルドの記録は残らない。保存先が5秒より長く塞がっていると、記録を失い、`OnRecordError` に知らせる。記録を書く間、`Publisher` は、次のビルドを始めない（6.12の177）。
- 鎖の頭の書き出し：失敗しても、操作は止めない（上記の「改ざんの検知」）。

**記録の無い書き込みを断る**

- 規則（案）：保存先の `Update` は、関数が成功した後に、記録のほかに何かを書き（`Tx.Changed`）、記録を1件も足していないトランザクションを、何もコミットせずに、`ErrUnrecorded`（`the transaction writes but adds no audit record`）で失敗させる。版の番号も、記録の番号も進まない。関数がエラーを返したときは、そのエラーを返す。数えるのは記録の件数だけで、どちらのログの、何件目でも通る。
- 通るもの：記録だけの `Update`（ログインの失敗・ビルドの結果・何も変えなかった成功の記録など）と、何も書かない `Update`（読むだけ・同じバイト列の `Put`・正しい索引の `RebuildIndex`）。
- 守るもの：新しい書き込みの道を足して、記録を忘れると、その書き込みが、すぐに失敗する（構造で守る）。記録を残さずに変更できる経路を、作らないための、保存先の側の守り。
- 抜け道は、テストのためのものも無い。保存先の口で直接書く道具とテストは、`store.write` の記録（`actor` は、`system` か、書いた人）を足す。本番のコードは、`store.write` を書かない。
- 例外：
  - 保存先の中の書き込み（作る・表の版の更新）は、エンジンを直接使い、この規則の外だが、自分の記録（`store.create`・`store.upgrade`）を、同じコミットに書く。
  - `PutOriginal`（メディアの原本。3.4の「原本」）は、`Update` の外で `files/` に書き、記録を持たない。ハッシュの名前のファイルを足すだけで、書き換える口も消す口も無く（同じ名前は、同じバイト列）、記録を持つメディアの文書（`media.add`・`media.replace`）が指すまで、サイトにも何にも効かない。指されない原本は、回収の対象（6.12の125）。成功した追加と差し替えでは、だれが原本を置いたかは、メディアの文書を保存した記録が、ハッシュ・大きさ・形式で残す。失敗した追加（形式が読めない・検証の問題・食い違い・記録の確かめの失敗）は、記録しない（上記の「記録する操作」）ので、その追加が先に置いた原本（1つ64MiBまで）は、`files/` に残り、だれが置いたかの記録が無い。`media.add` ができる人（author も。7.3の権限の表）が、失敗する追加を続けると、記録されずに、ディスクを埋められる（回数と合計の上限は、いまは無い。6.12の125）。
- 保存先を書く本番のコードは、`internal/edit`・`internal/account`・`internal/publish` だけで、どれも、書き込みごとに記録を足す（`internal/admin` と `cmd/whiteroom`・`internal/serve` は、保存先を書かない）。

**読む口と費用**

- 記録は、エンジンの監査イベント（3.5）に置く。ディスクのログにだけあり、メモリには数だけを持つ。表にも、索引にも置かない。
- 読む口（`Store.ReadAudit(ctx, f, fn)`）：両方のログの記録を、古い順に、絞り込み `f`（`audit.Filter`）に合うものだけ、`fn` が `false` を返すまで渡す。絞り込みは、ログ・期間（`From` 以上 `To` 未満）・アカウント（`actor` か `account` がそれのもの、または `target` がそのアカウントのもの）・操作（名前か、`.` で終わる接頭辞。`entry.` など）・対象（種類と `id`。どちらかは空でよい）で、空のものは問わない。1つの `View` で読むので、書くプロセスが書いている間も止まらない。読み手として開いた保存先（`OpenReader`）でも読め、ディスクに同期したコミットだけを見る。表の版5以下の保存先は、`ErrNoAuditLog`。記録として読めないイベントに会うと、`audit.ErrBroken` を包むエラーで止まる。
- `Store.AuditHeads` は、記録のあるログの頭を、ログイン履歴、アクティビティログの順に返す。`Store.VerifyAudit` は、上記の「改ざんの検知」。どちらも、表の版5以下の保存先では、`ErrNoAuditLog`。
- 新しい順のページ送りは、管理のAPI（#48）が、この口の上で作る（6.12の232）。
- 費用：絞り込みは、読んだ後に当てるので、毎回、ログの全体を、初めから読む（セグメントを1つずつ、メモリに読む。3.5の「制限」）。測った値：開発のマシン（16のCPU、メモリ30GB、NVMe SSD の ext4）、Go 1.27.3。ログインの失敗の形の記録（JSONで408バイト）200万件を、100件ずつの `Update` で書いた保存先（データのディレクトリは約887MiB）を、`OpenReader` で開いて測った（2026-11-12）。
  - 開く：25〜34ミリ秒。
  - すべて読む（絞り込みなし）：約3.7秒。アカウントと接頭辞で絞っても、約3.5秒（絞るのは、読んだ後）。`fn` が先頭の100件で止めれば、約35ミリ秒。
  - 確かめる（`VerifyAudit`）：約4.5秒。
  - 読む間のメモリ（最大RSS）：約211〜223MiB。セグメントを1つずつ読むので、ログの大きさに比例しない。
  - 1件を足す（記録だけの `Update`）：平均1.36ミリ秒、中央値1.30ミリ秒、99%点1.71ミリ秒、最大15.6ミリ秒（3,000回）。ログは、1件あたり約464バイト増える（記録のJSONに、約56バイトが足される）。
  - 文書が多いログ：8KiBの文書を保存した10万回に、1件ずつ記録が混ざった833MiBのログで、10万件を数えるのに0.41秒、デコードして絞るのに0.48秒（エンジンの `Events` で。2026-11-11）。
- 見積もり：記録が数千万件になると、1回に数十秒（200万件の約3.7秒から）。
- 索引を持たない理由：時刻と番号の索引を表に持つと、期間で絞るのが速くなるが、表はメモリに乗り、1件約96バイト（200万件で183MiB。開くのが0.25秒延びる）が、記録とともに増える。攻撃の失敗の記録（上記の上限の中）でも増える。記録そのものを表に置くと、すべての記録がメモリに乗る（1件約400バイト以上）。どちらも、いまは取らない（6.12の232）。

| OWASP Logging Cheat Sheet | 「Which events to log」に、認証の成功と失敗、認可（アクセス制御）の失敗、セッション管理の失敗、ユーザーの管理の操作（ユーザーの追加・削除・権限の変更）、データの取り込みと書き出しを挙げる。「Event attributes」は、いつ・どこで・だれが（利用者のIPアドレスと、利用者の識別子）・何を、を記録するとする。「Data to exclude」は、セッションの識別子（要るときは、ハッシュにした値に替えることを考える）・アクセストークン・認証のパスワード・暗号の鍵・機微な個人の情報を、そのまま記録しないとする。ログの注入を防ぐために、すべてのイベントのデータを整え、JSONのような構造のある形を使う。「Protection」は、記録が書き換えられたか消されたかが分かる仕組み（tamper detection）を組み込み、できるだけ早く読み出し専用の媒体に写すとする。「Event collection」は、記録の仕組みの失敗が、アプリケーションの動きを止めないようにする（情報も漏らさない）とする。「Disposal of logs」は、決めた保持の期間より前に消さず、期間を過ぎて持たないとし、期間は、法令・規制・契約の義務で決まることがあるとする（ハッシュチェーンという言葉は無い） | 記録する操作・記録の形・改ざんの検知・記録できなかったとき・保持 |
| journalctl(1)（systemd 262） | `--setup-keys` は、Forward Secure Sealing（FSS）の鍵の組を作る。封をする鍵は、ジャーナルのディレクトリに置かれ、そのホストに残し、検証の鍵は、外に置く。`--interval` は、封をする鍵を替える間隔で、既定は15分（短いほど、見つけられない書き換えの時間が短い）。`--verify` は、ジャーナルのファイルの中の整合を確かめ、FSS で作ったファイルに `--verify-key` を渡すと、本物であることも確かめる | 外への退避 |
| journald.conf(5)（systemd 262） | `Seal=` は既定で有効で、`journalctl --setup-keys` の鍵があるときに封をする。`RateLimitIntervalSec=`・`RateLimitBurst=` の既定は、1つのサービスについて、30秒に10000件で、超えた分は捨て、捨てた数を知らせる行を書く。`MaxRetentionSec=` の既定は0（時間では消さない）。`SystemMaxUse=` の既定は、ファイルシステムの大きさの10%で、4Gまで | 外への退避・プロセスへのつなぎ |
| RFC 5424（The Syslog Protocol。2009年3月） | メッセージの形を決め、転送は別の文書（RFC 5425・5426）で決める。実装は、TLS の転送を MUST、UDP の転送を SHOULD で持ち、配備には TLS を勧める。受け手は480オクテットまでのメッセージを受け付ける（MUST）、2048オクテットまで（SHOULD）。syslog は、届いたことの確かめを持たず、書き換えも、繰り返し（replay）の検出も、防がない。攻撃する人は、記録を途中で捨てて、行いを隠せる | 外への退避 |
| RFC 5848（Signed Syslog Messages。2010年5月） | syslog のメッセージに、送り手の確かめ・書き換えの検出・繰り返しへの耐性・順番・欠けたメッセージの検出を足す仕組み。署名のブロックは、前に送ったメッセージのハッシュを持ち、まとめて署名する | 外への退避 |
