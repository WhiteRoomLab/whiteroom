### 6.10 WordPressとの対応

#### 6.10.1 データ

| WordPress（WXR） | このCMS | 備考 |
| --- | --- | --- |
| 投稿、固定ページ | `post`、`page` | 親子関係・並び順・公開日・先頭固定を維持する |
| カスタム投稿タイプ | カスタムタイプ | サイト設定で定義してから対応付ける |
| カテゴリー、タグ、カスタムタクソノミー | タクソノミー／ターム | スラッグを維持する（下記）。エントリーには `terms` で付ける（カテゴリーは `category`、タグは `tag`） |
| 添付ファイル | メディア | WXRにはファイル自体が含まれない（URLのみ）。旧サイトからダウンロードするか、`wp-content/uploads` をコピーして取り込む（下記） |
| アイキャッチ画像（`_thumbnail_id`） | `featuredImage` | |
| 抜粋、`<!--more-->` | `excerpt` | 抜粋が空なら、`<!--more-->` より前を抜粋にする。ブロックエディタの「続きを読む」ブロックと、クラシックの本文の `<!--more-->` の位置は、本文の変換が返す（6.10.5） |
| 投稿者 | 著者プロフィール（`author`） | WXRに含まれるのは表示名などだけ（下記）。メールアドレスは公開プロフィールに取り込まない |
| 投稿のステータス | `status` | `publish` は `published`、`future` は `scheduled`（`scheduledRevision` と `scheduledAt` が要るので、エントリーの変換が書く。変換は、まだ無い）、ほかは `draft`（6.4.1。案） |
| 公開日（`post_date`・`post_date_gmt`） | `date` | 2つの差から時差を求め、時差付きの日時にする（案） |
| メニュー | メニュー | 行き先をIDに変換する（下記） |
| Contact Form 7 のフォーム | フォーム | フォームのタグから入力の項目を作る（下記） |
| 同期パターン（再利用ブロック） | 共有ブロック（段階2） | 共有ブロックができるまでは、使っている場所に中身を写す（6.10.2・6.10.5）。WXRにあるものだけで、テーマのパターンはWXRに無い |
| カスタムフィールド、ACF | `fields` | フィールドの対応表を用意して取り込む |
| SEOプラグインの設定 | `seo` | プラグインごとに対応表が必要。独自のテーブルに保存していて、WXRに含まれないものもある |
| 一般設定（サイトのタイトル、キャッチフレーズ、サイトアドレス、タイムゾーン、サイトの言語） | サイト設定の `name`・`tagline`・`url`・`timeZone`・`languages`・`defaultLanguage`（6.6.8） | WXRのチャンネルと、旧サイトのREST APIから作る（下記） |
| サイトアイコン、ロゴ | サイト設定の `icon`・`logo` | 添付ファイルから取り込んだメディアを指す（下記） |
| 表示設定（ホームページの表示、1ページの投稿数、検索エンジンでの表示） | サイト設定の `frontPage`・`postsPage`・`postsPerPage`・`seo.noindex` | 1ページの投稿数と検索エンジンでの表示は、取り込みの設定の値にする（既定は10件と、検索エンジンに載せる設定。下記） |
| パーマリンク設定 | URLの規則（6.6.8） | WXRにもREST APIにも無いので、推測して、取り込みの設定に書き出し、取り込む前に確かめてもらう（6.10.4） |
| 日付と時刻の形式、週の始まり | 取り込まない | 日付の表示の形は、テーマが決める（案） |
| 多言語プラグインの言語情報 | `language`、`translationGroup` | Polylang は言語と翻訳の関係をタクソノミーとして保存しているため、WXRから復元できる見込み。WPML は独自のテーブルに保存しているため、WXRだけでは復元できない可能性がある |
| 旧スラッグ（`_wp_old_slug`） | リダイレクト | 変える前のスラッグのURLから、エントリーへ転送する（下記） |
| リダイレクトのプラグイン（Redirection など） | リダイレクト | 独自のテーブルに保存するものは、WXRに含まれない。プラグインの書き出しから取り込めるかは、まだ確かめていない |
| 非公開・パスワード保護の記事 | 下書き | 意図せず公開されないよう、必ず下書きとして取り込む |
| コメント | 取り込まない | コメント機能は対象外。数だけを取り込みレポートに記録する（6.10.5） |

取り込みの流れ、WXRとREST APIの読み込み、取り込みの設定、IDの作り方、取り込みレポートの形は、6.10.5に書く。

サイト設定・ターム・メディア・著者プロフィール・メニュー・フォーム・リダイレクトの取り込み（案）：

- **サイト設定**：WXRのチャンネルと、旧サイトのREST APIの一覧（`/wp-json/`。ログインせずに読める。読み方は6.10.5）から作る。推測した値は、取り込みの設定（JSONのファイル）に書き出し、根拠と確かめる値を取り込みレポートに記録して、取り込む前に確かめて（直して）もらう（6.10.5の「取り込みの設定」）。値は、既定の言語のもの。
  - `name`・`tagline`・`url`：チャンネルのサイトのタイトル（`title`）・キャッチフレーズ（`description`）・ホームのURL（`link`。サイトアドレス）から作る。REST APIの一覧の `name` は、エスケープしたまま（`&amp;` など）返るので、使わない。`url` は、スキームとホストを小文字にし、末尾の `/` と既定のポート（`http` の `:80`、`https` の `:443`）を除く。それでもサイトのURLの規則（6.6.8）に合わないもの（Unicodeで書いた国際化ドメイン名など。punycodeには直さない）は、そのままにして、要確認として記録し、直してもらう。タイトルが空のときも、要確認として記録する。
  - `defaultLanguage`・`languages`：チャンネルの `language` は、翻訳の `html_lang_attribute`（`ja` など）か、ロケールの `_` を `-` にしたもの（`en-US`）なので、言語コードの正規の形（6.4.5）にそろえる。言語・用字・地域の後ろの変体（`de_DE_formal` の `formal`）は落とし（`de-DE`）、要確認として記録する（6.12の171）。言語コードにならないものと、無いものは、空にして、要確認として記録し、入力してもらう。`languages` は、いまは既定の言語だけにする。多言語プラグインの情報（上の表）から `languages` を作ることと、ほかの言語の `name` を入力してもらうこと（サイトのすべての言語で要る。6.6.8）は、まだ作らない。
  - `timeZone`：REST APIの一覧の `timezone_string`（IANAの名前）にする。空のとき（時差で指定したサイト）は、`gmt_offset` が -12〜14 の整数なら、符号を逆にした `Etc/GMT-9`（UTC+9）のような名前にする（0は `UTC`）。整数でない時差（UTC+5:30 など）、範囲の外の時差、6.6.8で受け付けない名前、REST APIが無いときと一覧に時差が無いときは、空にして、要確認として記録し、入力してもらう（空のままでは取り込めない）。`post_date` と `post_date_gmt` の差から、タイムゾーンを推し量ることはしない。
  - `frontPage`・`postsPage`：`show_on_front` が `page` なら、`page_on_front`・`page_for_posts`（固定ページの投稿ID。一覧には WordPress 6.8 から入る）の固定ページから取り込んだエントリーを、既定の言語の `frontPage`・`postsPage` にする。`show_on_front` が `posts` なら、どちらも書かない。`show_on_front` が一覧に無いとき（6.8より前のサイトと、REST APIを使えないとき）は、WXRで公開済みの固定ページのうち、`link` のパスが `/` になっているものが1つだけなら、それを `frontPage` にし、`postsPage` は書かない（0個や2つ以上のときは、書かずに、要確認として記録する）。WXRに無い、または固定ページでないものを指すときも、書かずに記録する。WordPressでは、`page_on_front` が0でも `page_for_posts` を設定でき、2つが同じでも警告するだけで保存できるが、このCMSの `postsPage` は、`frontPage` のある言語で、`frontPage` と別の固定ページだけ（6.6.8）。そこで、`page_on_front` が0なら、どちらも書かず（トップページには、WordPressと同じく最新の投稿の一覧を出力する）、`page_for_posts` の固定ページは、ふつうの固定ページとして取り込む（WordPressでは、そのページのパスにも最新の投稿の一覧を表示していた）。2つが同じなら、`frontPage` だけを書く。どれも取り込みレポートに記録する（案）。
  - `logo`・`icon`：`site_logo`（テーマのロゴの `custom_logo`）と `site_icon` は、どちらも添付ファイルの投稿IDで、一覧に `_fields` で求めたときだけ入る。取り込みの設定には、WordPressの投稿IDで書き、その添付ファイルから取り込んだメディアを `logo`・`icon` にする。WXRに添付ファイルが無いIDと、取り込まない添付ファイル（ゴミ箱のものなど）のIDは、書かずに記録する。ファイルが見つからないなどで、メディアの変換のときに取り込めなかったものと、画像でなかったもの（PDFなど）は、メディアの変換が、作ったサイト設定から外して記録する（6.10.5の「メディア」の「ロゴとアイコン」）。REST APIを使えないとき、または一覧が `site_logo` も `site_icon` も返さないとき（設定が無いサイトも、同じに見える）は、空にして、要確認として1つ記録し、入力してもらう。
  - `postsPerPage`・`seo.noindex`：一覧の1ページの投稿数（`posts_per_page`）はログインの要る設定のAPIにしか無く、検索エンジンでの表示（`blog_public`）はどちらのAPIにも無いので、取り込みの設定に、WordPressの既定と同じ10件と、検索エンジンに載せる設定（`noindex` なし）を書き出し、いつも要確認として記録して、確かめて（直して）もらう。
  - ほか：多言語プラグインの既定の言語や、言語ごとのトップページを読めるかは、まだ確かめていない。`seo.titleFormat`・`seo.ogImage` は作らない（SEOプラグインの設定から作れるかは、まだ確かめていない）。日付と時刻の形式と週の始まりは、取り込まない。URLの規則は、パーマリンク設定を推測して作り（6.10.4）、取り込みの設定に、ほかの設定と一緒に書き出す。
- **カテゴリー、タグ、カスタムタクソノミー**：WXRの `wp:category`・`wp:tag`・`wp:term` から、名前・スラッグ・親・説明を取り込む。
  - 対応付け：`category` は `category`、`post_tag` は `tag`（タクソノミー名 `post_tag` は `tag` にする）。カスタムタクソノミーは、カスタム投稿タイプと同じく、スキーマのファイル（6.6.8）に同じ名前で定義したものだけを対応付ける（名前の違う定義への対応は6.12の169）。定義の無いタクソノミーと、このCMSに当たるものが無いもの（`post_format`・`link_category` など）は、タクソノミーごとに、数を最初のタームの位置に記録して、取り込まない。`nav_menu`（メニュー）と Polylang のタクソノミー（`language`・`term_language`・`post_translations`・`term_translations`。多言語）は、ほかの変換が扱うので、ここでは何も記録しない。名前が `tag` のカスタムタクソノミーは、標準の `tag` と区別できないので、取り込まない。この記録は、スキーマのファイルに定義するようには言わず、`post_tag` を使うことを言う（`1 term of the taxonomy tag is not imported; whiteroom uses the name tag for post_tag`。案）。カスタム投稿タイプの項目も同じで、定義の無いタイプは、数を記録して取り込まない（`attachment`・`nav_menu_item`・`wpcf7_contact_form` など、ほかの変換が扱うものと、`revision`・`wp_block` など、WordPressの内部のものは除く）。
  - 名前：WordPressはエスケープして持つ（`News &amp; Events`）ので、HTMLの文字参照を戻す。改行とタブは空白にして、1行にする。空なら、スラッグにする。どちらも記録する。1MiBを超える名前のタームは、取り込まず、記録する。
  - スラッグ：日本語などのスラッグはWXRではパーセントエンコードされているので、戻してから取り込む（作り方は6.10.5の「スラッグ」。URLは変わらない。6.10.4）。
  - 親：親のスラッグで書かれているので、そのタームのIDに置き換える。親がWXRに無い・取り込まない・自分自身のとき、親が輪になっているとき（輪の中で、IDの文字列順が最も小さいタームの親を外す）、階層の無いタクソノミー（`tag` など）のときは、親を持たずに取り込み、記録する。
  - `language`・`translationGroup`：エントリーと同じく多言語プラグインの情報（上の表）から作る予定だが、いまは使わず、`language` はサイトの既定の言語（6.6.8）にして、翻訳グループはタームごとに作る（キーは6.10.5の「ID」）。
  - 説明：HTMLはタグを除いて文字だけを残し、リンクなど失ったものを取り込みレポートに記録する（6.10.5の「HTMLの文字だけを残す」。6.12の36）。
  - ID：WordPressのタームのID（`term_id`）は引き継がず、新しいIDを振る（`/?cat=123` などのURLは、リダイレクトで転送する。6.10.4）。投稿の無いタームも取り込む。
  - メタデータ：タームのメタデータ（`wp:termmeta`）は取り込まず、キーを取り込みレポートに記録する（10個まで。6.12の34）。
  - 文書の検証（6.7）を通らないタームは、取り込まず、記録する。そのタームを親にしていたタームは、親を持たずに取り込む。
- **添付ファイル**：WXRの添付ファイル（`wp:post_type` が `attachment` の項目）ごとに、メディアを1つ作る。取り込みの規則（案）は、ここに要点を書き、細かい規則・記録の文・上限は6.10.5の「メディア」に書く。ゴミ箱（`trash`）と自動下書き（`auto-draft`）の添付ファイルは、旧サイトで使われていないので、取り込まず、1つずつ記録する。ファイルは、`wp-content/uploads` のコピーから `_wp_attached_file`（`uploads` からの相対パス）で読み、コピーに無いものだけを、旧サイトから `wp:attachment_url`（ファイルのURL）でダウンロードする（片方だけを使ってもよい）。大きな画像を縮小した `-scaled` のファイル、向きを直した `-rotated` のファイル、HEICなどをJPEGに変換したファイルは、`_wp_attachment_metadata`（PHPのシリアライズした形で入る。読み方は6.10.5）の `original_image` に、元のファイルの名前が書かれている。縮小と向きの反映は、このCMSがビルドで原本から行う（6.6.2）ので、元のファイルを先に試して取り込む。使えないとき（見つからない・段階1の形式でない・上限を超える）は、添付のファイル（`-scaled` など）を取り込んで、要確認として記録する。添付のファイルの名前に、WordPressの画像の編集の印（拡張子の前の `-e` と13桁の数字）があるときは、`original_image` が編集する前の画像を指すので、試さずに、編集したファイルを取り込んで、要確認として記録する。`hash`・`size` と、形式・幅・高さ・向きは、ファイルの中身から求める（6.6.2）。`_wp_attachment_metadata` にある大きさは使わず、縮小版（`sizes`）のファイルも取り込まない（派生ファイルはビルドで作る）。ファイルが見つからないものと、中身が段階1の形式でないもの・上限を超えるもの（6.6.2）は取り込まず、取り込みレポートに記録する（ほかの形式は6.12の44）。同じ中身（`hash` が同じ）の添付ファイルは、メディアを分け、原本のファイルは1つにする（6.12の249）。`fileName` は取り込んだファイルの名前にし、6.6.2で使えない文字は、取り込みで直す（`/`・`\` は `-` に置き換え、双方向の書式文字は取り除く。直し方は6.10.5）。画像の `alt` は `_wp_attachment_image_alt` を、`caption` は抜粋（`excerpt:encoded`）を、サイトの既定の言語の値にする（6.6.8）。多言語プラグインの情報から、ほかの言語の値も作れるかは、まだ確かめていない。キャプションのHTMLは、タームの説明と同じく文字だけを残し、失ったものを取り込みレポートに記録する（6.12の36）。PDFには `caption` が無い（6.6.2）ので、PDFの抜粋は、取り込まず、記録する。添付ファイルのタイトルと説明は取り込まない（6.12の47）。説明が空でない添付ファイルは、1つずつ記録し、タイトルは、取り込み全体で1つの記録に、数だけを書く（WordPressは、タイトルをファイル名から付けるので、ほぼすべての添付ファイルにある）。`uploadedAt` は添付ファイルの公開日（`post_date`）にし、投稿の `date` と同じく、`post_date_gmt` との差から時差を求める（求められないときの読み方は6.10.5）。`uploadedBy` は、エントリーの `createdBy`（6.4.1）と同じく、取り込んだ人のアカウントにする（呼ぶ側がIDを渡す。コマンドが、どう受け取るかは #58）。取り込む時刻は使わない（同じ入力から同じ出力にする）。本文の画像・ファイル（6.5.4）とアイキャッチ画像（`_thumbnail_id`）からの添付ファイルの参照は、新しく振ったメディアのIDに置き換える。旧サイトのファイルのURL（`/wp-content/uploads/…`。`-scaled`・`-rotated` のファイルと縮小版も含む）は、リダイレクトで新しいURLへ転送する（行き先はメディアのID。6.6.6・6.10.4）。対応は `MediaURLs` が返す（リダイレクトの登録は、まだ無い。#56）。転送の元のパスは、WXRに書かれたままのURLとファイル名から作り、`fileName` と違って、NFCにそろえず、文字も取り除かない（NFDで書かれたファイル名の旧URLと合わなくなるため。6.5.2）。
- **投稿者**：WXRの `wp:author` にあるのは、ID・ログイン名・メールアドレス・表示名・名・姓だけで、プロフィールの文章（`description`）と著者ページのスラッグ（`user_nicename`）は無い。メールアドレスだけでなく、メールアドレスの形の名前とログイン名も、著者プロフィールの `name` と取り込みレポートに出さない（案）。WordPressは、新しい投稿者の表示名をログイン名にするので、ログイン名がメールアドレスのサイトでは、表示名もメールアドレスになる。`bio` など、旧サイトで公開していた文字の中のアドレスは、そのまま取り込む。`name` には表示名を入れる。旧サイトのREST API（`/wp-json/wp/v2/users`。公開中の投稿がある投稿者だけが返り、無効にされていることもある）から得られれば、その `slug`・`description`・`url`（ウェブサイト）を、`slug`・`bio`・`links` に入れる（`bio` は、サイトの既定の言語の値にする。6.6.8）。メールアドレス・名・姓とアバター（Gravatar）は取り込まず、ログインアカウントも作らない（7.2）。
  - 取り込む投稿者：WXRの投稿者（`wp:author` と、WXR 1.0のように、項目の `dc:creator` のログイン名にだけ出てくるもの）のうち、種類が `post` で、状態が `trash`・`auto-draft` でない項目を書いたものだけ。ほかの投稿者（固定ページやメニューの項目だけを書いたものなど）は、記録して、取り込まない。
  - REST APIとの対応付け：`wp:author_id` が `id` と同じ投稿者を、同じ人とする（REST APIの1人は、1人の投稿者にだけ対応する）。`wp:author_id` が無い投稿者（WXR 1.0）は、ログイン名からWordPressの規則で作ったスラッグ（`user_nicename`。6.10.5の「スラッグ」）が、REST APIの `slug`（戻したもの）と同じで、そのスラッグを持つほかの投稿者がいなければ、その人とする。WXRの投稿者のどれにも対応しないREST APIの投稿者は、記録して、取り込まない。REST APIを使わないときと、対応する投稿者が無いときは、WXRの値だけから作る。旧サイトが `/wp/v2/users` を塞いでいるとき（スナップショットの `unavailable` に経路がある）は、投稿者を使わず、要確認として1つ記録して、同じに作る。
  - `name`：表示名・REST APIの `name`・ログイン名の順に、空でなく、メールアドレスの形を含まず、WXRの `wp:author_email` と同じ（前後の空白と、大文字・小文字を問わない）でもない最初のもの（案）。表示名とREST APIの `name` は、HTMLの文字参照を戻し、改行とタブを空白にしてから確かめる。メールアドレスの形とは、`@` のうち、直前の文字が空白でも `@` でもなく、直後から次の空白か `@` か終わりまでの文字の連なりに、連なりの先頭でも末尾でもない `.` があるものを含むこと（`mary@example.org`。`John <john@example.com>` のように文の中にあるものも含む。`@john.doe`・`john@localhost`・全角の `＠` は、形ではない）。表示名でないものにしたときは、記録する（`the display name is empty; the name is "bob" here`・`the display name is an email address; the name is "Bob B." here`）。どれも使えなければ、スラッグを `name` にして、要確認として記録する（`the names of the author are empty or email addresses; the name is the slug "maryexample-org" here; correct it`）。
  - `slug`：REST APIの `slug`（戻したもの。6.10.5の「スラッグ」）。得られなければ（空のときも）、ログイン名からWordPressと同じ規則で作り、著者ページのURLが変わりうることを、要確認として取り込みレポートに記録する（6.12の170）。メールアドレスの形のログイン名からも、同じ規則で作る（`mary@example.org` は `maryexample-org`。WordPressの `user_nicename` も、ふつうはそうなるので、著者ページのURLを保てる。案）。ほかの投稿者と重なったら、REST APIの `slug` から作ったものが先に取り、ログイン名から作ったものと `author-<ID>` には `-2` などを付ける（6.10.5の「スラッグ」の(7)。案）。
  - `bio`：REST APIの `description`（HTML）から、文字だけを残す（6.10.5の「HTMLの文字だけを残す」。6.12の36）。
  - `links`：REST APIの `url` が http・https のURLのときだけ、1つ。ほかのスキーム（`javascript:` など）のURLは、取り込まず、記録する。メールアドレスの形を含むURL（`mailto:` など）は、記録の文にURLを書かない（`the website is not imported: must be an http or https URL`。案）。
- **メニュー**：WXRには、すべてのコンテンツを書き出したときに、メニューがタクソノミー `nav_menu` のタームとして、メニューの項目が投稿タイプ `nav_menu_item` として入る。メニューごとに、その項目から1つのメニューを作り、`title` はメニューの名前にする。項目は `wp:menu_order` の順に並べ、postmeta の `_menu_item_menu_item_parent`（親の項目の投稿ID）で親子にする。行き先は `_menu_item_type` で決まり、`post_type` では `_menu_item_object_id`（投稿ID）の投稿から取り込んだエントリーを `entry` に、`taxonomy` では `_menu_item_object_id`（タームID）のタームから取り込んだタームを `term` にする（`_menu_item_object` は、`post_type` と `post_type_archive` では投稿タイプ、`taxonomy` ではタクソノミー）。`custom`（カスタムリンク）では `_menu_item_url` を `href` にし、`post_type_archive`（投稿タイプの一覧）では、その投稿タイプのこのCMSでの一覧のパスを `href` にする（6.12の50）。項目の名前（`title`）は `label` にし、名前が空の `entry`・`term` の項目では `label` を省く（6.6.4。WordPressは、行き先と同じ名前の項目を、名前を空にして保存する）。名前の空の投稿タイプの一覧には、サイト設定で定義したタイプの `label`（6.4.4）を入れる（案）。名前に含まれるHTMLのタグは除く。`_menu_item_target` が `_blank` の項目は `newTab` にする（行き先のある項目だけ。6.6.4）。URLが `#` だけのカスタムリンクと、6.5.2の `href` の規則で受け付けないURL（`#top` のようなページ内の位置や、`/` で始まらない相対パスなど。ページ内の位置は6.12の50）のカスタムリンクは、行き先の無い見出しにし、子項目が無ければ取り込まない。名前の空のカスタムリンク（見出しを含む）と、行き先を取り込まなかった項目（取り込まないタイプのエントリーや、WXRに無いものを指す項目、対応付けていない投稿タイプの一覧など）も取り込まず、子項目は、その項目があった位置に並べる（案）。上限（6.6.4）を超える項目は、子項目とともに取り込まない。CSSクラス（`_menu_item_classes`）・XFN（`_menu_item_xfn`）・説明（`post_content`）・タイトル属性（`post_excerpt`）は取り込まない（6.12の50）。取り込まなかった項目・属性・URL（`#` だけのものを除く）と、名前から除いたタグは、どれも取り込みレポートに記録する。表示場所はテーマの設定（`nav_menu_locations`）にあって、WXRには含まれない。多言語プラグインがメニューの言語をどこに持つかも、まだ確かめていない。そこで、取り込むときに、メニューごとに表示場所と言語を指定してもらい（同じ言語・同じ表示場所のメニューは1つまで。6.6.4）、指定が無ければ、表示場所を空にして（どこにも表示しない）、言語をサイトの既定の言語（6.6.8）にする。メニューの表示場所は1つなので、複数の表示場所に出すメニューは、表示場所ごとに複製する（案）。ブロックテーマのナビゲーション（投稿タイプ `wp_navigation`）の取り込みは、まだ確かめていない（6.12の50）。
- **Contact Form 7 のフォーム**：WXRには、すべてのコンテンツを書き出したときに、投稿タイプ `wpcf7_contact_form` として入る。設定は postmeta にあり、タグを含むフォームのテンプレートは `_form`、メールは `_mail`（`recipient`・`sender`・`subject`・`body`・`additional_headers` などの配列で、WXRにはPHPのシリアライズした形で入る。読み方は6.10.5）、2通目のメール（自動返信などに使う）は `_mail_2`、メッセージは `_messages`、追加の設定は `_additional_settings` にある。フォームごとに1つのフォームを作り、`title` はフォームのタイトルにする。`_form` のタグのうち `text`・`email`・`tel`・`textarea`・`select`・`radio`・`checkbox`・`acceptance` を、同じ名前の型の入力の項目にし（`acceptance` は `consent`。6.6.5）、`*` の付いたもの（`[text* your-name]` など）は `required` にする（`consent` には書かない）。`name` はタグの名前にする。Contact Form 7 の名前には使えて、このCMSでは使えない `:`・`.`（6.7）は `-` に置き換え、ほかの項目と同じ名前になるときは、末尾に番号（`-2` など）を付ける（案）。`label` は、タグを囲む `<label>` の中の文字（既定のテンプレートの書き方）から作り、取れなければタグの名前を入れる。選択肢は、その文字を `value` と `label` にする。項目と選択肢の `label` は、サイトの既定の言語（6.6.8）の値にする。`acceptance` の同意の文は、タグで囲んだ中身（`[acceptance 名前] 同意の文 [/acceptance]`。無ければタグの最初の値）なので、それを `label` にする。`optional` の付いた `acceptance`（同意しなくても送れる）は、選択肢が1つの `checkbox` にし、`invert` の付いたもの（チェックすると、同意しないことになる）は取り込まない（案）。同意の文にリンクがあれば文字だけを残し、リンク先が取り込んだ既定の言語のエントリーなら、それを既定の言語の `policy` にする（案）。送信ボタン（`[submit "送信"]`）の文字は、既定の言語の `submitLabel` にする。文字の無い `[submit]` と、`[submit]` の無いフォームでは、Contact Form 7 が表示する既定の文字（`Send` を、WordPressのサイトの言語に訳したもの）を入れる（案）。ほかのタグ（`url`・`number`・`date` など）、タグのオプション（`autocomplete:name` など）と、テンプレートのほかのHTMLは取り込まない（6.12の51）。取り込める項目の無いフォームは作らない（ショートコードと、ブロックエディタのフォームのブロックは `legacy` に残る。6.10.3）。通知先（`notify`）は、`_mail` の `recipient` から作る。WXRから値の分からないメールタグ（既定の `[_site_admin_email]` など）は、取り込むときにアドレスを指定してもらい、6.7の規則で受け付けないアドレスは取り込まない。送信後の表示は、`_messages` の `mail_sent_ok`（送信した後のメッセージ）からHTMLのタグを除いて、既定の言語の `message` にし、`thanksPage` を取れなかった項目は、どれも取り込みレポートに記録する。多言語のサイトでは、項目と選択肢の `label`、`submitLabel` - **旧スラッグと「基本」設定のURL**：`_wp_old_slug` は、公開した投稿のスラッグを変えたときにWordPressが記録する、変える前のスラッグで、1つの投稿に複数あり得る。記録されるのは、階層の無いタイプ（投稿など）と添付ファイルだけで、固定ページには無い。公開日を変えたときの、変える前の日付（`_wp_old_date`。WordPress 4.9.3から）も同じ。エントリーごとに、旧サイトのパーマリンク設定（6.10.4）に変える前のスラッグ（日付を含むURLでは、変える前の日付も）を入れて旧URLを作り、そのエントリーのIDへのリダイレクトを登録する。スラッグと日付は別々に記録され、組にはなっていないので、いまのものと変える前のものの組み合わせごとに旧URLを作る（いまのスラッグといまの日付の組は除く。案）。添付ファイルの `_wp_old_slug`・`_wp_old_date` は、添付ファイルのページを持たない（6.12の47）ので使わない。WordPressは、旧URLのページが見つからないときだけ転送するので、旧URLが、このCMSで出力するパス（4.1）と重なるものは登録しない。複数のエントリーで同じになる旧URLも、`from` の重複（6.6.6）になるので登録しない（案）。どちらも取り込みレポートに記録する。旧URLは、`from` の正規の形（6.6.6）にして登録する。「基本」設定のURL（`/?p=123`・`/?page_id=45`・`/?cat=123`・`/?tag=news`・`/?author=2` など）も、それぞれのエントリー・ターム・著者プロフィールのIDへのリダイレクトで登録する（6.10.4）。取り込みで登録するリダイレクトの `status` は、添付ファイルの旧URLのもの（上記）も含めて、どれも `301` にする（WordPressも、旧スラッグは `301` で転送する）。

#### 6.10.3 自動では変換できないもの

- **ショートコード**：変換できるもの（`[caption]`・`[gallery]`・`[embed]` と Contact Form 7 のショートコード）はブロックにし、ほかは `legacy` に入れて「要確認」にする（対応表は6.12の191）。直すまでは、書いたままの文字として表示する（6.5.4）。Contact Form 7 のショートコードとブロックは、取り込んだフォーム（6.10.1）を参照する `form` ブロックにする（案）。見分け方と変換は、6.10.5の「本文（クラシックエディタ）」の「ショートコード」と、「本文（ブロックエディタ）」の「参照」。
- **ページビルダー（Elementor など）で作ったページ**：レイアウトは作り直す前提とし、本文欄に残っているHTMLだけを `legacy` として取り込む（Elementor の見分け方と、ショートコードで書くページビルダーの扱いは、6.10.5の「本文（クラシックエディタ）」の「ページビルダー」。ほかのページビルダーは6.12の225）。
- **テーマ・プラグイン独自のブロック**：対応表があるものだけを変換し、それ以外は `legacy` にする（対応表は、まだ無い。6.12の191）。WordPressが表示のときにHTMLを作るコアのブロック（最新の投稿・検索・ナビゲーションなど）と、テーマのパターン（`core/pattern`。WXRに無い）も、`legacy` にする（理由の文は、6.10.5の「本文（ブロックエディタ）」の「振り分け」）。

#### 6.10.4 URLの維持

パーマリンク設定の取り込み（案）：

| 共通設定の選択肢 | 共通設定（`permalink_structure`） | 投稿のURLの規則 |
| --- | --- | --- |
| 基本 | 空（投稿のURLは `/?p=123`） | 選んでもらう（既定の規則のままでもよい。6.6.8）。旧URLは、リダイレクトで転送する（下記） |
| 日付と投稿名 | `/%year%/%monthnum%/%day%/%postname%/` | `/{yyyy}/{mm}/{dd}/{slug}/`（既定の規則） |
| 月と投稿名 | `/%year%/%monthnum%/%postname%/` | `/{yyyy}/{mm}/{slug}/` |
| 数字ベース | `/archives/%post_id%`（`archives` は、翻訳によって違うことがある） | `/archives/{number}/`（末尾の `/` は下記） |

| カスタム構造 | 書いたもの（`/%category%/%postname%.html` など） | タグを置き換えたもの（`/{category}/{slug}.html`。下記） |

- タグ：`%postname%` は `{slug}`、`%post_id%` は `{number}`（元の投稿IDを引き継ぐ。6.4.1）、`%year%`・`%monthnum%`・`%day%` は `{yyyy}`・`{mm}`・`{dd}`、`%category%` は `{category}` にする。`%author%`・`%hour%`・`%minute%`・`%second%` に当たる置き換えは持たない（足すかは6.12の63）。これらのタグを使う共通設定と、規則に書けない共通設定（`.htm` で終わるものや、`%category%` を区切りの一部にしたものなど。6.6.8）の扱いは、下記の推測の「書けないとき」。
- 末尾の `/`：WordPressは、共通設定が `/` で終わらないと、投稿だけでなく、固定ページやタームの一覧などのURLからも、末尾の `/` を除く（`/archives/123`、`/about`）。このCMSでは、末尾が `/` でも `.html` でもないパスは作れない（6.6.8）ので、規則の末尾に `/` を足す（「数字ベース」は `/archives/{number}/`）。末尾の `/` の無い旧URLへのリクエストは、サーバーが `/` を付けたURLへ転送する（6.6.8）ので、リダイレクトは登録しない。
- `front`：WordPressは、共通設定の最初のタグより前の部分（`front`。「数字ベース」では `/archives/`、「日付と投稿名」などでは `/`）を、カテゴリーとタグ（カテゴリーベース・タグベースが空のとき）、投稿者、カスタム投稿タイプとその一覧とカスタムタクソノミー（`rewrite` の `with_front` が既定の `true` のとき）のURLの前にも付け、固定ページには付けない。これも、それぞれの規則に書いて再現する（「数字ベース」のサイトでは、カテゴリーは `/archives/category/{path}/`、投稿者は `/archives/author/{slug}/`、カスタム投稿タイプ `works` は `/archives/works/{slug}/` で、一覧があれば `/archives/works/`）。カテゴリーベース・タグベースを書いたサイトでは、`front` を付けずに、ベースの後ろにスラッグが続く（カテゴリーベースが `topics` なら `/topics/{path}/`）。カテゴリーのURLは祖先のスラッグを含み、カスタムタクソノミーは、既定では含まない（6.6.8の既定の規則と同じ。`rewrite` の `hierarchical` を `true` にした、階層のあるものは含むので、`{path}` にする）。
- `%category%`：WordPressは、投稿のカテゴリーのうち `term_id` の最も小さいもの（`term_id` は、すべてのコンテンツを書き出したWXRの、チャンネルの `wp:category` にある）と、その祖先のスラッグを使う。カテゴリーの無い投稿では、既定のカテゴリー（`default_category`）のスラッグを使う。取り込みでは、そのカテゴリーを `terms` の `category` の最初に置く（6.6.8）。既定のカテゴリーは、WXRにも、ログインせずに読めるREST APIにも無いので、共通設定に `%category%` があるときは、カテゴリーの無い投稿の `link` から推測し（下記の推測。WordPressの既定は、`term_id` が1のカテゴリー）、取り込みの設定の `defaultCategory`（戻したスラッグ）に書き出して、確かめて（直して）もらう。カテゴリーの無い投稿には、そのカテゴリーを付けて、取り込みレポートに記録する（エントリーの変換が行う）。使うカテゴリーは、プラグインが `post_link_category` のフィルターで変えられる（SEOプラグインの主カテゴリーがこれを使うかと、主カテゴリーをどこに保存するかは、まだ確かめていない）。`term_id` の最も小さいカテゴリーでは `link`（下記の推測）と合わない投稿は、ほかのカテゴリーのうち合うものを最初に置く。投稿ごとに `link` が使ったカテゴリーの決め方は、6.12の168。
- 日付：WordPressは、`%year%`・`%monthnum%`・`%day%` を、投稿の `post_date`（公開日の、サイトの時刻）で数える。取り込んだ投稿の `date` は、`post_date` に、`post_date_gmt` との差から求めた時差を付けたもの（6.10.1）で、`{yyyy}`・`{mm}`・`{dd}` は `date` に書いた時差で数える（6.6.8）ので、URLの日付も同じになる。取り込んだ後にタイムゾーン（`timeZone`）を変えても、変わらない。
- 推測：パーマリンク設定（共通設定・カテゴリーベース・タグベース）は、WXRにもREST APIにも無い。そこで取り込みでは、`link`（書き出したときのURL）から規則を推測し、取り込みの設定（6.10.5）に書き出して、ほかのサイト設定（6.10.1）と一緒に、取り込む前に確かめて（直して）もらう。規則は、取り込みが新しいサイトのディレクトリに作るスキーマのファイル（6.6.8）に、開発者が定義したタイプとタクソノミーに足して書く（6.10.5）。
  - 対象：エントリーの規則は、種類が `post` の項目、`page` の項目、スキーマのファイルで定義したカスタム投稿タイプの項目の `link` から推測する。タクソノミーの規則は、旧サイトのREST APIが返す各タームの `link`（`/wp-json/wp/v2/categories`・`/wp-json/wp/v2/tags` など。カスタムタクソノミーは、`show_in_rest` を有効にしたものだけ）から、著者ページの規則は、投稿者の `link`（`/wp-json/wp/v2/users`）から推測する。スキーマのファイルに書かれたURLの規則と一覧のパスは、推測で書き換えず、推測と違うときは要確認として記録する（6.10.5の「取り込みの設定」）。
  - 使う `link`：`http`・`https` で、ユーザー名・クエリ・フラグメントが無く、ホストとポートが、ホームのURL（WXRの項目はチャンネルの `link`、REST APIのタームと投稿者は一覧の `home`）と同じで、ホームのパスの下にあるものだけを使う（ホストは大文字と小文字を問わない。ポートは、省いたときの既定どうしも同じ）。ホームのURLより後ろのパスを、`from` の正規の形（6.6.6）にして比べる。「基本」の形の `link`（`/?p=123`・`/?cat=123` など。下書きなどのエントリーの `link` も、この形になる）は、クエリがあるので使わない。固定ページのトップページ（パスが `/`）も使わない。ホストの違う `link`（ドメインを移したサイトなど）も使わない。
  - 構造の探し方：`link` のパスを、そのエンティティの値と文字に分けたものを、WordPressのタグの構造の候補にする。値は、投稿が `%postname%`（スラッグ）・`%post_id%`・`%category%`（カテゴリーと祖先のスラッグのパス。付いたどのカテゴリーでもよい）・`%year%`・`%monthnum%`・`%day%`・`%hour%`・`%minute%`・`%second%`（`post_date`）・`%author%`（投稿者のスラッグ。REST APIの `slug`、無ければログイン名から作ったもの）、固定ページが `%pagename%`（祖先を含むパス）、カスタム投稿タイプがスラッグ（階層のあるものは、祖先を含むパスも）、カテゴリーが祖先を含むパス、タグがスラッグ、カスタムタクソノミーがスラッグ（REST APIで階層ありのものは、パスも）、著者ページがスラッグ。スラッグは、戻さず、小文字にもNFCにもせずに、`link` のパスと同じく `from` の正規の形（6.6.6）にして比べる。最も多くの `link` に合う構造を選ぶ。同じ数のときは、文字（タグでない部分）が少ないもの、要素が少ないものを選び、それでも決まらなければ、文字より先にタグを、タグは、スラッグ（`%postname%` など）・パス（`%pagename%` など）・`%post_id%`・`%category%`・`%year%`・`%monthnum%`・`%day%`・`%author%`・`%hour%`・`%minute%`・`%second%` の順に選ぶ。
  - 規則にする：タグを、上のタグの置き換えで規則にする（固定ページと階層のあるものの `path` は `{path}`、ほかのスラッグは `{slug}`）。最後の区切りに `.` が無く、末尾が `/` でも `.html` でもなければ、`/` を足す（上記の「末尾の `/`」）。スキーマのファイルの検証（6.6.8）を通るものだけが、規則になる。タクソノミーと著者ページの規則は、`/` で終わるものだけ。
  - 書けないとき：最も多くの `link` に合う構造が規則に書けない（`%author%`・`%hour%`・`%minute%`・`%second%` を使う、`.htm` など `.html` 以外の拡張子で終わる、検証を通らない）ときは、上位の候補のうち、書けるもので最も多くの `link` に合うものを規則にする（`/admin/{slug}/` のように、ある投稿者や時刻の文字を含み、一部の `link` にしか合わないことがある）。書けるものが無ければ、既定の規則にする。どちらも、要確認として記録する。
  - `link` が無いとき：パスのある `link` が無いとき（「基本」の設定）と、REST APIが無い・経路が塞がれている・項目が無いときのタクソノミーと著者ページは、WordPressの既定とみなして、既定の規則にし、要確認として記録する。投稿は `/{yyyy}/{mm}/{dd}/{slug}/`（6.6.8）。ほかは、`front`（投稿の構造の最初のタグより前の部分。構造が無いときと、タグが無いときは `/`）から作る：固定ページが `/{path}/`（`front` は付かない。`front` が `/index.php/` で始まるサイトでは、`/index.php/{path}/`）、カテゴリーが `front` + `category/{path}/`、タグが `front` + `tag/{slug}/`、著者ページが `front` + `author/{slug}/`、カスタム投稿タイプ `works` が `front` + `works/{slug}/`、カスタムタクソノミー `genre` が `front` + `genre/{slug}/`。`front` を付けた規則が検証を通らない（`front` に `%20` が入るなど）ときは、6.6.8の既定の規則にする。
  - 一覧：カスタム投稿タイプの一覧のパスは、REST APIの投稿タイプの `has_archive` から決める。`true` なら、規則の最初の `{` より前の、最後の `/` までの部分（`/works/{slug}/` なら `/works/`。規則にディレクトリが無ければ、パスは決められないので、一覧なしにして記録する）。文字列（`portfolio`）なら、規則が `front` で始まり、`front` が `/` でないとき（`with_front`）は、`front` の後ろに文字列と `/` を続け（`/archives/portfolio/`）、そうでなければ `/portfolio/`。`false` なら一覧なし。REST APIが無い、投稿タイプが無い、`has_archive` が無いときは、一覧なしにして、要確認として記録する。
  - 既定のカテゴリー：投稿の構造に `%category%` があるときだけ求める。カテゴリーの無い投稿の `link` にあるカテゴリーのスラッグ（最も多いもの。同じ数なら、WXRで先のカテゴリー）にする。`link` から分からず、カテゴリーの無い投稿（`trash`・`auto-draft` を除く）があるときは、WXRに `term_id` が1のカテゴリーがあればそれ（WordPressの既定）にし、無ければ空にして、指定を求める。
  - 記録：種類（投稿・固定ページ・カスタム投稿タイプごと・タクソノミーごと・著者ページ）ごとに1つ、要確認として、チャンネルの位置に記録する。行き先は、スキーマのファイルの規則の位置（`/types/post/url`・`/types/page/url`・`/types/<名前>/url`・`/taxonomies/<名前>/url`・`/authorUrl`。一覧は `/types/<名前>/archive`）。構造・合った `link` の数・規則を示し、合わない `link` があれば、その数（リダイレクトが要る）を示す。例（見本のサイト。`internal/wpimport/testdata/out/propose.txt`）：`site.xml:12:1: review: channel: inferred the permalink structure "/%year%/%monthnum%/%day%/%postname%/" of posts from 3 of 3 links; the URL rule is "/{yyyy}/{mm}/{dd}/{slug}/" -> site/schema.yaml#/types/post/url`。規則に書けないときの例：`the permalink structure "/%postname%.htm" of posts, which 2 of 2 links follow, cannot be a URL rule: a URL rule must end with "/" or ".html", not ".htm"; the URL rule is the default "/{yyyy}/{mm}/{dd}/{slug}/"`。
  - 上限：候補を作る `link` は、最初の16個（IDの順）で、1つから256個まで。数えるのは、全体から等間隔に選んだ256個までで、上位8個を、すべての `link` で数え直す。パスと値は8192バイトまで、祖先をたどるのは100段まで。この中で、同じ入力からは、いつも同じ結果になる。限界は6.12の167、プラグインが変えるパーマリンクは6.12の166。
  - リダイレクト：`link` のパスと、規則で求めたパスは、どちらも `from` の正規の形（6.6.6）にして比べる。推測の段階が記録するのは、規則に合わない `link` の数まで。違うエンティティ（スラッグが正規化で変わったものや、階層のあるカスタム投稿タイプの子など）の記録と、`link` のパスから、そのエンティティのIDへのリダイレクトの登録（出力するパスと重なるものや、複数のエンティティで同じになるものの扱いは、旧スラッグと同じ。6.10.1）は、リダイレクトの変換が行う（まだ無い）。末尾の `/` だけが違うものは登録しない（上記）。

ほかのURL：

- 日本語スラッグ（パーセントエンコードされたURL）も、そのまま維持する。
- 一覧：ページ送りは、WordPressと同じ形にする（`/page/2/`、`/category/news/page/2/`。6.6.8）。日付のアーカイブ（`/2026/10/` など。共通設定の最初の3つのタグに `%post_id%` があれば、`front` の後ろに `date/` が入る）を出力するかは6.12の39。
- トップページ：表示設定でホームページに固定ページを表示するとき、WordPressは、その固定ページのURLを `/` にし、その固定ページのパス（`/home/`）へのリクエストも `/` へ転送する（`redirect_canonical`）。このCMSでも、`frontPage` の固定ページは言語のパスに出力し（6.6.8）、規則のパス（`/home/`）からは、言語のパスへ301で転送する（案。ビルドが作るリダイレクト。6.6.6）。子の固定ページのパスは、どちらも、トップページのスラッグを含む（`/home/child/`）。
- 「基本」設定のURL（`/?p=123`）は静的ファイルとして置けないため、リダイレクトで新しいURLへ転送する（行き先はエントリーのID。6.6.6）。固定ページの `/?page_id=45` と、カテゴリー・タグ・投稿者の `/?cat=123`・`/?tag=news`・`/?author=2` なども同じで、行き先はエントリー・ターム・著者プロフィールのID（案。6.10.1）。
- 旧スラッグ（`_wp_old_slug`）と変える前の日付（`_wp_old_date`）から作る旧URLも、リダイレクトでエントリーへ転送する（案。6.10.1）。
- 取り込んだ画像とPDFの旧URL（`/wp-content/uploads/…`。縮小版などを含む）も、リダイレクトで新しいURLへ転送する（案。行き先はメディアのID。6.6.6・6.10.1）。旧URLとメディアの対応は、メディアの変換の後に、`MediaURLs` が返す（入るものと入らないものは、6.10.5の「メディア」の「旧URLの対応」）。リダイレクトの登録は、まだ無い（#56）。
- 多言語プラグインが使っていた言語ごとのURL（`/en/` など）は、6.6.8の言語のパス（言語コードを小文字にしたもの。`en-US` は `/en-us/`）に合わせ、異なる場合はリダイレクトで転送する。多言語プラグインがどんな形のURLを使うかは、まだ確かめていない（言語のパスを、言語コードと違うものにできるようにするかは6.12の30）。
- RSSのURL（`/feed/`）も同じ場所に生成し、購読者を引き継ぐ（案。ビルドは、言語ごとのRSS 2.0のフィードを、言語のパスの後ろの `feed/` に出力する。`/feed/`・`/en/feed/`。6.6.8）。`prefixDefaultLanguage` のサイト（6.6.8）では、既定の言語のフィードも `/ja/feed/` になるので、`/feed/` を保つには、`/ja/feed/` へのリダイレクト（6.6.6）が要る。カテゴリーなどの一覧ごとのフィードは、いまは出力しない（6.12の39）。

#### 6.10.5 取り込みの処理（案）

WordPressからの取り込みは、WXR（WordPressの「ツール」→「エクスポート」で、すべてのコンテンツを書き出したファイル）と、あれば旧サイトのREST APIから、サイトのディレクトリ（4.3）を作る。この節の規則は、どれも仮に決めたもの（案）。6.10.1〜6.10.4で「取り込みレポートに記録する」としたものは、どれも、この節の形で記録する。

**流れ**

- 読み込み → 推測と取り込みの設定 → 計画 → サイト設定 → ターム・著者プロフィール → メディア・エントリー → 書き出しの順に進む。この順が要る（下記）。
- 読み込み：1つのWXRを読み（まとめて読むかは6.12の143）、値を、書かれたままメモリに持つ。取り込みレポートも、ここで作り、取り除いた文字とコメントを記録する（下記の「WXRの読み込み」「取り込みレポート」）。旧サイトのREST APIを使うときは、その応答（スナップショット）も読む（下記の「REST APIの読み込み」）。
- 推測と取り込みの設定：WXRとスナップショットから、サイト設定とURLの規則を推測して、取り込みの設定（JSONのファイル）に書き出す。人は、取り込みレポートの根拠と確かめる値を見て、ファイルを直す。取り込みは、直したファイルを読んで進める（下記の「取り込みの設定」）。この段階は、IDの割り当てと変換をしない。
- 計画：取り込むものを決め、WordPressのオブジェクト（投稿・ターム・投稿者）ごとに、IDを割り当てた表を作る（下記の「ID」）。エントリーとメディアは、ここで、すべてにIDを割り当て、参照を記録する：エントリーはタイプ（スキーマのファイルでの名前）と言語（取り込みの設定の `site.language`）を、メディアは種類（画像かPDFか）を、WXRの項目から決める。メディアの部分は `PlanMedia` で、種類は、添付のファイルの名前が `.pdf` で終わるかで見込み、メディアの変換が、ファイルの中身から直す（下記の「メディア」）。サイト設定とあとの変換は、この記録を、検証の照会（6.7）で引く。
- サイト設定（`Site`）：取り込みの設定から作る（下記の「取り込みの設定」の「サイト設定」）。トップページ・投稿ページ・ロゴ・アイコンを、計画の表と参照で引くので、計画の後でなければならない（前に作ると、これらは、すべて取り込まなかったことになる）。ロゴとアイコンは、メディアの変換（`Media`）が、取り込めなかったものを、あとで外す（下記の「メディア」）。
- ターム・著者プロフィール（`Terms`・`Authors`）：サイト設定を渡して作る（既定の言語とタクソノミーの定義を使う）。サイト設定の後で、エントリーの前でなければならない（エントリーが、これらのIDを引く）。
- メディア・エントリー：メディア（`Media`。下記の「メディア」）を先に、エントリーを後に変換する（エントリーが、取り込めなかったメディアを指さないように）。メディアの変換はあり、エントリーの変換は、まだ無い（#55）。エントリーの変換は、取り込む項目ごとに `Body` を1回呼んで、本文のブロックの列を得る（渡すものと返すものは、下記の「本文（ブロックエディタ）」の「入口」）。参照（本文の画像・アイキャッチ画像・メニューの行き先・親・タームと著者プロフィールなど）は、表を引いて、IDにする。取り込めなかったもの（ファイルの無い添付ファイルなど）は、表から外して、それを指す参照を、無いものとして扱い、記録する。ロゴとアイコンのメディアが取り込めなかったときは、メディアの変換が、サイト設定から外して記録する（下記の「メディア」の「ロゴとアイコン」。6.12の174）。
- 書き出し：変換したエンティティを、サイトのディレクトリ（4.3）に書く（#58）。いまの変換は、文書をGoの値で返すだけで、ファイルは書かない。ただし、メディアの変換（`Media`）は、原本だけは、サイトのディレクトリの `files/` に書く（形式を読んでから、残すか捨てるかを決めるので、変換の中で書く。メディアの文書は、Goの値で返す。下記の「メディア」）。
- 推測と変換は、呼ぶたびに取り込みレポートへ記録を足すので、1つの取り込みで、1回ずつ呼ぶ（`Body` は、項目ごとに1回）。推測と取り込みで、別の取り込み（`Import`）と別のレポートを使うのは、このため。
- どの段階も、取り込まなかったもの・変えたもの・要確認のものを、取り込みレポートに記録する（下記の「取り込みレポート」）。

**WXRの読み込み**

- 版：WXR 1.0（WordPress 3.0まで）・1.1（3.1〜3.3）・1.2（3.4から）を読む。`wp:wxr_version` がほかの値なら、エラー（`unsupported WXR version "1.3"; use 1.0, 1.1 or 1.2`）。WordPressの版は、読むかどうかには使わず、分かれば取り込みレポートに記録する。ルートの前の `generator` のコメント（`<!-- generator="WordPress/6.8.3" … -->`。`WordPress` の大文字と小文字は問わない。WordPress 3.0は小文字で書く）から読み、無ければ、チャンネルの最初の `<generator>` の要素（`https://wordpress.org/?v=6.8.3`）から読む。どちらにも無ければ、空にする。
- 文字コード：UTF-8だけを読む。XML宣言の `encoding` が、無いか、`UTF-8`・`utf8`・`US-ASCII`（大文字と小文字は問わない）のものを読み、先頭のBOMも受け付ける。ほかの文字コードの宣言（`EUC-JP` など）とUTF-16は、エラーにして、UTF-8に変換してもらう（`unsupported encoding "EUC-JP"; convert the WXR to UTF-8`、`UTF-16 is not supported; convert the WXR to UTF-8`。6.12の142）。不正なUTF-8は、どこにあってもエラー。
- 読むもの：チャンネルの `title`・`link`・`description`・`pubDate`・`language`・`generator`・`wp:wxr_version`・`wp:base_site_url`・`wp:base_blog_url`、`wp:author`、`wp:category`・`wp:tag`・`wp:term`（と、それぞれの `wp:termmeta`）、項目（`item`）の、WordPressの書き出しの関数（`export_wp`）が書く子（`wp:post_id`・`wp:post_type`・`wp:post_name`・`wp:status`・`content:encoded` など）・`category` の要素・`wp:postmeta`。ターム（`wp:category`・`wp:tag`・`wp:term`）のタクソノミーは、`wp:category` が `category`、`wp:tag` が `post_tag`、`wp:term` が `wp:term_taxonomy` の値（メニューの `nav_menu` も `wp:term`）。`wp:comment` は、数だけを数え、中身は読まない（コメントは取り込まない。6.10.1）。
- 要素の見分け方：名前空間のURIで見分け、接頭辞の字は見ない（ファイルが `w:` と書いても、`wp:` と同じ）。`wp:` は `http://wordpress.org/export/1.0/`・`1.1/`・`1.2/`、`excerpt:` は、その後ろに `excerpt/` を付けたもの、`content:` は `http://purl.org/rss/1.0/modules/content/`、`dc:` は `http://purl.org/dc/elements/1.1/`。名前空間の無い要素は、RSSのもの（`title`・`link` など）。
- 値：書かれたままにする。`]]>` を含む値を分けて書いたCDATA（`]]]]><![CDATA[>`）は、つないで読む。改行は、XMLの規則で、CRLFもCRもLFになる（CDATAの中も）。前後の空白は残し、整数と `wp:wxr_version` だけ、前後の空白を除く。日時・状態・投稿タイプなどの意味は、読み込みでは決めない。スラッグはパーセントエンコードのまま読む（下記の「スラッグ」）。
- 受け付けるもの：XML宣言の前の空白、知らない要素（読まずに無視する。`rss2_head` が書く `image` など。入れ子のものも）、WordPressの書き出しが宣言しない接頭辞の要素（プラグインが `rss2_head` で、宣言せずに書く `atom:link` など。PuSHPressは `<atom:link rel='hub' …/>` を書く。知らない要素として、読み飛ばす。下記の「エラーにするもの」の接頭辞は除く）、コメントと処理命令（どこにあっても）、省かれた要素。
- WXR 1.0と1.1：1.0には、`wp:author` と `wp:term_id` が無い（投稿者は、項目の `dc:creator` のログイン名だけ。タームは、スラッグで引く）。1.0は、属性の無い `category` の要素（名前だけ）も書くので、読まない。項目の `category` の要素は、`domain` と `nicename` の両方が空でないものだけを読み、`domain` が `tag` のものは `post_tag` にする。WordPress 3.0（WXR 1.0）は、チャンネルに `<generator>` を2つ書く（書き出しの関数が書くものと、`rss2_head` が書くもの）ので、`<generator>` はいくつあってもよく、最初のものを使う。古いWordPress（WXR 1.0・1.1を書くもの）は、`]` で終わる値の後ろに空白を足し（`[告知] `）、`]]>` を含む値を分けずに書いて、XMLを壊すことがある。足された空白は、書かれたままなので残る（6.12の145）。
- タームのID：WordPress 4.2より前は、別のタクソノミーのタームが同じIDを持つことがあるので、`wp:term_id` は、タクソノミーと組で引く。
- エラーにするもの（どれも、最初の1つで止める。位置は下記）：
  - 空の入力（`not a WXR file: missing <rss>`）、ルートが `rss` でないもの、`channel` が無いもの・2つあるもの、`wp:wxr_version` が、投稿者・ターム・項目より前に無いもの。
  - DOCTYPE。コメントとCDATAでない `<!` の宣言は、どこにあっても（`DOCTYPE is not allowed`）。
  - 宣言の無い名前空間の接頭辞のうち、WordPressの書き出しが宣言するもの（`wp`・`excerpt`・`content`・`dc`・`wfw`）の要素（`undeclared namespace prefix "wp"`）。ほかの宣言の無い接頭辞の要素（`atom:link` など。上記の「受け付けるもの」）と、接頭辞の付いた属性は、エラーにしない。
  - 名前の文字参照のうち、XMLの5つ（`&lt;`・`&gt;`・`&amp;`・`&quot;`・`&apos;`）のほか（`&nbsp;` など。`invalid XML: invalid character entity &nbsp;`）。数値の文字参照（`&#12354;`）は読む。
  - ルートの外の文字（WordPressが書き出しに混ぜたPHPの警告など。`unexpected text outside <rss>; WordPress may have written a PHP message into the export`）と、2つ目のルート。
  - 必須の要素が無いもの（空白だけの値も、無いものとする。`missing <wp:post_id> in <item>`）：`wp:wxr_version`、項目の `wp:post_id` と `wp:post_type`、タームのスラッグとタクソノミー（`wp:term` は `wp:term_taxonomy`）、投稿者のログイン名、メタデータの `wp:meta_key`。
  - 正しくない整数（`invalid <wp:post_id> "abc": use an integer from 1`）：`wp:post_id`・`wp:term_id`・`wp:author_id` は1以上、`wp:post_parent` は0以上、`wp:menu_order`・`wp:is_sticky` は整数。
  - 重なり：同じ `wp:post_id`、同じタクソノミーの同じ `wp:term_id`（1以上のとき）か同じスラッグ、同じログイン名、1つのレコードに1つだけのはずの要素（`wp:meta_value` など。`duplicate <wp:meta_value> in <wp:postmeta>`）。
  - 値の要素の中の要素（`<title><b>x</b></title>`。`unexpected element <b> in <title>`）と、レコードの中の、要素の間の文字（`unexpected text in <item>`）。
  - XMLで使えない文字のうち、取り除けないもの（下記）。
  - ほかのXMLとしての誤り（`invalid XML: …`）と、上限（下記）。
- XMLで使えない文字：タブ・LF・CRのほかのC0制御文字（U+0000〜U+001F）と、U+FFFE・U+FFFFは、XML 1.0で使えない。WordPressの書き出しは、データベースにあるこれらの文字（文章に紛れ込んだU+0008やU+000B）を、そのまま書くことがあるので、文字・CDATAの中・属性の値・コメントの中・処理命令の中にあるものは、エラーにせず、取り除いて読む（取り除いた文字は、正規化（6.7）でも消える）。値（値の要素の中身と、`category` の要素の属性の値）から取り除いたものは、レコード（チャンネル・投稿者・ターム・項目）ごとに、取り込みレポートに「変えた」（`changed`）として、最初の文字の位置とともに記録する（`removed 2 characters that XML does not allow: U+0003 at 7:10, U+0003 at 7:14`。10個までを並べ、残りは `, and 3 more`）。コメントの中身・知らない要素・`wp:comment`・要素の間のものは、読まない部分なので、取り除くだけで記録しない。`&#8;` のような数値の文字参照は、取り除かずに、エラーにする（`invalid XML: illegal character code U+0008`）。
  - 取り除けないもの：取り除くと `]]>`（CDATAの終わり）・`-->`（コメントの終わり）・`?>`（処理命令の終わり）ができるもの（`]]` と `>` の間、`]` と `]>` の間のように、区切りの文字の間にあるもの）と、マークアップの中にあるもの（`<` の直後、タグの名前や属性の名前など、引用符の外のタグの中、`<!` の後、`<![CDATA[` の途中、宣言の中）は、エラーにする。区切りの前にあるもの（`]]<U+000B>]]>`・`<U+000B>]]>`）は、区切りの文字の間にはなく、取り除いてもCDATAの終わりが変わらないので、読める。
  - 理由：WordPressは、値の中の `]]>` だけを分けて書く（`]]]]><![CDATA[>`）ので、データベースの値に `]]` と制御文字と `>` を書くと、そのまま書かれる。取り除くとCDATAがそこで終わり、値の残りがマークアップになって、項目などを差し込めてしまう（コメントと処理命令の終わりも同じ）。タグの中のものは、WordPressの書き出しには無く、取り除くと、XMLでないものが正しいタグになる（`<ti<U+000B>tle>`）。
  - エラーの文は、英語で、文字のコードポイントと、どこにあるかを示す：区切りは `character U+000B that XML does not allow is in "]]>"`（`"-->"`・`"?>"` も同じ形）、`<` の直後と引用符の外のタグの中は `character U+000B that XML does not allow is in a tag`、`<!` と `<!-` の後と宣言の中は `… is in a declaration`、`<![CDATA[` の途中は `… is in "<![CDATA["`。

**位置とエラー**

- 位置：行と列で示し、どちらも1から数える。行はLFで数え、列は文字（コードポイント）で数える（タブもCRも1文字。取り除いた文字も数え、先頭のBOMは数えない）。
- 形：最初のエラーで止める。取り込み（`wpimport.Read`）は、ビルドのエラー（4.3の「エラーと警告」）と同じく、ファイルの名前を前に付けて、`wordpress.xml:12:5: …` と示す（ファイルは、渡した名前）。ファイルを読めないエラーは、位置の無い `reading the WXR: …` になる。
- 位置の決め方：`encoding/xml` が見つけた構文の誤り（`invalid XML: …`）は、見つけたところ（多くは、誤りの直後）。不正なUTF-8・ファイルの大きさの上限・タグの長さの上限は、そのバイトか、そのタグの `<`。取り除けないXMLで使えない文字は、その文字（区切りの間に複数あれば、最初のもの）。思いがけない文字（PHPの警告など）は、空白でない最初の文字。ほかは、その要素の開始タグ（必須の要素が無いものと、IDなどの重なりは、レコードの開始タグ。1つだけのはずの要素の重なりは、2つ目の要素の開始タグ）。
- 例（それぞれ、別のWXRのエラー）：
  - `wordpress.xml:7:11: invalid UTF-8; the WXR must be in UTF-8`（7行目の `<title>あいう` の後に、不正なバイトがある。列は文字で数えるので、日本語の3文字の後は11列目）
  - `wordpress.xml:5:14: invalid XML: element <item> closed by </post_id>`（`<item>` を、`</wp:post_id>` で閉じた。終了タグの直後）
  - `wordpress.xml:8:1: duplicate wp:post_id 1; the first is at 4:1`（同じ `wp:post_id` の項目が2つある。2つ目の `<item>` の位置）
  - `wordpress.xml:4000004:1: too many items: at least 1000001 (max 1000000)`（項目が100万個を超えた。1000001個目の `<item>`）
  - `wordpress.xml:1:1: unexpected text outside <rss>; WordPress may have written a PHP message into the export`（ファイルの先頭に、PHPの警告の文がある）
  - `wordpress.xml:7:20: character U+000B that XML does not allow is in "]]>"`（7行目の `<title><![CDATA[x]]` の後にU+000Bがあり、`>` が続く。取り除くと `]]>` ができて、CDATAが終わるので、取り除かずにエラーにする。列は、U+000Bの位置）
  - `wordpress.xml:7:4: character U+000B that XML does not allow is in a tag`（7行目の `<ti` の後にU+000Bがある。取り除くと `<title>` になるので、エラーにする）

**REST APIの読み込み**

- 目的：WXRに無い設定（タイムゾーン・トップページ・ロゴとアイコン。6.10.1）と、パーマリンクの推測に使うタームと投稿者の `link`（6.10.4）と、投稿者のプロフィール（6.10.1）を、旧サイトの公開のREST API（ログインせずに読める）から読む。読む処理は `internal/wprest`。旧サイトにつなぐか、保存したスナップショットのファイルを使うか、REST APIを使わないかは、呼ぶ側（コマンド。#58）が決める。REST APIを使わないと、足りない値は、取り込みの設定で入力してもらう（6.10.1）。
- 経路：ホームのURL（チャンネルの `link`）の `/wp-json/` を読み、読めなければ `/?rest_route=/` を読む。REST APIの索引（一覧）は、`namespaces` の配列を持つJSONのオブジェクトで、パーマリンクが「基本」のサイトは、`/wp-json/` に404やHTMLのページを返すので、次の経路を試す。どちらも読めなければ、エラー（`no REST API at <ホームのURL>: <URL>: <理由>; <URL>: <理由>`）。REST APIのルートのURLを渡せば、探さずに、それを使う。`Link` ヘッダーでの発見と、`wp-json` でない接頭辞は、まだ扱わない（6.12の165）。
- 読むもの：一覧、タクソノミー（`/wp/v2/taxonomies`）、投稿タイプ（`/wp/v2/types`）、各タクソノミーのターム（`/<rest_namespace>/<rest_base>`。`category` は `/wp/v2/categories`、`post_tag` は `/wp/v2/tags`）、投稿者（`/wp/v2/users`）。要求の `_fields` で、読む項目を絞る：一覧は `name,description,url,home,gmt_offset,timezone_string,show_on_front,page_on_front,page_for_posts,site_logo,site_icon,namespaces`（`site_logo` と `site_icon` は、求めたときだけ一覧に入る）、タームは `id,taxonomy,slug,name,parent,link`、投稿者は `id,name,slug,description,url,link`。タクソノミーと投稿タイプの応答は、名前をキーにしたオブジェクトで、WordPressの `rest_filter_response_fields` は、数字の添字の配列でない応答には、`_fields` を最上位のキー（名前）に当てるので、項目が消える。そこで、この2つは `_fields` を付けずに、全体を読む。
- ページ送り：タームと投稿者は、`per_page=100&page=<n>&order=asc&orderby=id` で読む。`X-WP-TotalPages` のページ数まで読み、無ければ、100件に満たないページまで読む。空のページと、最後のページの後に WordPress が返す `400` でも止める。前のページの項目を繰り返すページ（`page` を無視するサイト）は、エラー（`page 2 repeats the items of the pages before it; the site may ignore the page parameter`）。IDが重なる項目は、最初のものだけを使う。上限の件数に要るページ数より1ページ多く読んでも続くときも、エラー（`more than <ページ数> pages of terms`。投稿者は `users`）。
- 読まないタクソノミー：`nav_menu`・`wp_pattern_category`・`wp_theme`・`wp_template_part_area`・`post_format`・`link_category` と、Polylang の `language`・`term_language`・`post_translations`・`term_translations` のタームは読まない（タクソノミーの一覧には残る）。`/wp/v2/taxonomies` が塞がれていれば、`category` と `post_tag` だけを読む。
- 経路を作らないもの：`rest_base`・`rest_namespace` が、英数字・`.`・`_`・`-` の部分を `/` でつないだもの（空の部分、`.`、`..` は不可）でないタクソノミーは、サイトの返した値で別の場所を指せないよう、経路を作らず、要求を送らない（`invalid_route` として記録する）。
- 塞がれた経路：経路（ターム・投稿者は最初のページ）の応答が、`4xx`（`408` と `429` を除く）か、JSONでない `2xx` のときは、塞がれたもの（ログインの要る `users`、セキュリティプラグインなど）として、経路・タクソノミー・状態・WordPressのエラーコード（`rest_user_cannot_view` など。エラーの応答の本文から読む）を `unavailable` に記録して、続ける。使う側が、取り込みレポートに記録する（投稿者は6.10.1、URLの規則と一覧は6.10.4）。
- エラー：一覧が読めないとき、2ページ目以降の `4xx`（最後のページの後の `400` を除く）、`408`・`429`・`5xx`、繋がらない、応答がJSONでない・誤っている、上限を超える、転送の違反、時間切れは、エラーにして止める。メッセージは、どの要求かを示す（`GET <URL>: 500 Internal Server Error`）。再試行はしない（6.12の165）。
- 転送：同じサイトの中だけを、5回まで追う（`http` から `https` への転送は、同じサイト）。別のサイトへの転送はエラー（`redirected to <URL>, which is not on <スキーム>://<ホスト>; read the REST API there`）、ユーザー名のあるURLへの転送もエラー（`redirected to <URL>, which has credentials in it`）、6回目の転送もエラー（`stopped after 5 redirects`）。
- 送るもの・送らないもの：`GET` だけを、1つずつ送る。ヘッダーは `Accept: application/json` と `User-Agent: whiteroom-wpimport` だけで、Cookie・認証・Refererは送らない。
- 値は返されたまま：スラッグはパーセントエンコードのまま、名前はHTMLの文字参照のまま、プロフィールはHTMLのままで、戻すことと正規化は、取り込む側が行う（下記の「スラッグ」「HTMLの文字だけを残す」）。
- スナップショット：読んだものは、スナップショットとして持ち、JSONのファイルに書き、読み戻せる。旧サイトが無くなった後でも、同じ入力から取り込み直せる（同じ入力から同じ出力にする。4.3）。2つの空白で字下げし、末尾に改行を付ける。最上位のキーは `api`（読んだREST APIのルート）・`index`（一覧。いつも書く）・`taxonomies`・`types`・`terms`・`users`・`unavailable`。中のオブジェクトのキーは、WordPressのキー（`slug`・`name`・`rest_base`・`has_archive`・`page_on_front`・`gmt_offset` など）のままで、0・空の文字列・空の列は書かない。`has_archive` は `false`・`true`・文字列、`gmt_offset` は文字列で書く。列は決まった順（タクソノミーと投稿タイプはスラッグ、タームはタクソノミーとID、投稿者はID、`unavailable` は経路・タクソノミー・状態・コード）に並べるので、同じ値は同じファイルになる。見本は `internal/wpimport/testdata/site-rest.json`。読むときは、最上位の知らないキー・重複したキー・型の違う値・IDの重なり・上限を超える数をエラーにし、WordPressのオブジェクトの中の知らないキーは、読み飛ばす（応答には、読まないキーが付くため）。`null` は、無いものとして読む。エラーには、ファイルの中のJSON Pointer（RFC 6901）を付ける（`/terms/0/id: invalid id 0: use an integer from 1`）。
- 同じサイトか：REST APIを使うメソッド（`ProposeSettings`・`InferPermalinks`・`Authors`）は、はじめに、スナップショットの一覧の `home` が、WXRのチャンネルの `link` と同じサイト（ホスト名と、末尾の `/` を除いたパスが同じ。スキームとポートは問わない）かを確かめ、違うときと `home` が無いときは、何も記録せずにエラーにする（`the REST API is that of "https://other.example", but the WXR is of "https://example.com"`・`the REST API does not give its home, so it cannot be checked to be that of the WXR`。案）。取り込みの段階で別のサイトのスナップショットを渡したときも、使わない。

- 変えられない：取り込み（`wpimport.Read`）は、WXRを上の値のまま読む。
- メモリ：読み込みは、WXRの値をすべてメモリに持つ。項目・ターム・投稿者の数に上限があるのは、小さい要素を大量に並べたファイルで、メモリが増え続けないため。小さい要素を上限の数だけ並べたファイルでは、メモリがファイルよりずっと大きくなるので、メモリの少ないマシンでは、上限まで読めないことがある（6.12の144）。REST APIのスナップショットも、全体をメモリに持つ（応答は1つずつ読み、1つの大きさと、読んだ応答の合計に上限がある）。REST APIの読み込みの時間とメモリは、測っていない。本文の変換のメモリは、下記の「本文（ブロックエディタ）」の「上限」と、「本文（クラシックエディタ）」の「メモリ」に、メディアの変換のメモリと時間は、下記の「メディア」の「メモリと時間」に書く。
- 時間：クラシックの本文の変換の時間は、本文の長さに比例する（下記の「本文（クラシックエディタ）」の「段落の作り直し」と「上限」）。

**PHPのシリアライズした値**

- 範囲：`N;`（null）・`b:`・`i:`・`d:`・`s:`・`a:`（配列）を読む。オブジェクト（`O:`・`C:`）・列挙（`E:`）・参照（`r:`・`R:`）・`S:`（エスケープした文字列）は、エラーにする（`objects are not supported`。6.12の148）。PHPの `unserialize` と違い、オブジェクトを作らないので、クラスの読み込みなどの副作用が無い。
- 値の規則：`i:` は64ビットの整数に入るもの、`d:` は `INF`・`-INF`・`NAN` か10進の小数（`1e999` のように、有限の数が64ビットの浮動小数点に入らないものは、エラー）。配列のキーは、整数か文字列で、PHPと同じく、10進の整数の正規の形の文字列（`"5"`）と整数（`5`）は、同じキーとして重なりを確かめ、重なればエラー（`duplicate key`）。`"05"`・`"-0"`・`" 5"` は、文字列のままのキー。
- WordPressと同じ読み方：WordPressの `maybe_unserialize` と同じく、シリアライズした形に見える値（`is_serialized`。形だけを見る）だけを、前後の空白（PHPの `trim` が除く、空白・タブ・LF・CR・垂直タブ・NUL）を除いて読み、ほかの値は、書かれたままの文字列として扱う。二重にシリアライズした値は、1回だけ読み、中の文字列は文字列のまま。
- 読む値：変換が読む値（6.10.1）は、添付ファイルの `_wp_attachment_metadata`（メディアの変換は、`original_image` を読む。読めない値のときは、`original_image` を使わず、添付のファイルを取り込んで、要確認として記録する。値が配列でないときと、`original_image` が文字列でないときは、無いものとして扱い、記録しない。本文の変換と、旧URLの対応（`MediaURLs`）は、縮小版のファイルの名前と `original_image` を読む。6.10.5の「メディア」）、Contact Form 7の `_mail`・`_mail_2`・`_messages`、メニューの項目の `_menu_item_classes`、Polylangのタームの説明（`wp:term_description`）。
- CRLFの数え直し：XMLは、CDATAの中のCRLFもLFにする（上記の「値」）ので、CRLFの改行を含んでいた文字列（Contact Form 7の管理画面で編集したメールの本文など。ブラウザーは、テキストエリアの改行をCRLFで送る）は、`s:<バイト数>` が、読んだ文字列より、LFの数だけ長くなる。そこで、厳密に読めなかった値だけ、読み直す。文字列（配列のキーも）ごとに、まず書かれた長さで読み、その長さで文字列が終わらなければ（次が `";` でなければ）、中のLFをすべてCRLFだったとして、2バイトに数え直した長さで読む（書かれた長さは、バイト数とLFの数の和なので、数え直した長さは、あれば1つに決まる）。値の改行は、LFのまま残し、数え直して読んだ文字列の数を、取り込みレポートに「変えた」として記録する（`read the serialized value by counting the LF line breaks in 1 string as CRLF (XML turns CRLF into LF); the line breaks are kept as LF`。2つ以上は `in 2 strings`）。
  - LFだけの文字列（Contact Form 7の既定のテンプレートのままのものなど）と、CRLFだった文字列が、1つの値に混ざっていても読める。
  - 書かれた長さと、数え直した長さの、どちらでも文字列が終わる文字列（分かれ目）は、まず書かれた長さで読み、値の残りが読めなければ、最後の分かれ目から順に、数え直した長さに替えて、値の初めから読み直す（1つの値で16回まで）。Contact Form 7の `_mail` は、`body` の後ろが `additional_headers` のキー（`s:18:"additional_headers";`）なので、本文の改行がちょうど26個のとき、書かれた長さが、そのキーの終わりに当たる。
  - 1つの文字列の中で、CRLFとLFが混ざっていたものは、どちらの長さでも終わらないので、読めない。
  - 読む時間は入力の長さに比例し、読み直しの回数に上限がある（1MiBの値の最悪の場合で、17回読む）。
- 読めない値：厳密に読んだときのエラーを、取り込みのエラーにする。ファイルの位置は、その `<wp:postmeta>`（termmetaなら `<wp:termmeta>`）の位置で、`byte` は、WXRから読んだ値（改行はLF）の先頭から数えたバイトの位置（前に空白があれば、それも数える）。どう扱うか（その値を使わずに記録する、など）は、変換が決める。ほかの壊れ方は6.12の147。例：`wordpress.xml:9:1: the value of "_mail": byte 7: expected '"', found 'c'`（文字列 `abc` の長さを `s:2:` と書いたもの。`<wp:postmeta>` が9行目1列にある）

**スラッグ**

- WXRのスラッグ（`wp:post_name`、タームのスラッグと親（`wp:category_parent`・`wp:term_parent`）、`category` の要素の `nicename`、`_wp_old_slug`）は、日本語などのASCII以外の文字を、UTF-8のバイトごとに `%` と16進数2桁で書いたもの（`%e3%81%8a`）。読み込みは、書かれたままにする。
- 戻し方：`%` と16進数2桁（大文字も小文字も）を、バイトに戻し、ほかの文字は、そのままにする（`+` を空白にはしない）。1回だけ戻す（`%2541` は `%41`）。戻した結果が、UTF-8として正しく、制御文字（C0・DEL・C1）を含まないことを確かめ、満たさなければ、エラーにする（`invalid percent-encoding at byte 0`・`not valid UTF-8 after decoding`・`contains a control character after decoding`）。
- 小文字にすることと、NFCにすることは、取り込む側が、スラッグの正規化（6.4.2）で行う。ターム（`Terms`）と著者プロフィール（`Authors`）のスラッグは、戻せないものも含め、次の順に作る（案）。エントリーのスラッグは、まだ作らない（戻せないスラッグの扱いは、6.12の149）。添付ファイルは、メディアがスラッグを持たない（6.6.2）ので、作らない。
  - (1) 戻す。戻せなければ、書かれたままの文字から作り、理由に `it cannot be decoded: <理由>` を足す。
  - (2) 小文字とNFCにする（6.4.2）。変えたら、理由に `normalized to lower case and NFC` を足す。
  - (3) スラッグに使えない文字（6.4.2。ASCIIの `.`・空白・`!` などの記号、制御文字、書式文字を含む）の連なりを、`-` 1つにする。`-` に隣り合うときは、足さない。理由は `characters that a slug cannot have are "-"`。
  - (4) 両端の `-` を除く。(3)で置き換えていないのに除いたら（WordPressは、両端に `-` のあるスラッグを書き出さない）、理由に `"-" at the ends is removed` を足す。
  - (5) 200バイト（6.4.2）を超えたら、文字の途中を避けて切る。理由は `it is cut to 200 bytes`。
  - (6) 何も残らなければ、ターム `term-<wp:term_id>`（IDが無ければ `term`）、著者 `author-<wp:author_id>`（IDが無ければ `author`）にする。
  - (7) 同じタクソノミー・同じ言語のターム（著者は全体）の中で重なったら、WordPressのURLのままのスラッグを先にする（案）。タームは(1)〜(5)で理由が付かなかったもの、著者はREST APIの `slug` から作ったもの（(6)にしたものを除く）が、WXRの順に、まず自分のスラッグを取る。取れなかったもの（同じスラッグが2つあるとき）と、ほかのもの（理由が付いたもの、ログイン名から作ったもの、(6)にしたもの）は、その後に、この順で、それぞれWXRの順に、`-2`・`-3` を付ける（200バイトに収まるよう、元のスラッグを切る）。
  - 記録：変えたときは、取り込みレポートに記録する：`the slug "News" is "news" here: normalized to lower case and NFC`（理由が複数なら `; ` でつなぐ）、`nothing is left of the slug "!!!"; it is "term-3" here`、`the slug "dup" is also that of another term of category; it is "dup-3" here`（著者は `of another author`）、`nothing is left of the slug that the login makes; it is "author-8" here`（ログイン名から作る著者のスラッグが残らないとき。ログイン名は書かない）。
- ログイン名からのスラッグ（`user_nicename`）：REST APIから得られない投稿者のスラッグは、ログイン名の最初の50文字から、WordPressと同じ規則で作る。ASCIIの大文字は小文字に、`.` と空白は `-` にし、ASCIIの英数字・`_`・`-` 以外のASCIIの文字は除き、ASCII以外の文字はそのまま残し、`-` は両端に置かず、続けて2つ置かない。ログイン名によっては、空になる。アクセント記号を除く処理などはしないので、WordPressの `user_nicename` と違うことがある（6.12の170）。このスラッグも、上の(1)〜(7)を通す。

**ID**

- 同じWXRからは、同じIDにする（取り込み直しても、IDが変わらない。同じ入力から、同じサイトのディレクトリを作るため。#58）。乱数と、取り込んだ時刻は使わない。
- 形：接頭辞（6.7）とULID。ULIDの時刻の部分（接頭辞の後ろの先頭の10文字）は `0` で、残りの80ビットは、作り方の版（`whiteroom wpimport id 1`）・種・種類・キーを、それぞれの後ろにNULを付けてつないだもののSHA-256の先頭から作る。種類（`entry`・`media` など）を含めるので、同じ投稿を、エントリーにしても、メディアにしても、別のIDになる。種は、WXRのホームのURL（`wp:base_blog_url`。前後の空白を除く。無ければ、チャンネルの `link`）。例（種が `https://example.com`）：`wp:post_id` が123の投稿は、エントリーなら `ent_0000000000QNCGZPVAWT8HNPBA`、メディアなら `med_0000000000TB4EDMXTV7FVBCZF`。
- キー：投稿（添付ファイル・メニューの項目・フォームも）は `post` と `wp:post_id`、タームは `term`・タクソノミー・`id`・`wp:term_id`（IDの無い1.0は、`term`・タクソノミー・`slug`・書かれたままのスラッグ）、投稿者は `user` とログイン名を、それぞれNULで区切ったもの（数は10進）。ほかのもの（リビジョン・翻訳グループ・リダイレクトなど、1つのWordPressのオブジェクトから作らないもの）のキーは、それを作る変換が決める。タームの翻訳グループ（`tg_…`）のキーは、そのタームのキー（上記）で、タームごとに1つ作る。種類が違うので、タームのIDとは別のIDになる。例（種が `https://example.com`）：`category` の `wp:term_id` が3のタームは `trm_00000000009S0MYTEEWC021TN0`、その翻訳グループは `tg_000000000096ZK7YGJ9FBDKA0C`。
- 割り当て：同じオブジェクトは、同じ種類なら、いつも同じIDになり、別の種類にはできない。
- 旧サイトのURLが変わると（`http` から `https`、ドメインの移転）、同じサイトでも、IDが変わる（6.12の146）。作り方を変えても、IDが変わるので、変えるときは、作り方の版（上記）を上げる。

**取り込みの設定**

- 役目：WXRにもREST APIにも無い値と、推測で決めた値（サイト設定とURLの規則。6.10.1・6.10.4）と、本文の名前の対応表（下記）は、1つのJSONのファイルに書き出して、人に確かめて（直して）もらってから取り込む。ファイルの形は、仮に決めた（案。形を広げるかは6.12の173）。見本は `internal/wpimport/testdata/out/settings.json`。
- 2つの段階：取り込みは、推測と取り込みの2つの段階に分ける（段階ごとに新しい取り込みとレポートを使うことは、上記の「流れ」）。
  - 推測（`ProposeSettings`）：チャンネルと、あればスナップショットから、設定を作り、本文が使う名前を数える（下記の「本文の名前の対応表」）。`Settings.WriteJSON` でファイルに書き、根拠と確かめる値を取り込みレポートに記録する（見本は `propose.txt`。URLの規則は6.10.4。REST APIのサイトの確かめは、上記の「REST APIの読み込み」の「同じサイトか」）。
  - 取り込み：`ReadSettings` で、人が直したファイルを読み、`Site` でサイト設定を作り、あとの変換へ進む（上記の「流れ」）。推測はしない。
- キーと意味：

| キー | 意味 | 空・0のとき |
| --- | --- | --- |
| `site.name` | サイトの名前（`site.language` の `name`） | 入力が要る |
| `site.tagline` | キャッチフレーズ（`site.language` の `tagline`） | 書かない |
| `site.url` | サイトのURL（6.6.8） | 入力が要る |
| `site.language` | 既定の言語（`languages` もこの1つ） | 入力が要る |
| `site.timeZone` | タイムゾーン | 入力が要る |
| `site.postsPerPage` | 一覧の1ページの件数（1〜100） | 10 |
| `site.noindex` | 検索エンジンに載せない（`seo.noindex`） | `false` |
| `site.frontPage`・`site.postsPage` | トップページ・投稿ページの固定ページ（WordPressの投稿ID） | 0は、無し |
| `site.logo`・`site.icon` | ロゴ・アイコンの添付ファイル（WordPressの投稿ID） | 0は、無し |
| `site.allowHtml` | `html` ブロックを許すか（サイト設定の `allowHtml`。6.6.8）。`false` なら、カスタムHTML（6.10.2）は `legacy` になる | `false` |
| `urls.post`・`urls.page`・`urls.author` | 投稿・固定ページ・著者ページのURLの規則 | 既定の規則（6.6.8） |
| `urls.taxonomies.<名前>` | タクソノミー（`category`・`tag`と、スキーマのファイルで定義したもの）のURLの規則 | 既定の規則 |
| `urls.types.<名前>.url`・`.archive` | カスタム投稿タイプのURLの規則と、一覧のパス | 既定の規則・一覧なし |
| `defaultCategory` | `%category%` が、カテゴリーの無い投稿に使うカテゴリーのスラッグ（戻したもの。エントリーの変換は、WXRの `wp:category_nicename` を戻したものと比べて探す） | 要らない |
| `blocks.presets.<種類>` | 本文が使う、WordPress（本体・テーマ・プラグイン）のプリセットの名前（slug）から、このCMSのテーマ（5.4.2）のプリセットの名前への対応表。種類は、`color`・`gradient`・`fontSize`・`fontFamily`・`spacing` | 表に無い名前は、そのまま。値が空の名前は、取り込まない |
| `blocks.variants` | ブロックスタイル（`is-style-` の後ろの名前）から、バリエーションの名前への対応表 | 表に無い名前は、そのまま。値が空の名前は、取り込まない |
| `blocks.marks` | 文中の要素（`mark`・`span`）のクラスから、`highlight` のバリエーションの名前への対応表 | 値が空のクラスは、バリエーションにしない（色も無ければ、文字だけを残す）。表に無いクラスは、`mark` と `has-inline-color` の `span` では、`has-`・`wp-` で始まるものを除いて、そのままバリエーションの名前にし、ほかの `span` では文字だけを残す |
| `blocks.imageSizes` | 画像のサイズ（`sizeSlug`。クラシックのHTMLの画像は、`img` の `size-<名前>` のクラスと、`[gallery]` の `size`）から、テーマの画像のサイズの名前への対応表 | 表に無い名前は、そのまま。値が空の名前は、取り込まない（`full` は、サイズを付けない） |

- 空の意味：「入力が要る」値は、推測できなかったとき、空のまま書き出し、要確認として記録する。空のまま取り込むと、`Site` が、設定のファイルの位置を示すエラーにする（`/site/timeZone: missing timeZone`）。`postsPerPage`（10）と `noindex`（`false`）は、既定を書き出す。URLの規則は、推測した規則か、既定の規則を書き出す。空の規則は、既定の規則になる。
- ファイル：2つの空白で字下げし、末尾に改行を付ける。キーは、空・0・`false` のものも、直せる項目が分かるように、すべて書く（`blocks` の表は、空なら `{}`）。`urls.taxonomies` と `urls.types` の名前と、`blocks` の表の名前は、順に並べる。`urls.types` に書くのは、スキーマのファイルで定義したカスタム投稿タイプだけで、`post` と `page` は `urls.post` と `urls.page`。WordPressの投稿IDで書く `frontPage`・`postsPage`・`logo`・`icon` のほかは、このCMSでの名前と値で書く。版のキーは持たない。
- 読み込み（`ReadSettings`）：書いていないキーは、値が無いものとして読む。知らないキー（大文字と小文字を区別する。`schemaVersion` も）・重複したキー・`null`・型の違う値・整数でない数・範囲を超える数は、エラーにする（`unknown key`・`duplicate key`・`null is not allowed; omit the key`・`expected number, got string`・`must be an integer`・`out of range`）。エラーは、`null` のすべてと、ほかの誤りの最初の1つを、ファイルの名前・行・列と、ファイルの中のJSON Pointerを付けて、位置の順に返す（`settings.json:4:5: /site/foo: unknown key`）。JSONとして読めないファイル（コンマの抜け、途中で終わるもの、値の後ろの文字など）は、その構文の誤りだけを1つ返す（ほかの誤りは、読めるようにしてから示す）。値の中身（URLの規則やタイムゾーンが正しいかなど）は、読み込みでは確かめず、`Site` が確かめる。
- サイト設定（`Site`）：設定 `s` と、開発者のスキーマのファイル `defs` から、サイト設定（`content.Site`）を作り、正規化して、検証する。設定の文書（`site/settings.json`）とスキーマのファイル（`site/schema.yaml`）は、`MarshalSettings` と `MarshalSchema` で書く。
  - 設定の文書：`name`・`tagline` は `site.language` の値、`languages` と `defaultLanguage` は `site.language` の1つ。`frontPage`・`postsPage`・`logo`・`icon` は、WordPressの投稿IDを、計画の表で引いて、取り込んだエントリー（固定ページ）とメディアのIDにする。取り込めなかったもの（表に無いもの、エントリーとメディアが違うもの）は、書かずに、`the front page, page 30, is not imported` のように記録する（`the posts page, page 31, is not imported`・`the logo, attachment 50, is not imported`・`the icon, attachment 51, is not imported`）。負のIDは、エラー（`invalid ID -1: use 0 for none, or the ID of the page in WordPress`）。
  - スキーマのファイル：`defs` のタイプとタクソノミーを、定義した順のまま持ち、`urls` の規則を入れる（`post` と `page` は、その `url`。`author` は `authorUrl`。`taxonomies` と `types` は、同じ名前の定義の `url`（と `archive`））。`post`・`page`・`category`・`tag` の定義がスキーマのファイルに無ければ、その規則が空でないときだけ、定義を足す（前に置く）。規則も `label` なども無い、これらの定義は、書かない（`defs` にあったものも。空の定義は書けないため。6.6.8）。`urls` に、スキーマのファイルに無い名前があれば、エラーにする（`type "product" is not in the schema file`・`taxonomy "series" is not in the schema file`）。
  - エラー：設定のファイルの位置を示す（`/site/name`・`/site/url`・`/site/timeZone`・`/site/language`・`/site/postsPerPage`・`/site/frontPage`・`/urls/post`・`/urls/types/<名前>/url`・`/urls/taxonomies/<名前>`・`/blocks/presets/<種類>/<名前>`・`/blocks/variants/<名前>` など）。`blocks` の表の値のうち、空でなく、6.7の名前の規則に合わないものは、エラーにする。開発者が書いたものの誤り（ラベル・フィールド・設定に無い規則）は、スキーマのファイルの位置（`/types/…`）のまま示す。
- 構造は持たない：取り込みの設定は、URLの規則を持つが、WordPressのパーマリンクの構造（6.10.4）は持たない。旧URLのリダイレクトに構造が要るときの扱いは、6.12の168。
- 本文の名前の対応表（`blocks`）：本文（下記の「本文（ブロックエディタ）」と「本文（クラシックエディタ）」）が使う、プリセット・ブロックスタイル・画像のサイズ・文中の要素のクラスの名前は、WordPress（本体・テーマ・プラグイン）が決めたもので、このCMSのテーマにあるとは限らない。推測の段階が、取り込む項目（`post`・`page`・スキーマのファイルで定義したカスタム投稿タイプ・再利用ブロックの `wp_block`。ゴミ箱と自動下書きは除く）の本文を読み、使われている名前を数えて、`blocks` に書き出す。値は、名前の規則に合う名前なら同じ名前、合わない名前なら空にする（`marks` は、すべて空にする）。人は、新しいサイトのテーマにある名前に直す。新しいサイトのテーマを見て推測するかは、6.12の192。
  - 数える名前は、名前空間が `core` のブロックのうち、動的なブロック（WordPressが表示のときにHTMLを作るもの。6.10.3）でないものが使うもの。変換が別の理由で `legacy` にするブロック（動画など）と、写されない同期パターン（公開していないものなど）の本文も、数える。テーマやプラグインのブロックと動的なブロックは、`legacy` になるので、その中のブロックも含めて、数えない。`core/html`・`core/code`・`core/preformatted`・`core/cover` のHTMLは、文中の要素のクラスとして数えない。プルクオートは、バリエーション `pullquote` として数える。クラシックのHTML（区切りの無い本文の全体、ブロックの間のHTML、`core/freeform` と `core/shortcode` の中身、同期パターンの区切りの無い中身。Elementorで作った項目は読まない）も、変換が読むものを数える：`img` の最初の `size-<名前>` のクラス（`full` は除く）と、`[gallery]` の `size`（無ければ `thumbnail`。`full` は除く。`[[gallery]]` は文字）を画像のサイズとして、`mark` と `span` のクラスを文中の要素のクラスとして、`span` の色のプリセットのクラスを色のプリセットとして数える。数えないもの：`[caption]` の `class` の属性と、`figure` の `size-<名前>` のクラス（変換は、画像に無いとき読む）、ブロックエディタの段落ブロックの中身が `[gallery]` だけのもの、8MiBを超えるクラシックのHTML（変換は、部分に分けて読む）。残る論点は6.12の229。本文の大きさ（64MiB）か、区切りの数（4万個）の上限を超える項目は、数えない。文中の要素のクラスは、ブロックのHTMLを読んで数えるが、1つのブロックのHTMLが8MiBを超えるものは、読まず、数えない。1つの本文で読むHTMLも64MiBまでで、超える分は、同じく読まない。1つのHTMLで読む `[gallery]` は4万個までで、属性が1MiBを超えるものは読まない。
  - 種類ごとに1つ、要確認として、チャンネルの位置に記録する。名前は、使われた回数の多い順、名前の順に、10個まで並べ、残りは `, and <数> more` にする。例：`review: the blocks use 4 block styles of WordPress: "pullquote" (2 times), "rounded" (2 times), "solid-color" (1 time), "日本" (1 time); blocks.variants maps them to the variants of the theme of the site`。ほかの種類は、`the blocks use <数> color presets of WordPress: …; blocks.presets.color maps them to the presets of the theme of the site`（`gradient`・`font size`・`font family`・`spacing` も同じ形）、`the images use <数> image sizes of WordPress: …; blocks.imageSizes maps them to the image sizes of the theme of the site`、`the text uses <数> classes of inline elements: …; blocks.marks maps them to the highlight variants of the theme of the site, and the others keep only their text`。
  - カスタムHTMLのブロックの数も、記録する（`allowHtml` を決めてもらうため）。数えるのは、`allowHtml` が `false` のときに `legacy` になるもの。空のもの（空白と制御文字だけ）と、iframeが1つだけで許可リストに合い、`allowHtml` によらず `embed` になるもの（下記の `core/html`）は、数えない。HTMLを読まなかったもの（上記の上限を超えたもの）は、`legacy` になるものとして数える。行き先は `site/settings.json#/allowHtml`。例：`review: 1 custom HTML block becomes a legacy block unless site.allowHtml is true -> site/settings.json#/allowHtml`（2つ以上は `2 custom HTML blocks become legacy blocks unless site.allowHtml is true`）。

**HTMLの文字だけを残す**

- 対象：タームの説明と、著者プロフィールの `bio`（REST APIの `description`）。どちらも、装飾の無い文字列（6.6.1・6.6.3）なので、HTMLから文字だけを取る（6.12の36）。メディアのキャプション（6.10.1。画像だけ）も、同じ規則にする（メディアの変換が行う。下記の「メディア」）。
- 読み方：`internal/html` の構文解析で、`div` の中身として読む。構文解析の上限は、`html`・`legacy` ブロックのサニタイズ（6.5.4）と同じで、超えた値は取り込まない（下記）。`<` も `&` も無い文字列は、解析せず、整えるだけ。
- 残すもの：文字（文字参照は戻す）と、`<br>` の改行。ブロックの要素（`p`・`blockquote`・`pre`・`h1`〜`h6`・`ul`・`ol`・`dl`・`table`・`hr`・`figure`・`details`・`section`・`article`・`aside`・`header`・`footer`・`main`・`nav`・`form`・`fieldset`・`address`・`hgroup`・`dialog`）の前後は、空行で区切り、`div`・`li`・`dt`・`dd`・`tr`・`caption`・`figcaption`・`summary`・`thead`・`tbody`・`tfoot` の前後は、改行で区切る。表のセル（`td`・`th`）の後ろには、空白を1つ足す。リンク（`a`）の文字は残す。
- 除くもの：`script`・`style`・`template`・`noscript`・`iframe`・`object`・`embed`・`video`・`audio`・`canvas` と、SVGとMathMLの要素は、中身ごと除く。画像（`img`）は残らない。コメント・DOCTYPE・処理命令は、黙って除く。
- 整える：CRとCRLFはLFにし、行の終わりの空白とタブを除き、空行は続けて1つまでにして、前後の空白・タブ・改行を除く。
- 失ったものの記録：リンクの行き先、画像、`p` と `br` のほかの要素の名前を、失ったものとして、変えた（`changed`）で記録する：`kept only the text of the HTML; lost <一覧>`。一覧は、HTMLに出た順に、同じものは1回だけ、10個まで（残りは `, and 1 more` のように数える）。要素は `<strong>`（名前にASCIIの英数字と `-` 以外があれば `<"my_tag">`）、リンクは `a link to "https://example.com/"`（行き先が無ければ `<a>`）、画像は `an image "<src>"`（`src` が無ければ `<img>`）と書く。例（見本のサイトのカテゴリー `お知らせ`）：`site.xml:33:2: changed: term 3 (category "お知らせ"): kept only the text of the HTML; lost a link to "https://example.com/", <strong> -> terms/trm_00000000009S0MYTEEWC021TN0.json#/description`。
- 取り込まないとき：構文解析の上限を超えたときは `the description is not imported: it is too complex to read as HTML`（著者は `the bio is not imported: it is too complex to read as HTML`）、文字にした後の長さが1MiB（6.7）を超えたときは `the description is not imported: it is too long: <バイト数> bytes (max 1048576)` を、取り込まなかった（`skipped`）として記録する。説明や `bio` だけを取り込まず、ターム・著者プロフィールは取り込む。メディアのキャプションも、同じ形で記録し（`the caption is not imported: it is too complex to read as HTML`・`the caption is not imported: it is too long: <バイト数> bytes (max 1048576)`。行き先は `#/caption`）、キャプションだけを取り込まず、メディアは取り込む。残る論点は6.12の172。

**メディア**

添付ファイル（6.10.1）から、メディア（6.6.2）と、サイトのディレクトリ（4.3）の `files/` に置く原本を作る（案）。変換は `(*Import).Media`（`internal/wpimport`）で、サイト設定（`Site` が返したもの）と `MediaOptions` を渡し、メディアの文書の列（IDの順）を得る。文書は、Goの値で返す（書き出しは、ほかの変換と同じく #58）が、原本だけは、変換が `files/` に書く（形式を読んでから、残すか捨てるかを決める手順が、取り込みに固有のため。書き出しを作るときに、置き場所を見直せる）。

- 計画（`PlanMedia`）：取り込む添付ファイル（ゴミ箱と自動下書きを除く）のすべてに、メディアのIDを割り当て（上記の「ID」）、種類（画像かPDFか）を、添付のファイルの名前が `.pdf`（大文字と小文字は問わない）で終わるかで見込んで、参照に記録する（ファイルの名前の分からない添付ファイルも、画像として記録する）。ファイルは読まず、取り込みレポートにも記録しない。種類は見込みで、`Media` が、ファイルの中身から直す（拡張子と中身が違う添付ファイルがあるため。6.6.2）。サイト設定が、ロゴとアイコンを、この記録で引く（上記の「流れ」）。2回呼んでも、同じIDになる。
- 渡すもの（`MediaOptions`）：`Files`（原本を書くディレクトリ。サイトのディレクトリの `files/` のパス）、`Uploads`（`wp-content/uploads` のコピー。`fs.FS`）、`Download`（`Downloader`。下記の「ダウンロード」）、`By`（`uploadedBy` にするアカウントのID）、`Workers`（同時に読む添付ファイルの数。0以下は4。添付ファイルの数より多くは動かさない）。`Uploads` と `Download` は、片方だけでも、両方でもよい。サイト設定は、既定の言語（`alt` と `caption` の言語）、タイムゾーン（`uploadedAt`）と、文書の検証（6.7）に使う。引数が正しくないときは、何も読まず、何も記録せず、エラーにする（`the settings of the site are needed to make media`・`the default language of the site: …`・`the time zone of the site: …`・`the account that uploads the media: …`・`the directory of the originals is needed to make media`・`a copy of the uploads or a download is needed to make media`）。呼ぶのは、計画（`PlanMedia`）とサイト設定の後、エントリーの変換の前に、1回だけ（呼ぶたびに、取り込みレポートへ記録を足す）。
- 読む元と順：添付ファイルごとに、試すファイル（下記の「元のファイルの決め方」）の順に、コピーを先に読み、コピーに無いファイルだけを、ダウンロードで読む（コピーにあるファイルは、旧サイトに要求を送らない）。ファイルは、読めて、文書の検証を通った最初のものを取り込む（検証を通らないファイルは、すぐに捨てる）。
  - コピーのパス：`_wp_attached_file`。前後の空白と、先頭の `/` を除き、`path.Clean` で整える。空・`.`・`uploads` の外を指すもの（`..` で始まる）と、NUL・`?`・`#`・`\` を含むものは、パスが分からないものとして扱う。`original_image` のファイルは、添付のファイルと同じディレクトリの、その名前のファイル。コピーに無いのは、ファイルが無いときと、パスの途中がファイルのとき、名前が長すぎるとき。コピーの、通常のファイルでないもの（ディレクトリなど）と、64MiBを超えるものは、読まずに（大きさだけを見て）、そのファイルを使わない。コピーを開けない・読めないときは、取り込みを止める（下記の「エラーで止まったとき」）。絶対パスの `_wp_attached_file`・マルチサイト・ファイル名の大文字と小文字と正規化は、6.12の250。
  - ダウンロードのURL：`wp:attachment_url`。`http`・`https` で、ホストがあり、ユーザー名の無いものだけ（`#` の後ろは捨てる）。`original_image` のファイルは、最後の `/` の後ろをその名前にしたもの（クエリは残す）。
  - 名前：`_wp_attached_file` の最後の部分、無ければ `wp:attachment_url` のパスの最後の部分。どちらからも名前が得られない（空・`.`・`..`）添付ファイルは、取り込まない。
- 元のファイルの決め方：
  - 使える `original_image`：`_wp_attachment_metadata`（最初のもの。空白だけなら無いものとする）の `original_image` が、文字列で、空でなく、`.`・`..` でなく、添付のファイルと同じ名前でなく、`/`・`\`・NUL を含まないもの。
  - 順：使える `original_image` があれば、そのファイル、添付のファイルの順に試す。使えなければ、添付のファイルだけ。ただし、添付のファイルの名前の、拡張子を除いた終わりが、`-e` と13桁のASCIIの数字のとき（WordPressの画像の編集の印）は、使える `original_image` があっても、添付のファイルだけを試す（編集した画像として記録する）。
  - 取り込むもの：順に試して、最初に、読めて、文書の検証を通ったファイル。`original_image` のファイルが、見つからない・段階1の形式でない・64MiBを超える・1億画素を超える（検証）ときは、添付のファイルを試し、取り込めたら、要確認として記録する。どのファイルも取り込めなければ、添付ファイルを取り込まず、試した順に、ファイルごとの理由を記録する。
  - 理由：いつも `original_image` だけを取り込むと、WordPressで切り抜きや回転をした画像が、編集する前に戻り、HEICでアップロードした写真と、元の画像が上限を超える写真が、WordPressが作ったJPEG（`-scaled` など）があるのに、取り込まれない。
  - WordPressの動き（7.1.4の `wp-admin/includes/image.php` と `image-edit.php`、`export.php` で確かめた。関数の名前だけを書く）：`wp_create_image_subsizes` は、アップロードした画像の長い辺が2560画素（フィルターで変えられる）を超えるときに縮小し（ファイルの名前に `-scaled` が付く）、サーバーが変換する形式（HEICなど）のときにJPEGなどに変換し（印は付かず、拡張子が変わる）、EXIFの向きが1でないときに回転して（`-rotated`）、新しいファイルを添付のファイルにする。`_wp_image_meta_replace_original` が、そのとき、元のファイルの名前（ディレクトリは含まない）を `original_image` に書く。画像の編集（`wp_save_image`）は、編集した画像を、拡張子の前に `-e` と13桁の数字（時刻の秒数と3桁の乱数）を付けた新しいファイルに保存して、添付のファイルにする。`original_image` は変えず、編集する前のファイルは `_wp_attachment_backup_sizes` に残す。書き出し（`export_wp`）は、`_edit_lock` のほかの、添付ファイルのpostmetaをそのまま書く。
  - 限り：`-e` と13桁の数字で終わる名前は、人が付けたものにもありうる。編集した画像を、元の解像度では取り込めない（6.12の248）。
- 原本の書き方：原本は、`Files` の下に、`hash` の `sha256:` の後ろ（小文字の16進数64桁）を名前にして、階層を作らずに置く（4.3の `files/`）。作るディレクトリは、取り込む添付ファイルが1つでもあるときだけ（`0755`）。
  - 流し込む：ファイルは、メモリに全部読まずに、`Files` の中の一時ファイル（`.tmp-` と、16桁の小文字の16進数。`0644`）に書きながら、SHA-256を求める。64MiBを超えるところまで読んだら、そこで止めて、取り込まない（長さの分からない応答も、同じ）。
  - 確かめる：読み終えたら、一時ファイルを同期し（`fsync`）、中身から形式・幅・高さ・向きを読む（`internal/mediafile`。6.6.2）。形式が読めないもの・空のファイルは、取り込まない。
  - 残す：文書を作り、検証を通ったときだけ、一時ファイルを、ハッシュの名前に変える（同じ名前のファイルがあれば、置き換える）。同じ中身のファイルは、1つのファイルになる（メディアは分ける。6.12の249）。取り込まなかったファイルは、一時ファイルも含めて、何も残さない。ディレクトリの同期はしない。一時ファイルを残して終わったプロセスの後始末は、しない（6.12の252）。
- 文書（`content.Media`）：
  - `id`：計画のもの（上記の「ID」）。`hash`・`size`：取り込んだファイルのもの。
  - `mimeType`・`width`・`height`：ファイルの中身から（6.6.2。向きを反映した大きさ）。画像かPDFかも、中身で決める。`.jpg` のPDFはPDFのメディアに、`.pdf` のJPEGは画像のメディアになり、参照の種類も、そのとおりに直す。
  - `fileName`：取り込んだファイルの名前（`original_image` を取り込んだときは、その名前）。6.6.2で使えないものを、次の順に直す：UTF-8でないバイトを、1バイトずつ `-` に、`/` と `\` を `-` に、双方向の書式文字（Bidi_Control）を取り除き、正規化（6.6.2。制御文字と前後の空白を除いて、NFC）をかけ、空・`.`・`..` なら `file` に、255バイトを超えれば、拡張子（`.` を含めて2〜32バイトのもの）を残して、文字の途中を避けて切り、切った後ろの空白を除く。直したときは、変えたものとして記録し、理由を `; ` でつなぐ（`bytes that are not UTF-8 are "-"`・`"/" and "\" are "-"`・`bidirectional formatting characters are removed`・`nothing is left of it`・`it is cut to 255 bytes`）。正規化だけで変わったものは、記録しない。
  - `alt`（画像だけ。PDFの `alt` は読まない）：`_wp_attachment_image_alt`。改行（LFとCR）・タブ・VT・FF・NEL・U+2028・U+2029は空白にし（変えたら記録する）、前後の空白を除く。正規化の後で1MiB（6.7）を超えるときは、取り込まず、記録する。
  - `caption`（画像だけ）：抜粋（`excerpt:encoded`）。HTMLから文字だけを残す（上記の「HTMLの文字だけを残す」）。
  - `uploadedAt`：`post_date` に、`post_date_gmt` との差の時差を付けて、秒まで書く。差が、-12時間から+14時間までの、分の整数のときは、その時差（0は `Z`）。そうでないとき（`post_date_gmt` が読めない・`0000-00-00 00:00:00` など）は、`post_date` を、サイトのタイムゾーンの時刻として読む（夏時間で存在しない時刻は、Goの `time.Date` が決める側にずれる。6.12の57）。`post_date`・`post_date_gmt` は、`YYYY-MM-DD hh:mm:ss`（前後の空白は除く）で、年が1〜9999のものだけを読む。`post_date` が読めなければ、取り込まない。
  - `uploadedBy`：`By`。
  - 文書は、正規化してから検証する（6.7）。見本のサイトのロゴ（`internal/wpimport/testdata/out/media/med_0000000000SHPNF2S2S3ZAA14M.json`。正解のファイルは、`MarshalJSON` の出力の1行）：

```json
{"schemaVersion":1,"id":"med_0000000000SHPNF2S2S3ZAA14M","hash":"sha256:fb32fb549f9d6741552d370c52e1aef14a61a55c66efd8b8525b475b9f7b3409","fileName":"logo.png","mimeType":"image/png","size":2390,"width":48,"height":16,"uploadedAt":"2026-10-05T09:40:00+09:00","uploadedBy":"usr_00000000000000000000000002"}
```

- 取り込まないものと、記録の文：どれも、取り込みレポート（下記）に記録する。文書に入れないもの（取り込まない添付ファイルの全体と、取り込んだ添付ファイルの `alt`・`caption`・説明など）は、`skipped`、直したものは `changed`、確かめてほしいものは `review`。位置は、添付ファイルの項目で、行き先は、メディアの文書（`media/<ID>.json`）の中。記録の文は、次のとおり（英語。`<…>` は、値が入る所）。

| --- | --- | --- |
| `skipped` | `the attachment is not imported: it is in the trash`（自動下書きは `it is an auto-draft`） | なし |
| `skipped` | `the attachment is not imported: the WXR tells no file of it` | なし |
| `skipped` | `the attachment is not imported: its post_date "0000-00-00 00:00:00" cannot be read` | なし |

- 記録の書き方：名前は、Goの `%q` で書く（`"` で囲み、`"` と改行は `\"`・`\n`）。ファイル名は、`fileName` に直す前の、WXRのままの名前。
- ファイルごとの理由：`not in the copy of the uploads`・`not a regular file in the copy of the uploads`・`too large: <バイト数> bytes (max 67108864)`（コピーのファイル。大きさだけを見る）・`too large: more than 67108864 bytes`（読んだ分が超えた）・`empty file`・`cannot read the file: unsupported file format`（形式は合っていて壊れているものは、`cannot read the file: invalid PNG: unexpected EOF` のように、読み込みの理由が付く）・`the WXR does not tell where it is in the uploads directory`・`the WXR gives no address to download it from`・ダウンロードの理由（下記）・文書の検証の問題（`too many pixels: 20000x20000 (max 100000000)` など。複数は `; ` でつなぐ）。コピーとダウンロードのどちらも使えないファイルは、2つの理由を `; ` でつなぐ。
- 説明とタイトル：説明が空でない添付ファイルを1つずつ記録し、タイトルは1つにまとめるのは、説明は人が書いたもので、失うことを場所つきで知らせるため。タイトルは、WordPressがファイル名から付けるので、ほぼすべての添付ファイルにあり、1つずつ記録すると、レポートが埋まる（6.12の47）。
- 公開するファイルを作れない画像：取り込んだ画像を、`internal/imaging` の `Inspect`（ビルドが、公開するファイルを作る前に調べる処理。6.6.2）で調べ、公開するファイルを作れないもの（辺が65535画素を超えるもの、Adobeの `APP14` の無い4成分のJPEGなど）は、断らずに取り込み、要確認として記録する（`the build cannot make the published files of the image: too long a side: 70000x10 (max 65535); it fails if something published uses the image`）。取り込むかどうかを、文書の検証（6.7）で決め、失敗を決めるのは、公開するものがその画像を使うときのビルドだけ、という形は、保存の操作の追加（6.6.2）と同じ。取り込みレポートは、取り込んだ後に直すものを知らせる場所で、ビルドで初めて失敗するより早く分かる。アップロードで拒むかは、6.12の105。
- ダウンロード（`Downloader`）：旧サイトからファイルを読む。呼ぶ側が、取り込みごとに1つ作って渡し（ゼロ値で使える）、`Media` が、終わりに、接続を閉じる。
  - 取りに行く先：旧サイトのホーム（チャンネルの `link`、無ければ `wp:base_blog_url`）と同じサイト（ホスト名は大文字と小文字を問わず、スキームとポートが同じ。ホームが `http` のサイトの、`https`（ポート443）の同じホストも可）と、呼ぶ側が渡したホストの一覧（`Downloader.Hosts`。ホスト名だけで、ポートは書けない。大文字と小文字を問わず、どのスキームとポートのURLにも合う）だけ。転送の先にも、同じ範囲を使う。ホームが無いときは、一覧のホストだけ。許していないホストのファイルは、要求を送らず、取り込まずに記録する（`cdn.example.net is not the host of the old site; allow the host to download from it`）。`wp:attachment_url` は、CDNやオフロードのプラグインが書き換えることがあるので、外のホストを許す道が要る一方で、どこにでも取りに行くと、手を入れたWXRが、取り込みを動かすマシンから見える内部のアドレスに、`GET` を送らせられる。
  - 送るもの：`GET` だけ。ヘッダーは、Goが付けるもの（`Host`・`Accept-Encoding: gzip`）と `User-Agent: whiteroom-wpimport`（REST APIの読み込みと同じ）だけで、Cookie・認証・Refererは送らない（転送のときに付くRefererも消す）。gzipの応答はGoが展開し、大きさの上限は、展開した後の大きさで数える。プロキシは、環境変数のものを使う。接続10秒・TLS 10秒・応答のヘッダー30秒・ヘッダー64KiB・TLS 1.2以上の限りがある（`internal/wprest` の読み込みの `Transport` と同じ値）。本文を読む時間の限りは、1回の試行の時間（下記の「やり直す」）。
  - 大きさ：応答の `Content-Length` が64MiBを超えるときは、本文を読まず、取り込まない。長さの分からない応答は、64MiBを超えて読んだところで止める。
  - 同時の数：添付ファイルを同時に4つ（`MediaOptions.Workers`）。添付ファイルは数千から数万あることがあり、1つずつでは時間がかかる。4は、ビルドが同時に読む原本の数の上限（4）と同じ。コピーから読むときも、同じ数で動かす。
  - やり直す：要求が `408`・`429`・`5xx` を返したとき、繋がらないとき、1回の試行の時間（10分。`Downloader.Timeout`。要求を送ってから、本文を読み終えるまで）が過ぎたとき、本文が途中で切れたときだけ。最大3回（`Downloader.Attempts`）試し、2回目の前に1秒、3回目の前に5秒待つ（回数を増やしたときの、4回目以降の前も5秒）。`Retry-After` は読まない。長い取り込みでは、一時的な失敗が起きやすく、やり直さないと、取り込みを初めからやり直すことになる。
  - やり直さない：`404`・`403`・`410` など、ほかの答え（`408`・`429` 以外の `4xx`、`200` 以外の `2xx`、追わなかった `3xx`）、大きすぎる応答、許していない先への転送、形式が読めないファイル（HTMLのページなど）は、取り込まずに記録して、続ける。
  - ダウンロードの理由（取り込まないときの文に入る）：`GET <URL>: 404 Not Found`・`GET <URL>: 503 Service Unavailable (after 3 attempts)`（やり直しても読めなかった。やり直した理由は、`503 Service Unavailable`・`timed out after 10m0s`・`unexpected EOF`・`dial tcp …: connect: connection refused` など）・`GET <URL>: too large: <バイト数> bytes (max 67108864)`・`GET <URL>: stopped after 5 redirects`・`GET <URL>: redirected to <URL2>, which is not on the old site or an allowed host`（`http`・`https` でない先も同じ）・`GET <URL>: redirected to <URL2>, which has credentials in it`・`<URL> cannot be downloaded: use an http or https URL without credentials`・上の、許していないホストの文。URLのパスワードは、`xxxxx` にして書く。
  - 止める：すべての試行で読めなかったファイルが、読めたファイルも、やり直さない答え（`404` など）も挟まずに、20個（同時に読むときは、20個以上のことがある）続いたら、旧サイトが答えないものとして、エラーで止める（`the old site does not answer: 20 files in a row could not be downloaded; the last: GET <URL>: <理由>`。この文には、`(after …)` を付けない）。数は、読めたファイルと、やり直さない答えで、0に戻る。要求を送らずに断ったもの（許していないホストなど）と、取り消しは、数えない。最初の1つで止めると、いつも `500` を返す1つのファイルで、取り込みが進まない。止めないと、旧サイトが落ちているとき、すべてを試してから、メディアの無いサイトができる。
  - 認証と `Retry-After`：認証は送らない（認証の要る旧サイトは、コピーで取り込む）。`Retry-After` と、要求の間隔、取り直しの回避は、6.12の247。
- ロゴとアイコン：サイト設定（`Site`）は、計画の記録で、`logo`・`icon` のメディアを引く（上記の「流れ」）。`Media` は、`Site` が返した設定の `logo`・`icon` が、取り込めなかった添付ファイル（計画した添付ファイルで、ファイルが見つからないなど）と、画像でない添付ファイル（計画の見込みが外れた、PDFなど）を指しているとき、設定から外して（空にして）、記録する（`the logo, attachment 50, is not imported`・`the logo, attachment 50, is not an image`。`icon` も同じ。行き先は `site/settings.json#/logo`・`#/icon`）。呼ぶ側は、設定の文書（`site/settings.json`）を、`Media` の後に書く。計画に無い添付ファイル（ゴミ箱のものなど）は、`Site` が、もう記録している（上記の「取り込みの設定」の「サイト設定」）。取り込みの設定の誤り（WXRに無いIDなど）は、ファイルを読む前に、`Site` で分かり、取り込めなかったものを指す参照は、無いものとして扱い、記録する、という「流れ」の決まりと同じに扱う（6.12の174）。
- 旧URLの対応（`MediaURLs`）：取り込んだメディアの、旧サイトのファイルのパスと、WordPressの投稿ID・メディアのIDの対応（`MediaURL` の `Path`・`Post`・`Media`）を、`Path` の順に返す。`Media` の後に呼ぶ。リダイレクトの登録は、まだ無い（#56。行き先はメディアのID。6.6.6）。
  - 入るもの：`wp:attachment_url` のパスと、同じディレクトリ（`_wp_attached_file` のディレクトリ）の、`_wp_attachment_metadata` が書くファイル（`sizes` の `file` と `original_image`）。`-scaled` の画像では、`-scaled` のファイル・縮小版・元のファイル（`original_image`。取り込めずに、`-scaled` を取り込んだときも）が、同じメディアになる。PDFの `sizes` のファイル（WordPressが作るプレビューの画像）は、PDFのメディアになる（6.12の248）。2つの添付ファイルが同じパスを持つときは、WXRで先の添付ファイルのもの（本文のリンクの変換と同じ規則）で、あとの添付ファイルは、ほかのファイルを持つ。
  - `Path`：ホームのURLより後ろのパス（ホームのパスが `/blog` なら、それを除く）を、`from` の正規の形（6.6.6）にしたもの。必要なところだけをパーセントエンコードし、日本語のファイル名はそのまま、NFDで書かれた名前はNFDのままで、`/` の連なりは1つにする。NFCにそろえず、文字も取り除かない（6.10.1）。クエリと `#` は持たない。
  - 入らないもの：取り込まなかった添付ファイル、添付ファイルのページ（項目の `link`。ただし、プラグインが、ファイルのアドレスを `link` にしているときは、そのファイル）、ホームと別のホストのファイル（6.12の251）、ホームのパスの外のファイル、`wp:attachment_url` が無い添付ファイルと、`?` か `#` を含む `wp:attachment_url`（その添付ファイルの、ほかのファイルも入らない）、`_wp_attachment_backup_sizes` のファイル（6.12の248）、`/`・`?`・`#` を含む名前と `.`・`..`。
- 決まった結果：同じ入力（WXR・コピー・サイト設定・`By`）からは、同時に読む数（`Workers`）によらず、同じメディアの文書・取り込みレポート・表と参照・`files/` のファイルになる（4.3の「同じ入力から同じ出力」）。添付ファイルは並行して読むが、表・参照・取り込みレポートは、WXRの順に変える。旧サイトの答えが変われば（時間切れなど）、結果も変わる。
- メモリと時間：
  - ファイルは、メモリに全部持たず、一時ファイルへ流しながらハッシュを求める（形式を読む `mediafile.Probe` の確保は、1回で約0.14MiB）。ただし、画像は、`Inspect` がファイルの全体を要るので、一時ファイルを、メモリに1回読む（1つの添付ファイルで最大64MiB。画素は展開しない）。同時に読む数が4なら、ファイルの中身で最大約256MiB。`Inspect` の作業のメモリは、測っていない。
  - 結果は、`Media` が返すまで、メモリに残る。1つのメディアで、表・参照・文書を合わせて約1.1KiB（10万個で約110MiB）。
  - 時間は、ファイルの大きさと、旧サイトの速さで決まる。SHA-256は約2.1GiB/s。64MiBのファイルを書いて、同期して、名前を変えるのに約0.12秒（同期なしでは約0.07秒）。200KiBのファイル2000個では、約3.8秒（同期なしでは約0.34秒）。
  - 測った値（2026-11-14）：開発のマシン（16のCPU、メモリ30GB、NVMe SSD）、Go 1.27.3。
- エラーで止まったとき：エラーにするのは、引数が正しくないとき（上記）と、取り込みを続けられないとき：コンテキストが取り消されたか、時間切れになったとき（最後のファイルを読んだ後でも）、原本のディレクトリを作れないとき（`creating the directory of the originals: …`）、原本を書けない・読み戻せないとき（`saving an original in <ディレクトリ>: …`）、コピーを開けない・読めないとき（`reading the copy of the uploads: …`）、旧サイトが答えないとき（上記）。最初に見つけたエラーを返し、読んでいるほかの添付ファイルは中止して、終わるのを待つ。メディアの文書は返さず、表・参照・取り込みレポートも変えない（計画が割り当てたIDは残る）ので、直してから、新しい取り込みとレポートで、初めから取り込み直す（上記の「流れ」）。それまでに書いた原本は残る（取り込み直すと、同じ名前に置き換わる。ダウンロードは、すべて取り直す。6.12の247）。

**本文（ブロックエディタ）**

ブロックエディタ（WordPress 5.0から）が書いた本文（`content:encoded`）を、ブロックの列（6.5）にする。クラシックエディタが書いたHTMLは、下記の「本文（クラシックエディタ）」。この小節の規則は、どれも仮に決めたもの（案）。

- 入口：`(*Import).Body`（`internal/wpimport`）。エントリーの変換が、取り込む項目ごとに1回呼ぶ（上記の「流れ」）。渡すのは、サイト設定（`Site` が作ったもの。`allowHtml` を使う）・取り込みの設定（`blocks` の対応表。無ければ、名前はそのまま）・項目・書き込み先のファイルと、本文のブロックの列のポインター（`/body` など）・ブロックのIDの鍵。返すのは、ブロックの列と、「続きを読む」の位置（下記）。ブロックの列は、検証（6.7の取り込みの規則）を通る。リビジョンの文書には組み立てず、サイトのディレクトリにも書かない。呼ぶたびに取り込みレポートへ記録を足すので、取り込まない項目では呼ばない。同じ鍵と同じ本文からは、同じブロック・同じID・同じ記録になる。
- 区切りの読み方：区切りを読むのは `internal/wpblock` で、WordPress 7.1 の `parse_blocks` が作る木（名前・属性・内側のブロック・HTML・HTMLと内側のブロックの並び）と同じに読む。
  - 区切りは、`<!--`・空白・`wp:`・名前・空白・属性（あれば）・`-->` の順に並んだコメント。`wp:` の前の `/` は閉じる区切り、`-->` の前の `/` は自分で閉じるブロック。空白は、空白・タブ・LF・CR・FFのどれか。名前は、小文字の英字で始まり、小文字・数字・`_`・`-` が続く。名前空間の `/` を付けられ、付けないものは `core/` になる（`wp:paragraph` と `wp:core/paragraph` は同じ）。名前の後ろには、属性が無くても、空白が要る。
  - 属性は、`{` から、直後に空白と `-->`（か `/-->`）が続く最初の `}` までで、間の文字列は見ない（文字列の中の `}` と `-->` も、その位置が終わりに見えれば、終わりになる）。
  - 閉じる区切りは、名前を開く区切りと比べず、いちばん内側の開いたブロックを閉じる。開いたブロックが無いときの閉じる区切りは、そこで読むのをやめ、直前のブロックの後ろから文書の終わりまでを、1つのHTML（区切りも文字として）にする。ブロックの間のHTMLは、名前の無いブロックとして残す。
  - 7.1 と違うのは次の3つで、どれも後の版（開発版の7.2）に合わせた（6.12の190）。閉じ方：文書の終わりまでに閉じていないブロックが重なっているとき、内側のものを外側のものの中に入れて閉じる（7.1 は、それぞれを別のブロックとして、内側から順に並べる）。`0` だけの断片：HTMLの断片は、空のときだけ捨て、`0` だけの断片は残す（7.1 は、`0` だけの断片も、空と同じに捨てる）。空の断片：内側のブロックの閉じる区切りの直前の、空のHTMLの断片は、`innerContent` に残さない（7.1 は、残す）。
  - 時間は、文書の長さに比例する（同じ位置を二度探さないので、`<!-- wp:a {` を繰り返す文書でも）。
- 属性のJSON：PHPの `json_decode`（連想配列にするもの）と同じに読む。`true`・`false`・`null` は小文字だけ、FFとVTは空白でなく、片方だけのサロゲートと不正なUTF-8は断り、`\u0000` は受け付ける。名前が重なれば、最初の位置に最後の値を持つ。数は、書かれたままの文字で持つ。入れ子は511段まで（上記の「上限」）。JSONの後ろの空白（`}` と `-->` の間）も読む範囲に入り、FFがあると不正になる。不正なら、属性を空のオブジェクトとして変換し、変えたものとして記録する（`the attributes of the block "core/paragraph" are not valid JSON; they are ignored`）。
- 振り分け：ブロックの名前で、変換を決める（名前ごとの変換は下記）。変換の無い名前は `legacy` にする：WordPressが表示のときにHTMLを作るコアのブロック（最新の投稿・検索・ナビゲーション・コメント・投稿のタイトルなど。6.10.3）は `the block "core/latest-posts" is made by WordPress when the page is shown`、ほかの名前（テーマやプラグインのブロックと、変換の無いコアのブロック（`core/math` など））は `the block "acme-shop/product-card" is not converted`（対応表は6.12の191）。脚注（`core/footnotes`。WordPress 6.3から）も、表示のときにHTMLを作るブロックで、脚注の文は、項目のメタデータ（`footnotes`）にあり、いまは取り込まない。文の中の脚注の番号は、上付きのページ内のリンクとして残り、行き先が無い（6.12の197）。ブロックの間のHTMLは、空白と制御文字だけなら捨て、ほかは、クラシックのHTMLとして変換する（下記の「本文（クラシックエディタ）」）。クラシックのブロック（`core/freeform`）と、区切りの無い本文（全体を1つのHTMLとして）も同じ。`core/shortcode` は、中身を、段落を作ってから、クラシックのHTMLとして変換する。段落などの文字の中のショートコードは、探して、見つけたものを含むブロックを `legacy` にする（中身が1つのショートコードだけの段落は、それだけのブロックにする。下記の「ショートコード」）。1つのURLだけの段落は、許可リストに合えば `embed` にする（下記の「URLだけの行」）。開く区切りの無い閉じる区切りより後ろは、1つの `legacy` にする（`a block closer without an opener ends the blocks; WordPress shows the rest as it is`）。親の変換が読む部品のブロック（`core/list-item`・`core/column`・`core/accordion-item`・`core/accordion-heading`・`core/accordion-panel`）が、親の外にあれば、`legacy` にする（`the block "core/list-item" is outside "core/list"`）。
- `legacy`：WordPressのブロックごとに1つ作り（複数のブロックをまとめない）、`html` は、区切りから閉じる区切りまでの元の文字（内側のブロックも）、`reason` は理由の文にする。リスト・表・ボタンの組・カラムの組・アコーディオンのように、部品を自分で変換するブロックは、部品が1つでも変換できないと（セルの中の画像など）、そのブロック全体を `legacy` にする（6.12の194）。要確認（`review`）として、理由の後ろに `; it is a legacy block` を付けて、ブロックの位置に記録する（`the block "core/latest-posts" is made by WordPress when the page is shown; it is a legacy block`）。`html` が1つの文字列の上限（1MiB。6.7）を超えるときは、`legacy` を作らず、取り込まなかったものとして記録する（`the block "core/html" is not imported: its HTML is too long: <バイト数> bytes (max 1048576)`。6.12の24）。ブロックの名前が無いときは、`the block "core/html"` の代わりに、区切りの無い本文（クラシックの本文）なら `the content of the classic editor`、同期パターンの写しの中で、パターンの中身全体（区切りが無いもの）なら `the content of the synced pattern`、開く区切りの無い閉じる区切りより後ろなら `the rest of the content after a block closer without an opener`、ブロックの間のHTMLなら `the HTML between blocks`、ブロックの変換が部品の元の文字から作る `legacy`（古いギャラリーの項目など）なら `a part of the block` と書く。クラシックのHTMLの変換が作る `legacy` は、`the element <dl>`・`a part of the HTML of the classic editor`・`the shortcode [box]`・`the URL` と書く（下記の「本文（クラシックエディタ）」）。
- 改ページと「続きを読む」：改ページ（`core/nextpage`）は取り除き、本文ごとに1つ、取り込まなかったものとして記録する（`1 page break is removed; whiteroom has no page breaks`。2つ以上は `2 page breaks are removed; whiteroom has no page breaks`）。「続きを読む」（`core/more`）は取り込まない。最上位にある最初のものの位置を、その前にある最上位のブロックの数で返し（無ければ -1）、抜粋は、エントリーの変換（#55）が、その位置から作る（6.10.1）。最上位でないものは、どれも取り除いて記録し（`the more block is removed: it is not at the top of the content`）、最上位の2つ目からは、黙って取り除く。`noTeaser` が真なら、変えたものとして（`the more block hid the text before it on the page (noTeaser); whiteroom shows it`）、`customText` は、取り込まなかったものとして（`the text "<文字>" of the more link is not imported`）、本文の位置に記録する。同期パターンの写しの中の改ページと「続きを読む」は、WordPressが投稿の本文だけで抜粋とページを分けるので、記録せずに取り除く（改ページの数にも、「続きを読む」の位置にも入れない）。クラシックのHTMLの `<!--nextpage-->` と `<!--more-->` も、同じに数えて返す（下記の「本文（クラシックエディタ）」の「ページ」「続きを読む」）。
- 文中装飾：段落・見出し・リスト項目・引用の出典・表のセル・キャプションなどの文字は、HTMLを `internal/html` で読み、文中装飾（6.5.2）にする。
  - マーク：`b`・`strong` は `bold`、`i`・`em` は `italic`、`u`（と `text-decoration: underline` の `span`）は `underline`、`s`・`strike`・`del` は `strike`、`code`、`sub`、`sup`、`a` は `link`（下記）にする。`br` は `hardBreak`。`span` の `style` の `text-decoration`・`font-weight`・`font-style` も、`underline`・`strike`・`bold`・`italic` として読む（下記の「本文（クラシックエディタ）」の「文中の装飾」）。外の要素から順に並べ、すでにあるマークと同じものは、1つにする。`highlight` の中の `highlight`、`sub` と `sup` の入れ子は、内側を外して、変えたものとして記録する（`removed <sub> inside <sup>, <sup> inside <sub>`）。
  - ハイライト：`mark` と、クラスに `has-inline-color` のある `span`（`blocks.marks` が空でない名前に対応させているクラスのある `span` も）。`variant` は、`blocks.marks` が空でない名前に対応させているクラスのうち、最初のものの名前。そういうクラスが無ければ、`mark` と `has-inline-color` の `span` に限り、表に無いクラスのうち、`has-`・`wp-` で始まらない最初のものを、そのままの名前にする。`variant` にしたときは、色は取り込まず、色の指定（プリセットのクラスか、`style` の色）があれば、取り込まなかったものとして、要素のタグを並べて記録する（`the colors of <mark>, <span> are not imported: a highlight with a variant has no colors`）。`variant` にならなければ、色にする：クラスの `has-<名前>-color`・`has-<名前>-background-color` は、`blocks.presets.color` で変えたプリセット、無ければ、`style` 属性の `color`・`background-color`（透明は除き、色の規則（6.5.3）に合うもの）。取り込まないプリセットは、値で置き換えずに記録する。何も残らなければ、文字だけを残す。ほかの `span` も、`style` の `color`・`background-color` があれば（透明は除き、色の規則に合うもの）、その色のハイライトにする（TinyMCEが書く形。クラシックの本文と同じ）。
  - 文字だけを残す要素：ほかの要素（`span`・`small`・`abbr`・`kbd` など）は、タグを外して文字だけを残し、変えたものとして記録する（`kept only the text of <kbd>`。属性の無い `span` は記録しない）。ブロックの要素（`p`・`div`・`h1`〜`h6`・`blockquote`・`pre`・`figure`・`li` など）も、タグを外し、前後に `hardBreak` を入れる。`script`・`style`・`template`・`title`・`noscript`・`noembed`・`noframes` は、中身ごと取り除き、取り込まなかったものとして記録する（`removed <script>, <style>, <template>, <noscript> with their content`）。
  - 文中装飾にできない要素：画像・`picture`・`svg`・`math`・`iframe`・`video`・`audio`・`object`・`embed`・`canvas`・`ruby`・入力部品（`input`・`select`・`textarea`・`button`・`meter`・`progress`）・`map`・`ul`・`ol`・`dl`・`table`・`hr` を含む文字は、そのブロックを `legacy` にする（`the text has <img>, which rich text cannot have`。6.12の194）。
  - 空白：続く空白と改行は1つの空白にし、行頭・行末の空白と、ブロックの要素の前後の空白は除く。詩（`core/verse`）は、改行を `hardBreak` にし、空白をそのまま残す。垂直タブ・U+0085・U+2028・U+2029（詩では、タブとFFも）は空白にする。整えたことは、記録しない。
- リンク：`a` の `href` を、次のとおりにする。
  - `#名前`：ページ内のリンク（`anchor`）。名前が、6.7の名前の規則（日本語などは使えない）に合わなければ、リンクを外して文字だけを残し、取り込まなかったものとして記録する（`the link to "#日本語" is removed: the anchor is not a name that whiteroom accepts`。6.12の12）。クラシックのHTMLの飛び先（`<a name>` と `<a id>`）は、`anchor` にする（下記の「本文（クラシックエディタ）」の「ページ内リンクの飛び先」）。
  - 旧サイトのURL（スキームの `http`・`https`、ホストとポートがホームのURL（チャンネルの `link`）と同じで、ホームのパスの下にあるもの。パスは8192バイトまで。相対URLは、項目の `link` を基にする。`link` が無いときと、8192バイトより長いときは、ホームのURLを基にする）：取り込んだエントリーのURLなら `entry`、取り込んだメディアのURLなら `media`。パスの中で `/` が続くところは、探すときも、`href` にするときも、探す表に入れる投稿のURL（WXRの `link`・`wp:attachment_url`）のパスでも、1つにする（`//about/` は `/about/`。WXRが `https://example.com//2026/10/hello/` のような `link` を持っていても、`/2026/10/hello/` でも `//2026/10/hello/` でも探せる）。エントリーのURLは、`link` のパスと、`?p=`・`?page_id=` の形で、`#` の後ろは `anchor` にする（名前の規則に合わなければ、`anchor` だけを外して記録する）。パスで探すので、URLのクエリは、エントリーへのリンクでは落ちる。メディアのURLは、添付ファイルのページと、`wp:attachment_url`・縮小版・元の画像のファイル（`?attachment_id=` の形も）で、`#` の後ろは捨てる。ほかの、旧サイトのURL（取り込んでいない投稿、タームの一覧など）は、サイトの中のパスの `href`（`/about/?x=1#top` のように、クエリと `#` の後ろも）にする。ホームのURLと、その下の `index.php` に、クエリのあるURLは、`p`・`page_id`・`attachment_id` が投稿を指すときだけ、その投稿のURLとして探す。ほかのクエリ（`?cat=3`・`?s=…`・`?tag=…`・`?author=…` など）は、トップページではなく、WordPressが作る一覧なので、ここに入る（`href` は `/?cat=3` のように、クエリを付けたパスになる）。スキームの無いURLを、基にするURLで解いた長さは、読むHTMLに数える（下記の「上限」の「リンクのアドレス」）。
  - ほかのサイトのURLと、`mailto:`・`tel:` は、そのまま `href` にする。`href` の規則（6.5.2）に合わないもの（`javascript:` など）は、リンクを外して、記録する（`the link to "<href>" is removed: <理由>`。`<href>` は、HTMLに書いたまま引く。相対URLを、基にするURLで長くしたものではない）。
  - `target="_blank"` は `newTab`、`rel` の `nofollow`・`sponsored`・`ugc` は `rel` にする（`noopener`・`noreferrer` は取り込まない）。
- 見た目：ブロックの `textColor`・`backgroundColor`・`borderColor`・`gradient`・`fontSize`・`fontFamily`（プリセットの名前）と、`style`（`color`・`typography`・`spacing`・`border`・`elements.link.color.text`）から、`style`（6.5.3）を作る。古い形の `customTextColor` などの属性も読む。プリセットの名前の属性は、`style` の値より先に使う。
  - プリセット：属性の名前と、`style` の値の2つの参照の形（`var:preset|color|vivid-red` と `var(--wp--preset--color--vivid-red)`）を、`blocks.presets.<種類>` で、このCMSのテーマの名前に変える。表が空にする名前と、名前の規則に合わない名前は、取り込まずに記録する（`the color preset "pale-pink" is not imported: blocks.presets.color maps it to nothing`）。
  - 直接の値：6.5.3の長さと色の規則を通るものだけを取り込む。数は `px` にする。通らないものは、取り込まずに記録する（`the <項目> "<値>" is not imported: <理由>`）。グラデーションとフォントの家族は、プリセットだけを取り込む。
  - 辺と角：`padding`・`margin` は、4辺を別々に取り込む。`blockGap` は、横に並べるブロック（`columns`・`buttons`、`layout` が横向きの `flex` の `group`）では `left`、ほかは `top` を使い、もう一方の値が違えば記録する。枠線は、4辺の幅・種類・色が同じときだけ、角丸は、4つの角が同じときだけ取り込み、違えば記録して取り込まない（`the border is not imported: its sides differ, and whiteroom has one border for all four sides`。6.12の13）。
  - このCMSに無いもの（`style` の `typography.fontStyle`・`shadow`・`dimensions` など。ブロックごとの属性は、下記のブロックごとの変換）は、ブロックごとに1つの記録にまとめて、名前を並べる（`lost style.dimensions.minHeight of the block "core/button"; whiteroom has no such settings`。10個まで、残りは `, and <数> more`。6.12の20）。表示に関わらないもの（`th` の `scope` など）は、黙って捨てる。
- バリエーション・追加のクラス・アンカー：
  - `className` の `is-style-<名前>` は、`blocks.variants` で `variant` にする（`is-style-default` は黙って捨てる）。ブロックは1つのバリエーションしか持てないので、2つ目からは記録して捨てる（`the block style "solid-color" is not imported: a block has one style`）。表が空にするものと、名前の規則に合わないものも、記録して捨てる（`the block style "outline" is not imported: blocks.variants maps it to nothing`）。
  - ほかのクラスは、最初の1つを `className` にし、ほかは、取り込まずに記録する（`the classes "a", "b" are not imported: whiteroom blocks have one class name`。10個まで。6.12の11）。名前の規則に合わないクラスと、本体が付けるクラスの形（`b-xxxxxxxx`・`hl-xxxxxxxx`）も、取り込まない。埋め込みの `wp-embed-aspect-*` と `wp-has-aspect-ratio` は、黙って捨てる。
  - `anchor` は、ブロックの最初の要素の `id`。名前の規則に合わないとき（日本語など）と、ほかのブロックが先に使っているときは、取り込まずに記録する（`the anchor "section-1" is not imported: another block has it`。6.12の12）。`legacy` になったブロックは、アンカーを手放す。
- 名前の対応表：プリセット・バリエーション・画像のサイズ・`highlight` のバリエーションは、取り込みの設定の `blocks`（上記の「取り込みの設定」）で変える。表に無い名前は、名前の規則に合えば、そのまま使い、値が空の名前は、取り込まない。設定を渡さないときは、すべてそのまま使う。
- ブロックごとの変換：ブロックの名前ごとに書く。内側のブロックを持つブロックのHTMLのうち、内側のブロックの外にある文字や要素（古い版のグループの `wp-block-group__inner-container` など、WordPressが書く入れ物は除く）は、取り込まず、ブロックごとに1つ記録する（`the HTML of the block "core/group" outside its inner blocks is not imported`）。HTMLがWordPressの書き方でないとき（期待した要素が無いなど）は、`legacy` にする（`the HTML of the block is not as WordPress writes it: expected <p>`）。HTMLが複雑すぎて読めないときは、`the HTML of the block is too complex to read`。
  - `core/paragraph`・`core/verse`：`paragraph`。`textAlign` は、`left`・`center`・`right` を取り込む。`dropCap`・`direction`・`justify` などは取り込まず、記録する（`lost dropCap, direction, align of the block "core/paragraph"; whiteroom has no such settings`）。
  - `core/heading`：`heading`。`level` は要素（`h1`〜`h6`）から決め、`h1` は `h2` にして記録する（`the heading level 1 is 2 here; h1 is for the title`）。文字の無い見出しは取り除いて記録する（`the empty heading is removed`）。
  - `core/list`・`core/list-item`：`list`・`listItem`（`ordered`・`start`）。`listItem` の中に `paragraph` と、入れ子の `list` を作る。項目の無いリストは、取り除いて記録する（`the empty list is removed`）。`reversed`・`type` は取り込まず、記録する。
  - `core/quote`・`core/pullquote`：`quote`（出典は `citation`）。プルクオートは、`pullquote` のバリエーションの `quote`。文字揃えは取り込まず、記録する。
  - `core/code`・`core/preformatted`：`code`。文字は、書かれたままで（改行はLF、`br` は改行）、タグは外す。`language` は、`code` 要素（無ければ `pre`）のクラス `language-<名前>`。
  - `core/table`：`table`。行は `head`・`body`・`foot` の順に並べ、セルは `header`（`th`）・`colspan`・`rowspan`・`textAlign` を持つ。セルの文字は文中装飾。固定の幅（`hasFixedLayout`）と、取り込めない `colspan`・`rowspan`・`textAlign` は記録する（`lost hasFixedLayout of the block "core/table"; whiteroom has no such settings`）。WordPressの既定は固定の幅で、既定のままの表は、属性に書かれないので、固定の幅かどうかは、属性ではなく、`table` 要素のクラス `has-fixed-layout` で決める。セルが5000個を超える表と、セルに文字でないもの（画像など）がある表は、表全体を `legacy` にする（6.12の194）。
  - `core/separator`・`core/spacer`：`separator`・`spacer`。`height` は、数なら `px`、`var:preset|spacing|<名前>` なら、`blocks.presets.spacing` で変えたプリセット。受け付けない高さの `spacer` は、取り除いて記録する（`the spacer is removed: its height "var:preset|spacing|60" is not one that whiteroom accepts: blocks.presets.spacing maps it to nothing`）。
  - `core/html`（カスタムHTML）：iframeが1つだけ（単独か、1つの `div`・`p` の中）で、`src` が `youtube`・`vimeo`・`googleMaps` の許可リスト（6.5.4）に合えば、`embed` にして、変えたものとして記録する（`the iframe of the custom HTML is an embed block here`。`//` で始まる `src` は、`https:` を付けて読む）。ほかは、`allowHtml` が `true` なら `html`（両端の空白と改行は除く）にして、要確認として記録し（`the custom HTML is an html block; check what it shows`）、`false` なら `legacy`（`custom HTML, which the site does not allow (site.allowHtml is false)`）にする。サニタイズは、描画のときにする（6.5.4。6.12の98）。
  - `core/group`：`group`。`layout` の `constrained`・`default` は流れのまま（書かない。WordPress 5.9と6.0が `constrained` の代わりに書いた `{"inherit":true}` も同じで、記録しない）、`flex` は `row`（縦向きは `stack`）と `justifyContent`・`verticalAlignment`・`nowrap`、`grid` は `columns` と `minColumnWidth` にする。`tagName` は `section`・`article`・`aside` だけ取り込み、`main`・`header` などは `div` にして記録する（`the group's <main> is a <div> here`）。`align` は `wide`・`full` だけ。取り込めない `layout` の項目（`contentSize`・`wideSize` など）は、`layout.contentSize` のように記録する。ブロックの無いグループは、取り除いて記録する（`the empty group is removed`）。
  - `core/image`：`image`。画像は、取り込んだ添付ファイルの画像でなければならない（下記の「参照」）。`alt` は、`isDecorative` が真なら `decorative`、そうでなければ `img` の `alt`（無ければ、属性の `alt`）にする。どちらも空で、メディアにも `alt` が無いときは、`alt` を書かず、要確認として記録する（`the image has no alt; set alt, or decorative for a decorative image`。位置は `…/attrs/alt`。WordPressは、`alt` を設定していない画像にも空の `alt` を書くので、空の `alt` を装飾とは決めない。6.12の19）。`figcaption` は `caption`（文中装飾）、画像を囲む `a` は `link`（上記のリンク）、`sizeSlug` は `size`（`blocks.imageSizes`。`full` は書かない）にし、`width`（数は `px`）・`aspectRatio`・`align`（`left`・`center`・`right`・`wide`・`full`）を取り込む。`lightbox`・`height`・`scale`・`title`・`focalPoint` は取り込まず、記録する。ただし、エディタが画像の大きさを変えたときに書く `height` の `auto`（空も）と、`aspectRatio` を取り込んだ画像の `scale` の `cover` は、描画が同じなので、記録しない。
  - `core/file`：`file`。メディアは、属性の `id`、無ければ `href`、無ければ最初の `a`（`download` の無いもの）のURLで探す。画像でもPDFでもよいが、取り込んだ添付ファイルでなければ `legacy`（`the file is not an imported attachment`）。`label` は、その `a` の文字。`displayPreview` と `textLinkTarget` は取り込まず、記録する。
  - `core/embed`・`core-embed/<名前>`（WordPress 5.6より前）：`embed`。提供元は `providerNameSlug`（無ければ、ブロックの名前）で決め、`youtube`・`vimeo`・`twitter`・`x` だけ（`twitter` と `x` は `x`）。提供元の無い `core/embed` は、URLから、`youtube`・`vimeo`・`x`・`googleMaps` の順に当てる。URLは、属性の `url`（無ければ `wp-block-embed__wrapper` の文字）。許可リストに無い提供元（`instagram` など）と、受け付けないURLは `legacy`（`embeds of "instagram" are not allowed`・`the URL cannot be embedded: <理由>`）。`figcaption` は `caption`。
  - `core/buttons`・`core/button`：`buttons`（`justify`。`space-between` は `spaceBetween`）と `button`（`label` は `a` の文字、`link`、`width` は 25%・50%・75%・100%）。文字の無いボタンは、取り除いて記録する（`the empty button is removed`）。`buttons` の中に `button` 以外のブロックがあれば、`legacy`（`the buttons block has a block other than buttons`）。`buttons` の外の `core/button`（WordPress 5.4より前）は、ボタンが1つの `buttons` にする（`align` は取り込まず、記録する）。
  - `core/columns`・`core/column`：`columns`（`verticalAlign`・`stackOnMobile`）と `column`（`width`・`verticalAlign`）。カラムの中の `columns` は `group` にする：カラムに幅も揃えも無く、16以下なら `grid`（`columns` はカラムの数）、そうでなければ `row` で、カラムごとの `group` を持つ。変えたものとして記録する（`the columns inside columns are a group here`。カラムに幅があれば、幅は失い、後ろに `; the widths of the columns are lost` を付ける）。
  - `core/media-text`：`columns`（メディアと文章の、2つの `column`。幅は `mediaWidth` とその残りで、既定は半分ずつ。メディアが右なら、文章が先）。メディアは `image` にし、画像でなければ（動画など）、メディアのHTMLの `legacy` にする。変えたものとして記録する（`the media and text block is columns here`）。カラムの中では、2つの `group` を持つ `group`（`row`）にして、`the media and text block inside columns is a group here` と記録し、`mediaWidth` は、書かれていれば、取り込まずに記録する。
  - `core/gallery`・`core/cover`・`core/details`・`core/accordion`・`core/video`・`core/audio`・`core/block`：下記の「段階2のブロック」。`contact-form-7/contact-form-selector`・`core/pattern`：下記の「参照」。
  - 古い版が書いた形も読む：6.1より前のリスト（内側のブロックが無く、`li` がHTMLにある）、内側のブロックの無い古い形の引用（`p` がHTMLにある）、5.9より前のギャラリー（`li` の画像）、古い版のグループ（内側の入れ物）、5.6より前の埋め込み（`core-embed/<名前>`）、`div` で囲んだ配置つきの画像。
- 段階2のブロック（6.5.5）と、段階2にも無いブロック（アコーディオン）：このCMSに無いブロックは、次のように置き換え、変えたものとして記録する。段階2のブロックができたときの直し方は、6.12の193。
  - `core/gallery`：画像のブロック（内側の `core/image`。WordPress 5.9より前の形は、`li` の画像）の列。`figcaption` は、画像の後ろの段落。キャプションが文中装飾にできないとき（長すぎるとき、画像などがあるとき）は、キャプションだけを取り込まず、ギャラリーの位置に記録し（`the caption of the gallery is not imported: <理由>`。理由は、`the text has <img>, which rich text cannot have` や、上限の「文中装飾の文字」の文）、画像は残す。取り込めない画像は、その画像だけを `legacy`（理由は画像のもの）。ギャラリーの列数・切り抜き・`className` などは、取り込まずに記録する（`linkTo` は、リンクが画像のHTMLにあるので、記録しない）。記録は `the gallery is 2 images here; whiteroom has no gallery blocks yet (stage 2)`。
  - `core/cover`：`group`。背景画像は、先頭の `image`（`alt` が無ければ `decorative`）、重ねる色（`overlayColor`）は `backgroundColor`（`dimRatio` が0のときは付けない）、中身は後ろのブロック。背景画像が、取り込んだ画像の添付ファイルでなければ（外部の画像など）、先頭の `image` の代わりに、その `img` 要素のHTMLだけの `legacy` を置き、ほかの画像と同じに、要確認として記録する（`the image is not an imported attachment`・`the image is a PDF attachment`）。`img` 要素の無いカバーでは、背景を取り込まず、取り込まなかったものとして記録する（`the background image of the cover is not an imported attachment`）。`tagName`・`layout`・`align` は `group` のとおり。`dimRatio`（0と100のほか）・`minHeight`・`focalPoint`・`contentPosition`・`hasParallax`・`isRepeated` などは取り込まず、記録する（`lost dimRatio, minHeight of the block "core/cover"; whiteroom has no such settings`）。背景が動画のものは、背景を取り込まない。ブロックも背景画像も無いカバーは、取り除いて記録する（`the empty cover is removed`）。記録は `the cover is a group here; whiteroom has no cover blocks yet (stage 2)`。
  - `core/details`：`summary` の文字を `label` にした `group` で、いつも開く。記録は `the details block is a group here, always open; whiteroom has no details blocks yet (stage 2)`。
  - `core/accordion`（WordPress 6.9から）：項目（`core/accordion-item`）ごとの `group` を並べた `group`。項目の `label` は見出しの文字、中身はパネルのブロックで、いつも開く。記録は `the accordion is groups here, always open; whiteroom has no accordion blocks`。
  - `core/video`・`core/audio`：`legacy`（`whiteroom has no video blocks yet (stage 2)`・`whiteroom has no audio blocks yet (stage 2)`）。
  - 再利用ブロック（`core/block`）：共有ブロックができるまで、中身を写す（下記の「参照」）。
- 参照：画像とファイルは、取り込んだメディアを指し、フォームのブロックと再利用ブロックは、取り込んだ項目を探す。`Body` は、メディアの変換が、取り込めなかった添付ファイル（ファイルの無いものなど）を表から外した後に呼ぶ（上記の「流れ」）ので、外されたものは、取り込んでいないものとして扱う。
  - 画像のメディア：属性の `id`、無ければクラス `wp-image-<数>`、無ければ `src` のファイル（`wp:attachment_url`・縮小版・元の画像。相対URLも）から探す。取り込んだ画像でなければ、そのブロックを `legacy` にする（`the image is not an imported attachment`・`the image is a PDF attachment`）。外部の画像は、この `legacy` の中に残る（6.12の99）。カバーの背景画像は、`img` 要素のHTMLだけの `legacy` にする（上記のカバー）。
  - Contact Form 7 のブロック（`contact-form-7/contact-form-selector`）：属性の `hash`（7桁以上の小文字の16進数なら、フォームの `_hash` の先頭と比べる。Contact Form 7 6.2.4.1 と同じで、大文字を含むものは、ハッシュとして探さない）・`id`・`title` の順にフォームを探し、取り込んだフォームなら、そのフォームを参照する `form` ブロックにする（6.10.1・6.10.3）。見つからないものと、取り込んでいないものは、`legacy`（`the form "取り込まないフォーム" is not imported`。`title` が無ければ `the form 31 is not imported`）。
  - 同期パターン（再利用ブロック。`core/block`）：属性の `ref` の `wp_block` がWXRにあれば、その中身を、使っている場所に変換して写し、変えたものとして記録する（`the synced pattern 41 ("お問い合わせへの案内") is copied here; whiteroom has no shared blocks yet (stage 2)`）。写しは、使うたびに、別のブロックと別のIDになる。公開していないもの（`the synced pattern 42 is not published; WordPress shows nothing for it`）、パスワードのあるもの（`the synced pattern 43 has a password; WordPress shows nothing for it`）は、WordPressが何も表示しないので、写さず、`legacy` にする。WXRにないもの（`the synced pattern 99 is not in the WXR`）、自分を含むもの（`the synced pattern <番号> includes itself`）、上限を超える数のブロックを持つもの（`the synced pattern <番号> has more than 40000 blocks`）、写しの中の写しが32段を超えて続くもの（`the synced patterns are nested more than 32 deep`）も、`legacy`。写す中身の大きさは、読むHTMLに数える（上限）。上書き（ブロックの `content`）は写せず、記録する（`the overrides of the synced pattern <番号> are not applied`）。
  - テーマのパターン（`core/pattern`）：テーマのファイルにあり、WXRに無いので、`legacy`（`the pattern "twentytwentyfive/cta-banner" of the theme is not in the WXR`）。
- ブロックのID：`b_` と、小文字の英数字8文字（6.5.1）を、同じ入力から同じものになるように作る。作り方の版（上記の「ID」の `whiteroom wpimport id 1`）・`block`・呼ぶ側が渡す鍵（リビジョンのIDなど）・ブロックを作った順の番号を、それぞれの後ろにNULを付けてつないだもののSHA-256の先頭8バイトを、36の8乗で割った余りを、36進数にして、8桁にそろえる。重なったら、次の番号で作り直す。部品（`listItem`・`tableRow`・`tableCell`）には付けない。番号は、変換がブロックを作った順に数え、作ってから取り除いたブロックも数えるので、ブロックを足したり消したりして取り込み直すと、その後ろのブロックのIDが変わる（6.12の195）。作り方の版を上げても、IDが変わる。
- 守り（検証）：変換が作ったブロックの列は、正規化してから、検証（6.7の取り込みの規則。`allowHtml` と、照会の関数を使う）にかける。変換は、検証を通るように書いてある。通らないものが紛れたときは、問題のあるブロックを含む、流れ（本文の最上位と、引用・グループ・カラムの中）の中の1つを、同じWordPressのブロックの1回の変換から作ったブロック（同期パターンの2つの写しは、2回の変換）と一緒に、元の文字の `legacy` にする（理由は `the conversion does not pass validation: /attrs/media: missing media`。要確認）。元になるWordPressのブロックが無いブロックと、守りが作った `legacy` が通らないときは、そのブロックを取り込まずに記録する（`the block is not imported: /0/attrs/media: missing media`）。1回の検証で見つかった問題は、すべて直し、直したものを、また検証する。何度検証しても通らないときは、本文を取り込まずに記録する（`the content is not imported: it does not pass validation: <問題>`）。
- 上限：上記の「上限」の表のとおり。作るブロックは、6.7の上限に収める。
  - 本文のブロックが1万個を超えるときは、超える最上位のブロックから後を、取り込まずに記録する（`the blocks from /body/10000 on are not imported: a document has at most 10000 blocks`）。入れ子が32段を超えるブロックは `legacy`（`the blocks are nested more than 32 deep`）、セルが5000個を超える表も `legacy`（`the table has more than 5000 cells`）にする。
  - 変換するブロックの数か、読むHTMLの大きさが上限に達したときは、そこから後を、取り込まずに記録する（上記の表の「変換するブロックと、読むHTML」の行）。読むHTMLの上限に達したブロックは、`legacy`（`the conversion has read more than 67108864 bytes of HTML`）にする。
  - 数えるもの：WordPressのブロックと、変換が要素から作る部品を、1つずつ数える。カラム・ボタンのように、変換が内側のブロックを自分で読むブロックも数え、アコーディオンの項目は、見出しとパネルと合わせて1つ。部品は、リストの項目（古い形の `li` も）、古い形のギャラリーの項目、古い形の引用とプルクオートの `p`、表の行とセル。同期パターンの写しは、写すたびに、もう一度数える。数が上限に達したら、部品を作る途中でも、そこで変換をやめるので、1つのブロックが作る部品の数も、上限に収まる。数が上限に達して、ブロックに何も残らなかったときは、そのブロックを作らず、空のブロックを取り除く記録も付けない（変換をやめた記録だけが残る）。
  - リンクのアドレス：基にするURL（上記の「リンク」）の長さは、本文ごとに1回だけ求める。スキームの無いアドレス（相対URLと、`/` や `//` で始まるもの）は、基にするURLで解くたびに、基にするURLを写すので、その長さを、読むHTMLに数える（相対URL1つにつき1回。`../` で基にするURLのパスを外して、解いた結果が短くなっても、数える）。解いたものがエントリー・メディア・`href` のどれになっても、外されても、画像・ファイル・カバーの添付ファイルが見つかっても見つからなくても、同じで、スキームのあるアドレスは数えない。できる `href` の長さは、基にするURLと書いたアドレスの長さの和を（`%` で書き直す分を除いて）超えないので、数えた分が、`href` が足す分の上限になる。数えるのは、文中・画像・ボタンのリンクの `href` と、画像の `src`、ファイルの `href`（ブロックの属性と、リンクの `a`。属性で見つからなければ、`a` も解く）、カバーの背景の `url` で、数えて上限を超えたアドレスのあるブロックは、`legacy`（`the conversion has read more than 67108864 bytes of HTML`）にして、そこで変換をやめる（上記のとおり）。
  - 1つのブロックのHTML：内側のブロックのHTMLを除く、ブロックのHTMLが8MiB（8388608バイト）を超えるときは、読まずに、ブロックを `legacy` にする（理由は `the HTML of the block has more than 8388608 bytes`）。ただし、このブロックの元の文字は1MiBを超えるので、`legacy` は作られず、取り込まなかったものとして記録する（記録の文は、上記の表の「1つのブロックのHTML」の行）。この大きさのHTMLは、読むHTMLの64MiBに数えない。
  - メモリ：本文の変換のメモリは、おもに、1つのブロックのHTMLから `internal/html` が作る構文木で決まり、HTMLの約50〜70倍になる（1つのブロックのHTMLの上限は、このため）。8MiBのブロックが続く本文で、最大RSSは約1.2GBになった（前のブロックの木は、次の木が育ってから回収される）。クラシックのHTMLの変換の最悪も、同じくらい（下記の「本文（クラシックエディタ）」の「メモリ」）。
  - 同期パターンの入れ子：写しは、使うブロックと同じ深さに作るので、ブロックの入れ子の上限では、写しの連鎖が止まらない。そのため、写しの連鎖を32段までにする（上記の表と「参照」）。
  - 文中装飾の文字：1つの段落・見出し・セルなどの文字が、バイト数に、文字の断片と改行（詩は行ごと）ごとに20バイトを足して、1MiB（6.7の1つの文字列の上限）を超えるときは、読むのをやめて、そのブロックを `legacy` にする（理由は `the text has more than 1048576 bytes, counting 20 for each piece of text and each break`）。6.7は、文中装飾の断片の数を制限しないので、断片ごとに足して、数を抑える。画像のキャプション・リスト項目・表のセルなど、ほかの部品の文字が超えたときは、そのブロックが `legacy` になる（古い形のギャラリーの項目は、その項目だけ）。ギャラリーのキャプションは、超えても、キャプションだけを取り込まない（上記の `core/gallery`。ギャラリー全体を `legacy` にすると、キャプションが長ければ1MiBに入らず、画像も失うため）。
  - 変換したブロックのJSONの大きさは、確かめない（6.12の196）。リンクのアドレスは、そのリンクが付く文字の断片ごとにJSONに書かれるので、JSONは、読んだHTMLよりずっと大きくなることがある（アドレスは、読むHTMLに1回だけ数える）。
- 記録：取り込みレポート（下記）に、ブロックごと・種類ごとに1つ記録する（同じブロックの、取り込まなかった属性は、名前を並べて1つ）。行き先（`target`）は、書き込み先のファイルの、そのブロックの位置（`#/body/3`、内側のブロックは `#/body/2/content/0`、属性は `#/body/1/attrs/alt`）。ブロックでないものは、本文の位置（`#/body`）、取り除いたブロックは、それが入るはずだった列の位置。`legacy` にしたブロックについて、変換の途中に足した記録は、捨てる（`legacy` の記録のほかに、属性が不正なことと、ブロックが閉じていないことを記録する。`the block "core/paragraph" is not closed; it ends at the end of the content`）。空白の整理と、既定の値のままのものは、記録しない。例（`internal/wpimport/testdata/out-blocks/report.txt` の一部。ファイルの名前は、テストが決めた値）：

```text
blocks.xml:82:2: skipped: item 20 (post "テキストのブロック"): 1 page break is removed; whiteroom has no page breaks -> revisions/rev_0000000000JW4F4DHQTQQS04AF.json#/body
blocks.xml:82:2: changed: item 20 (post "テキストのブロック"): the heading level 1 is 2 here; h1 is for the title -> revisions/rev_0000000000JW4F4DHQTQQS04AF.json#/body/0
blocks.xml:261:2: review: item 22 (post "表"): the text has <img>, which rich text cannot have; it is a legacy block -> revisions/rev_00000000005DX2F6YZ7BS0EEWK.json#/body/2
```

**本文（クラシックエディタ）**

クラシックエディタ（TinyMCEの編集画面。WordPress 5.0より前の標準のエディタ）が書いたHTMLの本文と、ブロックのある本文のブロックの間のHTMLを、ブロックの列（6.5）にする。入口は、ブロックエディタの本文と同じ `Body`（上記）で、渡すものと返すものも同じ。この小節の規則は、どれも仮に決めたもの（案）。WordPress 7.1.4 が本文を表示するときの整形のうち、取り込みが要るもの（段落・ページ・ショートコードの見つけ方と属性・自動の埋め込みのURL・HTMLを部分に分けること）は、`internal/wpformat` で作り、HTMLをブロックにする部分は `internal/wpimport` に置く。

- 読むHTML：次のものを、クラシックのHTMLとして読む。
  - 本文に名前のあるブロックが1つも無いとき（区切りの無い本文）の、本文の全体。
  - ブロックのある本文の、ブロックの間のHTML（名前の無いブロック）と、クラシックのブロック（`core/freeform`）の中身。
  - ショートコードのブロック（`core/shortcode`）の中身。
  - 同期パターンの写しの、区切りの無い中身。
  - Elementorで作ったページは、本文を読まず、本文の全体を1つの `legacy` にする（下記の「ページビルダー」）。
- 段落を作るところ（WordPress 7.1.4 のソースで確かめた）：WordPressは、本文を表示するとき（`the_content` のフィルター）、埋め込み（優先度8。`[embed]` と、1行だけのURLの自動の埋め込み）→ブロックの描画（9）→ `wpautop` と `shortcode_unautop`（10）→ `do_shortcode`（11）の順に整形する。ブロックの描画は、本文に `<!-- wp:` があると、この表示から `wpautop` を外す（`has_blocks`。区切りの形は確かめない）。そのため、段落を作るのは、本文に `<!-- wp:` が無いときの本文の全体（ページごと）と、`core/shortcode` の中身（そのブロックの表示が、中身に `wpautop` をかける）だけにする。ブロックの間のHTMLと、`core/freeform` の中身（描画を持たず、書かれたまま出る）と、同期パターンの中身（その表示は、中身に `[embed]` と自動の埋め込みだけをかける）には作らない。`<!-- wp:Foo -->` のように、ブロックの区切りの形でないコメントが本文にあるときも、`wpautop` は外れるので、本文の全体を、段落を作らずに1つのHTMLとして読む。
- 段落の作り直し（`wpformat.Autop`）：WordPress 7.1.4 の `wpautop`（改行を `<br />` にする設定）と同じ文字列を作る。空行で `<p>` に分け、1つの改行は `<br />` にし、ブロックの要素（`div`・`ul`・`table`・`blockquote`・`h1`〜`h6`・`figure`・`style` など）の前後は段落にせず、`pre` の中は触らず、タグやコメントの中の改行は `<br />` にしない。時間は入力の長さに比例する（7.1.4 の `wpautop` は、長い空白の連なりなどで、長さの2乗に比例する時間がかかり、20万バイトの空白の連なりで約9秒かかった。開発シェルのPHPで測った）。違うのは、本文に `wpautop` が `pre` の中身を預ける置き場所の文字（`wp-pre-tag-` で始まる属性）があるときと、PHPの正規表現が上限で失敗する長い入力のときだけ。表示のときのほかの整形（`wptexturize` の引用符・ダッシュ・三点リーダー、`convert_smilies` の絵文字、`capital_P_dangit` の `Wordpress` → `WordPress`、画像の属性（`srcset`・`loading`）の追加など）は再現せず、書いたままの文字を取り込む（ブロックエディタの本文と同じ。6.12の221）。
- ページ：WordPressは、本文を `<!--nextpage-->` で分けたページごとに整形する。区切りの無い本文は、`wpformat.SplitPages` で、WordPressと同じに分ける（`<!--nextpage-->` の前後の改行を、WordPressと同じに取り除き、ブロックの `<!-- wp:nextpage -->` の区切りを取り除き、本文の先頭の `<!--nextpage-->` は数えない）。ページの数から1を引いた数を、改ページの数に足す（本文ごとに1つの記録。上記の「改ページと「続きを読む」」）。ブロックの間のHTMLとクラシックのブロックの中の `<!--nextpage-->` のコメントも、数えて取り除く。同期パターンの写しの中のものは、数えない。
- 続きを読む：WordPressは、ページの最初の `<!--more-->`（`<!--more 文字-->` の形もある。改行を含まないコメント）の前を、抜粋の位置にする。クラシックのHTMLでも、ブロックの「続きを読む」と同じに、本文の最上位にある最初の印の位置を、その前にある最上位のブロックの数で返す。段落の中の、`br` で区切った行が印だけなら、その行の前後で段落を分けて、そこを位置にする。文字もある行の印は、その行の後ろを位置にする（行は分けず、行の文字は印の前に数える）。入れ物（`group`・`quote` など）や、見出し・リスト・表・文中の要素の中の印は、位置にせず、取り除いて記録する（`the more tag is removed: it is not at the top of the content`。skipped。6.12の227）。2つ目からと、同期パターンの写しの中の印（WordPressは、投稿の本文だけで抜粋を分ける）は、記録せずに取り除く。位置にした印の `<!--more 文字-->` の文字（`the text "続きを読む" of the more link is not imported`。skipped）と、本文のどこかにある `<!--noteaser-->`（`the more tag hid the text before it on the page (<!--noteaser-->); whiteroom shows it`。changed）は、本文の位置に記録する。
- 読む順：HTMLは、次の順に読む。
  - (1) ページに分ける（区切りの無い本文だけ）。
  - (2) ページごとに、`[embed]` と、1行だけのURLを、要素に置き換える（WordPressが、段落を作る前に埋め込むため）。
  - (3) 8MiB以下の部分に分ける（下記の「大きなHTML」）。
  - (4) 段落を作る本文だけ、部分ごとに `Autop` をかける。
  - (5) ほかのショートコードを、要素に置き換える（WordPressが、段落を作った後に動かすため）。
  - (6) 結果をまた8MiB以下の部分に分け、部分ごとに `internal/html` で読んで（`div` の中身として）、要素ごとに変換する。
  - ショートコードとURLは、読む間、本文の要素と名前が重ならない要素で置き換え、段落の行や文の中での位置を保つ。`legacy` の `html` と、記録の文には、元の文字に戻す。タグ・コメント・CDATAの中と、HTMLの構文解析が文字として読む要素（`script`・`style`・`textarea`・`title`・`xmp`・`iframe`・`noembed`・`noframes`・`noscript`・`plaintext`）の中のものは、置き換えずに文字のままにする（6.12の223）。置き換えた要素が、タグの一部や文字として読まれたときは、その部分のショートコードとURLを文字のままにして、記録する（`the shortcodes and URLs in a part of the HTML of the classic editor are left as text: the HTML around them is not made of elements`。review）。本文の要素に、置き換える要素の名前が、すべて使われているときも、文字のままにして記録する（`the shortcodes and URLs of the HTML of the classic editor are left as text: it has elements of all the names that stand for them`。review）。
- 要素ごとの変換：流れ（ブロックの列）の直下にある要素を、次のとおりにする。ブロックの要素の外の文字と文中の要素は、続く間、1つの段落にまとめる。

| HTMLの要素 | このCMS |
| --- | --- |
| `p` | `paragraph`（下記の「段落」） |
| `h1`〜`h6` | `heading`。`h1` は `h2` にして記録する（`the heading level 1 is 2 here; h1 is for the title`）。複数行で書いた見出しの終わりの改行（`wpautop` が残す）は捨てる。文字の無い見出しは、取り除いて記録する（`the empty heading is removed`） |
| `ul`・`ol` | `list`。項目は、ブロックエディタの本文の古い形のリストと同じに読む。`start` を取り込み、`reversed`・`type` は記録する。入れ子のリストの後ろに文字や要素がある項目があれば、順序が変わるので、リスト全体を `legacy` にする（`a list item has content after its list`。review） |
| `blockquote` | `quote`。中身を同じ規則で変換する。出典は、子の `cite`（`wpautop` が `<p>` で包んだ、最後の `cite` も）の文字 |
| `table` | `table`。`core/table` と同じに読み（`thead`・`tbody`・`tfoot`、`th`、`colspan`・`rowspan`）、セルの文字揃えは、`data-align`、`has-text-align-` のクラス、`style` の `text-align`、`align` の属性の順に読む。`caption` の要素は、キャプション |
| `pre` | `code`。文字は書かれたまま。言語は、`language-<名前>` のクラスから（子が `code` だけなら、`code` のクラス。無ければ `pre` のクラス） |
| `hr` | `separator` |
| `div`・`section`・`article`・`aside`・`header`・`footer`・`main`・`nav`・`center` | `group`。中身を同じ規則で変換する。`tagName` は `section`・`article`・`aside` だけで、ほかは `div` にして記録する（`the group's <main> is a <div> here`）。中身が空なら取り除いて記録する（`the empty group is removed`） |
| `details` | `summary` の文字を `label` にした `group`。いつも開く（`the details block is a group here, always open; whiteroom has no details blocks yet (stage 2)`。changed） |
| `figure` | キャプション付きの `image`、または `table`（下記の「`figure`」） |
| `iframe` | `src` が `youtube`・`vimeo`・`googleMaps` の許可リストに合えば `embed`（`the iframe is an embed block here`。changed）。`//` で始まる `src` は `https:` を、`http://` は `https://` に直してから合わせる。合わなければ、そのiframeの `legacy`（`the iframe cannot be embedded: not a URL that a provider can embed`。review） |
| `script`・`style`・`template`・`noscript`・`title`・`noembed`・`noframes` | 中身ごと取り除いて記録する（`removed <script> with their content`。skipped） |
| `address`・`dl`・`dt`・`dd`・`fieldset`・`form`・`li`・`object`・`video`・`audio` など、ブロックにできない要素と、SVG・MathMLの要素 | その要素の `legacy`（`the element <dl> is not converted`。review）。`allowHtml` によらず、`html` にはしない |
| ほかの要素（`a`・`strong`・`em`・`span`・`img`・`br` など）と文字 | 段落の文中装飾 |

- 段落：`p` の中身を、`br` で区切った行に分けて読む（`wpautop` が、1つの改行を `<br />` にするため）。
  - 画像（`img`、または `img` だけを囲む `a`）だけの行は `image` にする。行の初めか終わりにある画像（空白とNBSPだけの文字をはさんでもよい）も `image` にして、行の文字の前か後ろに置く（段落は、そこで分かれる）。行の途中に画像がある段落は、`p` 全体を `legacy` にする（`the text has <img>, which rich text cannot have`。ブロックエディタの本文と同じ。6.12の194）。`img` の `alt` などの読み方は、下記の「画像」。
  - `iframe` だけの行は、上の表のとおり `embed`（か `legacy`）にする。ショートコード1つだけの行と、1つのURLだけの行は、それだけのブロックにする（下記の「ショートコード」「URLだけの行」）。`<!--more-->` だけの行は、続きを読むの印にする。
  - ほかの行は、続く行を `hardBreak` でつないで、1つの `paragraph` にする。文字を、ブロックエディタの本文と同じ規則（上記の「文中装飾」）で読み、文字の無い段落は作らない（`<p>&nbsp;</p>` は、NBSPの段落になる）。
  - `text-align`（無ければ `align` の属性）が `left`・`center`・`right` なら、`textAlign` にする。
- 画像：ブロックエディタの本文の `core/image` と同じに読む。取り込んだ添付ファイルの画像（クラス `wp-image-<数>`、無ければ `src` のファイルで探す）だけが `image` になり、ほかの画像（ほかのホストの画像、WXRに無い旧サイトの画像、`data:` の画像）は、その画像（と、囲む `a`）のHTMLの `legacy` にして、要確認にする（`the image is not an imported attachment`。取り込みでダウンロードして取り込むことはしない。6.12の99）。`alt` は `img` の `alt`、囲む `a` は `link`、`size` は `img` の最初の `size-<名前>` のクラス（無ければ `figure` のもの）を `blocks.imageSizes` で変えたもの。`align` は、`img` の `alignleft`・`aligncenter`・`alignright` のクラス（`alignnone` は指定なし）、`figure` のクラス、`[caption]` の `align`、段落の `text-align` の順で、最初にあるもの（文字のある段落の画像にも、段落の配置を渡す）。`title` は取り込まず記録する（`lost title of <img>; whiteroom has no such settings`）。`width`・`height` は、ファイルが持つ大きさなので、黙って捨てる。
- `figure`：画像の単位1つ（`img`、または `img` だけを囲む `a`。`wpautop` が包んだ `p` の中でもよい）か表1つと、子の `figcaption` 1つのほかに、空白・改行（`br`）・コメント・空の `p` しか持たないときだけ、キャプション付きの `image` か `table` にする（`figcaption` は `caption`。表に `caption` の要素があって `figcaption` が無いときは、その `caption`）。ほかの中身（2枚目の画像・文字・段落・入れ子の要素・2つ目の表・貼ったギャラリーのHTML・2つ目の `figcaption`・表の `caption` と `figcaption` の両方）があれば、中身を失わないよう、`figure` 全体の `legacy` にする（`the element <figure> is not converted`。review）。`figure` の `align*` と `size-` のクラスは、画像に使う。
- 見た目と class と `id`：クラシックの要素だけに、次の規則をかける（ブロックエディタのブロックは、上記の「見た目」のとおり、属性から読む）。
  - `p`・`h1`〜`h6`・`td`・`th` の `style` の `text-align`（無ければ `align` の属性）が `left`・`center`・`right` なら `textAlign`。段落の配置が、どのブロックにも渡らなかったとき（`iframe`・`[gallery]`・`[caption]`・埋め込みのURLだけの段落、取り込めない画像だけの段落など）は、記録する（`lost style.text-align of <p>; whiteroom has no such settings`。属性の `align` なら `lost align of <p>; …`）。段落と同じ配置の画像（中央揃えの段落の `aligncenter` の画像）は、配置を失わないので、記録しない。
  - ほかの `style` の項目と、古い見た目の属性（`align`（`textAlign` にしたもの以外）・`background`・`bgcolor`・`border`・`cellpadding`・`cellspacing`・`color`・`face`・`height`・`hspace`・`size`・`valign`・`vspace`・`width`）は、取り込まず、要素ごとに名前を並べて1つの記録にする（`lost style.padding-left of <p>; whiteroom has no such settings`、`lost border, width, cellpadding of <table>; …`。skipped。10個まで、残りは `, and <数> more`）。リストの項目（`li`）と、表の行・セルの `style`・class（WordPressのクラスを除く）・`id` も、消えるので、リストと表ごとに1つにまとめて記録する（`lost style.color, class, id of <ul>; …`。`figure` の中の表は `of <figure>`）。
  - class：WordPressがクラシックの要素に付けるクラス（`alignleft`・`aligncenter`・`alignright`・`alignnone`、`size-`・`wp-`・`attachment-` で始まるもの）は、画像の配置・サイズ・メディアを決めるのに使い、`className` にしない。ほかのクラスは、ブロックエディタの本文と同じく、最初の1つを `className` にし、ほかは記録して捨てる（`the class "second" is not imported: whiteroom blocks have one class name`。6.12の11）。`figure` のクラスは、画像の `className` の前に並べる。
  - `id`：ブロックの最初の要素の `id` を `anchor` にする。名前の規則に合わないものと、ほかのブロックが先に使っているものは、取り込まずに記録する（ブロックエディタの本文と同じ文。6.12の12）。
- ページ内リンクの飛び先：クラシックのHTMLの、`href` の無い `a` の `id`（無ければ `name`）は、その `a` を含むブロックの `anchor` にする（見出し・段落・画像・引用の出典など。リストと表は、項目やセルの中のものも、そのリストか表の `anchor`）。`a` の文字は、そのまま残る（`kept only the text of <a>` は付かない）。文字の無い `a` だけの行と、ブロックを作らない要素（空の見出しなど。空で消える `group` の中のものも）にある飛び先は、同じ流れで次に作るブロック（`legacy`・`group`・`quote` も）の `anchor` にする。`id` と `name` が違うときは `id` を使い、`name` は記録する（`the anchor "n" is not imported: the element has the id "i"`。skipped）。付けられないものは、取り込まずに記録する（skipped）：ブロックが自分の `id` の `anchor` や、先に付いた `anchor` を持つとき `the anchor "old-chapter2" is not imported: the block has the anchor "chapter2"`、同じ名前がほかのブロックにあるとき `the anchor "section" is not imported: another block has it`、名前の規則に合わないとき `the anchor "x" is not imported: invalid name "x": use ASCII letters, digits, "-" and "_"`（この2つはブロックエディタの本文と同じ文）、次のブロックが無いとき `the anchor "x" is not imported: no block comes after it`。1つの本文で読む飛び先は4万個まで（ショートコードとURLの数と同じ。超えた分は、取り込まず、`kept only the text of <a>` を付けて文字だけを残す。記録は、上記の表の「ページ内リンクの飛び先」の行。skipped）。変えないもの：`href` のある `a` の `id`・`name`、`details` の `summary` と `pre` の中の `a`、`span` などの `id`、ブロックエディタのブロックの `a`（6.12の228）。`#名前` のリンク（上記の「リンク」）は、この飛び先を指せる。
- 文中の装飾：ブロックエディタの本文と同じ規則（上記の「文中装飾」）で読み、`span` の `style` の次の項目も読む（ブロックエディタの本文の `span` も同じ。TinyMCEがこの形で書くため）。`text-decoration` が `underline` なら `underline`、`line-through` なら `strike`、`font-weight` が `bold`・`bolder`・600〜900なら `bold`、`font-style` が `italic`・`oblique` なら `italic`、`color`・`background-color`（透明は除き、色の規則（6.5.3）に合うもの）は `highlight` の色。クラシックのHTMLでは、マークにならなかった `style` の項目を、文字を読むごと（段落・見出し・セル・リストの項目など）に、要素の名前ごとにまとめて記録する（`lost style.font-size of <span>; whiteroom has no such settings`。skipped。1つの文字で、名前は100まで、1つの名前の項目も100までを保つ）。色の規則に合わない色（`red` など）は、マークにならないので、記録される。`center` は、文中でも `div` と同じく前後の文字と行を分ける。`a` の `href` に、ショートコードの形（登録名か、小文字の名前の形）があれば、リンクは書かれたままのアドレスから作り、記録する（`the address "[home_url]/about/" has a shortcode, which whiteroom does not run`。review。6.12の223）。
- `legacy`：変換できない要素は、その要素1つの `legacy` にする（ブロックエディタのように、区切りから閉じる区切りまでではない）。`html` は、段落を作った後のHTMLを、構文木から書き出したもので、元の文字ではない。理由は、上記の表のほか、`the text has <img>, which rich text cannot have`・`the image is not an imported attachment`・`a list item has content after its list`・`the element <figure> is not converted`・ショートコードの理由（下記）で、どれも要確認として、`; it is a legacy block` を付けて記録する（上記の「`legacy`」）。入れ物（`group`・`quote`・`details`）の入れ子が32段を超える要素は `legacy`（`the blocks are nested more than 32 deep`）、HTMLの入れ子が深すぎて `internal/html` が読めない部分は、その部分の `legacy`（`the HTML of the classic editor is too complex to read`）にする。`legacy` の `html` が1MiBを超えるときは、作らずに記録する（`the element <p> is not imported: its HTML is too long: <バイト数> bytes (max 1048576)`。skipped。`data:` の画像を貼った段落など。6.12の24）。
  - 手直し：`legacy` の `html` に書く、リンク（`a` の `href`）・画像（`img` の `src`）・引用元（`blockquote`・`q`・`del`・`ins` の `cite`）のうち、スキームの無い相対のURLと、`//` で始まるURLは、項目の `link` を基に、絶対のURLにする（描画のサニタイズ（6.5.4）が、相対URLを取り除くため。`/` で始まるパスと、`#` で始まるものは、そのまま）。基にするURLの長さは、リンクと同じに、読むHTMLに数える（上記の「リンクのアドレス」）。`data:` の画像は、そのまま残す（描画が取り除き、描画の警告に出る）。ブロックエディタの `legacy` の `html` は、元の文字のままで、直さない（6.12の100）。
- ショートコード：クラシックのHTMLの中のものは、`wpformat.FindShortcodes`（WordPressの `do_shortcode` と同じ見つけ方。閉じるタグの探し方、`[[foo]]` の書き方、要素の中の角かっこを数えないことも）で見つけ、属性は `wpformat.ParseAttrs`（`shortcode_parse_atts` と同じ読み方。1MiBを超える属性は読まない）で読む。
  - 見分け方：WordPressは、登録された名前のショートコードだけを動かし、ほかは書いたままの文字で表示するが、旧サイトで登録されていた名前（プラグインのもの）は、WXRに無い。そこで、`[` の直後の名前（英数字・`_`・`-` の連なり）が、次のどちらかのとき、ショートコードとみなす。(1) WordPress本体とContact Form 7 の名前（`audio`・`caption`・`contact-form`・`contact-form-7`・`embed`・`gallery`・`playlist`・`video`・`wp_caption`）と一致するとき（直後に何が続いてもよい。6.12の222）。(2) 英小文字で始まり、英小文字・数字・`_`・`-` が続き、直後が空白・`]`・`/`・`<` のとき（`<` は、`wpautop` が改行の前に置く `<br />`）。`[PR]`・`[1]`・`[注1]`・`[a.b]` は、書いたままの文字にする。この形に合う文字（`[sic]` など）は、ショートコードとして扱う（6.12の222）。`[[foo]]` は、`[foo]` の文字にする（記録しない）。`pre` と `code` の要素の中（開始タグから終了タグの間）では、WordPressとContact Form 7 の名前だけをショートコードとみなし（ほかと同じに扱う）、ほかの `a[i]` は、文字のままにする（`legacy` にも、記録にもしない。`[[i]]` も書かれたまま）。ブロックエディタの本文の文字の中の `code` の要素の中も同じ。
  - 単独のもの：ブロックの間にあるものと、段落の中で1行だけのものは、それだけのブロックにする（変換しないものの `legacy` の `html` は、そのショートコードの文字。段落をまたぐ中身も含む）。
    - `[caption]`・`[wp_caption]`：中身の最初の `img`（直前の `a` を含む）を `image` にし、画像より後ろの内容（`a` の中の文字も）をキャプションにする。画像より前の文字は、WordPressが表示しないので捨てる。`caption` の属性があるときは、その値のHTMLがキャプションになる（WordPressは、中身を全部出すので、画像のほかに内容があれば、そのショートコードの `legacy`。`the shortcode [caption] has the attribute caption and content other than the image`）。`width` が1より小さいか、キャプションが空なら、画像だけにする（WordPressも同じ）。`id` の `attachment_<数>` は添付ファイル、`align`（`alignleft`・`aligncenter`・`alignright`）は画像の `align`、`class` は画像のクラスの前に足す。画像が無ければ `legacy`（`the caption has no image`）、取り込んだ画像でなければ、そのショートコードの `legacy`（画像の理由）。
    - `[gallery]`：`ids`（無ければ `include`）の添付ファイルを、その順に。どちらも無ければ、`id`（無ければ、その投稿）の子の添付ファイルを、`menu_order`・IDの順に（`exclude` は除く）。`order` が `DESC` なら、逆の順。`orderby` は、`menu_order`・`ID`・`post__in` だけを読み、ほかの値（`rand` など）は、読まずに記録する。`image` の列にする（ギャラリーは段階2のブロックなので。`the gallery is 2 images here; whiteroom has no gallery blocks yet (stage 2)`。changed。6.12の193）。`size` は `blocks.imageSizes` で変える（無ければ `thumbnail`）。リンクは、`link` が `none` のとき以外、メディアへ（WordPressの既定の、添付ファイルのページは無いので）。キャプションは、添付ファイルの抜粋（文中装飾にできるとき）。`columns` と、読まなかった `orderby` は、取り込まずに記録する（`lost columns of the shortcode [gallery]; whiteroom has no such settings`）。取り込んだ画像でない添付ファイルは外す（PDFなど、画像でないものは、WordPressも出さないので、黙って外す。WXRに無いものと、取り込まなかったものは、記録して外す。`the image 999 of the gallery is not imported: it is not an imported image`。skipped）。画像が1つも残らなければ、取り除いて記録する（`the empty gallery is removed`）。
    - `[embed]`：中身（無ければ `src` の属性）のURLを、「URLだけの行」（下記）と同じ許可リストに合わせ、合えば `embed`、合わなければ `legacy`（`the URL cannot be embedded: not a URL that a provider can embed`）にする。`width`・`height` は、取り込まずに記録する。
    - `[contact-form-7 id="…" title="…"]`：`id` が7桁以上の小文字の16進数（Contact Form 7 6.2.4.1 と同じ）なら、フォームの `_hash` の先頭と比べ、ほかは、投稿ID、最後に `title` の順に、フォームを探して、取り込んだフォームを参照する `form` にする（ブロックエディタの `contact-form-7/contact-form-selector` と同じ探し方。上記の「参照」）。`[contact-form 123 "…"]`（Contact Form 7 4より前の書き方）は、最初の属性の数を、フォームの `_old_cf7_unit_id` で探す。見つからないフォームと、取り込んでいないフォームは、`legacy`（`the form "取り込まないフォーム" is not imported`）にする。フォームの見せ方を決める `html_id`・`html_name`・`html_title`・`html_class` と、`form` でない `output` は、取り込まずに記録する（`lost html_class of the shortcode [contact-form-7]; whiteroom has no such settings`。6.12の25）。
    - `[video]`・`[audio]`・`[playlist]`：`legacy`（`whiteroom has no video blocks yet (stage 2)`・`whiteroom has no audio blocks yet (stage 2)`・`whiteroom has no playlist blocks`）。ほかの名前も `legacy`（`the shortcode [box] is not converted`）。どれも要確認。対応表は6.12の191。
  - 文の中のもの：行に、ほかの文字もあるものと、リストの項目・表のセル・見出しの中のものは、それを含むブロック（リストと表は全体）を `legacy` にして、書いたままの文字で表示し、確かめてもらう（`the text has the shortcode [price], which whiteroom does not run`。2つ以上は `the text has the shortcodes [foo], [bar], which whiteroom does not run`。名前は10個まで、残りは `, and <数> more`。review）。
  - ブロックエディタの本文の文字の中のもの：段落・見出し・リスト・表などの文字の中のショートコードも、同じ見分け方で探し（WordPressは、本文の全体から探すため）、見つけたものを含むブロックを `legacy` にする。段落ブロックの中身が1つのショートコードだけのときは、単独のものと同じに変換する（段落の設定のうち、ブロックにできないものは記録する。`lost anchor, fontSize of the block "core/paragraph"; whiteroom has no such settings`）。`&lt;` を解いた `<` は、要素の始まりとみなさない。`&#91;` を解いた `[` は、ショートコードの始まりとみなす（WordPressは文字として表示するので、違う。6.12の222）。
  - 上限：ショートコードとURLの数と、ショートコードの属性の大きさは、上記の「上限」の表のとおり。超えた分は文字のままにし、属性が上限を超えたショートコードは、読まずに取り込まない。
- URLだけの行：WordPressの自動の埋め込みは、URLだけの行と、URLだけの段落（`<p>URL</p>`）を、埋め込みの対象として試し、埋め込めなければ、リンクにせず、URLの文字のまま表示する。`wpformat.AutoembedURLs` が、対象のURLを同じに見つける（`http://`・`https://` で始まり、空白・`<`・`>`・`"` の前まで続くもので、前後が行の端か空白。要素の中の改行は、行の端にならない）。`youtube`・`vimeo`・`x` の許可リストに合うURLだけを `embed` にする（段落の中の行なら、段落を分ける。記録しない）。WordPressは `http://` のURLも埋め込むので、`http://`（大文字と小文字は問わない）で始まるものは、`https://` にして合わせ、`https://` の形で `embed` にする（クラシックのiframeも同じ。`core/html` の、`//` で始まる `src` を `https:` にするのと同じ考え）。合わないURLは、文字のまま段落に残し、要確認として、その段落に記録する（`the URL "https://example.org/some/page" on its own line is text here; WordPress may have shown it as an embed, and whiteroom embeds only YouTube, Vimeo and X`）。許可リストの外の提供元は、WordPressが埋め込んだかもしれない（提供元が多く、旧サイトの設定にもよる）ので、確かめてもらう（6.12の224）。ブロックエディタの段落ブロックで、中身がURLの文字だけのものも同じ。リストの項目・表のセル・見出しの中の行のURLは、埋め込めるものも、文字のままで、同じ記録をそのブロックに付ける。
- ページビルダー：postmetaの `_elementor_edit_mode` が、空でも `"0"` でもない項目（Elementorで作ったページ）は、本文を変換せず、本文の全体を1つの `legacy` にして、要確認にする（理由は `the page was made with Elementor, which showed its own data in place of the content`。1MiBを超える本文は、取り込まずに記録する）。Elementorは、そのページを表示するとき、自分のデータから作った内容を、本文の代わりに出すので（`is_built_with_elementor` と `apply_builder_in_content` で確かめた）、本文のHTMLは、旧サイトに表示されていたものとは限らない。推測の段階も、そのページの本文は読まない。ショートコードで書くページビルダー（WPBakeryの `[vc_row]`、Diviの `[et_pb_section]` など）は、postmetaで見分けず、ショートコードの規則で、ショートコードごとの `legacy` になる。ほかのページビルダーの見分け方は、まだ無い（6.12の225）。
- 守り（検証）：変換が作ったブロックの列は、ブロックエディタの本文と同じに、検証にかける（上記の「守り（検証）」）。クラシックの要素から作ったブロックが通らないときは、そのブロックを含む、ブロックの流れの中の1つを、その要素（ショートコードやURLから作ったものは、そのショートコードかURL）のHTMLの `legacy` に置き換える（理由は `the conversion does not pass validation: …`。要確認）。本文の全体や、ブロックの間のHTMLの全体の `legacy` にはならない。入れ物（`group`・`quote`）そのものが通らないときは、取り込まずに記録する。
- 大きなHTML：構文木は、HTMLの約50〜70倍のメモリを使い、`wpautop` は、閉じていないタグの中に改行が並ぶ入力で、途中の文字列を約16倍の長さにする。そこで、クラシックのHTMLは、いつも8MiB（1つのブロックのHTMLの上限と同じ）以下の部分に分けて読み、`Autop` に渡す文字列も、8MiB以下にする。
  - 分け方（`wpformat.SplitBlocks`）：ページ（ブロックの間のHTMLと、クラシックのブロックと、`core/shortcode` の中身も）が8MiBを超えるときは、段落を作る前に、ブロックの要素の外の改行の後ろで、8MiB以下の部分に分ける。`div`・`ul`・`table`・`pre`・`script` などの要素が開いている間と、タグ・コメントの中では、分けない。部分ごとに `Autop` をかけ、その結果が8MiBを超えるなら、もう一度同じに分けてから、読む。読むのは、いつも1つの部分の構文木だけ。
  - 分けられない部分（改行の無い8MiBを超える行や、8MiBを超える要素）は、`Autop` にかけず、読まずに、取り込まないものとして記録する（記録の文は、上記の表の「クラシックのHTMLの1つの部分」の行）。
  - WordPressと違うのは、8MiBを超えるページの、分けた所だけ。分けた所の1つの改行は、`<br />` ではなく、段落の区切りになる（6.12の226）。
  - 読んだ部分のバイトは、読むHTMLの64MiBに数え、作ったブロックは、変換するブロックの4万に数える。
- 上限：上記の「上限」の表のとおり。ブロックエディタの本文と同じ数え方（変換するブロックと読むHTMLは、同期パターンの写しを含めて、本文ごとに数える）で、次を足す。
  - 数えるもの：変換した要素ごと（段落・見出し・リスト・表・画像・`legacy` など）と、リストの項目と表の行とセルの部品、`[gallery]` の画像を、1つずつ数える。ブロックを作らない要素（文字の無い見出しなど）と、文字が空で作らない段落の行（`script` だけの段落、空の `span` だけの段落、文字の無い `a` だけの行）も数える。作らないものにも記録が付くので、数えないと、本文の大きさに比例して、記録が増える。超えたら、そこから後を取り込まずに記録する（上記の表の「変換するブロックと、読むHTML」の行）。作らない段落が残す、本文に出ない記録は、捨てる。
  - ショートコードとURL、ショートコードの属性、ページ内リンクの飛び先：それぞれ上記のとおり（4万個、1MiB、4万個）。
  - 時間：`Autop`・`SplitPages`・`SplitBlocks`・`FindShortcodes`・`ParseAttrs`・`AutoembedURLs` は、入力の長さに比例する。
- メモリ：1つの部分の構文木の大きさで決まるのは、ブロックエディタの本文と同じ。部分に分けるので、木はいつも1つ分（8MiB以下）で、`Autop` に渡す文字列も8MiB以下になる。ショートコードとURLは、読む間、全文を本文の終わりまで持つので、ショートコードの多い本文で増える。測った最悪（`[a]` と `[/a]` の間に、`a` と改行を並べた約8MiBの部分を8つ並べた本文）は、最大RSSが約1.2GB、7.8秒で、測った14の形（本文は64MiBほど）のどれも、これを超えず、13秒以内だった。
- 測った値の条件：`internal/wpimport` のテストのバイナリ（`go test -c`。`-race` なし。`GOGC` と `GOMEMLIMIT` は設定しない）で、形ごとに別のプロセスを動かし、GNU time の最大RSS（入力の文字列を含む）と時間を測った。メモリの上限（`systemd-run` の `MemoryMax=12G`）の下で測り、どれも上限に近づかなかった。マシンは3.5の「ベンチマークの条件」と同じで、ほかのプロセスも動いていた（負荷は4〜10）ので、時間は長めに出る。測った値は1回ずつの値で、構文木を持つ形は、回収の時期で、最大RSSが1.6倍ほど変わることがある。
- 記録：ブロックエディタの本文と同じ形（上記の「記録」）。行き先は、ブロックの位置、本文の位置（`#/body`）、取り除いた要素が入るはずだった列の位置。クラシックの見本（`internal/wpimport/testdata/out-classic/report.txt`）の一部（ファイルの名前は、テストが決めた値）：

**取り込みレポート**

- 種類：取り込まなかった（`skipped`）・変えた（`changed`）・要確認（`review`）。取り込まなかったものは `skipped`、取り込んだが変えたもの（タグを除いた説明、置き換えた名前、取り除いた文字など）は `changed`、取り込んだが確かめてほしいもの（`legacy` にしたもの、推測した規則、翻訳が要るものなど）は `review` にする。どれにするかは、それぞれの変換が決める。
- 1つの記録：何を（`source`：WXRのファイル・行・列、レコード（`channel`・`author`・`term`・`item`。REST APIの値は `rest` で、ファイルはスナップショットの名前、行と列は無い）、WordPressのID、投稿タイプかタクソノミー、名前（投稿者はログイン名、タームは名前、項目はタイトル。REST APIの投稿者とタームは名前、経路はその経路。メールアドレスの形のログイン名と、`wp:author_email` と同じログイン名は書かず、IDで示し、IDが無ければ、ログイン名から作ったスラッグを書く。REST APIの投稿者の名前がメールアドレスの形なら、書かない。案）、メタデータのキー）、どうしたか（`kind` と、英語の文 `message`）、どこへ（`target`：サイトのディレクトリの中のファイルと、その中のJSON Pointer）を持つ。`target` は、変換が足す（ターム・著者プロフィール・サイト設定・メディア・本文の変換が足す。ほかの変換は、まだ無い）。
- JSON：`wxr`（WXRのファイルの名前・版・WordPressの版・サイトのURL（チャンネルの `link`））と、`entries`（記録の列）を持つ。2つの空白で字下げし、末尾に改行を付ける。`kind` と `message` は常に書き、空の項目は省く。記録が無ければ `"entries": []`。例（`internal/wxr/testdata/wordpress-6.xml` を読んだときのもの）：

```json
{
  "wxr": {
    "file": "wordpress-6.xml",
    "version": "1.2",
    "wordpress": "6.8.3",
    "site": "https://example.com"
  },
  "entries": [
    {
      "kind": "skipped",
      "source": {
        "file": "wordpress-6.xml",
        "line": 12,
        "column": 1,
        "record": "channel"
      },
      "message": "2 comments on 1 item are not imported; whiteroom has no comments"
    }
  ]
}
```

- テキスト：1行に1つで、ビルドの警告（4.3の「エラーと警告」）と同じく、位置で始める。`<ファイル>:<行>:<列>: <種類>: <何を>: <文>` で、行き先があれば、最後に ` -> <ファイル>#<JSON Pointer>` を付ける。`<何を>` は、`channel`・`author "admin"`・`author 3`（ログイン名を出さない投稿者）・`term 12 (category "News")`・`item 45 (post "Hello")` のようにレコードを示し、メタデータのキーがあれば、`postmeta "_mail"`（タームは `termmeta`）を続ける。名前は `"` で囲み、`"` や改行は `\"`・`\n` と書くので、1行に収まる。投稿タイプとタクソノミーも、WordPressが許す文字（英小文字・数字・`_`・`-`）だけでなければ、同じく `"` で囲む（`item 55 ("my type")`。ふつうの `post`・`post_tag` などは囲まない）。ファイル・行・列が無いときは、その部分を省く。例（コメントの付いた項目と、制御文字のある項目と、改行がCRLFだった `_mail` を持つフォームを含むWXRを読み、`_mail` を読んだときのもの）：

```text
wordpress.xml:2:1: skipped: channel: 2 comments on 1 item are not imported; whiteroom has no comments
wordpress.xml:7:10: changed: item 45 (post "Hello"): removed 2 characters that XML does not allow: U+0003 at 7:10, U+0003 at 7:14
wordpress.xml:17:1: changed: item 17 (wpcf7_contact_form "Contact") postmeta "_mail": read the serialized value by counting the LF line breaks in 1 string as CRLF (XML turns CRLF into LF); the line breaks are kept as LF
```

- REST APIの値：`rest` の記録の `<何を>` は、経路が `rest "/wp/v2/users"`、投稿者とタームが `rest 5 (user "Ghost")`・`rest 3 (category "News")`（ID、種類（`user` かタクソノミー）、名前）。投稿者の名前がメールアドレスの形なら、名前を書かない（`rest 5 (user)`）。ファイルは、スナップショットのファイルの名前（旧サイトから読んだときは、REST APIのルートのURL）。投稿者を返さなかった記録の例：`rest.json: review: rest "/wp/v2/users": the REST API did not give the users (401 rest_user_cannot_view); the slugs of the authors are made from their logins, and they have no bios or websites`。
- 変換の記録の例（見本のサイトの取り込み。`internal/wpimport/testdata/out/import.txt` の一部）：

```text

site.xml:24:2: skipped: author "writer": the website "javascript:alert(1)" is not imported: scheme "javascript" is not allowed -> authors/aut_0000000000XCC758X7YMPSJ3AK.json#/links
site.xml:33:2: changed: term 3 (category "お知らせ"): kept only the text of the HTML; lost a link to "https://example.com/", <strong> -> terms/trm_00000000009S0MYTEEWC021TN0.json#/description
```

- 並び：WXRの位置の順（ファイル・行・列・レコード・ID・種類・文・行き先の順に比べる。同じ位置のものは、取り込まなかったもの・変えたもの・要確認の順）。同じ記録からは、足した順によらず、同じ並びになる（4.3の「同じ入力から同じ出力」）。
- コメント：コメント（`wp:comment`）は、取り込まないので、数を、取り込み全体で1つの記録（`skipped`。位置は `<channel>`）にまとめる（`2 comments on 1 item are not imported; whiteroom has no comments`。1つのときは `1 comment on 1 item is not imported; whiteroom has no comments`）。
- 出し方：どこに出すか（標準エラーか、ファイルか）と、要確認があるときの終了コードは、コマンド（9.4。まだ無い）で決める。
